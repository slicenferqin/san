# 修 bug 的证据链

按证据链推进,不是按步骤清单打卡。每一环的产出物是下一环的输入;拿不到产出物就不进入下一环。

## 第一环:复现(产出物 = 一条可重跑的失败命令 + 失败输出)

在改任何代码之前,先让失败在你手里发生一次:

- 从用户描述提取线索(报错文本、操作路径、涉及的文件),把它变成一条**最小的可重跑命令**——一条失败的测试、一个触发报错的脚本、一次能观察到错误行为的构建/请求。
- 运行它,拿到**失败输出**(退出码非 0、断言差异、错误栈)。这条命令与输出就是证据 `repro`。
- 用户没给足信息时,优先从环境里自己找:搜报错文本、查最近改动(git log/diff)、跑现有测试套件缩小范围。实在复现不出来,如实报告你尝试过的命令与结果,向用户要缺失的输入——**不要在没有复现的情况下凭猜想改代码**。

产出物交给下一环:失败输出里的错误信息、栈、差异,就是定位的搜索起点。

## 第二环:定位(产出物 = 根因假设 + 代码位置)

- 拿第一环的错误栈/报错文本按图索骥:定位抛错点,沿调用链回溯到**根因**,不要停在最先看到的症状处。
- 产出物是一句可检验的根因描述("X 在条件 Y 下产生了 Z"),以及对应的文件与行号。
- 如果定位结论无法解释复现输出的全部现象,说明假设不完整,回到证据继续查,不要带着半个假设开工。

## 第三环:修复(产出物 = 针对根因的最小 diff)

- 只改根因要求改的地方。顺手的重构、无关的清理不属于本次修复。
- 修复要能用一句话对应到第二环的根因假设;对应不上就说明改错了地方。

## 第四环:复验(产出物 = 同一条命令的通过输出)

- 重跑**第一环同一条命令**(`sameAs: repro`),拿到通过输出。这是证据 `verify`。
- 禁止换一条更宽松的命令来宣称修好——换了命令,通过就不能证明原失败被消除。
- 如果复现命令是临时写的脚本/测试,评估它是否值得留下来当回归测试;有价值就落成正式测试。

## 第五环:回归面(产出物 = 影响范围的通过输出 + 交付说明)

- 跑改动影响面上的既有测试/构建/检查(如包内测试、类型检查),确认没有修好一处、弄坏三处。这是证据 `regression`。
- 交付说明按证据组织:根因是什么、改了哪里、`repro` 曾如何失败、`verify` 与 `regression` 如何通过。

## 禁止事项

- 没有失败的复现输出,不进入修复。
- 复验不与复现同命令,不算修好。
- 跳过回归面直接报告完成,不算完成。
- 复现不出来时,报告事实并提问,不编造"应该是修好了"。
