# 建站的证据链

模糊的建站需求("做个网站")最大的风险不是写不出代码,而是做出来的东西不是用户要的。所以第一环产出契约,后面每一环都对着契约交付。

## 第一环:需求契约回显(产出物 = 一段可确认的契约文本)

动工之前,把模糊需求翻译成一段**契约回显**发给用户,这是证据 `contract`:

- 一句话目标:这个站是给谁看/用的,解决什么事。
- 核心页面与功能清单:3~7 条,按"必须有"排序;明确本次**不做**什么。
- 技术选型与默认假设:框架/纯静态、数据存哪、部署到哪。用户没说的,选最简单能跑的默认并**写明**"未指定,默认采用 X"。
- 用户确认或未反对即视为契约生效;有异议就修订契约再动工。禁止跳过回显直接搭脚手架——契约就是后面所有环的验收标准。

产出物交给下一环:清单里"必须有"的第一条,决定骨架先搭什么。

## 第二环:骨架可启动(产出物 = 启动命令 + 无报错的启动输出)

- 建最小可运行骨架:项目脚手架、依赖清单、一条 dev server 启动命令。
- 运行启动命令,确认无报错、端口在听、根路径有响应。命令与输出是证据 `boot`。
- 骨架起不来之前不堆页面——后面每加一块都要能回到"启动成功"这个可验证状态。

## 第三环:核心路径可用(产出物 = 契约清单逐条可演示)

- 按契约清单逐条实现;每完成一条,验证一次:页面可访问、关键交互(表单提交、跳转、增删改查)真的完成。这是证据 `core-path`。
- 验证优先用可重复的方式:浏览器工具断言、curl 请求、能观察到结果的命令。目测截图只能作为补充。
- 发现契约定错了(做着发现走不通),回到第一环修订契约并告知用户,不要静默改需求。

## 第四环:交付说明(产出物 = 用户拿着就能用的说明)

交付说明是证据 `handoff`,对着契约写:

- 怎么启动:命令、地址、依赖前置(装什么、配什么)。
- 做了什么:契约清单逐条标注已实现/未实现,未实现的说明原因。
- 验证过什么:第二、三环的证据(启动输出、核心路径如何验证)。
- 下一步建议:最多 3 条,不展开做。

## 禁止事项

- 不回显契约直接开写。
- dev server 起不来就继续堆功能。
- 声称"完成"但核心路径没有逐条验证过。
- 静默替用户做重大选型变更而不写进契约。
