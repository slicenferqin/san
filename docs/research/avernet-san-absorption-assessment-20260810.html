01 · Identity

它到底是什么

准确分类：Avernet 是异构 Agent 的协作平面。类比上更接近“Agent registry + coordination service + session router + workbench”，而不是模型 SDK、推理框架或 coding harness。

它负责

  • Bot 身份、注册、能力描述与发现。
  • 群组、参与者、会话、关系与可见性。
  • @mention、广播和结构化路由。
  • 向异构运行时投递任务、注入上下文、取消、查询历史。
  • Web 工作台、Gateway、BaaS 与 Skills 发布/迁移。

它不主要负责

  • 不替代 Agent 自身的推理循环与工具调用。
  • 不自动拥有各运行时的完整会话历史；Provider/Engine 按 session_id 管理状态。
  • 不等于“多 Agent 一定更聪明”；它解决连接、路由、状态和治理。
  • BCS 可调用 LLM 插件做 Judge/协同决策，但这不是其主体定位。

公开组件

Agent RuntimeOpenClaw、自定义进程、既有 bot 平台
BCN / BCS注册、发现、路由、群组、协作状态
Gateway外部 API、鉴权、域路由
Backend / BaaSBot 服务、发布、运行时与容器生命周期
Workbench人机协作、管理与可视化

[观察] BCS 是 Rust 多 crate 微内核；Backend/BaaS 主要为 Python，另有前端与运行时集成。BCS 将 delivery adapter、service API、core/port、plugin API、plugin implementation 和 composition root 明确分层。

02 · Mechanics

真正值得看的五个机制

1. chat.send 与 chat.inject 是不同语义

chat.send 要求目标 bot 启动一次 run 并回复；chat.inject 只把上下文写入会话，不触发推理。这不是 API 命名细节，而是多 Agent 系统控制成本和避免“所有人都抢答”的关键边界。

对 San 最有价值：当前 hub send 给 idle agent 会启动真实 turn，给 parked agent 会先 revive；广播会触达所有 live peers。San 有“忙碌时 next-boundary aside”，却没有调用方可明确选择的“只观察、绝不启动 turn”操作。

2. 会话上下文是结构化字段，不只是一段 prompt

Avernet 下发 session_id、participants、originator、from、mentions、you_are_mentioned、is_sender 和 timeout。路由优先级为结构化 routing → 文本 @mention → 默认 driver 回复、其他成员观察。

San 的执行侧已有 scopeId / contractId / workKey / strategyKey / taskId，但内部 IrcMessage 目前只有 id / from / to / body / ts / replyTo。这形成一个明显断层：任务与账本是结构化的，Peer 消息仍是扁平文本。

3. 两种接入方式覆盖单进程与平台

方式适用对象传输状态归属
Plugin / Runtime单个本地 Agent 进程双向 WebSocket /ws/botAgent 进程持有会话，主动连接 BCS
Bot Provider托管多个 bot 的既有平台BCS webhook 下行 + /bot/events 异步回调Provider 按 (provider_bot_ref, session_id) 持有

Provider 协议要求版本、时间戳、认证、业务幂等键、统一错误码和一次 final。这个边界适合作为 San 未来外部 runtime adapter 的参考，但不应把 HTTP/WebSocket 细节直接写进 AgentSession。

4. API 规范、协议测试和 import 边界都是可执行约束

  • BCN 的 versioned OpenAPI 是权威源，当前文档列出 32 个协作操作，并提供 deterministic bundle/JSON 生成及兼容检查。
  • Microkernel Architecture Constitution 将规则分为 Invariant / Policy / Guideline；delivery 只能调 service API，core 不依赖 transport。
  • 每个边界模块的 README 声明 purpose / provides / consumes / internal_dependencies；测试把 internal_dependencies 当 import 白名单。
  • 每个 Plugin Protocol 必须有 consumer-level contract suite，并额外断言插件确实被调用，防止“测试通过但实现绕过了 adapter”。

5. 跨组件迁移使用窄 wire contract、版本锁定和 fail-closed

Skills Pool 不把引擎文件路径和 symlink 细节写入跨服务 manifest，只传 engine、active layout 和精确 contract version；未知版本拒绝 Pool publication，并以 quarantine、rollout audit、rollback 证据管理迁移。这种“冻结最小稳定语义、物理布局由末端拥有”的做法比复制其 Skills 平台本身更值得借鉴。

04 · San Mapping

San 已有的能力比表面上多，缺口集中在“协作语义”

维度AvernetSan 现状判断
产品职责 组织级异构 Agent 协作基础设施。 本地 coding-agent runtime、CLI、TUI 与执行控制。 互补，不是替代关系。
Agent 执行 主要把执行委托给接入 runtime/provider。 AgentSession + TaskTool 直接执行模型、工具、重试、预算、worktree。 San 无需吸收 BaaS 执行面。
发现 动态 bot registry；skills/domains/scopes；关系与可见性。 AgentDefinition 由 bundled/user/project/extension 文件发现；live AgentRegistry 是进程全局、平面命名空间。 远程 federation 前无需做能力市场。
Peer 消息 send 与 inject 分离；群组与结构化 session context。 hub send/wait/inbox/list；idle wake、park revive、busy aside；无显式 passive observe。 最明确的可补缺口。
执行身份 run/session/provider/bot IDs，业务请求幂等。 Task Contract v1 已有 scopeId/workKey/strategyKey/taskId/contractId 和重复 admission。 复用 San，不另造 ID 体系。
持久化与监督 注册、群组、会话与协作状态；不同路径 durable 程度不一。 append-only ExecutionLedger、CAS revision、不可逆 terminal state、DurableScheduler lease、Watchdog、session journal、park/revive。 San 执行闭环更贴合自身问题。
外部控制协议 Bot WebSocket + Provider HTTP callback。 RPC v2 已有 initialize/version、capabilities revision、session lease、run control、idempotency、event sequence、replay。 未来 bridge 应建在 RPC v2 之上。
多租户治理 Identity/Auth；权限、审计和安全处于不同开放阶段。 本地 approval、tool capability、host evidence；没有组织 RBAC/好友/群权限。 不是 San core 的当前目标。
架构守门 模块 import whitelist、协议 contract tests、OpenAPI 权威源。 RPC v2 已有 method catalog → schema/conformance，外部 ACP schema 验证；未见同等级的 coding-agent 模块依赖白名单。 选择性吸收边界测试。
核心判断：Avernet 不是给 San 提供“更好的执行器”；它提醒 San 把已经成熟的执行 scope/contract 与还比较原始的 peer messaging 接起来。

05 · Absorption Matrix

技术参考价值与最终取舍

候选能力适配度决定理由
Responder / Observer 分离中不单独推进语义合理，但没有证据表明它是 San 当前的关键瓶颈；有独立需求时再设计。
消息关联执行 scope 与 causation中不单独推进可复用 Task Contract / ExecutionLedger，但不因 Avernet 新增项目。
Adapter 行为契约套件中按需采用San 已有 RPC schema contract；只有新增外部 runtime adapter 时才扩展。
模块 Context Boundary中按需采用依赖边界测试是通用工程纪律，不需要从 Avernet 移植机制。
Plugin / Provider 双接入中作为扩展适合 San 接入外部 agent network，但不应污染 AgentSession 与核心工具。
动态 capability/domain registry中低需求后再做当前静态 agent description/tools/spawns 足够；无跨运行时池时只增加元数据税。
Skills Pool quarantine / rollout audit中借迁移思想适用于未来跨运行时 skill layout；当前不值得复制服务、表和运维面。
好友、社交关系、组织群组低不吸收San 的 agent 是任务执行者，不是长期社交主体。
Web Workbench / Canvas / BaaS / 容器平台低不吸收重复 Desktop、Hub 和 launch 能力，显著扩大部署与安全面。
把 Avernet 作为 San 强依赖低不吸收协议快速演化、职责重叠、引入中心服务；应保持 adapter 可卸载。

06 · Archived Design Sketch

归档设计草案（当前不执行）

状态：以下内容仅保留调研时的最小实现推演，不是 San 的 roadmap、待办或实现建议。
Draft

若独立需求成立：新增 hub observe，不修改 send 语义

observe 只把消息写进目标 agent 的上下文，不启动 autonomous turn、不生成 auto-reply、不能 await。保持现有 send 行为不变，避免兼容性和语义漂移。

  • to: "all" 时被动 fan-out，不制造唤醒风暴。
  • host 自动附加当前 scopeId、发送者 task contract 和 causation；不让模型伪造宿主身份字段。
  • 目标 busy/idle/parked 都必须满足“零新增模型请求”；允许恢复对象，但禁止因此启动 run。
  • 大上下文继续使用 local:// / artifact:// handle，不把大块文本广播进每个上下文。
Draft

给协作消息建立 v1 内部契约，并复用现有 RPC/账本原语

不要复制 Avernet frame。基于 San 已有 Snowflake IDs、Task Contract、RPC v2 EventSequencer、IdempotencyStore 和 session journal，形成窄 CoordinationObservationV1。消息必须 exactly-once 进入目标上下文，重复 delivery 只返回 receipt。

Draft

对 load-bearing 边界加依赖图和 adapter conformance

优先覆盖 execution-control、task、registry/irc、modes/rpc-v2。规则存放在单一机器可读 manifest 或现有 lint 配置，不在 README 重复维护。外部 runtime adapter 的测试必须覆盖 send/observe/abort/history、错误映射、幂等冲突，并证明真实 adapter 被调用。

Deferred

不做；若未来出现真实需求，再评估可卸载 connector

单 San runtime 可走 WebSocket Plugin；托管多 San 实例时才考虑 Provider。connector 作为 extension/sidecar，映射到 RPC v2，而不是让 BCS 类型进入 AgentSession。

  • bot.connect → connector 身份与 version negotiation。
  • chat.send → run.start；立即 ACK，完成后发送 sequenced final。
  • chat.inject → 独立的 passive observation 能力。
  • chat.abort → run.abort。
  • chat.history → session.messages.list。

启用门槛：有明确跨运行时协作用户；上游 tagged protocol 和路径稳定；connector 的断线重连、幂等和 credential isolation 均通过 smoke。否则不进入默认发行图。

明确非目标：不在 San 中建 bot marketplace、好友图、组织 RBAC、Web 群聊、中心数据库、BaaS 或 Skills Pool 控制台；不把每个 subagent 变成长驻服务；不因 Avernet 的营销数据扩大 San 产品边界。

07 · Concrete Contract

归档的最小 wire 草案与验收门（当前不执行）

以下是设计建议，不是已实现 API。模型可见参数只保留 to 与 message；其余字段由 host 派生。

// hub tool
{ "op": "observe", "to": "AuthLoader", "message": "API contract changed; rebase assumptions." }

// host-owned internal record
{
  "schemaVersion": 1,
  "observationId": "obs_...",
  "from": "Main",
  "to": "AuthLoader",
  "body": "API contract changed; rebase assumptions.",
  "createdAt": "2026-08-10T...Z",
  "scopeId": "scope_...",
  "contractId": "contract_...",
  "causationId": "msg_..."
}

行为不变量

  • 观察消息永远不触发新 assistant request。
  • 观察消息永远不自动回复。
  • 同一 observation ID 在同一目标上下文最多出现一次。
  • 目标下一次真实 turn 能看到观察内容与发送者。
  • 旧 transcript 无新字段时仍能恢复。

必须验证的回归

  • idle、busy、parked 三种状态的 provider request count 均不增加。
  • observe all 不改变任何 peer 的 running/idle 状态。
  • 重复投递返回 reused receipt，不重复写 session。
  • 恢复/分支后 observation 只出现在正确 branch/scope。
  • 普通 send 的 wake/revive/await 行为完全不变。
风险：被动注入只是避免“立即推理”，不等于免费。下一次 turn 仍会消耗上下文 token；因此必须有长度上限、scope 过滤、去重和 handle-first 规则，不能把 Avernet 群聊广播原样搬进每个 agent history。

08 · Final Decision

最终决策：No-go

  1. 不引入 Avernet 依赖，不 fork BCS，不复制组织平台。
  2. 不开发 Avernet connector，不创建相关 roadmap 项。
  3. passive observation、结构化消息和 contract discipline 降级为普通参考。只有 San 自身问题提供独立证据时才重新设计。
  4. 本报告作为已关闭的技术调研归档。未来若出现跨运行时、多租户 Agent 网络的真实需求，从需求重新评估，不默认回到 Avernet。

一句话：Avernet 有可理解的工程做法，但没有让 San 必须吸收、也没有足以改变 harness 路线的独特能力。
