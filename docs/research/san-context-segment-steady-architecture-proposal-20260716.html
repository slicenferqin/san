San Context Steady · Architecture Proposal · 2026-07-16

长任务上下文稳态：Segment 不是执行预算

本方案把数小时甚至一天的单次用户请求视为一个持续的逻辑 turn，但把内部执行拆成可维护的 segment。 Segment 只负责保存状态、压缩上下文和重建 provider working set，不拥有“剩余执行额度”，因此不会因为 segment 数量或维护次数而饿死 agent。

评审目标：确认逻辑边界、用户输入处理方式和长任务不会被维护机制意外终止

一、先给结论

逻辑成立，但 Segment 必须被定义为“上下文维护单元”，不能被定义为“执行配额单元”。 一个逻辑 turn 可以拥有无限数量的 segment；只有 provider 的物理上下文无法再构造时，任务才进入显式的 PAUSED_FOR_CONTEXT，而不是因为“segment 预算用完”自动停止。
原始记录不丢 Journal append-only 保存完整工具调用、工具结果、摘要和 compaction 边界。
当前请求可控 Provider working set 只保留目标状态、最新 checkpoint、有限 live tail 和未完成工具对。
维护失败可降级 摘要模型超时或限流时，使用确定性最小状态继续，不把摘要失败当成执行预算耗尽。

当前实现已经在 onTurnEnd + willContinue 安全边界做 mid-run compaction，但 San TurnDigest 仍主要在逻辑 turn 结束时生成；因此下一步重点是让 compaction、segment coverage 和 Context Plan 共用同一份 active-context 权威状态。 参考：mid-run maintenance、 TurnDigest。

二、三个预算必须分离

执行预算 用户或系统明确指定的最长时间、费用、步骤数。只有它可以主动结束任务；默认不由 Segment 生成。
上下文预算 Provider 的物理限制。达到 soft threshold 触发维护，达到 hard ceiling 执行一次恢复；不能假装成“执行额度”。
维护预算 摘要模型的 token、超时和重试上限。耗尽后切换到最小 checkpoint、artifact offload 或其他模型，不停止逻辑 turn。
之前方案中出现的 maxTokens、maxProviderRequests、maxDurationMs 必须标注为 maintenance hint（软触发），不能作为 hard cap。它们只回答“什么时候应该做维护”，不回答“任务还能执行多少”。

三、用户输入处理流程

用户输入和后台维护是两条并行流。输入路由器只决定消息进入当前执行、steering 或 FIFO 队列；它不因为维护中的摘要或 compaction 而丢弃、覆盖或重复消费用户消息。

主流程：一条用户消息可以持续数小时，但每次 provider 请求都必须可构造
用户输入新任务、补充要求、状态询问或中途 steering
→
输入路由器判断当前是否运行、维护中、可 steering 或必须 FIFO 排队
→
Prompt Boundary生成逻辑 turn / prompt generation，读取 active state
→
Context Gate估算 projected input，读取 active protected refs 和 coverage ledger
低于 soft threshold 直接发送 provider 请求。工具结果回到安全边界后继续同一个逻辑 turn。
超过 soft threshold 标记 MAINTENANCE_PENDING；先做最小 checkpoint 和 artifact offload，再重建 working set。
超过 hard ceiling 执行一次 compaction → coverage 重建 → Context Plan 重建 → replay 原请求一次；仍不适配才暂停。
Provider 请求稳定前缀 + checkpoint + live tail + 未完成工具对
→
工具调用 / 结果按 call id 配对；大结果写 artifact，保留错误和必要证据
→
安全边界工具对闭合后决定继续、维护或结束 segment
→
继续 / 结束继续：同一 logicalTurnId；结束：从 segment/checkpoint 生成最终 TurnDigest

维护过程中的新用户消息进入 FIFO queue；维护成功后按入队顺序交付一次。用户的状态询问可以单独走轻量 progress 事件，不能依赖正常 todo reminder 才有响应。

四、三层数据架构

关键是区分“完整可追溯”与“当前必须放进 prompt”。旧消息可以从 provider working set 移出，但必须有 replacement ref 和可恢复路径。

数据流：原始 journal 永久保留，active context 只承载当前执行所需信息
Journal
不可变事实层
用户消息 assistant tool call tool result segment record checkpoint compaction entry artifact index
↓ 通过 sourceRefs / replacementRef 建立 coverage
Coverage Ledger
替代关系层
active refs archived refs authoritative digest deterministic checkpoint degraded fallback generation / maintenanceId
↓ 只 materialize active coverage
Provider Working Set
执行上下文层
system / tools prefix current user intent latest checkpoint bounded live tail unresolved tool pairs selected evidence refs
Context Plan 的 requiredTokens 只能来自 active protected refs。 compaction 后，旧 journal entries 仍可查询，但不能因为仍存在于 branch 就继续参与 hard-pressure 计算。否则会出现“实际已压缩，planner 仍拒绝”的拒绝环。

五、Segment 生命周期与防饿死状态机

状态机：正常路径永远返回 RUNNING；暂停只表示物理上下文无法再恢复
RUNNING工具循环正常继续；不消耗 segment 执行额度
→
MAINTENANCE_PENDINGsoft pressure、segment hint 或大输出触发
→
RUNNING最小 checkpoint / compaction 完成，重建后继续
维护成功条件
active projected input 下降；active protected refs 已重算；同一 provider request 最多 replay 一次；工具不会重复执行。
维护失败条件
artifact offload、确定性 checkpoint、compaction 和可用模型都无法构造合法请求，才转入显式暂停。
PAUSED_FOR_CONTEXT显示具体原因和恢复动作；输入继续 FIFO 排队
←
RECOVERY_FAILED维护无进展或 provider 仍拒绝；禁止静默 stop
→
RECOVERY_ONCE一次 compaction + replan + replay；有 maintenanceId 防止循环

这里的“暂停”不是旧版本意义上的预算饿死：它是一个可观察、可恢复的状态。只要最小 continuation state 能放入 context，系统就必须回到 RUNNING，不受 segment 数量、摘要次数或摘要模型失败影响。

六、摘要与压缩的职责边界

机制 触发时机 输入 是否阻塞长任务 可替代的内容
最小 checkpoint 每个需要维护的安全边界 结构化执行状态和 artifact 索引 必须完成，但应是本地、确定性的 支持继续执行的最低状态
SegmentDigest segment 闭合后；可异步升级 单个有限 segment，不读完整 logical turn 不阻塞；超时降级 已闭合 segment 的语义摘要
Compaction soft/hard context pressure 当前 active context + 可替代的历史材料 只阻塞当前请求，不结束 logical turn provider working set 的旧 raw span
Final TurnDigest 逻辑 turn 真正结束 checkpoint / segment digest frontier / 最终状态 不阻塞后续用户输入 整条逻辑 turn 的可检索语义索引
raw entries → segment checkpoint → segment digest → checkpoint digest → final TurnDigest provider working set = stable prefix + current state + latest checkpoint + bounded tail + unresolved pairs

七、用户输入与维护并发时的处理

并发处理：消息不丢、不覆盖、不重复消费
用户消息 A任务补充 / steering / 状态询问
→
Input Queue记录 sequence、prompt generation、消息类型
→
维护中不交给会被 compaction 重置的临时队列
→
恢复后 FIFO 交付每条消息只注入一次，按序进入新的 prompt boundary
  • 维护期间的普通任务消息进入 FIFO；不会因为 compaction 重建 active messages 而丢失。
  • 状态询问可由 progress channel 立即反馈，但不能把状态询问误当成新的逻辑 turn。
  • 如果维护最终进入 PAUSED_FOR_CONTEXT，队列仍保留；用户可以继续输入恢复指令或主动终止。
  • 恢复 replay 的是 provider request，不是用户消息；因此不能重新执行已经成功的工具调用。

九、验收标准

长任务连续性

单个 logical turn 执行 200–1000 次工具调用，segment 数量不设上限，不因 segment hint 或摘要次数自动结束。

上下文稳态

每次 provider 请求的 projected input 不超过 hard ceiling；维护后 active protected refs 不包含已归档 refs。

摘要模型降级

digest 模型超时、429、400K 不足时，最小 checkpoint 仍能让任务继续；rich digest 可稍后升级。

工具安全

compaction/replay 不会重复执行成功工具；未完成 tool pair 不会被移出 working set。

输入可靠性

维护期间输入 FIFO 一次性交付；用户至少能看到 progress 或明确的 paused/recovery 状态。

真实物理极限

只有所有最小状态都无法适配 context 时才暂停，并给出恢复动作；不能用“预算不足”静默饿死。

十、需要审核的决策点

  1. 是否接受“segment 数量无限，维护 hint 仅软触发”：这是避免复现预算饿死的核心前提。
  2. 最小 checkpoint 是否允许作为 continuation authority：建议允许它替代旧 raw span 继续执行，但不把它当作最终高质量语义摘要。
  3. 摘要模型失败后的处理：建议立即使用 deterministic checkpoint，后台异步升级，不等待 gpt-5.4-mini。
  4. 物理上下文无法恢复时的用户体验：建议进入可见的 PAUSED_FOR_CONTEXT，保留 FIFO 输入和恢复指令，而不是自动 stop。
  5. 缓存边界：建议只在 segment/compaction 边界重写 provider history；普通工具调用不改变稳定前缀。

十一、实施状态与自动验收

P0 · 安全边界与恢复

ContextPlan 只对最新 compaction 后的 active journal 区间做 hard-pressure 计算；历史条目仍保留用于审计。用户边界最多执行一次 promotion/compaction/replan replay，失败时写入可见的 paused_for_context 审计。

P1 · Segment 维护协议

mid-turn compaction 会追加无执行预算的 san.context_segment。40K token 或 15 分钟只作为维护软提示；Segment 数量不设上限，不会令 agent 停止。

P2 · 有界摘要与观测

最终 TurnDigest 使用“最新递归 Segment checkpoint + active tail”，默认最多向摘要模型提交 160K token；/context plan 同时展示 active/archive 数量、cutoff、maintenanceId 和 recovery attempt。

自动压测结果

真实 AgentSession 已通过单个 logical turn 连续 60 次工具调用、多次 mid-turn compaction、多 Segment 后继续完成；纯边界测试以 500 条调用消息验证摘要输入不超过配置上限。

自动测试只证明协议和状态转换成立；真实模型下一轮连续使用仍用于校准 40K/15 分钟软提示、摘要质量和缓存命中表现。
