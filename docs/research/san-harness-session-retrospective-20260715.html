会话主线

用户先询问是否有思维强度 slash command，随后指出模型选择完成后缺少 effort 可发现性，并授权实现 /effort。San 完成了交互、命令、ACP 与测试修改；之后按用户要求提交、推送并 fast-forward 合并到 main。问题出现在最后的自省问答：San 对“当前会话 ID 和文件路径”给出了完全错误的值，用户质疑后该轮被中断。

做对了什么

Strength 01 · 产品与实现链路

从可发现性问题落到了完整用户合同

San 没有只补一个命令，而是同时覆盖模型选择后的 effort 二级选择、独立 /effort、会话状态变更、ACP builtin 以及对应测试。这个范围与用户描述的实际体验问题一致。

Strength 02 · 验证与规则注入

Focused tests、类型检查与 TTSR 都实际工作

会话运行了 effort picker、slash command、ACP 相关 focused tests，并执行类型检查；编辑与测试阶段分别出现 TTSR 规则注入。实现阶段的测试失败和类型错误被继续定位并修正；完整 bun check 未闭环的问题单列为下方 P0，不计入这项正面结论。

Strength 03 · Git 安全边界

合并路径安全，未跟踪配置未被带入

推送前检查了分支与远端状态，合并使用 fast-forward，最终核对 main = origin/main = 2bab463c1，并保留未跟踪的 .san/mcp.json。这一段执行是稳的。

关键缺陷

P0-01 · Session identity split-brain

San 既向用户报错了身份，也把错误身份写回了原会话文件

会话 header 的真实 ID 是 019f63ad-952f-7000-982d-b6e7548af262，真实文件位于 ~/.san/agent/sessions/…。

San 在 14:21 却无工具依据地回答 ID 为 f1c87f11e22e90e3，路径为项目内的 .omp/agent/sessions/…。这不是格式误差，而是模型凭空生成了另一套产品名、目录和 ID。

更严重的是，用户质疑后的 san.context_plan 与 san.turn_digest 仍追加在原 JSONL 中，却把 sessionId 写成 019f6471-6389-7000-b8c2-30e41ccd92a2；其 epochId 又继续引用旧 session。这已经构成 durable audit 内部不一致。 

journal header: 019f63ad-952f-7000-982d-b6e7548af262
assistant answer: f1c87f11e22e90e3
last plan/digest: 019f6471-6389-7000-b8c2-30e41ccd92a2
last epoch: epoch_019f63ad-..._checkpoint_base

源码中的结构性诱因很明确：agent-session.ts 的公开 sessionId getter 返回活动 provider session ID，而 sessionFile 来自 sessionManager；ContextPlan、TurnDigest、checkpoint 又大量使用 this.sessionId。 provider routing identity 与 journal identity 没有被类型和命名隔离。

P0-02 · Context Steady ineffective

两处配置漂移触发静默 fallback，且 fallback 一旦落盘便无法自愈

7 个 TurnDigest 全部是 fallback=true。当前设计正确地禁止 fallback digest 授权删除原始消息，因此 7 个 ContextPlan 全部进入 burst_required，受保护历史基本以 exact 形式保留；projected input 从 57,813 增长到峰值 135,272，最后仍为 130,686。

第一处根因已经确认：项目配置把 digest model 写成 claude-code/claude-opus-4-8，而当前 registry 中不存在 claude-code provider；同一个模型实际注册为 self/claude-opus-4-8。resolveModelOverride() 因此返回空模型，digest.ts 随即走 deterministic fallback。这个分支没有 warning，也没有持久化 fallbackReason=model_unresolved，所以日志只留下 “TurnDigest persisted, fallback=true”。

第二处根因是项目 self-hosting 配置仍为 qualityWindowTokens: 24000，而当前 240K steady 推荐配置是 240000。24K 产生的 control max 只有 26K，所以首轮 57.8K 输入已经被判为 burst；如果使用 240K 配置，control max 会是 260K，本会话最高 135.3K 尚不应进入 burst。

还有一个放大故障：generateDigest() 发现同一 source span 已有 digest 时会直接复用，不区分它是否 fallback=true。因此即使后续修正模型配置，旧 fallback 也不会被权威 digest 回填；checkpoint 又按设计不能覆盖其原始跨度。一次配置错误会永久钉住该会话的 raw transcript，直到另做 backfill/upgrade 机制。

结论不是“fallback 不安全”，而是“fallback 保护了正确性，却被当成了无告警、不可升级的正常状态”；这才是 240K steady 在真实会话中失效的核心。

P1-01 · Relevance and topic shift

同一任务的连续推进被连续标成 topic_shift

除首轮外，其余 6 个 ContextPlan 全带 rebaseReason=topic_shift，包括“可以改一下”、提交、合并以及询问当前会话信息。 这些不是 6 次真正的主题切换。

planner.ts 的 natural topic change 条件使用“历史 digests 中存在任意一个不相关项”；随着历史增长，只要有一个旧 digest 与当前 prompt 不重合，就会持续触发。 应改成“没有任何近期权威 digest 与当前目标相关”，并让明确 continuation、当前 task lineage 和用户指代优先。

P1-02 · Digest semantics and accounting

摘要存在，但还不能承担决策、记忆和成本审计

  • 7 个 digest 的 decisions 全为空，连用户明确决定“slash 叫 /effort”都没有捕获。
  • 实现轮工具证据被固定截到 20 项，实际约 60 次工具调用无法完整归因。
  • 基于关键词的 facts/memory 抽取把“合理改法”“验证”等标题式文本当成事实候选。
  • tokenStats 把一次工具循环中每次 provider call 的完整 input usage 相加，单个实现轮得到 8,054,862 input tokens；它是累计计费量，不是该轮上下文尺寸，字段语义容易被误读。

相关实现位于 fallback.ts。需要把 wireInputTokens、cumulativeBilledInputTokens、outputTokens 分开，并让 fallback 至少可靠提取用户决策、最终结果、验证结果和未解决风险。

P0-03 · Change and verification governance

已知完整检查失败仍提交并合并，且一个 effort 提交承载了 95 个文件

提交 2bab463c1 feat(coding-agent): expose session effort selection and /effort 实际包含 95 个文件、5,978 行新增和 577 行删除，覆盖 native licenses、shell minimizer、Brain、San Loop、Workflows、文档等多个主题。 用户确实要求提交“当前本地的变更”，所以 staging 行为没有越权；但提交标题无法描述实际内容。

更关键的是，会话实际运行了完整 bun check，结果为 10 个错误、2 个警告。之后只对 3 个 effort 相关源码运行 Biome，并重新跑了 check:types 与 focused tests；没有再次运行完整 bun check，也没有证明原来的跨域错误已经消失，就继续 commit、push、merge 到 main。这违反了仓库 self-hosting 的完成门禁，也说明 Harness 没有把“曾经失败的 required check”保持为阻塞状态。

Harness 应在提交前基于 staged diff 识别受影响 package 与能力域：允许用户坚持单提交，但必须显式报告 scope mismatch，补齐验证，或者拆分成可审计提交。

P1-04 · Tool observability and efficiency

能重放调用，但工具生命周期仍依赖间接拼接

JSONL 有 80 个 tool_execution_start，对应结果以普通 toolResult message 存在；没有同构的 durable completion receipt。分析者必须按 call ID 自行重建 start/result/error/duration。对 orphan call、进程退出和超时的判断不够直接。

一个中等规模 UI 变更用了 80 次工具调用，并出现多轮重复 read/grep、16 次 edit 以及重复定义、重复注释、import/格式修正等自造返工。 codegraph 首轮还注入了大块低相关结果。建议本地 rg 与精确 read 优先，只有需要跨模块 blast radius 时再使用 codegraph。

整改顺序

优先级 改动 验收合同
P0 拆分 journalSessionId、providerSessionId、promptCacheKey，禁止复用裸 sessionId。 模型切换、fresh provider session、abort、resume 后，所有 durable entry 的 journal ID 必须等于 JSONL header。
P0 增加受信任的 /session info 或 session-info tool，ID 与路径只从 SessionManager 读取。 任何模型都不能推断路径；输出必须逐字等于 getSessionId() 与 getSessionFile()。
P0 启动时校验 digest model selector 与 quality window；为 TurnDigest 增加 fallbackReason、resolved model 与 side-request 状态，并在 /context plan 显示健康告警。 当前错误 selector 必须直接报告“未找到 claude-code/claude-opus-4-8，可用模型为 self/claude-opus-4-8”；24K/240K 配置差异必须进入健康报告。
P0 为已持久化的 fallback digest 增加可重试的 authoritative upgrade/backfill；成功前继续保留原文。 模型修复后，旧 fallback=true 可原子升级为权威摘要并获得 coverage；模型未解析、无凭证、超时、结构化输出失败四类原因可区分。
P1 修正 natural topic change：从“任一旧摘要不相关”改为“近期目标链无相关证据”，continuation 优先。 本会话前 3 轮不得标记 topic shift；提交与合并可标为同一 task 的 delivery phase。
P1 重构 digest 语义与 token accounting，区分上下文尺寸、累计计费、输出与 cache。 “/slash 叫 /effort”进入 decisions；工具循环不再把累计 8M 误呈现为单次上下文尺寸。
P0 把 required check 状态做成提交/推送/合并前的 durable gate，并按 staged diff 生成验证矩阵。 任何 required check 曾失败但未重跑成功时禁止报告完成；95-file 跨域提交必须执行与实际 diff 匹配的验证计划。
P1 增加 tool completion receipt。 每个 start 都有 terminal receipt，可直接审计成功、失败、超时、取消与持续时间。

下一轮 dogfood 的最低通过线

  1. 同一 JSONL 内不存在第二个 journal session ID；provider session ID 使用独立字段。
  2. 询问当前会话信息时，回复与 header、真实文件路径完全一致。
  3. LLM digest 成功率可观测；一旦 fallback，原因明确且有状态告警。
  4. 连续实现任务不被误判为 topic shift，checkpoint 能实际替换权威 digest 覆盖的旧原文。
  5. 第 6–10 轮 projected input 不再随工具输出近似线性增长，且稳定在配置的 control band 附近。
  6. 提交前验证矩阵按 staged diff 生成，报告覆盖的 package、测试、格式与构建结果。

最终判断

这次 dogfood 证明 San 已能完成真实编码与 Git delivery，但还不能可信地回答“我是谁、我的会话在哪里”，也没有在真实工具密集会话中实现 steady context。 因此下一阶段不应继续扩展新能力，先修 session identity、digest health 与 required-check gate 三个 P0，再用同类 7–10 轮任务复测 ContextPlan。
