San architecture design · 2026-09-01

统一编排：一条默认路径，三条语义通道

在不合并现有状态机的前提下，统一 Task、Hub、San Loop 与 Workflow 的入口决策、活动读模型、运行身份和恢复边界。

范围：packages/coding-agent · 性质：技术设计与迁移方案 · 依据：当前源码、既有 San 设计稿、oh-my-pi 官方 issue 与评论 · 不是已实施功能

核心决定： San 不再让模型先学习“该调用哪套编排系统”。默认把普通可拆工作交给 task，把对已知执行者的追问交给 hub，只有用户明确要求验收、复核、重试或持续到终态时才升级到 Workflow / San Loop。统一的是入口、主句柄和只读活动视图；Task contract、Agent Registry、AsyncJobManager、IrcBus、Workflow ledger 继续各自拥有写入权。

1. 决策摘要

[建议] 以“一个逻辑协调对象、多个内部 authority、一个用户活动投影”作为统一编排的最小设计。

默认解决问题 普通工作先走 Task；不让用户先选择控制平面。
只保留三条语义通道 Dispatch、Message、Workflow，分别对应派发、联络、闭环。
内部状态不强行合并 读模型统一，写入边界和取消权保持分离。

1.1 事实、推断、设计决定

等级结论依据或限制

已观察San Loop 有独立 pipeline、角色工具白名单、预算、重试、blocked/pass 等终态；WorkflowManager 有批准、暂停、恢复、取消和写入交付状态。当前源码：san-loop/runner.ts、workflows/manager.ts。
推断主要摩擦不是单独的 Context Steady，而是模型被迫在多个控制平面之间反复做协议选择。压缩、provider 失败和长运行会放大循环；即使上下文稳定，入口仍有选择成本。
设计决定不创建一个越权的“万能 orchestrator”。先抽出共享派发边界，再建立可重建的活动投影。避免重复生命周期、双重重试、双重预算和 owner 隔离泄漏。
一句话验收：模型面对普通工作时只需要知道“派发给 Task”；需要补充信息时只需要知道“联系已有 agent”；用户明确要求质量闭环时才需要知道“启动 Workflow”。运行中的技术 ID 和内部记录不进入默认主路径。

1.2 目标与非目标

本设计解决

  • 统一入口选择与模型可见的语义边界。
  • 统一普通 Task、Workflow 节点、San Loop assignment 的活动读模型。
  • 让 Workflow 复用 Task 的真实调度边界，而不是调用工具包装层或复制一份 executor。
  • 定义批准、依赖、取消、重试、恢复和结果交付的可验证语义。
  • 提供从现有实现渐进迁移、可回滚的阶段路线。

本设计不解决

  • 不把所有普通 Task 自动升级为 San Loop。
  • 不引入无需用户意图的自治触发、定时运行或自动批准。
  • 不把本地 agent、远端 session、job、message 和 workflow node 伪装成同一个实体。
  • 不承诺外部 shell、provider、文件系统具备 exactly-once 或可回滚事务。
  • 不在第一阶段构建跨 session 的统一状态库或新的 UI 大面板。

2.2 “完成”不是一个事件

内部事实不能直接推导出的结论统一读模型应显示
Task job 已完成并自动交付结果。Agent 一定已经从 Registry 移除。“已完成；如需补充，可继续联系。”
Agent 状态为 idle 或 parked。Agent 仍在主动执行，或已经丢失。“当前没有执行；可以继续追问”或“暂时休眠，可唤醒”。
消息已投递、唤醒或 revive。被联系的 agent 已完成工作。“消息已送达；等待它继续处理。”
Workflow run 暂停。所有节点都应该停止或已经失败。“流程暂停；恢复后继续未完成的可运行节点。”
节点遇到未知外部副作用。可以安全地自动重跑。“无法确认上一动作结果；需要处理，不盲目重跑。”
设计约束：活动投影可以把多个内部状态翻译成用户语言，但不能改变事实。它不能替 Registry 改生命周期，不能替 JobManager 放开 owner 权限，也不能替 Workflow ledger 宣布一个未被批准的运行已经成立。

2.3 社区证据指向同一个缺口

OMP #2413 · 2026-06-12问题被描述为 orchestration enhancement，而不是小型 task() 修改。维护者评论列出现有的批量 spawn、共享 context、background jobs、lifecycle transcripts 和 bounded concurrency，并指出缺少一层显式 graph/state、持久依赖、取消/恢复和整体可见性。
OMP #6947 · 2026-07-29DAG 设计的边界是 runtime contract，不是薄工具包装。评论建议抽出共享 Task dispatch service；Workflow scheduler 应在首次调度前完成完整 preflight，并保留节点 ID 与 agent/job ID 的区别。
OMP #7962 · 2026-08-07计划批准后进入持久 Workflow 是明确的产品需求形状。评论把激活点限定在 plan approval 成功之后，而不是普通的 plan exit 或暂停路径。
OMP #7963 · 2026-08-07“三种模式”并非三个同类状态机。orchestrate 与 workflowz 是相近的单回合提示机制；vibe 是改变工具面和生命周期的持久 director mode。应统一分类，不应机械合并。
OMP #5334 · 2026-07-13模型专属委派提示可能压制 fan-out。这说明委派策略必须用行为数据验证，不能依靠一条模型特定规则把“是否派发”变成隐式禁令。

3. 统一分类：三条语义通道

统一编排不是增加第四个入口，而是让每个入口只回答一个问题。

通道唯一问题主要入口完成语义明确不承担
Dispatch
派发		谁来执行一次工作？task / 内部 TaskDispatchServiceassignment 产出结果；普通路径自动交付。不负责 peer 对话；不自建 review/retry ledger。
Message
联络		如何联系已知执行者？hub.send、hub.inbox、message wait消息已投递、等待、超时或无法送达。不创建新 agent；不冒充 job 完成状态。
Workflow
闭环		目标如何经过依赖、验收、复核后才算完成？Workflow manager、San Loop mode、未来 workflow toolcompleted、blocked、failed、cancelled 或需要用户。不把每个角色调用重复登记成普通 Task；不绕过批准。

3.1 普通 Task、批量 Task、Workflow 的选择

意图形状默认路径何时升级主句柄
一个明确、可独立交付的工作项。单项 task。不升级；结果交付后按需追问。agentId
多个互相独立的调查或实现项。一次 batch task。只有出现依赖、质量门或持续恢复要求才转 Workflow。每项一个 agentId，父级看聚合活动。
存在明确依赖、验收、复核、失败重试或“直到终态”的要求。Workflow / San Loop。不再额外包一层普通 Task。用户看活动摘要；详情保留 runId / nodeId。
已经知道某个 agent，需要补充信息或继续追问。hub.send(agentId)。只有需要新执行才重新 Dispatch；不能因 agent idle/parked 就自动重建。agentId 或显式远端地址。

3.2 模式与提示词的分类

单回合编排提示

orchestrate / workflowz 这类机制只改变当前回合的指导，不创建持久运行对象。

建议：在模型说明中统一称为“一回合编排提示”，保留现有兼容入口，不把它们误写成持久 mode。

持久 director mode

vibe 会保存 mode 状态、替换父级工具面并拥有独立 worker backend。

建议：继续作为独立 authority/runtime，不把它伪装成普通 Workflow run。

持久 Workflow run

在明确批准后创建有依赖、预算和终态的运行；跨后续回合继续，但第一阶段限于当前 session branch。

建议：Workflow 是执行合同，不是另一个 magic keyword。

不做的合并：不把 orchestrate、workflowz、vibe 和 Workflow run 粗暴压成一个枚举。应统一它们的说明、入口决策和活动投影；保留会影响工具权限、持久化和取消语义的真实差异。

3.3 一个逻辑对象，多个内部引用

CoordinationObjective
  ├─ objectiveId                 用户可理解的工作目标
  ├─ mode: direct | batch | workflow
  ├─ summary                     主路径的一句话状态
  └─ assignments[]
       ├─ assignmentId            逻辑工作项
       ├─ agentId                  后续联系的主句柄
       ├─ jobId                    后台执行句柄（详情层）
       ├─ contractId / scopeId     去重与作用域（详情层）
       ├─ runId / nodeId           Workflow 专用引用（详情层）
       ├─ messageIds[]             协调事件，不代表完成
       ├─ userState                working | done | blocked
       ├─ result                   可交付结果引用
       └─ nextAction               下一步或需要用户处理的原因

统一的关键不是制造一个万能 ID，而是规定引用优先级：普通 follow-up 使用 agentId；详情和恢复使用精确的 job、contract、run、node 引用。投影器负责映射，不改变任何 authority 的身份。

4.1 组件职责

组件拥有的职责禁止越权迁移策略
TaskDispatchService
新增内部边界		参数规范化后的 preflight、contract admission、并发、同步/后台调度、隔离、结果结算。不渲染模型工具文本；不拥有 Workflow 依赖图。从 TaskTool.execute 提取；TaskTool 变为薄适配器。
TaskContractRegistry按 scope/work/strategy 进行 admission、去重、heartbeat 和状态快照。不判断 agent 是否 parked；不代替 Workflow node 状态。保持现有 identity 和首个 admission 的 scheduler 初始化顺序。
AsyncJobManager后台 job、owner-scoped 可见性、取消权、进度和结果交付重试。不成为持久 Workflow 状态权威；不跨 owner cancel。Workflow node 直接绑定一次 Task attempt，不重复生成同一执行的第二个 job。
AgentLifecycleManagerfinished agent 的 idle、parked、revive 和冷恢复生命周期。Hub、JobManager、Projection 不直接写 lifecycle status。所有 send/focus/revive 继续调用 lifecycle API。
MessageGateway把本地 IrcBus 和跨 session client 归入同一 Message 语义。不创建新 agent；不把远端 session 当本地 job。沿用显式 san:<12 hex> 地址；先统一说明，再做只读远端投影。
WorkflowController图验证、依赖就绪、批准、暂停、恢复、取消、重试、blocked 和最终交付。不调用 TaskTool.execute() 作为内部 API；不包裹 San Loop 的每个角色。复用现有 WorkflowManager；其 bridge 改用共享派发边界。
SanLoop orchestratorsolo/team/council pipeline、角色选择、预算、验收和 Loop 专属 ledger。不把角色调用重复登记为普通用户 Task。保留 executor；增加 activity adapter 和统一终态映射。
CoordinationActivityProjector从各 authority 读取快照，生成活动行、三种用户状态和 nextAction。不写回 authority；不把推断状态伪装成已确认事实。先只读、内存重建；稳定后再接 TUI/ACP/SDK。

4.2 共享派发服务的最小接口

以下是设计接口，不是要求立即新增的公开 SDK。它的目的，是让模型工具和 Workflow scheduler 共享同一套执行语义。

interface TaskDispatchService {
  preflight(request: TaskDispatchRequest): TaskDispatchPlan;
  dispatch(
    plan: TaskDispatchPlan,
    options?: TaskDispatchOptions,
  ): Promise<TaskDispatchHandle>;
  cancel(handle: TaskDispatchHandle, reason?: string): CancelOutcome;
  snapshot(handle: TaskDispatchHandle): TaskDispatchSnapshot;
}

interface TaskDispatchRequest {
  ownerId: string;
  rootSessionId?: string;
  assignment: string;
  agent: string;
  contract?: TaskContractInput;
  isolation?: IsolationRequest;
  execution: "sync" | "background";
}

interface TaskDispatchHandle {
  agentId: string;
  jobId?: string;
  contract?: TaskContractSnapshot;
  completion: Promise<TaskDispatchResult>;
}
接口边界：Workflow scheduler 只负责“哪个 node 现在可运行、哪个 node 等依赖、哪个 node 被阻塞”。具体 agent 如何启动、如何获得 semaphore、如何进入 Registry、如何生成结果，必须只经过 TaskDispatchService。这样才能避免 TaskTool、Workflow 和 San Loop 各自维护一份近似但不相同的生命周期。

4.3 统一活动投影

投影是读模型，不是新的状态权威。每个活动行至少包含以下语义字段：

字段含义来源默认显示
activityId投影行稳定引用。assignment 或 node 映射。否；详情层。
label人话工作描述。assignment 摘要或 Workflow phase。是。
userStateworking、done、blocked。多个 authority 的保守归并。是。
progress可解释的最新进展，不伪造百分比。job progress、agent activity、node phase。是；一行。
nextAction系统下一步或用户需要处理的动作。状态转换和错误分类。是；一行。
primaryHandle后续追问使用的 agentId 或明确远端地址。Registry / MessageGateway。需要时显示。
technicalRefsjob、contract、run、node、message 等完整映射。各 authority。折叠详情或 stats。

投影冲突时采用保守规则：已确认的终态优先于瞬时 progress；blocked 优先于“看起来仍在运行”；无法确认外部副作用时显示需要处理，不自动降级为 completed。

5. 运行、取消与恢复语义

5.1 Direct / Batch Task

意图
  ↓ normalize + shape validation
contract admission
  ├─ reused → 返回已有活动引用，不重复 spawn
  └─ admitted
       ↓ TaskDispatchService preflight
       ├─ sync → 当前回合等待结算
       └─ background → AsyncJobManager 注册一次 job
                    ↓
              Agent Registry: running
                    ↓
          completed / failed / cancelled
                    ↓
       自动交付结果 + 更新 contract + 投影活动行
                    ↓
       AgentLifecycleManager 接管 idle → parked / revive
  • 同一批次可以混合 blocking 与 background，但投影必须把每项的等待语义说清楚；不要把整个 batch 误称为同一种执行。
  • 后台结果自动交付，模型不应为了“拿结果”反复调用 jobs 或裸 wait。
  • 取消只取消调用和 job；不声称已经回滚外部文件、shell 或 provider 副作用。
  • 完成后的 agent 仍可能 idle/parked；follow-up 使用原 agentId，不是重新 spawn。

5.2 Workflow DAG

draft
  ↓ validate complete graph + permissions + limits + all pending preflights
approved
  ↓ durable run_approved
running
  ├─ schedule dependency-ready nodes through TaskDispatchService
  ├─ node completed → unlock dependents
  ├─ node failed/interrupted → block descendant closure
  ├─ pause → stop scheduling at safe checkpoints
  ├─ cancel → stop scheduling + abort active Task calls
  └─ unknown external effect → blocked; never blind retry
       ↓
completed | failed | cancelled | blocked
       ↓
result delivery (at most one visible delivery per run)

第一版 Workflow 采用静态图和明确依赖。完整定义必须在第一个节点启动前通过验证；运行过程中不允许模型无审批地追加节点或扩大权限。

5.3 建议固定的五个语义决定

问题建议答案理由
取消是否影响运行中 Task？停止未来调度，并向 active Task 发送正常 abort signal。用户停止应能尽快生效；但状态只能标为 cancelled/unknown，不能声称外部效果回滚。
Workflow ID 的作用域？当前 session branch 唯一。满足跨回合恢复，同时不提前合并多个 session 的 Registry 和权限边界。
定义能否原地替换？创建后不可变；新定义使用新 ID 或新版本。避免批准键与运行时内容漂移。
恢复遇到失败节点怎么办？继续独立 ready 分支；失败节点及其后代保持 blocked。成功节点不重复执行；显式 retry 才能重置失败节点及受影响后代。
Workflow node ID 与 Task agent ID 是否相同？不同。 每次 attempt 仍分配一个确定的 Task agent ID，并保留 one-to-one Registry / Hub 身份。节点是声明性状态；agent 是执行者；混合会导致恢复和追问语义不清。

5.4 持久化与崩溃恢复

权威事实

  • 对话和关键运行事件采用 append-only 记录。
  • Workflow 当前状态采用可重建的 materialized snapshot / register。
  • usage、预算和交付状态必须有明确结算点。
  • UI stream 只是一种观察，不是恢复依据。

外部效果边界

  • provider、shell、文件系统不与 session commit 共享 XA 事务。
  • 调用前记录 intent；返回后记录 result 或 unknown。
  • 只读操作可 safe replay；有幂等键的操作依赖外部系统去重；不可安全重复的操作恢复为 interrupted/blocked。
  • 不要用“重放历史”替代副作用策略。

第一阶段可沿用现有 Workflow store 和 session custom entries 的持久化能力；不新增一套平行 journal。新增字段必须带 schema version，旧快照只能通过显式迁移读取，不能靠猜测缺失字段。

6.2 模型说明的五条硬边界

  1. task 创建新执行。 没有新工作时，不要为了追问再次 spawn。
  2. hub.send 联系已有执行者。 它不会创建新的 agent，也不代表工作已经完成。
  3. 普通 Task 结果会自动交付。 不为取结果连续轮询；只有明确需要等待消息、job 或进程时才使用对应参数。
  4. Workflow 只在闭环目标明确时使用。 不把普通 Task 和 Workflow 双重包裹。
  5. 默认只暴露一个后续句柄。 主路径使用 agentId；job、contract、run、node 只在详情层出现。

6.3 Hub 的参数分域

域参数特征语义错误用法
Messagingsend / inbox / wait(from) / list读写 peer mailbox、等待消息、查看 agent。用 message wait 等 job 完成；把 remote peer 当本地 agent。
Jobsjobs / wait(ids) / cancel(ids)查看或控制当前 owner 可见的后台 job。跨 owner 查询或取消；在结果自动交付后重复轮询。
Processesstart / ps / logs / stop 等受管长进程生命周期。把进程 readiness 当作 agent 工作完成。

Hub 可以继续是一个工具名，但 schema、prompt 和 renderer 必须显式分域。减少工具数量不应以隐藏参数路由为代价。

6.4 默认主路径的三种用户状态

正在做什么

“正在检查支付模块的类型错误，已启动 2 个独立检查。”

不显示内部调度记录，不让用户理解 scheduler 才能继续。

做完了什么

“已完成依赖升级检查；发现 3 个需要处理的兼容问题。”

结果先给结论，技术引用和完整过程放展开层。

卡在哪里

“无法确认上一个写入动作是否成功；请查看变化后决定重试或继续。”

不要用模糊的“仍在运行”掩盖 blocked/unknown。

不要把内部机制搬到主 UI：contract、scope、ledger、receipt、gate、owner 等词可以留在技术详情和 san stats，不应成为 novice 用户继续任务的前置知识。

7. 计划批准后的持久交接

“计划批准后把实现阶段交给持久编排”是一个有价值的产品入口，但它必须绑定到成功的批准事件，而不是普通退出计划模式。

7.1 建议流程

Plan review
  ↓ 用户批准计划，并选择执行配置（可选）
成功完成 plan approval
  ↓ 退出 plan mode、恢复工具面
创建并 durable 记录 workflow handoff
  ↓ 只在批准内容对应的边界内启动
Workflow run / San Loop execution
  ↓ 后续回合通过同一活动投影观察、暂停、恢复或处理
终态：completed / blocked / failed / cancelled
  • 激活 hook 放在成功的 approvePlan 执行 dispatch 之后，不放在通用 exitPlanMode；后者也覆盖暂停、拒绝和普通切换。
  • handoff 默认 opt-in，优先采用 plan-review 选择，而不是立刻增加一个会影响所有后续会话的全局开关。
  • 持久运行保持到显式终态或用户退出，不根据单回合 magic keyword 猜测何时自动结束。
  • ACP、print、非交互会话没有对应 UI 时，必须使用明确的配置或拒绝 handoff；不能静默进入用户无法观察的持久 mode。
  • handoff 只能复用批准计划的权限、模型和预算边界；改变任一边界就需要新的批准。

7.2 与现有 vibe、orchestrate、workflowz 的关系

机制是否作为 handoff 目标处理方式
orchestrate / workflowz不直接持久化为 mode。保留为单回合指导；如果批准后要持续运行，创建真正的 Workflow run，而不是重复注入 notice。
vibe不作为普通 Workflow 的别名。它改变 parent tool surface 和 worker authority；若未来支持批准后进入，必须单独定义工具恢复、session fork、ACP 和退出语义。
Managed Workflow可以。使用已批准且版本固定的定义；运行参数和边界必须匹配批准键。
Ad-hoc Workflow可以，但仍需逐次批准。草稿、参数、权限和过期时间绑定当前任务；不得因名称相同而复用批准。
San Loop team/council可以作为显式质量闭环。保留其角色预算、review 和 ledger；只接入统一活动投影，不再包一层普通 Task。
边界：批准后交接解决的是“单回合执行与持久运行之间的断层”，不是把所有编排方式都变成一个 mode。持久性属于 Workflow run；父级工具权限改变属于 vibe；单回合提示属于 magic keyword。

8. 迁移路线

迁移顺序先改读模型和内部边界，再改变产品入口。每一步都保留旧工具行为，避免一次重写同时改变调度、提示、持久化和 UI。

  1. P0 · 统一提示和入口说明，不改运行时。明确 Task / Hub / Workflow 的三条语义边界；把 Hub wait 按 from、ids、name 分域；普通结果说明自动交付；保留所有现有命令和关键词。
  2. P1 · 抽出 TaskDispatchService。把 TaskTool.execute 中的 preflight、admission、semaphore、sync/background、isolation、settlement 抽为内部服务；TaskTool 只负责 schema、模型文本和结果渲染；现有行为必须保持。
  3. P2 · 建立只读 CoordinationActivityProjector。订阅 contract、job、Registry、message 和 Workflow / Loop snapshot；为每项生成 userState、nextAction 和主句柄；先接测试和内部诊断，不改变主 UI。
  4. P3 · 让 Workflow 复用共享派发边界。WorkflowManager 的 bridge 调用 TaskDispatchService；静态 DAG 完整 preflight 后再调度；node ID 与 agent ID 分离；取消、重试、blocked 和结果交付遵循本设计。
  5. P4 · 接入 San Loop 活动适配器。保留 solo/team/council 的 role executor、预算和 ledger；映射 run/assignment 到活动行；禁止角色调用产生普通 Task 的第二次交付。
  6. P5 · 批准后 handoff opt-in。在 plan approval 成功边界创建持久 Workflow run；先只支持当前 session branch；非交互入口没有观察能力时 fail closed。
  7. P6 · 以 dogfood 数据决定默认值。采集控制面切换、无效等待、重复派发、终态解释率和预算内完成率；没有基线前不全局开启持久编排，也不删除旧入口。

8.1 迁移映射

现有位置迁移后角色必须保持
task/index.tsTaskTool adapter + TaskDispatchService 实现来源。参数兼容、batch、blocking、async、contract、isolation 和结果形状。
async/job-manager.ts后台执行和交付 authority。owner 过滤、取消权、delivery retry、retention。
registry/agent-lifecycle.tsidle/parked/revive authority。只有 lifecycle manager 改变 parked ↔ idle。
tools/hub/*Message / Jobs / Processes 的统一适配器。参数语义、远端地址显式性、不可越权查询/取消。
san-loop/*质量闭环和角色 pipeline。严格工具白名单、预算、retry、blocked/pass 和 ledger。
workflows/*批准、静态图、持久 run 和交付 authority。Managed / Ad-hoc 两种 product kind、批准键、写入冲突 blocked。
Task / Hub / Loop prompts统一模型协议。不把内部技术词汇变成默认用户前置知识；不再用模型特例压制可证明的 fan-out。

8.2 兼容和回滚

  • 旧的 task、hub、San Loop 命令和 Workflow 命令继续工作；新服务先作为内部实现替换，不改变公开 schema。
  • 旧 session 中的 agent、job、contract 和 Workflow snapshot 通过 adapter 生成活动行；缺少映射时显示有限状态，不猜测隐含关系。
  • 新持久记录带 schema version；读取失败时保留原始记录并进入 blocked/needs-user，而不是删除或自动修复成 completed。
  • Projection、handoff 和新的 Workflow tool 分别受独立 feature flag 控制；任一阶段出现重复执行、owner 泄漏或未批准启动即可关闭新层，旧路径仍可运行。
  • 不添加 deprecated alias 来掩盖语义冲突；兼容入口只在迁移窗口保留，并记录明确的移除条件。

9. 验证标准

设计必须用行为验证，而不是只验证类型能编译。重点观察模型是否少做了错误的控制面切换，以及运行是否在预算和终态边界内收敛。

9.1 必须通过的场景

场景期望行为失败信号
普通单项委派一次 Task；结果自动交付；需要追问时一次 Message。Task 后连续裸 wait，或结果到达后重复 spawn 相同 assignment。
独立 batch一次 batch；每项有明确 agentId；父会话看聚合结果。被拆成串行调用；item/job/agent 混淆；首项被错误判为 duplicate。
完成后追问使用原 agentId；idle/parked 经 lifecycle API 唤醒或 revive。把 parked 当丢失并创建替代 agent；直接改 Registry status。
Workflow DAG所有节点先通过验证；只调度 dependency-ready 节点；成功节点不重跑。运行中追加未批准节点；TaskTool 被程序化调用造成重复渲染或第二个 job。
Workflow 取消停止未来调度；active Task 收到 abort；最终显示 cancelled/unknown 而非 completed。取消只改 UI；活动节点继续运行且投影报告已完成。
失败恢复独立 ready 分支继续；失败节点后代 blocked；显式 retry 才重置闭包。自动重跑可能有副作用的节点；成功节点重复执行。
计划批准 handoff只有批准成功路径创建运行；拒绝、暂停、普通退出不创建。exitPlanMode 触发持久运行；未批准 agent 启动数大于 0。
跨 session 消息使用精确 san:<12 hex> 地址；只执行 Message 语义。把远端地址送给本地 cancel/jobs；依赖猜测的 session ID。
外部效果未知进入 blocked/unknown，要求用户处理。崩溃后无条件重跑删除、写入或发送操作。

9.2 指标

入口质量

  • 控制面切换次数：Task ↔ Hub ↔ Workflow。
  • 无效等待次数：没有可等待对象时的 jobs/wait。
  • 重复 admission 比例和重复 spawn 率。
  • 一次 dispatch 到终态的回合数。

运行质量

  • 无人值守终态率、终态可解释率。
  • 预算内完成率、取消响应时间、恢复后重复节点数。
  • 自动交付次数与重复交付次数。
  • 主会话 token 增长和总 token 的对照。

上述指标用于内部 dogfood 和 san stats，不直接出现在主 UI。当前没有入口摩擦基线；先采样，再决定阈值和默认开关。

9.3 验证层级

  1. 契约测试：Task admission 去重、owner 过滤、lifecycle revive、Workflow dependency 和状态转换。
  2. 集成测试：TaskDispatchService 到真实 Task runner 的 sync/background 两条路径；Workflow node 到同一 semaphore、Registry 和 delivery。
  3. 恢复测试：在 intent、provider 返回、结果结算和 delivery 各边界模拟中断，确认不盲目重跑。
  4. 交互 smoke：普通 Task、batch、follow-up、复杂闭环、计划批准 handoff、跨 session message 六类真实操作。
  5. 过夜 dogfood：观察是否出现少量新证据驱动的语义活锁；设置硬 max turns、tokens、cost、duration、provider requests 和 workers，达到上限必须进入明确终态。

10. 风险与防护

风险表现防护
跨压缩边界的语义活锁每一回合都有少量新输出，但反复重新选择 Task、Hub、Workflow。父级硬预算、终止状态、活动快照和“下一步”字段；不要仅依靠 prompt 记忆。
双重执行层Workflow 包 TaskTool，TaskTool 又注册后台 job，结果被交付两次。共享 TaskDispatchService；一次 attempt 只有一个 agent/job 绑定。
状态 authority 越权Hub 或 Projection 直接修正 Registry；JobManager 代替 Workflow 宣布完成。职责矩阵、封装 API、跨模块行为测试。
模型特定委派抑制某模型因为系统提示不再 fan-out，性能和完成率下降。把策略和模型能力分开；对每个 model/provider 做真实行为采样，不把单个 issue 的 workaround 当永久规则。
外部副作用重复进程崩溃后不确定操作被自动重跑。intent/result/unknown 三段式结算；safe、idempotent、never replay policy。
持久 handoff 越过用户意图普通 plan exit 或非交互会话静默启动长期运行。只挂在成功 approval；opt-in；无观察能力时 fail closed。
跨 session 过早合并把两个 Registry、job owner 和 lifecycle 混成一个总表。第一阶段只做本 session branch；远端继续是 Message peer。
推荐的停线条件：出现未批准启动、重复外部写入、跨 owner 取消/泄露、成功节点重复运行、取消后显示 completed、或无法解释的无界回合增长时，停止扩大 rollout，回退到旧 Task / Hub / Workflow 路径。

11. 仍需维护者明确的产品决策

以下不是运行时无法解决的技术问题，而是需要产品口径固定的选择。本文给出保守默认值，避免实现过程中把偶然行为写进持久格式。

决策点保守默认代价
持久 Workflow 的范围当前 session branch，跨回合可恢复；暂不承诺跨 session 总体编排。远端协作需要继续用 Message；后续可增加只读聚合。
用户如何启用 handoffplan-review 中明确选择，默认关闭。多一个选择，但不会让全局会话意外进入持久 mode。
Workflow 定义版本创建后不可变；任何脚本、权限、预算和参数边界变化生成新版本。需要管理版本，但恢复和批准可证明。
是否允许自治追加节点第一版禁止；图在首次调度前完整验证。复杂动态任务需要重新生成并重新批准草稿。
是否把 vibe 纳入统一入口统一分类和活动投影，不把它作为普通 Workflow 别名。短期保留两套持久 authority；换取工具权限语义不被掩盖。
何时改变默认值等控制面切换、无效等待和过夜终态率有基线后再决定。功能不会一上线就覆盖所有会话。
