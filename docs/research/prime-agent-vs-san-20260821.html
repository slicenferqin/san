Prime Agent vs San

两者共享 TypeScript coding-agent 基础、TUI、会话持久化、provider、MCP、skills 和子代理等共同血缘，但核心问题不同：Prime Agent 把持久化运行时、RLM/kernel 和长期自治放在第一层；San 把Context Steady、证据约束和可恢复执行循环放在第一层。Prime 不是 San 的替代品，San 也不应整体追随 Prime 的架构。更准确的路线是：保留 San 的上下文与执行治理，吸收 Prime 的 resident runtime、任务恢复和长期调度能力。

Prime 的最大领先daemon 持有 root session tree、persistent IPython、RLM 子代理、heartbeat、schedule、goal、autonomous continuation
San 的最大领先ContextPacket 预算与质量门、immutable objective、typed host evidence、CAS ledger、San Checks
不应照搬把所有模型能力收缩成一个无边界的 IPython 工具，或把 shell gate 通过等同于任务完成
建议优先级P0 resident worker / child admission；P1 MCP ownership / evidence-aware autonomy；P2 optional kernel workspace

1. 结论先行

判断：Prime Agent 更像“长期运行的 agent operating runtime”，San 更像“带上下文稳态和验收闭环的工程执行系统”。若目标是让 San 在断开终端后继续可靠完成任务，最值得吸收的是 Prime 的运行时持有和恢复语义；若目标是高风险修改不被模型自报完成带过，San 的 ledger、typed receipt 和 quality gate 应继续作为不可替代的核心。

Prime Agent 解决的首要问题

  • 如何让一个 agent 在终端关闭、客户端重连、kernel 重启和多轮 compaction 后继续工作。
  • 如何把上下文、文件/数据处理、递归子代理和技能组合成可编程的 Python 控制面。
  • 如何让 goals、heartbeat、cron schedule 和 bounded autonomous mode 共享同一个 resident worker。

San 解决的首要问题

  • 如何让 provider-bound context 在长任务中保持有界，同时不丢失目标、决策、文件、风险和下一步。
  • 如何让计划、执行、复验、失败收口和用户阻塞拥有明确状态，而不是依赖一段模型总结。
  • 如何让完成结论必须绑定真实宿主证据，避免模型文本伪造通过状态。

2. 两套系统的运行时拓扑

Prime Agent：runtime-first

client / TUI / JSON / RPC
        ↓ local daemon protocol
supervisor
        ↓ one resident worker per root tree
AgentSessionRuntime
  ├─ root AgentSession
  ├─ scheduler / goals / autonomous policy
  ├─ persistent IPython kernel
  └─ RLM child sessions + kernels
        ↓
JSONL session + session artifacts

官方架构文档明确规定：client 负责 UI，supervisor 负责路由、attachments、health 和消息投递；worker 才拥有 provider、tools、compaction、kernel、scheduler 和 descendants。

San：context/evidence-first

San AgentSession
  ├─ explicit tools + eval bridges + MCP
  ├─ Context Steady
  │   └─ digest → checkpoint → bounded packet → prune
  ├─ ExecutionRuntime / scope journal
  │   └─ ledger / CAS / watchdog / leases
  ├─ San Loop
  │   └─ Commander → Worker → Supervisor → Oracle
  ├─ task / agent bridge / worktree isolation
  └─ goals + launch/peer lifecycle substrate
        ↓
append-only session JSONL + typed custom entries

San 已有 daemon/launch broker、跨会话 peer broker 和长期 goal/调度部件，但它们目前服务于上述执行与上下文底座，而不是取代它们。

关键差异：Prime 的 worker 是“执行所有事情的常驻所有者”；San 的主要创新是“模型下一轮应该看到什么、什么证据才算完成”。前者决定任务能否持续活着，后者决定任务是否真的完成。

4. 最值得关注的四处差异

4.1 Kernel 不是 Context Steady 的替代品

Prime 的 persistent IPython 解决的是“模型可以把大对象、解析结果、函数和子任务句柄留在外部 namespace 中”；San 的 Context Steady 解决的是“下一次 provider request 究竟携带哪些有界、可追溯的状态”。前者保存工作状态，后者治理模型输入。引入 kernel 可以减少重复读取和程序化组合成本，但不能证明目标、风险、验收和工具证据仍然存在。

决策：San 可以增加可选的 kernel workspace，但不能用 kernel namespace 替换 digest/checkpoint/packet/quality gate。

4.2 Autonomous gate 与 San acceptance gate 不是同一层

Prime 的 gate 是 host policy：运行命令、截断输出、失败后继续；它刻意不把 gate pass 说成任务成功。San 的 acceptance gate 更靠近完成状态机：objective contract、gate revision、assignment/freshness 和 host receipt 必须一致，ledger 才允许进入 completed。

决策：借 Prime 的 continuation policy，借 San 的 completion invariant；任何自动续行都只能消费 typed receipt，不能直接把模型文本升格为通过。

4.3 Prime 的 resident worker 是 San 的长期任务缺口

Prime 把 detach、reconnect、schedule、heartbeat、goal、child runtime 和 artifact recovery 放进一个明确的 worker ownership 模型。San 已有 launch broker、goal runtime、durable scheduler、peer transport 和 remote-control 设计，但用户是否能“关掉终端后仍有一个可恢复的 San 任务”还需要把这些部件收成一个一致的产品路径。

决策：优先构建 San 的 resident root runtime；不要先做 Web UI 或更多 agent 角色。

4.4 ACP MCP 提交暴露了一个可复用的 ownership 模式

Prime main 最近的 ACP MCP commit 不只是“接入更多 MCP”：它把 session-scoped server 绑定到 ACP client owner，阻止另一个 attached client 替换或清理，释放时先撤销 credential source 再关闭 kernel transport，并覆盖失败 claim rollback 与 reap。

决策：San 的 MCP profile 已经覆盖发现、OAuth 和 reconnect；下一步应补 session/client scoped ownership，而不是再加一套 server config 格式。

5. San 应直接借鉴、谨慎借鉴、无需跟随

类别建议为什么边界 / 验收口径
直接借鉴 P0Resident root worker + detach/reattach/recovery 这是 Prime 相对 San 最清晰的产品差距，直接决定长任务能否跨终端继续。 worker 只能成为 San AgentSession 的持有者；恢复后必须重放 session journal、Context Steady 状态和 ExecutionRuntime，不得生成第二份任务状态。
直接借鉴 P0Admission handle + retained child registry 并行子任务不应阻塞父 turn，也不应要求父模型轮询；Prime 的 handle/消息/retain 语义值得吸收。 child 必须继承 execution scope、预算和 capability policy；完成报告只通过 host observation/typed receipt 进入 San ledger，文本报告不能直接完成 gate。
直接借鉴 P1统一 goal、heartbeat、schedule、后台队列 San 已有 GoalRuntime 和 DurableScheduler，缺的是统一的用户入口、worker ownership 和恢复语义。 每个自动 tick 都要有去重、claim、取消、预算和可恢复状态；漏 tick 合并而非无限堆积；完成仍需 acceptance evidence。
直接借鉴 P1MCP session ownership / lease fencing Prime 的 ACP MCP commit 给出明确的 owner-bound configuration、release、rollback、reap 形态，能补 San 多客户端/跨会话场景的生命周期风险。 同名 session-scoped server 不能覆盖别的 owner；断开先移除 credential binding，再关闭 transport；释放失败不可阻塞整个 session shutdown。
谨慎借鉴 P1Evidence-aware autonomous continuation Prime 的 bounded limits、gate output、changed-worktree 去重逻辑实用；但 San 的完成条件更严格。 把 gate 结果转换为 typed receipt；只在缺少 required evidence 或有 retryable defect 时续行；limit reached 永不渲染成 success。
谨慎借鉴 P2Optional persistent Python/JS kernel workspace 适合数据清洗、长文档、批量分析和程序化工具组合，San 已有 eval bridge 可作为切入点。 默认不改变显式工具与审批语义；限制内存、执行时间、并发和依赖安装；kernel snapshot 只保存工作变量，不成为完成证据或系统 prompt。
谨慎借鉴 P2Python-backed executable skills 能把重复 research workflow 封装成真正 callable，比纯 Markdown 指引更强。 先做显式安装、依赖锁定、审核和隔离；不允许 skill 自行修改稳定 prompt 或静默取得 provider/MCP credential。
无需跟随 把 San 的默认模型面改成单一 ipython 工具 会削弱 San 现有工具级 schema、审批、渲染、LSP/debug 和 typed evidence 边界；收益主要来自组合便利，不足以抵消治理损失。 保留显式工具；若增加 kernel，只作为额外工具/工作区，不做全量控制面替换。
无需跟随 把 continual harness 或 raw kernel state 当成 San 的 Context Steady 它们保存可复用工作状态，却不自动保证 active request、来源引用、保护带和 provider budget 正确。 Context Steady、summary authority、quality gate 和 journal-derived continuation 保持为独立硬边界。
无需跟随 默认所有任务都多 agent / autonomous San 自己的 GSAR README 结论也是 solo 作为日常默认，team/council 作为风险开关；Prime 的自治同样是 bounded policy，不是成功保证。 继续用风险分层：solo 低开销，team/council 高风险；自动化必须有预算、取消和可解释 blocker。

6. 建议的 San 下一步顺序

  1. 先收拢 resident runtime。把现有 launch broker、session lease、GoalRuntime、DurableScheduler、CrossSessionClient 和 session journal 串成一个“San background task”产品对象。第一版不需要 Web；CLI 关闭后可重连、可查看状态、可取消、可恢复就足够。
  2. 再统一子代理 admission 与证据回传。让 task/eval agent/San Loop 三条入口共享 child registry、execution scope、budget 和 lifecycle event；父模型收到的是 handle/status，完成与否由 host receipt 和 San Loop review 决定。
  3. 随后补 MCP owner fencing。沿用现有 MCPManager 的 config/profile/OAuth/reconnect，不新造平行配置；增加 session-scoped ACP/remote client server map、owner token、release/reap 和 failure rollback。
  4. 最后做可选 kernel workspace。先用 San 已有 eval/worker bridge 证明数据处理和批量操作收益，再决定是否引入持久 IPython；不要为了架构对称而引入。
目标架构：Resident San Worker → AgentSession → Context Steady + ExecutionRuntime → San Loop / task children。Prime 提供 worker/runtime 方向，San 继续负责“模型看什么”和“什么证据才算完成”。

7. 证据边界与未验证事项

  • 已观察：Prime 官方仓库 README、architecture/daemon/RLM/long-running/skills/usage 文档、autonomous.ts、package metadata、main commit feed 与 ACP MCP patch；San 本地 README、package metadata、Context Steady、execution-control、San Loop、goals、task/eval、peer、launch 和 MCP 文档/源码。
  • 未做：没有在同一任务集上安装并运行 Prime 与 San 的对照实验；没有重新执行 San README 中的 GSAR 或 Context Steady benchmark；没有把 Prime 文档中的 daemon stress benchmark 当作已验证性能结果。
  • 因此：“Prime 在 resident runtime 更完整”“San 在 typed completion governance 更强”是基于源码/设计边界的架构判断，不是吞吐、成本、成功率或用户体验的实测排名。
  • 版本注意：Prime package 0.7.4 发布于 2026-08-19，而 main 的 ACP MCP 提交更新于 2026-08-20；该提交代表当前 main 的方向，不应自动视为稳定包已发布能力。San 的 17.0.2 是本地 package metadata，源码可能包含 Unreleased 变更。
