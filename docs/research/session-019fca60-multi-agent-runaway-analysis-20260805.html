多 Agent 跑一夜、累计数亿 Token：不是单一“上下文稳态故障”

调查对象：主会话 JSONL、主/子会话 Context Probe、187 个子 Agent 日志，以及当前执行、重试、稳态维护与循环守卫实现。

结论：这是一个有真实进展但无法收敛的语义活锁（orchestration livelock）。Context Steady 是明确的放大器：本次 84 次物理压缩全部由 steady_target 单独触发，失控回合中 72 次，压缩后主工作集通常降到约 44K；18 次计划重建中 17 次紧跟压缩。但它不是数亿 Token 的直接来源，也不是唯一根因。主因是自由编排模式没有跨子任务的总预算/终止条件，故障 Provider 又被每个子会话独立重试和反复唤醒；现有收敛守卫把“新文件/新参数/新子任务名”当作进展，并豁免 hub，因此没有截停跨 Agent 的语义重复。

6. 因果链与根因排序

自由多 Agent 编排

没有逻辑回合共享的 token / request / wall-clock / spawn 总预算。

Provider 故障

每个子会话独立做最多 10 次重试，主 Agent 又反复唤醒/重派。

高频稳态压缩

每约 11 分钟将主工作集重写到约 44K，计划状态反复重建。

守卫看见“新进展”

新路径、新输出、新任务名绕过 no-progress，hub 又被豁免，最终不收敛。

1

主因：编排层缺少共享预算与终止合同

任务可以不断生新任务、唤醒旧 Agent、重新审查同一能力族。单 Agent 限制无法约束团队总量。

2

重要放大器：Context Steady 的频繁物理压缩

全部 84 次均为 steady-only 触发；与 Todo 重建高度同步。它降低单次上下文成本，却牺牲了编排连续性。

3

重要放大器：Provider 失败与错误重试策略

确定性无凭证错误仍走 transient 重试；Provider 级熔断没有跨子会话共享。

4

监控错觉：累计 Prompt 把 Cache Read 每轮相加

解释数值为何迅速上亿，但不改变实际存在的 132.35M 新输入与严重非收敛事实。

7. 修复优先级

  1. P0 · 为自由 task/hub 编排增加父回合共享硬预算。至少覆盖总 Provider requests、总 input/cache/cost、总 wall time、总 spawn 数；预算由所有新建和 revived 子 Agent 共同扣减，不能按子会话重置。达到阈值后强制进入一次“汇总现有证据并收尾”。
  2. P0 · Provider 级全局熔断。同一 Provider/模型在并发子会话中连续出现 auth_unavailable 或 stream stall 时，暂停新派发与旧 Agent 唤醒，取消等待队列，切换已验证 fallback 或向主 Agent返回明确阻塞。熔断状态必须跨子会话共享。
  3. P0 · 修正 AuthFailed + Transient 的恢复。允许重试处理器执行一次凭证轮换/模型 fallback；若没有实际切换，不允许对 auth_unavailable 做 10 次同模型重试。Stream stall 使用更小的有限预算，并计入 Provider 级失败预算。
  4. P0 · 增加编排语义收敛守卫。按“目标能力族 + 文件范围 + acceptance gate”去重，不按任务显示名去重；跟踪 mutation、测试、gate 状态的真实 delta。重复 hub send/jobs/inbox 若没有状态迁移也必须累计 no-progress，不能全部豁免。
  5. P1 · 把结构化执行账本放到压缩边界之外。持久化 owner、任务族、状态、已接收 mutation/test 证据、剩余 gate、失败 Provider；每次 compaction 后确定性注入。已有 Todo 未结束时拒绝无条件 init 覆盖，要求显式 reconcile。
  6. P1 · 用现有有预算执行循环承载大型团队任务。在自由 task 编排获得共享预算前，M3 级任务应走带 maxTokens、maxDurationMs、maxProviderRequests 的 /team 执行循环；当前这些预算默认 0，必须显式设置非零值。
  7. P1 · 做 Native/Steady 多 Agent A/B。同一固定任务、固定 Provider 健康状态、固定共享预算下比较通过率、重派数、Todo replace 次数与 Token。不要仅永久关闭 Context Steady：Native 阈值更高，可能减少状态重写，也可能增加每次请求成本。

临时止血：将项目级 retry.maxRetries 降到 2–3，设置非零 task.maxRuntimeMs，降低 task.softRequestBudget，并在多 Agent 开始前设置执行循环的共享 token/time/request 上限。这些只能限制损失，不能替代语义去重和 Provider 熔断。

8. 结论边界

  • CONFIRMEDContext Steady 确实触发了本次所有物理压缩，且压缩与计划重建高度相关。
  • CONFIRMEDContext Steady 的直接 LLM 开销只有 10.78M Prompt；绝大部分累计 Token 来自主/子 Agent 数千次请求。
  • CONFIRMEDProvider 故障、默认 10 次重试、反复 hub 唤醒和跨任务无共享预算共同造成长时间不收敛。
  • [INFERENCE]如果只关闭 Context Steady，计划重建可能减少，但任务仍可能在 Native compaction、Provider 重试和无限派发下继续失控；没有 A/B 不能声称“关闭稳态即可修复”。
  • 最终分类：不是严格的同一指令死循环，而是跨 Agent、跨压缩边界、持续产生少量新证据的语义活锁。
