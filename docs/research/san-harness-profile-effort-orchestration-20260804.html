San Model Harness Profile 与 Effort Orchestration

这是 Logical Model Routing 之后的下一层：不再要求用户理解每个模型和服务商，而是让用户表达任务需要多少努力，由 San 选择逻辑模型，并为该模型装配最能发挥其能力的 harness。

定位：下下个版本 状态：方向文档 依赖：Logical Model Routing 不包含：Remote Control
核心判断：模型越强，Harness 越不应依靠大量 must do / must not 与模型争夺推理控制权。稳定内核只保留安全、权限、协议和状态不变量；其余部分应成为可版本化的指导与能力增强 Profile，并通过 eval 证明它提高了任务质量或智能效率。

一、与前后版本的边界

Task / Effort用户显式选择，后续可由 San 判断
→
Logical Model Policy选择模型或模型池，不感知 provider
→
Harness Profile指导、工具、上下文、推理与 loop policy
→
Provider Route由上一版本 Route Group 选择具体服务商
层次回答的问题配置引用不应该知道
Effort Policy这个任务需要多少资源与自主性？Logical Model / model pool服务商名称、baseUrl、凭证
Harness Profile怎样让选中的模型发挥得最好？逻辑模型、模型族、能力标签价格排序、账号额度
Route Policy同一逻辑模型由哪个服务商执行？Concrete provider/model routes任务应使用哪个模型
Remote Control从哪台设备控制哪个 executor？host/session/task identity模型内部 prompt 与 provider secret

二、Profile 不是另一份巨型系统提示词

Stable Kernel工具执行、权限、审批、session 状态、日志、错误边界。只有真正不可协商的不变量进入这里。
Generic Guidance简短的通用工作原则，例如先理解任务、使用工具验证、完成后报告。默认使用指导语气。
Family ProfileOpenAI reasoning、Claude、DeepSeek、Qwen、GLM、Gemini 等模型族的推理、工具和 replay 特征。
Exact Model Profile具体模型的 lean/verbose posture、effort map、known quirks、工具暴露和 context policy。
Task / Effort Overlay任务阶段、风险、规模与努力档位带来的临时调整，不改写模型身份。
Transport Overlay由 concrete route 决定的 API dialect、wire encoding、headers、thinking 参数和 provider session。
User / Project PolicyAGENTS.md、SYSTEM.md、权限与用户明确要求。用户意图和安全边界始终高于优化 Profile。
约束分级：安全、权限、不可逆操作和协议正确性可以是硬约束；工作方法、探索路径、工具偏好和回答形式默认是建议。Profile 编译器必须能区分 invariant 与 guidance，不能把所有内容最终都渲染成同样强度的 system 命令。

四、建议配置形态

harnessProfiles:
  openai-reasoning:
    instructionPosture: guided
    promptModules:
      - core-workflow
      - tool-use-guidance
    tools:
      exposure: essential-plus-discovery
    context:
      stablePrefix: strict
      appendOnly: auto

  gpt-5.6-sol:
    extends: openai-reasoning
    instructionPosture: lean
    reasoning:
      defaultEffort: medium
      preserveModelAutonomy: true
    loop:
      progressReminders: on-stall

effortPolicies:
  low:
    models: [gpt-5.6-terra, glm-5.2]
    maxParallelAgents: 1
  medium:
    models: [gpt-5.6-sol]
    defaultModelEffort: medium
  high:
    models: [gpt-5.6-sol, claude-fable-5]
    defaultModelEffort: high
  ultra:
    models: [claude-fable-5, gpt-5.6-sol]
    advisor: gpt-5.6-sol
    defaultModelEffort: xhigh
  • Prompt 内容仍放在静态 .md 文件，通过 Handlebars 注入动态内容；YAML 只声明模块和政策。
  • Profile 必须有稳定 ID、版本、适用模型、最低 San 版本、来源和 eval provenance。
  • Exact model 不存在 Profile 时，按 exact → family → API dialect → generic 回退，并允许 inspect 最终组合。
  • 切换 Logical Model 或 effort 时重新编译；同模型 provider route fallback 只重算 transport overlay。

五、Effort Dial 的产品语义

Low

低成本、低等待

适合明确、局部、可快速验证的任务。优先小模型/低 effort，限制并行与反复审查。

Medium

默认工作档

选择综合能力和成本平衡的逻辑模型，允许正常工具循环与一次验证。

High

复杂推理与高风险

更强模型、更高 effort、完整验证；必要时加入 advisor，但仍避免无界并行。

Ultra

昂贵但追求上限

适合架构迁移、复杂调试和重要决策，可组合主模型与 oracle/reviewer。

Explicit first

先由用户选择

第一版 effort 是明确输入，不让分类器悄悄扩大成本或切换模型。

Auto later

后续学习任务难度

自动模式输出可解释的 effort decision；用户预算、项目政策和手动选择可覆盖。

Effort 的输出是一个 Execution Intent，至少包含 logical model、model effort、并行预算、验证强度和可选 advisor。它不直接输出 provider；provider route 由 Logical Model Routing 继续解析。

六、版本路线

H0 · Inspect输出当前 resolved prompt、tool surface、effort、cache boundary、compat 与 token 成本。先知道实际发给模型什么。
H1 · Static Profiles建立 profile registry、继承/组合、版本和切模重算；先落少量模型族 Profile。
H2 · Effort Intent用户选择 low/medium/high/ultra；映射到 Logical Model、effort、并行和验证预算。
H3 · Eval ReleaseMetaharness 对比 baseline/candidate，质量非劣后灰度、晋级、回滚；Profile 独立发版。
H4 · Adaptive自动判断 effort、基于受控数据调整 policy；保留预算上限、可解释与关闭开关。
建议的“下下个版本”发布边界：完成 H0–H2。用户可以 inspect 实际 Harness、Logical Model 能解析到稳定 Profile，并使用显式 effort dial 调度模型；H3/H4 属于后续持续迭代，不应阻塞首版。

七、Eval 与晋级规则

Profile 的目标不是“token 越少越好”，而是在质量门槛下提高智能效率。

指标层核心指标晋级规则
质量任务成功率、测试通过、正确性、安全性先满足非劣或显著提升；不允许用便宜掩盖质量下降
Agent 效率总 turns、工具调用、返工、无进展循环、用户打断至少一个关键维度改善，且无严重回归
模型效率输入/输出/reasoning tokens、TTFT、wall time按任务类型分层比较，不用全局平均掩盖长尾
缓存cache read/write、uncached input、first divergence稳定前缀变化必须有 provenance 与收益说明
可靠性tool parse failure、400、截断、retry、unsafe recovery不得新增协议级或副作用风险
经济性实际费用、premium requests、service tier在质量门槛之后比较
  • 每次 trace 记录 logical model、concrete route、profile ID/version、effort policy version 和工具集摘要。
  • 同模型跨 route 的差异与不同 Profile 的差异必须分开实验，避免错误归因。
  • benchmark profile 与日常 profile 分离；官方榜单参数只用于提出候选，不直接成为默认。
  • 任何自动晋级都必须可立即回滚到上一稳定版本。

八、非目标与风险

首版不做

  • 不为每个 provider fork 一套 agent。
  • 不自动在线下载未经验证的 Profile。
  • 不把所有模型差异都写成 prompt 文本。
  • 不让 auto effort 无上限增加费用和并行 agent。
  • 不以单个社区案例决定默认策略。

主要风险

  • Profile 继承过深，最终组合无法解释。
  • 指导语仍被渲染成大量强约束，与强模型冲突。
  • 工具面变化破坏缓存，却被误认为 prompt 优化。
  • 模型、route、Profile 同时变化，评测无法归因。
  • 努力档位变成隐藏的模型营销名称，而非稳定资源语义。

九、完成定义

  • san harness inspect 能解释最终 prompt 模块、工具面、effort、cache 和 transport overlay。
  • Profile 是独立、版本化、可灰度和可回滚的发布物，不再散落为 model ID if/else。
  • 切换 Logical Model 会完整重算 Profile；切换同模型 provider route 只重算 transport。
  • 显式 effort dial 只引用 Logical Model 与资源政策，不引用 provider。
  • Profile 默认采用指导语气；硬约束有明确类别和来源。
  • 至少一组真实模型 Profile 通过质量非劣门禁，并在效率或可靠性上有可复现收益。
