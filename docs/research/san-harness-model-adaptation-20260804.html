Competitive research · 2026-08-04

San Harness、模型适配与 Remote Control 竞品研究

覆盖 Amp、Codex、Claude Code、OpenCode、Pi、DeepSeek Harness 与 Reasonix；重点不是罗列功能，而是回答三个问题：同一基模为何会在不同 agent 中表现不同、San 当前差距在哪里、以及多模型 harness 怎样避免永远追在模型发布之后。

结论截至 2026-08-04 官方资料优先 社区数据明确降权 本地代码实测
核心判断：用户的方向判断成立，但问题不是“多模型产品必须为每个模型写一套 agent”。正确拆法是：保持一个稳定、通用的执行内核，把 prompt、工具 ABI、wire encoding、采样、缓存边界、压缩和 loop policy 做成可声明、可版本化、可 A/B、可快速回滚的 Model Harness Profile。San 已有这套架构的大部分底座，真正缺的是 profile 产品层和以 eval 为门禁的发布闭环。

一、先给结论

Remote Control

Amp 在产品形态上推进最快

Amp 已从“远程查看一个本地线程”推进到远程启动任意机器上的 agent、持久任务、定时唤醒和多人加入。Codex 与 Claude Code 则收敛到更清晰的安全架构：本机 executor + 出站 relay + Web/移动控制面。

Model adaptation

竞品都在做模型级适配

Codex 直接为 GPT-5.6 Sol/Terra/Luna 刷新 bundled instructions；Claude 对新模型默认 lean prompt、对旧模型保留旧策略；OpenCode 源码中按模型族选择独立 prompt。趋势不是“一份提示词适配所有模型”。

San

底层强，profile 层弱

San 的 provider 兼容、reasoning replay、tool dialect、append-only context、Context Steady、Metaharness 和 RPC v2 都很强；但 prompt/tool surface 仍偏重，模型切换时部分决策不会重算，也没有独立版本化的模型 profile。

Evidence

“Sol 在 Codex 不如 Pi/OpenCode”尚未被证实

有可信的机制证据和社区个案证明 harness 会造成巨大效率差异，但目前缺少独立、同模型、同题集、同预算、多次重复的 Codex vs Pi/OpenCode 对照。不能把体感直接升级成普遍结论。

DeepSeek

0731 是“模型 × harness”联合成绩

DeepSeek 明确披露 V4 Flash 0731 的 Code Agent 分数使用未发布 DeepSeek Harness minimal mode、max effort、特定采样参数；但 0731 同时做了 post-training，且未公布 harness ablation，因此无法把增幅单独归因给 harness。

Priority

先降低固定输入，再做 profile

San 当前一次请求的固定输入约 12,068 tokens，其中工具 schema 8,047，占 66.7%。这比继续微调几百字系统提示词更值得优先处理；随后再对 Sol、Claude、DeepSeek 做受控 profile 实验。

二、竞品近况：最近真正有方向意义的变化

2026-05-06 → 07-22 · AMP

从 remote-controllable CLI，扩到 runner、schedule 与 multiplayer

Neo 重做 CLI，加入线程远程控制、90% 自动 compaction、steering/queue 和插件 API；Agents Everywhere 将所有活动线程汇总到 Web/移动/CLI；Agents Anywhere 支持从 Web 远程唤起任意已注册机器和目录上的 headless runner；随后又加入 Schedule 与 Multiplayer。

值得注意的产品纠偏：Amp 取消可发现的公开线程，并为敏感远程操作加入 passkey proof-of-human。这说明 remote 的安全边界不是附属能力，而是核心产品能力。

2026-06-25 → 07-29 · CODEX

Remote GA、MCP tool search、模型指令包与远程 Code Mode host

Codex changelog 显示：Remote 在 6 月 25 日 GA；MCP tools 对支持的模型默认走 tool search；7 月 18 日刷新 GPT-5.6 Sol/Terra/Luna bundled instructions；7 月底又加入 session 命名/固定、side conversations、Agent Plugins 和可通过 WebSocket 连接的远程 Code Mode host。

app-server 协议 已包含 thread/turn/item 生命周期、实验性 WebSocket、remoteControl pairing/client revoke、环境发现与 remote exec。它比“一个网页 UI”更像完整 agent control plane。

当前 · CLAUDE CODE 2.1.x

Lean prompt、prompt audit 与成熟的本地远程执行

Claude Code changelog 记录：新模型默认 lean system prompt，但 Haiku、Sonnet/Opus 4.7 及更早型号保留旧 prompt；曾将日期移出 system prompt、增加跨用户可缓存动态 section 的排除开关，并持续修复 prompt cache invalidation。近期还加入 prompt-audit，专门检查 prompt/tool description 中面向旧模型的遗留模式。

Remote Control 已支持 server mode、最多 32 并发 session、按 session 建 worktree、浏览器/手机同步 subagent 状态、断线恢复和 Trusted Devices。执行与文件访问留在本机，本机只发起出站 HTTPS 连接。

当前 · OPENCODE / PI

OpenCode 走模型族 prompt；Pi 坚持小内核

OpenCode 的 system prompt selector 会按模型 ID 选择 Anthropic、GPT、Codex、Gemini、Kimi、Meta 等独立 prompt；其 Web UI 与 headless server 提供本地/LAN 的 client-server 形态，但还不是 Amp/Codex/Claude 那种互联网出站 relay 产品。

Pi 的 核心 prompt 默认只围绕 read/bash/edit/write，扩展通过 tools、prompt snippets、provider payload hooks 接入。它的优势首先是低固定开销和可组合性，不等于已经对每个模型做了深适配。

2026-07-31 · DEEPSEEK

V4 Flash 0731 公开承认评测 harness 是结果的一部分

官方更新 与 模型卡 明确给出 Code Agent 评测设置：未发布的 DeepSeek Harness、minimal mode、max effort、temperature=1、top_p=.95。模型原生面向 Responses API，并专门适配 Codex；模型卡还提供独立 encoding/parser，而不是通用 Jinja chat template。

四、Harness 不是系统提示词：至少有八层

把表现差异都归因于 prompt 长短会误导优化。真正的 coding harness 是一个闭环系统，任一层都可能让同一个模型出现明显不同的成功率、token、延迟和稳定性。

Wire encoding / parser消息如何编码、reasoning block 如何回放、tool call 与截断 JSON 如何解析、provider 特有字段如何保真。DeepSeek 0731 单独发布 encoding/parser，说明这不是实现细节。
Sampling / efforteffort 档位、temperature、top_p、max output、service tier。评测 profile 与日常 profile 不应该混用。
Tool ABI工具数量、schema 复杂度、native/freeform/programmatic tool、tool search、并行调用、patch/shell 的反馈质量。
Prompt posturelean/default/legacy，规则是否重复，是否按模型族选择措辞，动态内容是否放进稳定前缀。
Loop policytool choice、续写、重试、no-progress、repair、delegation、并行策略、什么时候要求总结或切换模式。
Context / cache字节稳定前缀、显式 cache breakpoint、append-only log、compaction 触发点、压缩产物是否改写历史。
Environment quality搜索、编辑、诊断、测试、terminal stream、权限和错误反馈。工具成功率本身就是模型上限的一部分。
Eval / telemetry质量、回合、总输入、uncached input、cache write/read、tool parse failure、stall、wall time；没有这层，适配只能靠体感。

七、目标架构：通用 kernel + Model Harness Profile

多模型接入并不意味着每家都 fork 一套 agent。最稳定的边界是：执行、权限、日志、工具实现、session state 属于 kernel；容易随模型变化的决策全部进入 profile。解析优先级应为 exact model → model family → API dialect → generic，并在每次切模时重新解析。

ModelHarnessProfile { id, version, match: { provider, api, family, exactModel } prompt: { posture, modules, legacyFallback } tools: { surface: essential | discoverable | macro, schema: inline | deferred | simplified, calling: native | freeform | programmatic, parallelism } wire: { encoder, parser, reasoningReplay, repairPolicy } sampling: { effortMap, temperature, topP, maxOutput, serviceTier } loop: { toolChoice, continuation, retry, noProgress, delegation } context: { stableRegions, cacheBreakpoints, compaction, dynamicPlacement } eval: { suite, baseline, nonInferiority, efficiencyGate, provenance } }

GPT-5.6 Sol profile

  • Responses native；跟随官方 Sol 指令包做独立 A/B，而不是复用 generic prompt。
  • 优先验证 freeform patch/shell、Programmatic Tool Calling 或等价 macro tool；这是最可能显著减少 turn 的位置。
  • 显式 cache breakpoint；max/ultra 只给困难任务，简单任务不强制 subagent。

Claude 新模型 profile

  • 新模型走 lean；旧型号保留 legacy，按 Anthropic 自己的代际边界回退。
  • 日期、MCP 动态说明等放到稳定缓存区之外；避免重复 harness reminder。
  • 开启 tool search/按需 schema，并分别验证 adaptive thinking 与并行 agent。

DeepSeek V4 Flash 0731 profile

  • 单独做 encoding/parser golden tests、reasoning replay、截断与 tool JSON repair。
  • benchmark profile 使用官方 max + temp 1 + top_p .95；日常 profile 另行评估，不能照抄榜单参数。
  • append-only、首分歧定位和 cache cost 作为强制 telemetry；不发送不支持的 tool_choice。

Profile 发布原则

  • profile 与 San 主版本解耦，可签名、灰度、回滚，并记录 catalog/CLI 最低版本。
  • 每个 profile 携带 eval provenance，不允许只凭 anecdote 提升为默认。
  • 用户 override 与 provider compat overlay 保留，但最终 resolved profile 必须可解释。

八、建议路线：先可观测，再适配，再远程产品化

P0 · 1–2 weeks

Harness inspect

增加 san harness inspect --model：输出 resolved profile、prompt/schema tokens、encoder、effort、cache boundary、动态 section。trace 记录 profile/version 与 first divergence。

P0/P1 · 2–4 weeks

瘦工具面 + profile MVP

先处理 top-level schema；拆 prompt kernel/modules；切模时重算 tool/prompt/cache 决策。落地 Sol、Claude、DeepSeek 三个 profile。

P1 · continuous

Metaharness promotion gate

同题、同模型、同预算、多 seed 比 baseline/lean/profile；质量须非劣，随后比较 turns、uncached/cache write、parse failure、stall、成本与延迟。

P1/P2

Runner + relay

把 RPC v2 产品化为 headless executor 与出站 relay；先做 pair/revoke、inventory、replay、approve，再做 schedule/background，最后才是 multiplayer。

实验门禁建议：每个候选 profile 至少覆盖 20–30 个任务、每配置多次重复；先设质量非劣阈值，再优化总 turn、总输入、uncached input、cache write、工具解析失败、无进展循环、wall time 与成本。公开 benchmark 只能用于提出假设，不能直接决定默认配置。

九、最终判断

  1. Harness 迭代确实开始落后于基模。原因不是工程师不会写 prompt，而是模型厂商同时改变 wire format、tool semantics、effort、缓存和并行能力；用散落 if/else 追版本必然越来越慢。
  2. San 不需要选择“通用”还是“深适配”。执行内核继续通用，profile 必须深适配；这是同时支持多 provider 与快速追模型的唯一可维护方案。
  3. San 当前最大短板不是推理 provider 支持。而是固定工具输入过重、模型姿态没有产品化、切模重算不完整、缓存边界不可见、Metaharness 还没变成发布门禁。
  4. Reasonix 与 DeepSeek 的信号应该吸收，但不用重造已有能力。San 已有同类 append-only 核心；下一步是 byte/token divergence telemetry、DeepSeek 0731 golden encoding tests 和官方参数 profile。
  5. Remote Control 应与 harness 解耦推进。它是控制面与执行面的协议工程；共享 session/event/approval substrate，但不会直接提高单模型能力。竞品已经证明，本地 executor + outbound relay 是当前最稳妥的产品边界。
