五、确认发现（按优先级）

LMR-01 · 配置热更新后，同 ID route 未重绑定新 target

高 / P1
置信度 0.99Phase 0 刷新边界Phase 1 session affinity
精确证据：packages/coding-agent/src/session/agent-session.ts，AgentSession.#ensurePromptModelRoute，18405–18416：新 registry 只按 routeId 查 eligibility，随后把旧 lease 与旧 model 交给 API-key 检查并直接返回。packages/coding-agent/src/session/model-route-lease.ts，ModelRouteLeaseController.recover，185–209：解析结果 route ID 相同即在 197 行返回，不比较 policyVersion 或 modelSelector。活动 lease 本身已保存这两个字段，见 10–17。

失败场景

会话持有逻辑模型 coding 的 route main → provider/a。用户成功热更新 models.yml，保持 route ID 为 main，把 target 改为 provider/b。新 registry 认为 main 合法；旧模型 provider/a 的 key 可用，于是每个后续 turn 继续请求已经从配置移除的端点。

合同影响

违反 Phase 0 “registry refresh 后原子替换 compiled index；在途 session 到请求边界使用旧 version”的后半段，也违反 Phase 1 实际 route 必须由当前 Logical Model policy 决定。配置显示与真实执行发生永久分叉。

用户影响

用户以为已切换 provider/endpoint，实际仍向旧服务发送请求；可能持续失败、继续使用已撤销或昂贵端点，亦可能形成合规与数据驻留风险。重启会“修好”，增加隐蔽性。

测试缺口

model-route-registry.test.ts:115–143 只验证 registry snapshot 被替换；model-route-lease.test.ts:7–66 的 reload 保持 selector 不变。缺少“相同 route ID、不同 selector/policy version、活动 AgentSession 在下一请求边界重绑”的合同测试。

修复摘要：在请求边界比较 active lease 的 policyVersion 与当前 group，以及 route ID 对应的当前 modelSelector；任一变化都必须重新解析、更新 lease、刷新 concrete metadata，并通过统一 provider-session-reset 入口切换后才能继续。详见修复计划 LMR-01。

LMR-02 · Route billing override 未应用到 effective model

高 / P1
置信度 1.00计费正确性硬预算
精确证据：packages/coding-agent/src/config/model-route-registry.ts，compileModelRouteRegistry，130–149：model 永远是 catalog 对象（131, 143），billing 只被单独冻结保存（148）。全源对 route billing 的读取仅见 schema 校验和该保存点。provider 以传入 model.cost 计算 usage.cost；硬成本上限直接读取 active model cost，见 packages/coding-agent/src/sdk.ts:2997–3015。

失败场景

route 为代理或私有 endpoint 配置 billing: { source: "override", input, output, cacheRead, cacheWrite }，价格不同于 catalog。resolver 选中该 route 后仍把未修改的 catalog model 交给 Agent/provider。

合同影响

配置字段被接受、编译、保留，却不产生承诺的可观察行为，违反显式 route 账单和版本完成定义中的准确 RPC/session 输出。错误不仅是展示问题，而是 accounting source 错误。

用户影响

session footer、HTML 导出、usage analytics/RPC 和累计费用全部错误；maxTotalCost 可能过早停止，也可能超过用户硬预算。任何基于成本的外部审计都会继承错误值。

测试缺口

没有测试断言 billing override 改变 selected model cost、provider usage、session/RPC 汇总或硬成本预算；也没有断言 catalog model 不被全局突变。

修复摘要：在 route 编译或选择边界创建 route-local effective model，仅以 billing override 替换 cost，保留 selector/transport/capability 且绝不修改 catalog 对象；所有执行和预算路径使用该对象。详见修复计划 LMR-02。

修复摘要：为 TUI 搜索、显示与 filter 分类，以及 HTML 搜索、tree 标签和主 transcript dispatcher 添加显式分支；所有用户字段转义，cooldown 可选。详见修复计划 LMR-03。

LMR-04 · 备用 route 可承载上下文时，逻辑模型仍被 picker 禁用

中 / P2
置信度 0.99Alt+Pcontext eligibility
精确证据：packages/coding-agent/src/modes/components/model-browser.ts，buildLogicalBrowserItems:167–217；核心缺口在 179–187：resolver request 只有 suppression/auth/provider availability，没有当前 context requirement，条目只持有 active/primary 代表模型。随后 ModelBrowser.#isDisabled:560–565 仅比较 item.model.contextWindow。Alt+P 在 model-picker.ts:104–107 启用该禁用逻辑，尽管 picker 已收到 currentContextTokens。

失败场景

用户影响

用户被迫直接选择 concrete backup，丢失 logical intent、session affinity 与后续 route fallback；或误以为整个逻辑模型不支持当前上下文。

测试缺口

model-route-resolver.test.ts:125–146 只测核心 context rejection；model-browser.test.ts 只有搜索/性能显示测试。没有 8k/128k logical group + 16k picker 的可激活合同测试。

修复摘要：让逻辑条目构建接收当前 context requirement，并用同一 registry resolver 选择满足条件的代表 route；active route 只有在同一 trace 下仍 eligible 才可优先。详见修复计划 LMR-04。

LMR-05 · Schema 接受运行时永不执行的 fallback 类别

中 / P2
置信度 0.99Fail fast安全策略
精确证据：packages/coding-agent/src/config/model-routes-schema.ts:7–11 定义完整 RouteFailureCategory，ModelRoutePolicySchema:21–26 允许其全部进入 fallbackOn；custom validator :97–108 只检查重复。运行时 packages/coding-agent/src/session/model-route-lease.ts，resolveFallbackDecision:139–149 即使策略列出 refusal、user_abort、context_overflow 也无条件返回 not_allowed。

失败场景

用户配置 fallbackOn: [refusal] 或另外两个类别。配置校验成功、服务正常启动；触发该错误时 route 不切换，且没有配置错误说明该值不可执行。

合同影响

接受的配置与安全运行时语义不一致，违反 Phase 0 的明确配置诊断和 Phase 1 的“unsafe replay 明确失败，不静默降级”。运行时的安全禁止是正确的，错误在配置边界。

用户影响

运维人员依据已成功加载的 policy 预期 failover，实际行为不同；只有生产错误发生时才发现策略是 no-op。

测试缺口

没有逐项断言 policy schema/validator 拒绝三类安全禁止值并给出 logicalModels.<id>.policy.fallbackOn[index]；也没有测试允许集合与运行时可执行集合完全相等。

修复摘要：保留完整 failure category 供分类和事件使用，新增更窄的 policy fallback category type/schema，并在配置边界拒绝三个不可重放类别，保留精确路径。详见修复计划 LMR-05。

七、本地体验验收清单

这是修复后必须实际执行的用户旅程。当前文档只做源审查，下面不把未执行项伪装成通过；阻断项直接对应确认发现。

  • 零配置启动：不配置 logicalModels，模型列表、concrete selector、resume 与 fallback 行为保持原样；当前有静态门控证据，仍需 full suite 绿。
  • 显式逻辑模型：配置同模型三条 route，/models 与 Alt+P 显示 Logical Models、当前 concrete route、备用数量，Enter 保存 logical intent。
  • 确定性选择：首个已鉴权、provider enabled、支持 tools/image/effort/context/output 的 route 稳定胜出；拒绝原因不泄露 secret。
  • 长上下文选择：8k primary + 128k backup，在 16k 会话中 logical row 仍可选并路由到 backup；当前被 LMR-04 阻断。
  • 安全 fallback：首 route 429 时先轮转凭证，凭证耗尽后当前 turn 切第二 route 成功；已有 tool call 时不得 replay。
  • Cooldown recovery：fallback 后保持 affinity；cooldown 结束后的下一用户 turn 才恢复更高优先级 route，harness profile 不变。
  • 配置热更新：活动 route ID 不变但 target 从 provider A 改 B，下一请求边界必须重绑 B、reset provider session 且不再请求 A；当前被 LMR-01 阻断。

  • 审计：/tree、搜索和 HTML 导出均展示 logical/from/to/reason/cooldown；当前被 LMR-03 阻断。

  • 错误配置：非法 ID、空组、重复 route、未知 model 和不可执行 fallbackOn 都在启动/刷新时给出精确 YAML 路径；当前被 LMR-05 部分阻断。
