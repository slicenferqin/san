Architecture Decision Record · 2026-08-25

San 应采用 Harness-first
不是 Prompt-first Profile

领域身份必须由一套有状态、可执行、可恢复、可验收的 Harness 决定。系统提示只是这套 Harness 向模型投影当前事实和行动边界的一个输出，不是能力、状态或完成权威。

决策：Harness 是一等运行时对象系统提示：只读投影Coding：首个领域 Harness
决定：不设计“Profile → 一段系统提示词”的通用化路径。

SanRuntime 负责通用循环与事实账本；每个领域由一套 Harness Suite 接入能力、上下文、工具观察、验证、恢复和显示。模型只在 Harness 给出的当前可行动作空间中工作。Prompt 只能解释这个空间，不能创建或改变它。

一、先消除术语冲突

已观察到的命名冲突：model-route-registry.ts 的 harnessProfile 是逻辑模型路由字段；sdk.ts 取它作为模型相关 Prompt 输入；agent-session.ts 的注释也明确称它为“行为 profile”。它不是运行时 Harness。

新设计不能复用这个名字。否则“Harness”会被错误地降格为模型提示词配置。第一轮实际代码改动前，应将现有模型路由字段改名为 promptProfile 或 modelBehaviorProfile；该迁移只改术语，不改变模型路由行为。

二、职责边界

用户请求 / 外部事件 │ ▼ SanRuntime ── Agent Loop · 会话日志 · ExecutionScope · 调度 · Provider · 生命周期 │ ▼ Harness Suite ── 领域状态 · 能力/权限 · 世界观察 · 证据 · 验证 · 恢复 · 用户投影 │ │ ├──────────────────────────────┼── 工具执行与真实结果 │ │ ▼ ▼ 模型投影（System Prompt / Aside） ExecutionLedger（权威事实）
层拥有的权力明确不拥有
SanRuntimeAgent Loop、会话与 journal、Context Steady、执行作用域、共享预算、调度、Provider 生命周期、通用工具调度。不猜测“代码修好了”或“研究结论足够”。
Harness Suite领域工具集及权限、领域上下文、工具结果的结构化观察、验收标准、恢复策略、最小用户状态投影。不通过模型文字伪造结果，不绕过通用预算/终态规则。
Skill提供领域方法、可读操作说明和声明式证据要求。不直接授予工具、不直接写完成状态、不取代 Harness。
System Prompt向模型投影已存在的工具、约束、当前阶段、Skill 指引和事实摘要。不能授予权限、改变账本、接受证据、完成任务、选择 Harness。

三、Harness 不是一个大类，是一组受同一生命周期驱动的控制器

避免再造一个 2 万行总管类。一个领域 Harness 应由小而明确的控制器组成，并由一个 HarnessRun 聚合其当前状态：

能力 Harness

能做什么

创建并缩减工具集合；定义路径、网络、浏览器、凭据和子 Agent 的权限边界；工具注册表而非 Prompt 才是能力事实。

上下文 Harness

模型该看什么

从工作区、浏览器、文档、任务账本等收集结构化事实，生成可压缩的模型投影，而不是在 Prompt builder 内直接猜测世界状态。

观察 Harness

真实发生了什么

把工具结果规范化为 HostObservation、产物引用或 EvidenceReceipt；例如命令退出码、浏览器交互、API 响应或文件修改。

验证 Harness

什么时候能收口

按领域合同声明并更新 Acceptance Gate；最终完成仍由 ExecutionRuntime.finishScope() 校验真实 Host evidence。

恢复 Harness

断线后怎么继续

把领域状态写成可恢复快照和产物引用；重启后根据账本/外部状态恢复，不让模型凭记忆重放副作用。

投影 Harness

模型和用户各看到什么

把已确认的 Harness 状态投影成模型提示和“正在做 / 已完成 / 卡在哪里”三种用户表述；它没有反向写状态的权限。

四、最小运行时协议

以下是边界草图，不是立即落地的完整 API。关键是事件先到 Harness，Harness 产生受类型约束的效果，最后才渲染 Prompt。

事件Harness 可产生的确定性效果不能用字符串替代的原因
task_started固定 Harness id/version，建立领域合同、默认验证门、初始能力集和恢复状态。根任务重启、子 Agent 继承和审计必须使用稳定身份。
before_tool_call允许、拒绝或收窄调用；附加路径/权限范围；记录不可变的调用意图。Prompt 中说“不要做”不能阻止一个已经发出的工具调用。
tool_result提取 HostObservation、EvidenceReceipt、产物引用、状态变化和下一步可行动作。只有真实工具结果可以成为完成事实。
completion_requested检查领域门是否完整，将证据交给通用 Execution Runtime；给出继续、阻塞或完成申请。模型的“done”文本不应改变终态。
session_restored恢复领域快照，检查外部副作用是否仍在，决定继续、等待或转为需用户输入。恢复不是重新发送旧 Prompt。

概念上可表达为：

HarnessDefinition └─ createRun(runtimeContext) → HarnessRun HarnessRun ├─ capabilities() // 工具与权限的权威集合 ├─ onEvent(event) → effects // 状态、准入、观察、证据、调度决定 ├─ modelProjection() // 只读、可重建的模型上下文 ├─ userProjection() // 三种产品状态的最小投影 ├─ snapshot() / restore(snapshot) // 可恢复领域事实 └─ dispose()

效果必须是结构化的：能力变更、调用拒绝、Host observation、evidence receipt、任务准入、状态快照、模型投影。禁止用“附加一段提醒”替代任何会影响权限、进展或完成的决定。

五、现有代码的接缝

现有位置现在承担的职责Harness-first 后的归属
sdk.ts#createAgentSession一次性组装工具、MCP、Skill、模型、工作区、执行运行时和 Prompt。成为 Runtime 装配器；调用 HarnessDefinition.createRun()，再把其能力与投影接入通用会话。
tools/index.ts#ToolSession向 Coding 工具传入巨大、混合的会话依赖包。第一阶段由 Coding Harness 包住并继续复用；后续按能力切出工具上下文，不把所有字段做成可选项。
AgentSession 的 afterToolCall、setOnTurnEnd、transformContext当前工具后处理、循环制动、上下文维护和提示重建的实际接缝。统一派发 Harness 事件；现有 Coding 行为先通过 CodingHarness 适配，不搬迁、不重写。
ExecutionRuntime.recordHostObservation()把真实观察写入账本，并由 scheduler 进行进展判断。保持为通用权威写入路径；Harness 是 observation/receipt 的领域解释者，不是第二本账。
buildSystemPrompt()直接收集工具、Skill、项目上下文和工作区信息并渲染文字。退为 renderer：消费 HarnessRun.modelProjection()，不再承载能力判断或世界状态采集。
SessionSkillGateStateSkill evidence 与命令/文件工具结果之间的会话级接线。演变为 Harness 的验证控制器输入；Skill 仍提供声明，Harness 用真实观察满足或拒绝证据。

六、选择与继承规则

  • 根任务开始时由确定性选择器选择一个 Domain Harness；选择结果、版本和能力范围写入任务账本。
  • 子 Agent 继承父任务的 Harness 身份与更窄能力范围；不能由子 Agent 仅凭 Prompt 自己换成更高权限的领域。
  • 一个任务可使用多个 Skill，但 Skill 只能增强当前 Harness 的方法和验证声明；它不能把研究任务悄悄变成有写文件权限的 Coding 任务。
  • 需要切换领域 Harness 时，必须是显式、可恢复的账本状态转移；不是模型输出一行“现在进入浏览器模式”。
  • 用户默认不选择 Harness。产品仍按“正在做 / 已完成 / 卡在哪里”呈现，内部选择和证据细节不进入主界面。

七、增量实施顺序

0. 术语隔离

先做

把现有模型路由 harnessProfile 改为 promptProfile 或 modelBehaviorProfile。这是无行为变化的安全改名，防止新运行时概念被旧 Prompt 概念污染。

通过条件：模型选择、缓存键和 Prompt 刷新行为不变；新术语不再暗示它是领域执行 Harness。

1. 在现有包内建立 Harness 协议

P0

先在 packages/coding-agent 内定义 HarnessDefinition/HarnessRun 及结构化事件效果；实现 CodingHarness 适配器，默认用户路径完全不变。

通过条件：同一 Coding 会话的工具、Skill gate、执行账本、恢复和 UI 行为与当前一致，且代码不依赖 Prompt 来决定权限/终态。

2. 让 Prompt 成为投影

P0

由 Harness 收集/保存结构化上下文，buildSystemPrompt() 只渲染。保留静态系统模板和 Skill 正文，但不让模板承担能力、准入、验证或状态变迁。

通过条件：删除或压缩模型提示不改变工具权限、账本事实和完成判定。

3. 跑通第二套 Harness

P1

实现一个不依赖代码仓库的研究/网页 Harness。它复用相同 Runtime、会话、Skill、ExecutionScope 和恢复机制，但使用不同能力、观察和验证适配器。

通过条件：真实非 Coding 任务可以无仓库运行、产出 Host evidence、在验收后结束；不需要注入 Coding Prompt 或工具。

4. 最后才抽包与改 CLI 身份

P2

只有两个 Harness 都稳定后，才移动纯通用模块、迁移公共调用方和决定新包/CLI 名称。依赖方向必须是领域 Harness 依赖通用 Runtime，而非 Runtime 反向依赖 Coding。

通过条件：没有双账本、长期别名或依赖反转；源代码、Worker 入口和 SDK 全部使用最终边界。

八、验证不是 Prompt 快照

必须证明的行为

  • Harness 拒绝的工具调用无法执行，即使模型提示要求执行。
  • 真实工具结果被正确映射为 observation/evidence；模型文字不能充当证据。
  • 缺少领域验收门时，完成请求被 ExecutionRuntime 拒绝。
  • 重启后恢复相同 Harness id/version/state，不重复已经发生的副作用。
  • Coding Harness 保持现有 Skill evidence、工具和会话行为。
  • 第二 Harness 不依赖仓库、LSP、Git 或 Coding 默认 Prompt 也能完成真实任务。

不应测试的东西

  • 某段系统提示是否恰好包含某行文字。
  • Harness 类是否调用了某个内部 helper。
  • 工具列表是否因 Prompt 描述出现而“看起来可用”。
  • 模型写出“已完成”后是否被视为终态。

这些都不是对 Harness 权力边界的行为证明。

结论

对：Profile 最终必须落成 Harness，而且应当从第一天就是 Harness。

更精确地说，San 不应选择一个“提示词风格”；它应为任务选择一个有身份、有状态、有权限、有观察和有验收权责的 Harness Suite。系统提示是其中一个可丢弃、可重建的投影。这样 Context Steady 可以压缩 Prompt，模型可以更换，子 Agent 可以重启，而任务的能力边界和完成事实仍然不变。
