San Agent 工作章法方案
不让用户写 Spec，也不让 Agent 随意发挥

这不是一份要求用户先填完整需求的规范，也不是再造一个更复杂的长任务系统。它要解决的是更基础的问题：Agent 每次接到事情，都应该知道先看什么、这一轮做什么、做完怎么确认、什么时候停下来。

面向：产品与研发决策性质：工作方法与落地建议原则：用户只说人话，系统负责把事情做得有顺序
结论：我们要造的不是“让用户填写 Spec 的表单”，而是一个藏在 Harness 里的“隐形带班人”。

用户只需要说“修一下这个问题”“把这个页面做好”“查一下为什么慢”。Harness 在后台自动给 Agent 一条很短的工作节拍：先看清、只做下一小步、马上验一下、确认后再走下一步。它不要求用户提前想完整，也不要求 Agent 一开始写一篇大计划。

一、先纠正方向：长任务不是第一问题

用户真正感受到的
没章法

Agent 一会儿查这里、一会儿改那里，做了很多动作，却说不清当前这一步为什么做。

容易走偏的解法
大 Spec

把整理目标、拆任务、写验收的压力提前推给用户。系统变得规范了，用户却更累。

应该解决的
工作节拍

不要求一次想完，只要求当前这一小步有理由、有结果、有收尾。

核心判断：用户没有义务充当项目经理。Agent 的“做事方法”应该是产品默认值，就像好的装修队不会让业主先写施工管理规范。

长任务当然重要，但长任务只是“这套方法能不能持续很多轮”的结果。眼下要先解决每一轮是否像一个靠谱的人在做事：有没有先了解情况，是否一次只处理一个问题，改完是否马上验证，做完是否知道停。

二、问题到底是什么

“没有章法”不是 Agent 不会调用工具，也不是它缺少更多角色。它主要表现为四种失序：

1. 先动手，后理解

还没确认文件、入口、现状和失败方式，就开始改代码或批量搜索。后面只能不断返工。

2. 做了很多，没形成一小段闭环

一次改太多地方，结果出了问题也不知道是哪一步导致的；或者只观察不行动，工具调用越来越多。

3. 改完不验，靠感觉宣布完成

测试、页面、接口或实际使用路径没有走一遍，最终结论只是“看起来应该可以”。

4. 已经够了还继续扩张

目标已经满足，却继续重构、加功能、换方案；或者遇到失败，只是换个名字重复原来的办法。

所以我们要约束的不是 Agent 的“想法”，而是工作的先后关系。 Agent 可以自由选择具体命令和代码写法，但不能自由跳过“了解—行动—确认—收口”这条基本顺序。

三、现有能力为什么还没有解决它

现有能力它已经解决的事它还没有解决的事
契约回显让 Agent 记住用户大致要什么，并承诺最后说明做了什么、验证了什么。没有规定现在先做什么；它是目标提醒，不是工作方法。
目标复诵长回合中把目标重新推回注意力范围，减少跑题。只能提醒“别忘了目标”，不能告诉 Agent 应该如何把目标拆成下一小步。
进展看门狗发现重复调用、无变化轮询和没有新结果的循环。它在失序已经发生后才提醒，不能在第一次改动前建立节拍。
Todo适合记录明确的多项任务和阶段进度。对普通小任务太重；而且让模型维护列表，不等于模型真的按顺序做事。
Plan Mode适合用户明确要求先规划，或确实需要大范围并行协作的任务。不应该成为所有任务的默认入口；计划文件会把心智负担前置。
San Loop给复杂团队任务提供 Commander、Worker、Supervisor、Oracle 等角色分工。角色分工解决“谁做”，不自动解决“每个 Agent 这一轮先做什么、怎么验”。

这说明此前把重点放在“统一任务账本、长任务恢复和最终状态”上是必要但不够准确。那是安全底座；用户现在痛的，是 Agent 的方向盘和脚下的节拍器。

四、核心抽象：轻量工作循环

不叫 Spec，也不叫 Plan。它是一种每轮都能重复的默认工作方式。用户不用写，Agent 不用先交一份长文，Harness 只在必要时给出三行内部提示。
看清先了解现状
→
做一小步只处理当前问题
→
验一下确认这步有效
→
收口完成就停，未完成再取下一步
01

看清：先拿到足够信息，不追求一次看完

找到相关文件、复现入口、当前错误或运行页面。达到“可以决定下一步”就停，不允许无目的扩展搜索。

02

做一小步：一次只改变一个连贯的问题

改动要能说清“它是为了解决刚才看到的什么”。不要求一次完成整件大事，但要求这一步是可回看的。

03

验一下：紧跟改动安排检查

优先跑最贴近刚才改动的测试、页面操作、接口请求或对比检查。没有合适的自动检查，就明确说明当前只能做到哪一步。

04

收口：判断继续、调整还是结束

验证通过就回到用户目标，不自动扩张；验证失败就根据新结果换下一步，而不是重复原动作。

长任务只是把这个循环重复很多次。 每次循环留下很短的“已经知道什么、刚做了什么、下一步是什么”，压缩或换 Agent 后也能接着走，但不需要维护一份面面俱到的 Spec。

五、Harness 只生成一张“三行工作卡”

这是整个方案最小的内部单元。它不是交给用户填写的表单，也不是要 Agent 展示给用户看的长计划。

现在要解决什么从用户原话和已经看到的事实中提取一句当前目标。
这一轮先做什么只放一个下一动作，例如“先跑失败测试确认入口”。
做到什么算这一轮完成放一个近处的完成信号，例如“失败测试转绿”或“页面按钮能提交”。

它和 Spec 的区别

  • Spec 试图提前描述整件事；工作卡只描述当前一小步。
  • Spec 往往需要用户提供；工作卡由 Harness 根据任务和观察自动产生。
  • Spec 是相对稳定的文档；工作卡随着每次验证结果即时更新。

它和 Todo 的区别

  • Todo 记录“还有哪些事情”；工作卡决定“此刻先做哪一件”。
  • Todo 可以由用户查看和维护；工作卡默认隐藏，只在 Agent 上下文中占很少空间。
  • 简单任务可以只有一张工作卡，不创建 Todo，不写计划文件。
用户体验：用户仍然只说一句话。系统不追问“请补充目标、范围、验收标准”，除非在实际执行后确实遇到无法继续的关键缺口。

六、不同任务自动采用不同节拍

不能用一套僵硬流程处理所有请求。Harness 根据用户表达、已有文件和工具结果，自动选最短的合适节拍。

任务样子默认节拍用户不需要提供什么
查问题 / 问原因看清 → 给结论 → 说明依据不用写研究计划。
明确修 Bug复现 → 定位 → 最小修改 → 回归检查不用先写完整修复方案。
加一个小功能看现有写法 → 明确一个行为 → 修改 → 运行相关检查不用先写 Spec 文档；测试或现有代码提供的约束优先。
页面 / 交互任务启动并观察 → 做一个界面变化 → 用真实操作确认不用懂前端验收术语；用户只需描述想要的效果。
重构 / 大范围改动先找边界 → 选一个连贯切片 → 改后检查 → 再取下一切片不用把整个仓库拆成几十项；系统只要求每次拿一个可收口切片。
目标明显不清先观察能观察的内容 → 只问一个阻塞问题不在开始时进行“需求访谈”；先用现有信息减少问题。

七、不要靠提示词祈祷，要在几个关键转折点扶一下

完全靠提示词，Agent 仍然可能忘记；完全靠硬规则，又会变成僵硬的审批流。建议只在四个转折点做轻量干预：

转折一

第一次要改东西前

如果当前还没有任何相关观察，提醒一次“先确认入口和现状”。小任务、用户明确给出文件和改法时可以直接通过。

转折二

发生改动后

把工作卡切到“检查优先”。下一步默认推荐最贴近的测试、运行或对比，不让模型马上继续扩大改动。

转折三

检查通过后

提醒回看用户原话：目标满足就收口；只有还有明确未完成部分，才生成下一张小工作卡。

转折四

同一办法再次失败

不再重复同一动作。要求换方法、缩小问题或说明缺什么；连续失败时才进入暂停或求助。

原则：正常路径尽量不拦，只给方向；只有重复副作用、危险操作、明显无效循环和完成前缺少必要检查时，才升级为硬限制。

八、两个例子：用户不用变专业，Agent 变得有顺序

例子 A：修一个超时问题

用户：“这个 API 最近经常超时，帮我修一下。”

步骤Agent 实际工作Harness 只给的内部提示
看清找到请求入口，运行一次或查看已有日志，确认超时发生在哪一段。当前一步：确认失败入口。完成信号：拿到可复现错误或明确日志位置。
做一小步只修改导致超时的那一处配置、等待逻辑或调用方式。当前一步：修复刚才确认的原因。完成信号：改动范围与原因对应。
验一下运行针对该 API 的测试或真实请求，观察超时是否消失。当前一步：回归同一条路径。完成信号：请求在预期时间内完成。
收口回看用户目标；如果问题已解决，报告改了什么、怎么确认的，不继续顺手重构。目标已满足，停止。

例子 B：把页面做得更好

用户：“这个页面帮我优化一下，感觉太乱了。”

  • 系统不会要求用户先写视觉 Spec；先启动页面、看真实界面，找出最明显的层级和操作问题。
  • Agent 先处理一个最影响使用的区域，例如标题、主按钮和信息层级。
  • 改完用浏览器重新走一遍主要操作，再决定是否继续处理第二个区域。
  • 如果“更好”涉及完全不同的审美方向，系统在看到页面后只问一个选择题，而不是开场进行长访谈。

九、落地方案：先做一个小控制器，不重做 Harness

第一步：新增“工作节拍”运行状态

P0

在现有 AgentSession 中增加轻量、可丢弃的状态，不创建用户必须维护的新文件：

  • 任务类型：查问题、修复、功能、页面、重构、模糊任务等。
  • 当前阶段：看清、改动、检查、收口。
  • 当前一步：一句短描述。
  • 完成信号：一个近处的检查方式。
  • 最近一次改动和最近一次检查：用于判断是否跳步或重复。
关键边界：它不是新的最终状态机，不替代现有长任务账本；它只负责把当前回合带入正确节拍。

第二步：复用现有工具结果，自动更新节拍

P0
  • 现有 ToolProgressGuard 已经能区分观察、改动和检查，直接复用这层分类。
  • 现有 Goal 复诵只负责目标提醒；新增的工作节拍提示负责“当前一步”，两者不要混成一段长提示。
  • 现有 watchdog 继续负责发现重复和无变化；工作节拍在更早位置提醒先看、改后验。
  • 提示使用静态模板，动态内容只有任务类型、当前一步和完成信号，不在代码里拼长 Prompt。
关键边界：默认提示不展示给用户、不要求用户确认；只有真正卡住时才转换成一句人话。

第三步：为常见任务补“默认检查方式”

P1
  • 修 Bug 默认优先复现和回归原测试。
  • 小功能默认优先运行新增行为的检查。
  • 页面任务默认优先浏览器真实操作。
  • 重构默认优先改前后同一组检查。
  • 研究任务默认优先留下可追溯的结论来源。

这些是 San 的默认工作方法，不是要求用户提交的 Spec。已有 Skill 可以提供更具体的检查偏好，但没有 Skill 时也必须有通用节拍。

第四步：给子 Agent 同样的“小步闭环”

P1
  • 父 Agent 派出的不是一句宽泛的“去看看”，而是一个有边界的当前小问题。
  • 子 Agent 返回三件事：处理了什么、怎么检查、还缺什么。
  • 父 Agent 只根据检查结果决定合并、换方法还是重新派工，不能仅根据一段漂亮总结继续扩大任务。

十、验证标准：先测“像不像一个有章法的人”

不要一上来只看整夜跑了多少小时。先看每个任务的基本动作是否变好了：

先看后改

需要理解现状的任务，是否在第一次改动前拿到相关信息。

改后必验

发生改动后，是否在继续扩大范围前做了贴近的检查。

做完会停

检查通过后，是否回到用户目标并停止无关扩张。

失败会换法

同一失败出现后，是否真正改变策略，而不是换名字重试。

少问问题

系统是否先利用可获得的信息，只在确实阻塞时问用户一个必要问题。

用户零负担

普通任务是否不要求用户填写 Spec、Plan、Todo 或验收表。

第一批验收样本：用现有北极星 benchmark 的修 Bug、小功能、模糊需求和中途纠偏样本，增加“首次改动前是否观察”“改动后是否验证”“通过后是否收口”三组行为指标。先证明短任务变得有章法，再把同样循环带到长任务。

十一、明确不做什么

不做

让用户先写完整 Spec

用户说清意图就够了；系统负责把它变成当前可执行的一步。

不做

所有任务强制进入 Plan Mode

计划是解决复杂度的工具，不应成为使用 San 的入场费。

不做

让 Todo 变成每轮必填表

Todo 适合多项工作，不适合作为 Agent 每一步的方向盘。

不做

增加一个常驻 LLM 监督员

先用节拍和工具事实解决大部分问题；模型监督只在规则无法判断时介入。

不做

用一套固定流程限制所有任务

查询、修复、设计、重构的最短路径不同；统一的是顺序，不是每一步的具体工具。

不做

把内部过程全展示给用户

用户只需要看到正在做什么、做成了什么、卡在哪里；内部节拍默认隐藏。

十二、建议现在拍板的三件事

  1. 把“工作章法”定为下一阶段主线。长任务、恢复和总账本继续做，但不再作为用户体验的第一叙事。
  2. 默认采用“看、做、验、收”的小步循环。它是 San 的默认行为，不是用户可选的高级配置。
  3. 先做无感控制器和短任务行为基准。不先增加用户表单，不先扩张新 Agent 模式；证明 Agent 的基本动作变稳后，再谈更长时间的自治。
一句话：不是让用户把事情想得更完整，才配使用 Agent；而是让 Agent 在用户只说半句话时，也能用正确的顺序把事情往前推进。
