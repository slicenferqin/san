Dynamic Workflows 兼容方案（历史稿）

记录 Claude Code Dynamic Workflows 与 San 的早期兼容判断。San v0.3 已完成，本稿不再作为后续实施入口。

状态：已被 2026-07-11 的 San v0.4 新提案取代

文档状态更新

本稿保留用于追溯最初为什么搁置 Workflow。面向产品审阅、当前代码和后续实施阶段的最新版本，请阅读 san-v0.4-dynamic-workflows-proposal-20260711.html。

结论

  • 当前不兼容原生 Workflow：San 不发现或执行 .claude/workflows/*.js。
  • 现有 JS/TS Extensions 不能冒充 Workflow：扩展与主进程同域、无沙箱，生命周期和持久化语义也不同。
  • 已有可复用底座：task、job、子代理、结构化输出、取消和后台交付可作为调度后端。
  • 正确路线：新增独立 Workflow Runtime，以受限 JS 编排层调用 San 原生调度器；禁止直接把 Workflow 文件作为普通 Extension 导入。
  • 排期：先完成 v0.3 Brain / Experience System，再单独立项。

事实基线

Claude Dynamic Workflows

  • 普通 JavaScript，支持顶层 await。
  • 脚本持有循环、分支和中间结果。
  • 核心原语包含 agent()、parallel()、pipeline()。
  • 后台运行、可观察、可暂停/恢复/停止。
  • 脚本自身无直接文件系统或 Shell 权限。
  • 项目与用户脚本位于 .claude/workflows/。

San 当前扩展系统

  • 支持加载 TS/JS Extension Factory。
  • 支持工具、命令、事件、消息和会话操作。
  • 扩展在主进程中执行，当前不沙箱化。
  • Claude 兼容发现覆盖 skills、commands、hooks、extensions 等。
  • 发现目录是 .claude/extensions，不是 workflows。

关键缺口

  • 没有 Workflow 文件发现与版本化契约。
  • 没有隔离 JS 编排运行时。
  • 没有 run/phase/agent 持久化状态机。
  • 没有脚本级断点、恢复和确定性重放。
  • 没有 Workflow 专属审批与权限模型。
  • Brain 的 workflow_pattern 只是经验候选，不可执行。

兼容目标

层级目标本提案决定
L0 发现兼容识别用户与项目 .claude/workflows/*.js应支持，项目路径遵循最近目录优先。
L1 语法兼容接受 meta、顶层 await、全局 args、核心 helper首版支持官方公开子集，不追逐内部未文档化 API。
L2 行为兼容后台执行、结构化结果、并发、取消、失败传播必须由 San 调度器提供，不由 JS 自建线程池。
L3 运行状态兼容暂停、恢复、重启单代理、会话内结果交付分阶段实现；恢复必须基于持久化事件，不依赖闭包快照。
L4 UX 兼容/workflows、保存为命令、进度视图可借鉴交互，不要求逐像素或命令完全一致。

建议架构

1Discovery

发现 San 与 Claude 路径，解析优先级和来源。

2Validator

验证 meta、参数和允许的运行时 API。

3Isolate

在独立 Worker/进程执行受限 JS。

4Bridge

把 agent/parallel/pipeline 映射到 San 调度器。

5Ledger

持久化 run、phase、agent、artifact 和 transition。

6Delivery

后台状态进入任务面板，最终结果注入原会话。

运行时契约

首版公开 API

export const meta = { name: "audit-routes", description: "Audit routes", }; const files = await agent("List route files", { schema }); const findings = await pipeline(files, file => agent(`Audit ${file}`, { label: file }) ); return findings;

候选 helper：agent、parallel、pipeline、output、log、phase。参数使用结构化 args，禁止 JSON 字符串二次编码。

明确禁止

  • Workflow 脚本直接访问 Bun、process、fs、网络或子进程。
  • 复用普通 Extension Loader 执行不可信脚本。
  • 脚本直接持有 AgentSession、SessionManager 或工具注册表。
  • 通过不可序列化闭包实现暂停/恢复。
  • Brain 自动生成后直接激活可执行脚本。
  • 把 Claude 私有、未文档化 runtime 行为设为兼容承诺。

安全与可靠性

能力隔离

  • Workflow Runtime 只暴露白名单桥接函数。
  • 代理继承显式工具 allowlist，脚本不拥有工具权限。
  • 每次运行绑定 session、cwd、source 和审批记录。
  • 全局并发、单 run 并发、代理总量和 token 预算均硬限制。

恢复语义

  • 所有调度决定写入 append-only Workflow Ledger。
  • 完成节点通过幂等键复用，禁止重复副作用。
  • 暂停只阻止新节点；在途代理进入可观察结算。
  • 恢复从已提交节点继续，而非重新执行整个脚本。

与 Brain / Experience 的关系

  1. Brain 可从成功执行轨迹提取 workflow_pattern Experience Candidate。
  2. Candidate 只描述可复用编排模式，不包含可直接执行代码。
  3. Consolidation 可生成 Managed Workflow Draft，保留来源、置信度和适用 scope。
  4. 用户必须审阅脚本、权限和预算后显式批准。
  5. 激活后形成版本化 Workflow；后续修改重新审批。
  6. 执行反馈回流 Experience，但失败记录不得自动扩大权限或 scope。

实施阶段（v0.3 后）

阶段范围完成标准
W0 契约冻结Workflow 文件格式、API 子集、状态机、权限和兼容等级黄金脚本与失败语义测试先于实现。
W1 最小 Runtime隔离 JS、agent、parallel、pipeline、结构化返回脚本无直接系统权限；取消和预算有效。
W2 Claude Loader.claude/workflows 发现、meta、args、命令映射官方公开示例可少量修改或无需修改运行。
W3 Ledger + UX后台进度、列表、暂停、恢复、重启节点、结果交付进程恢复后不重复已提交节点。
W4 Brain Integrationpattern → draft → approve → activate → feedback任何自动生成 Workflow 都必须经过显式审批。

为什么现在搁置

  • v0.3 正在建立 Brain 的 Capture、Consolidation、Activation 和 provenance 基础。
  • Workflow Runtime 依赖稳定的事件账本、幂等语义、scope、审批和恢复机制。
  • 现在实现会同时改变调度、执行沙箱、UI、权限和 Experience promotion，扩大 v0.3 风险面。
  • 先让 Brain 产出可信 Experience，再让 Experience 生成可执行 Workflow，依赖顺序更合理。

重新启动条件：v0.3 M1–M5 完成；Brain provenance 与 activation/undo 稳定；San Loop 的 run/worker 事件可复用；单独建立 Workflow 安全模型和兼容测试矩阵。
