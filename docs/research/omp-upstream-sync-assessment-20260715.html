6. 推荐合并顺序

  1. 在独立 worktree 建立 sync/omp-16.5.2，目标固定为 tag，不跟随上游 main。
  2. 按 v16.4.0 → v16.4.5 → v16.5.0 → v16.5.2 分阶段合并和验证，保留清晰的冲突边界。
  3. 先解决 catalog/effort，再解决 AI Provider；否则 coding-agent 层无法稳定类型检查。
  4. 迁移 agent/task schema 和生命周期，再接 San Brain、managed/ad-hoc workflows、Context Steady。
  5. 采用上游 Model Hub，把 San Provider connect/logout、统一模型选择和 /effort 移植到新架构。
  6. 保留 read/grep 独立 selector 协议，吸收其余上游工具修复。
  7. 最后处理 San 品牌、构建、README/文档、版本号、锁文件和生成文件。

8. 最终判断

应该同步 v16.5.2。 上游包含大量与 San 直接相关的可靠性和基础设施改进，继续停留在 v16.3.15 会扩大后续差距。

但这次应视为一次语义迁移，不是普通依赖升级。 最关键的决策是：采用上游新的 Model Hub、task schema 和 wire-exact effort 基础，同时保留 San 的 Context Steady、Brain/workflow、Provider UX、ultra 用户语义及独立 selector 工具合约。
