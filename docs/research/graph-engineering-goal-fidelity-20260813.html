Graph 工程与目标保真:San 如何不忘记自己在干什么

2026-08-13 · 触发问题:多轮摘要压缩后 agent 失去目标与进度("不知道在干什么,不知道要干什么")· 来源:LangGraph 1.0 文档与实践论文(arXiv 2607.19297)、Manus 官方 context engineering 博客、agentpatternscatalog、planning-with-files、2026 框架横评(particula/speakeasy/gurusup 等)· San 侧:execution-control / context-steady / san-loop 源码(本仓库)
一句话结论:graph 工程对"目标漂移"的解药不是"图",而是"目标与进度是每一步都强制可见的显式状态"。San 已经拥有比任何 graph 框架都硬的宿主侧目标锚(不可变 objective contract + 摘要无权改写),缺的只是最后一寸:把锚投影进模型每次请求的高注意力区。这一寸不需要图,Manus 用一个 todo.md 复诵就解决了;San 用一个新的 context plan 常驻材料就能解决,而且比 Manus 的更强——San 的锚是宿主持有的,模型自己都改写不了。

一、Graph 工程 2026 现状一页纸

系统定位与成熟度与目标保持相关的核心机制
LangGraph 1.0(LangChain)最主流的图式编排,1.0 已稳定(Klarna/Replit 等生产使用);低层框架,开发者手写节点与边typed state(目标/进度是 state 字段,每个节点每步可读);reducer 只增不覆写;checkpointer 每步落盘(SQLite/PG/Redis),线程恢复、时间旅行;interrupt()/Command 一等人机协作;边上手写循环上限守卫
OpenAI Agents SDK极简命令式(Agent/Runner/handoffs/guardrails),v0.10+,1.9 万星;OpenAI 生态绑定目标只活在消息列表;无内置 checkpoint,session 持久化 opt-in;长任务官方指路 Temporal(durable execution)
CrewAI Flows角色制多代理,Flows 提供事件驱动状态容器结构化 state + 事件 checkpoint(JSON/SQLite),resume/from_pending;粒度粗于 LangGraph
Manus(2025.12 被 Meta 收购)通用自主 agent 的产品标杆,任务平均约 50 次工具调用;其 context engineering 博客是行业必读Recitation(复诵):agent 维护 todo.md 并每步重写到上下文末端,把全局计划推进 recency 高注意力区,明确为对抗 lost-in-the-middle 与 goal drift 而设计;后期演进为专职 planner 子代理管计划(早期 executor 自管浪费约 1/3 动作在记账上)
planning-with-files(开源 skill)把 Manus 模式做成跨 60+ agent 的 SKILL.md:task_plan/findings/progress 三文件落盘每 turn 开始由 hook 强制重新注入活跃计划;完成门(Stop hook 检查所有阶段勾选)才准停;crash//clear 后从磁盘恢复目标
Temporal 路线workflow 引擎与 agent 结合(OpenAI SDK 官方 durable 路径)代码级 durable execution,重放恢复;解决的是"进程死了怎么办",不解决"模型忘了怎么办"

arXiv 实践论文的清醒定位值得引用:LangGraph 应"按工作流复杂度适配,而非普适默认"——简单工具使用用 ReAct 循环更好;它的价值区在"路由、暂停、审计需要成为显式产品行为"的场景。

二、目标/进度保持机制横向对比(核心表)

机制目标存在哪谁能改模型每步可见?压缩/重启后存活?
LangGraph typed statestate 字段(图外持久)节点代码经 reducer(只增)是——每个节点入参就是 state是——checkpointer 每步落盘
Manus todo.md 复诵沙箱文件系统agent(后期:专职 planner 子代理)是——每步重写到上下文末端(高注意力区)是——文件持久,重启重读

对比表读出来的结论非常清晰:San 在"谁能改"一列是全场最强(没人能改,连模型自己都不行),在"模型每步可见"一列是全场最弱。LangGraph 靠图结构保证可见性,Manus 靠复诵保证可见性,San 两者都没有——这正是作者观察到"多轮压缩后不知道在干什么"的机制根源:锚在引擎盖下,模型看不见锚。

四、移植方案(以 San 的形态,不放弃自由 loop)

方案 A(首选):goal-anchor 常驻材料 —— 把契约+进度做成 context plan 的一等材料

  • 做什么:context plan 新增 goal_anchor 材料类型:内容 = 契约目标(objective contract 的用户原话,不可变)+ 进度快照(todo 状态 + 最近 digest 的 nextSteps + 未满足的 evidence gates)。物化时渲染进 plan 消息——plan 消息本来就注入在最后一条用户消息之前(靠近上下文末端、高注意力区)、每次请求重建、永不参与压缩。几百 token 封顶。
  • 为什么对:这正是 LangGraph "state 每节点可见" + Manus "复诵到末端"的合成,但锚源是宿主的不可变契约——模型每步都看见目标,但改不了目标,比 Manus 的自管 todo.md 强一档(Manus 的 todo 是 agent 自己写的,漂移的 agent 可以写出漂移的 todo;San 的锚漂移不了)。
  • 改哪里:plan-types.ts(材料类型)、planner.ts(从 scope 契约 + todo 状态组装,恒定入选不参与预算裁剪——它就是"八项保护"之外的第九项)、materialize.ts + plan 模板(渲染)、契约来源用 getActiveExecutionScopeId → objectiveContract(#15 之后每 turn 都有)。
  • 工作量:2-3 天(材料管线是这两周刚摸熟的,挂点全部现成)。
  • 与自由 loop 兼容性:满分——不改任何决策路径,只改模型看见什么。

方案 B(叠加):压缩后 re-anchor 与长回合复诵

  • 做什么:两个确定性触发点补充 A:(1) 每次 compaction/checkpoint rebase 完成后,立即 fold 一条"目标+进度复诵"(A 的材料照常在,这是对压缩瞬间的额外强化);(2) 单 turn 工具调用数过阈值(如 20 次,Manus 平均 50 次的场景)时复诵一次。复用 TTSR/skill-reminder 的 fold 管线,一次性、不阻断。
  • 工作量:1 天。与 watchdog(#15)的提醒管线同构。

方案 C(方向,不急):planner-executor 分工进交互会话

  • Manus 后期演进(专职 planner 子代理管计划,executor 专注动作,省 1/3 记账动作)与 San Loop 的 commander/worker 是同一形态。San 可以把 San Loop 的 plan 语义"降档"到普通交互会话:长任务自动派生轻量 plan、由宿主维护进度勾选。但这是行为变化大的工程,应等 A+B 的数据说明"复诵不够"再上——Manus 也是先有 recitation 再演进 planner 的。

五、明确不值得借鉴的部分

  • 手写图拓扑(LangGraph 的节点/边/条件路由):San 是通用 coding agent,任务形态不可枚举;把决策路径框进开发者手写的图,等于把"处理未预见情况"的核心价值交出去。arXiv 论文自己也说图值得的场景是"路由与审批需要成为显式产品行为"——San 的对应物(San Loop、审批门)已经存在。
  • LangGraph 式 checkpointer:San 的 append-only journal + scope ledger + resume 重放已覆盖同一职责,且粒度更细(#24 刚修的就是这个体系的边角)。
  • 把"暂停等人"做成图中断原语:San 的 PAUSED_FOR_CONTEXT / needs-user 终态 + FIFO 恢复语义已有,补的应该是呈现(人话),不是机制。

六、对北极星 benchmark 的指标修正

指标定义怎么测
目标保真度(新,核心)终态产出与初始契约的一致性San 独有优势:初始契约不可变、宿主持有——终态时以(契约原文, 最终 diff/产出, 终态声明)为输入做 LLM-judge 对照评分 + 人工抽检校准;漂移检测可作为 goal-anchor 的副产品(anchor 与最新 digest 的语义偏离度)
介入效率(新)一次 steering 之后回到正轨的比例;同一问题被迫重复纠正的次数benchmark 样本里设计"中途注入一次纠偏"的场景;测纠偏后的目标保真度恢复
预算内完成 / 终态可解释(保留原定义)不变
删除:"无人值守率"作为独立追求介入不是失败;拉不回来才是。"全自主逼近目标"是渐近方向,不是当期可承诺的指标。
建议的执行顺序:方案 A(goal-anchor 材料,2-3 天)→ 方案 B(re-anchor 复诵,1 天)→ 用修正后的 benchmark 指标验证"目标保真度"前后对照 → 数据决定是否需要方案 C。这条线把 graph 工程的精髓(显式状态可见性)、Manus 的实践(复诵进高注意力区)和 San 的独有资产(不可变宿主锚)合成一个别人没有的组合:模型每步看见目标,但谁也改不了目标。
