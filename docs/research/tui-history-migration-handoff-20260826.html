3 · 新契约的最小心智模型

InteractiveFrameProvider.renderFrame(viewport)
  ├─ history?: HistoryBatch
  │    ├─ append  = 将已 settled 前缀追加进 native history
  │    └─ replay  = destructive reset 后重新提供完整逻辑前缀
  └─ viewport = 当前可重绘的 bounded rows

TUI
  ├─ 物理写 history + viewport
  ├─ 只在接受 batch 后调用 provider.acknowledgeHistory(id)
  ├─ resize settled 时选择 append / rebuild / preserve
  └─ 无 provider 时只画 bounded children viewport，不写 history

TranscriptContainer
  active → settled → committed
  ├─ settled: 仍由普通 viewport 渲染
  ├─ offered: 固定一个 batch，等待 acknowledgement
  └─ committed: 不再允许普通删除；replay 时重新开放并整体 re-offer

必须守住的外部行为：history 行有序且只接受一次；live 行仍可重绘；resize 时不丢内容、不把旧宽度内容误当新宽度内容；provider 返回的普通 viewport 不超过终端高度。

4 · 已处理的高优先级问题

设置迁移

tui.scrollbackRebuild 的 nested 和 flat 形式都迁移到 tui.resizeScrollback；true → rebuild、false → preserve，显式新键优先，旧键从内存和磁盘投影中移除，其他 tui 字段保留。

provider 顺序与 resize

InteractiveFrameProvider 将 prefix、transcript tail 和 suffix 组合成 bounded viewport；HistoryBatch 在 TUI 物理写入后才 acknowledgement。append、rebuild、preserve 三种 settled-resize 场景均由 VirtualTerminal 断言，resize drag 使用独立 resize frame。

stop / stale acknowledgement

shutdown flush 对不推进的 provider 明确失败而不会无限循环；已接受的 stale batch 不再重复调用 acknowledgement，并有回归测试。resize probe 在 stop 时取消，flush 只处理尚未接受的批次。

5 · 审查结论

检查项结论
history batch acknowledgement已确认只在新 batch 物理接纳后调用；重复 offer 不会重复确认；shutdown non-advancing offer 会 fail-fast。
transcript 删除与重排已核对真实调用点：已提交块不可撤回，active 块可移除；offered prefix 保持稳定时重排不破坏 acknowledgement。
standalone 默认策略standalone/env fallback 保持 preserve，interactive 按设置覆盖；这是 host 级别的有意差异，不是隐式旧契约。
