核验日期：2026-09-05 · 官方资料 + San 当前源码 · 研究分析，不修改运行时代码

GPT-6 Astra / Codex 与 San 上下文稳态
同一方向，不同层次

[INFERENCE] 核心结论：“跨窗口笔记 + 历史可回查 + 按需带入当前工作集”与 San Context Steady 属于同一类上下文管理范式；但不能把整套 Astra 能力都等同于上下文稳态。循环深度是模型内部计算，百万窗口是单请求容量，持久笔记是 Codex 的运行时功能，San 则还明确控制每次请求的上下文规模。

一、先校正原文的事实边界

原文主题本次核验结果应当如何理解
Astra 已发布官方发布页与系统卡可核验；系统卡发布日期为 2026-09-03。[1][2]不是只凭新闻标题判断存在与定位。
Looped Transformer、循环上限已读的官方发布页与完整系统卡没有给出足以核验具体循环层数、路由策略、最大循环数的架构说明。Raschka 的文章是在解释和纠正围绕相关报道的推论，并非披露 Astra 完整结构。[3]可讨论“层复用”这一机制，但不把传闻细节作为已确认的 Astra 技术参数。API 的 xhigh/max 是 effort 档位，不是公开的循环次数。
层复用没有额外代价Raschka 明确指出：重复使用权重不必重复存储权重，但多次通过网络会增加计算；他举的双循环示例接近两倍计算。并明确指出层复用本身不抑制可见 CoT。[3]“不增加权重份数”不能改写成“总显存、计算、延迟都不增加”，也不能推出“无需显式推理链”。
1.05M / 128K 与 MRCR官方模型页：1,050,000 上下文、128,000 最大输出；支持 low/medium/high/xhigh/max。官方发布表中 MRCR v2 8-needle 两段成绩为 100.0% 与 96.3%。[1][4]是窗口规格与特定基准成绩；不是任意长会话中绝不丢约束、绝不忘记失败原因的保证。
跨窗口持久笔记与历史检索官方明确写的是 In Codex：笔记跨窗口保存，先前窗口仍可搜索；发布时为实验功能，可配置开启，计划在之后几周成为 Astra 的默认体验。[1]是 Astra 与 Codex 的组合能力。仅把 San 的模型 ID 换成 Astra，不能据此认定 Codex 的笔记、历史索引和窗口管理也被带进了 San。
“Surgical Context Pulling”官方措辞是训练模型只把相关上下文放进 outputs，避免在产物中重复无关内容。[1]这是输出选择能力；官方这句话没有定义一个同名的输入上下文规划 API，更不等于 San 的输入投影器。
Mid-turn steering官方确认 Astra 支持 Responses WebSocket 的 response.steer；accepted 只是排队，随后在完成当前输出项和已开始的托管工具工作后接续。不会撤销既有输出或已开始的工具。[5]传输层支持与模型更善于保留任务主线，是两个互补条件；都不构成“永不跑偏”的硬保证。
官方关于笔记的关键原话：
“In Codex, Astra can keep notes across context windows … Earlier context windows remain searchable …”
范围限定词 In Codex，以及 experimental feature，不能在转述中省略。

“废弃了 Compaction”说得过头。压缩当前请求的活跃上下文，与删除磁盘上的原始历史不是同一个操作。真正需要避免的是“只有一个不断重写的摘要，又没有有效的原文回查通道”，而不是把所有 compaction 一概视为不可逆删除。

二、哪些属于同一个概念？

模型计算层隐藏状态、权重、推理深度。Looped Transformer 属于这一层。San 不修改模型权重或内部循环。
模型能力与 API 层原生上下文容量、长文本检索能力、effort、WebSocket steering。它们影响运行时能做什么，不替运行时保存业务状态。
Agent 上下文管理层原始历史、笔记、索引、当前工作集、窗口切换。Codex 的新笔记方案与 San Context Steady 的主要重叠在这里。

[INFERENCE] 两者共享的原则：历史可以持续增长，但不必每次全塞给模型；当前请求只带任务所需的工作集，细节不足时再回到原始记录。

保存层：原始对话 / 工具结果 / 中间状态
               ↓                    ↑ 按需回查
工作记忆：笔记、结构化摘要、检查点、引用
               ↓ 选择 / 裁剪 / 组合
当前请求：当前任务 + 必须保留的原文 + 相关历史
               ↓
模型执行 → 新结果继续记录

San 中“稳态”的额外含义，是对整个 provider 输入持续设定目标区间、弹性上沿与硬上限，而不是只有“窗口满了以后还能记住”。它不是每一步 token 数完全相等，也不是保证永远不需要压缩。

三、San 当前已经做到了什么

能力当前实现与 Codex 描述的关系 / 限制
分离历史与当前输入materializeContextPlanMessages 根据计划生成 provider 消息视图，对工具结果替换为小型引用；不修改传入的原始消息。[C1]核心方向一致：不把“没发给模型”当作“历史已删除”。
结构化工作记忆TurnDigest 记录源区间、用户意图、动作、决策、文件、工具结果摘要、风险与后续步骤。ContextCheckpoint 累积摘要及原始引用。[C2]承担相近角色，但不等同于模型主动编辑和持续维护一份技术笔记。检查点仍合并、截断摘要字段。
回查摘要漏掉的原文context_expand(ref) 根据 digest 的源区间读取当前分支历史；源细节不必先出现在 digest 文本中。[C3]按已知引用展开，不是一个任意自然语言搜索所有旧窗口的接口。仅开启稳态的根会话提供；默认返回上限 30,000 字符，超出截头留尾。文本渲染也不是原始多模态消息的逐字节还原。
控制输入规模默认有效目标 240K，控制上沿为目标的 13/12，默认 burst 上限 320K；再按模型窗口与预留空间下调。system/tools/messages 都计入总输入。[C4]这是 San 比“有笔记、有搜索”描述更明确的控制策略。不能据此推出质量优于 Codex。
摘要不能改写用户任务目标锚从当前执行契约对应的真实用户记录取原文；模板声明历史计划只作背景，最新真实用户请求优先。[C5]这是宿主提供的来源与优先级约束，不是模型行为的绝对保证。缺少有效目标来源时不会凭摘要编造目标。
持续运行时的回收pre-prompt 与 mid-turn 路径仍可执行自动 compaction；只有 segment 到期而未触发物理压力时可仅写 checkpoint/segment。物理维护带恢复区间，避免每步反复压缩。[C6]San 没有消灭 compaction，而是把它放在可回查的分层历史与输入控制机制中。
半途补充任务AgentSession.steer 排入 steering 队列；agent loop 在调用边界、工具轮次结束和退出前吸收消息。[C7]已有运行时 steering，但不是同一个 Responses response.steer 协议。本次搜索相关 provider/runtime 源码未找到原生该事件的接入。

默认状态不能与“代码里存在”混为一谈

当前源码中 san.contextSteady.enabled 默认 false；开启后通常达到 240K 阈值才激活，已激活状态可跨 compaction/resume 保留。stableProjection、老工具输出 offload、老图片 offload、recall、LLM digest 均有独立开关，默认并非全部开启。这里列的是源码默认值，没有读取或变更本机私有配置。[C8]

还需注意：checkpoint 的覆盖检查验证的是“条目是否有对应的表示或引用”，不是“摘要是否完整保留了该条目的每一个语义”。代码会保护原文并限制不可信 fallback 摘要的替代权限，但无法通过引用关系证明模型理解正确。

四、直接运行的小型验证

本次执行了现有纯函数，不调用真实模型、不新增测试、不修改运行时：

  1. 以模型窗口 1,050,000、源码默认稳态设置调用 resolveContextPlanBudget，得到：steadyTarget=240000，controlMax=260000，burstCeiling=320000。
  2. 构造两条历史原文和一条刻意未记录失败细节的 digest，调用 expandDigestSpan。成功返回两条原文，找回 FIRST_ATTEMPT_FAILED: null receiver at import boundary; exit=1.；truncated=false，原始输入结构未改变。

能证明：有界输入策略存在；已知摘要引用可恢复未写入摘要的源细节。不能证明：模型会主动想到去找、能在海量历史中找到未知引用，或多天任务质量与 Astra/Codex 相同。没有进行两套系统的长任务对跑。

五、对 San 的判断与可采纳方向

1. 保留稳态，不因为换 Astra 就关掉

[INFERENCE]更强的模型与更可靠的上下文管理是互补关系。模型页还明确规定，输入超过 272K 时整次请求适用更高费率；百万窗口不是零成本工作区。实际目标窗口应结合任务成功率、延迟、总输入与缓存成本选择，而非直接取模型容量上限。Astra 的长窗口和检索能力可以提高回查后的利用率，但不会自动替 San 建立 Codex 的历史索引。[4]

2. 下一处最明确的差距，是“能找”而不只是“能展开”

[INFERENCE / 建议]在现有源记录与引用之上，优先验证“用户只记得失败含义、不知道 digest ID 时，能否定位相关原文”。检索结果应能精确展开、分页并限定会话/分支；否则 30K 截头可能又丢掉恰好要找的旧细节。这里是建议，不是已经实现的能力。

3. 工作笔记与用户目标必须分开

[INFERENCE / 建议]可让工作记忆更明确保存“失败方法及原因、尚未验证的假设、当前状态、引用”，但不让模型生成的笔记决定用户目标或把未验证结果升级成已完成。模型写得更像真的，不等于它更有权威；保留宿主给出的用户来源与真实工具结果。

4. 原生 steering 是单独的传输接入，不是稳态改名

[INFERENCE / 建议]若后续接入 Responses response.steer，需按其 accepted/pending/failed、后继 response、工具回执以及连接断开语义处理。官方特别说明排队输入只存在于当前连接，断开后不能假定仍在；每个自动后继 response 的 token/tool-call 限额独立。因此仍要保留 San 对完整任务状态和整体执行限制的管理。[5]

最终表述：
我们与 Codex 的新上下文机制走在同一条路线：持久历史 + 可引用工作记忆 + 有限工作集 + 按需回查。San 已有其中的核心结构，并加入了明确的输入控制；但“主动维护笔记”和“未知历史的精准搜索”不能直接宣称等价。至于 Looped Transformer，与这一机制不是同一层，不能混着比较。
