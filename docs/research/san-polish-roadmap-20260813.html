San 打磨规划

2026-08-13 · 基线:main @ PR #16 合并后,在飞 PR #17–#22 · 性质:打磨规划(不加新功能)
本文档回答一个问题:不加任何新功能,把已有能力磨到什么程度,San 才算兑现两句承诺——"敢挂一晚上"(可靠性)和"拎包入住"(零门槛)。所有条目都是对已存在机制的收尾、调参、验证或呈现修正;凡是"新能力"一律不在此列。

模式很清楚:这几天的开发速度远超验证速度。机制都在、单测都绿,但"真实世界里跑起来是什么样"的证据只有 M3 的两次 dogfood。打磨的主线就是把验证补上,用数据替换拍脑袋值,再把用户可见面修到"零阅读可用"。

一、可靠性:兑现"敢挂一晚上"

P0 1.1 整夜无人值守 dogfood(缺口最大的一块)

现状:runaway recovery、watchdog、San Loop、证据门全部就位,但从未在"多小时 + 多 turn + provider 抖动"的真实组合下跑过整夜。8/7 简报把它列为 P1,至今未执行。

  • 用 cpa/opencode-go/deepseek-v4-flash(你确认过量够)设计 3 个过夜场景:长重构任务(触发 compaction/decay/superseded-edit)、依赖外部信息的任务(触发 needs-user 终态)、故意模糊的任务(触发 watchdog 重复检测)。
  • 每场景硬预算封顶(maxCost/maxDuration),晨检指标:是否到达可解释终态、token 曲线是否稳态、watchdog 提醒次数、cache probe 归因分布。
  • 验收:三场景全部在预算内到达可解释终态(完成/阻塞/需要用户皆可,唯独不能是"还在转圈")。

预估:脚本半天(复用 m3-skill-gates-dogfood 骨架),跑三晚,晨检各半小时。

P0 1.2 用真实数据回归所有拍脑袋参数

现状:decay 的 K=2.4/4.8 与 0.5 压力地板照抄 MC 形态;watchdog repeatThreshold=3;应急档 stub 成本 40 token;cache probe 命中阈值 0.5、TTL 5 分钟——全部是首版起步值,零真实数据支撑。

  • 1.1 的过夜会话 + 你日常使用一周的 journal,就是参数回归的数据集(cache probe、watchdog 决策、decay tier 选择都已落 journal/audit,数据自动在攒)。
  • 写一个离线分析脚本(读 journal 聚合,不碰运行时):decay 各 tier 的实际命中分布、watchdog 提醒的误报率(提醒后模型是否真的在原地打转)、应急档触发频率与挽回量。
  • 验收:每个参数要么被数据确认,要么被数据修正,audit reason 里能看到依据。

预估:分析脚本 1 天,数据积累与调参跟着日常使用走。

P1 1.3 watchdog 从"提醒"补到"制动"(收尾既有机制,不是新功能)

现状:根会话 watchdog 只 fold 一次性提醒,不阻断。交互会话这是对的(裁量权在人);但 auto-continue / 无人值守场景没人看提醒,失控回合会继续烧钱——这正是"挂一晚上"的洞。

  • 仅在无人值守路径(auto-continue 激活、San Loop worker)消费 watchdog 的 suspicious 决策:连续 N 次同指纹 suspicious → 停止自动继续,置可解释暂停(复用 PAUSED 语义与恢复路径,不新造状态)。
  • 交互会话行为零变化。
  • 验收:1.1 的"模糊任务"场景里,失控回合在制动点停住且晨检能看懂停在哪、为什么。

预估:2-3 天(消费点已存在,主要是 auto-continue 路径接线 + 测试)。

P1 1.4 flaky 测试系统性清理

现状:pause-gate 靠固定 sleep 的形态修过一例;message-pipeline 那个"分片顺序才暴露"的失败说明还有测试对执行顺序有隐性依赖。CI 一次 28 分钟,flake 一次就是半小时打水漂。

  • 全量扫描测试里的固定 Bun.sleep 等待(约束:等待条件而不是等待时间),以及跨文件全局状态(registerCustomApi 等注册表)的清理缺失。
  • 验收:连续 5 次全量 CI 无 flake;新增 lint 约束或测试守则条目防回潮。

预估:1-2 天。

二、信任呈现:兑现"拎包入住"

P0 2.1 错误消息人话化审计(拎包入住的最痛点)

现状:契约回显刚人话化(PR #22),但错误路径没审过。provider 报错、凭据缺失、预算触顶、PAUSED_FOR_CONTEXT——这些时刻用户最需要一句人话,现在很多是原始错误直出。

  • 枚举高频错误场景(凭据无效/额度耗尽/网络断/上下文暂停/工具超时),对每个场景检查 TUI 实际呈现,按"一句话说清卡在哪 + 一个可执行的下一步"重写。
  • 验收标准就用 AGENTS.md 新原则:零配置零阅读的小白看到错误后知道下一步做什么。

预估:审计半天 + 修 2-3 天(文案为主,少量呈现分支)。

P1 2.2 首启体验:唯一的硬门槛是凭据

现状:M1 配置减法解决了"配置面吓人",但第一次打开 san 到第一个任务完成之间的路径没有专门审过。凭据配置是唯一绕不开的一步,它的引导质量决定第一印象。

  • 跑一次"新机器冷启动"演练:干净环境装 san → 首启 → 配凭据 → 完成第一个任务,记录每一步的摩擦(提示是否明确、失败是否可恢复、默认模型选择是否合理)。
  • 只修摩擦点,不加向导框架(避免变成新功能)。
  • 验收:冷启动到第一个任务完成 ≤ 5 分钟、零文档查阅。

预估:演练半天,修补 1-2 天。

P2 2.3 "三状态"呈现一致性审查

现状:AGENTS.md 定了"用户只见三状态"(在干什么/完成了/卡在哪),但存量呈现没有按这个标准过一遍。San Loop 的结果输出、task 子代理的状态、后台任务通知——各有各的格式。

  • 对照三状态标准过一遍主要呈现面,把机制词汇和原始记录收进折叠层。
  • 验收:主路径上任何一条 agent 产生的状态消息,截屏给一个没用过 San 的人,能看懂。

预估:2-3 天,可拆小步随手做。

三、证据闭环:让"更好地完成任务"可测量

P0 3.1 北极星 benchmark 固化(novice-first 计划 §7 的未竟项)

现状:指标定义早就有了(无人值守终态率/终态可解释率/预算内完成率),M3 dogfood 脚本是雏形,但"10 条固定样本可重跑"没做。没有它,所有打磨都无法回答"变好了还是变坏了"。

  • 把 M3 的 fixture 模式扩成 10 条固定样本:5 条修 bug(不同语言/复杂度)、3 条小功能、2 条模糊需求,全部预算封顶。
  • 产出一个 bun run bench:north-star:跑完输出三个指标 + 每样本终态明细,JSON 落盘可对比历史。
  • 验收:同一 commit 跑两遍指标稳定;每次大改动前后各跑一遍成为惯例。这份数字也是将来对外叙事的弹药("什么是好 agent"的可测量回答)。

预估:2-3 天(样本设计是主要工作量,跑法复用 dogfood 骨架)。

P1 3.2 cache probe 基线 → §4.2 本体(严格按"观测先行"推进)

现状:归因观测已上(PR #21),基线在日常使用中自动积累。§4.2 本体(bust 时机对齐)必须等数据。

  • 一周后跑离线聚合:prefix_diverged 占比多高、集中发生在什么操作之后(checkpoint rebase?plan 重写?)。
  • 若数据显示 prefix_diverged 是主要击穿源且集中可归因 → 做对齐改动,前后对照验证;若不是 → §4.2 关闭,省下 1-2 周。
  • 验收:决策由数据做出,两个方向都算完成。

预估:聚合脚本半天(可与 1.2 合并),决策点在一周后。

P2 3.3 dogfood 资产归档制度化

现状:两份 M3 真实模型报告躺在 /tmp,重启就没了。这些是"San 兑现承诺"的第一批证据,应该入库。

  • 把 /tmp 两份 JSON 归档进 docs/research/dogfood-runs/;dogfood 脚本加 --archive 直接写该目录。
  • 验收:任何 dogfood 运行一条命令即可归档,报告带 commit hash 可追溯。

预估:半天。

四、内置内容:证据链 skill 的密度

P1 4.1 证据链 skill 从 2 条扩到覆盖高频场景(内容补齐,不是新机制)

现状:机制(M2/M3)支持任意证据链 skill,但内置只有 fix-bug 和 build-web。用户日常任务的大头(重构、加小功能、查性能、升依赖)没有证据链兜底——机制的杠杆没拉满。

  • 按 M2 写作规范补 3-4 条:refactor(改前后行为等价:同套测试前后都过)、add-feature(新测试先失败后通过 + 回归面)、debug-perf(基准数字前后对比)、upgrade-dep(升级后全量测试 + 构建)。
  • 每条都跑一次 soft dogfood 验证引导有效(复用现有脚本,deepseek-v4-flash)。
  • 验收:北极星 benchmark(3.1)的样本任务全部有对应证据链命中。

预估:每条半天(写 + dogfood),共 2 天。

五、执行顺序与本周建议

周期做什么为什么先做它
本周3.1 北极星 benchmark → 1.1 整夜 dogfood(前者是后者的度量工具)→ 2.1 错误消息审计(穿插做)先立尺子再跑夜车:没有 benchmark,后面所有调参和打磨都没有"变好了"的判据。错误消息审计独立无依赖,适合等 CI/跑夜车的间隙推进。
下周1.2 参数回归(夜车数据已攒)→ 1.3 watchdog 制动 → 4.1 skill 扩充 → 3.2 cache 数据决策全部依赖第一周的数据与尺子;skill 扩充给 benchmark 样本提供证据链覆盖。
随手1.4 flaky 清理、2.2 首启演练、2.3 三状态审查、3.3 归档制度无依赖、可拆小,适合 CI 等待间隙与心情调剂。
不做清单(明确排除,防止打磨变扩张):TUI 重写、web console、desktop(单独立项,不混进打磨)、上游横向功能追随、跨会话记忆库、语义检索栈、§4.2 本体在数据到位前的任何实现。判据只有一条:这件事让"稳定完成任务"的三个北极星指标变好吗?不能回答就不做。

六、一句话总结

这几天把"敢挂一晚上"的机器造完了;接下来两周的全部工作,是让机器自己证明这句话(benchmark + 整夜 dogfood + 数据调参),同时把用户会碰到的每一句话磨成人话(错误消息 + 首启 + 三状态)。功能一个不加,承诺全部兑现。
