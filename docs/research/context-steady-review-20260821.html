San · Context Steady 子系统复盘

上下文稳态子系统全量复盘：18 项缺陷，其中一项吃掉了全部归档收益

本文重新梳理 src/context-steady/ 全部 11 个模块与 agent-session.ts 的四个接入点， 列出复盘中确认的每一项缺陷。所有结论都用生产数据验证：会话 01a00e60-43bf-7000-bd9c-69cbcee1adcc 的 38,612 条 journal entry、 2,349 条 probe 记录，以及把真实压缩后窗口直接喂进生产 planner 的重放实验。

复盘日期 2026-08-21 · 分支 tmp/reliability-commit-20260817 · 未修改任何 src/ 代码

核心结论。ContextPlan 的物料准入用 JSON.stringify 估算 token， 淘汰环却用渲染后的 markdown 估算。两者系统性偏差：checkpoint 渲染体积只有 JSON 估算的 0.76 倍，digest 约 0.46 倍。于是一个真实上线只要 2,483 token 的 checkpoint，被 maxTokens: 3000 的预算按 3,279 的虚高估算拒掉。

而 checkpoint 落选时，它折叠的 digest 仍然被过滤在候选之外 （planner.ts:230 判的是 includeCheckpoint 而不是"是否真的进了 materials"）， 历史覆盖权直接归零。审计里既没有 checkpoint 条目、也没有 omitted 条目， 全程静默。

用生产输入实测：线上配置下 ContextPlan 归档 2 条 entry（8 token）、自身花掉 254 token ——净亏 246 token。仅把 maxTokens 从 3000 抬到 3400、其它一律不动， 归档变成 154 条 entry（39,733 token）、自身 2,551 token ——净省 37,182 token。

覆盖权归零 ⟹ 投影 token ≈ 原始 journal ⟹ steady 门触发 ⟹ 压缩 ⟹ 冷启动。 本会话 74 次压缩中 70 次的 primaryTrigger 就是 steady_target；97 次冷启动共 9,495,490 token，占本会话 prompt token 的 4.1%。

1. 覆盖权坍塌 D1〜D4

先讲清机制，四个缺陷是同一条链上的四环。

设计意图

ContextPlan 的价值在于覆盖权：一份物料（digest 或 checkpoint）声明它覆盖了哪些原始 entry，物化层就可以把那些 entry 从 payload 里删掉。覆盖权由 coverage.ts 严格从 当前这一版 plan 的 materials 累加—— 物料被淘汰，它覆盖的原始 entry 立刻回到 payload。这个设计本身是对的：不能让被删掉的 entry 失去任何代表。

D1 P0 准入与淘汰用两套估算器，方向系统性相反

planner.ts:59-61（准入）：

function materialTokenEstimate(value: unknown): number {
	return estimateTokens({ role: "user", content: JSON.stringify(value), timestamp: Date.now() });
}

planner.ts:480-482（淘汰）：

function estimateContextPlanWireTokens(renderedContent: string): number {
	return estimateTokens({ role: "user", content: renderedContent, attribution: "agent", timestamp: Date.now() });
}

checkpoint 的 tokenEstimate 还有第三套：checkpoint.ts:48 的 estimateCheckpointTokens，在 checkpoint.ts:256 落库时算一次，之后 planner 直接读这个存量字段（planner.ts:209）。

把本会话 5 个真实 checkpoint 和前 8 个真实 digest 分别过一遍"存量估算"和"渲染后上线体积"：

后果。偏差恒定 0.76，说明这不是噪声而是两个函数在度量两样不同的东西： JSON 里的引号、花括号、字段名、转义全都被计入了预算，而它们永远不会上线。 结果是预算门槛被系统性抬高约 30%：真实只花 2,483 token 的 checkpoint 撞在 3000 的墙上。 我先前的判断是"准入宽松、淘汰严格"，实测方向恰好相反——准入更严， 而且严到让第 3 个 checkpoint 起就永远进不去。

D2 P0 checkpoint 落选，但它折叠的 digest 仍被过滤掉

includeCheckpoint 表达的是"这个 checkpoint 与当前 prompt 相关、我想带上它"。 过滤 digest 时复用了这个变量，语义却被当成"checkpoint 已经在 materials 里，所以它折叠的 digest 可以省掉"。当 checkpointEstimate > remainingBudget 时，两个语义分叉： checkpoint 没进去，它折叠的 30 个 digest 也被排除了。

D3 P0 fitMaterialsToPlanBudget 声明的优先级从未生效

planner.ts:269-299 的注释写着 "Drop recall first, then oldest digests, then checkpoint last."——checkpoint 优先级最高，最后才淘汰。这个意图是对的： checkpoint 是覆盖权密度最高的物料，一条抵 30 个 digest。

但 checkpoint 在 buildMaterials 阶段就已经被拒掉，根本走不到这个淘汰环。 于是代码里同时存在两套互相矛盾的优先级：准入阶段 checkpoint 最先被牺牲， 淘汰阶段声明它最后被牺牲。实际生效的是前者。

D4 P0 坍塌全程不可观测

checkpoint 装不下时，buildMaterials 既不 push runtime 物料，也不写审计条目。 而 buildOmittedAuditMaterials（planner.ts:302-320）在生成 omitted 记录时，会主动排除掉被 checkpoint 折叠的 digest：

const checkpointCoveredRefs = new Set(sourceIndex.checkpoints.at(-1)?.coveredDigestEntryRefs ?? []);
return sourceIndex.digests
	.filter(source => !representedDigestRefs.has(source.entryId) && !checkpointCoveredRefs.has(source.entryId))

逻辑是"被 checkpoint 覆盖的 digest 不算遗漏"——在 checkpoint 真的进去时成立， 在它落选时正好把唯一的证据抹掉。

历史语料印证：本会话持久化的 31 条 san.context_plan 审计中， 零条包含 checkpoint 物料，coverage 计数依次为 1/0/3/0/0/0。checkpoint 机制在这个会话里 从未产生过任何效果，而没有任何一条日志说过这件事。

关于用户看到的"5 万 token 冷启动换 600 token 瘦身"。 这不是摘要算法的能力上限，而是这条链把它的输出全部丢弃后的残值。 同一份 checkpoint、同一份 digest、同一个窗口，预算门放对以后一次归档 39,733 token。 算法产出是好的，准入逻辑把产出扔了。

建议修复

  1. D1：统一到上线体积。准入也用渲染后估算——把候选物料先渲染一次再量， 或者给 checkpoint / digest 各自落一个 wireTokenEstimate 字段。 最小改动版本：materialTokenEstimate 改成走 renderContextPlanContent 的单物料路径。存量 tokenEstimate 保留给 checkpoint.maxTokens 的自身收敛逻辑， 不再参与 plan 预算判断。
  2. D2：把"想要"和"进了"分成两个变量。 const checkpointAdmitted = ...，第 230 行的过滤条件改用 checkpointAdmitted。这一行改动单独就能消除坍塌——checkpoint 装不下时， 它折叠的 30 个 digest 会重新成为候选，覆盖权退化为"按 digest 粒度"而不是"归零"。
  3. D3：让 checkpoint 走淘汰环。准入阶段无条件收下 checkpoint， 超预算的判断交给 fitMaterialsToPlanBudget——它已经写好了正确的优先级。
  4. D4：坍塌必须留痕。checkpoint 落选时写一条 representation: "omitted" 的审计，reason 带上 checkpointEstimate 与 remainingBudget 的实际数值； buildOmittedAuditMaterials 的 checkpointCoveredRefs 排除条件 加上"checkpoint 确实进入了 materials"的前提。

建议顺序：D2 单独可上（一行，风险最低，立刻止血）→ D4（可观测性，防止再次静默） → D1（估算器统一，收益最大但要重跑 planner 全部测试）→ D3（结构调整，依赖 D1 完成）。

2. 正反馈环：74 次压缩从哪来 D5〜D6

D5 P0 覆盖权归零 → 压缩 → 覆盖权更低

把 §1 的坍塌接到会话级行为上，得到一个自我强化的环：

  1. checkpoint 随折叠的 turn 数增长，第 3 个起 tokenEstimate 越过 contextPlan.maxTokens（1,926 → 2,970 → 3,098 → 3,332 → 3,279）。
  2. D1+D2：checkpoint 落选，它折叠的 digest 一并消失，覆盖权 ≈ 0。
  3. 覆盖权 ≈ 0 ⟹ 物化后 payload ≈ 原始 journal ⟹ 投影 token 撞上 steady 门。
  4. 触发压缩。压缩重写前缀，冷启动一次。
  5. 压缩把窗口切到 firstKeptEntryId 之后，更多 digest 的 source.fromEntryId 掉到窗口外（见 D6），能解析出的覆盖范围进一步缩小。
  6. 回到第 2 步，压力更大。

关键归因。74 次 context-full 压缩里，70 次的 primaryTrigger 是 steady_target，只有 7 次是 native_threshold。也就是说压缩不是被模型的原生上下文上限逼出来的， 是被我们自己的 steady 门逼出来的；而 steady 门之所以会触发， 是因为覆盖权坍塌导致投影 token ≈ 原始 journal。§1 那四个缺陷直接对应这 9,495,490 token 的冷启动。

D6 P0 压缩后 digest 的 span 解析退化成 toolEvidence 兜底

source-index.ts:20-29：

function sourceEntryRefsForDigest(entries: readonly SessionEntry[], digest: TurnDigest): string[] {
	const fromIndex = entries.findIndex(entry => entry.id === digest.source.fromEntryId);
	const toIndex = entries.findIndex(entry => entry.id === digest.source.toEntryId);
	if (fromIndex < 0 || toIndex < 0 || fromIndex > toIndex) {
		return digest.toolEvidence
			.flatMap(evidence => evidence.entryIds ?? [])
			.filter(entryId => entries.some(entry => entry.id === entryId));
	}
	return entries.slice(fromIndex, toIndex + 1).map(entry => entry.id);
}

planner 看到的 entry 只有压缩后窗口（agent-session.ts:10198-10262 的 #contextSteadyActivePlanningEntries 从最近一次压缩的 firstKeptEntryId 起切片）。digest 的 fromEntryId 一旦落在切点之前， 上面的分支就走兜底路径——用 toolEvidence 里零散的几个 entryId 代替本该是几百条的连续区间。

实测：该会话 journal 里共 32 条 san.turn_digest， 但最后一次压缩后的窗口里 buildContextSourceIndex 只解析出 4 条 digest —— 28 条（87.5%）对 planner 完全不可见。 这 28 条覆盖的历史只剩 checkpoint 一个载体（窗口内唯一那个 checkpoint 的 coveredSourceEntryRefs = 153 条、coveredDigestEntryRefs = 2 条）。

为什么这让 §1 变成灾难而不只是缺陷。digest 大量掉出窗口以后， checkpoint 是压缩后历史的唯一承载者。这时把 checkpoint 拒掉， 等于一次性丢掉整段历史的全部代表，而不是"少几条 digest"。 D1〜D4 的严重程度是被 D6 放大出来的。

建议修复

  1. D6：让 digest 自带持久化的 span，而不是每次现场反查。 digest 落库时就把它覆盖的 entryId 列表写进去（或者写一个稳定的 [fromSeq, toSeq] 序号区间），sourceEntryRefsForDigest 改成 "取交集"而不是"找端点"：storedRefs.filter(id => windowIds.has(id))。 这样端点掉出窗口只会等比缩小覆盖范围，不会掉进兜底路径。
  2. D6 兜底路径要留痕。走了 toolEvidence 分支时在审计里标记， 否则"解析出 20 条"和"真实 700 条"在日志里长得一模一样。
  3. D5：修完 D1〜D4 + D6 后重新量 primaryTrigger 分布。 steady_target 占比应显著下降；若仍居高，说明 steady 门本身的阈值需要单独审视， 而不是覆盖权问题。这条是验收指标，不是独立修复项。

3. 缓存维度：plan 每轮重渲染破坏前缀 D7〜D9

这一节是本次调查最初的入口问题（"5 万 token 冷启动换 600 token 瘦身"）。 §1 已经说明"600 token"是坍塌后的残值；这一节说明"5 万 token 冷启动"是怎么来的。

D7 P1 plan 消息每轮重渲染，且随覆盖推进塌向 payload 头部

两个机制叠加：

(a) 内容会变。materialize.ts:132 的 renderContextPlanContent 每次都把每个 digest 过一遍 projectDigestTier，而 tier 由 decay.ts 的 selectDigestTier(ageRank, pressure) 决定：

const PRESSURE_FLOOR = 0.5;
const COMPACT_ALLOWANCE_K = 2.4;
const ANCHOR_ALLOWANCE_K = 4.8;
export function selectDigestTier(ageRank: number, pressure: number): DigestTier {
	if (ageRank <= 0) return "full";
	if (!Number.isFinite(pressure) || pressure < PRESSURE_FLOOR) return "full";
	const effective = Math.max(pressure, 0.1);
	const compactAllowance = Math.ceil(COMPACT_ALLOWANCE_K / effective);
	const anchorAllowance = Math.ceil(ANCHOR_ALLOWANCE_K / effective);
	if (ageRank >= anchorAllowance) return "anchor";
	if (ageRank >= compactAllowance) return "compact";
	return "full";
}

ageRank 每来一条新 digest 就整体前移，pressure 每轮都在浮动。 于是即使没有新 digest 产生，同一批 digest 的渲染文本也会在某一轮突然从 full 变 compact，plan 消息字节改变，其后整条前缀失效。

(b) 位置会变。materialize.ts 里 insertAt = Math.max(0, substituted.findLastIndex(m => m.role === "user"))。 覆盖权删掉越多老消息，这个下标越往 0 塌，plan 消息越靠 payload 头部—— 一个每轮都可能变的消息被放在前缀最前面，是缓存最坏的位置。

已有的正确先例。agent-session.ts:10573-10615 已经在 单个逻辑 turn 内冻结 plan 字节，注释写得很清楚："每次工具调用都重写投影值会让 plan 之后的整条 turn 前缀失效，实际会把 provider cache read 压到仅剩 system/tools。" D7 要做的就是把这个已被证明有效的原则从"turn 内"推广到"turn 间"。

D8 P1 规划目标函数里没有缓存项

buildMaterials 的唯一预算变量是 remainingBudget， 计的是 payload token。改写 plan 前缀要付多少冷启动，在整个目标函数里没有任何表示。 于是"省 600 payload token"和"付 56,652 token 冷启动"这两件事， 在代码里根本不在同一个天平上——不是权衡错了，是没有权衡。

D9 P1 decay 为"可复现"设计，而不是"跨轮稳定"

decay.ts 头部注释："纯函数,同输入永远同输出——同一历史在同一压力下逐字节可重现。" 这个性质对测试和审计很有价值，但它不等于跨轮不变： ageRank 和 pressure 每轮都在变，所以"同输入同输出"的前提每轮都不成立。 设计目标定的是可复现性，缓存需要的是稳定性，两者被混同了。

建议修复（三个选项，需要拍板）

  1. 方案 A（推荐，改动最小）：plan 字节按 epoch 冻结。 把现有的 turn 内冻结提升为"直到发生 rebase 事件（压缩 / 新 checkpoint / 显式失效）才允许重渲染"。 digest 的 tier 在冻结期内锁定，新 digest 追加到 plan 尾部而不重排 ageRank。 代价：plan 在冻结期内略微偏离最优瘦身。
  2. 方案 B：把 plan 挪到 payload 尾部。让 plan 变成前缀里最后一个元素， 这样它变化时只失效自己之后的部分。需要确认物化层的语义（plan 必须出现在被它覆盖的 entry 之前才能解释删除）是否允许——大概率不允许，所以这是备选。
  3. 方案 C：给目标函数加缓存项。在 buildMaterials 里显式估算 "改写 plan 的冷启动成本"，只有瘦身收益超过它才允许重渲染。最正确，但需要引入前缀长度的运行时反馈， 工程量最大。
比例提示。D7〜D9 是真实缺陷，但量级远小于 §1。 digest 冷启动 19,205,063 token 是跨全部会话 339 次事件的累计； 单看本会话，冷启动总计 9,495,490 token，其中主导项是 70 次 steady_target 压缩。先修 §1，再看 §3 还剩多少。 修完 §1 以后 digest 事件数本身会下降（压缩变少 ⟹ digest 生成变少）， D7 的绝对收益需要重新测量再决定投多少工程量。

4. 窗口与周期错配 D10

D10 P1 recentDigests 与 checkpoint.everyTurns 互不知情

两个独立旋钮共同决定"一条 digest 会不会既进不了 plan、又没被 checkpoint 折叠"：

  • san.contextSteady.contextPlan.recentDigests，默认 5 （settings-schema.ts:2950）—— plan 最多带几条 digest。
  • san.contextSteady.checkpoint.everyTurns，默认 8 （settings-schema.ts:2976），用户线上配置 6 —— 每几个 turn 才折叠出一个 checkpoint。

checkpoint.ts:~220 明确写着不满一个周期的尾巴不折叠： "Residual digest tails smaller than checkpointEveryTurns intentionally stay unfolded; the ContextPacket recent-digest tail carries those fresh turns." ——这个设计成立的前提是 recentDigests ≥ checkpointEveryTurns。

配置recentDigestseveryTurns孤儿 digest

用户线上 .san/config.yml56每 6 条里有 1 条

孤儿 digest 的代价：它写入时付了摘要模型的费用，落库占了 journal 体积， 但既不上线也不授予任何覆盖权——纯粹的沉没成本。

建议修复

  • 把不变式写进配置解析：recentDigests = max(configured, checkpointEveryTurns)， 或在配置校验时对 recentDigests < everyTurns 报警。
  • 更彻底的做法是让 recentDigests 从 everyTurns 推导，不再作为独立旋钮暴露。

6. 配置陷阱：互不校验的旋钮 D12〜D14

D12 P1 checkpoint.maxTokens 允许生成一个 contextPlan.maxTokens 装不下的 checkpoint

用户线上配置：checkpoint.maxTokens: 12000、contextPlan.maxTokens: 3000。 checkpoint.ts:285-307 的收敛逻辑（先裁条目上限 20/20/30/12/12， 再按 nextSteps → risks → filesTouched → decisions → userIntents 顺序削减， 再把叙述文本从 120 字逐步夹到 8 字，最后 return null 失败关闭） 唯一的目标就是让 tokenEstimate ≤ checkpointMaxTokens = 12,000。

而 checkpoint 唯一的上线容器是 ContextPlan，预算 min(planMaxTokens, messageBudget) = 3,000。生成器的合法输出空间比容器大 4 倍，且没有任何一处代码校验这个关系。 已确认：grep 全仓库，checkpointMaxTokens 与 planMaxTokens 没有任何共同消费点（前者只在 checkpoint.ts 和 dogfood.ts， 后者只在 budget.ts、dogfood.ts 和 agent-session.ts 的四个调用点）。

修复：checkpoint 生成时就以 plan 能容纳的上线体积为收敛目标 （配合 D1 统一估算器后，这个数就是"渲染后 ≤ planTokenBudget × 某个占比"）； 或者至少在配置校验时对 checkpoint.maxTokens > contextPlan.maxTokens 报警。

D13 P2 burstWindowTokens < qualityWindowTokens 静默塌成零弹性带

budget.ts:34 一线：

const burstCeiling = Math.min(Math.max(configuredBurst, steadyTarget), hardInputCeiling);

配一个低于 qualityWindowTokens 的 burstWindowTokens， Math.max 会把它抬回 steadyTarget——burst 与 steady 相等， 弹性带为零，每一次压力尖峰都直接变成压缩，而配置里看不出任何异常。

用户已经踩过这个坑的变体，并把过程写在了 .san/config.yml 的注释里： "reserveRatio 0.25 put the reserve-derived hard ceiling at 193500, below the 240000 quality window, which clamped steady == control == burst: no elastic headroom, so every pressure spike became an immediate compaction and each compaction rewrote the cache prefix." ——踩坑记录进了注释，但代码里仍然没有告警。

修复：resolveContextPlanBudget 在 burstCeiling === steadyTarget 时输出一条 warn 级审计；配置校验对 burstWindowTokens < qualityWindowTokens 直接报错。

D14 P2 32k 固定 reserve 下限可以把 hardInputCeiling 打到 0

budget.ts:31：

const reserveTokens = contextWindow > 0 ? Math.max(32_000, Math.floor(contextWindow * reserveRatio)) : 32_000;

hardInputCeiling = contextWindow − reserveTokens。小窗口模型 （32k 及以下）上 hardInputCeiling ≤ 0，后续 steadyTarget / controlMax / messageBudget 全部退化。 当前线上模型窗口 258,000，不受影响，但这是一枚等着被小模型踩的雷。

修复：reserve 下限改成 min(32_000, floor(contextWindow × 0.2)) 之类的相对量，并在 hardInputCeiling 非正时明确失败而不是静默降级。

7. 性能：每请求二次扫描 D15

D15 P2 source-index.ts 在 filter 里嵌 entries.some

两处（source-index.ts 的 checkpoint 覆盖过滤与 sourceEntryRefsForDigest 的 toolEvidence 兜底）都是 O(coveredRefs × planningEntries)：

? ref.checkpoint.coveredSourceEntryRefs.filter(entryRef => entries.some(entry => entry.id === entryRef))

coveredSourceEntryRefs 的分布（全语料）： p50 = 98、p75 = 762、p90 = 1,733、p99 = 36,405、max = 38,347。 单条 checkpoint 的 JSON 最大 0.42 MB。

当前窗口只有 205 条 entry，所以实际开销约 7.2M 次比较/请求，可以忍。 但窗口在压缩触发前会长到数千条，此时比较次数进入 108 量级—— 而且这发生在每一次请求组装的关键路径上。

说明我先前的口径。我一度按整个 38,612 条 journal 估算出 70 亿次比较， 那是错的——planner 只看压缩后窗口。正确的表达是 coveredRefs × planningEntries，当前约 7.2M，压缩触发前可达 108 量级。

修复：把 entries 预先建成 Set<entryId> 或 Map<entryId, index> 传下去， some/findIndex 全部改成 O(1) 查表。这是纯机械改动，无行为变化。 配合 D6 的 span 持久化一起做最自然。

8. 死代码与三份重复实现 D16〜D18

D16 P2 prune.ts 221 行没有生产调用方

9. 测试盲区

test/context-steady/planner.test.ts 里 SETTINGS.planMaxTokens = 240_000——比任何真实 checkpoint 大两个数量级， 所以准入门在这些用例里永远不会触发。超预算路径只有两个用例， 用的是 planMaxTokens 40 和 135：小到连一条 digest 都装不下， 测的是"预算几乎为零"的退化形态。

真实形态从未被测：checkpoint 刚好越过预算，而 digest 还装得下。 这正好是生产上每天发生的情况，也正好是 D1+D2 联合发作的唯一条件。 这就解释了为什么一个能把归档收益从 +37,182 打成 −246 的缺陷能通过全部测试。

建议补的用例

  • 坍塌回归用例：1 个 checkpoint（tokenEstimate 略高于 planMaxTokens、渲染后低于它）+ 若干它折叠的 digest + 2 条新 digest。 断言：覆盖的 entry 数必须远大于新 digest 数（即 checkpoint 或它的 digest 至少有一方进来了）。 这个断言在修 D2 之前必失败，修完必通过。
  • 估算器一致性用例：对同一物料，断言准入估算与上线估算的比值在合理区间 （例如 0.9〜1.1）。D1 修完后成立，防止未来再分叉。
  • 净收益不变式：断言 归档 token > plan 自身 token， 否则 plan 不该被注入。这条能自动拦住所有"净亏"形态，包括还没想到的。
  • span 兜底用例：digest 的 fromEntryId 落在窗口外时， 断言覆盖范围按比例缩小而不是掉到 toolEvidence（D6 修完后成立）。
  • 配置不变式用例：recentDigests ≥ everyTurns、 checkpoint.maxTokens ≤ contextPlan.maxTokens、 burstCeiling > steadyTarget。
