San Context Steady v0.1 二次代码审查报告

对 GPT-5.5 修订后的当前工作区进行需求、运行时正确性、预算边界与安全边界复审

日期：2026-07-12 分支：feature/san-v0.4-workflows 基线：b014dd7c7 + 未提交修订 范围：packages/coding-agent/context-steady 性质：只审查，不修改实现

结论先说

本轮复审不通过，当前修订不建议合入。 GPT-5.5 修对了一批摘要质量问题，但新加入的“直接裁掉所有已生成 digest 的原始历史”与“永久保留每轮 delta packet”组合在一起，产生了两个阻断问题： 一边可能在没有替代上下文时丢失历史，另一边又让已注入的摘要、checkpoint 和召回内容无限累积。它目前既不能保证“上下文不失忆”，也不能保证“上下文进入稳态”。

功能默认仍处于实验关闭状态，这限制了普通用户面的影响；但推荐 dogfood 配置会把整条链路打开，因此不能用“默认关闭”代替修复。 当前更准确的状态是：TurnDigest 质量修复大体可保留，ContextPacket 裁剪与 append-only delta 架构需要重做。

详细发现

P0-1

原始历史在没有替代上下文时仍会被删除

packages/coding-agent/src/context-steady/prune.ts:93、:128、:157； packages/coding-agent/src/context-steady/packet.ts:413、:457； packages/coding-agent/test/context-steady/prune.test.ts:171

当前 pruner 在 allDigestEntryRefs() 中收集分支上的所有 TurnDigest，然后把这些 digest 覆盖范围内的普通消息全部删除。 它不再要求当前 provider 请求中真的存在 ContextPacket，也不要求某个 digest 被当前 prompt 选中。

因此以下情况都会删掉原文，却没有等价替代内容：

  • 当前 prompt 与旧 digest 无关，相关性过滤后 packet 为 null。
  • contextPacket.maxTokens=0 或 packet 内容大于预算，builder 返回 null。
  • digest 没有进入最近窗口，或者被 token budget 裁掉。
  • 第一轮已经产生 digest，但下一轮 packet 尚未成功构建。
复现结果：
irrelevantPacket = null
zeroBudgetPacket = null
provider messages = ["unrelated weather question"]

被 digest 覆盖的 old user / old assistant 均已消失。

这不是普通的信息压缩，而是“先删除、后看有没有替代”。它也直接违反原始方案中的 Recent Exact Turns：最近 5 轮保留原文。当前实现实际做的是“上一轮一旦有 digest，下一轮就可以删除整轮原文”。

根因：代码把“journal 中存在摘要”错误地当成“当前请求中已激活且足够完整的替代表示”。这两个状态必须分开。

改造方案

  1. packet builder 输出显式的 PruneCoverage，逐项列出本次请求实际注入了哪些 digest/checkpoint，以及它们允许替代哪些 journal entry。
  2. pruner 只消费这份 active coverage；禁止再扫描“所有 digest”自行推断。
  3. packet 为 null、功能关闭、预算不足、相关性未命中时，coverage 为空，原始历史不得被删除。
  4. 实现独立的 recentExactTurns 窗口。最近 N 轮至少保留 user prompt、关键 assistant 决策和必要的工具短摘。
  5. digest 只提供索引，不自动获得删除原始证据的权力。
P0-2

append-only delta 没有边界，ContextPacket 仍然线性累积

packages/coding-agent/src/session/agent-session.ts:4428、:8007； packages/coding-agent/src/context-steady/packet.ts:428、:434、:493； packages/coding-agent/src/context-steady/checkpoint.ts:217； packages/coding-agent/test/context-steady/agent-session-m2.test.ts:361

修订移除了旧 packet 的清理逻辑，让每轮只追加一个新 digest delta。方向上是在追求 prompt cache，但缺少“何时结束一个 append-only 段”的设计。 现在 recentDigests=5 和 maxTokens 只作用于本轮新建的 delta，旧 delta 全部继续留在 active context。 

配置：recentDigests=5, maxTokens=200
8 次同主题 delta：每次 tokenEstimate ≈ 114

单块检查：114 <= 200       通过
真实累计：912 > 200         失败
active digest refs：8 > 5   失败

问题不只在 digest：

  • 新 checkpoint 是此前 checkpoint 的累计摘要，但旧 checkpoint packet 仍保留，导致覆盖内容重复。
  • checkpoint 覆盖的旧 digest delta 也不退休，形成 checkpoint + 原 digest 的双份表示。
  • recall 是随当前 prompt 变化的 volatile 层，但旧 recall packet 也永久保留；切换话题后仍会继续影响模型。
  • 实时会话保留旧 packet；resume 时 SessionManager 又会过滤旧注入消息，行为在重启前后不一致。

当前进度文档所写的“ContextPacket 总预算 gate 已完成”只对单个新 packet成立，已经不再代表 provider 实际看到的 packet 总量。

根因：append-only 是缓存布局策略，不是无限保留策略。它必须有 bounded epoch、累计预算和受控 rebase。

改造方案：有界 epoch

  1. 把 active context-steady 状态建模为一个 epoch：epochId、base checkpoint、delta refs、exact-tail refs、累计 token。
  2. epoch 内允许逐轮追加 digest delta，以保住缓存前缀。
  3. 达到 checkpoint、最近窗口、总 token、topic shift 或 resume 边界时，执行一次受控 rebase：用“新 checkpoint + 最近精确轮次 + 当前相关 tail”替换旧 packet 消息。
  4. 承认 rebase 会造成一次缓存断点，但断点必须低频、显式、可观测；不能用无限累积来换缓存。
  5. recall 独立为本轮 ephemeral 层，每轮替换，不进入 append-only 历史。
  6. 所有预算都对 active union 计算，而不是只计算新 delta。
P1-1

摘要模型副请求绕过秘密混淆与统一出站管线

packages/coding-agent/src/session/agent-session.ts:4290、:4345、:7213； packages/coding-agent/src/context-steady/digest.ts:243、:317； packages/coding-agent/src/sdk.ts:2661； packages/coding-agent/examples/config/san-context-steady-recommended.yml:12

主请求和其他副请求会经过 SecretObfuscator；TurnDigest 则把原始 turn span 直接 JSON 序列化，最多携带约 18K 字符，然后直接调用 completeSimple()。 它没有调用 #convertToLlmForSideRequest()，也没有走 SDK 的 transformProviderContext。

这意味着用户 prompt、工具结果、文件片段或错误文本里的已配置秘密，可能明文发送给 pi/smol 对应的模型；该模型还可能属于不同 provider。 推荐 dogfood 配置明确开启了 LLM digest，因此这不是只有手工实验配置才会触发的理论风险。

额外放大：fallback 的 userIntent 会复制用户文本前 200 字符，工具错误短摘也会复制错误内容。摘要随后被包装为 agent-attributed developer 消息，而现有秘密混淆器有意跳过 agent-attributed developer 内容。因此秘密一旦进入 digest，后续主请求也可能绕过保护。

改造方案

  1. 给 digest 统一使用 session 的 provider-bound side-request preparation，包括秘密混淆、provider transform、路由与审计 hooks。
  2. 不要把原始 message 对象整体交给摘要模型；构造最小化、字段白名单的 digest input。
  3. 文件正文、长工具输出和二进制附件默认不进入摘要请求，只发送工具名、状态、路径、entryId 和受限短摘。
  4. 持久化 digest 时保留秘密占位符，不把 provider 回复中的占位符反解回明文。
  5. 增加跨 provider 数据边界说明：开启 LLM digest 时，哪些数据会发往哪个 model role。
P1-2

不可信历史内容被提升为 developer 权限

packages/coding-agent/src/session/agent-session.ts:8030； packages/agent/src/compaction/messages.ts:162； packages/coding-agent/src/prompts/context-steady/context-packet.md:1； packages/coding-agent/test/context-steady/agent-session-m2.test.ts:152

ContextPacket 以 role: custom、attribution: agent 注入；通用转换器把 custom 消息转换成 role: developer。 测试还明确断言了这一行为。

但 packet 中的动态内容来自历史用户 prompt、assistant 摘要、工具输出、仓库文件和 memory recall。这些都不是可信开发者指令。 模板虽然写了“当前用户 prompt 优先”，provider 的角色层级却恰好相反：developer 高于 user。自然语言免责声明不能抵消消息权限。

一个写在 issue、README、工具输出或旧用户 prompt 中的恶意指令，经过 digest/recall 后可能长期停留，并以更高权限影响当前任务。这是典型的 confused-deputy / prompt-injection 放大。

改造方案

  1. 可信规则与不可信数据分离。只有固定、静态、仓库受控的处理规则可以是 developer 内容。
  2. digest、checkpoint、recall 的实际数据使用 user/data 语义，放在当前 user prompt 之前；不要转为 developer。
  3. 每条数据携带 provenance 与 trust label，例如 source=user_history、source=repository、trust=untrusted。
  4. 对结构边界做转义和长度限制，但不要把“加 XML 标签”当成权限隔离。
  5. 增加消息角色级测试，断言任何用户/工具/记忆派生文本都不能进入 system/developer 角色。
P1-3

token 估算与真实 provider 请求的裁剪条件不一致

packages/coding-agent/src/session/agent-session.ts:7224、:10975、:16220

provider 路径只有在 san.contextSteady.enabled=true 且 contextPacket.enabled=true 时才调用 pruner； #estimateStoredContextTokens() 和 getContextBreakdown() 却无条件调用同一个 pruner。

一旦 session 中已有 TurnDigest，用户随后关闭 context steady 或只关闭 ContextPacket，provider 会发送完整原始历史，状态栏与 pre-prompt compaction 却按“原始历史已被裁掉”来估算。 结果是低估 token、延迟 compaction，最坏情况下直到真实 provider 请求溢出才发现。

改造方案

  1. 集中生成一个 ContextSteadyProviderPlan，包含最终消息集合、coverage 与 token 估算。
  2. provider conversion、状态栏 breakdown、pre-prompt compaction、自动 compaction 全部消费同一 plan。
  3. 功能关闭、packet 关闭或 active coverage 为空时，plan 必须是 no-op。
  4. 增加开关切换测试，比较“估算使用的消息集合”和“mock provider 实际收到的消息集合”。
P2-1

任何 digest 都能授权整段删除，没有质量与完整性门槛

packages/coding-agent/src/context-steady/digest.ts:132、:187； packages/coding-agent/src/context-steady/fallback.ts:221； packages/coding-agent/src/context-steady/prune.ts:113

fallback digest 是为了“摘要模型失败时不断主流程”，它只保留有限的意图、工具状态和规则匹配文本。它不是完整替代品。 当前 pruner 不区分 LLM digest、fallback digest、错误/中止轮次或摘要字段完整度，只要有 source span，就会删除 span 中全部普通消息。

原始设计明确说 digest 是证据索引，关键证据应可重读，并保留最近精确轮次。当前实现却让最弱的 fallback 也可以立即成为整轮唯一表示。

改造方案

  1. 给 digest 增加可执行语义：generationMode、completeness、evidenceRefs、terminalState。
  2. fallback 默认只能帮助裁剪明确的 bulky payload，不能授权删除 user prompt 和 assistant 决策原文。
  3. 中止、错误和摘要失败的轮次默认进入 exact tail，直到后续 checkpoint 明确吸收。
  4. coverage 必须逐 entry 声明，而不是用 source span 一刀切。
P2-2

克隆消息用内容指纹关联，身份不稳定

packages/coding-agent/src/context-steady/prune.ts:19、:33、:39、:175

为了识别 transform 后的克隆消息，修订用 role + timestamp + JSON.stringify(content) 生成 key。 这能修掉一部分 fileMention/image clone 场景，但它不是稳定身份：相同时间戳和内容的重复消息会碰撞；非法日期字符串会在 toISOString() 抛出；大型文件内容还会在每次请求中重复序列化。

改造方案

  1. 在 journal 到 active-message 的构建阶段保留稳定 entryId 或内部 source ref。
  2. provider plan 直接按 entryId 生成 keep/drop 集合，避免通过内容反向猜身份。
  3. 内部 source ref 不进入 provider payload；只用于本地组装和审计。

哪些修改是正确的

本次不建议把 GPT-5.5 的改动整体回退。以下修订解决了真实问题，可以作为后续重构的保留项：

  • extractSpanMessages 为 message shim 带上 journal entryId，修复 tool evidence 无法回指原始证据的问题。
  • fallback digest 收集所有 assistant 消息中的决策，不再只看最后一条。
  • memoryCandidates.importance 与 0-1 契约统一。
  • turn boundary 脱离 active branch 时增加 debug 证据，降级不再完全静默。
  • 用户归属的附件描述可以进入 turn source span，方向正确。
  • 单个 packet 的内部 total-budget 裁剪逻辑仍有价值，但必须上移为 active epoch 总预算的一部分。

建议重构方案

建议不要继续在现有 previousPacket refs + allDigest prune 上打补丁。下一轮按下面四个阶段重构，顺序不可颠倒。

R1 安全止血
目标：先保证不失忆。 删除 allDigestEntryRefs() 对裁剪资格的参与；没有 active replacement 就不裁原文。恢复最近精确轮次窗口，并让 fallback digest 失去“整段删除授权”。
R2 有界 epoch
目标：真正进入稳态。 epoch 内 append-only；达到窗口、预算、checkpoint、topic shift 或 resume 条件时受控 rebase。checkpoint 吸收的 delta 必须退休；recall 每轮替换。
R3 统一计划
目标：一个事实源。 引入一次性 provider plan，统一最终消息、entry coverage、token estimate 和 debug 数据。provider、状态栏和 compaction 不再分别重算。
R4 安全边界
目标：秘密与权限不降级。 digest 副请求走统一出站管线；动态上下文不使用 developer 角色；数据带 provenance/trust 标签；增加 secret 与 prompt injection 合同测试。
