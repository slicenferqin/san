OMP 上游选择性吸收实施计划

首批只吸收可独立验证、直接改善正确性或性能、且不改变 San 产品语义的上游修复。拒绝整段 merge，也不把 Agent Hub、goal、schedule、omptype 等高冲突能力夹带进来。每个并行工作流拥有互斥的生产文件和测试文件，由主代理独占 changelog、跨域集成与最终验收。

1. 实施原则

追溯锁定上游提交
理解完整修复链
适配按 San 当前结构
重放行为而非盲 cherry-pick
守约新增合同级回归测试
不测实现文本
集成主代理审查交叉影响
统一 changelog
验收聚焦测试 → check
→ 包级测试
  • 上游提交是设计证据，不是机械补丁；San 已有能力优先保留，只补缺失语义。
  • 没有可复现合同、依赖大规模前置重构或与 San execution-control 冲突的候选，进入后续观察清单。
  • 子代理不得修改未分配文件；发现跨域依赖时只报告，由主代理改动或重新分派。
  • 所有新增测试必须保护外部可观察行为；禁止 source-grep、mock.module() 和全局污染。

4. 验收与退出条件

  1. 每个工作流提交候选清单：已吸收、San 已具备、因依赖/冲突暂缓，并附上游 commit。
  2. 主代理审查每个生产改动与测试，核对是否保护同一个用户可见合同，而非照搬上游内部结构。
  3. 先运行新增与邻近测试，再运行 bun check；最后运行受影响包级测试。任何失败必须修复或明确从范围移除。
  4. 由主代理统一写入各受影响包 CHANGELOG.md 的 [Unreleased]，避免并行冲突。
  5. 最终报告记录上游来源、实际差异、测试结果、未吸收项和下一轮候选；未经用户要求不 commit、不 push、不创建 PR。
停止条件：若某候选需要引入上游大规模重构、破坏 San 现有持久执行合同，或无法用聚焦测试证明收益，则从本批剔除，不用兼容层或静默降级强行落地。

本计划冻结的是第一批执行范围，不代表一次性同步全部上游能力；后续以相同门禁滚动吸收。
