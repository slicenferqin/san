按需工具加载方案

降低每轮 provider 请求固定携带的工具描述与 JSON Schema 开销，同时保留完整工具能力，并让高频代码工作流无需额外发现往返。

Decision

核心开发工具常驻，其余工具按需激活

采用 tools.discoveryMode: all。常驻 read、bash、edit、write、glob、eval、grep、lsp；其他内置工具通过 search_tool_bm25 发现并激活。

该方案不删除工具，也不缩减 registry。区别仅在于工具 Schema 是否从会话开始就进入每轮 provider 请求。

Requirement

需求与验收标准

需要解决的问题

  • 目标会话的 System tools 固定占用为 16,958 tokens。
  • 说明文档与参数 Schema 每轮进入上下文，但多数专项工具并非每轮使用。
  • 长期 coding 会话更需要把稳定预算留给代码、决策、测试输出和历史状态。

必须保留的行为

  • 完整工具能力仍可到达，不以禁用工具换取节省。
  • 读、搜、改、写、执行和 LSP 导航无需先发现工具。
  • 已选 MCP 工具继续随会话恢复。
  • 配置仅作用于 San 仓库，不改变全局用户配置和产品默认值。

Implementation

项目配置

配置写入 .san/config.yml。tools.essentialOverride 是替换列表，不是追加列表，因此必须完整列出所有需要常驻的内置工具。 

tools:
  discoveryMode: all
  essentialOverride:
    - read
    - bash
    - edit
    - write
    - glob
    - eval
    - grep
    - lsp

Runtime Semantics

按需加载的实际语义

  1. 所有工具仍注册在内部 tool registry。
  2. 非 essential 内置工具不进入初始 provider tool list。
  3. 模型通过常驻的 search_tool_bm25 在本地 BM25 索引中搜索工具。
  4. 命中的工具加入 active set，并触发 system prompt 与工具列表重建。
  5. 激活是会话内累积的；当前实现不会在单轮结束后自动卸载。

初始按需工具包括：

ast_grep ast_edit browser debug task job irc todo web_search
Trade-offs

代价与控制措施

接受的代价

  • 专项工具首次使用前多一次发现调用。
  • BM25 是词法匹配，搜索词过于抽象时可能漏掉目标工具。
  • 发现工具默认 limit 为 8，宽查询可能一次激活多个工具。
  • 工具激活后持续占用后续上下文，收益会随会话使用面扩大而递减。

已有控制

  • grep 与 lsp 常驻，覆盖高频代码定位路径。
  • search_tool_bm25 自身标记为 essential。
  • 需要强制 tool choice 的功能由运行时保持对应工具 active。
  • 已持久化选择的 MCP 工具在恢复会话时继续 active。
使用建议：发现目标明确时，将 search_tool_bm25.limit 设为 1–3，避免一次激活过多相近工具。该建议不依赖本次配置变更。
Verification

验证记录

配置解析通过。 config get tools.discoveryMode 返回 all； config get tools.essentialOverride 返回配置的 8 个核心工具。
会话行为通过。 使用目标 JSONL 的临时副本恢复会话，实际得到 15 个活动工具、10,186 个 System tools tokens；原始会话文件未作为写入目标。

Token 口径与 San /context 面板一致：工具名称、完整说明文本及 provider wire JSON Schema 的估算总和。

Scope & Rollback

范围与回退

  • 本次只修改 San 仓库的 self-hosting 配置，不修改产品默认行为。
  • 不改变工具实现、权限、Schema、MCP 连接或会话存储格式。
  • 若发现工具可靠性不足，可将 discoveryMode 改回 auto 或 mcp-only，并移除 essentialOverride。
