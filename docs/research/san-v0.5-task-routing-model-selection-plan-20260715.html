San Research / 2026-07-15

v0.5 任务路由与模型策略规划

让 San 根据任务的认知复杂度、上下文规模、操作风险和证据要求选择最低安全配置，并在执行中根据可观察证据升级策略。v0.5 是 0.1–0.4 稳定之后的储备版本，不参与当前基础版本的验收。

状态：方案储备 默认关闭自动路由 前置：v0.1–v0.4 验收通过 目标：可解释的渐进升级
核心决策 v0.5 不追求一次性准确判断“任务难度”，而是实现“保守初始路由、有限升级、不能静默降级、每次决策可解释”的运行时策略。模型选择不能替代权限、审批、检查和恢复机制。

1. 版本边界

纳入
任务预检、结构化 TaskProfile、确定性路由策略、角色模型解析、执行中升级、成本与延迟预算、路由审计和评估数据。
不纳入
通用 AGI 式难度判断、每个 token 动态换模型、自动生成新的 Workflow 类型、Brain 使用独立 LLM、未经审批的高风险副作用。
前置依赖
ContextPlan 能稳定提供不同模型所需的上下文；San Loop 和 Workflow 的终态、预算、权限、恢复、交付契约已经可验证；Brain 默认保持低权限和可审查。

2. 为什么不能只做一个 easy / hard 分类器

任务复杂度不是单一维度。一个“读取文件”的请求可能因为包含密钥或生产配置而具有高风险；一个架构设计请求可能不修改任何文件，却要求高强度推理和证据组织。路由需要关注最低安全配置，而不是抽象的智力评分。

维度含义可观察信号
认知复杂度需要多少推理、权衡和跨文件理解设计、审计、故障归因、需求歧义
上下文负载需要多大的项目工作集文件数量、依赖范围、历史和工具尾部
操作风险错误的实际影响只读、修改、删除、发布、外部系统
可逆性失败后能否安全恢复补丁、提交、迁移、不可逆命令
不确定性任务是否可能在执行中改变形态用户描述不清、失败重试、范围扩大
证据要求完成结论需要什么证明无证明、测试、审查、审批、交付确认

3. 目标运行时架构

用户任务
  │
  ├─ Preflight：任务文本 + 最小仓库/会话状态 + 权限与预算
  │
  ├─ TaskProfile：意图、风险、范围、可逆性、不确定性、证据要求
  │
  ├─ RoutePolicy：计算最低模型、effort、工具能力、模式和预算
  │
  ├─ Execution：solo / team / council 或 Workflow 执行
  │       │
  │       └─ 观察证据：测试失败、范围扩大、超时、重复修复、证据不足
  │
  ├─ Escalation：只允许向更高能力或更高约束升级
  │
  └─ Result：结果、证据、实际模型、成本、升级原因和交付状态

模型路由属于控制平面，具体 Agent、San Loop 和 Workflow 属于执行平面。控制平面只决定最低安全配置，不直接绕过执行平面的权限和终态规则。

4. TaskProfile 契约

第一版不要求分类器完全理解任务，只要求输出可校验、可持久化、可回放的结构化结果。未知值必须显式表示为 unknown，不能被静默当作低风险。

{
  "intent": "chat | read | search | edit | test | plan | audit | release",
  "risk": "low | medium | high | unknown",
  "scope": "turn | file | module | repo | external",
  "reversibility": "reversible | recoverable | irreversible | unknown",
  "uncertainty": "low | medium | high | unknown",
  "evidence": "none | tests | review | approval | delivery_ack",
  "toolNeeds": ["read", "search", "edit", "shell", "workflow"],
  "budgetClass": "small | normal | large",
  "signals": ["cross_file_dependency", "write_path", "test_failure"],
  "confidence": 0.0,
  "source": "rule | triage_model | user_override"
}

TaskProfile 是路由输入，不是对用户任务的最终结论。执行中允许追加信号并触发升级，但不得覆盖原始任务和用户明确的约束。

5. 初始路由层级

R0 / DIRECT

无模型或轻量响应

问候、静态帮助、明确的只读信息、确定性格式化。无写权限，无复杂工具链。

R1 / FAST

快速通道

文件搜索、简单读取、单文件解释、低风险查询。使用 smol/fast 角色和小预算。

R2 / CODE

编码通道

普通代码修改、测试修复、局部重构。使用性价比高且具备编码能力的 task/default 角色。

R3 / DEEP

深度推理通道

方案设计、跨模块分析、审计、复杂故障定位。使用 slow/plan/advisor 等强角色，并要求明确证据。

R4 / CONTROLLED

受控执行通道

迁移、删除、发布、外部系统操作。强模型只是必要条件，还必须进入 Workflow、审批和交付确认。

ESCALATE

不确定升级

无法确定风险时提升约束或请求确认，不把未知状态自动降成 R0/R1。

6. 路由策略与升级规则

6.1 先确定安全下限，再选择模型

路由结果至少包含模型角色、effort、工具能力、最大 token、最大 wall-clock、执行模式和是否需要审批。模型解析必须使用精确的 provider/id，不允许持久配置静默模糊匹配。

场景默认路线最低证据不可省略的约束
简单问候R0/R1无不启动复杂上下文或多 Agent
文件查询/读取R1路径和读取结果只读能力；发现跨模块问题再升级
局部编码R2差异 + 定向测试修改范围、工具权限和预算受限
方案/审计R3引用、检查或审查记录ContextPlan；必要时 team/council
生产副作用R4审批 + 结果交付确认Workflow 隔离、可恢复、不可绕过

6.2 只允许有证据的向上升级

  • 测试失败、类型检查失败或 lint 失败；
  • 修改范围超过初始文件/模块边界；
  • 连续重复修复、工具失败或 provider 输出无效；
  • 需要读取新的历史、依赖或跨模块上下文；
  • 任务从只读变成写入，或从可逆变成不可逆；
  • 模型无法满足证据要求，或用户目标仍然存在高不确定性。

同一 turn 内不做无界模型振荡；升级在 turn、phase 或 role 边界发生。除非用户明确覆盖，否则不自动降级到更弱模型。每次升级必须记录触发信号、原路线、新路线和新增预算。

7. 与现有 San 版本的关系

基础版本v0.5 的消费方式前置要求
v0.1 Context Steady为不同路线提供一致的上下文工作集和 token 预算计划、provider wire、压缩、tool loop 的行为一致
v0.2 San Loop根据风险选择 solo/team/council，并绑定 commander/worker/supervisor/oracle终态、取消、检查、预算、恢复可靠
v0.3 Brain只提供低权限、作用域明确的记忆候选和 recall捕获、分类、审查、撤销和作用域隔离可靠
v0.4 Workflow承接 R4 的审批、执行、写入、恢复和交付重放、硬预算、写入隔离和 delivery ack 可靠

v0.5 不应该再创建一套独立的 run、budget 或 capability 状态。它只消费各基础版本已经稳定的契约。

8. 模型角色治理

普通用户只需要选择当前模型；自动路由使用现有角色的正式继承表。角色策略和当前会话模型必须分开，显式 artifact model 仍然可以覆盖默认路由，但最终解析结果必须展示在日志、审批和诊断中。

角色用途v0.5 约束
smol预检、简单查询、digest 等低成本工作不能执行高风险写操作
default/task普通会话和编码执行遵守 task profile 的工具与预算边界
slow/plan复杂计划、深度分析和审计要求更完整的上下文和证据输出
advisor监督、复核和风险判断输出建议或检查结论，不直接获得额外写权限
oracle高风险场景的独立意见保持 advisory；不能单独改变终态

9. 实施阶段

P0 / CONTRACT
冻结 TaskProfile、RouteDecision 和 EscalationEvent

建立 fixture、版本字段、未知值语义、审计字段和与 0.1–0.4 的兼容边界。此阶段不改变默认运行行为。

P1 / RULES
确定性规则路由

先覆盖明显的 chat/read/search/edit/plan/audit/release，使用现有模型角色和 effort 解析。规则必须能在没有 LLM 的情况下运行。

P2 / ESCALATION
基于证据的向上升级

把测试失败、范围扩大、工具失败、上下文不足、预算压力和副作用变化接入统一升级器；先不做自动降级。

P3 / EXPERIENCE
展示和诊断

在状态、日志和审批界面显示初始路线、最终模型、effort、预算、升级原因和证据缺口。普通用户不需要管理角色图。

P4 / DOGFOOD
受控自动化

使用固定任务集比较人工路由、确定性路由和自动升级，记录质量、成本、延迟、错误率和过度升级率。只有数据稳定后才考虑默认开启。

10. 验收门禁

SAFETY

不能错误放权

R0/R1 不能获得高风险工具；R4 不能绕过 Workflow、审批和交付确认。

QUALITY

不能静默降级

不确定、失败或证据不足时，必须升级、暂停或明确报告不足。

ECONOMICS

成本可解释

记录预算、实际 usage、升级次数、耗时和 fallback；不能只统计内部估算。

REPLAY

决策可回放

相同 TaskProfile、策略版本和输入条件应得到可解释且可比较的路由结果。

REGRESSION

不破坏基础版本

0.5 开关关闭时，0.1–0.4 的既有行为和验收路径保持不变。

EVIDENCE

基准而非印象

至少使用固定任务集、多轮重复和真实 provider 记录，不能用单次 dogfood 宣布成功。

11. 主要风险与暂定决策

风险暂定决策
分类器误判简单任务规则优先；不确定时保守升级，不让轻量模型获得超出能力的权限。
分类器误判复杂任务用执行中证据升级；测试失败和范围扩大必须成为硬触发器。
模型在不同 provider 上能力不一致按 capability 和 effort 解析，不按模型名称或价格推断能力。
频繁切换造成延迟和上下文损耗只在 phase/role 边界切换，并保留统一 ContextPlan 和路由事件。
自动路由掩盖用户意图保留 user override；显式模型、模式和 Workflow 设置优先于自动策略。
过早默认开启先运行 review-only/diagnostic-only，经过固定 benchmark 后再开放默认自动升级。

12. 结论

San v0.5 的核心不是“再加一个聪明的 Agent”，而是建立一个可控制的路由器：它知道自己的判断可能不可靠，能从低成本配置开始，能根据证据升级，能把预算和权限一起升级，并且能解释最终为什么使用了某个模型。

这份规划在 0.1–0.4 稳定前只作为研究和验收储备，不改变当前版本实现边界。近期工程重点仍然是 Context Steady 的真实验收和基础运行时契约收敛。
