1. 统计口径

  • 设置:settings-schema.ts 共 503 个叶子键;其中 303 个带 ui 元数据,283 个实际接入设置面板(settings-defs.ts 的 getAllSettingDefs())。裁决作用于设置面板层——不在面板中的键本轮不受 audience 标记影响(见 §5)。
  • 命令:builtin-registry.ts 顶层注册条目 73 个(含 3 个动态生成的 San loop 快捷命令)。仓库中约 210 处 name: 字段的其余部分是各命令的子命令(如 /workflow approve),子命令跟随父命令的 audience,不单独裁决。
  • 缺省语义:未标记 audience 的定义一律视为 daily,存量行为完全不变;标记只影响 UI 可见性,不影响加载、校验与程序化读写。

2. 三问裁决标准(规划文档 §3.2)

  • Q1:新用户第一周会需要动它吗?
  • Q2:不理解内部实现的人能安全地改它吗?
  • Q3:默认值是否已经对绝大多数人足够好?

任一问指向“专家调参”即标 audience: "expert";“到达目的地的前提”(凭据、模型选择、主题、无障碍)无条件留 daily。

8. 需要仓库所有者拍板的边界项

  • memory tab 整体进入 expert(含主开关 memory.backend):理由是整个记忆子系统默认 off 且依赖外部服务。副作用:memory tab 默认只剩 “Show expert settings” 一行。若希望记忆功能对新用户可发现,建议把 memory.backend 单独提回 daily。
  • tools.approvalMode 留在 daily:它改变安全边界,但首周必然遭遇审批弹窗,裁决认为“可发现”优先。若认为误改风险过高可降 expert(审批弹窗本身仍提供改动入口)。
  • /share 与 /export 留在 daily:share 涉及数据外发(加密链接)。若倾向保守可把 /share 降 expert,保留 /export。
  • /compact 留 daily、/shake//handoff 标 expert:上下文手术三兄弟按频率拆分,是否合适请复核。
  • San loop 入口全部 expert(/solo、/team、/council、/san-loop):若 San loop 是希望推广的旗舰工作流,可考虑把 /san-loop 提回 daily 作为唯一入口。
  • §5 的 20 个未接线键:第二轮处置方向(接线面板 vs 降常量)需要决策。

9. 机制与验证摘要

  • 设置面板:含 expert 项的 tab 底部出现 “Show expert settings” 切换行(会话内生效);全局设置搜索始终跨 daily+expert 两层——输入查询视为明确意图;从搜索跳转到 expert 项会自动展开 expert 层。
  • 命令补全:expert 命令派生 unlisted 标志——空前缀浏览列表不显示,名称/别名前缀匹配即显示,描述与模糊子序列匹配不会暴露 unlisted 命令;全名调用不受任何影响。
  • 兼容性:audience 只影响 UI;配置文件包含任意未知键时加载不失败的契约有专门测试防守。
  • 契约测试:test/modes/components/settings-audience.test.ts(默认过滤/切换包含/缺省 daily/前提项守卫)、test/slash-commands/audience.test.ts(expert 命令全名可执行、补全过滤)、packages/tui/test/autocomplete.test.ts(unlisted 契约)、test/settings-manager.test.ts(未知键容忍)。
