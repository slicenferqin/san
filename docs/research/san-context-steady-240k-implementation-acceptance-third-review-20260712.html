2. Findings

P0 · Tool loop 可以绕过 320K hard ceiling

Quality Gate 只在用户请求开始时运行一次，后续 tool result 直接沿用旧 plan。

agent-session.ts:8034-8044 只在 #buildContextSteadyRequestPlan 中计算 hard pressure；agent-session.ts:7213-7218 在每次 provider transform 时仅重新 materialize，不会针对新 live tail 重新估算或 gate。

real AgentSession tool-loop probe
first call                       = small prompt
tool result                      = 1,960,000 chars
second provider call             = executed
second wire-message estimate     = 490,120 tokens
configured burst ceiling         = 320,000 tokens
surfaced error                   = none

单次大型工具输出足以让第二次 provider 请求超过硬上限约 170K tokens。该路径既不暂停，也不 rebase、compact 或 promote。

P0 · Checkpoint 跨分支读取会恢复已丢弃分支内容

生产调用把整个 session tree 交给 checkpoint builder，而不是当前 branch。

agent-session.ts:4423 使用 sessionManager.getEntries()；checkpoint.ts:224-259 随后从所有 digest 和全局 latest checkpoint 合并 summary。用户 rewind/branch 后，非活动分支的 digest 会被写进当前分支的新 checkpoint，并在下一轮注入 provider。

branch-isolation probe
discarded branch intent = OFF_BRANCH_SECRET_REQUIREMENT
active branch intent    = active branch request
new checkpoint intents  = [OFF_BRANCH_SECRET_REQUIREMENT, active branch request]
off-branch content seen = true

这是分支隔离和隐私边界问题，不只是摘要相关性问题。SanLoop 的 latest plan refs 同样从 getEntries() 收集，扩大了该污染的传播面。

P0 · Fallback 经过 checkpoint 后重新获得删除原文权限

Planner 的直接 fallback 保护没有延伸到 checkpoint synthesis。

planner.ts:135-150 正确让 fallback=true digest 的 coveredEntryRefs 为空；但 checkpoint.ts:224-245 会无差别折叠所有 digest，并把其完整 source span 写入 coveredSourceEntryRefs。最新 checkpoint 随后通过 source-index.ts:162-168 恢复覆盖权。

two fallback turns + checkpoint probe
checkpoint coverage = [u1, a1, u2, a2]
raw turn 1 retained = false
raw turn 2 retained = false

默认每 8 轮生成 checkpoint，因此现有“fallback 原文保留”集成测试只验证了短期窗口，达到 checkpoint 阈值后合同再次失效。

P1 · Hard pressure 拒绝请求时既不持久化 audit，也不保留当前 prompt

异常在 append plan audit 和 agent prompt 之前抛出。

agent-session.ts:8041-8049 在 hard_pressure 时直接 throw；audit append 位于 throw 之后，用户消息则要到 #promptAgentWithIdleRetry 才会进入 journal。

real hard-pressure probe
provider calls             = 0
persisted plan audits      = 0
current prompt persisted   = false
visible result             = generic thrown error

首请求不再超限发送是正确修复，但失败路径不可审计、不可 resume，也没有执行方案要求的 safe rebase、compaction 或 model promotion。

P1 · Pre-prompt compaction 与 idle status 不消费 ContextPlan

Plan 建立得太晚，并在 prompt 返回后立即丢弃。

agent-session.ts:8648-8653 先运行 pre-prompt compaction，再创建 request plan；此时 agent-session.ts:11118-11125 只能估算完整 active history。agent-session.ts:8679-8681 又在 turn 结束时清空 plan，idle 状态栏重新回到 full-history 估算。

因此 provider send、status 和 compaction 并没有稳定消费同一 snapshot：长 journal 会在 projection 有机会生效之前触发传统 compaction，turn 结束后的状态也无法复现刚发送的 plan。

P1 · Topic shift 与语义 protected materials 仍未接入生产

生产 required set 只有当前 pending refs 和最近 3 个 turn bundle。

agent-session.ts:8025-8032 没有识别验收条件、未解决错误、当前文件或长期规格；planner.ts:109-156 总是选择最新 checkpoint 和 digest，未调用已有的 relevance/topic-shift 逻辑。

topic-shift probe

rebase reason        = none

单元测试可以手工传 baseRequiredEntryRefs，但生产没有对应的语义提取器。超过 3 轮的规格、错误和验收证据仍可被 checkpoint/digest 替代。

P1 · ContextPlan maxTokens 不是硬上限

Budget 只约束 material estimates，没有约束最终 rendered wire message。

planner.ts:242-247 按 material estimate 消耗预算，随后 planner.ts:268-285 渲染静态模板和标签，但不重新裁剪或拒绝超限结果。

plan cap probe

第二轮的“本地 0 / wire 90”估算漂移已经修好，但 cap enforcement 仍没有成立。另有配置语义冲突：schema 声明 qualityWindowTokens=0 表示无 cap，budget 实现却把 0 解释成 240K。

P1 · 持久化 audit 引用不存在的 pending entry IDs

当前 prompt 的 protected ref 在发送前临时生成，实际 journal 使用另一组 ID。

agent-session.ts:8083-8092 创建 pending_${generation}_${index}；plan audit 随后在真实 user entry 生成前持久化。独立 AgentSession 探针得到：

/context plan 虽能显示这些 refs，但无法沿 journal 追溯到实际 prompt，破坏了“audit 只存引用但可复核”的设计前提。

5. 下一轮硬门槛

  1. 在每次 provider call 前基于最终 transformed + materialized payload 重新 gate，至少把新增 tool call/result 作为原子 live tail 纳入 320K 门禁。
  2. Checkpoint 只消费当前 branch；分支、rewind、resume 加独立合同测试，禁止 discarded branch summary 或 refs 回流。
  3. Fallback digest 永远不能通过 checkpoint 间接获得 raw coverage；checkpoint 只能覆盖具备替代权限的 digest source。
  4. Hard pressure 先持久化可审计失败状态和当前 prompt，再执行 safe rebase、compaction/promotion 或显式暂停。
  5. 在 pre-prompt maintenance 之前建立 request snapshot，并让 provider、status、compaction 在 turn 生命周期内引用同一 plan ID。
  6. 实现 semantic required set 与 topic-shift/resume/budget rebase；最近 3 轮不能替代验收标准、未解决错误和当前文件证据。
  7. 对最终 rendered plan enforce maxTokens；统一 qualityWindowTokens=0 的 schema、兼容和运行时语义。
  8. 让 audit refs 指向真实 journal entries，修复推荐 overlay 测试，并新增上述三项 P0 的合同级回归测试。
  9. 将 dogfood 改为真实 AgentSession 20-turn、多 provider step、tool loop、status/compaction/resume 联合探针，再进入产品 A/B。

最终结论：第三轮仍不通过

当前版本已经不再是“可运行原型刚接线”的状态：首请求完整输入 preflight、hard-pressure 拒绝、coverage fail-closed、低权限 material、secret placeholder 和 provider-session checkpoint reset 都是真实进展。

但 240K ContextPlan 的核心合同必须覆盖整个 provider request 生命周期，而不是只覆盖首个 call。现有实现能在 tool loop 中发送约 490K tokens，会把 discarded branch 内容折入当前 checkpoint，并在 checkpoint 后删除 fallback turn 原文；完整测试套件也仍失败。因此代码级结论为 NO-GO，不可合入，不可宣称 R0-R6 完成，也不应进入产品级 dogfood。
