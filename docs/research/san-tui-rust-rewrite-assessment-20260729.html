San TUI 直接 Rust 重写评估

结论：技术上可行，当前不值得直接重写。 若保持现有能力与扩展兼容，真实工作不是“替换 renderer”，而是重写完整交互前端；预计 24–38 engineer-months，由 3–4 名熟悉 Rust、终端协议和现有 San 语义的工程师投入 8–12 个月。

仅为性能而改写不成立：本机现有热路径微基准大多处于亚毫秒级，文本宽度、ANSI 切片、按键解析、模糊匹配、SIXEL 等关键原语已经由 Rust N-API 承担。Rust 的主要潜在收益是长期状态建模、单一原生 UI 所有权和 Ratatui 生态，而不是当下可证明的用户延迟下降。

评估日期 2026-07-29 范围 packages/tui + interactive frontend 本机 Apple M5 / Darwin 不含 agent/provider/tool runtime 全量改写

1. 判断摘要

观测 84,624 行

当前 TUI 库与核心 interactive UI 生产代码规模；尚未计入散落在 tools、edit、task、extensions 中的专用 renderer。

观测 199 个测试文件

位于 TUI 测试目录或直接导入 @san/tui 的测试；合计 66,869 行，反映兼容面而非可机械换算的工作量。

推算 24–38 人月

保持 inline scrollback、图片、IME、工具流式渲染、扩展 UI、跨平台和测试合同的完整前端切换。

最关键的边界：San 的 agent/session/tool lifecycle 仍在 TypeScript/Bun；而 UI 不只是画字符串。 EventController 把流式消息、工具调用、重试、压缩、队列、子会话和 terminal 状态直接投影为可变 Component 树。 因此“Rust renderer + TypeScript UI”只会制造高频 FFI；要获得 Rust 的主要收益，Rust 必须拥有组件状态、布局、输入和终端写入。

耦合最深的合同

事件与组件是同一状态机

  • EventController 订阅 AgentSessionEvent，直接创建、更新、排序和销毁 transcript children。
  • 流式 turn 可产生数百个 message_update；工具还有 start/update/end 与 partial JSON reveal。
  • scrollback committed rows、stable prefix、live region seam 由组件逐层上报，不能只替换最终 ANSI emitter。

扩展 API 返回可执行 TypeScript 对象

  • 自定义工具的 renderCall/renderResult 返回 Component。
  • setEditorComponent 可注入自定义 editor factory。
  • 主题包含字符串 style callback，而不是纯数据 token。
  • 这些对象不能跨进程或 N-API 直接序列化；必须改 API、引入 declarative view AST，或降级为通用文本。

3. 性能基线：现有 renderer 不是已证实瓶颈

2026-07-29 在当前 Apple M5 工作区各运行一次现有基准。数据是方向性 micro-benchmark，不是 p95、不含真实 PTY/terminal flush，也不代表其他平台。

场景观测结果解释
Editor 无变更 render0.0205 ms/render 远低于 30fps 的约 33 ms 帧预算。
Editor edit + render0.0566 ms/op 即使 Rust 快数倍，单次输入可节省的绝对时间仍很小。
流式 Markdown，2k–6k 字符0.2335–0.4050 ms/step 首个 1k 样本为 3.2289 ms/step 的冷启动异常值；本次单跑不足以归因。
50/100/200 block transcript frame0.0154–0.0795 ms/frame 缓存命中后非单调；只证明该 synthetic hot path 很小，不证明长会话整体无问题。
ANSI wrap0.002326 ms/op 已经调用 Rust native implementation。
ANSI truncate/slice约 0.00033 ms/op 已经调用 Rust native implementation。
按键 match0.000560 ms/组 核心解析与匹配已经在 Rust native 中。 
结论边界：
已观测：synthetic render CPU 很低；若只移植这些路径，绝对收益有限。
未观测：真实终端写入、GC pause、低端机器、ConPTY、tmux、超长会话的端到端 p95。
因此不能声称 Rust “没有性能收益”，但当前也没有证据支持用完整重写购买该收益。

为什么理论加速不等于用户加速

  • 现有 TUI 已有 30fps 节流、backpressure、component-scoped repaint、stable prefix 与缓存。
  • Unicode width、ANSI wrap/slice/truncate、key parsing/matching、fuzzy matching、SIXEL 已经进入 @san/natives。
  • Bun、agent session、provider streaming、tool execution 和大部分消息对象仍会存在；重写 UI 不会移除主运行时。
  • 若采用 Rust sidecar，还会复制会话投影并增加 IPC/进程常驻内存；总 RSS 不保证下降。

4. 四种“Rust 重写”不是同一个项目

方案边界成本推算收益判断
A. Rust terminal kernel TS 仍生成完整 frame；一次批量 N-API 调用交给 Rust 做 diff、cursor、terminal write。 2–4 人月 可能减少 emitter CPU/主线程写入；不减少 TS component/render allocation。 只适合有数据后的定点优化
B. Rust widgets + TS controllers TS 发送 declarative view tree，Rust 做组件、布局、render；业务状态仍在 TS。 10–18 人月 布局和绘制原生化；但形成双状态、view AST 与复杂回调桥。 最差长期边界
C. Rust 完整 interactive frontend Rust 拥有输入、UI 状态、组件、layout、terminal；TS 只发送 session events、接收 user intents。 24–38 人月；3–4 人，8–12 个月 真正获得单一所有权、低 GC 敏感度、Rust 状态机与 Ratatui 生态。 唯一合理的完整目标，但当前 ROI 不足
D. 全 CLI/agent Rust 连 agent、provider、tools、extensions、RPC/ACP、配置与会话一起迁移。 本报告不估算；远大于 C 可真正移除 Bun，但会变成多包产品重建。 另立战略项目，不应伪装成 TUI 重写
不要采用每个 Component/每行跨 N-API 的混合模式。 它同时保留 JS allocation、Rust allocation、字符串复制和跨边界调度，复杂度上升而收益最小。 A 至少必须是“一帧一次调用”；C 则必须是“一批事件一次调用，Rust 独立完成绘制”。

5. 完整前端改写的成本构成

推算 假设功能对等、无长期双栈、由熟悉现有系统的工程师执行，范围已含合理联调与回归缓冲。

工作流人月必须交付主要风险
Rust TUI core6–9 inline viewport、diff、cursor、scheduler、capability、native scrollback、resize、panic/exit restore、图片协议。 Ratatui inline 能力不是 San exact-final scrollback 合同的现成等价物。
产品 UI 与输入8–13 editor、Markdown、transcript、tool blocks、status、所有 overlay/selector/wizard、mouse/IME/keymap。 大量行为藏在组件 mutation、focus、timer 与流式中间态。
TS↔Rust 协议与扩展4–7 版本化事件协议、backpressure、command response、approval/dialog、extension renderer 新合同。 序列化顺序、取消、重连和扩展 API 兼容；双状态最容易分叉。
平台与切换5–8 PTY oracle、macOS/Linux/Windows、tmux/screen、Ghostty/Kitty/iTerm/WezTerm/VS Code、打包、崩溃恢复、旧实现删除。 终端 bug 多为 host/protocol 组合问题，语言迁移不会自动消失。
整体预测24–38 工作流有并行与重叠，整体预测不是机械相加；日历期还受关键路径与 parity burn-down 限制。

机会成本

推算 3–4 名核心工程师投入 8–12 个月，意味着 Action Palette、Queue Center、Conversation Navigator、Terminal Doctor 等直接用户结果至少延后两个到三个季度。重写期间还要维护旧 TUI，直到新实现通过 parity gate；这段时间开发速度通常下降而不是上升。

7. Ratatui 能解决什么，不能解决什么

现成能力

  • 双 buffer 与 cell-level diff。
  • Crossterm backend、跨平台输入、raw mode、alternate screen。
  • Viewport::Inline 与 Terminal::insert_before。
  • TestBackend 的 screen/cursor/scrollback 检查。
  • 成熟 layout/widget 生态。

仍需 San 自己实现

  • 已提交 transcript 与 live tail 的 exact-final seam。
  • native scrollback commit/replay、ED3 destructive replay。
  • DEC 2026、terminal capability/reachability 与 host quirks。
  • Kitty/SIXEL 图片生命周期与 scrollback 降级。
  • 流式工具中间态、partial JSON reveal、组件级稳定前缀。
  • 扩展 renderer/editor 的可序列化替代合同。

xAI 的 Grok Build 证明完整 Rust coding-agent TUI 可行，但其官方 manifests 同时显示真实成本：除 Ratatui/Crossterm 外，还有专用 textarea/inline crates、Markdown、syntect、VTE、图片、PTY harness、设置 E2E 与多组 PTY 测试。它的 agent/tool ecosystem 也在 Rust 内，避免了 San 必须处理的 TS↔Rust 产品状态边界。因此 Grok 是可行性证据，不是“换两个 crate 即完成”的成本证据。

8. 如果仍决定做：正确架构

推荐目标只能是 C：Rust-owned interactive frontend。 继续让 TypeScript 负责模型、agent session、tools、配置持久化与扩展执行；Rust 负责 terminal、input、local UI state、layout 和 rendering。 边界必须是粗粒度、版本化、可录制重放的事件协议。

入站事件

session snapshot；agent/turn start/end；message start/delta/end；tool start/update/end；compaction/retry；queue projection；settings/theme/keymap； focused session/subagent；notice/error；approval/dialog request。流式 delta 必须批处理、合并并带顺序号，不能每 token 同步 FFI。

出站意图

submit/steer/follow-up/abort；command/action invoke；queue mutation；approval/dialog response；session focus；setting mutation；copy/open external editor； shutdown。Rust 不直接修改 agent 业务状态，只提交意图并等待权威 projection。

扩展合同

必须以 versioned declarative view AST 替代任意 TS Component callback；首版只允许有限 primitives（text、stack、box、markdown、table、image、status、input）。 若保留 TS renderer 输出字符串作为永久逃生口，Rust 就无法拥有布局、focus、mouse hit testing 与稳定缓存，最终会回到方案 B。

9. 决策门槛与低风险试验

不建议直接立项完整改写。若团队需要消除不确定性，先做可丢弃的 R0，不接入正式发布路径。

R0内容预算通过门槛
录制真实 event tape idle、streaming、200-block transcript、tool partial、overlay、resize、IME。 2 人 × 3 周，约 1.5 人月 TS 与 Rust 可消费同一确定性事件序列。
Rust vertical slice inline transcript + editor + 一个流式 tool block；粗粒度协议；TestBackend + PTY。 native scrollback 顺序、resize、cursor、取消均与 oracle 一致。
A/B 性能测量 相同 terminal/PTY 下测 input-to-paint、render CPU、event-loop stall、RSS、terminal bytes。 至少一项已归因核心指标改善 ≥30%，且无 RSS/启动/功能显著退化；否则停止。

30% 是立项门槛建议，不是当前性能事实；完整重写需要足够大的确定性收益，不能以微小 benchmark 优势覆盖迁移风险。

10. 最终建议

现在：不直接 Rust 重写。

  1. 继续现有交互路线：Action Palette、Queue Center、Conversation Navigator、Terminal Doctor；这些直接解决已识别的用户问题。
  2. 补齐 live PTY 性能观测，按 idle/streaming/large transcript/overlay/resize 分解 render、schedule、terminal write 与 GC。
  3. 发现明确热点后，优先继续扩展现有 @san/natives 的批量原语，而不是迁移整个 UI。
  4. 只有在“未来要建设 Rust-native frontend”成为独立战略目标，或 live 数据证明 JS UI 是主要瓶颈时，才执行 R0。

ROI 判断：以“让当前 San TUI 更好用、更流畅”为目标，Rust 全改写的收益不足以覆盖 24–38 人月和两到三个季度的机会成本； 以“建立可脱离 Bun 的长期原生前端”为目标，它才可能成立，但应被当作新前端产品线，而不是 renderer refactor。
