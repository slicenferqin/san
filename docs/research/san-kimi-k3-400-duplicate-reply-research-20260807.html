方案编号：SAN-KIMI-K3-400-001日期：2026-08-07范围：packages/coding-agent + CPA（腾讯云）

会话重复回复与 Kimi K3 400

两个独立问题：① 单条用户消息触发多条模型回复（会话 019fda1c）；② kimi-k3 经 CPA 调用时偶发 400。本文档给出根因、证据链与修复方案。

1. 问题与结论

结论 1（重复回复）：xd:// 设备挂载通知触发额外模型轮次，属设计行为。会话启动时 codegraph / node_repl / chrome_devtools 先后挂载，每条挂载通知 steer 一条 custom message，空闲 agent 消费后自动 continue，产生 3 个模型请求（2 成功 + 1 报错）。
结论 2（kimi-k3 400）：CPA 把 Responses API 翻译成 chat.completions 时，assistant 消息 content 保持数组格式，kuaileshifu 的 kimi-k3 通道对该格式间歇性拒绝。协议链上 kuaileshifu 不支持 Responses 端点，无法直传；修复需在 CPA 翻译层把纯文本 content 数组压平成字符串。
已知但暂不处理：kimi-k3 的 thinking levels 配置（low/medium/high/xhigh/max）与上游（仅 low/high/max）不符，选 medium/xhigh 会确定性 400。用户只用 max，暂不改。

目标

  • 消除 kimi-k3 经 CPA 调用的间歇性 400，兼容所有走 CPA 的 provider。
  • 不改动 kuaileshifu 服务端，不改动 CPA thinking levels 配置。
  • 文档化重复回复机制，评估是否需要在 san 侧抑制。

非目标

  • 不修改 kuaileshifu 侧的任何东西（对方不支持 /v1/responses，已实测）。
  • 不改 kimi-k3 思考档位（用户只使用 max）。
  • 不改变 Responses → chat.completions 的协议链路，只改 content 的编码形式。

2. 问题一：单条消息为什么回复多次

2.1 现象

会话 ~/.san/agent/sessions/-development-self-projects-xiaosongguo/2026-08-07T02-44-56-235Z_019fda1c-012b-7000-8517-2a02f19b7855.jsonl，用户 02:45:16 发一条"你好"，02:45:33 和 02:45:40 各收到一条回复，02:45:43 再报一次 400 错误。日志（journal + context-probe）显示实际发出 3 个模型请求。

2.2 触发链

时间事件模型请求
02:45:16user "你好"—
—codegraph 设备挂载 → steer xdev-mount-notice请求 1（含 codegraph notice）
02:45:33回复 1 "你好。有什么需要做的，直接说。"stop
—node_repl 设备挂载 → steer xdev-mount-notice请求 2（含 node_repl notice）
02:45:40回复 2 "你好。有什么需要处理的？"stop
—chrome_devtools 设备挂载 → steer xdev-mount-notice请求 3（含 chrome notice）
02:45:43报错 400error

2.3 机制（代码路径）

packages/coding-agent/src/session/agent-session.ts 中，每次 xd:// 设备挂载触发 #notifyXdevMountDelta() → agent.steer({ role: "custom", customType: "xdev-mount-notice", ... })。steered custom message 进入 steering 队列，经 convertToLlm 转成 user turn；队列非空时 #canAutoContinueForFollowUp() 返回 true，空闲 agent 自动 continue() 发起新模型请求。挂载通知本身 display:false，UI 不可见，但 agent 仍会消费并触发新轮次。

2.4 评估

属设计行为而非去重缺失。会话启动期多个 xd:// 设备异步挂载是常见场景，每条挂载通知都会唤醒 agent。若要在 san 侧抑制，可在挂载通知密集到达（启动窗口）时合并/延迟 steer，或让 xdev-mount-notice 不触发 auto-continue。当前不作为修复项，仅文档化。

3. 问题二：kimi-k3 400

3.1 现象

本会话第三个请求（即问题一的请求 3）报 400 Assistant messages must contain text, reasoning content, or tool_calls.。会话 400 请求体在 ~/.san/logs/http-400-requests/1786070742974-2vi5gwkxv1b8h.json。

3.2 协议链

san
Responses
/v1/responses
CPA
翻译
content 数组
kuaileshifu
chat.completions
/v1/chat/completions
  • san → CPA：OpenAI Responses 协议（openai-responses-server.ts），assistant 消息 content 天然为 parts 数组（[{type:"output_text",text:...}]）。
  • CPA → kuaileshifu：chat.completions（错误日志 upstream URL 证实）。

3.3 根因

CPA 翻译器 CLIProxyAPI-cpa-build/internal/translator/openai/openai/responses/openai_openai-responses_request.go（函数 ConvertOpenAIResponsesRequestToOpenAIChatCompletions，158–186 行）把 Responses 的 content parts 原样复制为 "content":[{"type":"text","text":"..."}] 数组。kuaileshifu 的 kimi-k3 通道对 assistant content 数组格式间歇性拒绝；纯字符串 content 则 100% 通过。

3.4 证据

测试结果
同一失败 body 反复重放时 200 时 400（多通道负载均衡不一致）
assistant content 数组 + reasoning_content高概率 400（约 50–80%）
assistant content 纯字符串 + reasoning_content100% 200
同数组格式换 deepseek-v4-flash / grok-4.5100% 200（kimi-k3 特有）
reasoning_effort: medium / xhigh确定性 400 "reasoning_effort must be low, high, or max"
reasoning_effort: low / high / max200
kuaileshifu /v1/responses 端点（含最简请求）500 not implemented（不支持 Responses）

官方 Kimi 文档确认 K3 的 reasoning_effort 仅支持 low/high/max（默认 max）：kimi-k3-quickstart。

3.5 为什么不能走 Responses 直传

实测对 https://newapi.kuaileshifu.com/v1/responses 发任何请求（含 {"model":"kimi-k3","input":"hi"}）均返回 500 convert_request_failed: not implemented——new-api 在请求转换阶段直接拒绝，未实现 Responses 通道类型，与模型无关。因此协议链路只能保持 san→CPA(Responses)→chat.completions。

4. 修复方案

方案：在 CPA 翻译层把纯文本 content 数组压平成字符串；含图片时保留数组。改动约 10 行，位于 openai_openai-responses_request.go 的 message content 翻译分支。
// 现状（158–186 行）：
//   content 为数组时，逐 part 转成 {"type":"text","text":...} 后 SetRawArrayItems 保留数组
// 改为：
//   收集 text parts；若全部是文本（无图片 part），
//   则 message = sjson.SetBytes(message, "content", 拼接后的字符串)
//   否则保留原数组逻辑（图片必须数组形式）

影响面

  • 只影响 assistant/非 assistant 消息中纯文本 content 的编码形式（数组 → 字符串）。
  • 字符串是 chat.completions 最通用的 content 形式，deepseek / grok / kimi 全部兼容（实测字符串对 kimi 100% 通过）。
  • 含图片消息保持数组，不受影响。
  • reasoning_content 独立字段，不参与压平，行为不变。

实施步骤

  1. 改 CLIProxyAPI-cpa-build/internal/translator/openai/openai/responses/openai_openai-responses_request.go 的 content 翻译分支。
  2. 在 test/thinking_conversion_test.go 同级补单测：纯文本数组 → 字符串；含图片数组 → 保留数组。
  3. 重建 Docker 镜像 local/cli-proxy-api:cpa-model-events 并部署（腾讯云 /root/apps/cpa-stack，docker compose up -d）。
  4. 回归验证：kimi-k3 会话连续多轮无 400；deepseek / grok 正常。
风险：改动影响所有走 CPA 的 provider，需在部署后做多 provider 冒烟；若 kuaileshifu 某些通道仍拒绝字符串（已实测不会），可回退。
