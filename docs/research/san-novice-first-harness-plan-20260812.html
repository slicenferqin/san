面向普通用户的 Harness 收敛规划
配置减法 · 证据链 Skill · 契约回显

快照日期：2026-08-12 基线：main @ 2177ad6502（PR #13 已合并） 范围：packages/coding-agent 性质：规划 + 技术实现方案

0为什么做这件事

San 的战略判断（见 2026-08-11 上游方向分析、2026-08-07 项目简报）已经收敛为一句话：San 是那个"敢挂一晚上"的 coding agent——上游 OMP 补横向平台能力，San 押注宿主持有的可验证执行。本文档解决这个定位下的下一个矛盾：

  • 能力是专家向的，目标用户是普通人。普通用户的输入是"帮我改下这个 bug"这种模糊需求；San 现有的 logical model routing、harness profiles、execution contract 对他们全是噪音。作者本人已表示"自己都玩不明白"——配置面超过了任何单人的认知预算。
  • Skill 是软引导，防不住模型偷懒。SKILL.md 是静态文本，模型可以读完就跳过复现直接改代码，长会话里更会走着走着忘掉。行业普遍停在这一层。
  • San 独有的硬约束（evidence gates）没有和 skill 打通。AcceptanceGate 目前只能由 San Loop 调用方手工编写传入，没有从技能声明或用户意图自动生成的路径。资产闲置。
北极星指标：无人值守执行长任务，在预算内到达可解释终态的成功率。三个信任维度——下限可预测、失败可解释可恢复、成本有硬顶。本规划的三个里程碑全部服务于该指标，且全部押在"模型变强也不贬值"的一侧（验证、预算、恢复、默认值），不押在"补模型短板"的一侧。

一句话规划：M1 做配置减法（纯删，最快见效）→ M2 把高频模糊需求写成证据链 Skill（软引导提质量）→ M3 用 skill 声明编译出 evidence gate 并加契约回显（硬约束保下限）。三个里程碑各自独立可交付、可单独发布。

1.1 配置面

  • Schema：config/settings-schema.ts（约 1,300 键）+ config/settings.ts（2,200 行装载逻辑）。
  • UI：modes/components/settings-defs.ts 已有 SettingTab 分组与 getSettingsForTab()，具备分层呈现的现成挂点。
  • 问题不是缺组织，是缺裁决：没有任何机制区分"日常必要"与"专家调参"，所有键地位平等地暴露给用户。

1.2 Skill 机制

  • 发现与加载：extensibility/skills.ts + discovery/helpers.ts（scanSkillsFromDir），支持 user / project / managed（autolearn 自动生成）三级来源，authored 优先于 managed。
  • 触发：system prompt <skills> 列表（description 命中）、skill://<name> 协议、/skill:<name> 命令；注入模板 prompts/skills/autoload.md。
  • 缺口：frontmatter 只有 name / description / hide 等描述性字段，没有任何可被 harness 消费的结构化语义——skill 说"先复现"，宿主既不知道、也无法检查。

1.3 Evidence gates 与契约

  • 类型完备（execution-control/types.ts）：AcceptanceGate（gateId / contractRef / objectiveClauseRefs / verifier / status / evidenceRefs / required）；回执 EvidenceReceipt 为 host-sourced，绑定 scopeId / contractRevision / contractHash / freshnessRevision / assignmentId，文本声称一律不算数。
  • 校验为纯函数：execution-control/evidence-gates.ts 的 verifyEvidenceGates()，可在任意层复用。
  • San Loop（san-loop/runner.ts 963 行起）接受 acceptanceGates 选项并物化模板、按回执更新终态；san-loop/dogfood.ts 有手写 gate 样例。
  • TaskContractRegistry（execution-control/task-contract.ts）已做确定性身份派生与重复派发拒绝。
  • 缺口一：gate 的生产端只有"调用方手写"一种；缺口二：objective contract 是纯内部机制，用户从头到尾看不见它。

2总体规划

里程碑交付物预估独立价值
M1 配置减法 配置清单审计脚本 + audience 分层标记 + 设置 UI 默认只显日常层 + slash command 同规则收敛 1–1.5 周 新用户十分钟可上手；作者自己重新"玩得明白"
M2 证据链 Skill SKILL.md frontmatter 的 evidence 扩展（纯声明、向后兼容）+ 两条内置 skill：fix-bug、build-web + 写作规范 1–2 周 模糊需求命中后有专家级证据链引导，即使不启用 M3 也提升质量
M3 硬约束 + 契约回显 skill evidence 声明 → AcceptanceGate 编译器 + 会话级 gate 检查（软拦截）+ San Loop 终态接线（硬拦截）+ 契约回显 UX 2–3 周 "完成"必须有宿主回执背书；San 独有的 skill×gate 组合成型
边界（明确不做）：不新增任何顶层配置项（M1 是减法，M2/M3 的开关折叠进既有 tools/tasks 组）；不重写 TUI；不强制存量 skill 携带 evidence 声明；不在本轮触碰上游 goal-gates/wayfinding 候选 PR 的合流（保持观察，语义冲突风险见 §6）。

3M1 技术实现：配置减法

3.1 第一步：生成可裁决的清单（脚本，一次性）

新增 packages/coding-agent/scripts/audit-settings.ts：从 settings-schema.ts 的 schema 对象递归提取每个键的路径、类型、默认值、所属 SettingTab、描述，输出为一张 JSON/HTML 清单。同理从 slash-commands/builtin-registry.ts 提取 214 个命令的 name/description/分组。这张表是后续所有裁决的工作底稿——先看清全貌，再动刀。

3.2 裁决标准：每个键过三问

问题答案 → 处置
Q1 删掉它并硬选一个默认值，会伤害谁？没人 → 降为常量（从 schema 移除，保留读取兼容：读到旧键时忽略并告警一次）
Q2 90% 用户在 90% 场景下是否只用同一个值？是 → 标记 audience: "expert"（保留但默认不可见）
Q3 它是不是"到达目的地"的前提？是（如 provider 凭据、model 选择）→ audience: "daily"，且必须有开箱即用默认或首启引导

预期结果量级：daily 层 ≤ 30 键。这不是拍脑袋——参照对象是任何一辆车的仪表盘。

3.3 实施挂点（全部是现成缝隙，无新架构）

// settings-defs.ts —— SettingDef 增加一个字段
interface SettingDef {
  // ...existing: path/label/description/tab/group/condition
  audience?: "daily" | "expert";   // 缺省视为 "daily"，存量行为不变
}

// getSettingsForTab() 增加过滤：默认只返回 daily；
// 设置界面尾部一个入口（或 /settings expert）切换显示 expert 层。
// slash command 同规则：CommandDef.audience，autocomplete 默认只列 daily，
// 完整名称输入时 expert 命令仍可直接执行（不破坏肌肉记忆与脚本）。
  • 降为常量的键：值收进模块内 const，schema 删除；settings.ts 装载时对未知键记 logger.warn 一次并跳过（禁止启动失败）。
  • 迁移安全：读取旧配置文件永不报错；写回时自动剔除已降级键。
  • 验收（DoD）：新装环境不改任何配置完成"修一个真实 bug"的全流程；设置界面首屏一屏放得下；audit 脚本重跑输出 daily 键数 ≤ 30。

4M2 技术实现：证据链 Skill

4.1 设计原则：证据链，不是步骤清单

专家处理"帮我改个 bug"的方式不是追问用户，而是从环境收集证据：先复现拿到失败输出，再定位，修完用同一条复现路径拿到通过输出。每一环的产出是下一环的输入。Skill 正文按这个逻辑写；frontmatter 把"环"声明成宿主可读的结构。

4.2 SKILL.md frontmatter 扩展（纯声明、可选、向后兼容）

# skills/fix-bug/SKILL.md（frontmatter 部分）
name: fix-bug
description: 修复缺陷。用户报告 bug、异常、报错、行为不符合预期时使用。
evidence:
  - id: repro
    phase: before-fix          # 进入修复动作前应当存在
    kind: command              # 复用 EvidenceVerifierKind，六选一
    expect: fail               # 此阶段期望的 outcome：先拿到"失败"的复现
    description: 可复现失败的最小命令及其输出
  - id: verify
    phase: before-done         # 报告完成前必须存在
    kind: command
    expect: pass
    sameAs: repro              # 必须与 repro 是同一条命令，防"换个命令绿了"
    description: 同一复现路径由失败转为通过
  • 解析落点：discovery/helpers.ts 的 scanSkillsFromDir 已解析 frontmatter；在 extensibility/skills.ts 的 Skill 接口上加 evidence?: SkillEvidenceSpec[]，非法声明进入现有 SkillWarning 通道（跳过该段、skill 本体仍可用，不让作者的 YAML 失误炸掉 skill）。
  • 类型放 execution-control/types.ts 旁定义 SkillEvidenceSpec，字段与 AcceptanceVerifier 对齐，M3 编译零转换成本。
  • M2 阶段该声明的唯一消费者是注入模板：prompts/skills/autoload.md 渲染 skill 时追加一段 Handlebars 生成的"证据要求"清单，提示模型按链推进——此时仍是软引导，但已经结构化。

4.3 内置两条高频模糊需求 skill

Skill证据链覆盖的模糊输入
fix-bug复现(fail) → 定位 → 修复 → 同路径复验(pass) → 回归面检查"帮我改下这个 bug / 这里报错了 / 怎么不对了"
build-web需求契约回显 → 骨架可启动(command: dev server 起) → 核心路径可用(browser 断言) → 交付说明"帮我做一个网站 / 做个页面 / 搭个后台"

正文写作规范（一并入库为 docs/skill-authoring.md）：每环写清"此环的产出物是什么、下一环拿它做什么";禁止无证据依赖的仪式性步骤;篇幅上限 150 行,超出拆子文件按需读取。

验收（DoD）：用 10 条真实模糊需求样本（bug 类 6 条、建站类 4 条）做 A/B dogfood，命中 skill 的会话必须在 transcript 中出现"先复现后修复"或"先契约后动工"的行为序列；未命中路径行为与今日一致。

5.2 两级拦截：软在会话，硬在终态

层机制为什么这样分
软拦截（会话内） skill 触发时把编译出的 gate 挂到会话级 registry；工具管线的既有 before-tool-call 钩子检查:处于 before-fix 阶段而 repro 回执缺失时,对 edit/patch 类工具注入一次结构化提醒(不阻断)。同一 gate 只提醒一次,避免唠叨循环。 会话内用户在场，最终裁量权在人；阻断式拦截会把"引导"变成"添堵"，违背 novice-first。
硬拦截（终态） San Loop 已有 gate 物化与终态判定（san-loop/runner.ts、orchestrator.ts）：把编译出的 gate 并入 options.acceptanceGates，required: true 的 gate 无 host 回执则终态不得为 completed——走已有 verifyEvidenceGates()，一行新逻辑都不引入判定层。 无人值守场景没有人兜底，"说完成"必须等于"有回执的完成"。这正是北极星指标的分子定义。

回执生产端：command 类 verifier 的回执由 shell 工具执行路径生成——工具层已经拥有 exitCode 与命令文本,新增一个薄适配把它写成 CommandEvidenceReceipt(绑定当前 scopeId/contractHash/freshnessRevision)。sameAs 校验用命令的规范化指纹(复用 progress-classifier.ts 的 stableValueFingerprint)。browser/api 类回执依赖既有 browser 工具的断言产物,首版仅接 command,其余 kind 声明合法但标注"暂无宿主适配"并按 review 门人工放行。

5.3 契约回显：objective contract 的 UX 化

把内部机制变成用户可见的一句话。触发条件：会话首个用户消息命中证据链 skill（或 San Loop 任务启动）。流程：

  1. agent 完成初步证据收集后,生成一条固定格式的契约消息:"我理解你要:修复 X(复现命令 Y 当前失败)。完成的标准:Y 通过且 Z 不回归。"——模板放 prompts/ 下静态 .md,Handlebars 填充,遵守仓库 prompt 规范。
  2. 用户确认（回车/继续即视为默认确认，不强制打断）；异议则修订。确认后契约文本与其 hash 写入会话 scope，成为 ObjectiveContractRef 的来源——5.1 编译器所需的 contractRef/contractHash 由此而来。
  3. 终态汇报时反引契约:"当初约定 Y 通过——回执 #id,exitCode 0"。失败终态同样对着契约解释卡在哪一环、花了多少。

验收（DoD）：fix-bug 场景端到端 dogfood——模型被诱导跳过复现时软提醒出现且只出现一次；San Loop 下伪造"已完成"文本无法把终态置为 completed；契约回显在 TUI 与 RPC 两条呈现路径一致（注意 AGENTS.md 中流式预览多路径的既有教训）。

6风险与应对

级别风险应对
P0M3 与上游候选方向（goal quality gates #8062、wayfinding）语义重叠，未来合流冲突San 的 gate 编译器与拦截层全部收在 execution-control/ 与钩子缝隙内，不改上游同名结构；持续对照上游 PR，语义趋同处优先对齐命名。该领域本就是 San 的差异化主场，先行落地即是筹码。
P1配置降级破坏存量用户/脚本读旧键永不失败（警告一次并忽略）；expert 命令仍可全名调用；发布说明列出全部降级键与既定常量值。
P1软提醒在某些模型上诱发过度合规（反复复现不动工）提醒是一次性的且措辞为"建议下一步"，不是禁令；dogfood 覆盖 3 个档位模型（旗舰/中档/小模型）。
P2skill frontmatter 扩展与外部生态（Claude/Cursor skills）分叉evidence 是可选段，外部 skill 无该段时行为与今日完全一致；不修改任何既有字段语义。
P2契约回显打断心流默认确认制（不阻塞），仅证据链 skill 命中时出现；expert 可用既有 settings 关闭。

7度量与后续

  • 北极星雏形基准：M3 完成后,把 10 条 dogfood 样本固化为可重跑脚本(复用 context-steady 公开 benchmark 的方法论):指标 = 无人值守终态率、终态可解释率(失败时能否指出卡在哪一环)、预算内完成率。这份数字就是 San 对"什么是好 agent"的可测量回答,也是对外叙事的弹药。
  • 顺序即优先级：M1 不依赖 M2/M3,先发;M2 发布后即可独立观察 skill 命中对行为序列的影响;M3 的软拦截与硬拦截也可分两次发布(先软后硬)。
  • 与既有 P0 的关系：本规划不替代"execution-control 根会话闭环"这一未竟事项——M3 的 San Loop 接线恰好是该闭环的一个具体消费场景,两者互为验证。
