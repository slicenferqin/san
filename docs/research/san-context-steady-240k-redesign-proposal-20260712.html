先保证高质量，
再把上下文稳定在 240K。

这份方案修正了我上一版偏“预算控制”的倾向。240K 不是一把砍内容的刀，而是一块足够宽的高质量工作台。 稳态的目的，是减少噪声、提高注意力和可预测性；当压缩会损害任务完成度时，系统应当暂时扩张，而不是机械服从数字。

01 / 共同原则

“稳定”服务于质量，而不是与质量竞争。

我们真正要控制的是无关噪声、重复 payload 和失控增长，不是为了数字好看而减少模型完成任务所需要的证据。

CONSTRAINT 0

高质量交付优先

当前需求、关键文件、未解决错误、测试证据和最新用户指令不允许被预算策略机械删除。

CONSTRAINT 1

240K 是稳态目标

常态请求尽量落在 200K–260K；上下文稳定后，注意力更集中、缓存更可预测、成本更平滑。

CONSTRAINT 2

必要时允许扩张

大型重构、复杂排障和最终验收可以暂时进入 260K–320K，待安全边界再回到稳态。

核心判断
低质量的 120K 不如高质量的 280K；但经过正确整理的 240K，通常会优于充满重复和旧噪声的 400K。
02 / 基本模型

从“维护一条不断增长的消息链”，改成“每轮生成一个高质量工作投影”。

完整历史仍然存在，但它属于 journal。模型每轮看到的内容由 Context Planner 从 journal 中重新选择，不再先塞满历史、再靠 pruner 猜哪些可以删。

ContextPlan 不是一段小摘要

它是对整个 240K 工作集的选择计划。TurnDigest 可能只有几千 tokens，但它只是一层索引，不能替代任务所需的全部原文和证据。

RULE 01没有明确 replacement coverage，就不能从 provider payload 省略原始 entry。
RULE 02最近精确轮次和当前证据是独立层，不与 recentDigests 混为一谈。
RULE 03动态历史和 recall 是不可信数据，不提升为 developer 权限。
RULE 04同一个 plan 同时驱动发送、token 统计、状态栏和 compaction。
03 / 预算不是配额

240K 是质量工作集目标；不同任务，内部构成应该不同。

下面是策略模拟，不是 benchmark 数据。它表达的是 planner 如何根据任务现场调整材料，而不是给每层锁死一个固定配额。

    04 / 质量闸门

    系统不能仅因为“超过 240K”就开始删内容。

    每次裁剪或 rebase 前，Planner 先证明任务所需信息仍然存在。如果证明失败，默认动作是保留或扩张，而不是压缩。

    01
    识别当前交付阶段
    探索、实现、排障、验收的证据需求不同。
    02
    建立 Required Context Set
    列出当前任务不可缺少的指令、文件、错误、决定和测试。
    03
    验证 replacement coverage
    被省略的原文是否有 checkpoint、digest、stub 或可重读 entryId。
    04
    比较压缩前后风险
    若可能降低完成度，进入 burst；若只是重复噪声，安全回收。
    质量检查通过，才允许 rebase 回到 240K。
    最新用户指令完整保留，不能被旧 digest 或 checkpoint 覆盖。
    当前任务规格验收条件、禁止项、设计决策与输出格式仍可见。
    活跃文件与差异保留当前版本或重新读取，避免依赖陈旧文件副本。
    未解决错误错误信息、失败测试与尝试过的方案不能只剩“失败了”。
    工具调用配对assistant tool call 与 tool result 作为原子 turn bundle 处理。
    开放决定与下一步没有落地的选择仍保留来源和状态，避免重复探索。
    秘密与权限摘要副请求先混淆；历史派生内容保持不可信 data 权限。
    证据可回读长日志可变成短摘，但必须携带稳定 entryId 与重读路径。
    上下文材料常态策略预算压力下绝不能做
    当前用户 prompt完整保留必要时扩大 burst摘要、截断或被旧指令覆盖
    当前活跃文件保留当前版本重新读取相关范围依赖多轮前的陈旧全文
    最近精确轮次目标 5 轮3–8 轮自适应一有 digest 就全部删除
    大型工具输出保留相关片段evidence stub + entryId每轮重复发送完整日志
    旧轮次digest ledgercheckpoint 吸收checkpoint 与旧 delta 双份常驻

    05 / 与你的想法对齐

    我保留架构判断，但调整预算哲学。

    我们在目标上没有冲突。差异主要在于我上一版更强调“有界”，现在把“有界”明确降为质量之后的第二约束，并把 240K 变成宽裕的工作集目标。

    完全一致的部分

    高质量交付是第一目标

    稳态不能以遗漏需求、证据或降低完成度为代价。

    240K 足够宽裕

    不需要把 ContextPacket 压到几千 tokens 后就认为上下文治理完成。

    稳定本身能提高质量

    减少重复和旧噪声后，注意力更集中，模型更容易保持任务主线。

    完整历史应当保留

    省略的是 provider 工作集，不是删除 session journal 中的证据。

    我对上一版的修正

    从硬 cap 改为控制带

    240K 是目标中心；260K–320K 是明确允许的质量弹性区。

    从“先压缩”改为“先证明可压缩”

    Quality Gate 失败时，系统应暂时保留更多材料。

    从固定分层配额改为任务自适应

    实现、排障和验收可以拥有不同的 exact/evidence/recall 比例。

    仍坚持单一 ContextPlan

    预算宽裕不代表可以接受多套裁剪与统计逻辑继续漂移。

    边界共识
    允许上下文暂时变大，但不允许它在没有理由、没有审计、没有回收点的情况下永久变大。
    06 / 破坏性重构边界

    重写上下文投影，不重写整个 San。

    TurnDigest 和 journal 已经有可复用价值。真正需要推倒的是 pruner、packet 累积、预算统计和 provider 注入之间的耦合。

    R0

    合同冻结

    定义 240K、burst、exact turns、quality gate、provider input 计量口径。

    R1

    ContextPlan

    实现 turn index、材料选择、coverage、预算分配和确定性 plan。

    R2

    Provider 投影

    用 materializer 替代 prune；发送、状态栏和 compaction 共用 plan。

    R3

    Epoch / Rebase

    epoch 内 append-only；在安全边界低频 rebase，退休旧 delta。

    R4

    安全与兼容

    secret pipeline、消息权限、Brain/San Loop/report v1-v2 adapter。

    R5

    真实验收

    长任务、排障、大文件、resume、topic shift 与质量 A/B dogfood。

    质量验收

    • 与 full-history 基线相比，任务完成质量不得下降。
    • 当前 prompt、验收标准和未解决错误不得丢失。
    • 复杂任务允许进入 burst，不因追求 240K 中断工作。
    • 最新文件状态优先于陈旧历史副本。

    稳态验收

    • 普通 20 轮任务绝大多数请求处于 200K–260K。
    • burst 有明确原因、持续轮数和回收结果。
    • checkpoint 后不再重复发送已吸收的旧 delta。
    • resume 前后生成语义等价的 ContextPlan。

    安全验收

    • 摘要和主 provider payload 均不含秘密明文。
    • 历史、文件和 recall 不进入 developer/system 权限。
    • 任何省略都能追溯 replacement coverage。
    • provider、token status 与 compaction 消息集合一致。

    需要在实施前冻结的产品决定

    D-01
    240K 的计量口径

    建议统计 provider 实际输入的全部内容，包括 system prompt、tool schemas 和 conversation messages，不只统计 ContextPacket。

    D-02
    弹性上限

    建议初值 320K；它是 planner 的强审查线，不等同于模型硬窗口。

    D-03
    最近精确轮次

    建议目标 5 轮，自适应范围 3–8；工具长输出可替换为带 entryId 的短摘。

    D-04
    Rebase 安全边界

    建议只在用户轮次边界、agent settled 后执行，不在未完成的 tool loop 中途改写上下文。

    D-05
    低窗口模型降级

    当模型硬窗口不足以支撑 240K + 输出预留时，按比例降低 steady target，并显式显示降级原因。

    D-06
    质量 A/B 基线

    重构验收同时跑 full-history 与 steady-plan，对最终正确性、遗漏约束和返工次数做对照。

    FINAL POSITION

    不是把上下文做小，而是把 240K 变成一份高密度、低噪声、完成任务所需信息充分的工作集。

    完整 journal 负责不遗忘；ContextPlan 负责当前任务；240K 负责稳定注意力；burst 负责在真正复杂时保护交付质量。四者各自承担不同职责，不再互相替代。

    QUALITY FIRST → PLAN ONCE → STAY NEAR 240K → BURST WHEN JUSTIFIED → REBASE SAFELY
