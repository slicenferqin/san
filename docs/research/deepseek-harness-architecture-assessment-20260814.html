DeepSeek Harness：不是“又一个 Coding Agent”，而是一套可重组 Agent 操作系统

调研日期：2026-08-14 · 对象：deepseek-ai/deepseek-harness · 取证版本：47f943859bef60e4160492346772ded9b24f765a（2026-08-13）· npm：@deepseek-ai/dsh@0.1.0-rc.6 · San 对照：本仓库 @san/agent / @san/coding-agent 当前源码

一句话结论：用户的描述基本准确，但“所有能力都能自由替换”需要加两个限定：替换的是公开 capability seam / service，而不是任意内部函数；部分前端卸载、ACP、持久化迁移和跨平台沙箱仍有明确缺口。

它真正有价值的地方，不是插件数量，而是把 Agent 的控制循环、数据面、安全策略和 UI都放进同一个可撤销依赖图：模型、工具、会话、存储、压缩、子代理、workflow、后台 job、沙箱、LSP、Web UI 都以 Cordis service / event / reversible effect 组合。这个架构比 San 当前的“强内核 + 多扩展点”更彻底；代价是配置、依赖图、版本协同和运行时故障面显著扩大。

一、它到底是什么

DeepSeek Harness（CLI 名 dsh）是 DeepSeek AI 开源的通用 Agent harness。默认产品面是浏览器 UI，不是 TUI：执行 npx @deepseek-ai/dsh web，本地服务默认监听 127.0.0.1:3080。另有 headless profile，接受一个任务、等待 Agent 完成后打印最终回复并退出。

它基于 DeepSeek vendored 的 Cordis。Cordis 的核心抽象只有五件事：

  • Plugin：函数式 apply(ctx) 或 Service 子类。
  • Context：服务仓库；消费者依赖 ctx.tools、ctx.llm、ctx.sessions 等稳定 key，而不依赖具体实现。
  • Inject：声明依赖；服务未就绪时插件等待，启动顺序由依赖图而非手工调用顺序表达。
  • Typed Events：emit、waterfall、parallel、serial 四种调度语义。
  • Reversible effects：工具、prompt section、provider、listener 都通过 ctx.effect()/ctx.on() 注册，插件卸载时反向撤销。

README；Cordis Primer。

二、“Everything is a Plugin”怎样落地

2.1 三层组合：bundle → profile → patch

空 Cordis entry list
  → profile 指定的 bundle（按顺序）
  → profile/cordis.patch.yml
  → $DSH_HOME/cordis.patch.yml
  → CLI --patch（可重复）
  → Cordis Loader 激活依赖图
  • Bundle 是可发布的 Cordis 配置行集合。dsh-base 安装模型、工具、会话、持久化、沙箱、审批、设置、凭据、遥测等基础层。
  • Profile 是命名组合。官方模板有 web 与 headless。
  • Patch 按稳定 row id 替换配置或插入插件；dsh --profile web --dump-config 可查看实际启动树。

重要限制：row 配置是整块替换，不是深合并。覆盖一个 row 时必须重述要保留的所有字段。这是强可组合性背后的直接操作成本。

Architecture；dsh-base bundle。

2.2 能力 seam：Definition / Provider / Consumer

项目不是把所有东西简单命名为“plugin”，而是进一步规定一项可替换能力通常拆成三种角色：

角色职责例子
Service Definition定义稳定 ctx key、类型、错误语义ctx.fs、ctx.sandbox、ctx.workflowEngine
Service Provider提供一种实现本地 FS / E2B FS；JSON / SQLite storage；本地 sandbox
Consumer消费能力，通常向模型暴露工具tool-fs、tool-lsp、tool-workflow

这使替换具有传导性。例如 filesystem 与 subprocess 指向同一远程执行世界后，Bash、PTY、LSP 可一起迁移，无需各自 fork。扩展插件被要求依赖 Definition，不依赖具体 Provider。

三、最值得看的内部设计

会话日志是模型上下文的事实源

turn/*、step/*、用户消息、assistant chunk/message、tool call/result 全部成为 durable SessionEvent。deriveMessages() 从日志投影模型历史；UI replay、fork、resume、telemetry 都读同一条流。项目给出硬原则：model-visible means logged。

控制面与事实面分离

session/event 是可重放事实；agent/* 是 inbox、status、request、steering、retry 等实时控制。SDK 若要 transcript，应消费 session events，而非把 live event 当历史。

Prompt 也不是一个字符串

ctx.systemPrompt 注册多个 PromptSection；每 step 通过 system-prompt/assemble waterfall 组装，并同时采集当前可用工具 schema。不同插件可增删 prompt section，不需要改 loop。

前后端都进入插件图

Host 扫描声明 dsh.client 的 Loader entries，生成 window.__DSH_BOOT__ entry graph，浏览器从 /plugins/<id>/client.js 加载 client bundles。UI 不是静态壳套后端 API，而是 composition 的另一半。

3.1 Turn / step loop

turn/start
  claim inbox input
  agent/pre-step waterfall（拒绝或改写输入）
  step/start
  append user/message
  assemble prompt + tool schemas
  agent/request → llm/stream → assistant/chunk* → assistant/message
  tool/call* → tool pipeline → tool/result*
  step/end
  若仍欠一次模型请求或有 next-step input：继续 step
  agent/turn-stopping
turn/end

Loop 本身可替换，但 durable event vocabulary 与 Agent service contract 是它必须遵守的兼容边界。换言之，不是“随便写个 while 循环即可”，而是在稳定事件协议内换 driver。

3.2 Tool pipeline

tools/pre-execute waterfall
  → monotonic guards（只允许 deny / abstain，保护 identity）
  → approval（无可回答审批面时默认 deny）
  → tools/execute waterfall（timeout / retry / metrics 可包裹执行）
  → tool body（FS mutation 另过 write/edit intent gate）
  → tools/post-execute waterfall
  → outer normalization
  → ToolDefinition.finalizeContent
  → tools/result 同步通知
  → durable tool/result

这条流水线把权限、安全、沙箱、超时、重试、观测、结果改写从具体工具中抽出，而且保持最终模型可见结果只有一个。Code Mode 的聚合调用与内部 serialized sub-call 也走同一管线，避免建立旁门。

Agent lifecycle；Tool execution pipeline。

3.3 持久化不是“写个 JSON 文件”

JSONL backend 的设计深度明显超过普通 preview 项目：session header 绑定 id/cwd/delegation depth/agent preset；事件 seq 连续；chunk runs 可无损打包；默认 zstd 多 frame；每次 append fsync；首写使用 POSIX hard link 或 Windows write-through no-replace publish；尾 frame 不完整可保留完整记录并补 synthetic closers；已提交 turn 之前的损坏则拒绝加载。

但它也明确承认：格式仍是 v0、无迁移；不删除日志；同一 session 只能有一个 live writer；更换压缩方式要求新 root。这正是“工程严谨但产品协议未稳定”的典型状态。

已确认的硬限制

  • Client runtime 的 loader.unload 仍是 stub：服务端 reversible effects 的承诺目前比浏览器端完整；Client HMR 失败也没有自动 rollback。
  • Sandbox 不等于完整安全边界：Windows ACL 是 partial，Landlock 在旧 ABI 上可能 partial；macOS 依赖已 deprecated 但仍随系统提供的 sandbox-exec。sandbox vocabulary 也不覆盖网络和进程可见性。
  • ACP 只是 automation 子集：fresh sessions only，不支持 load/list/resume/delete/fork；MCP server、附加目录和多模态输入等也有限制。
  • Session JSONL 无生命周期治理：没有 delete API，格式 v0 无迁移，一个 session 一个 writer。
  • 配置覆盖有重述风险：patch 替换整个 row config；高速版本变动中，上游新增字段可能被用户旧 patch 无意抹掉。
  • 自修改能力风险高：tool-cordis 允许 Agent 改 live runtime，虽然 host runner 使用 node:vm，但这不应被当作“不可信代码的强隔离”。生产 profile 应显式裁掉这一能力，除非场景就是 harness 研发。

San 并不是“不插件化”

San 已有 extension loader、skills、custom tools、MCP、xdev devices、model provider registry、memory backend、subagent definitions、workflow/eval runtime、RPC host tools 等大量可插拔面。区别是：

  • San 的扩展点异构：每个子系统按自己的生命周期和配置方式接入。
  • dsh 的扩展点同构：统一投影成 Cordis context/service/event/effect，再由 Loader 管生命周期。
  • San 的核心行为由 AgentSession 聚合，这个集中点便于实现 Context Steady、execution-control、advisor/watchdog、TUI streaming 等跨域不变量；dsh 则通过 event waterfalls 和 service contracts 分散这些横切关注点。

六、San 应该借什么，不该借什么

优先借鉴 1. 建立“能力契约 / provider / consumer”分类，而不是先引入通用插件框架

San 最值得吸收的是 dsh 对依赖方向的纪律：model-facing tool 依赖 capability interface，不依赖 local implementation；组合根才选择 provider。可先为 sandbox/subprocess/fs/LSP/subagent 等边界补齐统一命名与 contract tests，不需要先把整个项目迁进 Cordis。

优先借鉴 2. 把工具执行横切策略收敛为一条可验证 pipeline

dsh 的 pre → guard → approval → execute → post → finalize → result 顺序非常清楚，尤其是 monotonic guard 与最终 immutable outcome。San 已有 execution-control、tool hooks、approval、安全和 renderer，但分散在 Agent、AgentSession、具体工具及宿主层。应先画出并冻结 San 自己的顺序契约，再考虑统一注册 API。

优先借鉴 3. 继续强化 durable fact / live control 的分层

dsh 的 session events 与 agent events 分工简洁，能降低 UI、resume、SDK 各自发明状态的风险。San 已有 journal、continuation authority、execution scope、AgentSession events，能力更强，但可以进一步明确哪些 event 是可重放事实，哪些只能作为实时控制信号，并让 UI/SDK 只从相应层读取。

选择性借鉴 4. Profile / bundle 概念适合“官方组合”，不适合把默认体验交给用户

San 的“拎包入住”原则要求默认产品不暴露 226 个包和 Cordis row。可吸收的是内部组合测试：例如 core、desktop、headless、automation 作为官方封闭 profile，每个都做启动闭包验证；不要让普通用户先理解 bundle layering 才能获得完整功能。

不建议 5. 不要整体迁移到 Cordis，也不要把 AgentSession 拆成几百个 npm 包

  • San 当前优势来自强宿主控制：Context Steady 的 authority/coverage、执行 scope、跨 Agent 预算、TUI 流式预览等都依赖跨层事实。过早服务化会把这些不变量变成事件顺序约定。
  • 226 packages 带来发布原子性、版本锁步、构建图、类型 declaration merging、Host/Client 双编译面等巨大治理成本。DeepSeek 已用生成图、Typert、workspace constraints 和 CI gate 承担；San 没有必要复制这笔税。
  • 动态 self-modification 很适合 harness 研究 demo，不适合作为默认 coding-agent 能力。它扩大供应链、权限和可重现性风险。

七、综合判断

问题判断
是不是“模型、工具、技能、会话、沙箱、存储、循环、调度、UI 全插件化”？基本是。官方源码和 capability graph 能逐项对应；连默认 loop、Web client graph、prompt assembly、持久化 backend 都在 composition tree 中。
是不是能“自由替换”？在公开 seam 内可以，任意替换则不成立。provider 必须满足 service/event/durable-log 协议，替换后的组合还要满足 inject 依赖与启动 settlement。
现在能否当稳定生产底座？不建议无条件采用。developer preview + RC + 明示 breaking changes；更适合研究、原型、内部平台，或锁版本后做受控验证。
是不是普通用户产品？默认 Web UI 可以直接跑，但核心竞争力仍偏开发者平台。它已经努力提供 profile 与默认 bundle，然而真正价值只有在写 plugin / patch / provider 时才能发挥。
对 San 的威胁/价值是什么？不是短期替代品，而是架构参照物。dsh 在“可重组能力图”领先；San 在“零配置默认、TUI、上下文与执行正确性、成熟编排”更集中。最优策略是吸收其 seam discipline 与 pipeline contracts，不追求同规模插件化。

最终结论：DeepSeek Harness 证明了“Agent harness 可以像操作系统一样由 capability providers 组合”不只是概念。它的 session/event 数据面、tool waterfall、安全/审批分层、Host/Client 插件图和动态 provider 替换都做到了源码级闭环。

但它现在更像极其完整的 0.1 架构公测：底盘成熟度高，外部稳定度低。San 不应追逐“插件数”或整体重构；应把它当作一张对照表，逐个审视 San 的 capability 边界、工具执行顺序、durable/live event 分层和官方组合闭包。借纪律，不借规模。
