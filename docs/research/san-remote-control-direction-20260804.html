San Remote Control

Remote Control 不是“把 TUI 搬到网页”，而是把分布在公司电脑、家里电脑和远程主机上的 San executor 变成可寻址、可恢复、可审计的执行网络，让手机和浏览器成为控制端。

状态：方向文档 产品核心：多主机控制面 执行位置：用户机器 网络：runner 主动出站
核心判断：San 应先产品化 runner + relay + event log，再建设 Web/移动/IM 客户端。代码、工具、MCP、provider credentials 和最终审批权留在 runner；relay 负责身份、寻址、密文队列、事件游标和设备撤销，不成为远程 shell 的超级管理员。

一、核心用户场景

Start

从手机发起任务

选择“公司电脑 / 某仓库”，指定 prompt、effort 和分支策略，runner 在本地创建 session/worktree 并执行。

Observe

随时查看进度

跨设备查看文本、thinking 摘要、tool 状态、subagent、diff、todo 和资源使用，断线后按 cursor 补齐。

Control

Steer、Cancel、Approve

追加要求、取消当前 turn、处理审批。敏感操作仍受 runner 本机策略约束。

Resume

控制权跟人走

在 CLI 开始的 task 可由手机接管；回到电脑后继续在 TUI 操作，不创建平行副本。

Background

长任务与定时任务

机器在线时后台运行；完成、失败或等待审批时推送通知。调度属于后续阶段。

Multi-host

一个账号管理多台机器

看到每台 host 的在线状态、可用目录、能力和当前 sessions，不再靠分别打开 SSH/TUI。

Host公司电脑、家里电脑、runner VM
Environmenthost 上的 repo/cwd/worktree 模板

Task/turn/item 属于 session 内部协议。Remote Control 不应继续用临时 room ID 代替 host、environment 和 session 的长期身份。

四、Runner 与控制协议的最小 Contract

Runner 上报

HostDescriptor {
  hostId
  label
  platform
  runnerVersion
  environments[]   // stable id、display path、repo、capabilities
  capacity         // sessions、worktrees、resource hints
  activeSessions[]
  lastSeenAt
}

控制命令

  • session.create：host/environment、prompt、effort、logical model、worktree policy。
  • turn.start、turn.steer、turn.followUp、turn.cancel。
  • approval.resolve：签名的用户决策，必须带 approval ID、scope 和 expected state。
  • resource.upload：附件使用 content hash 和 resumable chunks。
  • session.list/get/archive：控制面 inventory，不复制 session 权威状态。

事件与恢复

  • runner 为 session event stream 分配单调 sequence；client 记录 cursor。
  • 断线重连从 cursor replay；重复命令由 idempotency key 消除。
  • 控制命令带 expected generation/leaf，防止两个设备在旧分支上同时操作。
  • relay 可以保存密文事件信封，但 session 真相仍由 runner 的持久状态决定。

五、安全边界

必须成立

  • runner 只建立出站连接，不要求给用户电脑开放入站端口。
  • provider key、MCP credential、repo 内容默认不进入 relay 明文。
  • 每台 host 使用可撤销设备密钥，pairing 需要已有可信设备或一次性 proof。
  • 审批最终由 runner 执行；relay/client 不能绕过本地 allowlist 和 policy。
  • 高风险操作可以要求 proof-of-human 或只允许本机确认。

必须记录

  • 哪个 device 在何时向哪个 host/session 发出什么控制命令。
  • approval 的请求摘要、决策、scope、签名和 runner 执行结果。
  • host key 轮换、设备撤销、pairing 与异常重放。
  • 不记录 secret、完整敏感 header 或无界工具输出。
E2EE 与 IM 渠道存在真实冲突：公共 relay 可以保持 content-blind，但飞书/Slack bridge 要渲染明文，就必须持有会话密钥。渠道适配器应作为用户信任环境中的 privileged guest 运行，而不是让公共 relay 获得明文；若不能接受，则渠道只发无内容通知，点击进入 Web 客户端查看。

六、阶段路线

R0 · Protocol冻结 host/environment/session identity，补齐 RPC v2 remote contract、版本协商、cursor 与 expected state。
R1 · Runnersan runner 常驻、开机自启、环境发现、session inventory；先在本地/LAN 或自托管环境验证。
R2 · Relay主动出站、pair/revoke、E2EE、跨网 Web 控制、断线 replay、基础 push。形成首个可用 Remote Control。
R3 · Background密文离线队列、schedule、持久任务、worktree capacity、唤醒与完成通知。
R4 · Channels飞书/Slack/其他 IM 作为 privileged guest；随后再考虑 multiplayer 和组织策略。
首个可发布边界：完成 R0–R2。用户能注册至少两台 host，从手机浏览器选择 environment、创建 task、实时查看、steer/cancel/approve，并在断线后完整恢复。Schedule、离线派发和 IM 不阻塞首版。

七、首版明确不做

  • 不先复制一套完整 Web TUI；Web 只实现 remote 核心流程。
  • 不把 repo、provider credentials 或工具执行迁移到中心云端。
  • 不让 relay 直接执行 shell、修改审批 policy 或伪造 runner event。
  • 不先做飞书/Slack 渠道；没有 host/session control plane 时，渠道只会固化错误架构。
  • 不做公开可发现 task/thread。
  • 不在首版承诺多人同时编辑同一 session；先保证多设备单用户的一致性。

八、与模型路线的集成

  • Remote client 发送 effort 或 Logical Model intent；不发送具体 provider key。
  • Logical Model、Harness Profile 和 Provider Route 都由 runner 根据本机配置解析。
  • 控制面展示 resolved logical model、route 和 profile version，但 provider credentials 永不上传。
  • 同一远程 task 在不同 host 上可能解析到不同 route；UI 必须展示差异，不能假设服务商一致。
  • Remote Control 与 Harness/Route 可并行开发，共享 session/event/approval substrate，但发版门禁独立。

九、完成定义

  • runner 重启后恢复 host identity、environment inventory 和活动 session。
  • 所有远程连接均由 runner 主动出站，设备可独立撤销。
  • Web client 能创建、观察、steer、cancel、approve，并从 cursor 恢复。
  • 两个控制设备并发操作时，过期 expected state 被明确拒绝，不覆盖新分支。
  • relay 无法读取 E2EE 会话内容，也无法绕过 runner 本地审批政策。
  • CLI 创建的 session 与 Web 控制的是同一个持久 task，不产生状态分叉。
