背景与分层预算数学模型

San 的上下文管理并非单一的“到达 N Token 就砍”的简单阈值，而是由 Context Steady（稳态质量模型） 与 Native Compaction（原生物理压缩） 构成的双层防御体系：

1. 稳态预算推导公式 (`budget.ts`)

输入预算根据配置参数与当前模型的物理窗口动态计算：

reserveTokens   = contextWindow × reserveRatio                     // 默认 25% (给输出/思维留白)
hardInputCeiling= contextWindow - reserveTokens                    // 输入允许的绝对物理上限
steadyTarget    = min(configuredQualityWindow, hardInputCeiling)   // 质量目标 (默认 240K)
burstCeiling    = min(max(configuredBurst, steadyTarget), hardInputCeiling) // 突发上限 (默认 320K)
controlMax      = min(burstCeiling, steadyTarget × 13 / 12)        // 稳态控制线 (1.083×)

2. 不同模型窗口下的预算对比表

核心盲区 1：固定 240K 全局目标的失配分析

从上表可以直观看出固定写死 qualityWindowTokens = 240000 的设计缺陷：

  1. 只做向下 Clamp，抹杀了缓冲设计： 当物理窗口 ≤300K 时，hardInputCeiling 直接小于 240K，导致 steadyTarget、controlMax 与 burstCeiling 全部坍缩并重合至同一个数值（如 256K 模型下全为 192K）。
  2. 失去容忍突发的能力： 在 500K 模型下，系统允许上下文短期冲到 320K 并在下一轮异步消化；而在 256K 模型下，一旦单次工具吐出大文本导致预计输入达到 192,001 Tokens，系统便没有任何缓冲阶梯直接判定为 hard_pressure。
  3. 静态数值缺乏比例感知： 240K 是针对 Anthropic Claude 200K+、OpenAI 1M 等超大窗口总结出的“最佳质量/性能平衡点”。对于中小窗口模型，硬套 240K 等于放弃了根据模型能力动态分配稳态比例的能力。

核心盲区 2：Tool-Loop 中段的 Pause 熔断逻辑

用户疑问：“既然超了，为什么系统不自动压缩或重建 Plan，而是要停下来等用户手动操作？”

代码审查（agent-session.ts 的 #refreshContextSteadyPlanForProviderCall）显示，系统在生命周期不同阶段对 hard_pressure 的处理策略有严格区分：

1. 阶段策略差异对比

触发阶段 执行逻辑 是否自动压缩/重建 Plan 失败后行为

2. 允许最多 maxRecoveryPasses 次 #runAutoCompaction
3. 重建 ContextPlan 		是 (多次重试) 若仍失败则拒答并标记 paused_for_context

2. Tool-Loop 拒绝自动压缩的四重安全考量

1. Live Tool-Pair 保护约束： 在工具调用链中，当前的 toolCall 与未返回/刚返回的 toolResult 属于活上下文（Protected Entry）。如果强行在中段执行 context-full 压缩，可能破坏正在进行的工具调用语义或导致 RPC 协议契约断裂。

2. 无法解套的死局（Deadlock）： 如果 Tool-Loop 膨胀是因为某次命令（如 read 大文件或 bash 打印长日志）产生了一块极大的单体工具输出，这块输出作为 active tail 无法被部分切碎。即使压掉所有历史，单体 tail 依然 > 192K，自动压缩必然失败。

3. 预防无限循环（Snapcompact Thrash）： 若中段允许自动 compact，可能出现“compact 完只腾出 1000 tokens → 下一次工具调用又超 → 再次 compact”的死循环，极大地浪费 Token 并拖垮响应。

4. 保护 Provider Prompt Cache 命中率： 在同一个逻辑 Turn 内，San 故意冻结 ContextPlan 字节。如果每次工具返回都重载/重压缩 plan，会破坏送给 LLM 的 Prefix，导致 Cache Read 命中率骤降为 0。只有突破 controlMax 时才会重新评估；一旦突破又挤不进 burstCeiling，系统选择主动熔断。

架构优化与修复方案 (Proposal)

为解决“中小窗口模型无 Burst 缓冲”以及“Tool-Loop 遇到轻微溢出即挂起”的问题，提出以下三项优化建议：

方案 1：自适应窗口比例推导 (Adaptive Window Ratio)

修改 settings-schema.ts 与 budget.ts，不再将 240K 作为唯一的静态默认值，引入按物理窗口比例计算的推导逻辑： 

// 当 qualityWindowTokens 未显式配置（或为 0）时：
const defaultRatio = 0.60; // 默认将物理窗口的 60% 作为稳态质量目标
const computedSteady = Math.floor(contextWindow * defaultRatio);
const steadyTarget = Math.min(configuredSteady ?? computedSteady, hardInputCeiling);

// 保持 burst 阶梯空间：
const burstTarget = Math.floor(contextWindow * 0.75); // 75% 作为 Burst 顶峰
const burstCeiling = Math.min(configuredBurst ?? burstTarget, hardInputCeiling);

效果： 对于 256K 模型，硬上限 192K 下，系统会自动计算出 steadyTarget ≈ 153K、burstCeiling = 192K。此时系统保留了 39K Tokens 的 Burst 动态缓冲带，不会因为溢出几百 tokens 就直接触发硬压。

方案 2：Tool-Loop 中段受限恢复 (Bounded Mid-Turn Recovery)

在 #refreshContextSteadyPlanForProviderCall 中，当发生 hard_pressure 时，增加一次针对“非活尾部历史（Non-Live History）”的定向轻量压缩或微剪裁（Shake），条件为：

  • 检查 requiredTokens（活尾部+保护条目）是否小于 burstCeiling - 10000。
  • 如果活尾部本身未顶爆，允许执行一次限定 1 次的轻量历史 shake，尝试剔除旧的单体长工具输出。
  • 若 shake 后成功将 projected input 降至 burstCeiling 以下，则恢复 Tool-Loop 运行，避免直接中断用户体验。

方案 3：UI/CLI 熔断提示强化与一键解套

当触发 paused_for_context 警告时，在前端控制面（San Desktop / CLI）提供明确的操作引导：

  • 明确提示：“上下文达到模型硬上限 (192K/256K)，自动工具链已暂停以保护会话安全。”
  • 提供一键快捷操作选项：[压缩历史 (/compact)] | [清理大工具输出] | [临时切换至大窗口模型]。
