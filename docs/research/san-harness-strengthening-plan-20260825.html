Management Brief · 2026-08-25

San Harness 补强方案
从“零件齐全”走向“整机可信”

这份报告回答三个问题：我们现在做到哪了，接下来该抽象什么，以及怎样让 San 真正做到“任务挂一晚上，早上要么完成，要么清楚地停在一个能解释的位置”。

面向：产品与研发决策 性质：架构收口建议，不是完成声明 范围：coding-agent 的长任务与多 Agent 执行底座
结论：不要再造一套 Harness。把现有的执行控制内核扶正为唯一总控，再把 Goal、Workflow、Todo、San Loop、普通 task 全部接到它上面。

San 缺的已经不是“更多 Agent、更多工具、更多模式”，而是一个从接单、派工、验收、暂停到恢复都说了算的总账本。关键零件大部分已经在代码里；下一步应当以收口、制动、恢复和实战证明为主。

一、先看结论

保留
Context Steady

继续负责“给模型看什么”，但不再承担“任务做到哪”的职责。

扶正
ExecutionScope

现有执行作用域升级为每个顶层任务唯一、持久的事实来源。

补齐
常驻运行者

终端断开后任务仍有主人；进程重启后能恢复，不靠模型回忆。

推迟
新模式扩张

新的角色、插件市场、TUI 重写、自修改 Harness 都先不做。

一句话架构：一个任务只有一张任务单、一套完成标准、一个共享预算和一个最终状态；Agent、工具、工作流只是完成这张任务单的不同手段。

二、当前进度：机器已经造了大半，主要差总装和路试

代码已确认下表来自当前源码与仓库文档核对；“待收口”不等于没有实现，而是已有机制还不是所有入口共同遵守的唯一规则。

能力目前已经有的还没有闭环的
上下文控制Context Steady 已证明能把长会话送给模型的上下文压到稳定范围；仓库基准中第 10 轮为 598 token，对照为 198,340。上下文压缩只能降低单次调用成本，不能判断团队是否在重复同一种失败。它是“视野管理”，不是“任务管理”。
执行控制内核execution-control 已包含任务合同、执行账本、验收凭证、进展分类、看门狗、Provider 健康、持久化调度与恢复状态。它虽然已经进入根会话、普通 task 与 San Loop，但尚未成为 Goal、Workflow 等所有路径的唯一完成权威。
根会话与子 Agent每个真实顶层用户请求会创建根执行作用域；子 Agent 继承同一个 runtime、scope 和任务准入表。迟到请求、陈旧结果、非宿主凭证已有拒绝规则。根会话看门狗当前仍以一次性提醒为主，不会在无人值守时真正制动；后台断线后的长期所有权也未统一。
San Loop已与执行作用域、任务合同和验收门深度接线；Supervisor 的一句“通过”不能直接宣布完成。这是显式团队模式的强闭环，尚不能代表普通交互、Goal 和 Workflow 都具有同等闭环。
Goal / Workflow / TodoGoal 有持续目标与 token 预算；Workflow 有并发、Agent、token、时长硬限制和暂停恢复；Todo 有分阶段状态与 reconcile。三者仍各自保存一套状态或预算。Goal 工具可直接把自身标为完成；Workflow 也有独立运行状态。局部都合理，合在一起却容易出现“谁说了算”的问题。
验收类型层已经支持命令、浏览器、API、产物、审查、外部依赖六类宿主凭证；根任务没有真实凭证时不会被账本记为完成。普通任务还不能稳定、自动地产生合适的完成标准；六类凭证的实际接线覆盖不均，很多一般任务会一直缺少可完成的验收门。
度量bun run bench:north-star 与 10 条固定小样本已经存在，覆盖修 bug、小功能、模糊需求和一次中途纠偏。样本以单 Agent、短任务、确定性命令为主；尚未覆盖整夜、多 Agent、Provider 抖动、压缩、进程崩溃与恢复等真正高风险组合。
对之前方案的更新：8 月 5 日事故修复方案里规划的很多“新机制”，今天已经成为代码。问题已经从“要不要做账本、看门狗、验收门”变成“怎样让它们覆盖所有入口，并在真实故障下证明有效”。

三、根问题：不是能力不足，而是局部闭环太多

记忆不等于状态

模型记得“我做到哪”只能算线索。压缩、重启、换模型之后仍然成立的任务状态，必须由宿主保存。

活动不等于进展

多开一个 Agent、多写一个文件、多查一次状态，都可能只是忙。只有让完成标准、依赖或可交付产物发生变化，才算前进。

复核不等于验收

Supervisor、Oracle 或多数模型都说“好了”仍然只是意见。测试、浏览器、API 或产物检查通过，才是完成事实。

为什么会出现“一晚上一直转”

目标仍未完成模型决定继续
→
派出新任务名字不同，工作相同
→
产生新活动轮询、错误、文件、消息
→
被误认成进展租期再次刷新

2026-08-05 的事故就是这一链条的极端版本：约 6.99 亿累计 Prompt Token、187 个子 Agent、1,972 个子 Agent 错误回合。Context Steady 让每一轮更便宜，却没有权力阻止团队重复同一失败路径。正确修法不是关闭压缩，也不是单纯把并发调小，而是让宿主识别“这次工作有没有让任务更接近完成”。

四、建议抽象：一个任务实例，三层职责，五类事实

代码层不建议再新建一个 Run 大对象。直接把现有 ExecutionScope 扶正。对产品和管理层可把它叫“任务实例”；对代码继续沿用现名，避免第二套概念。

4.1 三层职责

第一层：任务账本
只记事实，不做猜测。保存用户目标、版本、工作项、完成标准、共享预算、依赖、进展回执和最终原因。它是唯一能回答“任务现在是什么状态”的地方。
第二层：调度总控
根据账本决定下一步。负责能否派工、是否重复、Provider 是否健康、是否换策略、是否等待、是否恢复、是否必须停下。确定性规则常驻，模型只处理规则无法判断的语义问题。
第三层：不同视图
同一份事实，不同人看不同切片。模型得到精简上下文，用户只看到“正在做 / 已完成 / 卡在哪里”，Stats 得到成本和效率明细。任何视图都不能反过来改写事实。

4.2 账本只需要五类核心记录

1. 任务合同

用户到底要什么、哪些要求不能丢、什么叫完成。新要求不是覆盖旧目标，而是产生新版本。

2. 工作项

谁在做哪一块、依赖谁、采用什么办法、是第几次尝试。身份按“工作 + 方法”确定，不按 V2、Final、Repair 之类名字确定。

3. 宿主回执

工具真实做了什么：测试结果、浏览器检查、API 响应、文件产物、Provider 错误、后台任务状态。模型文字不能伪造。

4. 控制决定

继续、换办法、换人、等待、恢复、请用户补信息或安全停机。每个决定绑定当时的任务版本，过期即作废。

5. 资源账

根任务剩多少预算、每个子任务已预留多少、实际用了多少、结束后退回多少。所有子 Agent 共用同一上限。

展开：与现有代码的对应关系
  • 任务账本：execution-control/types.ts、execution-ledger.ts、persistence.ts。
  • 工作项：task-contract.ts 与 San Loop assignments。
  • 宿主回执：evidence-gates.ts 与 recordHostObservation()。
  • 控制决定：watchdog.ts、durable-scheduler.ts、provider-health.ts。
  • 不同视图：Context Steady、TUI、Stats、Todo、Plan、Goal 都改为读取投影，不再拥有平行真相。

五、核心逻辑：从接单到收尾，宿主必须走完八步

1

接单

每个顶层用户请求创建一个任务实例；目标、限制和用户原话被固定下来。后续 steering 只生成新版本，不重新发明目标。

2

先写完成标准

按任务类型自动生成最低验收：Bug 要先复现再确认消失；网页要从浏览器走一遍；API 要验证请求和响应；研究要交付带来源的产物。不能验收的要求明确标为人工判断项。

3

拆工与准入

派出任何 Agent 前先检查依赖、重复工作、Provider 健康、权限和根预算。条件不满足时不发起模型请求，直接等待、复用已有工作或拒绝重复派发。

4

统一执行管道

所有工具都按同一顺序经过：权限检查 → 执行 → 结果规范化 → 保存产物 → 判断是活动还是进展 → 写入账本 → 给用户展示。工具可以插件化，执行秩序不能插件化。

5

双制动：进展租期 + 安全上限

有真实进展就续租；只有活动没有进展则不续。与此同时，每个无人值守任务都有不可自动突破的成本/时长安全上限。进展回答“值不值得继续”，预算回答“最多能花多少”。

6

无进展时收敛，而不是重试

同一工作、同一办法、同一失败连续出现后，先抑制重复，再做一次诊断；只允许采用实质不同的新办法。没有新办法就等待或清楚地停下，不能换个名字再派一个 Agent。

7

完成只认回执

所有必需验收项都通过、没有未处理的必做工作、回执属于最新任务版本，才能完成。Agent、Supervisor、Goal 工具都只能提出完成申请，不能直接改最终状态。

8

断线与重启后恢复

后台运行者从账本恢复任务，核对仍在运行的进程与子 Agent，已执行的副作用不重复。无法安全判断时暂停并说明原因，绝不靠猜测重放。

对“有效进展无限续期”的修正：工程上仍然按进展续租，避免用固定回合数误杀长任务；产品上必须保留一个默认安全上限，避免任何错误路径拥有无限账单。上限可以由用户明确提高，但系统不能自行突破。

六、现有功能以后各司其职

现有模块以后负责什么不再负责什么
ExecutionScope / Ledger顶层任务唯一真相；记录合同、回执、预算和终态。不负责展示，不直接写提示词。
Task / Hub派工、通信、后台任务控制；所有子项继承根任务。不能私自创建无限预算，也不能把聊天消息当进展。
San Loop复杂任务的多角色调度策略。不再拥有一套平行的“最终完成”定义。
Workflow把重复做法固化成可执行模板，例如并行调研、发布检查。不再是另一套独立运行时；状态和预算写回根任务。
Goal长任务的自动续行策略和用户意图锚点。Goal 工具不能直接宣布最终完成。
Todo / Plan任务账本的可读计划视图，帮助人和模型理解下一步。不作为真实执行状态；压缩后不能整表覆盖。
Context Steady / Checkpoint控制模型当前看到什么、必要时回退对话上下文。不能重置合同、预算、工作项或验收状态。
Skills提供默认方法和默认完成标准，例如 fix-bug、build-web。高频安全规则不能永远只写在提示词里。
Stats从任务账本生成效率、成本、浪费和恢复报告。不再主要依赖事后猜测 transcript。

七、实施优先级：先收口，再制动，再常驻，最后证明

里程碑 A：一个任务只有一个总账本

P0 · 先做

建议把现有 ExecutionScope 定为架构中心，不重写内核。

  • Goal、Workflow、San Loop、普通 task、hub、auto-continue 都必须携带同一个根任务标识。
  • 把各模块自己的状态明确分成“局部运行状态”和“根任务最终状态”；只有后者能对用户宣告完成。
  • 把分散的 token、时长、Agent 数预算合并为根预算树；子项先预留、后结算。
  • Todo、Plan、TUI、Stats 改为读取账本投影，不再保存另一份权威状态。
验收：同一任务无论从普通聊天、Goal、Workflow 还是 San Loop 进入，都显示同一个状态、同一份剩余预算和同一个终止原因。

里程碑 B：无人值守时真正会刹车、会验收

P0 · 紧随其后
  • 交互模式仍以提醒为主；无人值守模式消费看门狗决定，对确定的重复派发、无变化轮询和陈旧结果直接制动。
  • 模型监督先保持建议权；只有“换计划、换人、等待”这类可逆动作可逐步自动化。模型永远没有直接完成权。
  • 把六类验收回执接入真实工具路径；由 Skill、任务类型和变更影响自动生成默认验收。
  • Provider 出错时只暂停受影响路径；断路期间不继续烧模型请求，健康恢复后自动续行。
验收：相同工作换名字不能绕过去重；Provider 故障期间零重复模型调用；没有宿主回执时零错误完成。

里程碑 C：让任务脱离终端仍有主人

P1 · 可靠性闭环
  • 增加一个常驻后台运行者，持有执行 runtime、调度器、Provider 健康和子任务登记；TUI 只是连接它的客户端。
  • 支持 detach / reattach；终端退出不等于任务失去控制。
  • 进程重启后通过日志回放恢复，再与实际进程、子 Agent、文件副作用对账。
  • 对不可安全重放的动作采用幂等键或明确暂停，不假装“应该没执行过”。
验收：强制关闭前台终端或后台进程后，任务可恢复到原任务版本；已完成的副作用不重复，状态不倒退。

里程碑 D：把“敢挂一晚上”变成发布门槛

P1 · 证明后默认开启
  • 保留现有 10 条北极星小样本，另建压力样本，不把两者混成一个平均分。
  • 固定复现六类风险：多 Agent 重复派发、Provider 抖动、频繁压缩、进程崩溃恢复、迟到结果、用户中途改目标。
  • 加入 2026-08-05 事故的缩小可重复版本，确保同类循环会收敛到完成、等待、需用户或安全停机。
  • 参数只能由回放和长期 dogfood 数据调整，不能继续靠拍脑袋。
验收：每次涉及执行控制的发布，都必须同时通过短任务正确性和长任务故障恢复；任何一次错误完成都阻断发布。

八、怎样判断补强真的有效

管理层不需要看内部账本和哈希。只看四个问题，再加三条红线。

完成率

无人值守任务最终真正完成的比例。

说清率

没完成时，能否明确说明卡点和下一步。

预算内

在默认安全上限内完成的比例。

可恢复

断线、崩溃、Provider 恢复后能否继续且不重复副作用。

红线发布要求为什么
错误完成必须为 0“说做完但实际没做完”直接破坏产品信任。
有效任务被误停高影响误停必须为 0看门狗只能先执行可证明的动作；不确定就继续观察。
恢复后重复副作用必须为 0重复发布、重复写数据、重复扣费比停住更危险。

建议增加一个内部效率指标：最后一次真实进展之后继续消耗的 token 占比。它比总 token 更能直接反映“是否在打转”。

九、以后什么该写进 Harness，什么不该

不是每条经验都值得做成新机制。建议采用四级升级规则：

一次性做法 → 对话或计划

只对当前任务有用，不进入全局系统。

重复方法 → Skill / Workflow

例如“修 Bug 先复现”“发布前并行检查”，做成模板即可。

反复造成损失 → 宿主硬规则

例如重复派发、陈旧结果、越过预算、无凭证完成，必须由代码拦住，不能只提醒模型。

对外承诺 → Benchmark / 发布门

凡是我们要向用户宣传的能力，都必须有可重复的场景证明。

判断标准：模型偶尔忘记一次，写提示词；模型反复忘记且代价高，写宿主规则；系统声称已经做到，写验收和基准。

十、外部方法论：吸收原则，不照搬产品

来源值得吸收不建议照搬
Anthropic长任务需要持久进度、明确功能清单和真正的端到端验证；浏览器验证能发现单测看不到的问题。不要把模型维护的 progress 文件当最终真相；San 已有宿主账本，应比文本文件更可靠。
OpenAI把知识、计划和架构规则放进仓库，并用 lint / CI 机械执行；不要依赖聊天和人的脑内知识。不照搬其具体仓库组织。San 应吸收“规则逐步升格为代码”的方法。
Prime Agent后台常驻、断线重连、持续目标、心跳、受预算约束的自动续行，正好补 San 的进程生命周期。当前不需要复制持久 Python REPL、自修改 Harness 或完整 RLM 路线；先补运行所有权。
DeepSeek Harness稳定接口和插件边界有利于让 CLI、Web、工具共享一套能力。不做“万物插件化”重写。只把工具执行管道和宿主回执接口做成稳定接缝。
San 自身Context Steady 解决“看多少”，Execution Loop 解决“怎么协作”，执行账本解决“凭什么继续和结束”。不能让三套能力各自长成完整产品；必须围绕一个根任务收口。

十一、明确不做

不做

再造一套运行状态机

现有 ExecutionScope 足够承载收口，新增 Run/Job 内核只会制造第三份真相。

不做

常驻第二个 LLM 当监工

监工也会循环。常驻的是确定性规则，模型监督只在疑难处被调用一次。

不做

用并发和重试上限冒充收敛

它们只能减慢事故，不能识别 187 个 Agent 是否在做同一件事。

不做

关闭 Context Steady 冒充修复

关闭后单次请求可能更贵，语义活锁依旧存在。

不做

把内部机制铺到用户面前

用户只看三种状态。账本、版本、回执、指纹都留在内部和 Stats 详情里。

不做

在闭环前扩张新模式

更多角色、更多自治入口、桌面端大改、插件市场都推迟到统一总控之后。

十二、建议现在拍板的四件事

  1. 架构拍板：ExecutionScope 是唯一根任务真相；新入口没有接入它就不能成为默认能力。
  2. 产品拍板：无人值守默认采用“进展续租 + 安全上限”，不允许无限预算，也不靠固定回合粗暴终止。
  3. 研发拍板：下一阶段暂停新增编排模式，优先完成 Goal / Workflow / 普通任务的状态、预算和验收收口。
  4. 发布拍板：“敢挂一晚上”必须由压力回放和恢复场景证明；没有证据，不进入默认开启。
最终判断：San 已经具备成为可靠 Harness 的核心零件。现在最有价值的工作不是继续展示“我们还能做什么”，而是让所有能力服从同一张任务单，并用事故回放证明它会完成、会停、会恢复。
