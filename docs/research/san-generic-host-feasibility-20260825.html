Architecture Decision Brief · 2026-08-25

San 通用 Agent Host
可行性与难度评估

判断目标：让 Coding 从 San 的默认身份降为一个领域能力包，同时复用现有 Agent Loop、Harness 和 Skill，不重写已经工作的执行底座。

结论：可行建议：增量抽象，不做一次性搬家范围：packages/agent 与 packages/coding-agent
结论：可行，但“做一个通用入口”和“把整个 Harness 抽成独立包”不是同一个难度。

可行第一种是中等难度：在现有会话外壳上增加可注入的领域配置，再用第二个非 Coding profile 验证边界。高难度第二种是高难度：当前会话层和 SDK 仍然把上下文、工具、提示、持久化、模型路由、UI、子 Agent 生命周期及 Coding 能力交织在一起。直接搬文件或改包名，风险明显高于收益。

一、为什么不是从零开始

Agent 内核
已有

@san/agent 已提供 Agent、agentLoop、agentLoopContinue、工具调用、流式传输和状态管理。它不要求工作对象必须是代码仓库。

执行控制
已有骨架

execution-control 已有运行时、任务合同、账本、持久调度、进展分类、Provider 健康和完成状态等边界。它已经被普通 task 与 San Loop 使用。

Skill
已有接线

Skill 能被发现、加载，并把声明式流程/检查编译进会话级状态；这正是领域方法进入通用运行时的入口。

关键判断：要补的是“宿主边界”，不是再造一个 Agent Loop，也不是再造一套长任务账本。

二、为什么完整拆分仍然不轻

当前代码已经证明能力存在，但还没有证明包边界已经干净。

观察事实来源对拆分的含义
会话类约 23,249 行packages/coding-agent/src/session/agent-session.ts它不是薄薄的适配器，而是模型、压缩、分支、工具、顾问、记忆、目标、工作流、提示、持久化和生命周期的汇合点。
SDK 约 3,854 行packages/coding-agent/src/sdk.ts会话创建同时负责工具发现、MCP、扩展、Skill、模型路由、执行运行时、工作区和 Provider 管道；需要先分层再移动。
公共入口导出面很宽packages/coding-agent/src/index.ts当前包同时导出 SDK、会话、执行控制、Skill、San Loop、任务、工具、LSP、Git 和 UI。改名或迁移会产生大范围调用方迁移。
会话导入了大量领域模块agent-session.ts 导入 edit、eval、LSP、Git/路径、代码智能、工作区、工具和 Coding 提示不能把整个 AgentSession 原样放进所谓的通用包；必须先把领域依赖变成显式能力接口。
[INFERENCE] 难度分级：“新增通用 profile 并复用现有底座”约为中等难度；“一次性把 Harness 迁出 coding-agent 并保持所有行为兼容”约为高难度。后者的主要成本不是代码行数，而是状态、事件、持久化和调用关系的迁移。

三、应该拆什么，暂时不要拆什么

优先视为通用层

  • @san/agent 的循环、工具协议、流式事件和状态管理。
  • 执行运行时、任务合同、预算/调度、进展和终态规则。
  • Skill 的发现、加载、覆盖和声明式检查编译。
  • 会话生命周期、上下文维护、压缩、恢复、Telemetry 和 Agent 注册。
  • 扩展、MCP、记忆和 Provider 管道的抽象接口。

保留在 Coding profile

  • 仓库/工作区上下文、Git、LSP、代码图谱和代码专用提示。
  • read/edit/grep/bash 等 Coding 默认工具组合及路径安全策略。
  • 代码领域的默认 Skill、修复流程和测试/构建检查。
  • Hashline、补丁、编译器/内核、代码浏览等强领域实现。
  • Coding CLI 的 TUI、命令和默认设置。

混合区域：当前 AgentSession、sdk.ts、Settings、扩展运行器、MCP 和任务执行器既包含通用机制又包含 Coding 默认值。它们应先变成“通用核心 + profile 注入”，不应先按目录机械移动。

四、推荐路线：先证明第二个 profile，再抽包

阶段 1：定义领域能力边界

P0

在现有包内引入一个明确的 Host/Profile 配置对象，描述工具工厂、上下文提供者、系统提示片段、持久化适配、验收提供者和 UI 能力。默认实现继续是 Coding，不改变用户路径。

通过条件：新接口能表达“无 Coding 工具”的 profile；不新增第二套 Loop、账本或完成状态。

阶段 2：做一个非 Coding 的最小 profile

P0

选择研究/网页助手这类不依赖仓库编辑的 profile，使用同一个 Agent Loop、会话生命周期、Skill 加载和执行控制。它只提供 web/search/browser 等能力，默认不挂载代码工具。

通过条件：真实跑通一条“提出问题 → 使用 Skill → 调用工具 → 得到可验证结果 → 正常结束”的路径；Coding 现有路径不回归。

阶段 3：按依赖方向移动纯模块

P1

先移动没有 Coding 导入的模块：Skill loader/compiler、执行控制纯类型与运行时、通用会话协议、工具/扩展接口。每移动一块就更新所有调用方和测试，不保留长期双真相。

通过条件：通用包不反向依赖 @san/coding-agent；Coding 只作为 profile/适配层依赖通用包。

阶段 4：最后处理公共包名和 CLI

P2

只有第二个 profile 稳定、依赖图清晰后，才考虑新包名、CLI 默认身份和公共导出迁移。先迁移仓库内调用方，再删除旧路径；不要用兼容别名掩盖未完成的边界。

通过条件：源码、测试、构建、Worker 入口、SDK 使用者和文档都只依赖最终方向。

五、最容易踩的三个坑

把“可选”做成满屏 undefined

[INFERENCE] 如果每个 Coding 子系统都变成可选字段，通用层会得到大量组合状态，故障只会从编译期推迟到运行期。应按能力组注入 profile，而不是把所有参数都变成可空。

先拆包，后找第二个用户

[INFERENCE] 没有第二个真实 profile，抽象只会围绕当前 Coding 需求重新命名，最后得到一个“换了名字的 coding-agent”。先做第二个消费者，边界才有压力测试。

同时重做状态模型

执行控制、Context Steady、Goal、Workflow、Todo 和 San Loop 已经各有状态。通用化阶段不应同时重写它们；先复用现有事实来源，避免两项高风险迁移叠加。

六、最终决策

建议继续，采用“内核不动、宿主分层、第二 profile 验证、最后抽包”的路线。
  • 可行性：高。现有 Agent Loop、Skill 和执行控制已经提供了足够的落点。
  • 短期风险：可控。先在 coding-agent 内做 profile 注入，不触碰公共包名和默认 CLI。
  • 完整拆分难度：高。核心难点是 AgentSession/sdk.ts 的交织状态和宽公共导出，而不是底层模型调用。
  • 不建议：一次性把 23k 行会话类搬到新包、同时改默认提示、工具集、持久化和 CLI 身份。
  • 下一步：先画出 Host/Profile 的最小接口，并从一个不需要代码仓库的真实场景开始验证。

依据

  • packages/agent/package.json：通用 Agent 包的职责描述与独立依赖边界。
  • packages/agent/README.md：Agent、工具、低层 Loop 和运行级遥测的公开接口。
  • packages/coding-agent/src/sdk.ts：会话创建时同时组装 Skill、工具、扩展、MCP、模型和执行运行时。
  • packages/coding-agent/src/session/agent-session.ts：会话生命周期、上下文、工具、目标、工作流、Skill、执行控制和 Coding 模块的汇合点。
  • packages/coding-agent/src/execution-control/：运行时、账本、任务合同、调度、看门狗和 Skill 检查边界。
  • packages/coding-agent/src/extensibility/skills.ts 与 skill-gate-compiler.ts：Skill 发现/加载及声明式检查编译。
