1. 最终结论

v0.4 的工程核心、自动化合同、安全边界和无凭据 dogfood 已完成，可以作为“默认关闭的内部试用候选”验收。 Managed 只能运行被批准的准确版本；Ad-hoc 只能先生成草稿、再逐次批准、最后显式运行一次；两者都没有自动触发和自动授权路径。
当前不能宣传“已实测比 Skill 节省 30% 编排 token、减少 50% 主上下文”。 真实模型的 Skill 对照样本尚未采集，报告器会诚实返回 insufficient_data。因此提案 W5 和 v0.4 产品终验仍为 PARTIAL，rollout 保持 keep-default-off。

2. 用户现在怎么使用

Managed SOP

  1. /workflow draft-managed 一段已有 SOP 可先生成不落盘、不发布、不运行的脚本草稿。
  2. 把已稳定的脚本放进项目 .san/workflows/*.js，也可发现兼容的 .claude/workflows/*.js。
  3. /workflow publish name 冻结版本，但不会批准或运行。
  4. /workflow approve name@version 先显示人话阶段、Agent 步骤、硬停止条件和完整脚本，再输入短时确认令牌。
  5. /workflow run name@version {JSON} 才会真正启动。
  6. 版本、参数 schema、权限、scope 或预算改变后，旧批准不再匹配。

Ad-hoc Dynamic

  1. /workflow generate 一段人话任务 只让模型返回 JSON 草稿，不执行工具。
  2. 静态解析器检查脚本、权限和预算，保存为有时效的一次性草稿。
  3. 需要缩小参数、权限或预算时，用 /workflow revise-draft old-id 新描述 生成新边界，旧草稿和旧批准立即失效。
  4. /workflow approve-draft id 完整复核后，再输入短时确认令牌。
  5. /workflow run-draft id 才运行，并原子消费这次批准。
  6. 同名新草稿不能继承批准；拒绝、过期或已经运行后删除脚本和参数，只保留会话内 hash 审计。

san.workflows.enabled 只打开 Managed；san.workflows.adHocEnabled 单独打开 Ad-hoc；修改文件还必须开启 san.workflows.allowIsolatedWrite 并使用非 none 的 task.isolation.mode。三层默认值都保持关闭。

4. 为什么它不会脱离掌控

可能失控的地方本次实现的控制失败时怎么处理
模型自己决定运行生成、批准、运行是三条独立路径；生成侧请求没有 Workflow 工具，也不落历史。没有显式 run 命令时 Agent 启动数必须为 0。
旧批准被偷换复用Managed 键绑定 source、版本、schema、scope、权限和全部硬预算；Ad-hoc 再绑定 task、args、过期时间并只消费一次。任何 hash 或边界不一致都拒绝。
脚本直接摸主机不使用现有高权限 eval；受限 AST 解释器拒绝 process、环境变量、模块、文件、Shell 和直接网络访问。静态拒绝或运行时 permission_denied。
Subagent 扩权工具集合取 Workflow manifest、当前会话和 Agent 定义的交集；严格模式关闭 MCP、扩展、自定义工具、task/IRC 和工具发现。不在交集中的工具从子会话中不存在。
路径穿越或软链接逃逸每次文件工具调用同时检查逻辑路径和 realpath；URL、附件、内部 URI 与未适配工具 fail-closed；隔离工作区重映射批准 scope。scope_violation，Agent 调用失败。
并发和成本暴涨并发 fan-out 先切分批准 token，分支内每次 provider 调用只拿剩余额度；Agent、时间、步骤和集合也都是硬上限。超出节点分配时不提交 usage/result，并停止新节点。
写入覆盖人工变化Agent 只能产补丁；用户看完全部补丁后拿到一次 token；应用前再比对工作树基线与补丁 hash。baseline_changed / blocked；不写入。
崩溃后重复应用apply_started 在副作用前写入 append-only ledger；恢复时未完成应用转成 unknown，绝不自动重放。人工检查，不猜测、不重跑。

5. 受控写入的实际链路

显式运行 isolated_write Workflow
  → Agent 只在独立 worktree 修改
  → 主工作树保持不动，生成 patch artifact
  → /workflow review-write <artifact-id> 显示完整补丁
  → 检查 artifact hash、路径 scope、密钥、嵌套仓库
  → 仅本次审阅产生 opaque apply token
  → /workflow apply-write <review-token>
  → 再检查主工作树 baseline + git apply --check
  → ledger 先记 write_apply_started，再应用一次
  → 验证 post-image，最后才交付 Workflow 结果

用户也可以用 /workflow reject-write <artifact-id> 明确拒绝。只要还有补丁未应用或未拒绝，最终结果就不会被标成已经交付。该链路要求 san.workflows.allowIsolatedWrite=true，且 task.isolation.mode 不能是 none。

7. 验收矩阵

提案验收项当前结论说明
Managed 同版本稳定、边界变化失效、显式启动、暂停恢复、单次交付工程通过合同、manager、runtime、store 和 25-run 确定性 dogfood 共同证明。
Ad-hoc 模型仅生成、逐草稿批准、一次运行、拒绝零执行、不自动升级通过命令入口使用独立 ephemeral turn；生成后仍走静态验证和双步骤批准。
共同安全门禁：主机逃逸、工具交集、硬预算、取消、unknown、脱敏通过恶意 fixtures、路径 scope、严格 SDK 工具和 ledger tests 全绿。
受控写入：完整审阅、基线保护、凭证检查、无重复写、崩溃可判断通过真实临时 Git 仓库验证 apply once、CAS、tamper、secret 和 interrupted apply。
Managed 编排 token -30%、主上下文增长 -50%、质量不回退待真实样本报告器与阈值已实现，但不能在没有真实对照数据时宣布通过。

验收口径：工程核心可作为 default-off 内部试用候选验收；提案完整 W5 和 v0.4 产品终验尚未完成，不能扩大 rollout，也不能宣传“更省 token”。
