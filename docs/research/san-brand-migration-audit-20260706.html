San 品牌迁移清扫审计

日期：2026-07-06。口径：基于当前 working tree，排除 node_modules、.git、crates/vendor、coding-agent 大型 session fixture、packages/coding-agent/CHANGELOG.md 和 bun.lock。本报告只做梳理，不直接修改代码。

结论

现在应继续清扫，但不能做全仓机械替换。仓库里旧命名同时承担四种含义：用户可见产品文案、历史兼容接口、发布链路标识、内部包生态标识。正确路径是按这四类分别收口。

最高优先级不是内部包名，而是发布面和产品面：当前 san update 和安装脚本已经转向 San release，但 CI release 仍在构建和上传 omp-* 二进制，Homebrew tap 仍指向 Formula/omp.rb。这会直接导致新安装或更新失败。

一、产品面

产品面是用户直接看到或复制使用的内容。这里应该尽早清扫，因为发布后再改会让用户文档、命令、配置路径和错误提示混乱。

二、兼容面

兼容面是旧用户、旧插件、旧配置和旧 session 仍能工作的承诺。这里不能按品牌直觉删除，应转成“San 优先，legacy 可读，尽量不再写 legacy”的策略。

兼容对象 当前状态 保留原因 迁移建议
旧配置目录 ~/.omp / 项目 .omp 已有部分迁移：settings 从 sibling legacy .omp/agent/settings.json 迁移； 扩展 roots、secrets、WATCHDOG、task agents 已开始改到 .san。 老用户升级不能丢设置、secrets、extensions、commands、skills。 增加集中 migration 表：每个 surface 明确 old path、new path、读写策略、一次性迁移时机。原则是 San 写 .san，只在缺失新配置时读取 .omp。
环境变量 SAN_PROFILE 优先，OMP_PROFILE/PI_PROFILE 兼容； SAN_CONFIG_DIR 优先，PI_CONFIG_DIR 兼容。OMP_BIN 仍出现在 benchmark scripts。 CI、脚本、用户 shell 配置可能仍用旧变量。 文档只写 SAN_*。旧变量保留读取并标注 deprecate。benchmark 脚本可支持 SAN_BIN 优先、OMP_BIN fallback。
插件 manifest package.json#omp 插件 loader、manager、installer、examples 仍以 omp/pi manifest 为核心。 第三方插件已经按 omp 字段发布，直接改会断生态。 新增 san manifest 字段，解析优先级 san -> omp -> pi。 新文档和模板写 san；旧字段继续支持。
omp-plugins.lock.json 和 .omp-plugin/marketplace.json 仍是插件安装、marketplace 和兼容测试的核心文件名。 这是持久化格式，重命名需要迁移和 fallback。 短期保留旧文件名作为兼容格式；新增 san-plugins.lock.json 前先写 migration test。 .omp-plugin/marketplace.json 可先作为 marketplace 兼容路径，新增 .san-plugin/marketplace.json。
omp:// internal URL 工具、router、prompt、docs 中仍作为 harness docs 协议。 旧 session、用户习惯、测试可能引用。 新增 san://，保留 omp:// alias。禁止新文档继续推荐 omp://。
历史 changelog、fixtures、session jsonl 大量旧字符串来自历史记录和 test fixture。 它们是历史证据或回归输入，改掉会降低测试真实性。 不做品牌清扫；仅当 fixture 的预期行为变更时更新。
旧 @oh-my-pi/* import 全仓 11,296 次相关匹配，主要是 workspace package import。 这是包名和模块解析契约，不只是文案。 归入内部包名迁移阶段；产品面不要直接暴露这些名字，代码 import 可暂保留。

仓库内真实 legacy 配置目录

当前仓库仍跟踪了 .omp/commands/*.md 和 .omp/skills/**。这不是用户 HOME 状态，而是项目自身的 agent 配置。由于项目原生目录已经切到 .san，这批文件应迁移到 .san，并保留一轮 discovery 测试证明旧 .omp 只作为 fallback。

三、发布面

发布面是当前最大风险。前面已经把启动更新检测和 san update 的 GitHub release 查询改向 slicenferqin/san，安装脚本也改为下载 san-*。但 release pipeline 仍在生产和上传 omp-*，这会造成“代码找 San 资产，CI 发 OMP 资产”的断链。

发布环节 当前发现 风险 建议动作
本地 binary build packages/coding-agent/scripts/build-binary.ts 输出 dist/omp 或 dist/omp-<target>。 高 本地构建出的二进制名仍是 OMP。 改为 dist/san / dist/san-<target>，同步 smoke test。
CI release binaries scripts/ci-release-build-binaries.ts targets 仍输出 packages/coding-agent/binaries/omp-darwin-arm64 等。 高 GitHub release asset 名与安装/更新脚本不匹配。 目标文件改为 san-darwin-arm64、san-linux-x64、san-windows-x64.exe。
GitHub Actions release matrix .github/workflows/ci.yml release matrix、artifact name、download pattern、release files、macOS verify 仍用 omp-binary-* 和 omp-*。 高 即使 build script 改了，workflow 仍会找旧路径。 同步改 binary_path、artifact name、download pattern、release files、verify download URL。
Homebrew scripts/ci-update-brew-formula.ts 仍渲染 class Omp、omp-* URL、bin/"omp"；workflow 仍 checkout can1357/homebrew-tap 并写 Formula/omp.rb。 高 san update 已改为 brew upgrade san，但 tap/formula 并不存在或未更新。 决定是否开 slicenferqin/homebrew-tap 和 Formula/san.rb。未就绪前， san update 不应优先走 brew，或应给出明确不可用错误。
mise san update 已改为 github:slicenferqin/san，但 CI / docs 里仍有旧 github:can1357/oh-my-pi 片段。 中 更新检测路径和安装方法可能不一致。 补 mise 安装/更新 smoke：mise install github:slicenferqin/san@vX.Y.Z。
NPM 分发 scripts/install.sh / install.ps1 仍通过 @oh-my-pi/pi-coding-agent source install。packages/coding-agent/package.json bin 已是 san。 中 如果 San 不继续发布旧 npm 包，source install 会失败；如果继续发布，品牌仍不独立。 短期可保留旧 npm 包名，但 release 文档要明确；中期发布新包名并让旧包依赖/转发新包。
macOS signing / notarization docs/macos-signing-notarization.md、workflow signing step 仍引用 omp-darwin-arm64。 中 签名和验证路径跟二进制名耦合。 随 release binary rename 一并改，避免签旧文件名。
安全 / repo metadata .github/SECURITY.md 仍指向 can1357/oh-my-pi private advisory。 中 用户报告安全问题会走错仓库。 改到 slicenferqin/san 的安全通道。

发布面必须形成的闭环

  • GitHub release 能产出 san-linux-x64、san-linux-arm64、san-darwin-x64、san-darwin-arm64、san-windows-x64.exe。
  • scripts/install.sh --binary 和 scripts/install.ps1 -Binary 能下载这些 asset。
  • san update --check 查 San release，san update 选择的安装器能实际安装同一版本。
  • release verify job 下载并 smoke 测试 San asset，而不是 OMP asset。
  • Homebrew 公式在未准备好时不应该被 san update 当成可用路径。

四、内部包名

内部包名是最大但最低优先级的迁移面。当前 monorepo 的 TypeScript import、workspace catalog、测试、生成 registry 都建立在 @oh-my-pi/* 上。这里可以晚于产品面和发布面处理，但必须提前决策路线。

包 / 模块 当前名称 建议
coding agent @oh-my-pi/pi-coding-agent，bin 为 san 短期可保留包名以降低发布风险；中期确定新包名，例如 @slicenferqin/san 或 @san/coding-agent，再做 dual-publish / redirect。
核心 TS 包 @oh-my-pi/pi-ai、@oh-my-pi/pi-utils、@oh-my-pi/pi-tui、@oh-my-pi/pi-agent-core、@oh-my-pi/pi-catalog、@oh-my-pi/pi-wire 不在第一轮改。先让产品面不暴露这些包名；包 scope 迁移需要 workspace、exports、release、npm ownership 一起改。
stats @oh-my-pi/omp-stats 比其他内部包更用户可见，因为 CLI 有 san stats。建议优先在内部 API 保持旧包名，产品文案和命令改 San；后续包名可迁到 san-stats。
native packages @oh-my-pi/pi-natives、@oh-my-pi/pi-natives-<tag> 与 npm optional dependency 和 release sentinel 绑定，迁移风险高。等 binary release 闭环稳定后再做。
Python packages python/robomp、python/omp-rpc、omp_local.py 如果它们属于 San 产品，应改名；如果是内部 CI/机器人遗留，可暂列为内部包名/工具名，不阻断 CLI 发布。
Infra runner omp-kata、arc-omp-values.yaml、omp-kata-runner 这是 CI 内部 label 和 runner image 名，非用户产品面。可以后置，但文档若公开应标注为 legacy infra name。
生成兼容 registry legacy-pi-bundled-registry.ts 静态引用大量 @oh-my-pi/* 短期不改。包 scope 迁移时重跑 generator，并保留旧 specifier remap 以支持旧插件。

建议执行顺序

阶段 目标 具体任务 完成判据
Phase 1 产品面清扫 改 CLI/TUI 文案、prompt、examples、日常 docs、.omp 项目配置迁移到 .san。 用户文档默认只出现 san / .san；.omp 只出现在 migration/legacy 段落。
Phase 2 发布面闭环 改 binary build、CI release asset、GitHub release verify、install scripts、Homebrew/mise 策略。 一次 tag release 能产出 san-* asset；scripts/install.sh --binary 和 san update --check 都能指向同一 release。
Phase 3 兼容 alias 标准化 引入 san://、package.json#san、.san-plugin 等 San 原生入口，同时保留旧入口。 新文档只推荐 San 入口；旧 OMP 入口有回归测试覆盖。
Phase 4 内部包名迁移决策 决定新 npm scope、dual publish、旧包转发、workspace import 改名策略。 有明确 npm 发布计划和回滚策略；不和产品面清扫混在一个 PR。

建议增加的检查

  • 新增一个“产品面旧名检查”脚本，只扫描 docs、prompts、examples 和用户可见 CLI 组件。允许 legacy、migration、compat 文件白名单。
  • 新增 release asset smoke：构建完成后断言 packages/coding-agent/binaries/san-* 存在，且不存在待上传的 omp-*。
  • 新增 config migration matrix 测试：.san 优先，.omp fallback，只写 .san。
  • 新增 internal URL alias 测试：san:// 和 omp:// 读取同一 docs index，但 help/prompt 只展示 san://。
  • 新增 plugin manifest alias 测试：san manifest 优先于 omp，omp 仍可加载。

下一步建议

下一步应先做 Phase 2 的 release asset 闭环，因为它会影响安装和自动更新是否能工作。并行做 Phase 1 中最直接的产品面文案清扫：prompts、examples、用户文档和 TUI tips。内部包名迁移先不动，只建立决策文档和白名单。

可直接落地的第一批任务：

  • 把 scripts/ci-release-build-binaries.ts 和 .github/workflows/ci.yml 的 release binary 路径改成 san-*。
  • 把 scripts/ci-update-brew-formula.ts 改成可渲染 Formula/san.rb，或暂时禁用 brew update path。
  • 把 packages/coding-agent/src/modes/components/tips.txt、prompt、examples 里的 omp 命令改成 san。
  • 把 docs/mcp-config.md、docs/settings.md、docs/secrets.md 改成 San 原生路径，并集中说明 legacy .omp。
  • 迁移仓库跟踪的 .omp/commands 和 .omp/skills 到 .san。
