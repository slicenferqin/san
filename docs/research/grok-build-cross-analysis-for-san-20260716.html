Grok Build x San：值得借鉴，但重点不是“功能追平”

这是一份基于两边当前源码的交叉分析。Grok Build 的优势是工业 harness 的安全边界、变更归因和持久自治；San 的优势是 Context Steady、结构化 subagent 交付、跨平台隔离、Execution Loop 与可审计 Brain。正确做法是补齐 San 的边界层，而不是重写或复制整套产品。

分析日期 2026-07-16 Grok Build b189869b7755 San 1a94da7f0a47 源码级架构 / 产品能力 / 落地优先级
最值得吸收

Folder Trust、OS sandbox 与细粒度权限策略，直接补 San 当前最真实的供应链和本机安全缺口。

最值得联动

把 Grok 的 goal verifier/stall detection 接到 San Goal + San Loop，完成从“自报完成”到“证据判定完成”的升级。

最值得复用思想

Agent/user hunk 归因和 compact 前 durable flush，让审阅、Supervisor 与 Context Steady 使用同一份可信证据。

不要重复建设

San 已有 plan 共审、后台 job bus、结构化 yield、更多隔离后端和多 provider；这些不是当前差距。

最终判断：有帮助，而且帮助很具体。建议把 Grok Build 当作“安全与自治运行时参考实现”，而不是新的产品路线。按价值排序，San 应先做项目信任与 sandbox，再做证据化 Goal 收口与 hunk provenance，最后才考虑 monitor/scheduler、code graph 和 worktree pool。

许可证与协作现实

不能从该快照推出什么

4. 优先借鉴项

P0 4.1 Folder Trust：先堵住项目级代码执行入口

Grok 做法：检测 repo-local MCP、LSP、hooks、plugins、envrc、Claude settings 与 agents；交互环境询问，headless 未授权即阻断；信任状态放在用户目录，使用 canonical path，父目录授权可向下继承，更具体的 child deny 优先。

San 缺口：当前 extension loading 文档明确说明项目 .san/extensions 会以 Bun module 形式进入同进程，extensions 不 sandbox。项目 MCP / Hook 也没有共同的 folder-trust verdict。这比普通 tool approval 更早发生，tool approval 无法补救恶意模块初始化。

建议合同：

  • 新增统一 ProjectTrustVerdict，在 discovery 之前计算，覆盖 extension、hook、plugin executable entry、stdio MCP、LSP 与项目环境注入。
  • 持久化文件必须位于用户配置根，永远不能从 checkout 内读取；canonicalize 查询与写入；home、filesystem root、relative path 不允许成为可继承 trust root。
  • 仅当发现 code-exec marker 时提示；headless 默认 fail closed，并提供显式 --trust-project 或预置 policy。
  • 不要复制 Grok 的“本地 build 自动关闭 trust”逻辑。开发构建应与发布构建拥有同一安全语义，测试可通过注入 store/decision seam 完成。

证据：Grok folder_trust.rs、trust.rs、San extension-loading.md。

P0 4.2 OS Sandbox：把“约束意图”升级成 kernel enforcement

Grok 做法：workspace、read-only、strict、devbox profile；macOS Seatbelt，Linux Landlock；child network 在 Linux 用 seccomp；敏感 deny path/glob 在 Linux 借 bwrap bind-over，在 macOS 转为 Seatbelt regex。

对 San 的价值：San 的 team/council、Goal、workflow 与 background tasks 会放大命令并发和执行时长。Worktree 只隔离项目副本，不阻止读取 ~/.ssh、cloud credentials 或项目外秘密；path-scope 也只覆盖经过 adapter 的工具参数。

建议合同：

  • 先定义 off | workspace | read-only | strict 四档，不先承诺复杂 custom DSL。
  • profile 在 session 建立时解析并持久化；resume 不允许静默换成更宽权限。
  • strict 与显式 profile 不能 fail open。kernel primitive、helper 或 deny path 任一无法落实时，拒绝启动该 session。
  • 应用层 approval/path-scope 继续保留：permission 决定“该不该做”，sandbox 决定“最多能做到哪里”。
  • OS primitive 适合放入 Rust/native 边界；不要用 shell string wrapper 模拟安全边界。覆盖 direct file tools、bash child、subagent 和 workflow runner 的一致性要成为验收条件。

证据：Grok sandbox guide、xai-grok-sandbox、San path-scope.ts、pi-iso。

P1 4.3 Permission Policy：借架构，不抄 matcher

Grok 将多来源规则归一到 deny > ask > allow，支持 command/path/MCP/domain pattern、危险命令、session remembered grants 与 permission mode。San 当前已有正确的 tier 基础：read < write < exec 和 per-tool allow | deny | prompt。

不能照抄的细节：Grok 文档明确说明 Bash(git *) 的 allow 对整串命令做 prefix match，因此可能允许 git status && rm -rf /；它依赖额外 deny 规则兜底。San 应从 shell AST 得到每个可执行 segment，并要求每段均满足 allow，未知构造降级为 ask/deny。
  • 复用 San 已有 ToolTier，在其上增加参数级 policy evaluator，不重写 approval wrapper。
  • bash policy 使用 pi-shell 的解析结果处理 env assignment、wrapper、pipeline、subshell、redirection 与 command substitution。
  • 路径策略对 direct tools 与 shell 文件访问使用同一 canonical/symlink 语义；安全 deny 不允许被 yolo 覆盖。
  • 保留 San hook tool-call error 的 fail-closed 行为；不要复制 Grok 文档中“hook 崩溃时继续执行”的安全语义。

证据：Grok permissions guide、San approval.ts、San hooks.md。

P1 4.4 Goal + San Loop：用独立证据决定完成

Grok 源码里最容易被忽略、但对 San 很有价值的一点：它的 Goal 不只是重复 prompt。它维护 Planning/Executing phase、不同 pause reason、planner baseline、多 skeptic 独立 scratch、verification details、gap fingerprint、连续无进展 early pause、classifier run cap 与 strategist restructure。

San 当前组合：Goal runtime 负责持久目标、token/time budget 和 continuation；goal.complete 仍由执行模型自报。San Loop 已经拥有 Commander/Worker/Supervisor/Oracle、ledger、checks 和 retry，但没有成为 Goal 的 completion gate。

推荐的 San 原生融合：

Goal objective
-- San Loop Commander / Workers execute
-- Supervisor checks observable evidence
-- Oracle only for council/high-risk mode
-- evidence verdict achieved? ---- yes --> Goal complete
-- normalized gaps unchanged twice? -----> Goal paused: no_progress
-- infra / budget / human blocker? -------> typed paused state
  • 不要新增另一套 Grok-style goal orchestrator；让 Goal 负责跨 turn 生命周期，让 San Loop 负责单轮工程执行与验证。
  • 扩展 Goal status 的 pause reason；未知 persisted status 恢复为 paused，绝不能恢复为自动执行。
  • 把 Supervisor 的 defects/evidence 规范化为 gap fingerprint；相同 gap 连续出现达到阈值时停机，而不是继续烧 token。
  • completion gate 必须消费 checks、diff/hunk evidence 与产物，不接受只读模型声明“已完成”。

证据：Grok goal_tracker.rs、goal_classifier.rs、San goals/runtime.ts、San Loop runner.ts。

P1 4.5 Hunk Provenance：建立可信变更账本

Grok 的 xai-hunk-tracker 用 actor 串行维护 baseline，接收 agent tool write 与 fs-notify external change，将每个 hunk 标成 AgentEdit(prompt_index)、ExternalEditOnAgentFile 或 External，并提供按 hunk/file/turn 的 accept/reject 与统计。

这对 San 的价值不是“多一个 diff UI”，而是形成跨模块共享的事实源：

  • Context Steady filesTouched 不再主要依赖 transcript/LLM 推断。
  • Supervisor 只审 agent 引入的 diff，不把用户并行编辑归罪于 worker。
  • Workflow isolated write 从整 patch 决策逐步升级到 hunk 级决策。
  • 多 subagent 共享 workspace 时，可以检测覆盖、交叉编辑和 stale baseline。

MVP 顺序：先做 append-only provenance ledger 和查询 API；第二阶段接 TurnDigest/Supervisor；最后再做 accept/reject UI。默认绝不自动回滚 external hunks。

证据：xai-hunk-tracker、San digest.ts、file-recorder.ts。

P1 4.6 Memory Lifecycle：加 barrier，不再造一个 memory product

Grok 的 memory 组合包括：人可读 Markdown、workspace/global/session scope、SQLite FTS5 + 可选 vec0、0.7/0.3 hybrid score、session temporal decay、可选 MMR、按时间和 session 数触发的 Dream，以及默认开启的 pre-compaction flush（距 compact threshold 4000 token，单 cycle 一次，带 exact/semantic dedup）。

San 已经有更适合自身路线的 TurnDigest/checkpoint、Brain candidate/approval/activation/projection，以及 mnemopi/hindsight。再复制 MEMORY.md + Dream 会形成第三套权威状态。

值得吸收的是 lifecycle contract：

  1. 进入 destructive compaction/history rewrite 前，等待当前 settled turn 的 digest/Brain capture 完成。
  2. 强制 flush hindsight retain queue，并在需要时追加 Context Steady checkpoint。
  3. 计算 source coverage；只有 coverage 缺口存在时才调用额外 LLM flush，避免每次 compaction 重复付费。
  4. 为 Brain/mnemopi consolidation 增加 min-hours + min-sessions gate，并可选 MMR 去冗余。

San 已有 session_before_compact hook，是合适的接入点；这个 barrier 失败时 compaction 可以按 policy 选择阻断或记录 degraded evidence，但不能静默假装 durable state 已经完整。

证据：Grok memory config、memory_flush.rs、dream.rs、San brain/capture.ts。

6. 两个有条件价值的后置项

Monitor / Scheduler

Grok 将长进程每行输出转成受速率限制的 session event，并提供最短 60 秒、最多 50 个、7 天过期的 recurring scheduler。San 可用于 CI、部署、日志观察，但必须增加 coalesce、secret filtering、line/byte budget 和 durable ownership；否则会把 Context Steady 变成日志吞吐管道。

Tree-sitter Code Graph

Grok 的 graph 支持 Rust/Go/JS/TS/Python、缓存和 fs 增量更新。San 可把它作为 LSP unavailable/slow 时的 fallback，并给 ContextPlan relevance 提供 symbol neighborhood。立项门槛应是：在无 LSP 环境下，真实任务的 tool turns 或 time-to-first-definition 显著下降。

8. 最小验收清单

安全

  • clone 一个带恶意 project extension/hook/MCP 的 fixture，未授权时没有进程、网络或模块初始化副作用。
  • strict profile 下验证项目外 secret 的 direct read、shell read、rename-then-read、symlink read 全部失败。
  • resume/fork/subagent/workflow 保持或收紧原 profile，不发生 silent widening。

证据与自治

  • agent 与用户在同文件交错修改，ledger 能稳定归因到 turn/actor，Supervisor 只审 agent hunks。
  • Goal 模型声称完成但 check 失败时不能终止；修复后 evidence verdict 才能完成。
  • 两轮相同 verifier gaps 自动进入 no_progress pause，并保留可恢复证据。

Context / Memory

  • compaction 前最后 settled turn 的 digest/capture/retain queue 均已 durable，或明确记录 degraded reason。
  • compaction 后 ContextPlan 可引用同一 evidence；额外 LLM flush 只在 coverage gap 时触发。
  • consolidation 有节流、冲突/重复指标和可回滚记录。

非回归

  • 现有 plan review、AsyncJobManager、task yield、San Loop 和 workflow exactly-once 合同不被替换。
  • pi-iso 继续作为 workspace isolation PAL；sandbox 是额外 capability boundary。
  • 多 provider/model routing 与 Context Steady wire shape 保持独立。

10. 决策结论

Grok Build 能帮助 San，但不是通过“搬功能”。

San 现在最需要的，是把已经很强的 Context/Loop/Brain/Workflow 语义，放进一个更可信的执行外壳：项目代码先经过 trust gate，工具受 permission policy 与 OS sandbox 双重约束，文件修改有 actor/turn provenance，Goal 的完成由独立 evidence verifier 判定，compaction 前有 durable barrier。

这些机制一旦补齐，San 的差异化会更清楚：Grok 强在通用 harness 完成度；San 强在上下文稳态与可审计执行语义。San 应吸收前者的边界工程，让后者真正能长期、安全地跑。

本报告未修改产品代码，也未运行 Grok Build 的完整 workspace test suite。已完成 git clone、固定 commit、Cargo metadata 解析、关键源码/用户文档交叉核对，以及 San 当前实现逐项对照。
