接渠道，还是做独立 Web 站？

对 OpenClaw 与 Harness（Tencent Cloud）做了一手核实，再对照 San 仓库现有代码判断。结论是这个问题问错了方向：两家的"渠道接入"都不是通知层，而是完整交互面；但两家的执行模型都和你"两台电脑 + 一只手机"的场景不同。San 的正确形态既不是纯渠道插件，也不是又一个 Web 站。

结论

IM 渠道和 Web 控制台解决不同粒度的问题，San 该做的是第三件事：多主机控制面。

OpenClaw 和 Harness 的渠道接入都被证实是完整交互面（历史、审批、媒体、reply context 全在协议里），不是通知层——所以"接渠道 = 轻量、Web 站 = 重量"这个直觉不成立。但两家的 agent 都跑在 gateway 主机上：一个 Gateway 进程拥有所有会话与执行。你的场景是执行环境分布在公司电脑和家里电脑，控制权跟着人走，这与 gateway-owns-agent 模型正交。

San 已经有控制面所需的三件套（ACP server、RPC v2、E2EE collab relay + 浏览器客户端），缺的是常驻 runner、多主机注册、离线排队和推送。先补这四样；Web 控制台是它的第一个消费者；IM 渠道是之后挂在 relay 上的一个薄适配器，而不是让每台电脑各自连飞书。

OpenClaw 的"渠道"实际承担什么 一手核实

结论先说：渠道是完整交互面，不是通知层。判断依据是它的协议面而不是宣传语。

架构事实

  • 单一常驻 Gateway 进程拥有所有消息面（WhatsApp/Telegram/Slack/Discord/Signal/iMessage/WebChat），并且"one Gateway per host"。
  • 控制面客户端（macOS app、CLI、Web Control UI、自动化）通过 WebSocket 连 Gateway，默认 127.0.0.1:18789。
  • 渠道目录里有 30+ 个条目，绝大多数是 official plugin 按需装，核心只内置 Telegram、Reef 和 WebChat。飞书、WeCom、微信、元宝都在插件层，其中微信和 WeCom 还是 external plugin。

为什么说它是完整交互面

WebChat 用的 RPC 方法是 chat.history / chat.send / chat.inject / chat.message.get——这套东西的复杂度已经说明问题：

  • chat.history 有有界化逻辑：超长文本截断、重负载元数据剔除、超大条目替换为占位串，客户端可按请求传 maxChars 覆盖；"Show more" 再走 chat.message.get 单条补全。
  • 有分支语义：history 跟随 active transcript branch，chat.send 带 expectedLeafEntryId 做乐观并发校验，别的客户端切了分支就把消息 park 住而不是写到错分支。
  • 有幂等键：chat.send 带 idempotency key，重试不会产生第二个 run。
  • 有reply context 注入：右键 Reply 把目标 transcript id 作为 replyToId 送上去，Gateway 解析出与 Discord 同构的、标注为 untrusted 的 reply 上下文块给 agent。
  • 有显示归一化：剥掉 runtime-only 上下文、inbound 信封、[[reply_to_current]] 一类投递指令、泄漏的 tool-call XML 和模型控制 token；NO_REPLY 整条丢弃；isReasoning 载荷不作为可见回复。
  • 有双数据路径的明确划分：SQLite transcript 是持久模型日志，Gateway 的 ReplyPayload 事件是投递投影，两者不等同。
通知层不需要分支冲突检测、幂等键和 reply context 注入。这套东西的形状说明 OpenClaw 把 IM 当作与本地 UI 平权的一等交互面。

它怎么跨机器

  • Node 是外设，不是 gateway：nodes 显式声明 role: "node"，暴露 canvas.* / camera.* / system.* 命令，靠设备签名 + pairing 审批接入。文档原话是 "Nodes are peripherals, not gateways"，渠道消息只落在 gateway 上。
  • 要在另一台机器执行命令，用 remote node host：模型仍然和 gateway 说话，gateway 在 host=node 时把 exec 转发到 node host。审批存在 node 本机的 SQLite（exec_approvals_config），走 per-node allowlist。
  • Gateway 默认 bind loopback，远程 node 要 SSH 隧道或 Tailscale 才连得上。
关键差异：OpenClaw 是"一个大脑（gateway）+ 多个手脚（node）"。跨机器共享的是执行，不是会话所有权。你的场景恰恰相反——公司电脑和家里电脑各自有完整的、正在跑的、带本机凭据和内网的会话，你要的是控制权漫游。

它对 agent runtime 的态度值得抄

OpenClaw 把 agent runtime 抽象成可插拔后端：内置 openclaw harness、Codex app-server harness（embedded 插件），以及通过 ACP/acpx 接入的一整排外部 harness——claude、codex、copilot、cursor、droid、gemini、kimi、kiro、opencode、qwen、pi…… 还有 openclaw 自己的 ACP bridge。

这是对 San 最实际的一条情报：San 已经有 san acp（src/commands/acp.ts，--mode acp）。也就是说 San 今天就能作为 acpx 的一个自定义 agent 被 OpenClaw 驱动——通过 plugins.entries.acpx.config.agents.<id>.command 指向 san acp。"接入渠道"这件事的最低成本路径不是自己写飞书适配器，而是让别人的 gateway 来调 San。

Harness 栈实际承担什么 一手核实

先纠正一个容易混的命名：Harness 不是一个产品，是 Tencent Cloud 的一组库，组装成品叫 Octop。

组件PyPI / 仓库职责
harness-agentorcakit-harness-agent 0.9.18agent runtime，本质是 LangChain Deep Agents 的生产化封装——最终委托给 deepagents.create_deep_agent
harness-gatewayharness-gateway 0.8.8多平台 IM 桥，9 个渠道：飞书、钉钉、QQ、WeCom、微信 iLink、元宝、小艺、MQTT、Telegram
harness-memoryTencentCloud/harness-memory分层记忆 L0 原始事件 → L2 atom → L3 实体页
harness-browserTencentCloud/harness-browserCDP 浏览器自动化
OctopTencentCloud/Octop把上面四个组装成单进程自托管助手：FastAPI + React 控制台 + CLI + IM + cron，单一 SQLite ~/.octop/octop.db

它的渠道抽象

核心契约极简：你的处理器是一个 Callable[[InboundMessage], AsyncIterator[MessageEvent]]。MessageEvent 分 MESSAGE（整条）/ DELTA（token 流）/ COMPLETED（flush）。ChannelManager 负责 async 队列、每渠道 worker 池、媒体后端（MediaBackend）、约束（限流 / 超时 / 正在输入指示）和主动推送（push_text / push_content / push_to_all）。多租户靠 channel_id 隔离，同一种渠道可以跑多个实例。

这层抽象比 OpenClaw 薄得多，但也是完整交互面：有 token 流、有媒体、有 typing 指示、有主动推送。它同样不是通知层。

它的执行模型

  • Octop 明确是单进程：dashboard、CLI、IM、cron 全在一个进程里，状态从 ~/.octop/octop.db 重建，重启安全。
  • 组装根是 OctopServer.start()，顺序拉起 SharedServices → ExpertCatalog → AgentManager（每个 agent 一套 HarnessAgentRuntime + GlobalProcessor + BackendWorkspace）→ Gateway → CronManager → UserManager。
  • 跨机器能力靠 pluggable backend 换工作区（本地盘 / S3 / COS / PostgreSQL），而不是靠多主机 runner。
  • 它也有 ACP：acp/ 目录提供 stdio ACP server，让 IDE / 终端 AI 来驱动它——方向是"被别人调"，和 OpenClaw 的"调别人"互补。
关键差异：Octop 是"一台机器上的全能助手"。它连"多主机"这个问题都没进入视野——单进程 + 单 SQLite 是它的显式设计目标。你的两台电脑在这个模型下只能各跑一个互不知情的 Octop。

顺带一个判断

harness-agent 自述是 Deep Agents 的 façade，这意味着它的差异化不在 loop 和上下文，在工程外围（模型路由、17 个服务商预设、记忆、存储后端、安全策略、CLI）。这恰好是 San 的镜像：San 的差异化在 loop 和上下文工程，外围反而靠 omp 基座。两者不构成正面竞争。

San 现有底座：控制面已经有三分之二 仓库核实

在决定"接渠道还是做 Web 站"之前，先看清 San 手里已有什么。以下都是仓库里跑得通的东西，不是计划。

1 · Collab：E2EE 实时会话共享 + 浏览器客户端

/collab 已经做到了"手机看电脑上的会话"的雏形：AES-256-GCM 全载荷加密，relay 只看到 room id、连接数、密文帧大小和 4 字节路由前缀。packages/collab-web 是独立浏览器客户端，guest 端不需要装 San，relay 在 / 直接托管它，链接即点即入。

2 · 权限模型已经分级

full link（48 字节：32 字节房间密钥 + 16 字节 write token）可 prompt / 打断 / 操作 Agent Hub；view-only link（裸 32 字节）只读。host 在 join 时校验 write token。变更宿主机的一切（/model、/compact、bash、python）是 host-only。

3 · Relay 已经是 content-blind 的可自托管服务

一个小 Go 服务，除活跃连接外无状态：GET / 托管 web 客户端、GET /r/<roomId>?role=host|guest 升级 WebSocket、POST /s + GET /s/<id> 做 /share、GET /healthz。这就是 Relay 方案的现成骨架。

4 · RPC v2：JSON-RPC 2.0 控制协议

src/modes/rpc-v2/ 已有 envelope / errors / capability / ids、按域分文件的 methods、event catalog、Session / Run / Approval / Context / Evidence DTO、session-manager 的 lease 与 sync，以及 crash-recovery.ts 的 lease + recovery 文件（跟随 session 文件而非源码目录）、backpressure-writer.ts 的有界按序 NDJSON writer 和 stdout 纯净守卫。

5 · ACP server 已就绪

san acp / --mode acp 已实现：session/new 工厂、client bridge、event mapper、elicitation 桥接（skill/extension UI → ACP elicitation）、编辑工具的 diff metadata、acp-bridge 写穿透。这让 San 可以被任何 ACP 客户端驱动，包括 OpenClaw 的 acpx。

6 · Hub 拓扑已经是 host 权威

guest 从不互联；entry（持久条目，在 blob 外化前广播，图片保持内联）、event（活事件，仅事件渲染防双渲染）、state（去抖 footer 快照，含 host 完整 model 对象与 thinking level）、bus（子 agent 生命周期）、agents（注册表快照）。guest→host 只有 hello/prompt/abort/agent-cmd/fetch-transcript。

缺什么

能力现状差距

多主机注册与发现缺relay 只有 room 概念，没有"我有哪几台机器、哪台在线、各自在跑什么"的注册表。
离线排队缺relay 显式无状态（除活跃连接）。机器离线时派发的任务会丢，不会等它上线。

六项缺口里，只有最后一项是"渠道"问题。前五项无论你接不接飞书都必须做，而且做完之后接渠道是薄薄一层。这就是为什么"接渠道 vs 独立 Web 站"是个伪二选一。

判断：分层，不二选一

先把问题重新定义

你真正的约束是三条，两家的方案都不同时满足：

  1. 执行必须在原机。公司代码、内网、凭据、已有 worktree 都在公司电脑上；家里电脑有自己的项目。这不是"选一台跑 gateway"能解决的。
  2. 控制权跟人走。在公司用公司电脑的 TUI，回家用家里电脑，路上用手机。同一个会话要能被不同前端接管。
  3. 手机上要的是低带宽介入：看到卡在哪、批一个审批、发一句纠偏。不是在手机上读 diff。

三层结构

为什么不是"接飞书就完事"

让两台电脑各自连飞书，你会得到两个互不知情的机器人，在同一个群里抢答，且无法回答"哪台在跑什么"。渠道解决触达，不解决编排。而且飞书是公司的 IM——把家里电脑的会话推进公司飞书，边界不干净。

为什么不是"做个 Web 站"

Web 站给不了推送。任务卡在审批上，你不会主动去刷网页。而且 packages/collab-web 已经是 Web 客户端了——真正缺的不是页面，是页面背后的常驻 runner 和主机注册表。再起一个站是在缺口上盖房子。

为什么 relay 是正确的枢纽

它已经 content-blind、已经自托管、已经有 room 语义和 E2EE 帧格式。加"主机注册 + 离线队列"是扩展现有服务，不是新架构。而且 relay 天然是唯一知道"所有机器"的地方——渠道适配器挂在这里，一个适配器覆盖所有主机。

渠道适配器该挂在哪

挂 relay 侧，不挂每台电脑。这样：单点配置、单个机器人身份、天然跨主机路由、E2EE 边界清晰（适配器需要明文，所以它必须是你自己的可信组件，而不是公共 relay 的一部分——这点必须显式设计）。

必须正面处理的矛盾：现有 relay 的核心卖点是 content-blind——它看不到明文。但 IM 适配器要把内容渲染成飞书消息，必须拿到明文。这意味着渠道适配器不能是 relay 的一个 handler，而应该是一个持有房间密钥的特权 guest 进程，跑在你信任的机器上（比如那台腾讯云服务器）。这样 relay 保持零知识，明文只在你自己的 bridge 里。这个设计约束不解决，"在 relay 上接渠道"就是把 E2EE 白送掉。

与 ACP 的关系

San 已有的 ACP server 提供一条零成本的过渡路径：现在就可以把 san acp 注册进 OpenClaw 的 acpx，用别人成熟的 gateway 和 30+ 渠道，验证"手机介入"这个需求到底值多少。代价是执行落在 OpenClaw gateway 所在的那台机器上——恰好不满足约束 1，所以它只能是需求验证工具，不是终态。

先花一天用 acpx 挂上去试，比先花两周写飞书适配器更能回答"这个功能我到底会不会用"。

落地顺序

按"每一步单独可用"排序，不做大爆炸式改造。

#动作触碰单独交付的价值
0 用 acpx 把 san acp 挂进 OpenClaw，从手机上真用几天 零改动（配置） 用真实使用回答"手机介入值不值得投入"，避免凭想象造功能
1 san runner：常驻、无人值守、开机自启，启动即向 relay 注册 {hostId, label, 能力, 当前会话列表} 新命令 + relay 注册表 两台电脑第一次能被同时看见。此时用现有 collab-web 就能远程接管，无需任何渠道
2 relay 加主机注册表 + 心跳 + 离线任务队列（仍不解密，队列存密文信封） relay/ 公司电脑关机时派活，开机自动接手
3 扩 collab-web 成多主机控制台：主机列表 / 会话列表 / 审批队列 / 单句纠偏 packages/collab-web 手机浏览器就是控制台。这一步之后 Web 站需求已经被满足，不需要新项目
4 推送：审批阻塞 / 任务完成事件出队 → Web Push 或直接进第 5 步 relay + web client 不用主动刷
5 san bridge：持房间密钥的特权 guest，跑在腾讯云那台机器上，把明文渲染进 IM 新包 渠道接入。此时它只是一个 guest 客户端，不改动 relay 的零知识属性
6 第一个渠道选个人可控的（Telegram / 自建 Bot），而非公司飞书 san bridge 插件 先验证协议形状，避开公司数据边界问题
0 和 1 就能解决你 80% 的痛点，且第 1 步不依赖任何渠道决策。真正需要"选路线"的决策被推迟到第 5 步，那时你已经有真实使用数据。

协议形状可以直接抄的部分

  • 抄 OpenClaw 的 chat.history 有界化：手机端带宽和渲染都受限，maxChars + 占位替换 + 单条按需补全这套三段式是被验证过的解法，比"传全量再前端截断"正确。
  • 抄乐观并发校验：expectedLeafEntryId 解决的问题（多客户端 + 分支切换）在 San 的多主机场景里更严重。San 的 RPC v2 已有 lease，把它和"预期叶节点"合并考虑。
  • 抄 Harness 的处理器契约：Callable[[Inbound], AsyncIterator[Event]] + MESSAGE/DELTA/COMPLETED 三态。San 的 bridge 插件接口用这个形状，写新渠道就是几十行。
  • 抄 node pairing 的设备签名 + 审批：runner 自注册必须有身份校验，否则 relay 上任何人都能声称自己是"公司电脑"。

风险与反对意见

最大风险：E2EE 与渠道渲染的根本冲突。上面用"特权 guest bridge"绕开了，但代价是多一个必须长期在线、持有密钥的组件。如果那台腾讯云服务器被攻破，攻击者拿到的是明文会话流。若不能接受，替代方案是渠道只推不含内容的通知（"会话 X 卡在审批"），点链接跳 Web 控制台看明文——牺牲便利换零明文外泄。这是个真实的取舍，必须显式决定。
常驻 runner 的安全面。一个开机自启、能被远程派活执行 bash 的进程，等于把两台电脑变成远程执行端点。必须：默认拒绝、per-host allowlist、审批留在本机（照抄 OpenClaw 把 exec_approvals_config 存在 node 本机 SQLite 的做法）、relay 绝不能有绕过审批的通路。
公司设备边界。公司电脑跑一个常驻远程可控进程，可能违反公司 IT 政策。这是非技术阻塞项，值得先确认再动手第 1 步。
"直接用 OpenClaw 就好了"这个反对意见部分成立。如果你能接受把执行集中到一台机器（比如腾讯云服务器上跑 gateway，两台电脑当 node），OpenClaw 今天就能满足你，还白送 30+ 渠道。它不成立的地方只有一处：node 是外设，跑不了"公司电脑上那个已经有完整 worktree 和内网访问的会话"。如果这个约束其实可以放松，那第 1–5 步都不用做。这个前提值得你自己再确认一遍。
规模现实：这是一人用的系统。第 2 步的离线队列不要做成消息中间件，SQLite 一张表足够。第 3 步不要引入前端框架，现有 collab-web 的形态就够。任何"为了以后扩展"的抽象在这个规模下都是净负债。

  • OpenClaw — 官方文档与仓库：gateway 单进程 / 一主机一 gateway、控制面 WebSocket 127.0.0.1:18789、渠道目录 30+（核心内置仅 Telegram / Reef / WebChat，飞书 WeCom 微信 元宝为插件，微信与 WeCom 为 external）、chat.history/chat.send/chat.inject/chat.message.get 四方法及其有界化、分支 expectedLeafEntryId、idempotency key、replyToId untrusted reply 块、显示归一化与 NO_REPLY、SQLite transcript 与 ReplyPayload 双路径、node "peripherals, not gateways" 与 canvas.*/camera.*/system.*、remote node host 的 host=node exec 转发与 exec_approvals_config 本机审批、loopback 默认绑定、agent runtime 插件化与 acpx 支持的 harness 列表及 plugins.entries.acpx.config.agents.<id>.command。
  • Harness / Octop（Tencent Cloud） — orcakit-harness-agent 0.9.18 委托 deepagents.create_deep_agent；harness-gateway 0.8.8 支持飞书 / 钉钉 / QQ / WeCom / 微信 iLink / 元宝 / 小艺 / MQTT / Telegram；处理器契约 Callable[[InboundMessage], AsyncIterator[MessageEvent]] 与 MESSAGE/DELTA/COMPLETED；ChannelManager 的队列 / worker 池 / MediaBackend / 限流超时 typing / push_text push_content push_to_all / channel_id 多租户；harness-memory 的 L0→L2→L3 分层；harness-browser 走 CDP；Octop 单进程 + ~/.octop/octop.db、OctopServer.start() 组装顺序、pluggable backend（本地 / S3 / COS / PostgreSQL）、acp/ stdio ACP server。

仓库核实（San）

  • src/commands/acp.ts 与 --mode acp：ACP session/new 工厂、client bridge、event mapper、elicitation 桥、编辑工具 diff metadata、acp-bridge 写穿透。
  • src/modes/rpc-v2/：envelope / errors / capability / ids、按域 methods、event catalog、Session / Run / Approval / Context / Evidence DTO、session-manager lease 与 sync、crash-recovery.ts、backpressure-writer.ts（有界按序 NDJSON + stdout 纯净守卫）。
  • Collab：AES-256-GCM 全载荷加密；relay 仅见 room id / 连接数 / 帧大小 / 4 字节路由前缀；full link 48 字节（32 房间密钥 + 16 write token）vs view-only 32 字节；host 校验 write token；/model /compact bash python 为 host-only；hub 消息 entry/event/state/bus/agents，guest→host 仅 hello/prompt/abort/agent-cmd/fetch-transcript。
  • packages/collab-web：独立浏览器 guest 客户端，由 relay 在 / 托管，guest 无需安装 San。
  • Relay 端点：GET /、GET /r/<roomId>?role=host|guest、POST /s、GET /s/<id>、GET /healthz；除活跃连接外无状态。
