Agent Harness 的收敛方向

OMP 的 Rust 迁移、Pi Harness v2/v3、Maka Runtime Host，以及 San 的下一阶段边界

2026-08-27 · 面向后续架构决策的内部研究记录

核心判断：oh-my-pi 以性能为入口进行 Rust 化，但会同时改变底层架构；Pi 的 harness-v2 没有被废弃，而是经过 effects variant 和 v3 收敛后并入当前 harness.md；Pi、Maka、San 最终靠近数据库和操作系统的 durable execution 原则，是长时间运行 agent 在崩溃、并发、外部副作用和上下文限制下的约束趋同。

1. 证据范围与结论等级

本记录优先采用仓库、提交、官方架构文档和当前本地源码。社区讨论用于发现问题，不作为架构事实的唯一依据。

等级含义本记录中的典型内容
已观察可由官方仓库、提交或本地源码直接确认。OMP 主仓库同时包含 TypeScript 与 Rust；Pi 的 v2 文档被提交删除并由当前规格取代；Maka Runtime Host 的单写者和 State Root。
推断基于事实和工程约束作出的方向判断，不伪装成维护者公开承诺。OMP2 的深层目标会进一步形成 Rust runtime/core；三个项目的架构相似主要来自约束趋同；San 应先稳定 durable semantics，再选择性 Rust 化。
建议面向 San 的设计选择。采用“不可变事实 + 当前状态寄存器 + 外部效果边界 + 上下文/UI 投影”的混合模型。
不应混淆的三条线Pi upstream 的 Rust issue #4609 是已关闭的玩笑 issue；oh-my-pi 的 omp2 是现实中的 TypeScript-to-Rust 迁移线；Pi 当前真正明确推进的是 durable harness/storage/recovery 规格。

2. OMP 的 Rust 重写：性能入口，架构结果

oh-my-pi 官方 README 仍把自己定位为 Pi 的 fork，但已公开展示约 80k 行 Rust core，并列出 Rust 侧的 shell、AST、walker、隔离等基础能力。主仓库的顶层产品仍不是纯 Rust 应用，而是 TypeScript 产品层与 Rust native core 的组合。

已观察 本地 San 仓库也已经存在相近的 native 基础设施：crates/pi-walker 提供带缓存和 heartbeat 的目录扫描，crates/pi-natives 提供 N-API AST 查询，crates/pi-iso 提供 APFS、overlay、reflink、ProjFS、git worktree 和递归复制等隔离后端，另有 pi-shell 与 vendored shell utilities。

重写层次被替换的成本带来的能力
文件与代码热点JS 对象、字符串复制、GC、逐文件调用和部分 fork/exec更低的 grep/glob/AST/walker 延迟，更稳定的内存行为
执行基础设施外部 shell、PTY、隔离和路径处理的多层胶水进程内 shell、统一资源生命周期、更细的并发控制
runtime 边界产品逻辑和系统能力互相穿透Rust core 负责机制，TypeScript 负责产品、策略和扩展
Rust 适合解决大仓库扫描、AST、shell/PTY、路径和字节处理、快照/哈希、隔离、并发本地任务。
Rust 不会自动解决模型延迟、上下文膨胀、compaction 质量、agent 语义循环、provider 错误恢复和不可回滚的外部副作用。

推断 OMP2 的深层目标不是把 TypeScript 文件机械翻译成 Rust，而是把原先由 Bun/TypeScript 承担的系统级热路径和资源生命周期下沉到 native runtime。它会让 OMP 与 Pi 在源代码组织和内部 API 上越来越远，但不必然改变 prompt → model → tools → continuation 这层用户可理解的基本模型。

性能重写的边界：如果瓶颈是模型规划或 prompt token 数，换 Rust 不会改变账单和上下文上限；如果瓶颈是本地工具链和大仓库扫描，Rust 才有直接收益。必须按阶段测量，而不是把“Rust”当作端到端性能保证。

3. Pi Harness v2 没有消失，而是被收敛

你找不到当前 main 上的 harness-v2.md，原因是它已经被后续规格吸收并删除。历史演进如下：

2026-07-29 · 4f0437e加入 Durable AgentHarness design v2建立 session tree、lanes、operation logs、global facts，以及“intent → effect → result”的耐久执行模型。
2026-08-03 · a0014c1选择 effects variant 并完成 v2 设计收敛补充 deferred provider、usage ledger、overflow、abort、hook durability 和恢复规则。
2026-08-11 · 85a2060删除旧 v2 文档，harness-v3.md 重命名为 harness.md文件名去掉版本号，当前主线规格继续承载前面验证过的核心不变量。

从 v2 operation log 到当前 hybrid state model

早期 v2 的重点

每条 lane 有独立 operation log，记录：

operation_started
  → task_attempt
  → tool_started (provisioned result id)
  → external effect
  → result entry
  → operation_finished

恢复逻辑读取未完成的 intent，决定重试、安全 replay、生成 interrupted result 或等待 deferred handle。

当前 harness.md 的重点

持久化分成三类：

entries       不可变 conversation tree
registers     当前可变状态
usage ledger  成本和 token 账本

操作的完整当前状态写入类似 op.state/{operationId} 的 register；context 和 UI 从 canonical state 重新投影。

保留下来的核心接受操作必须先 durable；外部效果前先写意图；结果必须可结算；每条 lane 至多一个未完成 operation；UI stream 不是恢复权威；context 只在尾部增长，compaction 是显式例外。
发生变化的实现模型 当前规格不是纯 event sourcing。对话和 usage 适合 append-only；operation current state 适合 materialized register。恢复不是无条件重放所有历史副作用，而是读取状态并从明确的 effect boundary 继续收敛。

外部副作用是 durable harness 最难的地方

以下流程仍然存在不确定窗口：

commit: “准备调用工具 X，结果使用 R”
        ↓
execute X
        ↓ 进程可能在此处崩溃；X 可能已经成功
commit: “R 的结果为 Y，operation 进入下一状态”

因此工具需要明确 replay policy：

  • safe：恢复时可以用持久化参数重新执行，例如只读查询。
  • never：不能安全重复执行，例如删除文件、发送消息、写入外部系统；恢复时可以写入合成的 interrupted result。
  • idempotent：外部系统以 operation id 或幂等键去重，但这依赖外部系统配合。
没有 XA 事务银弹 数据库可以保证自己的 commit 一致，但不能让模型 provider、邮件服务、shell、文件系统和数据库写入共享同一个可回滚事务。正确目标是“可识别、可恢复、可结算”，不是虚假的 exactly-once。

5. Maka：同一组不变量，重点不同

Maka 官方的 Runtime Host 架构把 Host 作为长期运行的唯一执行权威：一个 State Root 只有一个写者；Desktop、TUI、CLI、bots 是 Clients；客户端断开不会取消已接受的 work；Durable Stores 是恢复依据；provider 调用前先持久化 Run Composition；Session Continuity 向客户端提供 snapshot 和有界 live updates。

持久化entries、registers、usage、operation stateDurable Stores + Runtime factscanonical facts 与派生投影分离

模型边界context projection、compaction、deferred providerRun Composer 冻结模型可见 basisprovider 前冻结 prompt/tool basis
多任务lanes 和 operationSession、Turn、Run、root execution把 operation admission、cleanup、settlement 分开

推断 “Pi 和 Maka 几乎相同”在不变量层面成立，在实现和产品重点层面不成立：Pi 更关注 coding agent 的 conversation tree、lane、context 和 compaction；Maka 更关注 Runtime Host、State Root、多客户端、远程连接和生命周期 ownership。两者可以互相验证，但不应直接复制对方的全部 API。

“Maka 的核心作者来自数据库背景”没有从官方仓库和架构文档中核实到，因此不作为本记录的事实依据。相似架构本身已经足以说明问题。

6. 扩展系统与源码二开：两条互补的分发路径

社区对 Pi Package Catalog 扩展“大而全、难组合”的批评有现实基础，但它说明的是扩展颗粒度和接口设计问题，不是“插件系统没有价值”。

变化类型最合适的路径原因
新增外部能力或 APIMCP Tool能力边界清晰，独立进程和协议适合组合。
新增工作规约和知识Skill低耦合、可项目级或用户级覆盖。
新增稳定命令或局部 UI可选 Plugin不需要 fork 核心即可复用。
改变调度、持久化、恢复、上下文、权限源码二开 / fork这些是架构边界，插件 API 无法完整表达。
改变 grep、AST、shell、snapshot 等基础设施native core / Rust需要控制资源、内存和系统调用，而不是增加 hook。
源码二开的优势模型可以直接处理上下游合并、删除重复实现、裁剪冗余文件、迁移调用者和新增跨边界能力。用户拥有最终源码，而不是被预设 API 限制。
源码二开的代价模型可以解决文本冲突，却不能保证语义冲突已经正确解决。需要类型检查、行为测试、恢复测试和持续的 upstream rebase。

shadcn/ui 类比的适用范围

shadcn/ui 适合被复制和拥有，是因为组件是相对独立的 leaf。durable harness 核心不是 leaf：它包含 session schema、operation state、effect settlement、usage ledger、migration 和恢复不变量。

推断 Agent 软件更可能形成三层分发：

核心运行时：源码拥有 / fork / patch queue
能力模块：Skills / MCP / optional extensions
产品表面：可复制 UI、模板、preset

你给出的 rerere、zdiff3、fetch.prune 等配置非常适合作为源码所有权工作流的基础设施。它们降低维护成本，但不替代测试和人工审查。

7. Pi-rewind：工作区回滚和 harness 恢复要分开

全仓库 checkpoint 在大型 monorepo 上带来扫描、复制和磁盘成本；只备份 Edit/Write 触碰的文件把成本从“整个仓库”降低到“本次修改集合”，更适合交互式 coding agent。

机制负责什么不负责什么
Edit/Write preimage snapshot撤销模型通过编辑工具产生的文件变化Bash、生成器、chmod、symlink、数据库和网络副作用
Full workspace snapshot更完整的工作区回滚成本、空间和大仓库性能问题
Durable harness恢复 operation、tool result、session 和上下文状态让外部副作用自动回滚

建议把产品语义拆成三档，而不是让一个 /checkpoint 同时承担全部责任：

  1. Edit-safe checkpoint：默认保护 Edit/Write 触碰的文件，快且适合日常。
  2. Full workspace checkpoint：通过 overlay、工作树或全量快照保护更大范围，作为专家模式。
  3. Durable run recovery：保证 session 和 operation 不损坏，工具按 replay policy 恢复，不虚假承诺文件回滚。

8. San 的未来方向

San 不需要在“跟随 OMP Rust rewrite”和“坚持自己的方向”之间二选一。两者位于不同轴线上：

  • OMP 的优势轴：native toolchain、系统调用、扫描、shell、AST、隔离和本地并发。
  • San 的优势轴：Context Steady、compaction、continuation、execution-control、brain/memory、模型路由和长期任务可靠性。

推断 从本地源码形态看，San 当前真正需要降低的风险是语义边界集中在 AgentSession 周围，而不是缺少 Rust。packages/agent/src/agent-loop.ts、append-only-context.ts、replay-policy.ts、compaction 目录，以及 packages/coding-agent/src/session、context-steady、execution-control、task、brain 之间已经形成丰富能力；下一步应把这些能力的 ownership 和 durable boundary 变得清晰。

建议推进顺序

  1. 先固定 durable semantics明确 canonical facts、operation state、effect intent、settlement、abort、replay policy 和 deferred provider 的行为契约。
  2. 再拆 AgentSession 的 ownership让 session persistence、operation reduction、context projection、UI events 和 effect execution 不再互相持有隐式状态。
  3. 把 Context Steady 接到 durable operation 边界在 provider 前做 bounded context plan；overflow、compaction、discard 和 retry 必须有明确的收敛终点。
  4. 把 Skills/MCP/Plugin 限定为能力适配层允许扩展工具和知识，不让扩展通过大量全局 hook 重新接管核心状态机。
  5. 按 profile 选择性 Rust 化先测量 walker、grep、AST、shell、PTY、snapshot/hashing 等热点；只有 profiling 证明收益时才扩大 Rust 边界。
  6. 最后建立源码分发维护流官方基线、个人 fork、patch queue、rerere、语义迁移检查和恢复 smoke test 一起构成可持续工作流。
最终路线San 自己定义 durable semantics；吸收 Pi/Maka 的恢复不变量；吸收 OMP 的 native hot paths；保留 Skills/MCP/Plugin 作为可选能力层；允许用户通过源码 fork 拥有自己的 agent。
