预算坍缩与 Model Reload 熔断修复方案

同一 AgentSession 内 model reload 导致上下文窗口热缩小，旧 ContextPlan 仍按原预算运行， 下一次 Tool-Loop provider call 被新 hard ceiling 直接拦截且无恢复路径。 本方案从预算一致性、模型热变更、受限恢复三层修复。

1. 根因分析

1.1 预算坍缩（Budget Collapse）

resolveContextPlanBudget 的推导链： 

hardInputCeiling = contextWindow − max(32K, contextWindow × reserveRatio)
steadyTarget     = min(configuredSteady=240K, hardInputCeiling)
burstCeiling     = min(max(configuredBurst=320K, steadyTarget), hardInputCeiling)
controlMax       = min(burstCeiling, steadyTarget × 13/12)

当 hardInputCeiling < 240K（例如 256K 模型 × 20% reserve → 204.8K）， steady / control / burst 三者全部重合到 hardInputCeiling， 失去 control→burst 缓冲区。任何超出该值的投影输入直接判定 hard_pressure。

1.2 Mid-Run 维护阈值与 Gate 分裂

#maintainContextMidRun 使用独立的阈值公式： 

contextSteadyTarget = min(contextWindow, configuredSteadyTarget || 240K, burstWindowTokens)

该公式不经过 resolveContextPlanBudget，不考虑 hardInputCeiling。 256K 模型下维护目标 = 240K，但 ContextPlan gate 在 204.8K 就熔断。 Gate 先于维护触发，维护永远来不及运行。

1.3 Model Reload 不失效 ContextPlan

#setModelWithProviderSessionReset 只重置 provider session 和 append-only context， 不触碰 #contextSteadyRequestPlan。虽然 #contextSteadyPlanInputsChanged 能检测 contextWindow 变化并触发重建， 但重建后若命中 hard_pressure，直接 throw 暂停整个 tool-loop，无恢复路径。

事故链：model reload → 窗口缩小 → 旧 plan 失效 → 重建 plan → 预算坍缩（steady=burst=control=204.8K）→ 当前输入 > 204.8K → hard_pressure → 无恢复 → 暂停，需要用户消息才能解套。

2. 修复方案（三层）

Layer 1 — Model 变更时失效 ContextPlan 预算

agent-session.ts

在 #setModelWithProviderSessionReset 中增加：

  • 比较旧、新模型的 contextWindow。
  • 若窗口缩小，将 #contextSteadyRequestPlan 置为 undefined（强制下次 provider call 重建）。
  • 设置 #contextSteadyPendingBudgetPressureRebase = true，使重建时走 rebase 路径（带 checkpoint 物化）而非直接熔断。
  • 递增 #contextSteadyRecoveryAttempt = 0（重置恢复计数器，给新窗口一次完整恢复机会）。
#setModelWithProviderSessionReset(model: Model): void {
  const currentModel = this.model;
  if (currentModel) {
    this.#closeProviderSessionsForModelSwitch(currentModel, model);
    if (!modelsAreEqual(currentModel, model)) {
      this.#clearInheritedProviderPromptCacheKey();
    }
    // ── NEW: invalidate context-steady budget on window shrink ──
    const oldWindow = currentModel.contextWindow ?? 0;
    const newWindow = model.contextWindow ?? 0;
    if (oldWindow > 0 && newWindow > 0 && newWindow < oldWindow) {
      this.#contextSteadyRequestPlan = undefined;
      this.#contextSteadyPendingBudgetPressureRebase = true;
      this.#contextSteadyRecoveryAttempt = 0;
    }
  }
  this.agent.setModel(model);
  this.#syncAppendOnlyContext(model);
}

Layer 2 — 统一 Mid-Run 维护阈值到 Budget Resolver

agent-session.ts · #maintainContextMidRun

将 #maintainContextMidRun 中的 contextSteadyTarget 计算 替换为调用 resolveContextPlanBudget 取 steadyTarget： 

// BEFORE (misaligned):
const contextSteadyTarget = contextSteadyActive
  ? Math.max(1, Math.min(contextWindow, configuredSteadyTarget || 240_000, burstWindowTokens))
  : Number.POSITIVE_INFINITY;

// AFTER (unified):
const budget = resolveContextPlanBudget({
  settings: {
    qualityWindowTokens: this.settings.get("san.contextSteady.qualityWindowTokens"),
    reserveRatio: this.settings.get("san.contextSteady.reserveRatio"),
    planMaxTokens: this.#contextSteadyPlanMaxTokens(),
    burstWindowTokens: this.#contextSteadyBurstWindowTokens(),
  },
  contextWindow,
  nonMessageTokens: computeNonMessageTokens(this),
});
const contextSteadyTarget = contextSteadyActive
  ? Math.max(1, budget.steadyTarget)
  : Number.POSITIVE_INFINITY;

这确保维护阈值 = 预算解析器的 steadyTarget（已考虑 hardInputCeiling）， 维护一定在 gate 熔断之前触发。

Layer 3 — Tool-Loop 熔断前的一次有界恢复

agent-session.ts · #refreshContextSteadyPlanForProviderCall

当前 #refreshContextSteadyPlanForProviderCall 在 hard_pressure 时 直接暂停并 throw。修复后增加一次有界恢复尝试：

  • 条件：hard_pressure 且 #contextSteadyRecoveryAttempt === 0。
  • 动作：递增 recoveryAttempt，运行一次同步 auto-compaction（phase: "mid_turn"，trigger: "budget_pressure"）。
  • 压缩后重建 plan：若 outcome 不再是 hard_pressure，返回新 plan 继续 tool-loop。
  • 若仍为 hard_pressure 或 recoveryAttempt > 0：走原有暂停路径。
if (plan.audit.qualityGate.outcome === "hard_pressure") {
  // ── NEW: one bounded recovery attempt before pausing ──
  if (this.#contextSteadyRecoveryAttempt === 0) {
    this.#contextSteadyRecoveryAttempt++;
    const recovered = await this.#attemptToolLoopBudgetRecovery(messages, plan);
    if (recovered) return recovered;
  }
  // Original pause path (unchanged)
  this.sessionManager.appendCustomEntry(CONTEXT_PLAN_CUSTOM_TYPE, plan.audit);
  this.#pauseForContextSteadyPressure(plan, "mid_turn", ...);
  throw new Error(...);
}

#attemptToolLoopBudgetRecovery 执行：

  1. 调用 #runAutoCompaction("threshold", ...)，phase = "mid_turn"，trigger = "budget_pressure"。
  2. 压缩完成后，用压缩后的 messages 重建 ContextPlan。
  3. 若新 plan outcome ≠ hard_pressure，更新 #contextSteadyRequestPlan 并返回。
  4. 否则返回 undefined，走暂停路径。
注意：#refreshContextSteadyPlanForProviderCall 当前是同步方法。 恢复需要 async compaction，因此需将其改为 async 并更新调用方 #transformContextForProvider（已经是 async）。

3. 预算解析器改进（可选，低优先级）

当前 resolveContextPlanBudget 在小窗口下三区坍缩为一点。 未来可考虑引入最小缓冲区保证： 

// 保证 control → burst 之间至少有 10% 或 8K 的缓冲
const minBuffer = Math.max(8_000, Math.floor(steadyTarget * 0.1));
const burstCeiling = Math.min(
  Math.max(configuredBurst, steadyTarget + minBuffer),
  hardInputCeiling
);

但这会改变所有窗口的预算行为，需要完整的回归测试。当前三层修复已解决事故链， 此项作为后续优化跟踪。

4. 测试计划

层级测试内容验证点

5. 风险评估

  • Layer 1 风险低：仅在窗口缩小时失效 plan，窗口增大或不变时行为不变。
  • Layer 2 风险低：将维护阈值从"取 min 的独立公式"改为"消费统一 budget resolver"，逻辑更简单。对大窗口模型（contextWindow ≥ 300K），steadyTarget 仍为 240K，行为不变。
  • Layer 3 风险中：在 tool-loop 中引入 async compaction 可能增加单次工具调用延迟。但仅在 hard_pressure 且首次恢复时触发，正常路径无影响。压缩失败仍走原有暂停路径，不会死循环。
