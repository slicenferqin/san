01 · Executive summary

结论不是“未实现”，而是“实现存在，但关键合同不成立”

三个版本都不是空壳。v0.2 有真实多角色 executor 与 append-only ledger；v0.3 有 Candidate、Decision、activation、projection 和 debug read model；v0.4 有两种产品合同、精确审批指纹、受限解释器与隔离补丁审阅。问题在于这些能力尚未组成需求承诺的端到端闭环，而且若干失败路径会给出错误终态或突破安全边界。

Release decision NO-GO 三版本均不满足扩大 rollout 门禁
P0 findings 9 状态正确性、身份隔离、恢复、预算与交付
P1 findings 15 需求链路、隐私分类、事务与验收证据
Runtime counterexamples 6 4 个 v0.2、1 个 replay、1 个 loop closure
v0.2 · NOT ACCEPTED

可运行实验骨架

多角色顺序执行和持久记录已存在，但 stop 不取消 child、失败 Worker 可被 Supervisor 覆盖、Oracle 能提前 finalize、retry 与 DAG 合同失真。它尚不是需求定义的成熟执行闭环。

v0.3 · NOT ACCEPTED

机制完整度高，产品闭环不完整

显式审批、activation 与 projection 值得保留；但 Brain 的“低权威”内容被映射为 provider developer role，scope identity 未按冻结合同实现，默认 capture 路径几乎不产出候选，recall 隔离 fail-open。

v0.4 · CONTRACT CANDIDATE

默认关闭的原型

产品范围和审批边界清晰，但 run 只在内存、replay 未绑定输入、total-token 预算并非硬限制、结果是 at-most-once 交付，写入路径仍有 TOCTOU。不能视为工程核心完成。

Rollout 判定

保持 San Brain、Context Steady、Managed Workflow、Ad-hoc Workflow 与 isolated write 默认关闭；停止扩大内部 opt-in。此前文档中的“所有 P0/P1 门禁通过”“工程核心完整通过”“P1-P5 已完成”等表述，需要降级为“已有实现与测试基线，最终需求验收未通过”。

02 · Scope and method

以冻结需求定义目标，以生产代码与运行时反例定义事实

本报告同时检查需求 gap、实现漂移、正确性、安全性、代码风格、简洁性与维护性。审计对象冻结在当前分支 HEAD；没有把未跟踪的其他研究文档纳入本报告变更。

需求基线

v0.2 以需求与实施计划及技术方案为基线；v0.3 以P0 冻结合同为最高权威；v0.4 以Dynamic Workflows 提案为基线。

实际实现

逐条追踪生产入口、状态机、ledger、task-agent bridge、scope resolver、memory backend、restricted interpreter、delivery 与 token report。实现报告仅作为历史声明，不覆盖代码事实。

验证方式

复跑 40 个聚焦测试文件，执行 coding-agent 包级 check，并通过只读运行时 probe 验证失败 Worker、retry=0、Oracle、并发 stop、replay 调度和 for (let) closure 行为。

判定规则

满足表示生产路径与失败路径均兑现合同；部分表示机制存在但关键边界缺失；不满足表示核心验收项可被反例推翻。单元测试全绿不会自动提升合同状态。

证据优先级 用途 本报告处理方式
1. 冻结需求 / 验收合同 定义“应该是什么” 不以较晚实现说明悄然缩小原需求。
2. 生产代码与真实入口 定义“现在是什么” 从 slash/session 入口追到实际 child、provider、ledger 与副作用。
3. 运行时反例 推翻不成立的不变量 一条可重复反例足以否定“hard”“exactly-once”“终态不可逆”等强合同。
4. 测试与 dogfood 说明已覆盖行为 只有走真实默认产品路径且断言外部合同，才可作为验收证据。
5. 实施 / handoff 报告 记录历史声明 与上述证据冲突时，结论降级而不是反向解释代码。

07 · Findings by severity

严重度排序 Findings

P0 表示会导致错误终态、权限/隔离突破、不可恢复损失或强预算合同失效，必须在任何 rollout 前关闭。P1 表示需求闭环和发布证据不足。P2 是会持续放大缺陷概率的维护性与观测性问题。

P0

必须阻断 rollout 的 9 项问题

P0-01 · v0.2 · Abort is not cancellation

/san-loop stop 只追加 aborted snapshot，不能取消正在运行的 child；迟到结果可把终态改回 passed。

slash 命令在builtin-registry.ts:227-238仅调用 ledger helper；runner 的 child promise 没有共享 run registry、AbortController 或终态 CAS。ledger.ts:333-352写入 aborted 后，原 runner 仍继续写 worker/finalized。

反例：函数返回与最终 ledger 均为 passed，事件仍包含 aborted → worker_completed → finalized。

P0-02 · v0.2 · Invalid state machine authority

失败 Worker、DAG 依赖和 Oracle second opinion 都没有被正确约束，仍可形成 passed/finalized。

runner.ts:220-287记录所有 Worker 后无失败汇总或依赖调度，直接调用 review。Oracle 也走正式 applySanLoopReview()，其 pass 先生成 finalized；非 pass 则在 Supervisor 前提前退出。orchestrator.ts:326-375没有按 reviewer 区分 authority。

反例：{status:"passed", workerStatus:"failed"}；Oracle pass 后 Supervisor blocked，ledger 已含一次 finalized。

P0-03 · v0.3 · Prompt authority inversion

声明为“低权威”的 Brain 状态在 provider 请求中实际是 developer role，高于当前 user prompt。

agent-session.ts:7942-8000创建 role: custom 的 Brain prelude；messages.ts:162-176将所有 custom/hook message 转为 provider developer。当前用户消息在 agent-session.ts:7919-7922明确为 user role。内容里的 XML 标签或“low authority”文字不能改变 provider 的角色优先级。

P0-04 · v0.3 · Scope isolation is fail-open

scope identity 未实现冻结合同，recall 还会接受没有 scope 的 legacy item。

agent-session.ts:8770-8777中的 user:local 与 session key 符合冻结合同，但 project 直接使用 cwd、repo 直接使用绝对路径，没有 remote/common-dir hash、realpath identity、持久 UUID 或 alias migration。recall.ts:90-119仅在 item 自带 scope 时过滤；无 scope 结果默认通过，Hindsight/Mnemopi search 也未消费传入的 scopeKeys。

P0-05 · v0.4 · No durable run recovery

Workflow run、runtime、completed calls 与结果 payload 都只在内存，重启或 session 切换无法恢复。

manager.ts:164-181以 #runs Map 持有执行；workflows.ts:36-80在 identity 变化时 cancel、close 并删除 manager。ledger.ts:15-173只重建 status、delivery 与 write state，没有 source、args、budget、result payload 或 completed call value，无法 resume。

P0-06 · v0.4 · Replay identity is not input-bound

call ID 只绑定 sourceHash、callsite 与到达顺序，cache hit 不校验 prompt/input hash。

interpreter.ts:445-506以 invocation counter 生成 ID，并直接返回 #completedCalls。并发分支调度顺序变化时，同一 callsite 的两个不同 prompt 可交换历史结果。只读 probe 已复现，违反确定性重放的基本前提。

P0-07 · v0.4 · Hard token budget is post-facto

所谓 total-token 硬预算被下传为 child 输出上限，真实输入 token 已花费后才检查。

runtime 在interpreter.ts:517-556将剩余额度放入 request；bridge 在agent-bridge.ts:133-181转为 hardTokenLimit；task executor 又在executor.ts:2230把它作为 maxOutputTokens。总 usage 只在 child 返回后比较，超支结果在计入 workflow budget 前被拒绝，账本反而少记真实花费。

P0-08 · v0.4 · Result delivery is at-most-once

result_delivered 在 UI output 前写入，输出失败后无法重放，也没有 payload 可恢复。

manager.ts:456-476先 append delivery event 再返回值；observer 在workflows.ts:84-95之后才调用异步 output()。断连、renderer 失败或进程崩溃都会永久丢结果。ledger 只保存 result hash，不保存 payload 或消费方 ack。

P0-09 · v0.4 · Write and path TOCTOU

批准后的写入与工具路径授权都存在 check/use 时间窗。

delivery.ts:318-370在 baseline hash、canApplyText 与真实 apply 之间没有 repo lock 或逐文件 preimage CAS。path-scope.ts:34-84同步 realpath 检查发生在工具 I/O 前；agent-loop.ts:2021-2048随后才执行 tool，symlink 可在窗口内改变目标。

P1

阻断需求验收的 15 项问题

P1-01 · v0.2 · Retry contract

needs_fix + retryable=false 仍进入 retry；maxRetries=0 被默认正整数归一化与状态逻辑绕过。

orchestrator.ts:326-343对所有非 pass/blocked/out_of_scope 且未 exhausted 的报告选择 retrying，而不要求 retryable；runner 的 positiveInteger() 也不允许 0 turn 语义。

P1-02 · v0.2 · Checks are orphaned

San Checks 完成 discovery/render 后没有生产消费者。

全仓只有 helper 与 tests 引用 discover/select/renderSanLoopChecks；配置中的 enabled/includeBuiltins/projectDir 对实际 loop 结果无影响。

P1-03 · v0.2 · Role context and capability boundary

角色工具与上下文只是约定，不是可证明的最小权限。

task executor 只为 Commander 拼接 conversation context；Worker/Supervisor/Oracle prompt 主要接收完整 run JSON，role packet 未注入。context.ts:117-174只打超限标记，不做 material 裁剪。

P1-04 · v0.2 · Exception and recovery semantics

executor 抛异常会留下 active run；启动恢复只是把它改成 blocked，不恢复工作。

runner.ts:166-290没有 try/finally terminalization；agent-session.ts:8780-8785只对最新 active snapshot 调 recoverSanLoopRun()，该 helper 实际写 blocked。

P1-05 · v0.2 · Budget, mode and config drift

预算只数 Commander/Worker/reviewer 调用；solo 仍是三角色；多个设置无消费者且 CLI/SDK 默认不同。

没有 provider request、input/output token、cost 或 wall-time 记账。orchestrator.ts:81-103的 solo 仍允许 2 workers；schema 默认 workers/turns 与 runner policy 不同，reserveRatio、Oracle enabledInModes、Checks settings 未进入实际 policy。

P1-06 · v0.2 · Dogfood proves helpers, not lifecycle

deterministic verifier 手工调用 abort/recovery helper，无法覆盖真实 child 并发与 stop 竞争。

dogfood.ts:214-360的 recovery/abort 场景不启动 runner；“council runs oracle before supervisor”甚至把 Oracle 产生 finalized 当作成功条件。

P1-07 · v0.3 · Default capture path is nearly empty

默认配置关闭 LLM digest，而 fallback 明确返回空 memoryCandidates。

settings-schema.ts:2653-2669默认 digest.llm.enabled=false；fallback.ts:254-294设置 memoryCandidates: []。extractor 主要遍历该数组，因此正常偏好/事实/决策不会进入 Brain inbox。

P1-08 · v0.3 · Sensitivity classification is absent

所有自动候选被硬编码为 sensitivity: normal。

extract.ts:76-199的 profile、workflow 与 failure candidate 都不识别 secret/sensitive。后续 activation/projection 再严格，也是在错误标签上做选择。

P1-09 · v0.3 · SQLite cannot be rebuilt globally

权威源与 materialized store 的灾难恢复承诺不完整。

store.ts:378-411只同步调用者传入的一组 session entries；生产入口传入当前 session branch/entries。没有枚举 agentDir 下所有 session JSONL、alias migration 或完整重建命令。

P1-10 · v0.3 · 150ms capture boundary is not enforced

下一 prompt 会等待所有 post-prompt tasks，而非只等待 150ms。

agent-session.ts:4643-4675循环等待 task promise；digest/capture 在 agent-session.ts:4250-4425内部可等待 30s timeout。冻结合同要求超 150ms 本轮跳过。

P1-11 · v0.3 · Incomplete product candidate and budget wiring

投影能力存在，但生产 extractor 不会产生主要 action；全局 injection planner 也没有 ContextPlan 候选。

extract.ts:184-208只形成有限三类候选；agent-session.ts:7959-7976只把 San Loop 与 Brain 放入 global plan，冻结合同要求的 Brain + Context + San Loop 统一裁剪没有完成。

P1-12 · v0.3 · Dogfood bypasses the default path

M6 verifier 手工构造 memory candidate、recall policy、managed skill 与 check candidate。

dogfood.ts:115-190直接创建带候选 digest 和任意 experience candidate；这些 fixture 适合测下游状态机，但不能证明生产 extraction、classification、scope resolution 与 prompt authority。

P1-13 · v0.4 · Ad-hoc task identity is session identity

同一 session 内多个用户任务共享审批 taskRef。

workflows.ts:109-119把 sessionManager.getSessionId() 传为 taskRef。这扩大了一次性审批的信任域，与提案的“当前任务”绑定不符。

P1-14 · v0.4 · Loop lexical semantics

for (let i...) 复用单个 environment，closure 全看到最终值。

interpreter.ts:855-869只在 loop 外创建一次 Environment。probe 中三个 closure 都返回 item-3，这会破坏动态 fan-out prompt 和 replay identity。

P1-15 · v0.4 · Transaction and benchmark provenance gaps

Ad-hoc 清理跨事务；token report 只校验调用者提供字段的内部一致性。

manager.ts:241-257, 334-335, 363-386把状态、event 与 delete 分开；crash 可能残留敏感 source/args。token-report.ts:105-153, 221-248不读取 ledger/session/artifact 验证字段 provenance。

P2

维护性与可观测性风险

P2-01 · v0.2 · Oversized executor and permissive parsing

task-executor.ts 约 1029 行，混合 prompt 组装、subprocess、容错解析和业务 policy。

provider 返回被宽松字段别名与 fallback 接受，缺少清晰的 schema-fail boundary；部分 prompt 仍在代码字符串中构造，增加审计和演进成本。

P2-02 · v0.2 · Ledger atomicity and validation

snapshot/event/review 分散 append，schema guard 只验证顶层字段。

崩溃可能留下 snapshot 无 event 或 review 无 transition；重建没有显式标出这种不一致，错误状态容易被“最后 snapshot”掩盖。

P2-03 · v0.2 · Status observability

报告表面不足以识别 orphan child、错误 reviewer authority 与实际 provider 成本。

当前 status/report 主要呈现最后状态和少量计数，缺少 child PID/agent ID、cancel ack、per-request usage、DAG readiness 与 terminal revision。

P2-04 · Cross-version · Duplicated lifecycle primitives

三个版本分别实现 ledger、状态机、预算、恢复与 projection/delivery，没有共享不变量。

San Loop、Brain、Workflow 对“terminal、resume、idempotency、scope、budget、delivery”各自定义，导致同类 bug 以不同形式重复出现。

P2-05 · Cross-version · Claims outpace evidence

确定性 fixture 的绿色结果被提升为生产路径与发布级结论。

v0.2 handoff、v0.3 M6 与 v0.4 implementation report 都包含正确的局部证据，但完成口径没有持续绑定原始验收条款和反例集合。

09 · Cross-version drift

跨版本设计漂移

1

身份混用

session、task、project、repo path 与 user 被当作可互换 key，导致批准、记忆和恢复边界不稳定。

2

状态机重复

每个版本独立实现 terminal、retry、resume、idempotency 与 ledger，缺少共享的不可逆终态和 CAS 规则。

3

预算名实不符

turn、output limit、reported usage 被称为 total hard budget，却没有统一 provider request/token/cost accounting。

4

自构造验收

dogfood 直接构造理想 digest、candidate、usage、abort/recovery，绕过最容易出错的真实入口与默认配置。

漂移主题 v0.2 v0.3 v0.4 统一方向
权威状态 最后 snapshot 胜出 JSONL + SQLite materialization session events + 内存 run 统一 append-only command/event envelope、revision CAS 与可验证 rebuild。
身份 sessionId/runId user key 合规；project/repo 使用原始路径 sessionId 充当 taskRef 单一 identity resolver：user UUID、repo remote/common-dir hash、worktree、project UUID、task UUID。
预算 角色调用数 各 injection 层局部 token cap child output cap + 返回后 usage 统一预算账本，记录预留、实际 input/output/cache/cost、超支与释放。
恢复 启动时 active → blocked projection 有局部 reconcile session switch 取消并丢 manager durable run envelope、可重放节点结果、side-effect receipt 与 resume policy。
完成口径 terminal/dogfood 通过 手工 14-turn 通过 固定 usage dogfood 通过 每条需求绑定 production-path test、反例集、真实 provider 样本和残余风险。

Stage 1 建议实现顺序

  1. 统一 identity resolver：先定义稳定 user/project/repo/worktree/task key 和 migration；Brain、Workflow 与 San Loop 共用。
