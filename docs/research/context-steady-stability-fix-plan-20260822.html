0 · v1 → v2 修订记录评审意见的处置

评审意见判定本稿处置
1. orphan 定义过宽，须限定"可投影 entry"采纳WS1.1 不变量改为只作用于 projectable entries，返回值六分类（§3.1）
2. steady_target 趋零目标与触发设计冲突采纳WS1.2 改为分层指标；故障信号 = 无有效回收或短时重复触发，而非触发本身（§3.2）
3. epoch 边界不够严格，须区分动态 gate 重算与快照采纳WS2.2 增加边界契约表与"gate 动态 / 材料快照"分离规则，测试对齐最终 provider payload（§4.2）
4. recall 须现在就按 volatile 独立通道设计采纳新增 §4.4"stable / volatile 边界契约"，接口定义提前到 M1，M2 直接按最终架构实现（§6）
5. 净收益公式不能直接用全部 covered token采纳WS3.1 改为基于最终 provider projection 的差值公式，含排除清单；"整包不注入"限定为只撤销 derived replacement（§5.1）
6. 图片/文件/大段输出卸载未落方案采纳新增 WS4 投影策略契约（image/file/tool output 三种 policy），立项为 M4（§5.3）

3 · WS1：不丢消息的收口（P1）

3.1 可投影 orphan 断言v2 修订：限定作用域 + 六分类返回

不变量（修订版）：active scope 中本应参与 provider context 的可投影 entry，在最终 provider payload 中必须存在原文、合法 stub 或已准入 coverage 三者之一；非可投影 journal metadata（custom 审计 entry、compaction/label/mode_change 等元数据）不参与 orphan 判定。

"可投影"的判定口径：以 provider transform 之前的消息态为准——message 与会被投影的 custom_message；已被 responseDocuments.project() 或 provider transform 正常折叠的内容，按折叠后的对应关系核对，不按原始 entry 逐项机械比对。tool stub 属"保留消息、替换内容"，计为存在（stubbed），不算缺失。

返回形态（六分类，不只是一个 orphans 列表）：

auditProjectionCoverage() → { missingProjectableRefs: 真正的丢失——唯一算失败的类别 coveredRefs: 被 coverage 合法省略 stubbedRefs: 被 stub 合法替换 unmatchedNonProjectableRefs: 本就不投影的 entry(预期类别,用于口径自检) duplicateMatches: 双通道匹配的重复/歧义(口径质量信号) invalidCoverage: coverage 授权了不该授权的引用 }

执行策略：测试环境 missingProjectableRefs 必须为空（写进测试基线 + 真实 replay 回归）；生产环境不 throw，六分类计数进 probe 与 san stats（详情页，不进主表面）。既有基础：validateContextPlanCoverage() 已校验 coverage↔material 一致性、materialize 在校验失败时放弃 coverage——本断言补的是对最终投影 payload 的反向完整性审计。

验收：review-20260821 的真实重放，修复前 planner 报出 D2 孤儿、修复后 missingProjectableRefs 为空；同时 unmatchedNonProjectableRefs 恰好等于 scope 内非可投影 entry 数（口径自检）。

3.2 steady_target 分层指标v2 修订：放弃趋零目标

定位修正：steady_target 是稳态物理 ceiling 低于当前上下文时的保护性维护，本身不是 bug——窗口变小、非消息 token 增长、大 tool output、resume 后 scope 大都可能正当触发它。故障信号是：触发后无有效回收、或短时间重复触发。

指标含义
触发次数 / 请求数基线频率（观测，不判失败）
触发后成功回收 token 数触发是否产生了实际收益
触发后重复触发率核心故障信号：回收无效、问题未解决
steady_target 与 native_threshold 同时命中比例区分稳态自身压力与全局压力
触发导致的用户可见暂停次数体验成本
触发前后 cache read rate冷启动代价（对照 9.5M token 基线）

用户可见一行状态（"已整理较早的历史，正在从摘要继续"）保留；触发时须校验当前 user/tool loop 仍在场（并入断言口径）。

3.3 记忆可得性观测

维持 v1：checkpoint 与 digest 同时缺席时审计记"历史代表降级到 recall-only"；memoryCandidates 仍不自动 retain。与 3.1 共用审计通道。

4 · WS2：缓存命中率（P2）

4.1 位置钉死（维持 v1）

turn N payload = [历史…, plan_N, user_N, 工具循环…] ← 公共前缀止于 plan_N 旧位置 目标 payload = [plan_epoch(冻结), kept历史…, user_N, …, user_{N+1}, …] ← 前缀跨 turn 单调增长

注入点从 findLastIndex(role === "user") 改为 active scope 头部（firstKeptEntryId 对应消息之前）。测试必须针对最终 provider-bound payload（过完 responseDocuments.project 与 provider transform 之后），不能只测 materialize 的中间数组——防止 plan 被后续 transform 再次移动而不自知。

4.2 epoch 冻结的边界契约v2 修订：事件表 + gate/快照分离

冻结范围：材料集合、tier、渲染字节三者全部，epoch 内一致。

epoch 边界事件表（写成测试，不留给实现者临场判断）：

事件epoch说明
新增普通 user/assistant/tool entry不变历史代表材料不重选——这是本设计的核心目的
新 checkpoint 落库新 epochrebaseReason = checkpoint
物理 compaction新 epochrebaseReason = budget_pressure；scope 头部移动
明确 topic shift新 epochrebaseReason = topic_shift
model / context-window 变化新 epoch渲染依赖 window 推导；现状 #contextSteadyPlanInputsChanged 会失效——归入 epoch 事件而非每次重算
non-message budget 变化gate 重算，epoch 不变见下方分离规则
hard pressure recovery新 epoch恢复即压缩，scope 重排

gate / 快照分离规则（评审点 3 的核心）：每个请求允许动态重算 gate 类数值（projectedInputTokens、压力判定、是否跨 controlMax、emergency stub 档）；不允许因此重选历史材料。落点：#refreshContextSteadyPlanForProviderCall 的重建分支拆成两条路径——gate 超限走"gate 重算 + 材料沿用 epoch 快照"，只有 epoch 事件表命中才走"材料重选"。否则会出现"看起来冻结、实际每次 tool-loop 因 projected input 变化重建 plan"。

基线事实（已核实）：#contextSteadyEpochId() 由最近 rebase checkpoint + reason 派生，不含 current leaf，是正确起点；#contextSteadyPlanInputsChanged() 的失效三元组（compaction / contextWindow / nonMessageTokens）需要按上表重新归类。

附不变量：plan 审计 entry 永不成为 digest span 的 toEntryId（resolveDigestToEntryId 现已偏好 message/custom_message，固化为测试）。

4.3 同批落地约束（维持 v1）

只钉位不冻结字节会把失效点挪到头部（更糟）；只冻结不钉位前缀仍被切断。feature flag 默认关闭或仅 dogfood；同批原子提交。

4.4 stable / volatile 边界契约v2 新增：接口先行，避免先锁后拆

现在就定死边界，M2 直接按最终架构实现（消除 v1 里"M2 冻结 recall、M3 再拆"的返工）：

stable planvolatile 通道
内容checkpoint / digest（历史代表）recall / 与当前 prompt 相关的即时上下文
生命周期epoch 级冻结每请求可变
位置scope 头部（冻结前缀首条）冻结前缀之后、当前 user 之前
coverage 权有永远没有；两侧永不能互相授权
估算/注入/剥离各自独立；token 估算、注入、剥离互不耦合

volatile 通道的接线清单（少接一条就出现估算与真实 payload 漂移）：独立 custom type；剥离纳入所有路径——实时 transform、transcript rebuild、status/compaction estimate、最终 provider conversion；recall 失败/为空/backend 不可用时静默降级，不影响冻结 plan 与 raw history 保留。现有 stripPriorDerivedPlanMessages() 只认 san.context_packet.injected 与 san.context_plan.injected，新类型须全部补齐。

5 · WS3 / WS4：省 token（P3）

5.1 projection 净收益门控v2 修订：差值公式 + 排除清单

公式（修订版）：

netBenefit = rawProjectedTokens − projectedTokensAfterReplacement − replacementWireOverhead

必须在最终 provider projection 后测量，不能用"全部 covered entry token 之和"（会把本就不进 payload 的、已被 stub 的、protected 的都算成收益）。天然挂点：#buildContextSteadyPlanForProvider 的定长不动点迭代已经在反复测投影，差值在这里顺手可得。

排除清单：protected exact/live refs；未实际出现在原始 payload 的 refs；fallback digest 贡献的 coverage；重复 coverage；仅被 stub 替换（未被省略）的 tool result；plan 自身的 budget/reason/refs 包装开销（计入 wire 侧）。

"整包不注入"的精确语义（修订）：只撤销 derived replacement（coverage 授权与 plan 消息注入）；当前 user、工具调用、必要审计、volatile recall 通道不受影响。≤ 0 时不注入 = fail-safe 行为，与 3.1 断言自然兼容（无覆盖授权 → 无孤儿）。

5.2 上轮 review 遗留小项（维持 v1）

omitted reason 区分"预算不够/相关性排除"；恢复路径 digest 年龄淘汰顺序；digest 物料构造两处重复合并。

5.3 WS4：图片 / 文件 / 大段输出的投影策略v2 新增：评审点 6

省 token 的大头不在 planner material，在图片、文件内容和大段工具输出。三种 projection policy：

类别策略约束
image原始 image block → 缩略描述 / 引用不能按字符/token 估算一刀切；区分原始 block、描述、文件快照引用三态
file content→ 有界摘录 + 可重读引用（path / hash-line 锚点）引用必须可重新验证，不可把无法验证的摘要当原文替代
tool output→ stub / 可展开引用（"保留最近结果、旧结果 stub"）复用既有 superseded/emergency stub 机制并推广

统一约束：卸载只改 provider projection、永不改 journal；一切卸载必须通过 3.1 的同一 orphan/coverage 审计（stubbedRefs / coveredRefs 类别正是为它准备的）。与 superseded stub 的差别要写清：stub 是"同消息降级"，这里是"整块内容形态置换"。

立项位置：M4（依赖 3.1 断言先行），不阻塞 M1〜M3。

6 · 里程碑（v2 修订）

里程碑内容验收标准风险
M1WS1 全部 + WS3.1/3.2 + §4.4 接口契约定义可投影 entry 零 orphan（且旧代码能报出 D2）；coverage 校验失败时 raw 保留；fallback digest 永不授权删除；net benefit ≤ 0 时 derived replacement 不注入（user/tool/审计不受影响）；steady_target 有计数、有原因、有回收结果——触发次数本身不判失败；volatile 通道接口与剥离路径清单评审通过极低——只增不改行为
M2WS2.1 + 4.2 + 4.3 + 4.4 volatile 通道实现（直接按最终架构，无先锁后拆）最终 provider payload 公共前缀字节级测试通过；epoch 内材料集合 / tier / renderedContent 三项均不变；4.2 事件表逐行有测试；feature flag 默认关闭或 dogfood 灰度；dogfood cacheRead 对比提升中——原子提交 + flag + 灰度
M3打磨：分层指标看板、transcript rebuild 路径核对volatile 通道在 rebuild/estimate/conversion 各路径估算一致；分层指标在 san stats 详情页可查低
M4WS4 三种 projection policy每类卸载过同一 orphan 审计；文件引用可重读可验证；dogfood 大输出场景 token 对比中——内容形态置换，需逐类灰度

非目标（维持）：摘要模型配置校验自动化（配置层另行处理）；compaction 子系统重构（只做交棒显式化与分层指标）。M4 的 image policy 不做视觉模型调用，只做投影置换。
