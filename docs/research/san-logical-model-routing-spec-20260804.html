Architecture proposal · 2026-08-04

San 逻辑模型路由：完整能力、分阶段 Spec 与技术实现

目标是让用户选择 gpt-5.6-sol 这样的逻辑模型，由 San 在多个服务商提供的同一模型之间执行便宜优先、会话亲和、故障切换和恢复回切；同时把“同模型换路由”与“换成另一个模型”彻底分开。

状态：设计提案 建议：下一版本核心能力 作用域：packages/coding-agent 为主 兼容：provider/model 永久保留
核心决策：不恢复已经删除的 catalog-wide canonical 启发式归并，而是引入显式的 Logical Model → Route Group。现有 Model<Api> 继续表示可执行的具体端点；新增逻辑模型、路由策略和路由租约，不污染 provider transport，也不在冷启动阶段扫描并猜测数千个模型的等价关系。

User contract

用户选择模型，不选择供应链

modelRoles.default 保存逻辑模型。服务商新增、降价或故障时，不需要修改角色和会话语义。

Determinism

第一版是优先级，不是随机权重

便宜路由健康时始终使用它；只有失败或不满足请求能力时才进入下一条。随机流量权重是后续可选策略。

Semantics

路由切换不等于模型切换

同一逻辑模型切换服务商时保持 harness profile、effort 和任务语义，只重算 transport、凭证、上下文上限和 provider session。

Cache

默认保持会话亲和

路由解析不是每次请求重新抽签。正常情况下保持当前 route lease，避免 provider cache、Responses session 和 KV 前缀反复失效。

Recovery

Agent 原生理解安全边界

San 知道请求是否已输出文本、是否产生 tool call、能否安全丢弃失败消息；这是外部 HTTP 路由器无法完整判断的状态。

Debuggability

逻辑身份与实际执行同时可见

会话、日志和 stats 同时记录 logicalModel、route、选择原因、fallback 触发原因与实际费用。

为什么不恢复旧 canonical 实现

  • 旧实现依赖 catalog-wide 归并、字符串启发式和 canonical index，曾因冷启动成本被删除。
  • 路由关系是用户的供应链政策，不只是模型 ID 规范化问题；价格、订阅、可靠性和服务商信任都无法从 ID 猜出。
  • 显式 Route Group 的复杂度只与每组路由数量相关，通常为 2–10，编译后解析为 O(group routes)。
  • 后续可以提供“发现同 ID 候选并建议加入”的 UX，但不得静默把候选加入可执行路由组。

五、配置 Spec

模型库存与 Route Group 放在 models.yml；角色选择和全局运行策略放在 config.yml。这样 provider/model 定义与用户运行偏好保持分层。

  self-botcf:

      - id: asxs-cheap

        equivalence: exact

5.4 Selector 解析优先级

  1. 角色 alias（例如 @default）。
  2. 精确 provider/model：永久表示强制具体路由，绕过 Route Group。
  3. 精确 Logical Model ID：进入 route resolver。
  4. 现有裸 concrete ID、variant alias 和 fuzzy legacy matching。

因此配置了 Logical Model gpt-5.6-sol 后，裸选择优先解释为逻辑模型；需要绕过时必须写完整 provider/model。

六、运行时 Spec

6.1 Route resolution 输入与输出

interface RouteResolutionRequest {
  logicalModelId: string;
  thinkingLevel: ConfiguredThinkingLevel | undefined;
  requiredContextTokens: number;
  requiresImages: boolean;
  requiresTools: boolean;
  sessionId: string;
  turnId: string;
  nowMs: number;
}

interface ResolvedModelRoute {
  logicalModelId: string;
  routeId: string;
  model: Model<Api>;
  reason: "primary" | "affinity" | "failover" | "recovery" | "manual";
  policyVersion: number;
}

逻辑路由类型属于 packages/coding-agent，不加入 catalog 的 Model。这样 provider SDK、模型目录和 transport handler 继续只处理具体模型。

6.2 Eligibility pipeline

1. Config validityroute enabled；selector 能精确找到 concrete model；provider 未被禁用。
2. Authentication快速阶段用 hasAuth/keyless 判断；真正发请求前调用 getApiKey(model, sessionId)，允许现有 credential rotation 重新排序。
3. Healthroute 不在 selector cooldown / open circuit；half-open 只允许一个探测请求。
4. Request capability检查 image、tools、required context、max output、API transport 和请求需要的特殊能力。
5. Effort compatibility显式 effort 默认不得静默降档。V1 route 必须支持相同语义 effort；不支持则拒绝该 route 并给出诊断。
6. Equivalenceexact 和 compatible 可自动选择；unknown 只能手动 pin。
7. Ranking手动 pin → 可用 affinity lease → policy score → priority → config order。所有 tie-break 必须稳定。

6.3 请求与 fallback 顺序

  1. 解析 Logical Model 和当前有效 Route Lease。
  2. 在具体 route 内执行现有 credential selection/rotation。
  3. 对短暂 network/timeout/5xx 按政策进行有限次 same-route retry。
  4. route 失败且满足 fallbackOn 时，标记 cooldown，切换同一 Route Group 的下一条路由。
  5. Route Group 全部不可用后，才进入现有 cross-model retry.fallbackChains。
  6. 所有候选耗尽后返回结构化错误，列出每条 route 的拒绝原因；不得无限回绕。

6.4 错误分类与动作

错误类别same-route retrycredential rotationroute fallback说明
429 / quota / usage limit通常否先尝试凭证耗尽后立即沿用 Retry-After/cooldown
network / timeout有限 1 次否可避免一次抖动立刻破坏缓存
5xx / overload有限 1 次否可相同 route 连续失败后 open
model unavailable / router 404否否立即明显是路由能力问题
auth failed否先尝试可配置如果该 provider 所有凭证均失效，可换 route
context overflow否否默认否交给 compaction/context promotion；Phase 3 可选择足够窗口的同模型 route
invalid request / schema 400否否默认否可能是 San/transport bug，盲目换路由会掩盖根因
refusal / safety / sensitive否否否模型决策，不伪装成 provider 故障
user abort / interrupt否否否必须立即终止

6.5 安全重放边界

  • 不得在同一个 streaming request 内“无缝换 provider”；route switch 总是产生一个新请求。
  • 失败消息只有 text/thinking partial 时，可沿用现有逻辑从 active context 移除后重试。
  • 失败消息已包含 tool call 时，默认不可自动重放，避免重复执行写文件、部署、发送消息等副作用。
  • 已完成一个完整 tool round 后的下一次 provider request，可以使用新 route；此时历史已经有确定的 tool result。
  • 切换 route 必须调用现有 provider session reset 入口，关闭不兼容的 Responses/WebSocket/session state。

七、Harness、缓存与 Context Steady 集成

组合公式：Resolved Execution = Logical Harness Profile + Concrete Model Capabilities + Provider Transport Profile + Route Policy。其中行为层由逻辑模型决定，wire 编码、thinking 参数、headers、API 和 provider session 由具体 route 决定。

Harness profile

  • route fallback 不重选 system guidance、tool policy、loop policy。
  • 具体 route 的 compat、API dialect、thinking map 仍需重新解析。
  • equivalence: compatible 可声明 route-level profile overlay，但必须显式，不能由 provider 名推断。

Prompt cache

  • 缓存域至少包含 provider/baseUrl/model/credential family；跨 route 默认视为 cache cold。
  • session affinity 是默认排名前置条件，不因每次价格计算反复切换。
  • route switch 记录明确的 cache reset reason，stats 不把预期 miss 误判为回归。

Context Steady

  • 逻辑模型不变时，不触发语义 profile reset。
  • 仍按新 route 的真实 contextWindow/maxTokens 重新做 preflight。
  • 新 route 容量更小时，切换前必须完成 compaction 或拒绝候选，不能等 provider 400。

Provider payload replay

  • Responses reasoning item、Anthropic signature、tool call IDs 按目标 route 的 transport policy 转换。
  • 不能把 provider-private state 当作逻辑模型上下文直接搬运。
  • 复用现有跨模型切换时的 provider payload 清理路径，不另造一套宽松兜底。

8.1 Session persistence

8.3 Route health state

Healthy / Closed正常参与选择；成功请求更新延迟和最后成功时间。
Cooling / Open在 cooldownUntil 前不可自动选择；手动 pin 需明确提示。
Half-open冷却结束后只允许一个探测请求，其他并发继续使用 fallback。
Disabled配置禁用或用户手动 drain；不自动恢复。

Phase 1 只使用当前进程内 selector suppression；Phase 2 才将 circuit 状态与 failure counters 持久化到 AgentStorage。

Phase 0 · Internal foundation

显式边界与纯函数 resolver

不对用户开放

目标：在不改变任何现有选择行为的前提下建立数据结构、验证器和执行边界，避免直接把更多分支塞进已经很大的 AgentSession。

Spec

  • 新增 Logical Model / Route Group schema，但默认不启用。
  • 实现精确 selector 编译、重复 route 检查、循环/冲突诊断。
  • 实现纯函数 eligibility + priority resolver。
  • 可选 shadow mode：只记录“如果启用会选哪条 route”，不切换。
  • 修正文档中已经 inert 的 canonical/equivalence 描述。

技术实现

  • config/model-routes-schema.ts：ArkType schema 和强类型。
  • config/model-route-registry.ts：在 concrete ModelRegistry 完成加载后编译小型 route index。
  • config/model-route-resolver.ts：无 I/O 的 deterministic resolver。
  • 不得把逻辑字段加入 catalog Model，不得恢复 catalog-wide canonical index。
  • registry refresh 后原子替换 compiled index；解析中的 session 继续使用旧 policy version 到请求边界。

验收标准

  • 没有 logicalModels 配置时，现有 model selection、fallback、启动耗时和 session 文件字节行为不变。
  • 相同输入的 resolver 输出稳定，不依赖 Map 迭代偶然顺序或 MRU。
  • 未知 model、重复 route id、非法 logical id、空 route group 在启动时给出具体配置路径。
Phase 1 · Next-version MVP

显式同模型优先级路由与故障切换

建议下一版本发布

目标：用户配置多个服务商的同一模型后，只选择 Logical Model；San 确定性使用首个健康 route，并在安全错误上自动切换。

用户可见 Spec

  • models.yml.logicalModels 和 modelRoles: logical-id 生效。
  • 策略只支持 priority；便宜 route 由用户显式排在前面。
  • 默认 session affinity；fallback 后在 cooldown 结束的下一用户 turn 回切。
  • route fallback 先于 cross-model fallback。
  • provider/model 继续强制具体 route。
  • /models 显示 Logical Models 分组、当前 route 和备用 route 数。

技术实现

  • 扩展 model selector parser：exact concrete → exact logical → legacy bare/fuzzy。
  • AgentSession 增加 active logical intent 和 route lease；Agent 仍只接收 concrete Model。
  • 从现有 fallback 代码提取 route candidate 遍历；复用 AIError 分类、selector suppression 和安全重放。
  • 每次切换调用 #setModelWithProviderSessionReset，并重新校验 context/effort。
  • 扩展 session entry、AgentSessionEvent、RPC v2 DTO 和 event adapter。
  • route retry budget 与 model fallback budget 分开，route 切换不能消耗完后者。

明确不做

  • 不按 catalog 价格自动排序；V1 只信显式 priority。
  • 不持久化跨进程 circuit；沿用进程内 cooldown。
  • 不做随机 weight、在线探测、质量学习和 task effort 自动判断。
  • 不自动把同 ID provider 加入 route group。

验收标准

  • 三个 route 中首个已鉴权且满足能力的 route 必须稳定胜出。
  • 首 route 429 后先轮转同 provider 凭证；凭证耗尽后切第二 route，当前 turn 成功完成。
  • 失败消息包含 tool call 时不得自动重放。
  • resume 后 Logical Model intent 不被临时 fallback assistant message 覆盖。
  • 所有 route 不可用时，错误列出每条候选的精确拒绝原因。
  • 没有 Logical Model 配置的现有用户行为完全兼容。
Phase 2 · Operations

持久健康、Route Inspector 与完整遥测

可运营

目标：路由不只“能 fallback”，还要能解释、观察、恢复和远程控制。

用户可见 Spec

  • Route Inspector 展示 route 状态、最后错误、cooldown、TTFT/TPS、成功率和最近费用。
  • 支持 session pin、unpin、disable/drain route；手动 concrete 选择仍等价于 pin。
  • 支持 san models routes 和 JSON 输出，便于脚本/Remote Control 消费。
  • RPC v2 客户端能收到 route resolved/changed/health changed 事件。
  • 路由状态跨 session 和进程重启保留，但有过期时间。

技术实现

  • AgentStorage 新增 model_route_health 与 model_route_perf 表；route key 使用 logical id + stable route id。
  • 被动 circuit breaker：连续失败阈值、openUntil、half-open single-flight；启动不主动发网络探测。
  • 扩展现有 perf drain，批量记录 success/error category/TTFT/TPS/cache ratio/cost。
  • TUI 在 model hub 中新增 logical group detail，不复制另一套 picker。
  • stats 包按 logical model 和 concrete route 两个维度聚合。
  • 所有事件不包含 API key、完整 headers 或敏感 baseUrl query。

验收标准

  • 同 route 连续失败达到阈值后 open，多个并发 session 不再同时冲击故障服务。
  • cooldown 到期只有一个 half-open 请求；成功后 close，失败后指数延长。
  • UI、RPC、session dump 和 stats 对同一次 route switch 使用相同 route id 与原因。
  • 健康数据库损坏或不可写时明确报错/告警，不静默伪装为全健康。
Phase 3 · Economics & SLA

请求级成本估算、多策略与防抖

经济性优化

目标：从“用户手工把便宜 route 排前面”升级为“San 能基于当前请求、账单模型和 SLA 做可解释排序”。

用户可见 Spec

  • lowest-cost：在满足质量/健康约束后选择预估边际成本最低的 route。
  • balanced：成本、成功率、TTFT/TPS 的显式可配置线性/分层策略。
  • latency-first：在预算上限内选择最快健康 route。
  • weighted：仅用于流量分散或 A/B，必须显式开启。
  • 支持 per-turn/per-day budget ceiling 与超限动作。

技术实现

  • 新增 RouteScorer，输入不可变 snapshot：request estimate、billing、perf、health、affinity。
  • 预估成本公式使用 uncached input、cache read/write、expected output 和 fixed request/premium charge。
  • Model.cost 是默认 route price；用户 billing override 优先，并记录来源。
  • subscription/free route 不能简单写成零成本无限使用；需同时建模 quota window 与剩余额度。
  • 加入 min dwell、switch penalty、hysteresis，防止几毫秒/几分钱波动导致 cache thrash。
  • score breakdown 进入 debug/inspector，最终选择必须可解释。

成本公式

estimatedCost =
  uncachedInputTokens × inputRate
  cacheReadTokens     × cacheReadRate
  cacheWriteTokens    × cacheWriteRate
  expectedOutput      × outputRate
  fixedRequestCost
  premiumRequestCost
  switchPenalty       // cache 失效与 provider session 重建的估算成本

验收标准

  • 相同请求与相同 metrics snapshot 得到稳定 score 和选择结果。
  • 未知价格 route 不得被当作免费；默认排在已知价格 route 之后，除非显式 priority/pin。
  • 策略选出的 route、预估费用和实际费用差异可被 stats 追踪。
  • 启用 affinity 后，微小价格差不得触发频繁切换。
Phase 4 · Adaptive scheduling

Effort → Logical Model → Provider Route

长期能力

目标：把 provider routing 接到更上层的资源调度：用户只表达任务努力程度，San 先选逻辑模型，再在该模型的 Route Group 中选择执行端点。

用户可见 Spec

  • effort tier 映射到一个或多个 Logical Model，而不是具体 provider/model。
  • Agent 可基于任务阶段、上下文规模、工具风险和用户预算建议/选择 effort。
  • 质量底线满足后优化价格与延迟；不同模型的 fallback 位于 route exhaustion 之后。
  • 项目可固定模型政策，禁止自适应探索。

技术实现

  • 新增独立 EffortPolicy；不得把 effort 模型选择塞进 RouteScorer。
  • 执行管线固定为：task policy → logical model → route resolver → concrete model。
  • 质量数据只来自版本化 eval、明确用户反馈和可审计 outcome，不能用“请求没报错”冒充质量。
  • 自适应 exploration 默认关闭或严格限额；生产 route 选择有可复现实验 ID。
  • harness profile 版本参与 eval key，避免把 profile 变化错误归因给 provider route。

验收标准

  • effort 政策不引用 provider 名称，只引用 Logical Model。
  • 同一 logical choice 在所有 route 上使用相同 harness profile version。
  • 自适应决策可通过记录的 inputs/policy version 离线重放。
  • 质量门禁未满足时，成本再低的 route/model 也不得进入生产候选。

十一、测试、Eval 与发布门禁

配置与 resolver 合同

  • 精确 route 绑定、非法 ID、重复 route、未知 model、空 group。
  • priority、config order、affinity、manual pin 的稳定排序。
  • auth、tools、image、context、effort、suppression 的逐项拒绝原因。
  • provider/model 永久绕过 logical routing。

AgentSession 集成合同

  • 429 → credential rotation → route fallback → model fallback 的严格顺序。
  • text/thinking partial 可安全重试；tool call partial 不重放。
  • route switch 关闭旧 provider session，并按新 context window preflight。
  • fallback 得到独立 retry budget，不产生无限环。

持久化与远程合同

  • resume 保持 logical intent，临时 route 不覆盖用户选择。
  • 旧 session 没有 logical 字段时照常恢复。
  • TUI、print、RPC v2、ACP/extension 对事件的处理不崩溃。
  • route health schema migration 与 full-suite isolation。

Harness route-invariance eval

  • 同 Logical Model、同 profile、同任务分别固定到每条 route。
  • 比较 tool schema、system prefix、effort wire mapping、上下文 replay。
  • 检测 provider 注入、模型快照漂移和能力缺失。
  • 质量显著偏离的 route 自动标记 unknown/degraded，不直接归因于基模。

故障注入矩阵

注入期望行为必须断言
首 route 429 + Retry-After标记 cooldown，选择次 route不等待超长窗口；记录 trigger/cooldown
首 route 单次网络断开有限同 route retry 后再切换无 cache thrash；retry 次数有界
首 route 5xx 持续失败open circuit，后续 session 直接跳过half-open 单飞恢复
候选 contextWindow 过小请求前拒绝候选不向 provider 发出必然失败请求
失败消息已有 tool call停止自动 route replay工具副作用只发生一次
所有 route 无鉴权进入 cross-model fallback 或明确失败诊断列出每个 provider 的 auth 原因，不泄露 secret

十二、兼容与迁移策略

  • 零配置兼容：没有 logicalModels 时，所有现有行为、模型 UI 和 session 恢复保持不变。
  • 显式 concrete 永久有效：provider/model 始终绕过 route resolver，适用于调试、基准测试和强制服务商。
  • modelProviderOrder 保留：只服务 legacy 裸 ID 歧义选择，不作为 Route Group 的成本政策。
  • retry.fallbackChains 保留：Phase 1 起定义为 Route Group 耗尽后的 cross-model fallback；旧 concrete primary 仍按原逻辑工作。
  • 不自动迁移 fallbackChains：现有 chain 可能混合不同模型、不同 effort 和 provider wildcard，静默转成等价 route 有语义风险。
  • 可提供只读建议：CLI 可以检测“多个 provider 存在同 ID + chain 只换 provider”，生成候选 YAML diff，但必须由用户确认写入。
  • 旧 canonical 文档：删除 inert equivalence 示例，增加迁移说明，避免用户误以为当前已经支持逻辑路由。

十四、版本完成定义

下一版本可宣告完成的边界：完成 Phase 0 + Phase 1。也就是用户能显式定义 Route Group、角色保存 Logical Model、San 以确定性优先级选择 route、在安全错误上完成同模型 provider fallback、保持 session affinity，并在 session/UI/RPC 中同时展示逻辑模型和实际 route。
  • 配置、解析、鉴权、能力过滤、fallback、安全重放、resume、UI 与 RPC 的合同测试通过。
  • 现有 concrete-only 用户全量测试无行为回归。
  • 冷启动没有恢复 catalog-wide canonical index 或新增启动网络请求。
  • 同模型 route fallback 与 cross-model fallback 在类型、状态和事件上已经分层。
  • route switch 不改变 Logical Harness Profile，只重新解析 concrete transport。
  • 配置错误、无可用 route 和 unsafe replay 都明确失败，不静默降级。

推荐发布表述

选择模型，而不是服务商。

为同一个逻辑模型配置多个 provider route，San 会优先使用你排序最靠前的
健康路由；遇到配额、限流、超时或服务故障时，在不改变模型 profile 和
effort 的前提下自动切换，并保留具体执行路由的完整可观测性。

设计原则：显式优于猜测；逻辑身份与执行端点分离；同模型 route fallback 先于跨模型 fallback；缓存亲和与安全重放优先于动态最优。
