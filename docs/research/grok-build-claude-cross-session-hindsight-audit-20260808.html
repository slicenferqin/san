二、昨日 Grok → San 报告逐项复核

报告项核查结果需要修正对 San 的判断
Tree-sitter Bash 权限门 方向正确，细节部分失真 当前 Grok main 已允许 redirected_statement、file_redirect、heredoc 与 >/>>/2>&1；“出现重定向就 fail-closed”已不成立。替换、控制流、未知 AST 节点仍会走保守路径。 San 的权限路径仍主要依赖 tier/审批与可选正则 interceptor，缺 AST 级命令分段和未知结构 fail-closed；但仓库已经依赖 tree-sitter-bash（crates/pi-ast），不应再引入 web-tree-sitter WASM。
OS 级 sandbox 缺口成立 Grok 是对 agent 进程生命周期施加 Landlock/Seatbelt，不是简单给每次 Bash 套一层 bwrap。Linux 只有非空 read-deny 等场景必须使用 bubblewrap。沙箱默认关闭；内置 profile 应用失败会警告后继续，显式 custom profile 才 fail-closed。 San 的 pi-iso 是代码树隔离，不是进程能力沙箱；Bash、文件工具、LSP 与子进程仍缺统一的 OS 边界。这是报告中最可靠的真实差距。
Worktree + Btrfs 快照 San 现状判断错误 Grok 的 Linked 不是“硬链目录”：它是 git worktree add --no-checkout + 并行 CoW 文件复制 + index finalization；Standalone 是独立 .git 的 CoW 副本。 San 已有并已接线的原生 PAL：APFS clonefile、Btrfs、ZFS、Linux reflink、overlayfs、ProjFS、Windows block clone、rcopy/worktree 回退，并支持 diff/merge。能力默认 task.isolation.mode = none，但不能再列为“San 尚未具备”。
Prefire 两段压缩 事实成立 默认提前量确为 10%；pass-1 约覆盖 95% 前缀；前缀变化会使缓存失效。但 two_pass_compaction 默认是 false，它是可选延迟优化，不是 Grok 默认路径。 San 已有 Context Steady prefixFingerprint 与变更观测，但未发现后台预跑摘要。可借鉴 single-flight、指纹失效和取消语义；在近期 runaway 问题背景下，必须先有硬预算和陈旧结果丢弃，不能无界预跑。
Leader + ACP San 现状判断错误 Grok 的共享 leader、Unix socket 与多客户端 session registry 确实值得研究。 San 不只是 tools/acp-bridge.ts：已有完整 san acp stdio server、AcpAgent、多 managed sessions 与 ACP client bridge。真正缺口是“多个独立 San 进程/客户端共享同一活动 session”，不是 ACP 本身。
对原报告的总体评价：执行安全方向正确；San 源码盘点不完整。原路线中的“快照回滚阶段”应删除，“引入 web-tree-sitter”应改为复用原生 pi-ast，“ACP bridge”应改写为“已有原生 ACP server，是否再做共享 leader 是另一项产品决策”。

三、Grok harness 值得借鉴什么

P0 · Shell policy

复用 pi-ast，补 AST 级审批分类

  • 解析完整 Bash AST，再将简单命令链拆成可独立判定的 segments。
  • 已知危险结构走 Reject；无法可靠解释的扩展、替换、eval、bash -c 走 AskFailClosed，不静默放行。
  • 重定向不应一律拒绝：应把目标路径、方向和 append/truncate 语义送入现有 write/exec tier。
  • 这一层与 San 现有 approval 正交：parser 提供事实，approval 决定策略。
P0 · Process boundary

借鉴进程级 sandbox，而非 Bash wrapper

  • 让 San 本身在受限进程中重执行，确保 read/write/bash/grep/LSP/子代理继承同一边界。
  • profile 至少区分 workspace、read-only、strict，并独立描述文件读、文件写、网络、Unix socket、环境变量继承。
  • 用户显式要求的 profile 应 fail-closed；不要照搬 Grok 内置 profile 的“应用失败后继续无沙箱”。
  • pi-iso 继续负责代码副本和合并；sandbox 负责“副本之外不能做什么”。两者不可合并成一个概念。
P2 · Latency

Prefire 只做受控实验

保留 Grok 的好部分：single-flight、前缀指纹、分支/回退立即失效、真正压缩时只消费匹配当前 generation 的结果。额外要求共享 token 预算、任务取消、最大墙钟时间和失败不重试。否则它会把“压缩卡顿”换成“后台重复烧 token”。

Do not transplant

不重做 worktree，不先做 leader

San 的任务隔离后端已比报告描述的 Grok 路径更广。共享 leader 会侵入 TUI、RPC v2、ACP 与 session ownership；眼下更小、更直接的收益是本机跨会话消息，而不是把 TUI 改造成 ACP client。

四、Claude Code 2.1.224 跨会话消息如何工作

它不是把两个上下文拼起来，也不是共享完整 transcript。发送方只传一段纯文本和 reply address；接收方把它作为“来自另一个 agent session”的低权限消息处理。

ListAgents读取活动 session 的注册文件，按 name/短 ref 展示
→
SendMessage同机连接目标 session 的 Unix domain socket；跨机走 Remote Control
→
Inbound gateaccept / hold / refuse，结合双方 permission mode 判断
→
Delivery忙时在 tool 边界注入；空闲时启动新 turn；回执返回发送方
机制2.1.224 行为安全含义
发现ListAgents / /list-agents / /peers；每个活动 session 写注册文件并绑定 inbox socket。只有能看到同一注册文件并访问 socket 的同机 session 可互达；容器文件系统天然隔离。
消息内容纯文本、sender name、reply address；不传历史、文件或权限状态。不会隐式泄漏整个上下文，也不能伪装成用户。
调度接收方忙时在 tool calls 之间读取，不中断正在执行的工具；空闲时自动启动 turn。避免半途打断非幂等工具。
入站控制crossSessionInbound = accept | hold | refuse；默认根据发送/接收 session 是否 bypass permission prompts 决策，held 对话默认五分钟过期。高权限/无人值守 session 不会默认接收普通 session 的指令。
权限peer message 不能批准权限、不能修改配置、不能执行 slash command；接收方自己的审批规则照常生效。消息是信息，不是授权。
环路保护按 sender 限流、短窗口相同消息去重、待读队列最多 50；held 队列最多 100。两个 agent 互相回复不会无限增长。
跨机器2.1.224 通过 Anthropic Remote Control 支持跨机回复；不能主动发起。同机消息不经过 Anthropic；跨机需要云端 relay 与 Remote Control 身份。
版本差异：当前 changelog 顶部已到 2.1.226。2.1.225 又增加了“按 name 主动发起到其他机器 Remote Control session”；官方跨会话文档页面仍写“跨机只能 reply”，存在文档更新滞后。讨论 2.1.224 时应以 reply-only 为准，不能把 2.1.225 行为倒灌回首发版本。

五、San 是否应做：应做，但只做薄 transport 层

San 已有大部分会话内语义。IrcBus 与 AgentRegistry 都是 process-global in-memory 单例；hub 已支持 list/send/wait/inbox、replyTo、回执、busy 时 non-interrupting aside、idle wake、parked revive。缺的是“跨进程发现与传输”，不是一套新的消息模型。

Already here

可直接复用

hub 工具契约、Snowflake message id、replyTo、delivery receipt、AgentSession 的 busy/idle 注入、agent attribution、TUI incoming card。

Missing

必须新增

跨进程 presence、同机 socket、session 名称冲突消解、入站 hold/refuse、过期与 stale cleanup、限流/去重/环路熔断。

Do not reuse blindly

权限边界需硬化

当前“父代理给忙碌子代理”的特殊路径会产生 role: user、但 attribution 为 agent 的 steer。独立 session 消息绝不能走该父子特权路径，只能作为 role: custom、attribution: agent 注入。

建议的本机 v1

~/.san/agent/runtime/peers/
  <session-id>.json       # pid、sessionId、name、cwd、socket、permissionClass、heartbeat
  sockets/<short-id>.sock # 0700 目录；socket 仅当前 OS 用户可访问

PeerEnvelope {
  protocolVersion
  messageId
  fromSessionId
  fromName
  toSessionId
  body                 // 纯文本，大小受限
  replyTo?
  sentAt
  senderPermissionClass
}
  • 工具面不扩张：继续用 hub op:list/send/inbox/wait。跨进程目标显示为稳定 session ref；to:"all" 第一版仍只广播当前进程，避免跨 session stampede。
  • 活动 session 才可达：每个 CLI 自己监听 socket，无常驻 daemon；进程退出即下线。stale presence 由 PID/heartbeat/socket 三重检查清理，不做“离线后自动执行旧消息”。
  • 默认同机：macOS/Linux 先行。目录和 socket 权限建立 same-user 边界；协议仍校验目标 session、版本、消息 id 与长度。
  • 接收策略：新增 crossSession.inbound = accept | hold | refuse | auto。auto 采用 Claude 的 permission-class 规则；headless session 对 held 消息不自动放行。
  • 权威语义：peer message 永远不是 user consent，不能回答 ask、改变 config/permission、触发 slash command、覆写 continuation authority。
  • 环路安全：每 sender token bucket；短窗口 body hash 去重；最大消息 hop/对话往返；每 session 待读队列上限；重复或超限给明确 receipt，不静默重试。
发布门槛：在 San 最近出现过跨 Agent 语义活锁和超大 token 消耗的前提下，环路限流、重复抑制和 peer message 的低权威属性不是后续增强，而是 v1 前置条件。没有这三项，不应开放 agent 自主跨 session 发送。

验收场景

  1. 启动两个真实 San CLI 进程：A 能列出 B，按 session ref 发送；B 空闲时启动新 turn，忙时只在工具边界读取。
  2. B 处于 bypass/headless 模式时，普通 A 的消息进入 held，不会直接执行；审批过期后 A 收到明确结果。
  3. 消息中的 /compact 只作为文本；消息不能批准 B 正在等待的文件写或 Bash 权限。
  4. 同 body 循环互发被去重/限流；队列满后行为确定，不触发模型无限续跑。
  5. 崩溃进程的 presence 会清理；同名 session 用短 ref 消歧，不会错投。
  6. 源码运行、npm bundle、编译二进制均通过双进程 smoke；无 native Windows 支持时明确显示 unavailable。

跨机器放在后续

San 已有 Remote Control / collab relay 方向，可在本机协议稳定后复用设备身份、E2EE relay 和 session presence。不要让第一版同时承担本机 IPC、跨机身份、离线队列与多端 UI；这会把一个薄 transport 变成新的控制平面。

六、Hindsight 当前是否在用

没有启用 Hindsight。当前实际后端是 Mnemopi。

Hindsight 官方模型是 Memory Banks + retain / recall / reflect，结合 semantic、keyword、graph、temporal 检索。San 的 adapter 已覆盖这些接口，但不能与 Mnemopi 同时成为 active backend。是否迁移应另做质量、延迟、隐私和运维对比；当前问题的答案只是：支持，但没在用。

七、修订后的路线

P0-A · AST shell policy复用 pi-ast/tree-sitter-bash；输出命令 segments、重定向事实与 fail-closed 原因，接入现有 approval。
P0-B · Process sandbox建立进程生命周期级 profile；与 pi-iso 代码树隔离叠加，显式 profile 应用失败即停止。
P1 · Local peer messaging扩展 hub：presence + UDS + inbound gate + authority guard + loop fuse；先同机，不做离线 daemon。
P2 · Prefire experiment在硬预算、single-flight、generation 校验和取消齐备后，再以 opt-in 实验验证首 token 延迟与额外 token 成本。

不再安排“新增 worktree 快照”或“重做 ACP”阶段：前者已有更完整实现，后者不是当前缺口。
