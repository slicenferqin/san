冒烟客户端 8 步全链路真实运行,7 通过 1 异常。结论:聊天窗口第一版的主数据流(握手/流式/中断/进程级恢复)当下即可开发;审批与断线续流两处需要按下文事实设计,San 侧各有一个对应的补强项。

一、三个问题的实测答案

问题实测事实对客户端的含义
审批以什么形态到达? 通用对话降级。工具审批到达为 extension_ui_request method=select,工具名与命令嵌在 title 自由文本里,options 是纯字符串数组(["Approve","Deny"]);回复 extension_ui_response {id, value:"Approve"}。代码层面 requestToolApproval 结构化接口存在但 RPC UI context 未实现。 能弹对话框、能放行,但客户端无法结构化识别"这是工具审批"(只能靠 title 文本猜),做不了风险着色、命令语法高亮、"记住此工具"等专门审批 UI。第一版可以用通用对话渲染顶住;专门审批 UI 需要等 San 侧补强(见 §三)。
断线后怎么恢复? 进程级恢复可靠:杀进程后以 --continue 重启,get_messages 返回完整 transcript(5 条 = 5 条,实测)。但没有细粒度续流协议:无 ack/游标/gap 语义,重连 = 全量重建,流式进行中断线的那条消息按持久化终态恢复。 客户端把"重连"实现为:重启进程(或重开管道)→ get_messages 全量重建 → 继续订阅事件。不要尝试增量续流,当前协议没有这个概念。对聊天窗足够;高频断连场景(移动网络、远程)体验一般。
会话模型是什么? 单进程单活跃会话;new_session/switch_session/branch 是进程内切换。实测 new_session 响应异常(未成功切换,transcript 未清空)——待查的真实 bug 线索。 desktop 多 tab 的稳妥架构:一个会话 = 一个 RPC 子进程(隔离好、崩溃不互相影响、天然并发);进程内切换只用于同 tab 的历史切换。在 new_session 修复前不要依赖它。

三、San 侧对应补强(建议顺序)

#补强内容预估
1结构化审批帧RPC UI context 实现 requestToolApproval:新帧型 tool_approval_request 带 toolCallId/toolName/tier(read|write|exec)/命令预览/策略来源,响应带六终态结算(借 v3 语义:accepted/cancelled/timed_out/unsupported/failed/disconnected)。旧客户端不受影响(能力未声明时继续 select 降级——v3 的"缺 UI 不强转布尔"原则)。2-3 天
2new_session bug冒烟已复现:RPC 模式 new_session 响应异常且会话未切换。先修——它挡着单进程内的会话管理语义。0.5-1 天
3观测 ack/游标(可后置)按 v3 形态加 snapshot-then-subscribe + 累计 ack + gap 事件 + journal 游标重连。聊天窗第一版用"全量重建"即可,此项等 desktop 遇到真实断连痛点再做,字段命名对齐 v3 以便未来概念映射。~1 周
给你开发中客户端的一句话建议:按"一会话一进程 + 全量重建式重连 + 通用对话渲染审批"起步,这三条今天就是稳的;San 侧先补结构化审批(#1)和 new_session 修复(#2),你的审批专门 UI 等 #1 落地再接。
