San v0.3 Technical Design Review · 2026-07-10

顶层方向正确，但当前技术实现文档还不能直接拆 issue：先冻结时序、状态合同和可逆投影协议

本评审对照三份 v0.3 设计文档、当前 packages/coding-agent 实现、San v0.1/v0.2 基础设施和 12 组定向测试，判断设计是否与现状匹配、哪些能力已经具备、哪些合同必须在开工前补齐。

直接结论

Conditional Approval
通过顶层设计，不通过当前“可直接实施”状态。 Brain / Experience System 的核心判断是对的：Memory 保存材料，Brain 形成判断，Skill / Workflow 固化行为；现有 TurnDigest、ContextPacket、memory backend、managed skills、San Loop ledger 也确实能复用。但技术实现文档仍缺少几项决定正确性的基础合同：稳定触发时序、唯一状态源、跨存储幂等/撤销、typed activation、scope identity、冲突模型和 legacy auto-retain 迁移。
顶层模型8.5 / 10

Brain、Memory、Skill、Risk、Profile 分层清楚，目标面向行为改变而非文本堆积。

复用现状8 / 10

关键 primitives 均存在，文档大部分基线判断准确。

实施就绪度5 / 10

主体模块尚未落地，关键不变量和失败恢复协议未冻结。

建议决策：先补一个短周期 P0 Design Freeze，再开始 M1。若直接按当前 M1-M7 拆分，最可能返工的是 store、activation、undo 和 lifecycle 四个区域。

设计中做对的部分

行为优先

把“经历改变下一次行动”设为北极星，比新增一个文本记忆库更符合现有架构。

复用而非替换

Brain 位于 TurnDigest、memory backend、managed skills、San Loop 之上，避免重写已有存搜和技能系统。

证据、scope、undo 前置

长期状态必须可追溯、可撤销、可缩小作用域，这些原则应保留为实现门禁。

Prelude 而非 base prompt 膨胀

用 hidden CustomMessage 注入 active state，与 ContextPacket 的现有模式一致。

LLM 默认关闭

deterministic capture + optional classifier 的 rollout 顺序合理，便于做可重复 dogfood。

外部系统分层基本正确

GBrain 可作为 MCP knowledge layer；Hermes Agent / OpenClaw 属完整 agent runtime。措辞应强调“San 的接入方式”，而非断言 GBrain 只能是轻量插件。

P0 必须修正

级别问题现状证据必须冻结的合同
Blocker Digest → Capture 时序写错 文档引用不存在的 #maybeGenerateContextSteadyDigest()（技术方案 237-239）；真实方法为 #generateTurnDigest()，通过 #trackPostPromptTask() 异步调度（agent-session.ts:3308-3313, 3404, 3432-3568）。 Capture 必须链接到 digest 持久化完成后的同一 Promise；同时定义下一 prompt 是否等待 capture、超时后跳过还是使用 message-span fallback。
Blocker 跨四个状态面的原子性和 undo 未定义 设计同时写 session JSONL、brain.sqlite、memory backend、managed skill 文件；memory backend 只有 search/save，无通用 delete/update（memory-backend/types.ts:79-134）。 JSONL decision ledger 为权威源；SQLite 为 materialized state；外部 backend/skill/check 全部通过 idempotent outbox projection；每个 projection 记录 pending/applied/failed/compensated。
Blocker 自动生效早于解释/撤销面 技术方案 M4 先做 activation，M5 写 skill draft，M6 才提供 /brain explain/undo（技术方案 636-651）。 任何 auto-apply 前必须已有 explain + undo + audit。M1-M3 应先 review-only；最小命令面提前到 activation 之前。
High 名称与 schema 有多个 source of truth san.brain.profile_note 与存储章节的 san.brain.profile_candidate 冲突（技术方案 165 与 387）；旧文档使用 san.experienceRouter.*、/experience、/memory inbox，新文档使用 san.brain.*、/brain。 冻结唯一命名；旧 Experience Routing 文档顶部标记 superseded，仅保留历史和需求来源，不允许继续作为 issue 拆分依据。
High 数据合同引用了不存在的字段 相关性筛选使用 taskTags，dedupe 升级使用 repeatCount，但 SanProfileNote/SanExperienceCandidate 均无这些字段（技术方案 180-222, 277-280, 465-471）。 在编码前补齐 task tags、repeat/evidence count、expiry、conflict/supersede、scope key、sensitivity、revision 和 projection 状态。
High Scope 只有枚举，没有身份 合同只有 user/project/repo/session，无 userId/projectId/repo identity；M1 又只实现用户级 store，却要求 M4 注入 project/repo state。 定义 scopeKind + scopeKey，repo 建议使用规范化 remote/worktree identity，而不是 cwd basename；定义移动目录、worktree、fork、symlink 的迁移语义。
High state_patch 与 activationRule 是自由文本 SanStatePatch.content、activationRule 均为 string（技术方案 197-203），随后直接进入 hidden prompt。 改为 typed selector + typed action；模型只能提议，不得生成可执行规则字符串。注入文本必须按“不可信历史数据”转义，明确不能覆盖当前用户指令、项目规则和工具结果。
High Legacy auto-retain 会绕过 Brain 决策 memory.backend 默认 off，但一旦选择 Mnemopi/Hindsight，autoRetain 默认 true（settings-schema.ts:2220-2239, 2349-2369, 2652-2655），按 N 轮直接 retain transcript。 Brain dogfood overlay 必须显式关闭 legacy autoRetain；长期写入只能由 Brain projection 发起。定义已有用户配置的迁移和兼容模式。
High Managed skill 没有 draft 和安全回滚协议 writeManagedSkill() 写入 active managed-skills 目录；deleteManagedSkill() 只能删除当前目录，没有 revision/owner/CAS（managed-skills.ts:152-255）。 草案必须存 Brain store 或独立 draft root；批准后带 decisionId/revision 写 active skill。Undo 只能回滚自己创建的 revision，不能覆盖后续人工或其他进程更新。
High Durable schema 迁移无法按文档执行 接口有 schemaVersion，SQL 表草案没有 schema_version 列（技术方案 180-221, 396-401），却要求逐 row normalize/migrate 和 future-version unsupported。 选择并写清：库级 PRAGMA user_version 原子迁移，或 row-level schema_version。不要同时承诺两种语义。
Medium Profile dedupe 与冲突被混在一个 key Profile key 使用 type + scope + subject + predicate；碰撞语义直接合并证据和提高/降低 confidence（技术方案 271-284）。 拆分 claimKey（同一命题槽位）与 dedupeKey（同一值）；“默认 HTML”改成“默认 Markdown”必须形成 conflict/supersede，不得合并为同一事实。
Medium 全局上下文预算缺失 Brain、ContextPacket、San Loop role context 分别声明 token cap；当前 buildSanLoopRoleContext() 只设置 trimmed: 1，并未真正裁剪 content（san-loop/context.ts:100-154）。 建立统一 injection planner，按 authority 和 cache priority 分配总预算；任何 layer 不得仅打标不裁剪。
Medium San Loop evidence 缺 attempt/batch 语义 retry 会持续追加 assignments/results；Supervisor 接收 run.workerResults 全集而非当前 batch（runner.ts:218-285），result schema 无 attempt。 经验 collector 只能消费最终 accepted attempt，并用 runId + assignmentId + attemptId + reviewId 做 provenance；否则旧失败与新成功会重复固化。

状态原则：Candidate 是建议；Decision 是不可变审计；Active State 是 materialized view；Memory/Skill/Check 是可失败、可重放、可补偿的 projection。不要让任一外部投影反过来成为 Brain 的 source of truth。

推荐架构

1Evidence

TurnDigest、用户纠偏、San Loop accepted review、工具/文件 refs。

2Candidate Ledger

append-only；只记录建议和证据，不产生行为变化。

3Consolidation

typed policy 计算 scope、claim、confidence、impact、conflict。

4Decision + Active Store

事务内写 decision、revision、active materialized state、outbox。

5Activation Planner

按 role/task/scope/authority/预算选择 state，并渲染安全 prelude。

6Projections

Memory、managed skill、check suggestion；幂等执行、失败可重试、undo 可补偿。

建议实施顺序

阶段内容退出条件
P0冻结命名、scope identity、typed activation、source-of-truth、outbox/undo、legacy autoRetain 迁移、prompt precedence。三份文档无冲突；数据合同能表达所有后续章节引用字段；失败矩阵有确定结果。
M1Candidate/Decision ledger + SQLite materialized store；只读命令 /brain inbox/profile/explain。append/list/resume/migrate/idempotency/concurrency 通过；不改变 agent 行为。
M2Digest 完成后 deterministic capture；接入 accepted San Loop review；仍为 review-only。固定 fixtures 输出稳定；同一 evidence 不重复；旧 retry attempt 不进入 active candidate。
M3已完成（2026-07-10）：Consolidation、conflict/supersede、approve/discard/undo；仍不注入 prompt。状态转换幂等；JSONL Decision 可重放到 SQLite；undo 后可继续递增 revision；Brain 定向测试与 bun check 通过。
M4已完成（2026-07-10）：Brain prelude activation、scope/role/relevance filtering、安全 typed rendering、Brain + ContextPacket + San Loop 全局预算和 activation audit；保持显式批准，不实现 auto-apply。只在真实用户下一轮注入；当前用户冲突时跳过；prompt injection、scope/role isolation、单项预算和总 token cap 测试通过。
M5Memory projection、managed skill draft/approval、check suggestion；legacy autoRetain 迁移。外部写入失败不影响主 turn；重试不重复；补偿和人工修改冲突有明确处理。
M6Policy-aware recall、10+ turn dogfood、真实会话报告、默认策略评估。候选数受控；不相关任务无污染；误固化可解释、可撤销；四种 backend 均有降级证明。
M3 开发记录：brain/consolidate.ts 负责 duplicate/conflict 分组和 active payload 证据合并；brain/commands.ts 生成不可变 approve/discard/supersede/undo Decision；/brain consolidate 只报告、不静默批准。验证覆盖冲突替换、重复命令幂等、undo 后续 revision、session ledger 重建和 slash command 闭环。
M4 开发记录：brain/activation.ts 对已批准 active state 执行精确 scope、role、task、command、file glob、language 和 risk selector；只渲染 typed action，并对历史字段做控制字符清理、长度限制和 JSON/XML 安全编码。AgentSession 仅在真实用户下一轮注入 hidden Brain prelude，按 San Loop > Brain > ContextPacket 权限顺序执行共享 token cap，并写入不可变 san.brain.activation 审计。验证覆盖当前用户覆盖、跨 scope/role 隔离、恶意标签与工具语法、整项裁剪、总预算和 synthetic turn 不注入。
最关键的顺序调整：把 explain/undo 提前，把 auto-apply 和 skill 激活后移。系统先拥有控制面，再拥有自动改变长期行为的能力。

验收门禁

  • 时序：同一 turn 的 digest/capture 是否能保证在下一次 activation 前完成；超时行为可重复。
  • Crash matrix：decision 已写、SQLite 未写；SQLite 已写、backend 未写；skill 已写、activation 未写等每个断点均可恢复。
  • 并发：两个进程同时 consolidate 同一 claim，不产生重复 active state 或覆盖人工 skill。
  • Scope：同名 repo、worktree、fork、移动目录、symlink 不串状态。
  • 冲突：新偏好覆盖旧偏好时形成 supersede，不通过 evidence merge 增强两个相反结论。
  • 安全：历史文本中的命令、XML 标签、工具指令不能升级为当前指令；Brain state authority 永远低于当前用户、项目规则和真实工具结果。
  • 预算：Brain + ContextPacket + San Loop 总注入量受一个真实执行的 cap 控制。
  • 可控性：任一 auto-applied 行为在同版本内均可 explain、undo、降权、缩 scope。
  • 兼容：Brain dogfood 开启时 legacy Mnemopi/Hindsight autoRetain 不得旁路写入。

文档修订建议

  1. 将顶层设计保留为主文档；技术实现方案升级为唯一 implementation spec。
  2. 在 Experience Routing 需求文档开头增加 Superseded by Brain Technical Implementation，删除可被误用的配置、命令和 custom-type 规范。
  3. 修正 #maybeGenerateContextSteadyDigest() 为真实 lifecycle，并画出 Promise/turn ordering。
  4. 新增“状态权威与投影协议”“Prompt authority”“Scope identity”“Crash/undo matrix”四个章节。
  5. 统一 profile_candidate/profile_note、/brain//experience、san.brain/san.experienceRouter。
  6. 把 M6 命令面拆分：read/explain/undo 提前，skill/hook/check 管理命令留在后期。
  7. 外部系统措辞改为“San 将 GBrain 作为 MCP knowledge plugin 使用”；明确 Hermes 指 NousResearch/hermes-agent，避免与 Hermes 模型家族混淆。

最终判断

可以开始 P0，暂不建议开始 M1 编码。 这不是方向问题，而是控制面问题。现有代码已经给 v0.3 提供了足够好的地基；当前最大的风险不是“做不出来”，而是同时接入 JSONL、SQLite、memory backend、skills 和多角色上下文后，行为已改变但无法证明哪条状态生效、无法安全撤销、也无法在崩溃后恢复。P0 收敛后，M1-M4 可以沿现有结构增量落地，不需要重写 v0.1/v0.2。
