3.1 P0 — 中途静默停机（产品验收致命）

用户在 12:34、01:35、01:42×2、02:59、03:00、03:01 反复追问进度/为何停下。 全会话 stopReason=stop 仅 3 次（评估答复 + 两次进度答复），大量工作以 stopReason=toolUse 链结束而没有用户可见收尾。

  • 第一次静默停（~10:40，L428–L430 之后）：正在做 v16.4.5 Model Hub 迁移编辑， 下一事件直接是 san.context_plan（qualityGate=hard_pressure）+ turn_digest， 没有 assistant 文本向用户交代。用户 2 小时后才发现停了。
  • Agent 自述原因（L505）：「上一轮错误地把进度汇报当成了可停点」。这是行为层 bug，不是仓库阻塞。
  • 后续即便承诺「不再中途汇报」，仍在 v16.5.2 批量 read 冲突后再次断掉，且被 compaction / dispose 打断。
验收缺口：长任务缺少「连续执行合约」——没有 turn budget / 未完成 todo 自动续跑 / 用户可见的 running checkpoint。Context Steady 的 hard_pressure 与 turn 切断耦合后， 表现为「做一点就停」。

  • 从第二次用户交互起，几乎每个 context_plan 的 qualityGate 都是 hard_pressure， reasons 固定包含 protected_entries_exceed_message_budget / control_band / burst_ceiling。

  • compaction 3 次；最后一次摘要约 1.94MB 写入 JSONL，用户在压缩期间连发 3 条消息， 会话以 session_exit dispose 结束，没有交付态答复。
  • turn_digest 的 tokenStats 累计 input 已到 ~1.75M（含 cacheRead 统计口径），说明长会话成本与噪声都很高。
Context Steady 在本会话更像「持续告警 + 强制压缩」，未能把「长 merge 会话」压回可控执行环。 保护条目过多导致 budget 形同虚设，是验收里值得单开的 CS 缺陷。

8. 总评

这是一次「能力上半场很强、执行下半场失稳」的 dogfood。 San 在评估、隔离、分里程碑、冲突工具上证明了价值；但在 连续执行、错误恢复、上下文压力、验证收敛 上未达可验收标准。 最近几轮错误不是「偶发一次 merge 冲突」，而是 静默停机 × Provider 风暴 × 契约测试红 × hard_pressure 切断 的叠加。

产品优先级建议：先修 A1（连续执行）与 A2（provider 退避），再修 A3（CS hard_pressure 策略）； A4/A5 作为 coding-agent 工作流 hardening。业务上用新会话收尾 v16.5.2，不要复活本会话硬扛。
