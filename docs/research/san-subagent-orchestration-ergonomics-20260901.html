San 子 agent 编排体验诊断

2026-09-01 · 范围: packages/coding-agent 的 task / Agent Registry / AsyncJobManager / IRC-Hub / San Loop · 性质:架构研究与迁移建议
结论先行: 当前“不顺手”主要不是上下文稳态，也不是子 agent 能力不足，而是同一个协作过程被拆成了多个需要模型自行选择的控制平面。task负责启动，hub负责联络与作业控制，San Loop 负责带验收和重试的流程；Registry、JobManager、IrcBus、ledger 又分别保存不同层次的状态。可靠性在底层是增强的，但入口处缺少一条默认、可预测的“怎么做”路径。这里的“主要”是基于代码结构的架构判断，不是已有用户研究的统计结论。

一、先把三个词分开

用户说“有 subagent、IRC、task”，实际上是在把角色定义、执行入口、通信通道放在同一层比较。它们不是三个互相替代的实现。

用户看到的词代码里的真实职责它启动新 agent 吗适合解决的问题
subagent既可指一个 agent 定义，也常被用来指 Registry 中的一个子 agent 实例。定义由 frontmatter 描述名称、工具、模型、是否 blocking、能否继续 spawn 等；实例由稳定 agentId 标识。不是入口本身“谁来做、能用什么、以什么约束做”。
taskTaskTool.execute。解析一个或多个 assignment，做 contract admission，决定同步/后台执行，分配输出 ID，并把后台任务注册到 AsyncJobManager。是“现在派一个人或一批人去做一次工作，并收结果”。
IRC进程级 IrcBus 的 peer mailbox；Hub 的 send / message wait 使用它。发送不会创建新 agent，可唤醒 idle 或 revive parked agent。否“我已经知道这个 agent，给它补充信息、追问或恢复工作”。
San Loop独立的执行编排器：按模式调用 commander、worker、oracle、supervisor，持久化 run 状态、验收门、预算和 retry/blocked/pass 终态。会启动角色 subprocess，但不是普通 task 的另一种展示“这件事必须按目标、验收、复核和重试闭环完成”。
关键判断: task 与 IRC 不重复。task 是 dispatch，IRC 是 follow-up / steering。真正重叠的是：两者都让模型面对一个可持续存在的 agent；San Loop 又为“派发 + 复核 + 重试”提供了另一条入口。问题不是删掉其中一个，而是把边界和默认选择说清楚。

二、当前实际调用路径

2.1 普通 task: 一次派发，结果异步回传，实例可继续存活

模型
  │ task({agent, task} 或 task({context, tasks[] }))
  ▼
TaskTool.execute
  ├─ 解析默认 agent（未指定时通常是 task）
  ├─ contract registry admission / duplicate guard
  ├─ 按 agent frontmatter 判断 blocking
  ├─ blocking → 当前调用内同步执行
  └─ non-blocking + async manager → 注册 background job
          │
          ├─ job id（当前 task 路径显式使用 agent id）
          ├─ Agent Registry: running → idle / parked
          ├─ 自动交付 task-result
          └─ 后续可 hub.send(agentId) 继续

这条路径的优点是强：批量任务有共享 context，contract 可防止重复派发，后台任务有 owner 隔离，完成后结果自动送回，agent 仍可被查询或恢复。摩擦也集中在入口：

  • 一次 task 调用不一定是同一种等待语义：agent 可能声明 blocking: true，其他项则成为后台 job；同一批次甚至可以混合。
  • 模型需要理解 batch、async、blocking、recursion、isolation 以及何时用 Hub；这些都是合理能力，但不是一个 novice-first 的单一动作。
  • “结果已完成”与“agent 已终止”不是同一件事。Registry 明确保留 finished agent 为 idle，必要时变成 parked，只有显式 release 才移除。

2.2 Hub: 一个工具名承载三个域

hub
  ├─ messaging: list / send / inbox / wait(from?)
  ├─ jobs:       jobs / wait(ids?) / cancel(ids?)
  └─ process:    launch / ps / logs / send(name) / wait(name) / stop ...

Hub 源码明确把自己定义为“single agent-coordination surface”，但内部 renderer 和 dispatcher 仍要根据参数判断是 messaging、job 还是 process。尤其是 wait 和 send：

调用形状实际含义模型必须先判断什么
wait({from})等待 peer message；可涉及本进程或 san:<12 hex> 远端 session。我在等人回信。
wait({ids})等待自己可见的后台 jobs。我在等一次已派发的执行。
wait({name})等待受管进程的 readiness / exit / pattern。我在等一个外部进程。
裸 wait在合适条件下同时考虑 job 和 peer liveness，并按 poll ladder 返回。我是否真的已经“无事可做”？

实现已经处理了很多边界：job 可见性按 owner 限制，jobless running agent 会进入 roster，message wait 有 liveness 与 timeout，后台任务结果不需要轮询。可是这些规则越完整，模型就越需要先构造一份正确的内部状态图；这正是“能力很强但用起来不丝滑”的来源之一。

2.3 San Loop: 另一条带政策的执行图

/solo   → worker
/team   → commander → worker → supervisor
/council→ commander → worker → oracle → supervisor

每次角色调用:
  role-specific prompt + role context
  → runSubprocess（严格工具白名单、模型覆盖、硬 token/cost/time/request budget）
  → 结构化结果
  → ledger transition
  → review / retry / blocked / pass

San Loop 不是普通 task 的“高级结果渲染”。createSanLoopTaskAgentExecutor按角色直接调用 runSubprocess，并给 commander、worker、supervisor、oracle 分配不同工具白名单；orchestrator 自己维护 pipeline、assignment、review 和预算。它因此能提供普通 task 没有的闭环，但也产生了第二套“如何派人、如何等待、如何判定完成”的心智模型。

当前默认配置进一步放大了断裂：

配置当前默认对体验的影响
task.eagerdefault（由模型决定是否委派）系统没有在入口替模型选择“自己做 / 派发 / 走闭环”。
task.batchtrue普通 task 默认偏向批量 shape；能力更高，但简单调用的 schema 更重。
task.isolation.modenone普通子 agent 默认共享工作区；隔离是专家选项，不是默认工作流。
san.executionLoop.enabledfalse，且标为 expert最完整的目标—验收—复核闭环不是默认路径；用户只有知道它存在，才会主动进入。
task.maxRecursionDepth2有安全护栏，但又增加一个模型需要理解的深度维度。

三、为什么会“不顺手”

原因 1 协议选择被推给了模型，而不是由意图决定

task 的真实行为由 async 是否可用、agent 是否 blocking、是否 batch、深度是否允许、是否有 contract 等条件共同决定。task.eager=default 又明确让模型自行决定何时委派。模型必须先决定“我要哪种执行协议”，才能开始解决用户问题。

这会把一个用户意图拆成两次推理：先选控制平面，再做任务本身。上下文压缩可能放大它，但即使上下文完全稳定，选择成本仍然存在。

原因 2 一个 agent 同时有多个身份和多个 ID

当前系统至少区分：

  • agent definition: task、scout、reviewer、san-worker 等能力/角色类型；
  • agent instance: Registry 中可 running、idle、parked、aborted 的 agentId；
  • job: AsyncJobManager 中一次后台执行及其 owner；
  • task contract: 用于 scope、root session、task、agent 推导和去重的身份；
  • message: IRC 或跨 session 传输的 mail；
  • San Loop run / assignment: 一次闭环和其工作节点。

这些对象在实现上各有必要，不能简单合并。但当前 task 结果、Hub jobs、Agent Hub、San Loop ledger 分别向模型或用户暴露不同切片；模型需要自己完成 ID 翻译。普通 task 中 job id 当前显式使用 agent id，只能缓解一部分问题，不能消除“执行、实例、合同、消息、闭环”不是同一对象这一事实。

原因 3 “完成”是两个事件：结果完成，生命周期未必结束

后台 task 完成时，结果会自动交付；但 Agent Registry 保留该 agent 为 idle，之后可能 parked 并可 revive。这样设计是为了支持“完成后追问”，可靠性是对的；问题是主路径没有用一个统一的用户语义解释它：

task-result arrived  ≠  agent released
job completed        ≠  peer no longer addressable
parked               ≠  lost

如果模型把“completed”理解成完全终止，可能重复 spawn；如果把 idle/parked 理解成仍在主动工作，可能无意义地 poll。这里需要的是统一呈现和命名，不是删掉可恢复生命周期。

原因 4 Hub 的统一工具名反而隐藏了域边界

把消息、后台 jobs 和受管进程放进同一个工具，减少了工具数量，却把参数形状变成了隐式路由。wait 在三个域里都合法；裸 wait 还可能同时等待 jobs 与 peer。对人类 UI 这是可接受的高级入口，对模型则是一个容易被误用的多态协议。

尤其当 task 已经提示“结果会自动交付，不要轮询”，而 Hub 又提供 wait/jobs/cancel，模型很容易在“等待结果”“等待消息”“检查是否卡住”之间反复切换。现有 smart poll ladder 只能降低轮询成本，不能解决语义选择。

原因 5 San Loop 的质量闭环没有成为普通委派的默认升级路径

San Loop 已有很清楚的政策：solo、team、council；每种模式有固定 pipeline、retry、worker 上限、review 角色和预算。可是它由独立 slash command 进入，且默认关闭；普通 task 不会因为 assignment 有验收标准就自动进入这条流程。

因此系统同时存在两种合理但断开的答案：

  • “派一个 subagent 做完给我结果”——task；
  • “把这件事按计划、证据、复核和重试跑到终态”——San Loop。

用户或模型必须自己知道哪一种才适合当前目标。对于复杂任务，这个选择本身就是额外工作。

原因 6 可靠性机制很多，但默认呈现没有收敛成三个用户状态

San 的底层已经有 contract admission、owner-scoped jobs、idle/parked revive、cross-session delivery、role budgets、ledger 和 acceptance gates。这些机制彼此并非重复，且大部分是必要的。但 task、Hub、San Loop 各自输出自己的状态词和下一步提示；如果主路径把这些内部差异直接交给模型，就会出现“机制都在，动作不确定”。

应当把内部状态投影成统一的三种用户可理解状态：正在做什么、做完了什么、卡在哪里以及下一步是什么。ID、contract、ledger、receipt 等细节留在展开层或 stats，不进入默认主路径。

四、建议的统一编排模型

不建议删除 task、IRC 或 San Loop。建议统一的是心智模型和读模型，不是把所有状态强行塞进一个状态机。最保守的边界是：TaskTool 负责 dispatch，Hub messaging 负责 peer communication，San Loop 负责 policy-driven workflow；Registry 和 JobManager 继续做内部生命周期，不能被互相越权替代。

4.1 三条语义通道

通道唯一问题入口完成语义禁止承担的职责
Dispatch谁来执行一次工作taskassignment 产出结果；默认自动交付。agent 是否仍可追问是另一个生命周期问题。不负责 peer 对话，不自己实现 review/retry ledger。
Message如何联系已知执行者hub.send / hub.inbox / message wait消息已投递、未投递或等待超时；不等同于工作完成。不创建新 agent，不冒充 job status。
Workflow如何让目标经过验收后才算完成/solo / /team / /council 或未来的显式 workflow mode通过、阻塞、需要用户、失败或预算终止；由 Loop policy 决定。不把每个 role 调用重复登记成普通用户 task。

4.2 一个逻辑对象，多个内部引用

不需要立刻新建一套持久化系统；先规定所有主路径都按同一份逻辑关系解释已有字段：

Coordination / Objective
  ├─ mode: direct | batch | workflow
  ├─ objective / user-visible summary
  └─ assignments[]
       ├─ contractId + scopeId       （去重与作用域，不是人类称呼）
       ├─ agentId                    （用户/模型后续联系的主句柄）
       ├─ jobId                      （后台执行句柄，详情层）
       ├─ runId / assignmentId       （San Loop 仅在 workflow 中出现）
       ├─ messageIds[]                （协调事件，非完成证据）
       ├─ status                      （统一读模型）
       └─ result / nextAction

重要的是不把这些 ID 伪装成同一个 ID。统一的做法是指定一个主句柄：普通 follow-up 只说 agentId；jobId、contractId、runId 放入详情层，并在内部保存明确映射。当前 task 路径已经有 agent/job 映射，San Loop 需要把 run/assignment 映射到同一份 activity projection，而不是另造一个“万能 agent”。

4.3 默认决策树

用户给出普通可拆工作
  └─ 默认走 task
       ├─ 单项 → 一个 agent
       ├─ 明确互相独立 → task batch
       └─ 需要补充信息 → hub.send(agentId)，不是重新 task

用户明确要求“验证、复核、失败重试、直到终态”
  └─ 走 San Loop
       ├─ 小而单一 → solo
       ├─ 有并行分工 → team
       └─ 有争议/高风险 → council

用户给出远端 session 地址 san:<12 hex>
  └─ 走 hub messaging 的 cross-session adapter
       └─ 不把远端 session 当本地 job 或本地 agent

这个决策树的原则是：默认解决问题，不默认让用户学习编排系统。San Loop 在 benchmark 证明成本可接受前不应贸然全局开启；但它应当在“用户明确提出闭环目标”时成为清晰、可发现的升级路径，而不是与 task 并列、互不相通的隐藏功能。

五、与现有架构约束核对

已有约束建议如何兼容不能做什么
AgentLifecycleManager 是 idle ↔ parked 的唯一 owner统一 projection 只读 registry；Hub 的 send/focus 调 lifecycle API，不直接写 status。不能让 JobManager 或 Hub 自己“修正” agent 状态。
Task contract registry / runtime scheduler 负责 admission 与去重普通 task 继续在 admission 边界建立 contract；workflow 通过 metadata 映射 assignment，不绕过 duplicate guard。不能用“看起来相同的任务文本”替代 contract identity。
AsyncJobManager 有 owner-scoped 可见性和取消权activity projection 保留 owner 过滤；父 agent 看到自己的 jobs，子 agent teardown 不影响父 jobs。不能为了“一个总列表”放开跨 owner cancel/inspect。
IrcBus + CrossSessionClient 分属本地与跨 session 通信统一为 Message 通道的两个 transport；主句柄仍是 peer address，跨 session 继续用显式 san:<12 hex>。不能把远程 session 伪装成本地 Registry ref。
San Loop 角色有严格工具白名单和自己的预算/重试/ledger保留 role executor 直调 runSubprocess；只把 run/assignment 投影进统一活动视图。不能把每个 commander/worker/reviewer 再包一层普通 task，造成双重 retry、双重预算和双重结果交付。
没有跨 Registry、Job、IRC、ledger 的 XA 事务银弹采用幂等事件和最终一致读模型；每个 authority 继续拥有自己的原子状态转换，投影可重建。不能声称一次“spawn”同时原子提交所有状态；失败恢复必须可重放、可解释。
主路径只应显示三种用户状态主 TUI 统一显示正在做什么、完成了什么、卡在哪里；技术 ID 和原始记录放展开层。不能把 evidence、receipt、scope、gate、ledger 等机制词汇变成默认 UI。
最重要的架构取舍:统一的是读模型、提示、入口决策和主句柄，不是统一所有写入 authority。把 Registry、JobManager、IrcBus、San Loop ledger 合成一个巨型 AgentManager，会丢掉现有的 owner 隔离、生命周期边界和 workflow 专属预算，反而制造更难恢复的状态耦合。

六、近期改造优先级

P0 让模型先选对通道，不新增机制

  • 重写 task 和 hub 的模型说明，用一句硬边界固定语义：task 创建新执行；hub.send 只联系已有 agent；普通 task 结果自动交付，不为取结果而轮询。
  • 在 Hub 的 schema/提示中把 messaging、jobs、process 三个域显式分组；对 wait 说明 from、ids、name 的唯一含义，裸 wait 只作为“确实无其他工作可做”的兜底。
  • 普通 task 结果的主文案只保留一个后续句柄：agentId。jobId 放到展开详情；不要让模型同时把两个 ID 当成两个需要操作的对象。
  • San Loop 命令在关闭时给出“适合什么任务”的短说明，而不是让用户从设置名猜出它是 task 的替代品。
  • 建立最小行为观测：每次 dispatch 后统计 task→result、result→follow-up、hub wait/send 次数、loop terminal reason。没有这些数字，不应凭体感改默认值。

目标:不改底层生命周期，不改可靠性保证，先消灭模型对“该调用谁”的猜测。

P1 建一个只读的统一活动投影

  • 基于 Agent Registry、AsyncJobManager、Task contract snapshots 和 San Loop snapshots，产出一份 CoordinationSnapshot；它是 read model，不夺走任何组件的写入权。
  • Task result、Hub jobs、Agent Hub、San Loop 状态都消费同一份 assignment/activity 行；每行优先显示 agentId + activity + user status + nextAction。
  • 为核心转移补行为测试：后台 task 完成后仍可 idle follow-up；parked agent 经 hub send 能 revive；job owner 过滤不泄露；San Loop retry 最终进入 pass/blocked/needs-user；loop role 不产生普通 task 的二次交付。
  • 把 task 的一次性 assignment 和 workflow 的 assignment 映射到同一活动行，但保留不同的完成策略；“活动统一”不等于“执行语义相同”。

目标:用户只看一张活动地图，内部仍由各 authority 管理自己的状态。

P2 只有数据证明入口仍有摩擦，才引入显式模式字段

  • 若 P0/P1 后模型仍频繁在 task 与 loop 之间选错，再在高层 assignment 上增加显式 mode: direct | workflow（命名以实际 schema 设计为准），不要继续依赖 settings、agent frontmatter 和 prompt 拼接来推断。
  • 可以把“有验收标准但没有复杂复核”的普通任务映射到轻量 direct 路径；需要 retry/review/预算闭环时才升级 workflow。不要把所有 task 默认包进 San Loop。
  • Agent Hub 从“表格/聊天两个视图”进一步收敛为“活动、等待后续、已完成、需要处理”四类可理解区段；技术详情继续折叠。
  • 跨 session 继续沿用 Hub message；只在统一活动投影已经稳定后增加远端活动的只读呈现，避免提前把两个 Registry 合成一个跨进程状态库。

目标:避免为了修入口摩擦而新增第四套编排抽象。

七、验证标准

这份诊断当前是结构性判断，下一步需要真实 dogfood 证据。验证不应只看“代码能运行”，而要看模型是否少做了错误的控制面切换。

场景应该观察到的行为失败信号
普通单项委派一次 task；结果自动返回；需要追问时一次 hub.send；不为拿结果反复 jobs/wait。task 后连续裸 wait，或结果到达后重新 spawn 同一 assignment。
批量独立调查一次 batch；每项有清晰 agentId；父会话只等聚合结果，不逐项手工轮询。批量被拆成串行 task；模型混淆 item、job、agent；重复派发。
完成后追问 / parked revive用 agentId 发一条消息；收到 delivered/woken/revived 后继续；不新建替代 agent。把 idle/parked 当成丢失，重复创建；或对不存在的 job 反复 cancel。
复杂修复闭环明确进入 team/council；commander、worker、reviewer 各走自己的预算和状态；最终 pass/blocked/needs-user 可解释。普通 task 与 Loop 同时包裹；双重 retry；模型在两个结果源之间循环。
跨 session 协作用 roster 中的精确 san:<12 hex> 地址发消息；远端只是 message peer。把远端地址当本地 job id、尝试本地 cancel，或依赖猜测的 session ID。

建议把指标接到已有 north-star / overnight dogfood 体系：无人值守终态率、终态可解释率、预算内完成率之外，加上“控制面切换次数”和“无效等待次数”。这两个指标是本问题的直接量化，当前尚无基线，需先采样再设阈值。

八、不应做的事

  • 不要删除 IRC。它承担已有 agent 的 steering、唤醒、revive 和跨 session 消息，不能由 task result 替代。
  • 不要把所有 task 自动升级为 San Loop。Loop 有角色调用、预算、review 和 ledger 成本；简单调查不应承受这套流程，且当前默认关闭本身说明它仍是专家路径。
  • 不要把 Registry 和 JobManager 合成一个生命周期表。agent 的存活/可恢复性与一次 job 的执行/取消权是两个不同边界。
  • 不要再造一个“万能 orchestrator”工具。先统一 assignment 的解释和活动投影；增加第四入口只会把选择成本继续转移给模型。
  • 不要把内部机制词汇搬到主 UI。可信度来自系统正确处理细节，不是让用户学习 contract、scope、gate、receipt 或 ledger。

九、一句话结论

San 现在的问题不是“子 agent 太少”，而是子 agent 的启动、通信、生命周期和质量闭环没有被收敛成一个默认协议。短期应保留三套底层能力，先让模型和用户稳定遵循一条路径：task 派发，hub 追问，San Loop 闭环；Registry、jobs、ledger 退回内部实现。先用 P0 的提示/入口修正和 P1 的统一活动投影验证摩擦是否下降，再决定是否需要显式 workflow mode 或调整默认值。
