一、magic-context 是什么

1.1 定位与设计目标

magic-context 自称「coding agent 的海马体」:一个挂载在 OpenCode / Pi / Oh My Pi(OMP) 三个 harness 上的上下文管理与长期记忆插件,属于 CortexKit 插件家族(另有 AFT「感觉运动皮层」与未发布的 Alfonso「前额叶」)。它的口号概括了全部目标:"Unbounded context. Memory that manages itself. One session, for life."——让一个会话跑数周、数月甚至数年,永不因 compaction 停顿,也永不遗忘。

GitHub 仓库描述与 README.md("What is Magic Context?"、"Part of CortexKit" 两节)。

它对问题的叙事是:coding agent 患有「顺行性遗忘症」——每个任务都是一次新雇佣,任务中途还会被 compaction 打断并悄悄丢失已知信息。它给出两条承诺:agent 永远不停下来管理上下文(无 compaction 停顿),以及永远不遗忘(跨会话、跨 harness 的项目记忆)。

值得注意的排他性设计:magic-context 要求端到端独占上下文管理权——安装时关闭宿主内建 compaction(OpenCode 的 compaction.auto/prune、OMP 的 compaction.enabled 与 memory.backend),检测到其它上下文管理插件(DCP、oh-my-opencode 的三个 hook)时 fail-safe 自禁用。理由是「两个上下文管理器会双重压缩历史并打爆 prompt cache」。

README.md "Quick start" 与 "Compatibility with other context-management plugins" 节。其中 OMP 适配要求 OMP ≥ 17.1.7,并声明「honors OMP profiles、PI_CODING_AGENT_DIR」——即它直接触碰 San 上游 oh-my-pi 的 compaction/memory 配置面。San 作为改名后的 fork 是否仍在其检测范围内,未核实。

1.2 核心机制

其根 ARCHITECTURE.md(约 41KB,工程细节密度极高)给出了完整机制图。骨架是:插件在每次 LLM 调用时重写 message array 与 system prompt,变换本身不做任何 LLM 调用,重活全部交给后台隐藏子代理。

(a)m[0]/m[1] 双块缓存稳定注入

注入内容拆成两个消息块:m[0] 是稳定基线(项目记忆、ARCHITECTURE.md/STRUCTURE.md 文档、按 decay 渲染的分舱历史,截至上次物化),常规轮次永不改变;m[1] 是易变增量(新记忆、新分舱、用户画像增量)。关键创新是把 m[0] 的重建时机(HARD fold)围绕「bust 分类学」组织:只有当 provider 缓存本来就要失效(模型切换、system prompt 哈希变化、闲置超过缓存 TTL)或基线内容真正变化时才折叠;新分舱、新记忆等日常增长刻意不触发折叠,只进 m[1],等下一次天然 bust 时搭便车合并。另有压力兜底:m[1] 相对 m[0] 过大(约 20% 历史预算)时在下一个 bust 点强制重折。

ARCHITECTURE.md "m[0]/m[1]"、"mustMaterialize (HARD fold) triggers" 节。

(b)Historian 分舱压缩(后台异步)

后台 historian 子代理(推荐用便宜甚至本地模型)把旧原始历史压成分层分舱(tiered compartments):每舱携带 4 个 paraphrase 层级(p1 详尽 → p4 仅锚点)、importance 分数(衰减率语义)、episode 类型。触发按阈值相对压力(context_limit × execute_threshold × 5%,夹在 5k–50k)。「protected-tail boundary」用真实 token 尺寸(而非用户轮数)决定哪段前缀可压,尾部保护;未闭合的工具调用对(open tool arcs)只在「近期」时挡住边界,过期的死工具调用不会永久冻结 historian;已闭合的工具对保持原子,不被舱边界切开。压缩不阻塞前台——这是它「无 compaction 停顿」承诺的实现基础。

ARCHITECTURE.md "Historian compartment flow" 与 "Protected-tail boundary" 节;README.md "Context management" 节。

(c)确定性 decay 渲染(无 LLM)

每次组装 prompt 时,由确定性公式为每个分舱选择渲染层级:半衰期 H = H50·2^((I−50)/D)/max(p, 0.10)(H50=24、D=25,I 为 importance,p 为本 pass 的预算压力),对数成本层级边界 [0.201, 0.729, 1.322, 2.587]。越旧、越不重要、压力越大的舱降到越粗的层级,过归档线渲染 p4 或丢弃。因为是确定性规则,同样的历史永远渲染出同样的字节——旧历史「平滑淡出」而非「掉下悬崖」,且自动适配不同模型窗口。

ARCHITECTURE.md "Render (decay)" 节(decay-render.ts、decay-curve.ts);README.md "Decay rendering"。

(d)Replay-everything 缓存不变量

所有持久性消息变换(reasoning 清除、噪声剥离、caveman 压缩、drop 占位符等)在每个 transform pass 上确定性重放,保证线上字节逐位一致,provider prompt cache 存活整个会话。这是「插件没有 loop 控制权」的补偿:它无法保证宿主传入的数组不变,只能保证自己的变换幂等。

ARCHITECTURE.md "Overview" 节第三条 tenet。

(e)Agent 参与式缩减与应急梯度

  • ctx_reduce:给工具输出打 §N§ 标签,agent 可主动标记过期内容;drop 排队并 cache-aware,只在缓存安全时刻应用。配套两条 nudge 通道(工具输出附注 + 一次性合成用户消息)。
  • Smart drops(可选):自动压缩「已被覆盖的旧 edit」为 edit_marker(保留 filePath 与 40 字符区域提示,输出替换为 [dropped §N§])、丢弃过期控制面输出(旧 todowrite 等)。
  • 分层应急驱逐(≥85% 压力带):工具输出按层级 oldest-first 驱逐(T3 杂项 → T2 编辑/搜索 → T1 导航),最新 20% 保留;被丢的近期工具调用保留 tool_use 骨架以维持 provider 配对。≥95% 且无折叠可用时 fail-closed 阻断请求而非静默溢出。

ARCHITECTURE.md "ctx_reduce nudges"、"Smart-drops"、"Tiered emergency drop"、"Error handling" 节。

(f)记忆三部曲:Capture / Consolidate / Recall

  • Capture:historian 压缩历史时「顺路」提炼持久知识进项目记忆(5 类分类法:PROJECT_RULES / ARCHITECTURE / CONSTRAINTS / CONFIG_VALUES / NAMING)——「记忆免费,来自你本来就在做的工作」。也可用 ctx_memory 显式写入。
  • Consolidate(dreamer):夜间后台代理跑 12+ 种维护任务(map-memories 映射记忆到支撑文件、verify 对照代码库校验、curate 去重收紧、classify 打分、retrospective 从用户纠正中学习、维护 ARCHITECTURE.md/STRUCTURE.md、用户画像、primers、smart notes),按任务 cron 调度、冲突域租约串行化、临时子会话执行。
  • Recall:每回合自动、缓存稳定地注入活跃记忆与压缩历史;ctx_search 一个查询横跨记忆、原始对话(FTS5)、git commit 索引、notes、primers(语义嵌入 + 全文回退);ctx_expand 把压缩历史区间解压回原文;auto search hints 每回合后台搜索并「耳语」提示。跨会话、跨 harness 继承。

README.md "Capture / Consolidate / Recall" 三节;ARCHITECTURE.md "Memory, search & embeddings"、"Dreamer" 节。

(g)持久化与架构分层

所有持久状态在单一本地 SQLite(~/.local/share/cortexkit/magic-context/context.db),跨 harness 共享;记忆键在「稳定项目身份」上(从 git repo 派生,跨 worktree/clone/fork 跟随项目)。嵌入向量为 SQLite BLOB + 内存 Float32Array 余弦扫描(明确拒绝 sqlite-vec,理由是 bun:sqlite 无法加载扩展 + 写放大);本地嵌入模型 Xenova/all-MiniLM-L6-v2(约 90MB ONNX)。存储不可用时 fail-closed(宁可报错也不让 prompt 无限增长)。分层:bootstrap → 薄适配层(src/plugin/)→ 运行时 transform(src/hooks/magic-context/)→ 特性服务(src/features/magic-context/)→ 工具(src/tools/)。另有实验性 Rust 运行时:crates/mc-core / mc-store / mc-module / mc-tokenizer 在 subc daemon 下重写整条 transform 管线,TS 层退为协调器(状态同步 + LKG 回退)。

README.md "Storage" 节;ARCHITECTURE.md "Overview"、"Layers"、"Storage & migrations" 节;git tree(crates/ 四个 crate、packages/plugin 873 文件、packages/pi-plugin 153 文件)。

二、San 上下文稳态是什么(一页纸)

San 的 Context Steady State 是内建于 coding-agent 的会话级子系统(packages/coding-agent/src/context-steady/,26 文件约 6,700 行),不是插件。目标定义:「每轮 agent 停下时都把上下文收敛到结构化、可裁剪、可缓存、可召回的工作态,而不是等到爆窗再被动压缩」;并且明确质量优先于预算——「240K 不是一把砍内容的刀,而是一块足够宽的高质量工作台」。

docs/research/context-steady-state-san.html(2026-07-04 愿景稿);docs/research/san-context-steady-240k-redesign-proposal-20260712.html(质量优先重构)。

三层数据架构

Journal(不可变事实层,append-only,永久保留)
  → Coverage Ledger(替代关系层:digest/checkpoint 对原始 entry 的 replacement coverage)
    → Provider Working Set(执行上下文层:每次请求由 Context Planner 重新选择物化)

核心规则:「没有明确 replacement coverage,就不能从 provider payload 省略原始 entry」;同一个 ContextPlan 同时驱动发送、token 统计、状态栏与 compaction(单一决策点,消灭多套裁剪逻辑漂移)。

240k 重设计提案「基本模型」节;context-steady/plan-types.ts(ContextPlanAudit/ContextPlanCoverageAudit/ContextSourceIndex)、planner.ts、materialize.ts。

预算:三段控制带,不是配额

budget.ts 推导:steadyTarget = min(配置 240K, hardInputCeiling),其中 hardInputCeiling = contextWindow − max(32K, contextWindow × reserveRatio);controlMax ≈ steadyTarget × 13/12(约 260K 控制带);burstCeiling(默认 320K)为质量弹性区,由 quality gate 判定 burst_required 时启用。0–200K 舒适区 / 200–260K 稳态控制带 / 260–320K 质量弹性区 / 320K+ 强审查区。2026-07-24 的事故报告修正了小窗口模型(256K)下 steadyTarget 被 clamp 后弹性带被抹平的适配盲区。

context-steady/budget.ts(1–56 行);240k 重设计提案第三节;docs/research/san-context-steady-multi-window-adaptation-and-tool-loop-pause-research-20260724.html。

沉淀单元:TurnDigest / Checkpoint / Segment

  • TurnDigest(types.ts):逻辑 turn 结束后生成的结构化摘要——userIntent、actionsTaken、decisions、filesTouched、toolEvidence、factsLearned、openQuestions、risks、nextSteps、memoryCandidates,带 source 区间(fromEntryId/toEntryId)与 token 统计;LLM 生成失败时走确定性 fallback(fallback.ts),失败原因入档,append-only 升级替代。
  • Checkpoint(checkpoint.ts):每 N 轮把 digest ledger 合并为稳定摘要,v2 带 epochId、coveredSourceEntryRefs、rebaseReason(checkpoint / resume / budget_pressure / topic_shift)——低频改写以保缓存。
  • Segment(segment.ts):长逻辑 turn 内部的上下文维护边界,只描述「已被 compaction summary 替代的 journal 区间」,不携带执行配额、不能作为停止 agent 的条件(类型注释明文规定)。40K token / 15 分钟只是维护软提示;segment 数量无上限。每个 segment 携带本地同步生成的最小 checkpoint(摘要模型失败时仍可恢复)。

context-steady/types.ts(86–262 行)、segment.ts、checkpoint.ts;分段稳态提案第一、五节。

质量闸门与防饿死状态机

裁剪前先证明:识别交付阶段 → 建立 Required Context Set(最新用户指令、活跃文件、未解决错误、工具调用配对等八项保护)→ 验证 replacement coverage → 比较压缩前后风险;证明失败默认保留或扩张(burst)而非压缩。执行态状态机:RUNNING → MAINTENANCE_PENDING → RUNNING;硬压力下 RECOVERY_ONCE(一次 compaction + replan + replay,maintenanceId 防循环)→ 仍失败才进入显式 PAUSED_FOR_CONTEXT(可观察、可恢复,用户输入 FIFO 保留),禁止静默停止。Continuation authority(continuation.ts/summary-authority.ts):活跃用户请求与执行证据只能从 journal 真实 entries 同步派生,compaction 摘要与 assistant 自述无权改写,越权有审计(ContextSummaryAuthorityAudit)。

240k 重设计提案第四节;分段稳态提案第五节;context-steady/quality-gate.ts、continuation.ts(ActiveContinuationState 注释)、tool-progress-guard.ts。

召回与记忆

recall.ts 用「近期相关 digest 行 + 当前 prompt」拼召回查询,经 memory-backend(local-backend/off-backend 可插拔)检索,按 memoryType/scope 过滤去重后作为 ContextPlan 的 recall 材料(只对当前 prompt 生效,不跨轮累积);digest 的 memoryCandidates 带授权分级(explicit_user/inferred,由本地权威分类器设置,memory-authorization.ts)。缓存布局:稳定前缀 + append-only digest ledger + 低频 checkpoint 重写 + 动态召回靠后 + 当前 prompt 最后。

context-steady/recall.ts、types.ts(memoryCandidates)、packages/coding-agent/src/memory-backend/;愿景稿「缓存命中设计」节。

三、逐维度对比

与 agent loop 的耦合 外挂 transform hook:每次 LLM 调用重写消息数组,宿主 loop 无感知;代价是 replay-everything 不变量、宿主兼容矩阵(三 harness × 版本)、与宿主 compaction 的排他约束 深度内嵌:prompt 边界组装 ContextPlan、onTurnEnd + willContinue 安全边界做 mid-turn 维护、输入路由器 / FIFO / 暂停状态机直接接管执行语义(分段稳态提案 §三、五) MC 没有 loop 控制权,只能「重写字节」;San 拥有 loop,可以「改变行为」(暂停、replay、FIFO)。San 能做到 MC 做不到的执行级保证(工具不重复执行、输入不丢),MC 能做到宿主无关。
可移植性 高:OpenCode / Pi / OMP 通吃,数据库跨 harness 池化,Pi 分支 fork 继承状态;正向 Rust/subc 迁移以进一步脱离宿主运行时 无(设计如此):San 专属子系统,与 session journal、task executor、TUI 深度绑定 不同的产品形态决定:MC 是「卖给所有 harness 用户的插件」,San 是「自己 harness 的核心能力」。
成熟度 5 个月、1,731 stars、单主力作者、日均多 commit;v74 迁移、e2e + Docker、桌面应用、22 语言 README、安装向导 + doctor;经受多 harness 兼容性磨砺(issue 驱动的修复痕迹密集) 自 2026-07-04 起约 6 周演进,三轮设计迭代 + 两次事故驱动修复(loop failure 20260723、多窗口适配 20260724);有公开 benchmark 设计与发布报告(docs/research/san-context-steady-*benchmark*);单仓自用,无外部用户压力测试 MC 在「多环境鲁棒性」上明显更成熟;San 在「执行语义正确性」(防饿死、authority 隔离)上思考更深。两者都是高速迭代期。

四、San 可借鉴的点(与不值得借鉴的点)

4.1 值得借鉴:多分辨率历史表示 + 确定性 decay 选级

借什么。MC 每个分舱预存 4 个 paraphrase 层级,渲染时由确定性公式(年龄 × importance × 预算压力)选级,旧历史平滑降清晰度且逐字节可重现。San 目前 digest/checkpoint 是单分辨率:一个 TurnDigest 要么整个进 plan、要么被 checkpoint 吸收、要么被裁掉(ContextPacketTrimDecision 只有「省略」没有「降级」);ContextSegment 已有 historicalSummary + shortSummary 双粒度雏形但未体系化。引入「digest 生成时同时产出 2–3 个粒度 + materialize 按 ContextPlanBudgetAudit 压力确定性选级」,可以让 200–260K 控制带内的裁剪从「二值化」变成「渐进式」,直接提高旧轮次信息存活率。

改哪里。context-steady/digest.ts(生成期多粒度,复用现有 LLM 调用一次产出)、types.ts(TurnDigest 加 tiers 字段,schema v2)、materialize.ts + planner.ts(选级函数,输入用 budget.ts 已有的压力信号)。San 已有确定性 fallback digest 管线,fallback 层级天然是最低 tier。

预估工作量。中:3–5 天(含 schema 迁移与既有会话兼容);选级公式本身照抄 MC 的半衰期形态即可起步。

4.2 值得借鉴:bust 分类学——重写时机与缓存失效对齐

借什么。San 的缓存策略是「结构性」的(append-only ledger、checkpoint 低频改写、动态内容靠后),但 checkpoint rebase 的触发(rebaseReason: checkpoint / resume / budget_pressure / topic_shift)完全由自身节奏决定,没有和「provider 缓存此刻是否本来就要失效」对齐。MC 的核心洞察是:模型切换、system prompt 变化、闲置超 TTL 这些时刻缓存已死,重写是免费的;而例行增长绝不应主动触发重写。把这个「搭天然 bust 便车」的触发分类引入 San 的 checkpoint rebase 与 plan 刷新决策,可以在不改变任何数据结构的前提下降低缓存击穿率。

改哪里。context-steady/checkpoint.ts(rebase 触发加 bust 感知条件)、agent-session 的 plan 刷新入口(检测模型/系统提示变化、闲置时长,San 在 session 层天然掌握这些信号,比 MC 的插件位置更容易拿到);配套在 dogfood 观测(dogfood.ts)里加 cache-hit 归因。

预估工作量。中偏大:约 1–2 周,难点不在改动而在验证——需要 provider 缓存命中率的前后对照观测。

4.3 值得借鉴:pause 之前的分层应急降级档

借什么。San 的 hard_pressure 路径是 RECOVERY_ONCE → PAUSED_FOR_CONTEXT,fail-closed 语义正确但体验硬(20260724 事故:超 325 tokens 即熔断)。MC 在阻断之前有一整段梯度:85% 压力带按工具类别分层驱逐(杂项 → 编辑/搜索 → 导航,最新 20% 保留),被驱逐的调用保留 tool_use 骨架 + [dropped] 占位维持 provider 配对。San 已有 evidence_stub 表示级别与 entryId 重读路径,quality gate 的八项保护清单恰好界定了「绝不能降级」的边界——在 recovery 与 pause 之间插入一档「把 quality gate 允许的已闭合工具输出降为 stub」,能消化掉大部分几百 token 级的边缘溢出,而不违背「可证明覆盖」原则。

改哪里。context-steady/prune.ts / tool-progress-guard.ts(已闭合工具对识别已存在)+ quality-gate.ts(在 hard_pressure 判定前增加 stub 降级重算)+ planner.ts(降级材料的 coverage 记账)。

预估工作量。中:约 1 周(降级选择器 + 审计 + 回归用例;20260724 报告的会话可直接作为回归场景)。

4.4 值得借鉴:superseded-edit 压缩(小而准)

借什么。「同一文件后续又被编辑过,旧 edit 的完整 diff/输出已无信息量」——MC 压成 edit_marker(保 filePath + 区域提示)。San 的 filesTouched(action: modified/created/deleted)与 tool_pair 材料已具备识别条件,是 planner 里一条低风险高收益的表示降级规则,长重构会话中 edit 输出是 token 大户。

改哪里。context-steady/source-index.ts(标记 superseded tool_pair)+ planner.ts(降表示为 evidence_stub,写 coverage)。

预估工作量。小:2–3 天。

4.5 值得借鉴:历史自助解压工具(ctx_expand 等价物)

借什么。San 的 coverage 体系保证「被替代的原文可重读」,但重读通道目前只有系统侧;MC 把它做成 agent 工具,模型发现摘要不够时自己拉原文区间。San 的 journal + entryId + extractSpanMessages(session.ts)已是现成地基,补一个工具定义即可,与「digest 不能替代证据」的既有原则完全同向。

改哪里。coding-agent 工具注册处新增(如 context_expand),实现调 context-steady/session.ts 的区间提取;输出经预算夹紧。

预估工作量。小:1–2 天。

4.6 不值得借鉴

  • Replay-everything 不变量与 m[0]/m[1] 的插件式实现。这是「没有 loop 控制权」的补偿性复杂度:MC 必须每 pass 重放全部变换以保证字节一致,并用双消息块骗过缓存断点。San 拥有 loop 与 journal,在 plan 层直接决定物化内容即可,引入 replay 语义只会增加一层无收益的间接。借它的 bust 分类思想(§4.2),不借它的实现形态。
  • Dreamer 夜间管线全家桶。12+ 任务、per-task cron、冲突域租约、临时子会话、非 agentic manifest 协议——这套框架服务于「记忆库是跨年资产」的前提。San 的记忆量级(会话内 digest + memoryCandidates + 可插拔 backend)远未到需要夜间整理的规模,先建这套框架是典型的过度设计。其中「verify:记忆对照代码库校验时效」的单点想法值得记下,等 San 跨会话记忆真正成为主路径时再评估。
  • 本地嵌入模型 + 五语料语义检索栈。90MB ONNX 下载、向量表、嵌入哈希守卫、provider 替换守卫……对 MC 合理(跨月会话的海量分舱必须语义检索),对 San 当前形态是重资产:San 的召回场景以「本会话 + 近期偏好」为主,digest 相关性 + memory-backend 全文已够用。若未来要做,优先考虑复用 pi 生态既有向量设施而非自建。MC 语义检索的实际召回质量未核实(无公开评测)。
  • 排他式接管宿主 compaction。MC 必须关掉宿主压缩避免双压,这是插件与宿主的领土冲突;San 的 native compaction 本来就是自己体系内的兜底层(「context steady 是常态工作流,compaction 是应急」,愿景稿),双层防御是设计而非冲突,无需改变。
  • 「一个会话用一辈子」作为产品叙事。San 的会话模型(journal 为工作单元、跨会话走 memory backend 与 handoff)与之根本不同;追随该叙事意味着重写会话生命周期,收益不明确。San 已有 authoritySource: "handoff" 等跨会话交接原语,方向是「会话可交接」而非「会话不死」。

五、结论

一句话判断:同一问题(长会话上下文治理)的两种解,但目标函数不同——magic-context 解「会话无限延长 + 跨会话不遗忘 + 缓存成本最优」,San 解「单会话工作集质量 + 执行语义可证明正确」;在「后台压缩 + 分层表示 + 缓存稳定 + 可召回」这个核心子集上两者高度同构,互为镜像验证。

值得跟踪。理由:(1)它与 San 同处 pi 生态(直接适配 San 上游 oh-my-pi 的 compaction/memory 配置面),其兼容层动向对 San 有直接情报价值;(2)它以外部用户规模(1,731 stars、三 harness)验证了与 San 高度相似的架构判断(异步压缩、确定性渲染、fail-closed、coverage 式可追溯),它踩过的坑(ARCHITECTURE.md 里密集的 issue 编号)是 San 的免费回归清单;(3)其 Rust/subc 迁移与 San 的 crates/pi-natives 路线可相互印证。建议每 4–6 周扫一次其 CHANGELOG 与 ARCHITECTURE.md diff。
