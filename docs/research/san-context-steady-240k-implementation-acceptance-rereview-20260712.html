3. 阻断性发现

P0 · 240K/320K 预算没有约束真实 provider payload

Quality Gate 在生产调用中没有输入，超出 burst ceiling 仍被审计为 pass。

agent-session.ts:7986-8012 构建 plan 时只传 journal、模型窗口和 non-message tokens；没有传 currentPromptEntryRefs、liveTailEntryRefs、baseRequiredEntryRefs、activeToolCallIds 或 tokenEstimateByEntryRef。这些字段除单元测试外没有生产调用者。

Planner 只替换已有 digest/checkpoint 覆盖的历史；没有 digest 的原始历史全部保留，也没有计算最终 projected payload 总量。

adversarial probe:
model window       = 500,000
steady/control     = 240,000 / 260,000
burst ceiling      = 320,000
projected messages = 375,002
audit outcome      = pass

这意味着系统可以明确超过 320K，却仍报告 steady/pass；核心稳态目标尚未实现。

P0 · Fallback digest 仍授权删除最近原文

技术方案明确禁止的行为，被新 planner 测试固化成了正确行为。

planner.ts:91-109 不区分 LLM digest 与 fallback=true 的 deterministic digest；两者都会产生 coverage 并删除原始 user/assistant。

fallback digest probe:
raw user preserved = false
coverage            = ["u1", "a1"]

而实施方案测试矩阵要求：fallback 不授权删除最近 user/assistant 决策原文。现有 planner.test.ts:83-114 使用 fallback=true，却断言旧 raw user/assistant 必须消失。

P0 · Hard pressure 不会暂停、rebase 或升级模型

Quality Gate 即使得到 hard_pressure，Planner 仍返回可发送 plan，AgentSession 也无处理分支。

protected current prompt = 400,000 tokens
quality outcome          = hard_pressure
materialization          = still proceeds

真实 AgentSession 又没有传 protected refs，因此通常连 hard_pressure 都得不到。实施方案要求超过 burst ceiling 时尝试 safe rebase、evidence stub、compaction/model promotion，仍失败则显式暂停；当前这些动作均未连接。

P1 · Provider 发送与状态/compaction token 统计仍不一致

ContextPlan custom message 本地估算为 0，转成 provider user message 后才产生真实 token。

planner.ts:192-208 用 estimateTokens(customMessage) 记录 plan token；materialize.ts:201-210 的 projected estimate 也对 custom message直接估算。但 session/messages.ts:791-801 会在真正发送前把它转换成 user message。

empty plan rendered chars = 358
planner/custom estimate  = 0
provider role            = user
provider estimate        = 90

因此 plan payload 不进入状态栏和 pre-compaction 估算，contextPlan.maxTokens 也没有实际 enforce。带 checkpoint、5 个 digest 和 recall 时，偏差会更大。

P1 · Coverage validator 没有证明 replacement 真正覆盖 source

任意现存 material 都可以“认领”任意现存 entryRef。

coverage.ts:54-76 只检查 replacement material 存在、source ref 在 index 中；没有验证 coverage.sourceEntryRefs 属于该 material 的 coveredEntryRefs，也没有检查同一 source 的唯一 representation。

material actually covers = ["u1", "a1"]
audit claims it covers   = ["u2"]
validator valid          = true
current prompt preserved = false

这破坏了 C-04/C-05 的核心证明边界。Planner 当前生成的数据通常一致，但 validator 无法阻止未来 drift、损坏 audit 或错误 planner 删除不相关原文。

P1 · “质量优先” protected set 在运行时基本为空

最近 exact turns、验收条件、当前文件、错误证据和当前 prompt 都没有进入 plan 决策。

SourceIndex 虽然能索引 turn bundle、file mention 和 tool pair，但 Planner 不自动选择最近 3–8 个 exact turns，Quality Gate 也不会自动保护文件/附件/错误/验收标准。AgentSession 没有传 pending prompt 的 synthetic ref。

结果是：每个刚 settled 的 turn 一旦生成 digest，下一轮就可能立即删除 raw user/assistant；topic shift 也不会触发 rebase。独立探针中，与当前任务无关的旧安全审查 digest 仍进入新模型比较请求。

P1 · Epoch/rebase 只有字段，没有生命周期

所有请求永久使用 epoch_${sessionId}，checkpoint 继续线性累积 digest refs。

agent-session.ts:7993-8008 每轮写死相同 epoch；checkpoint 调用没有传 epoch/rebase reason。代码中没有 topic shift、resume 或 budget pressure 的 rebase 触发，也没有因 safe rebase 重置 append-only cursor/Responses provider session。

Checkpoint v2 字段已经加入，但 entryRefs 与 coveredSourceEntryRefs 仍合并所有历史，尚不能证明 12–20 轮 active union 有界或 resume 前后语义等价。

P1 · Secret placeholder 在持久化前被反解

出站传输已脱敏，但 journal 中的 TurnDigest 重新出现明文 secret。

digest.ts:285-356 在解析 provider 输出时递归 deobfuscate，然后才 normalize/persist。新增测试也明确要求 persisted userIntent 和 actionsTaken 包含原始 secret。

这与实施方案“持久化 digest 保留 placeholder，不做 deobfuscation”及“placeholder 不反解”直接冲突，也绕过了主会话“磁盘只写 placeholder”的安全设计。

P1 · 最终 dogfood 与配置仍验证旧 ContextPacket

绿色 dogfood 不能作为 ContextPlan 产品证据。

context-steady/dogfood.ts 仍调用 buildContextPacket 并要求最终 packet；推荐 YAML 仍使用 contextPacket 且 quality window 为 24000，不是批准的 240K。Changelog 也没有本次迁移条目。

因此当前的 dogfood 通过只证明 legacy path，没有证明 20-turn p95、burst 恢复、full-history A/B 或 ContextPlan resume/cache 生命周期。

P2 · 项目规则与兼容收口
  • planner.ts:68 使用项目明确禁止的 ReturnType<>。
  • Schema 文案称 qualityWindowTokens=0 表示“无 cap”，预算实现却把 0 解释为 240K 默认值。
  • SanLoop 类型支持 contextPlanRefs，但 slash 启动的 runConfiguredSanLoop 没有把当前 plan refs 传给 run，worker assignment 仍可能拿到空 refs。

5. 重新进入第三轮验收前的硬门槛

  1. 让 AgentSession 在 plan preflight 前建立 pending/live synthetic sources，并传完整 protected refs 与逐 entry token estimates。
  2. 用最终 materialized provider messages 计算完整 input；将 plan user-message token 纳入 send/status/compaction 同一 snapshot。
  3. 禁止 fallback digest 覆盖最近 exact turns；实现最近 3–8 个 exact turn 的独立保留策略。
  4. Coverage validator 校验 coverage 是 runtime material coveredEntryRefs 的合法子集，并强制每个 settled source 唯一 representation。
  5. hard_pressure 必须进入显式控制流：safe rebase、stub、compaction/model promotion 或暂停，不得继续静默发送。
  6. 实现真实 epoch state、topic-shift/resume/budget rebase、delta retirement 和 provider session reset 合同。
  7. 持久化 digest 保留 secret placeholder；补磁盘/journal 断言，不只检查 provider payload。
  8. 把 dogfood、recommended YAML、SanLoop run refs、changelog 和 20-turn/A-B 验收全部迁到 ContextPlan。

最终结论：第二轮仍不通过

这次不能再说“只有五个骨架文件”：GPT-5.5 已经完成了一批有价值的真实实现，上一轮多个局部 P0/P1 也确实修复了。但批准方案的核心不是“把 ContextPacket 改名为 ContextPlan 并能注入 digest”，而是完整 provider 输入可证明地稳定在 240K 控制带、质量证据受保护、超压有明确控制流、epoch/rebase 可审计、秘密不落明文。

当前六项独立探针直接击穿这些核心合同，因此结论保持 NO-GO：不可合入，不可宣称 R0–R6 完成，不应开始产品级 dogfood。
