Reading this plan

这是一份实施契约，不是新的产品提案。

产品方向以 《240K 质量优先重构提案》 为准。 本文只回答：哪些模块要换、每一步怎样接入 AgentSession、什么情况下允许 burst、怎样证明没有丢任务信息，以及怎样安全地替换当前 ContextPacket + prune 路径。

Implementation scope

重写的是投影层

保留 session journal、TurnDigest、Brain、SanLoop 与既有 compaction 能力；替换「小 packet 注入 + 另一套 prune」这条并行决策路径。

Explicit non-goal

不重写整个 San

不迁移历史 JSONL，不改变用户可见 transcript 的完整性，不把自然语言摘要当作唯一历史，也不在本轮要求完整产品 dogfood。

Definition of done

先代码闭环，后产品验收

本次交接要求完成可测的运行时与兼容层。全历史 A/B、长任务质量和真实使用体验留给后续联合验收，不在实现中用猜测代替。

Current worktree rule

当前工作区已有 GPT-5.5 / 用户未提交的 Context Steady 改动。实施者必须先 git status --short，保留其中已有的 entryId 证据、全 assistant decision 提取、importance 归一化、退化日志与附件边界等有价值改动； 不得 reset、checkout、revert 或为了让旧 packet 测试通过而回退它们。 本文要求替换的是旧的 all-digest pruning 与 packet delta 累积方向，而不是抹掉已完成的底层改良。

Non-negotiable contract

八条不可变合同。

每一个模块、每一个测试和每一次降级都必须遵守这些合同。它们优先于「刚好把 token 压下来」的局部优化。

C-01

Journal 永远完整

SessionEntry journal 是事实来源。ContextPlan 只是当前 provider 请求的工作投影，不能反向覆盖或删除原始历史。

C-02

240K 统计全输入

预算包括 system prompt、tool schemas、provider 固定开销与 messages；不允许只统计 packet 或可见 conversation。

C-03

质量能打破目标

200K–260K 是常态控制带，260K–320K 是有记录的质量 burst。质量闸门失败时，不能为回到 240K 强行删活跃证据。

C-04

原文退出必须有替代

每个已 settled 的旧 turn 在 provider 可见上下文中恰好一种表示：exact、evidence stub、digest、checkpoint 或明确 omitted；omitted 必须有 coverage 引用。

C-05

工具对不可拆

当前 assistant tool call 与对应 tool result 是原子 bundle；当前 prompt、未结束 turn、当前附件和活跃文件证据同样受保护。

C-06

同一计划驱动一切

发送、状态栏、/context、pre/mid/post compaction 估算与审计必须读取同一个 ContextPlan，而不是各自重新 prune。

C-07

动态数据没有高权限

digest、checkpoint、recall 和材料化的背景内容属于数据，必须以 user/data 语义进入 provider，不得伪装成 system 或 developer 指令。

C-08

关闭即等价

san.contextSteady.enabled=false 时必须走原有非 steady 路径；不增加消息、不改变顺序、不重置 provider cache，也不改变旧 session 行为。

Architecture replacement

从两套独立裁剪，换成一次选择、两次使用。

当前实现在 agent-session.ts 中先构造并注入 ContextPacket，再在 provider transform 中单独调用 buildContextSteadyPrunedMessages。 两者看见的对象、预算口径和删除理由不同，容易造成重复、漏算、状态栏漂移与缓存抖动。

当前路径

ContextPacket + prune
  1. 01从 digest / checkpoint 组装一个小型 ContextPacket，并作为自定义 prelude 注入消息链。
  2. 02SanLoop / Brain / packet 进入全局 injection 候选池，可能再被各自的预算逻辑截断。
  3. 03provider transform 对完整消息再做 prune.ts，却不知道 packet 是否覆盖了被裁内容。
  4. 04状态、compaction 与发送不保证使用同一估算或同一选择。
→

目标路径

Journal → ContextPlan → materialize
  1. 01完整 journal 建立 source index，按 turn bundle 与证据材料归档，不直接删除原文。
  2. 02planner 根据当前任务、epoch、质量闸门和总输入预算生成不可变 ContextPlanAudit。
  3. 03materializer 严格按 plan 渲染 provider messages；同一 plan 也提供准确 token 估算和可读 debug。
  4. 04在安全边界才新建 epoch / rebase；普通 tool loop 内稳定追加活跃 tail。
Budget contract

240K 是质量工作集目标，不是机械截断线。

预算的单位始终是本次 provider 的完整输入。如果模型窗口不足以承载 240K 加输出预留，系统必须显式降级； 如果质量闸门要求保留更多证据，系统可以进入有理由、可观察的 burst。

固定的计算口径

configuredSteady = positive(qualityWindowTokens) ? value : 240000
reserve = max(32000, floor(model.contextWindow × reserveRatio))
hardInputCeiling = max(0, model.contextWindow - reserve)
steadyTarget = min(configuredSteady, hardInputCeiling)
configuredBurst = positive(burstWindowTokens) ? value : 320000
burstCeiling = min(max(configuredBurst, steadyTarget), hardInputCeiling)
controlMax = min(burstCeiling, floor(steadyTarget × 13 / 12))
messageBudget = selectedInputLimit - nonMessageTokens

240K 时 controlMax 为 260K，舒适观察线为 floor(steadyTarget × 5 / 6)，即 200K。 舒适线只是「不用主动填满历史」的提醒，不触发删除。只要相关内容少于目标，宁可保持短而清楚。

nonMessageTokens 来自当前模型的 system prompt、tool schemas、provider overhead 等固定输入；它不是 Context Steady 可以假装不存在的容量。 当 messageBudget 连当前受保护材料也放不下，进入 hard_pressure，而不是悄悄截断。

0–200K舒适区：只保留相关材料，不为了凑满 240K 加旧历史。
200K–260K控制带：最常见且理想的 240K 稳态。
260K–320K质量 burst：必须记录原因，在下一个安全边界复核。
320K+强压力：走 rebase、证据回读、既有 compaction 或模型升级，不静默删任务。
Plan data model

把「为什么这个消息还在」写进 ContextPlan。

计划必须可审计，但审计记录不能再次存入大段敏感内容。持久化的是来源引用、表示方式、token 估算、质量结论与 coverage； 实际 provider message 只在内存中 materialize。

EXACT

原样 turn bundle

当前 turn、当前 tool pair，以及 epoch 内最近的 3–8 个高价值 settled turns。按时间顺序发送。

EVIDENCE_STUB

可回读的证据指针

旧大文件、旧 tool 输出、旧图像的完整内容退出后，保留 path、hash、entryId、为何相关与重读动作。

DIGEST

轮次索引

TurnDigest 是压缩后的「发生过什么」索引，不能自动等价为足够证据，也不能授权删除最近 exact turn。

CHECKPOINT

epoch 事实底座

只渲染最新 checkpoint；旧 checkpoint 保留在审计链中，不重复进入 provider。

OMITTED

明确的缺席

只能用于已被 digest/checkpoint/证据 stub 覆盖的历史，并记录 coverage refs。没有替代物，就不能 omitted。

Required in-memory companion

BuiltContextPlan

执行时不只需要 audit。planner 返回一个不可变的内存对象：

  • audit：可以 append 到 san.context_plan custom entry 的纯元数据。
  • messages：由 materializer 生成、仅本次 provider 请求使用的 AgentMessage[]。
  • requestKey：绑定 prompt generation、epoch 和 live tail，防止 tool loop 内重复选择旧历史。
  • coverage：每个 omitted 或 stubbed source 指向它的替代材料，供 invariant 与 debug 读取。

禁止：把 rendered message 全量写进 audit；也禁止让 materializer 重新做一次「我觉得哪些重要」的选择。

Planner algorithm

先保护任务，再回收噪声，最后才考虑重建 epoch。

planner 的职责不是找「最短消息列表」，而是找能让当前任务继续高质量完成的最小充分工作集。 所有可删项都有固定优先级；不可删项由 quality gate 决定。

每个 settled turn 只有一个 provider 可见表示

exact 与 digest / checkpoint 不能不受控地叠加。否则看似保留了更多信息，实际是重复占用上下文、污染 cache，也让模型面对互相矛盾的旧状态。

「选择一次，渲染一次；没有 coverage，就不允许缺席。」

当前 open turn 不属于这条降级链。它保持 exact，直到 agent settled 且下一个安全边界到来。

  1. 01

    建立 source index 与 turn bundles

    将 assistant tool call 与 result 配对；标记 current prompt、未解决错误、当前文件提及、附件、extension 增量、SanLoop / Brain 已验证的当前内容。

  2. 02

    先选 required materials

    当前 prompt、当前 open turn、活跃 tool pair、用户显式约束和验收条件、最近至少 3 个 exact turns、可直接影响当前任务的文件 / 图像证据必须进入候选。

  3. 03

    为旧 turn 指定恰好一种表示

    先保留 exact target 5（自适应范围 3–8）；可回读的大 payload 优先转 evidence stub；剩余历史选 digest 或最新 checkpoint 覆盖，并写 coverage map。

  4. 04

    materialize 并估算完整 provider input

    将 system / tools 固定开销与计划 messages 合并计算。不要用字符数替代 provider token estimate，也不要只数 context steady 自己生成的部分。

  5. 05

    控制带内：直接接受

    如果 projected input 不超过 controlMax，保存该 plan。小于 steady target 时不追加无关历史。

  6. 06

    超过控制带：只回收低风险材料

    依次降低低分 recall、重复 / 过期的大 payload、已被 checkpoint 覆盖的 digest；只有到安全 rebase 边界才可把 oldest exact 降到 min 3。

  7. 07

    质量闸门复核

    若所需规格、关键错误、工具因果、文件证据或验收条件缺失，恢复材料并标记 burst_required。

    允许到 burst ceiling；记录什么被保护、为什么不能收缩。
  8. 08

    超过 burst：进入 hard pressure

    仅在用户轮次边界尝试 safe rebase、针对性 evidence stub、既有 compaction / model promotion。仍放不下时中止静默发送并报告可解释的压力原因。

    绝不丢当前任务材料来伪造「已稳定」。
AgentSession integration

运行时接入只有五个安全点。

当前关键锚点位于 agent-session.ts 的 #generateTurnDigest、#maybeAppendContextSteadyCheckpoint、 #buildContextSteadyPacketPrelude、#promptWithMessage 与 #transformContextForProvider。 新实现要移除 packet prelude，而不是在这些锚点旁边再叠一层上下文。

A / USER BOUNDARY

创建 ContextSteadyRequestState

在用户 prompt 进入实际 agent loop 前，异步执行 recall、读取 branch、评估 topic shift / resume 是否需要新 epoch，并冻结本 request 的 identity。

  • state 至少包含 requestId、promptGeneration、epochId、recall 候选、rebase reason、plan snapshot。
  • 此时不再调用 #buildContextSteadyPacketPrelude，不写 injected custom message，也不加入 Brain 全局 injection 候选池。
  • topic shift、resume、manual 和已到 interval 的 checkpoint 只能在这里或已 settled 的安全边界触发。
B / PRE-FLIGHT

在 #promptWithMessage 前构建可解释的预检 plan

文件 mention、附件、prepend messages、当前 prompt 和可见 session 状态准备完成后，基于 [...this.messages, ...pendingMessages] 形成 preflight source snapshot。

  • pre-prompt compaction 查询的是这个 plan 的 projected input，不再调用独立 prune estimate。
  • plan 将当前扩展消息标记为 protected live content；没有 journal source 的 extension 增量不能被误认为可删旧历史。
  • 此阶段只准备选择，不能在未结束 tool loop 中 reset append-only cache。
C / PROVIDER SEND

在 #transformContextForProvider materialize 最终投影

先保留现有 #transformContext(messages, signal) 的 extension 处理；随后从同一个 request state 取 plan，并根据最终 transformed messages 增量补入 live tail。

  • 关闭 steady 时原样返回 transformedMessages，保证 disabled parity。
  • 开启 steady 时返回 materializeContextPlan(...).messages，不再调用 buildContextSteadyPrunedMessages。
  • 旧 epoch 的选择稳定；只有本轮新产生的 assistant / tool tail 可以追加，不能重新排序历史。
D / TOOL LOOP

保持一条 request state，保护工具原子性

同一用户 request 的多次 provider 调用共享 epoch 与旧历史选择。每个新 tool call/result 以 bundle 追加；当前文件和图像保持第一轮完整内容。

  • 较早的大 tool 输出只有在存在 artifact / path / hash 可重取时才能变为 evidence stub。
  • 较早完整文件副本转为 path + hash + entryId + re-read instruction；旧图像转为描述或证据指针。
  • 禁止在中途 topic shift / rebase；否则 provider prefix 与 append-only context 会被无意义打断。
E / AGENT END

写 digest、checkpoint 与 plan audit；只在必要时 rebase

agent settled 后生成净化 digest，必要时写 checkpoint v2，并 append san.context_plan audit。若计划决定 rebase，才执行 cache / provider session 重置。

  • 唯一允许的重置：agent.appendOnlyContext?.resetSyncCursor() 与 #resetCurrentResponsesProviderSession("context-steady-rebase")。
  • 非 rebase 普通 request 不得 reset cursor；否则 240K 稳态会反而制造 cache miss。
  • 状态栏、breakdown、/context plan、后续 compaction 都读取最后的 plan snapshot / audit，不重新猜测。
Materialization order

有固定顺序，但不把动态摘要伪装成更高权限。

顺序的目标是稳定 prefix、清晰的因果关系和可预测缓存，而不是把所有派生材料塞到最前面。

4ephemeral recall外部 / 记忆检索数据同样是低权限数据；先去重、限额、标注 provenance，优先成为最先可回收的材料。
5当前用户 prompt、附件、当前文件证据live request保护完整性；附件 / 图像第一个相关轮次不得因为预算目标变成无来源摘要。
6live assistant / tool tail当前未 settled loopassistant tool call 与 result 原子配对；只追加，不重排旧 epoch。
Trust and secret boundary

摘要是数据处理，不是第二个高权限 agent。

现有 generateContextSteadyDigest 的 side request 必须严格缩小输入面。它的目标是为未来检索提供事实索引， 不是把完整原始消息 JSON 再送给一个小模型，也不是把模型产物变成 developer 指令。

内容类型允许的 provider 语义禁止事项
当前系统规则、现有可信 developer 指令保持当前应用已有的角色与权限路径。Context Steady 不修改或复制它们。
checkpoint、digest、evidence stub、recalluser / data 语义；静态包装明确它们是参考材料，不是控制指令。不得 role=developer 或 system；不得把外部文本的命令当作任务规则执行。
SanLoop / Brain 已验证 prelude遵循各模块现有的 runtime policy 和 provenance 检查。不得借用为 Context Steady 的动态摘要提升权限。
ContextPlan audit不发送；仅本地 debug / report / 运行时估算使用。不得持久化 raw provider messages 或 secret 解密后的正文。
Compatibility and migration

前向写新格式，向后读取旧记录，不做 session 大迁移。

历史 session 是用户资产。新实现不要求重写 JSONL，也不让老的 ContextPacket 重新混入 active provider context。 兼容层只做读取、展示和转换，不留下长期双运行时。

Checkpoint

v1 / v2 双读，v2 单写

checkpoint v2 增加 epoch、覆盖 turn、前置 checkpoint、rebase reason 与 fallback coverage。reader 先解析 v2，再兼容 v1；writer 从切换点起只产出 v2。

Old packet

旧 packet 只读留档

san.context_packet 以及旧 injected packet message 在 resume 时从 active context 过滤。新 planner 忽略它们，但 /context packet 过渡期仍可解释历史记录。

Commands

新增 /context plan

新报告展示 budget、quality outcome、representation、coverage 与 rebase。旧 /context packet 作为兼容 alias，可按 record schema 读取 v1 / v2，而不是要求用户记住迁移日期。

SanLoop

计划引用成为新主字段

SanLoop run / role context 新增 sourceContextPlanRefs。保留已有 contextPacketRefs 作为旧 run 的 optional input，不再为新 run 写 packet refs。

Brain

TurnDigest v1 不动

Brain 对 TurnDigest 的 capture / recall 合同不改。只改变 digest side request 的净化方式和 Context Steady 将其作为材料时的 coverage 规则。

Rollback

一个总开关，零数据回滚

san.contextSteady.enabled=false 立即走旧 non-steady 发送路径。新 audit 是附加 custom entry；回滚不需清除用户历史，也不应留下两套活跃配置。

Configuration contract

配置只暴露真实产品决定，不把内部调参泄露给用户。

控制带从 steady target 推导，避免再新增一串互相冲突的 budget 参数。配置变更要同步更新 recommended YAML、设置说明和 changelog 的 Unreleased 段。

保留 / 新增的稳定设置

  • san.contextSteady.enabled默认 false；总开关
  • san.contextSteady.qualityWindowTokens默认 240000；非正数也解析为 240000
  • san.contextSteady.burstWindowTokens新增，默认 320000
  • san.contextSteady.reserveRatio保留，默认 0.2
  • san.contextSteady.exactTurns.target新增，默认 5
  • san.contextSteady.exactTurns.min新增，默认 3
  • san.contextSteady.exactTurns.max新增，默认 8
  • digest / checkpoint / recall保留各自的 enable 与上限

移除的旧 packet 配置

  • san.contextSteady.contextPacket.enabled删除；总开关唯一
  • san.contextSteady.contextPacket.maxTokens删除；不再有小 packet cap
  • san.contextSteady.contextPacket.recentDigests迁移为 plan 选择输入或 digest 相关设置

这是一个有意的语义变化：当前 qualityWindowTokens=0 表示「不设质量窗口」， 新引擎中它表示「使用默认的 240K 质量工作台」。必须在 schema description、recommended YAML 和 changelog 的 Breaking Changes 中说清楚。

配置读取需要容错旧配置存在，但新 schema 与 UI 不应继续展示 packet 选项。不要为新旧 engine 再增加一个隐藏双开关。

Delivery plan

按六个阶段推进；每阶段都留下可验证的出口。

下面的顺序刻意把纯决策逻辑放在大类接线之前。这样 GPT-5.5 可以用小 fixture 固化质量与 coverage 合同， 而不是先在 AgentSession 里堆分支、最后才发现没有办法解释为什么删了内容。

Test contract matrix

测试验证外部行为，不验证代码长什么样。

所有新测试必须捕获 observable contract：provider payload、plan audit、状态估算、可恢复性或错误映射。 不读取实现源码做 grep，不使用 mock.module()，不为了凑覆盖率写「长度变大」之类的弱断言。

合同fixture / 场景断言
coverage 完整旧 turn 含关键决定与大文件；尝试把 raw turn 移出 exact。若没有 digest / checkpoint / evidence stub 覆盖，raw turn 仍在 provider payload；plan audit 的 omitted 项均有有效 coverage refs。
无重复表示12–20 个 settled turns，含 checkpoint 与多个 digest。每个 settled turn 在 materialized provider context 中恰一种表示；最新 checkpoint 不与它已覆盖的 digest 重复。
质量 burst最终验收需要 diff、测试、错误与验收标准，超过 260K 但不超过 320K。plan outcome 为 burst_required，payload 保留所需证据，audit 记录理由；不是直接压到 240K。
hard pressure低窗口模型甚至放不下 protected live material。返回可解释压力原因与安全回退，不悄悄删当前 prompt / tool pair，也不虚报 token estimate。
工具原子性assistant 发 tool call，tool result 很长，随后继续分析。当前 call/result 成对出现；可回读的旧长结果只能在 pair settled 后变 evidence stub。
rebase 与 cache多轮 normal request、一个 topic shift、一个 resume。normal request 不 reset append-only cursor；只有 rebase reset 一次并标明 reason；旧 epoch 不在 tool loop 内改写。
resume / rewind含老 ContextPacket、v1 checkpoint、分支 rewind 的 session。旧 injected packet 不回放；v1 checkpoint 可读；恢复后 plan 语义等价且不污染 active context。
disabled parity同一输入，steady disabled。provider messages 与当前非 steady transform 等价；不写 plan audit、不触发 reset、不加入背景数据。
secret transportturn 中放置可识别 secret marker、长文件正文和工具大输出。捕获的 digest side-request payload 不含原 marker / 大正文；持久化 digest 保留 placeholder 而非还原文本。
角色边界checkpoint、recall、外部文本包含「忽略之前规则」等内容。materialized derived message 使用 user/data 语义，不能出现 developer / system；当前可信指令路径不被改变。
单一计划有 pre-compaction estimate、mid-run check、最终 provider send 的 session。三处读取同一 request plan id 或等价 snapshot，且 token 组成与最终 payload 一致。
文件 / 图像 / artifact当前附件、历史大文件、历史图像、可重取 tool artifact。当前材料完整保留；历史内容只有在可重取且 stub 带 path/hash/entryId 时才可收缩。
兼容报告同时含 packet v1、checkpoint v1/v2、plan v1 的 session。/context plan 读新 audit；兼容 alias 解释旧 packet；新写入不产生 packet ref。

GPT-5.5 handoff

实施者从这里开始，不要先碰大类里的旧分支。

下面是执行顺序、工作区保护与删除条件。它的目的不是限制实现者，而是避免这类跨 session/runtime 改造在中途变成不可审查的混合状态。

Start sequence

先建立共同事实

  1. 阅读已批准架构提案、本技术方案，以及现有 context-steady 的 packet、prune、checkpoint、digest、session 代码。
  2. 执行 git status --short，逐项确认 dirty worktree；不做 reset / checkout / revert。
  3. 运行当前聚焦测试，记录现状；区分已有改动导致的预期失效和真正回归。
  4. 先实现 R1/R2 的纯模块和契约测试，再把其接入 AgentSession。
Keep intentionally

这些方向不是重构目标

  • 已有 entryId 证据边界与可追溯性增强。
  • 全 assistant message 的 decision extraction 改进。
  • importance 归一化到 0–1 的语义修正。
  • 退化路径日志和用户附件边界处理。
  • TurnDigest v1 作为 Brain capture / recall 的稳定合同。
Replace deliberately

这些方向必须退休

  • 将所有 digest 直接裁成一个 packet 的全局 pruning 思路。
  • 跨 request 累积 ContextPacket delta，再把它混入原 messages 的策略。
  • packet prelude 与 provider prune 各自做预算、各自删内容的双路径。
  • 断言「ContextPacket 被注入」而非断言质量、coverage 与 provider payload 的旧测试。
Change hygiene

交付方式

  • 按 R0–R6 推进，每完成一段就运行局部契约测试并记录结果。
  • prompt 只能放静态 .md，通过 text import 使用；不要在 TS 里拼装 prompt。
  • 不使用 any、ReturnType<>、inline import 或 mock.module()。
  • 未得到明确请求前不提交、不推送；logical commit 边界可以记录在实施报告中。
Stop conditions and acceptance

不能安全装下时，系统应该诚实地停下来，而不是安静地遗忘。

这既是实现边界，也是后续验收边界。稳定不是让图表漂亮，而是让模型始终拥有完成任务所需的注意力与证据。

Hard-pressure 停止规则

在 burst ceiling 内仍无法同时容纳 required material 时，按以下顺序处理：

  • 只在安全用户边界尝试 rebase，保留当前任务与 active tool bundle。
  • 将已验证可重新读取的大文件、图像和 artifact 替换为 evidence stub。
  • 调用既有 compaction / model promotion / fallback 策略，但把该操作记录为压力恢复，而不是 ContextPlan 的静默删除。
  • 仍无法满足时，返回 hard_pressure 的可解释错误 / 暂停状态，明确缺的是窗口还是不可压缩的任务材料。

两层验收，不混为一谈

代码级完成条件

所有目标 contracts 通过；Bun check 通过；无 active packet / prune runtime 路径；audit 无 raw 大内容；send、status 和 compaction 共用 plan；disabled parity 可证明。

产品级联合验收条件

后续单独执行 full-history 与 steady-plan A/B。20-turn 真实任务的常态 p95 不高于 260K；合理 burst 不高于 320K 且有原因与恢复；resume 语义等价；无 secret 泄露；复杂实现、排障与验收质量不下降。

Rollback 条件

发现任务规格、工具因果、秘密边界、resume 语义或缓存稳定性任一违反合同时，关闭 san.contextSteady.enabled，保留 audit 与 journal 供定位，不清理用户历史。

Implementation thesis

完整历史负责不遗忘；ContextPlan 负责当下；240K 负责集中；burst 负责质量。

这次改造的成功标准不是「又多了一个压缩器」，而是任何一轮都能回答： 当前 provider 看到了什么、为什么看到它、哪些原文由什么替代、何时可以安全 rebase，以及为什么这次允许超过 240K。

JOURNAL IS TRUTH → PLAN ONCE → MATERIALIZE ONCE → MEASURE THE SAME PLAN → BURST FOR QUALITY → REBASE ONLY WHEN SAFE
