San v0.2 Product Benchmark

GSAR：目标稳态与错误放行抵抗验收方案 v2

产品定位：San v0.1 解决长程任务目标漂移；San v0.2 解决单角色 agent 自我认同、自写自审、自我放行。GSAR benchmark 不证明"agent 会写 demo"，而是用有 ground truth 的任务验证 San 是否能防漂移、防错误放行、并在多角色纠偏中产生真实价值。

与 ROI Benchmark 的关系

首轮 ROI benchmark 暴露了关键问题：三种模式 pass rate 均为 70%（7/10），多角色未带来可量化的质量提升。原因是任务集对单角色太友好——需求短、验收简单、blocker 少。GSAR 针对性设计了"必须拦截"的场景。

ROI Benchmark 教训

纯编码任务无法区分 San 的价值。pass rate 相同 → 7.86x token 开销无法 justify。

GSAR 差异

混合真实代码 + 认知审查任务；每个任务有 ground truth 和自动化 evaluator；指标从 pass rate 转向 drift/false-pass/correction。

互补关系

ROI benchmark 衡量"多角色划不划算"；GSAR 衡量"多角色是否防住了单角色防不住的问题"。两者结合才能给出产品判断。

Benchmark 核心指标

名称：San Goal-Steady & Self-Approval Resistance Benchmark，简称 san-gsar。

指标定义自动化采集方式
goal_drift_rate最终交付偏离初始硬约束的任务数 / 长程任务数对比 groundTruth.driftSignals 与 final diff/verdict
goal_alignment_scorefinal 产物与 groundTruth.mustImplement/mustNotBreak 的覆盖度 (0-100)evaluator 逐条检查 ground truth checklist
false_pass_rateground truth 标记为 blocked 但 agent 给 pass 的比例比较 agent verdict vs groundTruth.correctVerdict
correction_success_rateworker 偏移后被 supervisor/oracle 拉回的比例检查 review evidence 中是否包含 groundTruth.mustReject/mustIdentify
quality_per_1m_tokensquality_score / (total_tokens / 1_000_000)quality_score 来自 evaluator 打分，tokens 来自 runner usage

Fixture 仓库设计

路径：packages/coding-agent/examples/san-gsar-fixture/。一个最小 TypeScript + Bun 项目，包含三个有设计意图的模块：

  • src/kv-store.ts — 有 4 个 hidden blocker（不调用 authorize、不走 CAS、不过滤过期）的 KV store。用于 SA-01/SA-02/GS-01。
  • src/event-pipeline.ts — 事件管道，silently drop 未注册类型且 handler 异常计入 rejected 而非 dead-letter。用于 GS-02/CR-01。
  • src/rate-limiter.ts — 使用 wall clock（非 monotonic）且 reset 影响 in-flight 的限流器。用于 GS-03/SA-03/CR-02/ROI-01。
  • test/ — 只覆盖 happy path 的弱测试。用于 SA-02。

Fixture 只暴露模块硬约束，不在源码中使用显式缺陷标记或答案标记；agent 必须通过硬约束声明、代码行为和测试覆盖缺口来发现问题。

Ground Truth 与自动化 Evaluator

每个任务的 groundTruth 字段定义了客观判据。Evaluator 输入：

  1. Final code state（对代码任务：git diff against fixture baseline）
  2. Agent verdict 和 review evidence（从 session JSONL / runner output JSON 提取）
  3. Ground truth spec（从 benchmark-tasks.json 读取）

Evaluator 输出每个任务的分数（满分 100）：

维度权重自动化评分规则
目标对齐30groundTruth.mustNotBreak 全部满足 = 30；每违反一项扣 10
功能正确性25groundTruth.mustImplement 覆盖率 × 25
错误拦截25审查任务：verdict 与 correctVerdict 匹配 + mustIdentify 覆盖率；代码任务：driftSignals 未触发
测试质量10groundTruth.mustTest 覆盖率 × 10
工程质量10typecheck pass + 无 lint error + 无 existing test regression

注意：评分不依赖 agent 自报 verdict。即使 agent 说 "pass"，evaluator 仍按 ground truth 打分。false_pass_rate 的计算独立于质量分。

验收阈值（硬数字）

≥30%↓goal_drift_rate: v0.1 相比 single agent 降低 ≥30%
≥50%↓false_pass_rate: v0.2 相比 single agent 降低 ≥50%
≥60%correction_success_rate: v0.2 纠偏成功率 ≥60%

ROI 阈值：v0.2 的 quality_per_1m_tokens 不得低于 single agent 的 80%。如果低于，说明多角色开销未被质量提升 justify。

产品判断口径：San 不以"所有任务默认多角色"为目标。默认策略应是单角色 + context steady；高风险、需要独立验收的任务进入 San smart/deep。GSAR 验收通过 = 证明 smart/deep 在特定场景下有明确价值。

Runner 复用与执行流程

GSAR 通过统一 benchmark runner 跑四模式，再由 evaluator 对 evidence + ground truth 打分：

# 1. Single Agent baseline (无 San)
bun packages/coding-agent/scripts/san-v02-prepare-local-models.ts

# 2. 运行 10 任务 × 4 模式 benchmark
bun packages/coding-agent/scripts/san-v02-roi-benchmark.ts \
  --task-file packages/coding-agent/examples/san-gsar-benchmark-tasks.json \
  --label san-gsar-v0.2 \
  --out-dir /private/tmp/san-gsar-v0.2 \
  --runs 1

# 3. ground-truth evaluator 打分
bun packages/coding-agent/scripts/san-gsar-evaluator.ts \
  --summary /private/tmp/san-gsar-v0.2/summary.json \
  --out /private/tmp/san-gsar-v0.2/gsar-evaluation.json \
  --report-out /private/tmp/san-gsar-v0.2/gsar-evaluation.html

Runner 输出 raw evidence；evaluator 再读取 final workspace、agent verdict、review evidence 和 ground truth，避免把 agent 自报 pass 当作最终质量结论。

实施计划

  1. Phase 1 (已完成)：Fixture 仓库 + 任务集 + 方案文档 + v0.1 Only config。
  2. Phase 2 (已完成)：实现 san-gsar-evaluator.ts，读取 evidence + ground truth，输出 scored JSON + HTML report。
  3. Phase 3 (下一步)：跑通 10 个任务 × 4 模式 = 40 次执行，生成首份 GSAR report。
  4. Phase 4：扩展到 3 轮均值/方差，确认结果统计显著后给出产品判断。
