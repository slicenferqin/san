Context Steady 数据结构全景

San · packages/coding-agent/src/context-steady/ · 梳理稿 v1 · 2026-08-22 · 静态 HTML，无外部依赖 · 为后续优化讨论做地基

这份文档只回答一个问题：上下文稳态到底用了哪些数据结构，各自长什么样、活多久、锚定在什么上。 不含优化方案；文末只列出结构本身的接缝，作为下一步讨论的输入。所有结论以当前分支源码为准（本轮 planner 修复之后）。

0 · 一图总览：五层数据，三种寿命先看这个

L0
Session Journal — SessionEntry[]，append-only 事实源
三种 entry：message / custom_message（进 LLM 上下文）、custom（纯账本，不进上下文）。entry id 是全局稳定锚点。
L1
派生物料（持久） — 本身也是 journal 里的 custom entry
san.turn_digest（回合卡）、san.context_checkpoint（大总结卡）、san.context_plan（当次计划收据）。同层还有压缩侧的 san.context_segment / continuation。
L2
ContextSourceIndex — 内存派生索引，每次规划重建，请求结束即弃
把 journal 扫描成 7 个视图：exact / turn_bundle / tool_pair / file_evidence / attachment / digest / checkpoint，并解析覆盖锚点。
L3
BuiltContextPlan — 一次请求的计划产物
audit（预算 + 质量门 + 物料审计 + 覆盖映射）+ materials（digest/checkpoint/recall/tool_stub）+ renderedContent（渲染成一条消息）。
L4
Payload 投影 — AgentMessage[]，纯临时
物化函数按 plan 把被覆盖消息省略、把被取代的工具输出替换成 stub，再把 plan 消息插到最后一条 user 消息之前。发给模型的只有这一层。

数据流只有一条方向：

L0 journal ──扫描──▶ L2 source index ──准入+试装──▶ L3 plan ──物化投影──▶ L4 payload ──发给模型 ▲ │ └────── 覆盖关系（entry id 引用）──────┘ 关键点：L1 的 digest/checkpoint 不直接进上下文，它们只是"覆盖权凭证"；真正发给模型的是 L3 渲染出来的那一条 plan 消息，和 L4 里未被覆盖的原文。

1 · L0：Journal —— 唯一事实源寿命：永久，append-only

SessionEntry 是判别联合，三种形态的语义分工是整套设计的地基：

形态谁写入进 LLM 上下文？说明
message会话各方是真实对话消息（user / assistant / toolResult / fileMention…），携带完整 AgentMessage
custom_message系统注入是需要模型看见的派生内容（如注入的 plan 消息本身）；同时有展示属性
custom稳态/审计否纯账本记录：turn_digest、checkpoint、context_plan 审计、maintenance 审计等

两条不变的纪律：(a) append-only —— 任何层都不修改、不删除既有 entry（"原文永远留在档案库"）；(b) entry id 是唯一稳定身份 —— 所有覆盖关系最终都引用它。窗口裁剪、压缩、resume 都不改变已落盘 entry 的 id。

2 · L1：派生物料 —— 覆盖权凭证寿命：永久，但可被同 span 升级覆盖

2.1 TurnDigest（回合卡）覆盖权的最小单位

一个已落定的逻辑回合的结构化摘要，存为 custom entry。字段分三组：

  • 锚点组：source: { sessionId, fromEntryId, toEntryId, promptGeneration, userEntryId? } —— 用 journal entry id 区间声明"我替代谁"。这是覆盖权的声明处。
  • 内容组：userIntent / actionsTaken / decisions / filesTouched / toolEvidence / factsLearned / openQuestions / risks / nextSteps / memoryCandidates —— 渲染进 plan 的素材。
  • 权威组：fallback: boolean + fallbackReason + supersedesEntryId —— fallback digest 是"仅供参考"的降级品，不授权省略原文（source-index 会剥掉它的覆盖）。同一 span 的权威摘要后落时覆盖 fallback（collectDigestRefs 按 span key 去重）。

2.2 ContextCheckpoint（大总结卡）覆盖权密度最高的物料

对若干 digest 的二次聚合，同样存为 custom entry。v2 schema 的锚点字段是两级的：

  • entryRefs: string[] —— 覆盖的 digest entry id 列表（一级：折了哪些回合卡）；
  • coveredSourceEntryRefs?: string[] —— 直接覆盖的原始 entry id 列表（二级：展开后替代哪些原文）。v1 没有，只能从 digest span 展开。
  • previousCheckpointEntryId + rebaseReason —— checkpoint 链，声明自己作为安全重排边界的原因（checkpoint / resume / budget_pressure / topic_shift）。

注意一个历史包袱：tokenEstimate: number 是落库时用 JSON 尺子算的存量值，与渲染后 wire 体积是两种单位（比值约 0.76）。它现在只用于审计展示，但字段名不带单位语义，是 D1 类 bug 的残留土壤。

2.3 压缩侧的邻居（不同子系统，共享 L0）

  • ContextSegment —— 物理压缩的边界记录：描述 journal 中哪段已被 compaction summary 替代（firstKeptEntryId 之后才是在窗内容）。
  • ActiveContinuationState —— 当前逻辑 turn 的权威执行状态（活跃 user 请求、成功 mutation/验证证据），由真实 journal 派生，压缩摘要无权改写。

这两者属于压缩/维护子系统，与稳态共用 journal 锚点但生命周期不同：digest/checkpoint 是非破坏性投影（每次请求重新决定带不带），segment 是破坏性裁剪（落盘即生效）。

2.4 ContextPacketlegacy

san.context_packet 是 M2 时期的注入机制（三层：stable_checkpoint / turn_digest_ledger / retrieved_context），已被 ContextPlan 取代，源码里仅剩识别与剥离逻辑（isContextPlanLegacyPacketEntry、物化时过滤）。复盘 D16〜D18 点名的死代码主要在这一支。

3 · L2：ContextSourceIndex —— 每次规划重建的内存索引寿命：单次规划

从窗口内 entries 全量扫描出 7 个视图（source-index.ts）：

视图内容用途
exactEntries全部消息 entryexact 物料、token 估算
turnBundles权威 user 消息到下一条 user 消息的分组回合边界
toolPairstoolCall↔toolResult 配对 + supersededByToolCallId 标记stub 替换候选
fileEvidence / attachments文件提及 / 图片描述附件保护与降级
digests去重后的 digest + 解析出的 sourceEntryRefsdigest 物料
checkpointscheckpoint + 解析出的 coveredDigestEntryRefs / coveredSourceEntryRefscheckpoint 物料
这一层真正重要的不是视图，是覆盖锚点的三条解析规则：
  1. digest span 解析（sourceEntryRefsForDigest）：from/to entry id 都在窗内 → 取区间；端点不在（被压缩裁掉）→ 退化为 toolEvidence.entryIds 里还存在的零散引用。这就是复盘里"窗口裁剪后覆盖碎裂"的出处。
  2. checkpoint 一二级展开：coveredDigestEntryRefs = entryRefs ∩ 现存 digest；二级覆盖优先用 v2 显式 coveredSourceEntryRefs（过滤到现存 entry），否则从 digest span 展开。
  3. fallback 剥离：任何只由 fallback digest 贡献的原始 span，从 checkpoint 覆盖里剥掉 —— fallback 永远不授权省略原文。

4 · L3：BuiltContextPlan —— 一次请求的计划寿命：单次请求（turn 内冻结）

组成结构角色
audit.budgetContextPlanBudgetAudit：steadyTarget / burstCeiling / messageBudget / planTokenBudget…从 contextWindow 和 reserve 反推的容器预算（budget.ts）
audit.qualityGateoutcome（pass / burst_required / hard_pressure）、protectedEntryRefs、emergencyStubEntryRefs…保护集判定：哪些 exact/live 物料不可省略；压力时的应急降级档
materials判别联合：digest | checkpoint | recall | tool_stub前三类渲染进 plan 消息并携带 coveredEntryRefs；tool_stub 只作用于投影替换，恒不授权覆盖
audit.coverage{ sourceEntryRefs[], replacementMaterialId, reason }[]覆盖映射表：entry id → 替代物料。省略的唯一授权来源
renderedContent / messageHandlebars 模板渲染出的字符串 → 一条 custom_message真正发给模型的东西；wire token 只量它

准入与定型的流程（本轮修复后）：全部候选先入场 → 统一用渲染后 wire 体积试装 → 装不下按 recall → 最旧 digest → checkpoint 顺序淘汰 → checkpoint 被淘汰时恢复它折叠的 digest 候选 → 定型。覆盖映射在定型后由 materials 的 coveredEntryRefs 累加生成，再经 validateContextPlanCoverage 六项校验（无物料、引用缺失、越界、重复、审计不一致）。

5 · L4：Payload 投影 —— 唯一真正发送的东西寿命：单次请求

materializeContextPlanMessages(messages, branchEntries, plan) 四步：

  1. 校验：coverage 校验不过 → 当作没有覆盖权（保守保留原文）。
  2. 省略：按 coveredEntryIds 从 payload 里删消息。匹配走双通道：WeakSet 引用（消息对象就是 journal entry 里的那个对象）+ 内容键（role + timestamp + content，带计数处理同键重复）。
  3. 替换：superseded / emergency 的 toolResult 内容换成小 stub（省略先行，已被省略的不再替换）。
  4. 注入：先剥掉上一轮的 plan/packet 注入消息，再把本轮 plan 消息插到最后一条 user 消息之前。

6 · 恒等与锚点模型整套系统的心脏

覆盖权的传导链：

digest.source{from,to} ──┐ ├─▶ L2 解析(∩现存,fallback剥离) ─▶ material.coveredEntryRefs checkpoint.entryRefs ─────┘ │ ▼ audit.coverage{entryId → materialId} │ ▼ L4 投影省略(双通道匹配) ─▶ 最终 payload

顶层（L1〜L3）全程用 journal entry id 锚定 —— 稳定、可验证。底层（L4）却要面对"payload 是 AgentMessage[]，不是 entry"的现实：正常路径靠对象引用（WeakSet）匹配，压缩/resume 后消息是副本，只能退到内容键（role+timestamp+content）。锚点体系在最后一公里换了一次坐标。

两把 token 尺子：JSON 尺（materialTokenEstimate，用于审计字段和落库存量）与 wire 尺（渲染后估算，唯一参与预算决策的尺，本轮已统一）。尺子统一了，但 JSON 尺仍在数据结构里留有存量字段。

7 · 结构本身的接缝优化的输入，不是优化方案

  1. 锚点双坐标：覆盖传导在 L1〜L3 用 entry id，L4 用"对象引用 / 内容键"双通道。内容键通道是压缩后覆盖权静默失效的结构性风险点（Step 3 讨论的正是这里）。
  2. 覆盖引用四处冗余声明：digest span、checkpoint 两级 refs、material.coveredEntryRefs、audit.coverage 各存一份，靠校验函数事后对账，无单一属主。
  3. 持久化数据里存派生值：checkpoint.tokenEstimate 是落库时的 JSON 尺读数，单位与决策尺不同；类似地 digest 的覆盖依赖运行时解析而非落库时固化的展开结果。
  4. 索引全量重建：每次规划对窗口 entries 完整重扫（span 解析内层 findIndex，最坏 O(n²)），无增量。
  5. 投影位置无锚：plan 消息插在"最后一条 user 消息之前"——位置随 turn 漂移，不在任何持久锚点上（这是缓存稳定问题的结构根源）。
  6. 两套压缩层级并存：稳态（digest→checkpoint，投影式、可逆、每请求重决定）与 compaction（segment，破坏式、落盘生效）共享 journal 但无共同表示树；稳态失败时静默落入 compaction。
