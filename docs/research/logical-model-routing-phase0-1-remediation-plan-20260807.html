一、修复目标与硬边界

目标不是扩展功能，而是让已承诺的 Phase 0–1 合同成立。 完成后，同 ID route 的配置更新在请求边界正确重绑；billing override 成为 effective model 的成本；route change 在本地 tree/HTML 可审计；逻辑 picker 以整组 eligibility 判断上下文；配置只接受运行时可能执行的 fallback 类别；独立 package full suite 退出 0。

必须保持

  • provider/model exact concrete 永久绕过 logical resolver。
  • 无 logicalModels / routing disabled 的行为与 session 兼容。
  • Logical Model intent 与 concrete route lease 分层；route switch 不改 harness profile。
  • 每次 concrete target 切换继续走统一 provider session reset 入口。
  • RPC/Extension 采用现有 event 名与加法式可选字段，不创建第二协议。

明确不做

  • 不持久化 circuit/failure counters，不实现 half-open single-flight。
  • 不做 Route Inspector、pin/drain、route health database 或 route-level perf 产品化。
  • 不按 catalog 或 billing 自动排序；Phase 1 仍只信显式 priority/config order。
  • 不引入 weighted/random routing、SLA policy、质量学习或 effort 自适应。
  • 不自动迁移 fallbackChains，不自动把同 ID provider 归组。

合同来源：权威 Spec 的 Phase 0/1、兼容策略与版本完成定义。缺陷详情与当前证据：合同审查。

二、实施原则、依赖与总顺序

  1. 以当前 registry snapshot 为真：route ID 只是稳定 identity，不代表 target 永远不变；policy version 与 model selector 共同决定 lease 是否需要重绑。
  2. effective model 单一流向：选中 route 后，执行、usage、预算、UI/RPC 汇总必须观察同一个 route-local Model；不得在多个 accounting consumer 各自补丁。
  3. 一个 eligibility resolver：picker 不复制 context/auth/capability 判断；把当前请求约束传给现有 resolver。
  4. 持久 entry 必有 reader：新增 session union variant 时，TUI tree、HTML tree/search、HTML transcript 与 filter 都必须显式处理。
  5. 配置先失败：运行时出于安全永不执行的 policy 值，必须在配置路径上明确拒绝。
  6. 不掩盖 baseline：web-search full-suite failure 独立修复，不允许 skip、过滤或归因给 routing。
1 · LMR-05收紧配置输入，先固定 policy 合同。
2 · LMR-01修复请求边界的 lease/current registry 一致性。
3 · LMR-02建立 route-local effective model 与统一成本流。
4 · LMR-04复用 resolver 修正 Alt+P 上下文可选性。
5 · LMR-03补齐所有持久 reader 与导出。
6 · Gates焦点合同 → 本地体验 → baseline track → full suite。

LMR-01 与 LMR-02 在代码上可独立实现；以上顺序用于降低调试歧义。Baseline suite track 可与路由轨并行，但最终门禁必须汇合。

最小源修改

  1. 在 lease controller 增加一个明确的 reconcile/rebind current snapshot 操作，或等价地扩展 recovery，但不得受 policy.revert 限制。
  2. 用当前 group resolution 比较：active.policyVersion !== resolution.policyVersion，或同 ID compiled route 的 modelSelector !== active.modelSelector。任一为真即视为 stale。
  3. 用当前 request constraints 重新解析；相同 route ID 但新 selector 也必须返回 selection，更新 active lease 的 selector/version，同时保留原 role 与已选定的 harnessProfile。
  4. AgentSession 在下一 provider 请求前完成 API-key 检查、metadata refresh、#setModelWithProviderSessionReset、thinking reapply 和 sync；失败则恢复 transition snapshot。

兼容 / 迁移行为

  • 没有 config refresh 时无行为变化，不增加每 turn 的 catalog 扫描，只比较小型 group snapshot。
  • 流式在途请求继续使用开始时的旧 model；只在下一请求边界重绑，符合 Phase 0 原子快照约束。
  • 相同 ID + 相同 selector、仅无关配置版本变化时可刷新 lease version 而不 reset transport；相同 ID + selector/transport target 变化必须 reset。
  • 旧 session 只保存 route ID，恢复逻辑仍把它作为 affinity；不需要迁移 JSONL。

可观察合同测试

  • AgentSession：活动 logical lease 后热更新模型配置；下一 prompt 只调用 B，A 不再被调用，provider session reset 恰好发生一次。
  • 请求边界：更新发生于一次流式请求期间，该请求仍由 A 完成；下一用户 turn 才用 B。
  • 同 ID/同 selector 的无关 policy refresh 不做无意义 provider reset，但 active policy version 对齐。
  • B 无鉴权/不满足 context 时，resolver 选择下一 eligible route；全不可用时列出当前 trace，不静默回旧 A。
  • resolved event、activeModelRoute 与 RPC snapshot 最终都指向 B。

依赖现有 registry policyVersion 单调递增与 #captureModelRouteTransition 回滚语义；不依赖 LMR-02/03/04。建议在 LMR-05 固定 policy 输入后实施，随后再让 billing effective model 复用同一 selection 流。

根因

精确文件 / symbol

  • src/sdk.ts：hard cost calculation 2996–3015、actual usage accumulation 3070–3074（验证对象，不应补第二份 override 逻辑）。
  • 测试：test/model-route-registry.test.ts、test/sdk-logical-model-routing.test.ts。

最小源修改

  1. 在编译每条 route 时构造 effectiveModel：无 billing 时复用原 catalog model；有 override 时创建 route-local immutable Model，复制所有 transport/capability/thinking 字段，仅把 cost 替换为四个 override 值。
  2. CompiledModelRoute.model 指向 effective model；modelSelector 仍保持原 provider/id，billing metadata 可保留用于解释来源。
  3. 不得原地修改 catalog model 或共享 cost object；同一 concrete model 在其他非 route/其他 route 上继续使用自身价格。
  4. resolver/lease/AgentSession 不增加 accounting 分支：它们已有统一 selection.model 流，确保 provider calculateCost 与 maxTotalCost 自然读到 effective cost。
  5. 对 provider 返回 authoritative charge 或 service-tier multiplier 保持现有后处理顺序；override 是基础单价，不应再次在 session/RPC consumer 乘价。

兼容 / 迁移行为

  • 没有 billing 的 route 与所有 concrete 模型字节/对象行为不变。

  • 旧 session 里已经记录的 usage.cost 保持不可变；只对修复后的新 provider response 生效。
  • 若外部 RPC 客户端依赖错误的旧费用数值，不提供兼容开关；发布说明应明确该 bug fix，但不引入 schema migration。

可观察合同测试

  • 编译：override route 的 route.model.cost 精确等于配置，原 catalog model cost 未变，对照无 override route 未克隆/未改变。
  • 选择：ModelRouteLeaseController.select/failover 返回 effective model，selector 与 capability 仍正确。
  • usage：固定 token 数的 mock provider response 产生按 override 计算的 input/output/cacheRead/cacheWrite/total。
  • 硬预算：catalog 低价、override 高价时 maxTotalCost 按高价截断；反向场景不被 catalog 高价过早截断。
  • 汇总：session stats、footer/HTML 输入和 RPC usage analytics 观察同一个 assistant usage.cost，不重复应用 override。
  • route switch：primary/backup 各自 override，在 failover 后下一 response 使用 backup 单价。
