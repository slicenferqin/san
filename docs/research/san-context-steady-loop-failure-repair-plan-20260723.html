Repair Plan / Context Steady

San 会话循环故障修复方案

修复对象不是单一阈值，而是三条失效的系统契约：压缩摘要越权定义当前任务、Segment 维护错误触发完整压缩、工具循环缺少“证据是否增长”的收敛判断。

结论：拆开权威状态、维护边界与执行收敛；不能只改 Prompt 或调大阈值

2026-07-23
优先级
P0：目标不漂移、不过早压缩、循环可终止
主要范围

兼容策略
append-only 升级；旧 JSONL 不重写

1. 修复决策

采用四层修复：第一层建立由 journal 直接派生的当前任务权威态；第二层把 40K/15 分钟 Segment 边界改为无 LLM、无历史重写的 checkpoint；第三层增加“动作指纹 + 证据增量”收敛守卫；第四层补齐真实触发原因、目标冲突和重复动作的观测与回归。

故障链 修复不变量 权威态与来源隔离 Segment 与压缩解耦 循环收敛守卫 可观测性 代码落点 测试与验收
0

摘要的任务权威

Compaction summary 只保存历史证据，不再拥有当前 Goal、完成状态或执行许可。

40K ≠ Compact

Segment 的真实语义

Segment 是逻辑维护边界，不是物理 working-set 压缩阈值。

有限

无增量侦察

重复动作在软纠偏后仍无新证据时，下一轮强制输出结论或诚实阻塞。

2. 已确认故障链

输入
读取外部会话 JSONL

工具结果中包含另一个会话的用户消息、## Goal 与完成声明。

污染
摘要混淆来源

压缩模型把被调查会话的任务当成当前会话任务。

继承
错误 Goal 递归保留

update summary 继续携带 previous summary 中的错误目标和假完成状态。

放大
40K Segment 触发完整压缩

压缩后基线约 30K～50K，再增长 40K 就再次摘要。

失控
无证据循环

反复读取、搜索和压缩，没有 edit、test 或新事实，也没有强制收敛。

现场 可观察事实 说明
调查会话 019f8c8a-… 已有有效结论后又执行约 62 次工具调用；发生 4 次压缩，后三次约在 79K～115K。 调查任务本身被被调查材料污染，并进入同类循环。
原始异常会话 019f8935-… 33 次 Segment 压缩；用户纠正“应该实现代码”后约 981 次工具执行，仍无 edit/write。 不是单纯模型偶发重复，而是运行时缺少阶段转换和停止条件。
触发配置 activationThresholdTokens=240000，segment.maxTokens=40000，maxDurationMs=900000。 240K 只控制 Context Steady 激活；激活后的 40K hint 实际走完整 compaction。
现有循环守卫 只识别“单工具、完全相同参数、连续重复”，达到阈值时仅注入一次提醒。 交替读取 A/B、参数微调、不同查询但无新证据、提醒后继续执行均可绕过。

排除项：muyuan rate limit 和 504 会延长等待，但不能解释目标替换、70K～100K 重复压缩和近千次无写入侦察，因此不作为根因修复入口。

3. 修复后必须成立的不变量

A-1 当前任务只来自当前会话

当前任务由 branch journal 中真实的 user entry 与最新用户 steer 派生。工具输出、compaction summary、被读取的 JSONL、网页和日志无权更新它。

A-2 执行完成必须有工具证据

“已创建/已修改/测试通过”只能由成功配对的 mutation/test tool call + result 支撑；assistant 文本和 LLM 摘要不能生成完成事实。

M-1 Segment 不等于压缩

token/time Segment 到点只关闭一个逻辑片段并持久化 checkpoint，不调用摘要模型、不重写 working set。

M-2 物理压缩只由容量压力触发

只有 steady target、native threshold、hard pressure、overflow 等真实容量原因可以进入 compaction。

C-1 长任务按进展而非调用数判断

60 次不同且持续产生新证据的工具调用可以继续；6～12 次重复且证据不变的侦察必须被纠偏或终止。

C-2 用户消息始终抢占

任何排队中的用户纠正或状态询问都先于 advisor 等待、Segment checkpoint 和非必要压缩送达模型。

4. P0 权威状态与来源隔离

现有 compaction-summary-context.md 已经说明“kept latest user prompt authoritative”，但当前用户消息在长逻辑 turn 多次压缩后可能已不在 kept tail；仅加强 Prompt 仍会重现。本方案把权威关系变成可验证的数据结构和消息顺序。

4.1 新增确定性 ActiveContinuationState

interface ActiveContinuationState {
  schemaVersion: 1;
  sessionId: string;
  logicalTurnId: string;          // 当前会话真实 user entry id
  activeUserEntryId: string;
  supersededUserEntryIds: string[];
  promptGeneration: number;
  executionEvidence: {
    successfulMutations: ToolEvidenceRef[];
    successfulVerifications: ToolEvidenceRef[];
    observedResources: ToolEvidenceRef[];
  };
}
  • activeUserEntryId 只按 journal role 和 branch 顺序选择，不让 LLM重写或归纳。
  • 恢复上下文时用该 entry id 从 append-only journal 读取用户原文；Segment 不复制一份可能失真的“Goal”。
  • 用户 steer 一旦持久化，新 user entry 立即成为 active entry，旧 entry 进入 supersededUserEntryIds。
  • execution evidence 只从成功配对的工具调用/结果生成；没有 edit/write 时明确记录 mutation count 为 0。
  • assistant 自述、TurnDigest 的 factsLearned 和 LLM summary 均不能进入权威字段。

4.2 固定 provider 上下文顺序

1
System / Developer

运行规则与项目规则。

2 · 数据
Historical summary

明确标记为非权威历史证据。

3 · 权威
Continuation state

journal 用户原文 + 已验证执行证据。

4
Kept live tail

最近工具调用和结果。

5 · 最高
Latest user steer

若存在，覆盖 continuation state。

continuation message 由静态模板渲染，推荐 custom type san.context_continuation.authority，隐藏显示、agent attribution。它必须在 local summary、remote compaction、 snapcompact 和 extension compaction 后统一注入，不能只修 local summary 路径。

4.3 Compaction summary 降权

生成协议

  • 移除输出格式中的 ## Goal，改为“历史请求与证据”。
  • 工具输出统一标记为 quoted/untrusted data，其中的 user/system/Goal 只允许被描述，禁止被采用。
  • 摘要不输出“当前下一步”；只能记录历史上尚未验证的事项。
  • previous summary 先降权再合并，旧 Goal 不再递归继承为当前任务。

运行时协议

  • Compaction entry 继续保存原始 summary 供审计，但 provider 渲染始终套 historical wrapper。
  • 若 summary 声称修改文件，而 execution evidence 无 mutation，continuation state 明确给出冲突事实。
  • 新摘要出现禁止的 active-goal 字段时执行一次有限修复请求；仍无效则记录明确错误并使用标记为 incomplete 的确定性历史摘要。
  • fallback 必须写入来源和错误原因，禁止静默伪装成 LLM 摘要成功。

4.4 旧会话兼容

  • 不回写、不批量修改已有 JSONL；读取 v1 Segment/Compaction 时按“历史非权威数据”处理。
  • 首次新维护边界写入 v2 Segment 与 ActiveContinuationState，形成 append-only 升级。
  • 旧 summary 中即使存在 ## Goal，也不能覆盖从其 source user entry 恢复出的当前请求。
  • 找不到 source entry 时显式写入 authority_source_missing 并停止自动继续，不猜测 Goal。

5. P0 Segment checkpoint 与物理压缩解耦

5.1 一个决策对象，两个动作

type ContextMaintenanceTrigger =
  | "segment_tokens"
  | "segment_duration"
  | "steady_target"
  | "native_threshold"
  | "hard_pressure"
  | "overflow"
  | "idle"
  | "incomplete";

type ContextMaintenanceAction =
  | "checkpoint"
  | "context_full"
  | "snapcompact"
  | "remote_compaction"
  | "handoff"
  | "none";

interface ContextMaintenanceDecision {
  primaryTrigger: ContextMaintenanceTrigger;
  matchedTriggers: ContextMaintenanceTrigger[];
  action: ContextMaintenanceAction;
  contextTokens: number;
  segmentDeltaTokens: number;
  segmentElapsedMs: number;
}

保留 #runAutoCompaction() 的旧 operational reason 仅用于兼容时，也必须额外传递 ContextMaintenanceDecision。日志、Segment、audit 和 probe 一律记录真实 primaryTrigger，不再把所有路径都写成 threshold。

触发条件 新动作 是否调用摘要模型 是否重写 working set
segment_tokens / segment_duration 同步生成确定性 checkpoint，append Segment boundary 否 否
steady_target 按配置执行 context-full / snapcompact / remote 按策略 是
native_threshold 执行 native compaction 策略 按策略 是
hard_pressure / overflow 容量恢复；失败后显式暂停 按策略 是
idle / incomplete 保持现有显式路径，但写入独立 trigger 按策略 按策略

5.2 #maintainContextMidRun() 新流程

1. 持久化刚结束的 tool turn，并读取排队中的用户消息。
2. 若有 user steer：除 overflow/hard pressure 外，跳过 advisor 等待和维护，先交付用户消息。
3. 同时计算 matchedTriggers，不丢失“两个阈值同时命中”的事实。
4. hard_pressure / overflow / native_threshold / steady_target 命中：执行一次物理维护并关闭当前 Segment。
5. 仅 segment_tokens / segment_duration 命中：append checkpoint-only Segment，然后直接返回。
6. 无触发：继续下一次 provider request。

5.3 Segment 阈值改为模型相关

默认阈值不再对所有模型固定 40K。建议默认采用：

physicalMessageBudget = min(steadyTarget, nativeThreshold) - nonMessageTokens
autoSegmentTokens = clamp(8_000, 64_000, floor(physicalMessageBudget * 0.20))
  • segment.maxTokens 显式配置为正数时继续作为精确覆盖值。
  • 未显式配置时使用 auto；禁用 Segment 统一使用 segment.enabled=false，不再复用 0 的双重语义。
  • maxDurationMs=15min 可保留，但只产生 checkpoint，不再产生昂贵摘要和历史重写。
  • 物理压缩后 Segment delta 清零；下一次完整压缩仍以总 working-set 容量为准，而不是“压缩基线 + 一个 Segment”。

预期效果：500K context、240K steady target 的会话可在 40K～50K 左右持续写 checkpoint， 但不会因此在 70K～100K 完整压缩。只有 provider working set 再次接近 240K 或 native threshold 时才物理维护。

6. P0 “动作指纹 + 证据增量”循环收敛守卫

保留现有 ToolCallLoopGuard 的精确重复快速检测，同时在 coding-agent 层增加 ToolProgressGuard。新守卫以 logical user turn 为作用域，识别交替循环和“参数不同、结果等价”的无效侦察。

6.1 记录模型

Action fingerprint

规范化工具名、资源、查询、范围、cwd 和参数；忽略 intent、call id 等易变字段。

Evidence fingerprint

对结构化结果或规范化文本、exit code、文件 diff/test outcome 计算稳定 hash。

Progress delta

新资源、新结果、新 diff、新测试状态、成功 mutation 或新用户消息才算进展。

read/search/exec/browser 各自使用明确 normalizer，不能用一套删除数字/时间的万能正则，以免把真实变化抹掉。未知工具退回“完整规范化参数 + 结果 hash”的保守判定。

6.2 默认状态机

状态 默认进入条件 动作 退出/重置条件
tracking logical turn 开始 记录最近 12 个 action/evidence fingerprint 检测到 saturation
soft_redirect 同动作同结果 3 次；或最近 8 个观察动作只覆盖 ≤2 个资源且无证据增量 注入一次隐藏纠偏，列出已知证据、重复模式、mutation/test 计数 产生新证据、mutation、verification 或用户消息
finalize_required soft redirect 后再发生 3 个无增量观察动作 下一次 provider call 使用 toolChoice="none"，强制输出结论/明确阻塞 文本答复结束 logical turn；新用户消息开始新状态

6.3 强制收敛内容

  • 调查任务：基于已有证据直接回答；区分“已确认”“推断”“尚缺证据”。
  • 修改任务：若 mutation count 为 0，禁止宣称实现完成；明确说明尚未改动及被守卫终止的重复模式。
  • 已发生 edit/write 但未验证：明确列出改动证据和缺失的测试，不把“写入成功”当作“功能正确”。
  • 用户状态询问/纠正：取消 pending finalization，立即把用户消息放到下一 provider call 的最高优先位置。

6.4 误报控制

  • 结果 hash 变化、新文件/新范围、新 diff 或测试状态变化会重置无增量计数。
  • 已知 poll/wait 工具按工具元数据分类，不进入普通观察饱和判断；仍接受用户 interrupt。
  • 长任务不设统一“最多 N 次工具调用”；只限制无新证据的重复模式。
  • 软纠偏每个 logical turn 只注入一次，避免守卫自身变成新的上下文噪声。

7. P1 可观测性与故障归因

将 context probe 升级到 schema v3；旧 v2 继续可读。记录计数和 hash，不写完整工具输出或用户原文。

分组 新增字段 用途
maintenance primaryTrigger、matchedTriggers、action、segmentDeltaTokens、segmentElapsedMs 区分 40K checkpoint、steady target、native threshold 和 hard pressure。
compaction tokensBefore、tokensAfter、summaryInputTokens、summaryOutputTokens、summarySource 确认完整压缩间隔和摘要成本。
authority activeUserEntryId、authorityStateInjected、forbiddenGoalField、executionClaimConflictCount 发现摘要越权和“声称已修改但无 mutation”冲突。
convergence actionRepeatCount、noEvidenceCount、uniqueResourceCount、softRedirects、forcedFinalizations 证明循环被收敛，同时观察误报。

日志原则：每次维护只写一个 decision record；开始/结束事件共用 maintenanceId。不得再用单一 reason: threshold 代表多种触发源。

9. 回归测试与验收门槛

9.1 必须新增的契约测试

契约 测试构造 通过条件
外部 Goal 不能污染当前 Goal 当前用户要求调查循环；read tool 返回包含“## Goal：实现二维码”和假完成声明的 JSONL；强制两轮 compaction。 后续 provider payload 的 authority state 始终引用调查请求；响应不得继续二维码任务。
执行声明必须有工具证据 compactor 故意输出“已创建 SQL/Controller”，journal 中没有 mutation tool。 continuation state 记录 mutation count 0；模型不得把这些文件视为已创建。
Segment boundary 不触发完整压缩 将测试 Segment 阈值设得很小，连续产生多个不同工具结果，但总上下文低于 steady/native target。 Segment/checkpoint 数增长，compact() 调用数为 0；跨过物理阈值后才精确调用 1 次。
完整压缩不再每 70K～100K 重复 模拟 500K window、240K target、40K～50K checkpoint delta。 相邻物理压缩由 working-set target 决定，checkpoint 数不影响 compaction count。
交替读取循环可终止 模型交替 read A/read B，结果 hash 不变并忽略一次 soft redirect。 有限次数后下一请求 toolChoice=none，输出已有结论；不再发工具调用。
真实新证据不会误杀 相同查询每轮返回不同内容，或每轮读取新路径，最终产生 edit + test。 no-evidence 计数重置，任务正常继续，最终不触发 forced finalization。
用户纠正立即抢占 soft redirect 后排队用户消息“停止调查，直接给结论”。 下一 provider call 先看到用户消息；pending compaction/finalization 不覆盖它。

9.2 现有测试调整

  • context-steady/agent-session-dogfood.test.ts 中“60-call logical turn across recursive Segment maintenance”改成：不同且有进展的 60 次调用允许继续；checkpoint 可以递归产生，但完整 compaction 只受物理压力驱动。
  • context-steady/agent-session-m2.test.ts 中“no-op Segment maintenance”不再期待一次 auto-compaction；改为期待一次 checkpoint append、零 compaction。
  • agent-session-tool-call-loop-guard.test.ts 保留精确重复覆盖，并新增 A/B cycle、结果变化、mutation reset、用户 steer 抢占。
  • context-steady/probe.test.ts 验证 v3 trigger/action 字段及 v2 兼容读取。

9.3 Benchmark 发布门禁

  • Meta-investigation 场景在至少一次 compaction 后仍保持正确 active user entry。
  • 嵌套日志中的 Goal、system prompt 和假完成状态只作为被引用数据。
  • 无证据重复工具调用在默认阈值内进入 final answer，不出现开放式循环。
  • 有新证据的长任务不因总调用数被提前终止。
  • 500K 模型在低于 steady/native target 时不会仅因 Segment delta 执行完整压缩。
  • probe 能还原每次 checkpoint/compaction 的真实原因、成本和收敛动作。

10. 发布、迁移与回滚

上线顺序

  1. Authority 修复直接作为正确性不变量启用，不设长期关闭开关。
  2. Segment/compaction 解耦随 schema v2 启用，保留显式旧阈值读取兼容。
  3. Progress guard 先 probe-only，再 soft，再 hard；每阶段用真实会话分布检查误报。
  4. 通过 meta-investigation benchmark 后再作为默认发布配置。

回滚边界

  • Segment v2 与 probe v3 都是 append-only，旧二进制忽略未知 custom entry。
  • Progress hard finalization 可单独回到 soft-only，不回退 authority 隔离。
  • 不得通过重新启用“40K 直接 compaction”回滚；容量问题应回到 steady/native trigger 排查。
  • 不删除、不重写用户已有 session JSONL。

风险与控制

Authority message 增加 token 只注入当前 user entry 和有界执行证据；原文超预算时记录截断并保护 source ref，不能静默改写语义。
Checkpoint 数量增加 custom entry 不进入 provider context；通过 source frontier 只消费最新 Segment，避免递归读取所有 checkpoint。
Loop guard 误杀调查 以 evidence delta 而非调用数判断；先 soft redirect；变化结果、新资源、mutation、test 或 user steer 均重置。
Remote compaction 绕过修复 authority 注入放在 session context 重建层，覆盖 local、remote、snapcompact 和 extension 路径。

11. 明确不采用的方案

只把 40K 调大

只能延迟循环，仍然混淆 Segment 与物理压缩；小窗口模型还会失去维护边界。

只修改 summary Prompt

现有 wrapper 已声明最新用户优先仍然复现；Prompt 不能替代 journal 权威态和结构化冲突规则。

设置统一工具调用上限

会误杀有真实进展的长任务；应限制“无证据增量”的模式，而不是工具调用总数。

把 504/rate limit 当根因

网络失败需要有限重试与明确错误，但无法修复目标污染、假完成状态和本地重复侦察。

12. Definition of Done

  • 外部日志、网页或工具输出中的 Goal 无法成为当前任务权威。
  • 摘要声称已修改文件但 journal 无 mutation 时，系统显式识别冲突且不宣称完成。
  • 40K/15 分钟 Segment 边界只写 checkpoint，不触发完整 compaction。
  • 所有物理维护都能从 probe 中还原真实 trigger、action、before/after tokens 和 summary 成本。
  • 精确重复与 A/B 交替循环都能在有限轮次内软纠偏并最终收敛。
  • 不同且持续产生新证据的 60+ 工具调用仍能完成。
  • 用户纠正和状态询问在下一 provider boundary 抢占非必要维护。
  • focused tests、bun check、benchmark smoke 和 meta-investigation 发布门禁全部通过。
  • 旧 session 无需迁移重写即可安全恢复；没有未记录的 fallback、错误或警告。
