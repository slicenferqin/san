1. 结论先行

当前不适合把 v0.1–v0.4 统称为“成熟可用”。 v0.1 的主要稳态链路已接近代码级闭环，本轮发现的 ContextPlan 漂移也已有工作区修补；但 v0.2 的默认关闭、并发收敛和账本单调性，v0.3 的跨会话 scope，以及 v0.4 的交付确认并发隔离，仍存在生产入口可达的合同破坏。
v0.1 · 条件 GO

核心路径完整；本轮关闭 tool-loop/compaction 后审计快照失真。真实模型长轮质量仍属于产品验收。

v0.2 · NO-GO

功能开关不能阻止显式运行；Worker 异常可在 run 已终止后继续执行；runId/revision 可破坏账本单调性。

v0.3 · NO-GO

生产 capture 把 project fact、workflow、failure posture 全部写成 session scope，跨 session Brain 实际失效。

v0.4 · NO-GO

全局 prepared-delivery 集合允许无关命令提前确认后台结果；过期 checkpoint 还拥有 1ms 继续完成窗口。

4. v0.1 · Context Steady

V01-01 · P0 ContextPlan 计划快照与真实 provider 输入发生漂移

生产证据
AgentSession.#buildContextSteadyRequestPlanWithRecovery() 在首请求前建计划；tool-loop 后消息继续增长，compaction/model/non-message budget 也可能改变输入边界。
反例
首个 provider request 的 projected tokens 在 control band 内；工具结果把下一次请求推过边界，但旧 plan 仍用于 materialize/status/audit，导致“审计显示安全、实际 payload 已变化”。
影响
质量门、hard-pressure 判断、持久化 audit 和真实请求不一致，直接破坏 v0.1 的可审计稳态合同。
修复合同
每次 provider call 前重新比较 plan 输入指纹和 projected tokens；尾部增长只刷新 audit，结构性输入变化则完整重建；compaction 后清空 stale last plan。
当前状态
工作区已修补 agent-session.ts 与 agent-session-m2.test.ts 已有对应改动，仍需纳入本轮最终全量验证。
本轮未再确认新的 v0.1 代码级阻断。 Digest ledger、fallback、ContextPlan materialize、checkpoint/rebase、recall scope filtering 和 provider role 路径在当前实现中均有生产调用与合同测试。真实模型质量、长轮 p95 和 burst 恢复持续轮数仍需产品验收，不能由单元测试替代。

5. v0.2 · Execution Loop

V02-01 · P0 默认关闭只是“少注入上下文”，并没有阻止执行

生产证据
settings-schema.ts 将 san.executionLoop.enabled 默认设为 false；但 runConfiguredSanLoop()、/san-loop run、/solo、/team、/council 都未检查该值。
反例
保持默认设置，执行 /team ship it，仍会创建 task-agent executor、发现 checks 并启动 Commander/Worker/Supervisor。
影响
违反“显式启用、默认交互路径关闭”的发布合同；用户以为功能关闭时仍可能产生模型调用、子 Agent 和工作区变更。
修复合同
所有 run/shortcut 入口统一 fail-closed；status 和 stop 保持可用，避免关闭后无法观察或中止历史 run。

V02-02 · P0 Worker throw 后兄弟任务可越过终态继续运行

生产证据
runner.ts::mapWithLimit() 使用共享外部 signal 和 Promise.all(workers)；任一 mapper reject 会立刻退出，没有 batch AbortController，也不等待其他 worker settled。
反例
A Worker 立即 throw；B Worker 已启动并等待 I/O。runner catch 持久化 failed 并返回/抛错，active registry 清理；B 仍持有未 aborted signal，可在终态后继续读写。
影响
ledger 终态不再代表副作用终止；迟到结果不入账，abort/status 也无法再找到 active run。
修复合同
首个异常原子触发 batch abort，停止新调度，等待所有已启动 Worker settled，再持久化 terminal；保留第一个业务错误作为 surfaced error。

V02-03 · P1 append-only ledger 不是 revision 单调视图

生产证据
rebuildSanLoopLedger() 按 entry 遍历直接 latestRuns.set(runId, entry)，不比较 revision；runSanLoop() 只拒绝“当前 active”同 ID，不拒绝历史 terminal 同 ID。
反例 A
revision 5 后追加一个迟到 revision 3 快照，重建结果回滚到 revision 3。
反例 B
复用 terminal runId 会追加 revision 0 新 run，覆盖旧运行的查询视图，并把两次生命周期的 event 混在同一个 runId 下。
修复合同
创建前拒绝任何历史重复 runId；重建选择最高 revision，同 revision 只允许后写 entry 作为等价迁移兼容。

V02-04 · P2 SDK 数值边界未归一化

生产证据
maxWorkers = Math.max(1, Math.floor(value)) 对 NaN 仍为 NaN；maxRetries 原样进入 snapshot。
反例
SDK 传 maxWorkers: NaN，Array.from({length: NaN}) 启动 0 个 worker；输入数组存在但结果为空，后续状态机可错误推进。NaN retry cap 也会破坏 exhausted 比较。
修复合同
worker 使用正整数归一化；retry 使用非负整数归一化，并保留合法的 0。

6. v0.3 · Brain Runtime

V03-01 · P0 稳定 identity 已实现，但 capture 生产路径没有使用

生产证据
AgentSession.#generateTurnDigest() 调用 captureSanBrainTurn() 时固定传入 { kind: "session", key: this.sessionId }。稳定 user/project/repo scope 只在下一轮 activation/recall 时解析。
传播范围
extract.ts 把 project fact、standing decision、workflow pattern、skill/check/recall candidate、failure posture 全部放入 fallback scope。
反例
Session A 捕获并批准项目事实；Session B 位于同一 worktree。B activation 查询稳定 project/repo key，但候选 key 是 A 的 sessionId，因此永远不匹配。
影响
v0.3 对外最核心的“跨 session 项目经验”在真实 AgentSession 中不可达；dogfood 手工传 repo scope，因此没有暴露生产差异。
修复合同
capture 前解析稳定 identity；user preference 使用 user scope，其余 deterministic fallback 使用更窄且稳定的 project scope；解析失败时 fail-closed 到 session scope，不能扩大。
150ms 边界属于需要继续守住的合同。 当前 Brain capture 开启时会把 digest 单次请求 timeout 压到 150ms，但 retry 与 provider abort 服从性仍需最终测试覆盖“总等待时间”，而不是只检查配置值。本报告暂不把它列为已证实的第 9 个缺陷；修复 V03-01 时会补生产 capture 测试，并保留这一残余风险说明。

7. v0.4 · Workflows

V04-01 · P0 unrelated command 可以替后台结果完成 delivery ack

生产证据
WorkflowCommandService 用实例级 #preparedDeliveries 保存所有 delivery；每个前台命令 output 成功后，helper 调用 acknowledgePreparedDeliveries() 批量确认全部。
并发反例
后台 run completion 调用 deliverCompletedRun(A) 后阻塞在 output(A)；此时用户执行无关 /workflow list，它 output 成功并批量 ack A；随后 output(A) 失败。结果从未交付给消费者，但 durable state 已是 delivered。
影响
破坏“只有对应消费者成功接收后才确认”的 exactly-once/at-least-once 边界；失败后无法 replay。
修复合同
delivery preparation 必须返回显式 receipt；调用方只 ack 本次 output 对应的 receipt。移除全局 bulk-ack，不允许跨命令、跨后台观察者串线。

V04-02 · P1 已过期 checkpoint 仍被赋予最少 1ms

生产证据
RestrictedWorkflowRuntime 计算 remainingDurationMs = Math.max(1, limit - elapsed)，即使 elapsed 已超过 hard duration 也创建 1ms timer。
反例
恢复一个已经超过 duration 的 paused checkpoint，脚本只执行同步 return 或命中 completed-call cache；在 timer 触发前即可完成并被标为 completed。
影响
硬时间预算在 crash/resume 边界失效，且结果与机器调度速度相关。
修复合同
构造时记录“启动即过期”，execute() 在 parse/step/缓存命中之前同步抛出 time_limit；未过期才创建剩余时长 timer。
