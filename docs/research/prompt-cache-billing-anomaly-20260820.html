02

先排除我们自己的问题

客户端改写 prompt 前缀会正当地导致缓存失效。我们把这部分先全部剔除了。

我们的客户端会在每次请求前为「可缓存前缀」计算一个指纹，覆盖：模型标识、system prompt、工具定义表、上下文计划、最近一次上下文压缩点。任何一项变化都会被记录下来。

当天 cache_read = 0 且 prompt 超过 2 万 tokens 的请求共 44 笔。其中 31 笔确实是我们改了前缀——上下文压缩、工具表变更等——这 31 笔属于预期行为，我们不认为是贵方的问题，也不在本报告的索赔范围内。剩下 13 笔的前缀指纹与上一笔请求完全一致。

以其中一笔（15:20:15）为例可以逐 token 验证前缀未被改写：上一笔请求 prompt 合计 121,254 tokens、输出 660 tokens，两笔之间客户端只追加了一个 7,429 字符的工具返回，本笔 prompt 为 124,918 tokens——纯追加，无任何前缀重写；紧随其后的下一笔请求又正常命中了 120,320 tokens，说明这条前缀链本身是连续且可缓存的。

07

附带观察

以下几项不构成投诉，只是排查过程中发现的、可能对贵方定位有帮助的现象。

  1. 失败请求在用量导出中不可见。客户端在 14:00 – 16:50 观察到 55 次上游 5xx，用量导出中没有任何对应记录；我们无法自行核对失败率。此外我们的客户端熔断器当天对该端点触发过 8 次。
  2. 21 行 0 token 记录。导出中有 21 行 input / output / cache read 全为 0、无首字时间、耗时 1 – 2041 ms 的记录，全部为 WS 通道，分布在 10:04 – 14:18。想确认这些代表什么（连接建立？客户端取消？失败重试？）。
  3. Cache Creation Tokens 全天恒为 0。如果这个字段本应记录缓存写入，那么它与 cache read 的异常可能出自同一处计量逻辑。
  4. 首字延迟存在约 6 秒的地板。即使新增 input 不足 5,000 tokens，首字中位数也有 6,143 ms；新增 input 到 10 – 20 万 tokens 时，中位数才 7,031 ms。首字几乎不随 prefill 量增长——这既是我们判断「缓存可能其实命中了」的依据，也说明这条链路上有一段固定开销值得排查。
08

希望协助确认的问题

用第 04 节的 13 个 response id，查一下上游返回的原始 usage 中 prompt_tokens_details.cached_tokens 是多少？

这一条能直接区分两种情况：上游确实未命中（路由/亲和性问题），还是上游命中了但中转层未透传或未计入账单（计量问题）。首字延迟的证据更偏向后者。

中转层是否把客户端传入的 prompt_cache_key 原样透传给上游？WS 通道是否同样透传？

我们确认客户端在整个会话中发送的是同一个固定值，未做任何轮换。

Account ID 4 这个分组下是否有多个上游账号或节点在轮询？同一 prompt_cache_key 是否保证落到同一上游？

异常 B 中「命中了一份更浅的旧快照」的形态，与请求在多个上游之间轮转的表现一致。

如果确认属于计量侧未计入 cached_tokens，能否按第 06 节的口径修正当天账单？

我们更关心的是止损后续，而不是这一天的金额本身——如果是计量 bug，它每天都在按 10 倍单价结算这部分 tokens。
