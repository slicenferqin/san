上下文稳态重新设计：先保证不丢，再谈省 token

这是一份独立方案，不修改、不续写 原复盘报告。 我把问题换成一个更容易评审的比喻：搬家时，必须先确认新家已经放下箱子，才能把旧家里的箱子扔掉。 现在的流程偶尔先扔箱子，再发现新家装不下，于是历史就失去了代表。

面向评审的版本 少术语 静态 HTML，无外部依赖 不改原报告
先看结论
Context Steady 的第一目标不是“压得最薄”，而是“任何被删掉的内容，都必须有一份已经放进去的替代品”。

只要这条规矩成立，摘要模型偶尔失败、预算暂时偏小、缓存优化尚未完成，都只是“省得少”；不会再变成“历史突然没了”。

01 / 一句话看懂

先修“会不会丢”，再修“省不省”

目前最严重的不是摘要写得不漂亮，而是摘要没有装进计划时，系统仍然把它覆盖的旧消息排除掉。这个顺序反了。

2 → 154

只改 400 个预算单位，覆盖量断崖变化

真实会话重放：预算 3000 时只覆盖 2 条 entry；预算 3400 时覆盖 154 条。说明核心问题在“准入规则”，不是摘要内容。

ds-flash

当前摘要模型名称找不到

当前有效配置开启了摘要 LLM，但 san models ds-flash --json 返回空列表。摘要会落到不能替代原文的 fallback 路径。

3 / 31

原报告有一处统计需要更新

引用的 session 中实际有 31 个 plan，其中 3 个包含 checkpoint。原报告“31 个全部没有 checkpoint”不是当前 journal 的准确统计，但核心故障仍可重放。

02 / 三条规矩

这份方案只守三条规矩

它们比具体采用哪种摘要模型、用多少 token 更重要。实现方案可以换，规矩不能换。

RULE 01

没有替代品，就不删原文

摘要没生成、摘要放不下、摘要覆盖范围说不清，全部按“没有替代品”处理。保留原文比静默丢历史更安全。

RULE 02

只用“最后真正发送的大小”算账

不要一会儿按 JSON 大小算，一会儿按渲染后的文字算。候选内容先按最终发送形态试装，再决定能不能占位。

RULE 03

先摆好，再搬走

规划阶段只做试装，不改变原消息。等替代内容、覆盖范围、总大小都确认后，才一次性生成发送内容。

03 / 现状与目标

现在的流程，和应该有的流程

现在先删，后发现装不下

  1. 1找到一个 checkpoint，觉得它“应该”能代表一段旧历史。
  2. 2用一套偏大的旧估算判断它装不下，于是跳过 checkpoint。
  3. 3仍然把 checkpoint 覆盖的 digest 过滤掉。
  4. 4原文重新回到发送内容，压缩频繁发生，且过程没有明显提示。
→

目标先试装，成功后才删

  1. 1保留当前对话和正在进行的工具调用，不参加“省空间”竞赛。
  2. 2把 checkpoint、digest 按最终发送形态试装。
  3. 3只有替代品真的装入计划，才允许它覆盖旧消息。
  4. 4装不下就退回原文或更小卡片，不允许出现“两个都没了”。
04 / 可视化流程

新的发送流程：每一步都能回答“旧内容去哪了”

绿色路径是正常路径；黄色是可接受的降级；红色是宁可暂停也不偷偷删历史的路径。

可以继续 尝试降级 保守停下

核心改变只有一句话：删除旧消息是最后一步，不是试装失败后的默认动作。

05 / 新方案的结构

把上下文分成三个抽屉

每个抽屉有不同职责。不要让一张摘要卡片同时承担“记住事情”“证明覆盖”“节省空间”三个互相冲突的任务。

DRAWER A / 永远在手边

正在聊的内容

当前用户请求、最近几轮对话、未完成的工具调用和最新结果。

  • 优先级最高
  • 不参加历史压缩
  • 直到这一轮结束都不移动
DRAWER B / 已整理的卡片

可以替代旧内容的摘要

checkpoint 是较大的总结卡；digest 是较小的回合卡。它们只有在真的装入发送内容后，才有资格替代旧消息。

  • 按最终发送形态计量
  • 装不下就降低粒度
  • 不能替代原文的 fallback 不占主要预算
DRAWER C / 原始档案

完整 journal

完整记录永远留在 session journal 中，供回放、展开和故障恢复使用；发送时是否带上，由已确认的替代关系决定。

  • 不因一次发送失败而删除
  • 窗口裁剪只取交集
  • 找不到覆盖范围时默认保守

每张卡片都必须回答三句话

  1. 1我是谁？这是一张 checkpoint、digest，还是普通 recall。
  2. 2我替代谁？明确列出旧消息范围；范围不完整就只替代已知部分。
  3. 3我真的进去了？以最终发送内容为准，不以候选状态或旧估算为准。

预算先看“有效内容”，再看“装饰内容”

下面不是精确比例，而是规划顺序。当前消息和安全余量先占位；摘要只有在能带来真实节省时才进入。

当前必须保留
卡片有效替代
原文必要时保留
余量给模型输出

如果“卡片”占满预算却没有减少原文，直接放弃卡片，不为了显示“启用了稳态”而发送它。

06 / 四个关键决定

我建议评审直接拍板这四件事

决定一：安全默认是“保留原文”

摘要模型不可用、范围不完整、预算不够，都不删除原文。代价是偶尔多花 token；收益是不会把错误的摘要当成事实。

决定二：checkpoint 大小从容器反推

不要再让 checkpoint.maxTokens=12000、contextPlan.maxTokens=3000 各自独立。checkpoint 的可用大小应由当前计划容器和余量共同决定。

决定三：摘要模型启动时必须可验证

配置里写了一个当前找不到的 ds-flash，应该在启动时明确提示并切到“只保留原文”模式，而不是静默生产大量无覆盖能力的 fallback。

决定四：缓存优化放到第二阶段

缓存前缀稳定很重要，但它不能掩盖覆盖权错误。先证明“旧内容没有丢、计划确实省了空间”，再冻结 plan 字节和优化重渲染。

07 / 落地顺序

四步落地，不一次改完所有东西

每一步都有独立的“能不能继续”标准。这样出现问题时，知道是安全规则、预算、范围，还是缓存造成的。

STEP 1
先止血

禁止“两个都没了”

拆开“摘要与当前请求相关”和“摘要已经装入计划”两个状态。摘要没进计划，就恢复它覆盖的 digest；摘要范围不确定，就保留原文。

通过标准同一份真实 replay 不再出现“checkpoint 未进入、covered digest 也消失”。
STEP 2
统一算尺

所有内容按最后发送的样子计量

候选卡片先渲染、再计量；计划未定稿前不改变原消息。让 checkpoint、digest、淘汰逻辑共用一把尺。

通过标准预算 3000 的临界用例不再因为 JSON 外壳被误判；计划自身大小不会超过承诺。
STEP 3
补牢历史

压缩后仍能找到旧摘要覆盖的那一段

摘要保存稳定的范围标记；当前窗口只取这个范围与窗口的交集。端点在窗口外，不代表整张卡片失效。

通过标准窗口裁掉一端时，覆盖范围按比例变小，而不是突然变成几个零散 tool evidence。
STEP 4
最后稳缓存

同一轮对话不要反复改写计划

沿用现有单回合冻结原则：新工具结果不触发无意义的 plan 重排；只有新 checkpoint、压缩或明确话题切换才重新布局。

通过标准计划内容在工具循环中稳定，缓存收益不会因为每次重渲染被自己打掉。

配置层的同步动作

这不是最终设计，但应立即做：

# 用一个当前能解析、并且确实有凭据的模型；不要继续使用 ds-flash
san:
  contextSteady:
    digest:
      llm:
        modelRole: <可解析且已认证的模型 selector>

当前项目配置的 reserveRatio: 0.15 已与历史 session 使用的 0.25 不同；项目配置只在从该仓库目录启动的新进程中生效。修改后重启会话，再观察新数据。

08 / 验收标准

评审不要只看“测试通过”，要看这五个结果

检查现在的基线新方案必须做到判断
预算临界 3000 时覆盖 2；3400 时覆盖 154 临界时要么卡片进去了，要么它覆盖的 digest 仍然可以进；不能两边都落空 硬条件
摘要模型 ds-flash 当前查询不到 启动时能发现不可用配置；新 session 不再静默积累无覆盖能力的 fallback 硬条件
窗口裁剪 端点离开窗口后可能退化为零散引用 覆盖范围取交集，能保留窗口内仍然可证明的部分 硬条件
净收益 小计划可能比它省下的 token 还贵 如果计划自身大于它实际省下的内容，就不注入计划 硬条件
缓存稳定 新 digest 会频繁改变 plan 前缀 同一逻辑 turn 内 plan 字节稳定；缓存指标在前三步通过后再比较 第二阶段

现有聚焦测试为 27 pass，但当前测试没有覆盖“checkpoint 存量估算略高于 plan 预算、渲染后却能装下”的真实临界形态。新方案的第一批测试必须直接钉住这条边界，而不是继续扩大宽松预算让测试自然通过。

09 / 给评审的最终判断

这不是“把参数调大”能解决的问题

应当接受的方向

把 Context Steady 定义为一个保守的“历史搬运系统”：它可以省空间，但不能在没有替代品时删除原文；所有替代关系都要在最终发送内容里成立。

不建议接受的方向

继续通过调大 recentDigests、提高 steady 阈值、单独放大 checkpoint 上限来掩盖准入错误。这些只能改变故障出现的时间，不能修复“两个都没了”。

推荐的评审决策：先批准 Step 1 和 Step 2，暂停缓存层的大改；同时把不可解析的摘要模型配置清掉。 等真实 replay 证明“预算临界时仍然有替代品、窗口裁剪后仍然有覆盖”，再进入缓存稳定化。

附录 / 事实边界

哪些是已观察事实，哪些是本方案判断

已观察

当前源码在 checkpoint 未准入时仍会按 includeCheckpoint 过滤 covered digest；真实窗口重放得到 3000→2、3400→154；当前有效摘要角色为 ds-flash 且模型查询为空；聚焦测试 27 pass。

方案判断

“先试装、后删除”“原文保守保留”“把 checkpoint 大小从容器反推”“缓存放到第二阶段”是本方案的设计选择，不是对现有代码行为的描述。
