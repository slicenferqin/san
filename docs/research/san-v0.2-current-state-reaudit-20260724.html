05 · Current findings

当前阻断项

P0 表示会造成错误产品行为、错误放行、权限边界突破或资源预算失效；P1 表示阻断原始验收或发布证据；P2 表示会持续扩大维护和诊断成本。

P0 · 4 rollout 前必须关闭

P0-01 · Evidence-free pass

Supervisor 可以在零测试、零证据、零缺陷时直接把 run 终结为 passed。

SanLoopReviewInput.testsRun、evidence 和 defects 全部可选；createSanLoopReviewReport() 将缺省值变成空数组；applySanLoopReview() 只看 verdict === "pass"。内置 supervisor-gate 只是 prompt 文本，没有 host-owned 证据引用或 check result gate。

运行探针：{status:"passed", calls:["commander","worker","supervisor"], reviewEvidence:[], testsRun:[], defects:[]}

P0-02 · Read-only role is not read-only

Supervisor 虽无 edit/write，却拥有无约束 bash；角色“禁止写代码”的硬隔离不成立。

SAN_LOOP_ROLE_TOOLS.supervisor 为 read/grep/glob/bash/yield。runSubprocess() 的 strict tool whitelist 阻止额外工具，但没有为 bash 设置只读命令集、工作区快照或路径 scope。Supervisor 可通过 shell 改文件；Worker 同样没有 assignment-specific path scope。

P0-03 · Solo contract mismatch

README 把 solo 定义为“单 agent 单角色”，生产路径却固定运行 Commander、Worker、Supervisor。

/solo 与 /san-loop run --mode solo 都进入同一个 runSanLoop() 主循环。模式只改变 turn budget 和 Oracle；Commander、Worker、Supervisor 在所有模式都会运行。生产设置还把全局 maxWorkers=3 传给 solo，覆盖 policy 中的 1。

README：solo = 单 agent 单角色。运行探针：solo passed，实际 role calls = commander → worker → supervisor。

P0-04 · Hard budget is turn-only

token、cost、provider request 和 wall time 只被记录，不会在调用前阻止超支。

runner 的唯一消费门禁是 remainingTurns。单个 role agent 内可以发生多次 provider request 和工具循环；瞬断重试也不消耗新的 role turn。usage 最终写入 snapshot，但没有 max token/cost/time/provider settings 或 preflight reservation；budget.reserveRatio 无生产消费者。

P1 · 6 阻断需求验收

P1-01 · Recovery is not resume

重启后 active run 被改成 blocked，没有恢复 DAG、pending assignment 或剩余执行。

recoverSanLoopRun() 固定写 status: "blocked"；命令面只有 run/status/stop，没有 resume。当前行为可以叫“安全收口”，不能叫原始合同中的 abort/resume。

P1-02 · ContextPlan references without materials

角色上下文只列出 ContextPlan entry ID，没有把稳定材料投影给角色。

context.ts 验证 ContextPlanAudit 后只收集最近 3 个 entry ID；role template 输出 Source ContextPlan refs。San-loop 目录没有读取 audit.materials 或构造 role-specific material view 的代码。Commander 另有 parent conversation；Worker/Supervisor 主要依赖 assignment、run 和模型生成摘要。

P1-03 · Non-atomic ledger transition

run snapshot、event 和 review 分开 append，崩溃可留下半个状态转换。

recordSanLoopTransition() 先 append snapshot，再 append event；review 又在 transition 前单独 append。rebuild 只选最高 revision，不校验 snapshot/event/review 对应关系。运行探针表明有 1 个 planning run、0 个 event 的 ledger 会被正常接受。

P1-04 · Checks fail open

Check 文件读取失败会被静默忽略，severity 也不参与 host 决策。

readCheckDir() 对目录和单文件错误返回空结果；blocker/error 只渲染成文本。没有“配置了 check 但无法加载时拒绝运行”的语义，也没有把 check ID、执行命令、exit code 和 evidence ref 写入 review。

P1-05 · Release evidence is not reproducible

README 的 5/10、8/10、9/10 结论无法从仓库内证据独立复验。

两份 GSAR run 报告都明确写“证据不完整”，且仅 1 run/mode。报告引用的 /private/tmp/...-evidence 目录当前不存在；仓库没有对应 summary JSON、task outputs 或 ground-truth evaluator 输出。当前 ROI runner 也没有 source commit/dirty provenance，且 summary 引用外部可变 workspace/session 路径，不是自包含 artifact。

P1-06 · Settings and public contract drift

设置表、推荐配置、模式策略和公开文案没有形成同一份可执行合同。

README 宣称 solo 默认；schema 与推荐配置的 defaultMode 是 team。roles.oracle.enabledInModes 和 budget.reserveRatio 无消费者；ledger.enabled=false 只影响主会话 prelude/recovery，不阻止 run ledger 写入；policy 的 maxWorkers/maxRetries 又被全局设置覆盖。

P2 维护性与观测性

P2-01 · Shallow validation and weak report

runtime guard 只校验顶层 shape；报告不汇总实际资源使用。

event type、reviewer、verdict、nested task/assignment/result 并未深校验；错误 entry 可能被当成有效数据。状态报告只输出 budget snapshot 数量，无法看到累计 token/cost/duration/provider requests。failed status 又常搭配 finalVerdict: blocked，增加诊断歧义。

08 · Repair order and release gates

下一步只修 v0.2，不继续扩展新版本

1

冻结产品合同与模式语义

让 solo 真正成为单 agent 单角色路径，或立即撤回该命名和 README 声明。统一 schema、recommended config、CLI/RPC 默认模式和 policy；删除无消费者设置。

2

建立 host-owned Supervisor Gate

pass 必须引用完成 assignment、required check result、确定性 command/test evidence；blocker/error checks 不得只靠 prompt。check 读取或执行失败要 fail closed。

3

兑现权限与硬预算

为 Supervisor 提供真正只读验证工具或隔离工作区；Worker 绑定 assignment path scope。增加 total/input/output token、cost、provider request、wall-time 硬上限，并在每次 role/provider 调用前预留。

4

补 durable transition 与恢复合同

用单一 transition envelope 或可重放 receipt 原子绑定 snapshot/event/review；rebuild 校验 revision 连续性。选择并兑现一种明确语义：真正 resume，或公开定义为 recover-to-blocked。

5

把 ContextPlan 材料投影给角色

按 role/assignment 选择并裁剪稳定 materials，而不是只显示 entry ID；持久化每次 subagent 实际收到的 role packet hash、refs 和 token accounting。

6

重新建立发布证据

GSAR runner 必须保存 source commit/dirty state、配置 hash、workspace diff、session/probe、host-owned check evidence 和 evaluator output。按同一冻结快照跑至少 3 runs/mode，发布均值、方差和失败样本。

Gate A

状态、权限、预算

零证据 pass 被拒绝；solo 角色数符合文案；Supervisor 无写能力；token/cost/time 超限在调用前终止。

Gate B

持久执行与上下文

transition 可 crash-replay；resume 语义明确；角色收到可审计的 ContextPlan material view；重启不产生静默半状态。

Gate C

产品质量与 ROI

false-pass rate 相对 baseline 降低 ≥50%；correction success ≥60%；quality / 1M tokens 不低于 baseline 的 80%；至少 3 轮。

最终决定： Context Steady 可以转入守护模式；v0.2 是下一条唯一主线。保持 san.executionLoop.enabled=false 默认值，回撤“准备对外发布”和已证明质量提升的声明。只有 Gate A–C 全部通过，才能重新标记 v0.2 为 Mature Execution Loop，并继续讨论 v0.3/v0.4 rollout。
