SAN / MODEL ROUTING
诊断 架构 角色 作用域 交互 迁移 实施
治理提案 · 讨论稿 03 · 2026-07-13

先连接服务商，再选择模型；把路由复杂性留在系统内部。

San 底层已经把模型标识为 provider/model，也有 provider 配置、认证存储、模型发现和 provider tab；但产品入口分散在 /setup、/login、/logout、环境变量、models.yml 与 /model。 本方案把普通用户心智模型收口为/connect 管服务商，/model 管当前模型，角色路由和作用域治理只在高级设置出现。

主张：Connect → Model → Work 兼容：保留现有 selector 语法 范围：provider 连接与模型路由体验 不改：认证存储、模型目录与角色运行职责
RECOMMENDATION
两个日常入口，
一次确认切换，
高级能力不挡路。
  1. 01/connect 统一 OAuth、API key、本地服务和自定义 endpoint。
  2. 02/model 只列已连接服务商的模型，Enter 立即切换。
  3. 03没有可用模型时，/model 自动引导到连接流程。
  4. 04角色、fallback、scope 与高级 effort 不进入普通选择主路径。
01 / 现状诊断

底层有 provider，产品层却没有统一的“连接服务商”。

数据模型是清楚的：models.yml 以 provider 为顶层，ModelRegistry 以认证状态筛出 available models，模型主键是 provider/id，当前 picker 也按 provider 建 tab。缺的是一个完整产品流程：添加凭据、验证连接、发现模型、选择当前模型现在由多个命令和配置文件共同承担。

核心结论
普通用户只需要回答两个问题：我连接了谁？我现在用哪个模型？其他问题都不应阻塞开始对话。
ROOT CAUSE 01

连接入口碎片化

/login 只覆盖 OAuth；/setup 又把模型登录和 web search 放在同一个 providers 场景；API key、base URL 和自定义 provider 主要依赖环境变量或手写 models.yml。

ROOT CAUSE 02

模型确认路径过深

现有 TUI picker 选择模型后还要选择十余个 role action，再选择 thinking。日常“换当前模型”与“编辑长期角色路由”被放进同一个菜单，Enter 不是最终确认。

ROOT CAUSE 03

高级配置仍缺治理

角色写入作用域不明确，持久 selector 又会经过 exact、Bedrock profile、retired variant、fuzzy 与 substring 解析。复杂性确实存在，但它应进入高级诊断，而不是进入普通模型切换。

还有一个前置一致性问题。

02 / 目标架构

把连接与目录、路由策略、单次调用拆成三层。

普通 TUI 只直接操作第一层的连接和第三层的当前模型。中间的角色策略仍然存在，但只服务自动路由与高级设置，不进入每次选择的确认链。

PLANE A / CONNECTION + CATALOG

服务商连接与模型目录

回答“连接了谁、有哪些模型、是否可用”。

  • /connect、认证方法与连接状态
  • provider、base URL、模型发现
  • context window、max output
  • text/image、tools、reasoning
  • 凭据留在 AuthStorage，非秘密配置留在 models.yml
→
PLANE B / POLICY

角色路由策略

回答“这个工作角色应该用谁”，是唯一持久模型绑定面。

  • modelRoles 用户 / 项目作用域
  • 角色继承与 ordered fallback
  • 显式 thinking effort
  • 来源、解析与兼容性状态
→
PLANE C / INVOCATION

会话与调用覆盖

回答“这一次是否例外”，不回写长期策略。

  • /switch 当前会话模型
  • session role override
  • CLI / RPC / ACP 显式参数
  • workflow / agent 调用 override
INVARIANT 01日常只有两个入口

/connect 管 provider，/model 管 current model；角色默认继承并自动路由。

INVARIANT 02解析必须可解释

每次解析同时返回 requested、resolved、source、effort、fallback index 和状态。

INVARIANT 03搜索可以模糊，保存必须精确

交互搜索保留 fuzzy；用户确认后只保存 canonical provider/id。

INVARIANT 04覆盖必须自动失效

session/invocation 覆盖不得静默写入用户或项目配置。

WHY 01

requested 与 resolved 分开，才能发现 selector 漂移和 provider 模糊命中。

WHY 02

source 与 shadowed 让 UI 在写入前后都能说明哪一层真正生效。

WHY 03

status 让消费者使用同一套 fail-fast、warn 或 fallback 策略，不再各自猜测。

WHY 04

on-disk 第一阶段继续使用现有字符串与逗号 fallback 语法，先统一行为，不同时做破坏性 schema 重写。

03 / 角色体系

代码当前有 10 个通用角色，但普通用户不需要看到“角色”。

04 / 作用域与优先级

简单切换不问作用域，长期策略只在高级设置里写。

/model 永远只切换当前会话，Enter 不弹出 scope 菜单。用户进入 Models 设置并主动选择“设为默认”时，才询问“当前项目”或“所有项目”；高级路由写入显示最终生效层与被遮蔽层。

NEW API

ModelRoleAssignmentStore 是新增服务，替代 UI 对 Settings.setModelRole() 的直接调用。迁移期后者仅作为 deprecated user-scope wrapper，最终移除，不形成双写路径。

CLEAR

清除某层 assignment 后，UI 立即显示下一层继承值，而不是显示空白。

YAML

用户级和项目级写入使用 comment-preserving YAML document patch、文件锁与原子替换，只修改 modelRoles.<role>。

SESSION

现有 model_change 继续只记录活动模型变化；非活动角色覆盖使用新的 san.model_role_override custom entry。

OVERRIDE

Launch/runtime overrides 保持只读。写 user/project 不再同步修改 #overrides，而是返回“已写入但被遮蔽”；overrideModelRoles() 仅保留给启动参数与测试。

WHY

model_change 会影响活动模型恢复、role cycle 和 cache-reset 解释；用它记录非活动角色写入会混淆现有契约。

RESUME

按当前 branch 从 root 到 leaf 折叠每个 role 的最新 custom entry，天然支持 rewind 与 branch。

COMPAT

旧 session 没有该 entry，等价于没有 session role override；旧版本会忽略 custom entry，因此不需要重写历史 JSONL。

Comment-preserving YAML writer 是 project scope 和自定义 endpoint 上线的硬门禁。

现状使用 YAML.stringify 整文件写回，会丢注释并重排内容。P0/P1 必须先提供基于 YAML Document/CST 的 path patch、文件锁、原子替换和最小 diff 测试；若采用现有 yaml package，应声明为直接依赖，不能依赖传递安装。门禁未通过前，高级路由不得写 .san/config.yml，/connect → Custom endpoint 也不得写用户级 models.yml。API key 永远写 AuthStorage，不写 YAML。仍不新增平行配置源。

05 / 解析与推理强度

搜索允许模糊，持久策略禁止静默模糊。

现有 fuzzy engine 对交互搜索很有价值，不应删除。需要改变的是它在持久配置中的地位：旧值可以兼容解析，但必须带警告；新写入必须 canonical。

1. Exact provider/id包含 variant alias 与 OpenRouter routed/date fallback。
2. Exact bare id出现多个 provider 候选时进入 preference ranking。
3. Bedrock profile解析 Bedrock inference profile model id；当前代码位于 retired variant 之前。
4. Retired variant将已折叠的 effort-tier 旧模型 id 映射到逻辑模型。
5. Provider fuzzy仅在已识别 provider 内 fuzzy match。
6. Substring按 alias 优先、否则最新 dated id 选择。
Candidate ranking歧义候选依次参考 model usage、modelProviderOrder、provider usage 与 catalog order。
Outer grammar:effort、ordered fallback 与 @upstream routing 在匹配引擎外层继续处理。

这是行为修复，不是现状描述。

当前 subagent 执行使用 thinkingLevel ?? resolvedThinkingLevel，frontmatter 可以压过 role selector。调整优先级需要进入 coding-agent changelog，并覆盖普通 subagent、四个 Execution Loop agent、显式/继承/不支持 effort 的回归场景。

保留现有正交能力。

自定义 role key 继续工作；auth 检查和 retry fallback 不并入 role inheritance；模糊候选仍保留 usage 与 modelProviderOrder 偏好。当前 picker 中只有选择 default 会同时切换 live session model，其他角色只更新 settings，这个差异会在新 UI 中显式展示。

增加一条可机器消费的诊断命令。

san models doctor --json 输出每个角色的 requested、resolved、source、capabilities、auth、fallback 与 warning；普通 /model 不读取角色菜单，高级 Models 设置和 /model roles 专家直达才展开完整诊断。

06 / 产品交互

终端交互完全可行，前提是一个页面只做一件事。

借鉴 OpenCode 的清晰边界，但复用 San 已有的 AuthStorage、ModelRegistry 和动态发现能力：/connect 处理 provider，/model 处理 current model。两个页面都支持直接搜索，普通操作最多一次下钻、一次确认。

这是明确接受的 breaking TUI UX。

现状中，TUI /model 是 model → role → thinking 的多层菜单，选择 default 还会持久化全局；/switch 才是 session-only。目标版本把 TUI /model 和 Alt+M 都改为“一次 Enter 切换当前会话模型并关闭”。角色编辑迁到 Models 设置；/model roles 只保留为专家直达命令，不在普通空命令流程里露出。该变化必须写入 Breaking Changes。

空状态直接串起两步，但不合并两个概念。

当没有可用模型时，/model 直接打开 /connect；连接成功并刷新目录后，自动进入只显示该 provider 的模型列表。只有一个模型时预选它，仍由用户按一次 Enter 确认。Esc 可逐层返回，不把 provider 表单和模型列表堆在同一屏。

Custom endpoint 是高级连接方法，不是另一套模型系统。

默认只询问显示名、base URL 和可选 API key，先探测 OpenAI-compatible model list；无法判断协议时才展开 api/discovery 高级字段。非秘密 provider 元数据写用户级 models.yml，key 写 AuthStorage。项目级 endpoint 与手工 model override 继续走高级配置和 YAML writer 门禁。

凭据写入与 custom-provider 校验必须先改合同。

AuthStorage.set() 会替换一个 provider 的全部凭据；/connect 需要新增按类型 upsert/replace API，或在替换前明确确认，绝不能因添加 key 静默删除多个 OAuth 账号。与此同时，validateProviderConfiguration() 当前定义 custom models 时要求内联 apiKey；目标版本必须允许 auth: apiKey 仅声明认证模式，并在运行时通过 AuthStorage 判定 availability，否则“key 不进 YAML”无法成立。

STEP 02选择认证方法

有 OAuth 就优先推荐；否则粘贴 API key。本地服务允许 no-auth。

STEP 03验证并发现

08 / 失败治理

模型路由正确，不代表每轮都值得等 30 秒。

这次体验问题由显式开启的 digest LLM side request 暴露。san.contextSteady.digest.llm.enabled 默认是 false；只有开启后才会发起该请求。角色面板解决“选谁”，还需要统一 side-request 的失败策略，避免认证、余额、禁止访问或持续超时在每轮重复阻塞。

CLOSED

正常

按角色解析并调用，记录 resolved model、耗时和结果。

DEGRADED

退化

首次 transient error 后有限重试；不得在一个 turn 内无限叠加 timeout。

OPEN

熔断

余额不足、401/403、模型不可用立即打开；后续 turn 直接走确定性 fallback。

HALF OPEN

探测

冷却后只允许一次探测；成功关闭，失败继续熔断。

错误类型策略用户可见结果
selector unresolved / incompatible / 无认证请求前 fail fastrole health 显示红色；side role 立即 fallback
余额不足、401、403、明确模型下线不重试，session 级熔断只提示一次具体原因
网络中断、503、短暂 stream close有限重试后熔断显示 degraded，不重复阻塞每轮
timeout角色级 bounded timeout；达到阈值后熔断fallback 继续，保留诊断事件
结构化输出不合法有限重试；随后 deterministic fallback不把功能失败伪装成 Brain MCP 错误
对当前仓库的即时建议。

仅对当前这类已开启 LLM digest 的项目：在统一治理落地前，先将 san.contextSteady.digest.llm.enabled 设为 false，使用 deterministic fallback；或者把 digest 改到一个已验证可用、响应快的模型。未开启 LLM digest 的用户不受该 30 秒路径影响。

10 / 实施顺序

按可验证的契约拆成五个阶段。

不要先重画 selector，再补底层语义。UI 必须建立在来源可追踪、解析可解释、消费者已统一的服务上。

P0 / PREREQUISITES

固定层级与写入安全

先让 project source precedence、凭据边界和 YAML patch 都可预测。

  • 修正 settings provider merge 顺序
  • AuthStorage typed upsert
  • custom auth validation 解耦 inline key
  • config.yml + models.yml writer
  • 冲突与最小 diff 测试
P1 / CONTRACT

统一解析与作用域

建立正式继承表、来源与新写入服务。

  • 现有 10 role graph
  • ResolvedModelRole
  • ModelRoleAssignmentStore
  • session custom entry
P2 / CONSUMERS

收口消费者

功能模块固定消费现有角色。

  • digest → smol
  • execution → slow/task/advisor/plan
  • effort precedence 修复
  • legacy adapter + doctor
P3 / EXPERIENCE

统一 /connect 与 /model

先连接 provider，再用一次 Enter 切换当前模型。

  • built-in OAuth + API key
  • custom endpoint discovery
  • empty-state handoff
  • 80×24 / 40-column probes
  • breaking UX + changelog
P4 / RELIABILITY

运行时治理

阻止 side request 重复卡顿。

  • role health
  • circuit breaker
  • deduped diagnostics
  • deprecated field removal gate

配置契约

  • API key 只写 AuthStorage；日志、状态和 YAML 都不出现明文。
  • 新增 API key 不会静默覆盖同 provider 的 OAuth 或其他账号。
  • 自定义 endpoint 的非秘密元数据写用户 models.yml，并保持注释。
  • 用户、项目、session 三层可分别 assign 和 clear。
  • 每次读取返回 effective source 和 shadowed sources。
  • 新持久 selector 必须 exact 或合法 role alias。

运行契约

  • digest 与 Execution Loop 只经现有 smol/slow/task/advisor/plan 角色解析。
  • selector 显式 effort 能抵达实际请求。
  • unavailable/incompatible 在网络请求前暴露。
  • LLM digest 开启时，非重试错误不会在每个 turn 重复等待 30 秒。

体验契约

  • /connect 同时覆盖 OAuth、API key、keyless 和 custom endpoint。
  • /model 只处理当前模型，Enter 切换并关闭，不弹 role/effort/scope。
  • 单 provider、单 model 在连接后只需一次确认即可开始使用。
  • 无可用模型时自动从 /model 进入 /connect，再返回过滤后的模型列表。
  • 40 列终端仍可完成连接和选择，80×24 不出现横向滚动依赖。
  • TUI、CLI、RPC、ACP 对“持久”和“临时”的定义一致。

冻结决策

D-01

保留现有字符串语法

第一阶段不引入结构化 binding schema，降低迁移面；在运行时解析为强类型对象。

D-02

不新增公开 ModelRole

digest 与 Execution Loop 固定消费现有角色。普通 /model 不展示任何角色；Models 高级设置才展开 lane 和现有 10 个角色。

D-03

新增 session custom entry

保留 model_change 的活动模型语义；非活动角色覆盖写 san.model_role_override，旧 session 无需迁移。

D-04

普通用户冻结为 /connect + /model

/connect 管 model provider；TUI /model 与 Alt+M 都是 session-first 一次确认。/setup providers、/login、/logout 和 /switch 保留兼容转发。

D-05

YAML writer 是硬门禁

继续使用 .san/config.yml 和用户 models.yml；comment-preserving patch 未通过前，不开放 project scope 写入或 custom endpoint 持久化。API key 只进 AuthStorage。

D-06

先兼容，再移除

旧功能 modelRole 有真实持久化用户，必须经过 deprecation 周期；冲突配置不自动迁移。

D-07

连接面只管理 chat model provider

Web search 回到 Settings；STT、TTS、embedding、本地 tiny runtime 等不同协议模型不进入 /connect 或 chat model roles。

D-08

显式 artifact override 保留

workflow 和 agent artifact 仍可固定模型，但必须在审批、日志和诊断中显示。
