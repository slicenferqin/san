结论

核心价值成立：让 ChatGPT 网页版操作真实仓库

用户在 ChatGPT 网页版发出编码任务，ChatGPT 通过自定义 MCP App 连到 Coding Tools MCP，再由它读取仓库、应用补丁和执行测试。模型调用发生在 ChatGPT 产品内；Coding Tools MCP 不需要 OpenAI API key，也不负责模型计费。这正是“复用已有订阅，不再单独搭一套 API Agent”的产品卖点。

但“有 ChatGPT 会员就行”过于宽泛。截至 2026-07-29，OpenAI 官方只向 Business、Enterprise 和 Edu 网页版提供带 write/modify 的 Full MCP beta；Pro 只能连接 read/fetch MCP，官方 Full MCP 清单未包含 Plus。

它也不是 San 自动把任务投递给 ChatGPT 网页版的桥。正确方向是 ChatGPT Web → MCP → 工作区；若要 San 自动调度网页 ChatGPT，还需要独立的编排或浏览器自动化层，本项目没有该能力。

一句话决策

最适合ChatGPT Business / Enterprise / Edu 网页版，把已有订阅模型变成可读、可改、可测试真实仓库的编码 Agent。
有限适合ChatGPT Pro 只能做 read/fetch；也适合其他支持完整 MCP 的订阅型聊天客户端。
不能这样用Plus 直接获得完整写入能力；Agent mode 调用自定义 App；San 无额外组件自动投递任务到 ChatGPT Web。

它是什么：连接“订阅型聊天客户端的模型能力”和“真实代码工作区”的工具执行层。它以 Python 3.11+ 实现，通过 MCP 暴露文件读取与搜索、原子多文件补丁、命令执行、交互进程、Git 查询和运行时信息。

它不是什么：不拥有模型循环、ChatGPT 登录、订阅转 API、计划、记忆、上下文压缩或任务队列。ChatGPT 网页版负责推理与工具编排；本项目只提供工作区能力。上游将其定义为“primitives, not an agent workflow engine”。

“移交任务”的准确含义：你把任务交给 ChatGPT 网页对话，ChatGPT 在同一轮或多轮工具循环中驱动 MCP 完成工作。它复用 ChatGPT 产品内的模型权益，而不是把 ChatGPT 订阅凭据导出给 San 或转换成 OpenAI API。具体模型、调用次数、上下文和限额仍由 ChatGPT 套餐与当前产品策略决定。

连接方式

  • ChatGPT 不能直接连接 localhost 或 stdio MCP；服务必须提供 ChatGPT 可达的远程 HTTPS MCP 端点。
  • 本机或内网服务应使用 OpenAI Secure MCP Tunnel，或项目文档所述的认证 HTTPS tunnel；不要裸露无认证的远程命令执行端点。
  • 需要改代码时使用 full 工具 profile；read-only 只能检查。compat-readonly-all 会把可变更工具伪报成只读，只是客户端兼容逃生口，不是安全边界。
  • ChatGPT 会按 App 权限和动作风险要求确认；MCP 服务端的 safe / trusted / dangerous 策略是另一层独立门禁。

设计上做对的几件事

  • 写入单入口：apply_patch 是唯一直接文件变更工具。多文件操作先解析和准备，基线在提交前再次检查；失败时尝试恢复备份。
  • 结果分层：content 是简洁、可续读的模型文本；structuredContent 是完整机器接口，避免把大 JSON 重复塞进上下文。
  • 长进程显式化：短命令可在单次调用结束；长命令返回 session_id 与可直接执行的 next_action，支持 PTY、stdin、分页输出与终止。
  • 上下文自动注入：初始化时加载根目录 AGENTS.md / CLAUDE.md，嵌套规则只索引路径，不无界注入。
  • 错误契约稳定：工具失败仍返回统一 envelope，包含 code、category、retryable 与 details；协议错误使用标准 JSON-RPC 码。
原子性边界：单文件替换使用同目录临时文件、fsync 与 os.replace；多目录、多文件无法在普通文件系统上形成真正事务。上游明确承认回滚失败会以 PATCH_ROLLBACK_FAILED 暴露，而非静默宣称成功。

安全边界：应用层扎实，不能替代隔离

工作区路径拒绝绝对路径、..、NUL 与 symlink escape；直接文件工具仅接受工作区相对路径。
命令策略safe 默认拦截网络特征、shell 展开、内联脚本和破坏性命令；trusted 放开前三类但保留机密过滤与破坏检查。
运行环境HOME、TMPDIR、cache 位于工作区外的服务端运行时目录；环境变量经过过滤；进程、输出、时限和总字节数有界。
内核约束Linux 可启用 Landlock 文件系统约束；dangerous 会关闭命令门禁与 Landlock。
远程认证HTTP 支持 bearer 或 OAuth 2.1 + PKCE + 动态客户端注册；非 loopback 部署需要认证，除非操作者显式选择 no-auth。

必须理解的三个限制

1. macOS 没有 Landlock。本机当前是 macOS；因此只能依赖路径解析、命令分类与环境过滤。恶意编译器、解释器、依赖脚本或运行中的程序仍可能利用服务进程本身拥有的 OS 权限。上游明确建议对不可信仓库使用外部容器或 VM。
2. “拦截网络特征”不是 egress 防火墙。项目文档明确排除 active network egress firewall，也不是 package-manager policy engine。对不可信代码必须在网络层另行限制出口。
3. safe 模式不能在所有客户端内交互升级。request_permissions 当前不使用 MCP elicitation：除 dangerous 自动授权外，它返回 ELICITATION_UNSUPPORTED。被 safe 策略拦截的合法命令通常需要调整服务配置或重启，而不是在 San 内点一次批准。

遥测与远程面

  • 遥测默认发送每工具成功率、延迟和版本/平台维度；上游承诺不发送路径、参数、命令或文件内容。严格环境应显式设置 CODING_TOOLS_MCP_TELEMETRY=off 或 DO_NOT_TRACK=1。
  • OAuth 注册与授权码是进程内状态；重启后客户端需要重新注册。需要 token 跨隧道变更存活时，应配置稳定 token secret 与公开 URL。
  • --dangerously-fake-readonly-annotations 会向客户端伪报所有工具只读，只允许与 dangerous 模式并用；这是兼容逃生口，不是安全功能。

San 侧的审批细节

粗粒度：当前 San 的 MCPTool 与 DeferredMCPTool 都统一声明 approval = "write"，不依据上游 readOnlyHint 把 read_file 和 exec_command 区分为 read / exec。是否弹窗取决于 San 当前审批模式；服务端自己的 safe/trusted/dangerous 策略仍会执行。接入前必须把这两层当成独立边界，而不是假设 annotation 会自动映射成 San 的能力等级。

San 侧的准确结论

不要为了“复用 ChatGPT 会员”把它装进 San。San 调用这个 MCP 时，执行模型仍是 San 当前配置的模型，并不会消耗或调用 ChatGPT 网页订阅。要利用网页订阅，应从 ChatGPT Web 发起任务；若同时需要 San 自动派单，则必须另建调度层。

采用建议

ChatGPT 网页版主路径

  1. 先确认套餐：完整编码闭环需要 Business、Enterprise 或 Edu 的 Full MCP beta；Pro 只适合只读，不能笼统按“有会员”判断。
  2. 启动远程可达服务：固定 coding-tools-mcp==0.2.2，限定到单个工作区，使用 full profile；可信日常开发从 safe 开始，需要包管理器和 shell 特性时才切 trusted。
  3. 建立安全连接：优先 OpenAI Secure MCP Tunnel；或使用 TLS + OAuth/Bearer 的认证 tunnel。ChatGPT Web 不能直接访问本机 stdio 或 localhost。
  4. 在 ChatGPT 创建 App：由符合权限的管理员/开发者扫描工具、测试、发布；在普通网页对话选择该 App，不使用 Agent mode。
  5. 给出编码约束：采用项目官方 ChatGPT Agent Prompt，要求先检查 server_info，只使用真实 MCP 工作区，编辑后运行验证并检查 Git diff。
  6. 不可信仓库：将服务运行在 Linux 容器或 VM 中，移除宿主秘密并限制网络出口；MCP 的 safe 模式不等于完整沙箱。
  7. 隐私：部署模板显式加入 CODING_TOOLS_MCP_TELEMETRY=off，除非组织接受上游匿名指标。
CODING_TOOLS_MCP_TELEMETRY=off \
CODING_TOOLS_MCP_SERVER_URL=https://mcp.example.com \
uvx coding-tools-mcp==0.2.2 \
  --workspace /absolute/path/to/workspace \
  --host 127.0.0.1 --port 8000 \
  --oauth-mode \
  --tool-profile full \
  --permission-mode safe

# 再通过 Secure MCP Tunnel 或认证 HTTPS tunnel
# 将 https://mcp.example.com/mcp 配置为 ChatGPT 自定义 App

升级验收门槛

  • initialize 协商预期协议版本，serverInfo.version 与固定版本一致。
  • tools/list 工具数量和 annotation 与预期一致，不启用 fake-readonly。
  • 验证 ../、绝对路径与 symlink escape 被拒绝。
  • 对 apply_patch 做 dry-run、基线冲突与多文件失败回滚演练。
  • 验证 safe 模式确实拒绝网络、内联脚本和破坏性命令；容器出口规则独立验证。
  • 在 San 中确认 MCP 工具审批提示与当前 approval mode 符合预期。
