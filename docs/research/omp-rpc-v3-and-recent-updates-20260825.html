OMP RPC v3 与近期更新核查

核查日期：2026-08-25　|　对象：can1357/oh-my-pi 与本地 San RPC v2

结论：社区的 RPC v3 不是已经合入 OMP 的现成版本。主线仍公开为 RPC v1/v2；#8196 和它所依赖/重叠的 #7439 都没有合并，且分支已经严重落后主线。对 San 不应整包移植；应从现有 RPC v2 上选择性吸收“可验证的协议契约”，优先做命令能力清单、跨命令操作生命周期与外部 Host 重连一致性。

1. RPC v3 PR 当前状态

用户记忆中的主 PR 是 #8196 feat(rpc): add v3 session protocol and native UI parity。另有更早、重叠度很高的 #7439 feat(rpc): expose complete headless control surface。

Review 暴露的真实风险

  • 维护者的 P3 review 将其定性为约 50,401 行、215 文件的协议 rollout，并指出它聚合了仍开放的 #7439，建议先拆分/排序。
  • 行级 review 曾指出：空闲时插入 queue item 可能不触发 drain；expectedRevision 没有覆盖所有权威 mutation；provider auth 的 method 参数没有真正选择 OAuth/paste flow；协作快照使用固定 30 秒 deadline，持续进展的快照也可能被误判失败。
  • PR 描述后续声称这些问题已解决，但 PR 仍 open、dirty、长期没有主线同步；因此最多说明作者分支上的实现意图，不能说明上游已经接受。

2. OMP 最近更新

最新稳定发布是 v18.0.4，发布于 2026-08-24。发布后主线又新增 24 commits；因此应区分“稳定版已发布”和“main 正在快速变化”。

v18.0.4 最值得关注

  • omp git：全屏 Git TUI，split/inline/hunk diff、minimap、语法高亮、侧边栏 staging、行级 staging、commit/amend、鼠标和 revision pinning。
  • /extensions Control Center：全屏扩展控制中心、统一 inspector、MCP live connection 管理、鼠标和可展开详情。
  • 流式与启动体验：流式 Markdown 代码块实时高亮；启动期间即可编辑 composer 并保留草稿。
  • 长会话稳定性：批量化 streaming markdown/thinking 更新；优化 edit verification 和 session restore；修复 transcript layout、scrollback、resize、孤儿 tool card、快速 tool completion 等问题。
  • 错误分类：HTTP 413 区分 token context overflow 与 provider byte/media budget，避免错误 compaction，并允许正确的 fallback-chain model switching。

v18.0.0–v18.0.3 的方向

  • 新增 omp render、omp bench、instruction-following benchmark、编辑器 typo/Tab completion/autocorrect，以及更强的 edit payload recovery。
  • 新增 edit auto-repair：AST 破坏后由 smol model 修复并重新 parse，失败则回滚并把差异呈现给用户。
  • 新增 stable/canary update channel；Unexpected Stops 增加 None、Mechanical、Smart 三种策略。
  • 大幅重做 transcript retirement、terminal scrollback、resize replay、启动预加载和 context-file containment dedup；这些比单纯 UI 功能更值得 San 关注。

主线当前的 unreleased 方向继续集中在三件事：把 TUI 大型内容处理移出首帧和主线程、让 transcript 在 streaming/resize/shutdown 下保持可退休且不重放、以及把错误恢复从“字符串判断”升级为结构化分类。

3. 对 San 的可吸收内容

San 当前不是 OMP 旧 RPC 的空白实现。本地 packages/coding-agent/src/modes/rpc-v2 已有：中心化 method registry、capability negotiation、session lease/revision、session sync/recovery、sequence event、run/queue lifecycle、idempotency、approval/interaction、context continuity、subagent、model/provider auth/config、resource/artifact、host tool/URI 和 worktree lifecycle。故正确策略是“契约吸收”，不是“代码移植”。

上游想法San 已有基础建议
命令级能力 manifest
每个 command 暴露 schema、alias、并发类别、confirmation 要求、可用性和 disabled reason。		 San 已有 server.getCapabilities、buildServerCapabilities 和 RPC_V2_METHOD_DEFINITIONS；但能力主要按 capability group 暴露，不等于完整 command manifest。 高价值，优先吸收。从现有 registry/validator 生成，不另建一份手写目录。桌面端可 feature-detect，避免按版本号猜行为。
server-owned operation lifecycle
accepted/started/completed/failed/cancelled、operation snapshot、cancel/reconcile、准确 idle settlement。		 San 已有 RunSnapshot、run lifecycle events、OperationId causation、idempotency、lease 和 sequence；但 method registry 没有独立的 operation list/reconcile/cancel surface。 高价值，增量吸收。先覆盖 bash、auth、compaction、worktree、subagent 等非 run 长操作；重点验证断线重连、重复请求、steer/follow-up 后不被旧的 agent_end 误判 idle。
session/workspace catalog
分页、workspace roots、session info、生命周期投影、resume/fork/delete/rename。		 San 已有 session list/get/create/open/rename/branch/delete 和 recovery snapshot。 中等价值。如果 Desktop 要做 session browser，再补 workspace-root 和 resumable/recoverable/reconnectable 投影；不要重写现有 session manager。
schema-driven settings UI
安全披露 schema、redaction、事务更新、逐字段结果和 revision。		 San 已有 typed settings schema、settings.get/update，以及带 revision/file lock 的 RPC runtime settings store。 值得吸收。先限制在明确标记可读的字段；凭据必须 fail-closed；返回 authoritative post-write snapshot，不泄露“密钥是否存在”。
headless plan/Ask/extension parity
外部 UI 不靠 slash command 模拟 TUI 状态机。		 San 已有 structured approval/interaction、host tool/URI、资源上传和 plan snapshot 类型；完整 plan control 仍不是现有 method registry 的独立表面。 按产品需求吸收。若 San Desktop 要无损复刻 plan review，移植状态机契约；不要先引入完整 rpc-ui 双模式和大型 UI projection。
TS/Python client resilience
raw frame observer、listener isolation、重启状态清理、分页和 lossless transport。		 San 已有 TS/Python client、协议 v2 frame limits、sequence/replay、资源/URI/host-tool frame。 持续吸收。把“坏通知不杀 reader”“终态一定 settle 本地 pending operation”“分页 cursor stale/busy 有 machine-readable code”作为 conformance contract。
collaboration snapshot/guest projection
多人协作、媒体、lossy projection、authority transfer。		 San RPC v2 当前重点是单 Host/session authority；已有 lease/recovery 边界。 暂不吸收。这是独立产品面和高风险传输系统；上游 review 已暴露 snapshot deadline 等边界问题。除非明确要多人协作，否则投入产出比低。

4. 建议的 San 路线

  1. 不引入 RPC v3 大版本。在现有 v2 上做 additive capability；当前协议已经有 lease、revision、sequence、recovery 和结构化错误，贸然换协议会丢掉已有收敛。
  2. 先做 command manifest。让外部 Host 能知道“能不能调用、参数是什么、是否需要确认、是否会并发、当前为什么不可用”。这是 #8196/#7439 最通用且最容易独立验证的部分。
  3. 再补统一 operation reconciliation。沿用 San 已有 Run/Session/Event DTO，避免另造第二套状态机；用断线、重启、重复 idempotency key、stale revision、steer 后 idle 五类场景做 conformance。
  4. 最后才做 settings/plan/catalog UI parity。这些是外部 UI 的产品能力，不是 RPC 核心；按 Desktop 的真实缺口逐项加。
