2.1 当前控制面为什么失效

当前机制源码事实本次盲点
单子 Agent 软预算task/executor.ts：scout/sonic 100、default 200；1.5× 后强制 yield。约束单个 Agent，却不能判断 187 个 Agent 是否在重复同一失败策略；总量上限又可能误杀真实长任务。
并发与墙钟task.maxConcurrency 默认 32，Semaphore 为每个 TaskTool/session 独立；maxRuntimeMs 默认 0。并发是背压，不是收敛；墙钟无法区分长时间有效构建与无意义等待。
San execution looprunner.ts 已有 Commander、Worker、Supervisor、Oracle 和 ledger，但主要服务显式 loop。自由 task/hub 编排未统一进入旁路监督；现有 retry/turn 终止仍可能以次数代替语义判断。
完成证据门applySanLoopReview() 已拒绝无 host receipt 的 Supervisor pass。当前门只要求当前批次任一 host-owned bash exitCode 0；无关命令可能误放行，UI/研究等无 bash 合同又可能被误拒。
错误分类auth_unavailable 同时命中 AuthFailed 和 Transient；retriable() 因 Transient 返回 true。Provider 内部凭证恢复已经失败，AgentSession 仍可做最多 10 次同模型退避。
ToolProgressGuard新 resource 或新 result hash 即 progress；默认豁免 hub/yield。新文件、V2/V3 名称、不同 hub 调用持续把 no-progress 清零；它也无法识别合法长任务心跳。
Context continuityActiveContinuationState 已保护当前 user request 和工具证据。没有 owner、工作族、acceptance gate、策略 revision、Provider 健康与监督决策的跨压缩运行账本。
Todotodo init 直接返回新列表并替换旧状态。物理压缩后模型可无条件重建 Todo，丢失尚未完成的约束和阶段。

2.2 修复后的硬不变量

A-1 事实优先于模型判断

Supervisor 只能引用 ledger 中存在、类型与 scope 匹配且仍新鲜的 evidence；不能凭文字声明 pass、blocked 或 needs_user。

A-2 不确定时必须 abstain

证据冲突、置信不足或仍有合法活动时，默认继续观察或请求 Oracle，不得中断有效工作。

A-3 陈旧决策永不落地

每个决策绑定 basisRevision 和 basisHash；运行态已变化就丢弃并重新评估。

L-1 有效进展可无限续期

默认资源阈值只记录和提醒；只要验收门、任务依赖或可验证产物发生变化，run 就继续。

F-1 故障只封锁故障路径

Auth/stall breaker 跨会话共享；受影响任务 park，其他任务继续，恢复后自动 resume。

C-1 名称不是身份

ProcessHostV3/V4/Final/Repair 若 family/scope/gates/strategy 相同，就是同一工作合同。

P-1 Compaction 无权重置执行态

summary 只描述历史；任务合同、gate、progress revision、breaker 和监督结论来自 append-only ledger。

R-1 可恢复等待不是终态

Provider 或外部资源暂不可用时进入 durable waiting；只有 host evidence 全通过、用户取消或运行时不变量损坏才终结。

3.2 Scope 生命周期

  1. 主 AgentSession.prompt() 持久化新的非 steering 用户 entry 后，创建 scopeId = rootSessionId:logicalTurnId。
  2. 同一 logical turn 的 steer、自动继续、compaction、handoff 保留 scope；新的独立用户 turn 关闭旧 scope，再创建新 scope。
  3. TaskTool 与 hub send/resume 继承 scope 和 assignment/strategy revision；旧 scope 消息不得跨 scope 偷渡执行。
  4. Provider 或外部资源暂不可用时，scope 进入 durable waiting；健康事件触发自动 resume，不依赖用户重新发消息。
  5. 只有全部 host evidence gates 通过、用户显式取消，或 host 运行时不变量损坏时进入终态；迟到结果只追加 evidence，不得逆转已验证的终态。

4. P0 旁路监督与防误判协议

关键不是“再放一个更聪明的模型盯着”，而是把判断权拆开：Host 负责事实、时序和准入；Watchdog 负责确定性模式；Supervisor 只处理剩余语义；Oracle 仅复核高影响且低置信的建议。资源总量不参与默认终止。

准确性边界：不能承诺任意 LLM 在开放世界里“零分类误判”。可工程化保证的是：语义误判不能伪造完成、删除目标、丢失已有工作或直接终止 root run；不确定就 abstain，陈旧就丢弃，高影响结论由 host facts 与 policy 裁决。

4.1 权威模型：谁能决定什么

Host verifier
唯一能把 acceptance gate 设为 pass；验证 evidence 类型、scope、assignment、freshness 和断言结果。
Watchdog
可直接拒绝字节/合同级重复、打开已知 Provider breaker、停止无变化 polling、修复 ledger/Todo 漂移；不能仅凭计数宣布目标失败。
Supervisor
可以诊断假设、提出 replan/reassign/switch/park/needs_user；不能伪造 evidence、删除 gate、直接 spawn 或宣布 completed。
Oracle
提供独立反证；只在证据冲突、低置信或准备进入 needs_user 时按需调用，不以“两个模型投票”代替 host facts。
Scheduler
仅执行通过 CAS 和 policy 校验的动作；动作尽量可逆，保留 mutation 和迟到 evidence。

4.3 停滞只能由多信号确认

单一计数、单次超时、没有 mutation 或长时间运行都不能独立触发纠偏。进入 suspected_stall 至少同时满足：

  1. 目标无变化：观察窗内没有 gate、依赖、有效产物或 blocker revision 的单调变化。
  2. 策略重复：同一 strategy fingerprint、failure signature、Hub cursor 或等价工作合同重复。
  3. 不存在合法等待：没有带 heartbeat 的 build/test/job，没有 Provider retryAt，也没有已登记外部事件订阅。
  4. 没有新权威输入：用户 steer、凭证变化、Provider 健康变化或新 host receipt 都会使旧判断失效。
默认偏置：不确定时宁可继续观察，不打断有效工作。阈值只创建诊断快照和触发审查；不会完成、失败或终止 root run。

4.5 完成证据必须按合同类型验证

现有局限validatePassEvidence() 当前只检查当前 assignment batch 是否存在任一 host-owned bash exitCode 0。这比信任模型文本安全，但仍可能让无关的 bun --version 放行，也会误拒绝纯浏览器、API 或研究任务。

任务类型可接受 evidence明确拒绝
Bug 修复同一 reproduction gate 的修复前 fail + 修复后 pass；receipt 属于当前 contract revision。无关命令成功、旧 retry 的测试、worker 文字声称“已修复”。
永久功能/API覆盖新可观察合同的 host test/check；必要时附实际 smoke。仅编译通过、仅文件发生 mutation、模型自评。
UI浏览器 scenario assertions、页面状态与视觉 evidence refs。强制要求 bash receipt，或只看源码存在组件。
研究/调查结构化 artifact、来源 refs、实验输出与问题覆盖矩阵。因为没有 mutation 就判停滞，或只以文本长度判完成。
外部依赖类型化 permission/auth/resource receipt，且证明无独立 runnable work。模型猜测“可能需要用户”、单次网络错误。

4.6 进展租约与资源策略

租约绑定当前策略，不绑定整个任务时长。有效 gate/evidence/dependency revision 自动续期；重复 activity 只提升监督强度。资源总量默认只做遥测：

信号默认动作是否终止 root run
累计 Token / 请求 / 成本 / 时长记录、趋势告警、TUI/通知；可降并发或提高监督频率。否；只有用户显式配置预算才执行。
并发达到配置值排队和背压。否。
同一策略与错误签名重复冻结该路径，确定性恢复或触发 Supervisor。否；允许实质不同策略。
Provider breaker open受影响 assignment park；切已验证 fallback；single-flight probe。否。
host 运行时不变量损坏保存现场，进入 runtime_fault，防止不可审计执行。是；这是实现故障，不是资源耗尽。

4.7 Supervisor 自身的防活锁

  • 同一 basisRevision + basisHash 只允许一次 Supervisor 调用；没有新 evidence 不重复审查。
  • Supervisor 使用有界结构化诊断包，不读完整 transcript：目标、gate、任务图、最新失败指纹、active heartbeat、Provider 健康和 evidence refs。
  • Supervisor 不持有 task/hub 工具；只能输出 schema 约束的建议，由 host 验证后执行。
  • confidence=low、证据冲突或 action 不满足 policy 时必须 abstain；默认回到观察，不做破坏性动作。
  • needs_user 必须证明具体外部依赖，并确认没有可独立执行的剩余节点；否则只能 park 或 replan。
  • 所有改派、park、取消 duplicate 都保留已有 mutation 和 evidence；新进展到达时可立即撤销干预。

4.8 验收门本身也必须防误解

  • 真实 user entry 是目标权威；Commander 生成的 gate 必须携带 objectiveClauseRefs 和不可变 contractHash，不能只保存改写后的摘要。
  • Supervisor 可以补充更严格的检查，但不能删除、放宽或把未完成 gate 改成 out-of-scope；只有新的权威用户输入才能改变目标语义。
  • 存在歧义时优先执行可逆、对各解释都有效的工作；互斥且不可逆的选择才进入 needs_user，并明确列出冲突解释。
  • Gate revision 必须说明由哪条用户输入或哪项 host evidence 触发；compaction summary、worker summary 和 Supervisor rationale 都不是 revision authority。

5. P0 错误语义与 Provider 级熔断

5.1 先修正错误优先级

已确认packages/ai/src/error/flags.ts 中 auth_unavailable 同时命中 AUTH_FAILURE_PATTERN 与含 “unavailable” 的 transient pattern；retriable() 因 Transient 返回 true。Provider 内部凭证轮换最终失败后，AgentSession 因此仍可能重复同模型请求。

拟议将 AuthFailed/OAuthExpiry 设为 ordinary retry veto，但保留一次能够证明发生真实切换的 route/model fallback：

export function retriable(id: number | undefined, opts?: { replayUnsafe?: boolean }): boolean {
  if (is(id, Flag.AuthFailed) || is(id, Flag.OAuthExpiry)) return false;
  if (is(id, Flag.ContentBlocked)) return false;
  if (is(id, Flag.MalformedFunctionCall)) return true;
  if (opts?.replayUnsafe) return false;
  return ((id ?? 0) & RETRIABLE_KINDS) !== 0;
}
  • Provider driver/api-key resolver 先完成自身 401 refresh/sibling rotation；只有其最终失败事件才进入 shared breaker。
  • #isHardErrorModelRouteFallbackEligible() / #isHardErrorFallbackEligible() 仍可尝试一次真实 route/model switch；没有 switchedRoute/switchedModel 就不能退回同模型 backoff。
  • 纯 503、network error、规范化 stream stall 仍可短暂恢复；用户主动 abort、client backpressure 或仍有活跃字节流不计为 stall。

5.3 阈值只控制故障路径

故障确认条件局部动作自动恢复
auth_unavailableProvider 内部凭证轮换已耗尽，且本次没有真实 route/model switch。按 endpoint 立即 open；相关 assignment 转 waiting_for_provider，不结束 root run。凭证变更事件立即 probe；否则按退避 single-flight half-open。
stream_stalled无 terminal、无有效 heartbeat、非用户 abort；同 key 在时间窗内多次出现，最好跨 session 交叉确认。按 model/endpoint open；冻结相同 retry path，保留本地 edit/test。首次短退避，复开逐级延长；只放行一个 probe，成功才 closed。
成功响应收到有效 assistant terminal message，而非仅建立 HTTP 连接。清零连续失败并发布 provider health revision。唤醒依赖该 key 的 parked assignments。
429 / usage limit使用 Provider retry-after 和现有 credential block receipt。park 到明确 retryAt；继续运行不依赖该 Provider 的任务。retryAt 到期后 single-flight probe。

5.4 四个入口必须共享同一状态

  1. SDK Provider dispatch：最终防线；open 时返回 typed ProviderCircuitOpenError 和 retryAt，不进入普通 retry。
  2. Task spawn：目标 route open 时不创建会立即请求同一 Provider 的 child；assignment 进入 waiting 队列，有已验证 fallback 则改派。
  3. Hub revive/send：消息若会触发 open route 的新 turn，则持久化为待投递，不反复唤醒；只读 roster/list 不阻塞。
  4. San loop worker dispatch：Commander/Scheduler 跳过 open route，继续无依赖节点；不能把整个 run 转成终态 blocked。

6. P0 编排语义收敛守卫

保留 per-session ToolProgressGuard 作为局部信号，但 root-scope OrchestrationGuard 才负责团队级判断。它必须同时避免两类错误：把同一失败策略当新工作，以及把真正独立的并行方案误判为重复。

6.1 工作合同与策略身份分离

export interface TaskStrategy {
  strategyId: string;
  hypothesis: string;
  expectedEvidenceKinds: string[];
  independenceKey?: string;
}

export interface TaskContract {
  family: string;
  scope: string[];
  acceptanceGateIds: string[];
  strategy: TaskStrategy;
  retryOf?: string;
  changeReason?: string;
}
  • Work key = family + normalized scope + acceptance gate revision，表示“要完成什么”。V2/V3/Final 名称不参与。
  • Strategy key = work key + hypothesis + expected evidence，表示“准备怎么证明”。同一 active strategy 直接复用现有 Agent，不重复 spawn。
  • 不同 hypothesis 或不同独立 scope 的策略可以并行；共享写作用域时仍由 concurrency/exclusive lock 串行化，不能因 family 相同一刀切。
  • 同一策略失败后不能靠改措辞重启；必须由 Supervisor 给出被推翻的假设和新的 expected evidence。
  • 不设置“全 run 最多几个策略”的默认硬上限；重复策略被永久去重，实质不同且仍有验收价值的策略可继续。

7. P1 压缩边界外的结构化执行账本

旁路监督若依赖当前上下文，就会在 compaction 后失忆。采用 append-only custom entry 保存事实、策略和监督过程；LLM summary 仍然只是非权威历史。

7.1 Journal 协议

customType: "san.execution_scope"

type ExecutionScopeJournalRecord =
  | { schemaVersion: 1; type: "scope_started"; snapshot: ExecutionScopeSnapshot }
  | { schemaVersion: 1; type: "request_started"; request: ProviderRequestSnapshot }
  | { schemaVersion: 1; type: "request_finished"; requestId: string; usage: UsageDelta; outcome: string }
  | { schemaVersion: 1; type: "assignment_transition"; assignment: AssignmentSnapshot }
  | { schemaVersion: 1; type: "gate_transition"; gate: GateSnapshot }
  | { schemaVersion: 1; type: "progress_observed"; observation: ProgressObservation }
  | { schemaVersion: 1; type: "supervisor_decision"; decision: SupervisorDecision }
  | { schemaVersion: 1; type: "provider_circuit"; circuit: ProviderCircuitSnapshot }
  | { schemaVersion: 1; type: "scheduler_transition"; transition: SchedulerTransition }
  | { schemaVersion: 1; type: "scope_snapshot"; snapshot: ExecutionScopeSnapshot };
  • request_started 在网络 dispatch 前 append，request_finished 记录真实 usage 与 outcome；用于审计和错误指纹，不作为默认余额。
  • 每个 gate、assignment、strategy、breaker、progress class、Supervisor decision 和 waiting/resume 迁移都增加单调 execution revision。
  • 每次 compaction/handoff、监督干预、Provider 状态变化以及固定事件间隔写 snapshot；记录 refs/hash，不复制完整 prompt、tool output 或凭证。
  • 崩溃恢复时未完成 request 标记 interrupted；按 replay safety 与 breaker policy 决定恢复，不因“账没结完”重置整个执行态。
  • Legacy active turn 无完整 ledger 时以低置信 observe 模式重建已存在的任务/evidence；在获得足够新事件前不得取消工作或判 needs_user。

7.3 与现有模块的关系

  • ActiveContinuationState.executionEvidence 继续证明 mutation/verification；ledger 保存 owner、family、strategy、gate、progress、Provider health 和 usage telemetry，二者引用同一 tool result id。
  • AgentRegistry 只保存 executionScopeId、assignmentId 和 strategyId；park/revive 时恢复引用，不复制 ledger。
  • ContextProbe 从 schema v3 升 v4，增加 scope、strategy、gate、watchdog、supervisor、breaker 与 usage counters；reader 兼容 v3。
  • SanLoopRunSnapshot 继续保存领域计划；既有显式用户预算保持可选，但默认监督不以 usage 终止。

8. P1 Todo 未完成时禁止无条件替换

已确认todo.ts 的 applyEntry("init") 当前直接返回 initPhases()；只验证新列表内部重复，不检查旧列表是否仍有 pending/in_progress。

8.1 新操作合同

  • init 仅在当前列表为空，或所有现存任务均为 completed/abandoned 时允许。
  • 若存在 pending/in_progress，init 返回 error，携带现有 phases；不得修改 session state。
  • 新增 reconcile：同内容任务保留原状态，新任务追加为 pending；未出现在新列表中的 unfinished 任务仍保留。
  • 要删除 unfinished 任务，必须先显式 drop 或 rm；然后才能 init/reconcile。不能用一个 replace=true 参数绕过审计。
  • 完成任务也保留在 reconcile 结果中，直到显式 rm；避免压缩后模型把已完成阶段重新变成 pending。
case "init":
  if (hasUnfinished(phases)) {
    errors.push("Todo list has unfinished tasks; use reconcile, or explicitly drop/rm them before init");
    return phases;
  }
  return initPhases(entry, errors);

case "reconcile":
  return reconcilePhases(phases, entry, errors);

8.2 与执行账本联动

  • Todo completion 只能更新展示计划；Acceptance gate 的 pass/fail 仍由 verification evidence 决定。
  • 每次 init/reconcile/drop/rm 记录 todo revision 到 execution ledger；重复 init 失败不增加 progress revision。
  • compaction 后恢复时，最新 Todo snapshot 与 execution scope 的 assignment/gate 做一致性校验；有冲突时以 journal 工具结果和 execution ledger 为准，并向 main 注入 reconcile 提示。

9. P1 Context Steady 的处理：先隔离状态，再做 A/B

不直接永久关闭。本事故 84 次物理压缩全部由 steady target 触发，说明它是放大器；但压缩请求只占总 Prompt 的 1.54%，关闭后自由编排和 Provider 重试仍可能活锁。先让 ledger/watchdog 跨压缩稳定，再比较。

9.1 A/B 设计

变量A · NativeB · Steady
代码、任务、Provider同 commit、固定任务集、同模型/故障注入、同 Watchdog/Supervisor policy、同最大并发；均不设默认累计资源硬上限。
上下文策略san.contextSteady.enabled=false保持当前 steady 配置；记录每次 physical compaction。
样本至少 20 组配对运行；随机先后顺序；Provider 故障和长任务 heartbeat 使用可重复 fixture。
主要指标acceptance pass、误报/漏报、stale decision discard、charged tokens、Provider requests、assignment/revival、Todo reconcile、plan rebuild、wall time。
发布门槛0 次 false completion；0 次合法长任务被中断；0 次目标/账本漂移；0 次 compaction 后重复派已完成策略。

9.2 决策规则

  • Steady 只有在 acceptance pass rate 不劣于 Native 超过 5 个百分点，且监督误报率不增加时，才可保留为多 Agent 默认。
  • 若 charged tokens、assignment/revival 或 Supervisor 调用显著增长，先调整 compaction hysteresis 和诊断包，而不是增加终止预算。
  • 重点分析 physical compaction 后短时间内的 Todo reconcile、strategy 重派和 stale supervisor decision。
  • 所有 A/B 均保持 Provider breaker、typed evidence gate、Watchdog 与 durable recovery 开启；不得用资源硬停掩盖活锁。

13.3 提醒与异常信号

  • 累计 Token/请求/成本/时长按绝对值和增长率发 warning/notification；默认不改变 run 状态。
  • 同 strategy/failure signature 重复、assignment churn 或 Supervisor 调用频率异常时，提高诊断强度并降低并发，不结束 root run。
  • 任一 Provider key 出现最终 auth_unavailable 或确认 stall 时发送 breaker alert，并展示自动 probe/recovery 状态。
  • physical compaction 后 Todo reconcile、已完成策略重派或 gate 回退，记录为高优先级一致性事件。
  • 线上持续统计“suspect 后在无干预情况下迅速出现合法 progress”的 shadow 误报代理指标，用于收紧/放宽多信号 policy。

14. 迁移、准确性灰度与回滚

14.1 灰度顺序

  1. 先发 Auth precedence。独立正确性修复；保持 Provider 内 401 rotation 和真实 route/model fallback。
  2. 上线 typed evidence gate。先把 false completion 风险封住，并为 UI/研究/API 补齐非 bash verifier。
  3. ExecutionLedger 只写事实。影子记录 request、usage、progress、strategy、heartbeat、breaker 和 revision，不改变调度。
  4. Watchdog shadow。在事故回放与健康长会话语料上输出 would-suspect/would-act；suspect 后很快出现合法 progress 记为误报代理。
  5. 只 enforce 确定性动作。先启用 exact duplicate、stale Hub poll、最终 Auth breaker、revision CAS；这些不依赖模型判断。
  6. Supervisor advisory。记录建议、abstain、Oracle 分歧和后续真实结果；不自动改派。
  7. 启用可逆语义动作。只开放 replan/reassign/park/switch；completed、needs_user、唯一 worker cancel 继续由高影响 host policy 控制。
  8. 启用 durable recovery。验证进程/compaction/Provider 恢复后自动 resume，再开展 Native/Steady A/B。

14.2 兼容策略

  • 新 san.execution_scope 为未知 custom entry；旧二进制忽略，不重写旧 JSONL。
  • 旧 Task contract 缺失 strategy 时生成 low-confidence compatibility key；在证据不足前 observe，不自动取消。
  • 旧 San loop bash receipt 继续可作为 command gate evidence，但必须绑定具体 check；不再接受任意成功命令。
  • 旧 Todo tool result 继续可读；新 init guard 只影响新调用。
  • ContextProbe v4 writer 配套 v3/v4 reader；legacy active turn 以 observe 模式重建，不能从零猜 gate。
  • 已有用户显式 maxTokens/maxCost/maxDurationMs/maxProviderRequests 继续生效；默认值为 disabled，不再由产品强加。

14.4 主要风险与控制

误判合法长任务heartbeat/active process 是合法等待；单信号不干预；不确定时 abstain。
无意义 mutation 伪装进展mutation 默认只算 activity；关联当前 gate/evidence/dependency 才算 progress。
Supervisor 幻觉结构化 refs 必须在 ledger 存在；模型不能改变 gate；host verifier 裁决。
并发导致陈旧建议basis revision/hash CAS；期间任一新 progress 使建议失效。
模型共识仍然错误Oracle 只提供反证，不投票；事实与类型化 verifier 始终高于模型多数。
Provider 永久不恢复durable waiting 不烧模型请求；明确需登录时按 host receipt 进入 needs_user 并保留可恢复队列。
恢复后重复执行副作用request/tool replay safety、assignment revision 和幂等 receipt；不可安全重放时等待人工，而非猜测。

14.5 准确性晋级门槛

  • 标签来源：用事故回放、健康长任务、研究/UI/API、Provider 恢复、并发迟到 evidence 构成固定语料；ground truth 来自 host receipts 与人工确认的目标合同，不能让 Supervisor 自己给自己打分。
  • 确定性 enforce：语料中高影响误报必须为 0，所有预期 exact duplicate、stale poll、terminal Auth 和 revision race 必须命中；任一反例即阻断晋级。
  • 语义 advisory：必须先收集“建议后真实发生的 progress / regression / blocker”结果；无法归因的样本计入 abstain，不得从分母删除来美化 precision。
  • 可逆动作：只在无 artifact/evidence 丢失、stale action 应用数为 0、fixture 自动恢复率为 100% 时开启；线上出现一次不可恢复误干预立即回 advisory。
  • 高影响结论：completed 永远不授予语义 Supervisor；needs_user 永远不靠模型置信度单独晋级，因此不依赖一个虚假的“模型准确率阈值”。

15. 明确不采用的方案

默认累计资源硬上限

会把仍在产生真实进展的长任务人为截断；资源默认只做遥测，用户显式配置除外。

只向主 Agent 发软提醒

主 Agent 可能忽略、压缩后遗忘，或自身就是活锁源；旁路 Watchdog 必须有局部控制权。

常驻第二个 LLM 监工

监督者也会循环和消耗；确定性规则常驻，LLM 只在语义疑难时按 revision 调用一次。

Supervisor/Oracle 多数投票

模型共识不是事实；完成、外部阻塞和高影响动作必须由 host evidence policy 决定。

只降低 retry 或 concurrency

只能减速局部爆炸，不能识别跨 187 个 session 的同一语义策略。

任务名正则去掉 V2/V3

名称可任意改写；必须区分稳定 work key、strategy hypothesis 和 independence key。

“新文件 = 新进展”

新资源和 mutation 默认只是 activity；必须关联 gate/evidence/dependency 才续期。

让 compaction summary 保存监督态

LLM 输出不是数据库；合同、revision、gate、breaker 和决策必须来自 append-only ledger。

16. Definition of Done

  • 默认累计 Token、请求、成本、时长与 assignment 数不终止 productive root run；用户显式预算仍可选。
  • 主、子、嵌套、revived Agent 共享 root execution scope；compaction/handoff/restart 后 revision、gate、strategy 和 waiting 状态不回退。
  • Supervisor 无法凭文本、无关命令、陈旧 receipt 或不存在的 evidence 把 gate 设为 pass。
  • command/browser/API/artifact/review/external gate 均有 host verifier；当前 bash-only evidence 门完成迁移。
  • 单信号、合法 heartbeat、研究 artifact、不同 hypothesis 不会被误判为语义活锁。
  • 相同 strategy、失败 signature、无变化 Hub poll 和 V2/V3 改名无法绕过去重与诊断。
  • Supervisor 决策绑定 basis revision/hash；期间出现任何新进展时旧决策必然丢弃。
  • needs_user 只有在 external receipt 存在、无 runnable 节点且高影响 policy 通过时成立。
  • Auth/stall breaker 跨 session 生效；只 park 故障路径，half-open single-flight，健康后无人 steer 自动 resume。
  • Provider 故障等待期间不重复消耗 LLM 请求；独立任务继续运行。
  • Todo 有 unfinished 时 init 原子拒绝；reconcile 保留状态，Supervisor 不能静默删除目标。
  • 事故回放在无用户输入下经历故障、compaction、恢复并最终通过所有 gate；合法长任务未被取消。
  • Watchdog shadow、语义 advisory、可逆 enforce 三阶段均达到第 12/14 节门禁后才能默认开启。
  • 20 组 Native/Steady 配对 A/B 后再决定多 Agent 默认上下文策略；两组都不以资源硬停掩盖活锁。
  • 实现、focused tests、真实 smoke 与 bun check 通过后，更新 packages/ai 和 packages/coding-agent Unreleased Changelog。
