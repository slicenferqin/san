一、可以确认的外部机制

  1. 跨窗口笔记，不反复压成唯一总摘要。OpenAI 发布页明确写的是 In Codex，并称其为实验功能：笔记跨窗口保存，避免反复压成一个摘要。[1]
  2. 笔记漏记，不代表原文不可找。官方明确说明，之前窗口的消息与工具输出仍可搜索，包括未写入笔记的需求和测试结果。[1]
  3. 窗口切换前给保存笔记留空间。Codex 主分支 schema 包含 reminder_threshold_tokens、auto_compact_fallback_buffer_tokens、窗口 rollover 前采样的 auto_compact_fallback_prompt，以及 use_history_notes_extension。这是可核验的配置设计，不是已复现的完整运行流程。[2]
  4. 当前窗口与独立保留状态分开。Codex 的 ContextManager 同时持有模型历史 items 和独立的 retained_context，并分别记录历史重写版本与用户输入修订。用户消息保留受开关控制；不能把这部分代码直接等同于 notes 搜索实现。[3]

边界：官方发布页描述的是 Astra 与 Codex 的组合能力，不是调用 Astra API 就自带笔记数据库。本次没有核验到 notes 扩展的完整检索、排序和笔记编辑算法，也没有进行 Codex 实机长任务对跑；因此下面是 San 的设计建议，不是照搬一份已知的 Codex 实现。旧 core/src/config/types.rs 地址本次返回 404，配置结论以成功读取的官方 schema 为准。

二、San 已有的基础，不应重复建设

当前机制已核验事实真正需要补的部分
原始记录与请求视图materializeContextPlanMessages 生成投影视图，替换旧工具输出、卸载旧图像的路径不改 journal。[C1]不是重新建设历史保存层，而是让已有历史更容易定位与读取。
已知摘要引用展开context_expand 参数只有 ref；expandDigestSpan 默认 30,000 字符，超长截头留尾。[C2]未知引用搜索、按命中消息读取、分页与续读。内部 helper 可增大上限，不等于工具端已有分页。
会话历史入口history:// 可读取存活、停放及磁盘上的 agent transcript，但渲染为简洁转录；成功工具结果通常仅显示状态与行数。[C3]简洁转录不能直接当完整工具输出的搜索语料。需要回到源条目，而不是只搜索展示文本。
已有搜索与 recallHistoryStorage 的 FTS5 索引列是用户 prompt；稳态 recall 以当前请求和近期 digest 生成查询，再调用已配置的 memory backend。[C4]两者都不能据此宣称已经覆盖所有旧窗口的原始消息与工具输出。复用接口和 SQLite 使用模式，不混淆输入历史与原始会话索引。
结构化摘要TurnDigest 已有 factsLearned/openQuestions/risks/nextSteps、文件与工具引用；不应再提“从零增加风险与下一步”。[C5]缺的是跨回合、按问题修订的工作笔记生命周期，以及方法失败原因与适用条件的稳定表示。
检查点ContextCheckpoint 合并有条数上限的 intents、decisions、files、risks、nextSteps；预算不足继续裁剪。其摘要没有逐项承接所有 factsLearned/openQuestions，但保留源引用。[C6]引用可回查不等于每个事实都被当前摘要保留。应按需取回，不无限扩张 checkpoint。
输入控制与缓存稳定预算计算已有 steady/control/burst；planner 已有相关性筛选、受保护条目和目标锚；stable projection 将变化的 recall 与稳定前缀分离。[C1][C7]把新的检索结果纳入现有预算与失效规则，不再叠加一个独立的输入控制器。
中途维护与任务来源mid-turn 路径已先保存消息，区分 checkpoint-only 与物理压缩；排队中的用户输入优先。手动压缩路径从 journal 构造 continuation 状态并约束摘要。[C8]新增笔记可接到既有边界；不另建切窗循环，不让笔记覆盖真实用户任务或自行证明工作完成。

源码默认值：稳态总开关 false、激活阈值 240K；LLM digest、recall、stable projection、旧工具输出/图像 offload 均默认 false。功能存在与默认生效是两回事。本次没有读取或修改个人配置。[C9]

三、建议按这个顺序吸收

本节所有方案与收益判断均为 [INFERENCE / 建议]，尚未实现或测得效果。

P0：先打通“搜索原文 → 定位命中 → 精确读取”

用户可感知的结果：即使只问“上次这个修法为什么失败”，不知道 digest ID，且摘要没记原因，也能找回当时的工具输出。

  • 语料来自当前会话分支的源消息与工具结果，而不只来自摘要、Mnemopi 等长期记忆或 history:// 的展示文本。原始 journal 仍是唯一来源；索引是可重建的派生数据，按新增条目更新，不每轮全量扫描。
  • 优先使用明确路径、符号、错误码、工具名与关键词定位；复用现有 SQLite 模式。自然语言改述、中文和代码标识符需要单独验证召回效果，不能把“有 FTS”称为“已经实现语义检索”。混合检索或 reranker 留到失败样本证明需要时。
  • 搜索先返回短命中片段和稳定的源定位信息；读取再按消息/区间有界展开，提供续读位置。复用、扩展现有读取与 context_expand 能力，避免同时建设互不兼容的读取接口。
  • 读取目标不再必须是一个完整 digest span；结果明确是否截断。源图像、附件、溢出输出保留可解析的原始引用，不声称文本展开能逐字节恢复多模态输入。
  • 默认只查当前允许访问的分支；跨会话、子 agent 历史沿用已有可见性与授权边界。源记录删除或过期时明确不可用，不用相似摘要冒充原文。

首个验收：原文里有、摘要里没有、模型不知道 ref 的失败原因，能定位到正确源结果并读到完整原因；超过 30K 的区间首部也能取回，不需要无上限增加返回量。

P1：把工作记忆升级成“按问题维护的增量笔记”

不是再写一份总总结。在现有 journal/custom entry 与工作记忆投影上增加可修订、可失效的笔记表示；复用 TurnDigest 提供的事实与引用。回合摘要继续承担时间线，不强迫它同时承担全部当前状态。

笔记保留什么避免什么失真
方法、运行条件、观测到的结果及源引用只记“试过了”，却忘记为何失败；把失败永久归因于方法本身，忽略代码或环境已经变化。
假设与未解决问题把猜测写成已验证事实；下一轮重新发明同一个假设。
有来源的决策、当前阻塞点和下一项验证只记宏观计划，恢复后无法接着做具体工作。
适用的源版本/条件、替代或失效关系代码已更新，旧测试成功或旧失败结论仍被当作当前状态。
  • 按问题/对象更新增量；旧记录保留，当前视图取有效版本。不每轮重写所有笔记，不把整本笔记灌回上下文。
  • 文件读写、工具成功/失败来自实际执行记录；模型可以整理原因和假设，但不能仅凭笔记文字把测试改成“通过”。
  • 用户请求、约束来源继续走既有目标锚与 continuation 机制。历史用户消息可用于理解未撤销约束，但检索到的旧任务或生成笔记不得自动替代当前请求。
  • 会话笔记不默认写入全局长期记忆；需要长期保存的内容继续走既有候选记忆流程，避免临时假设污染后续项目。

首个验收：连续多个窗口之后，仍能区分“这个方法在旧条件下失败”“现在改了条件，需要重新验证”“这个原因只是猜测”；不是仅检查笔记文件还在。

P1：切换前保存必要增量，而不是临界时被迫补写

吸收 Codex schema 的“提前提醒 + 给记录笔记留空间”，但挂在 San 已有 checkpoint/physical maintenance 边界上：

  • 重要试验结论形成时就能保存小增量；接近实际切换边界、仍有未保存的工作状态时，再做一次有界补写。不要每个工具调用都额外调用摘要模型。
  • 先保证源消息持久化，再关联笔记与来源；读取/查询索引可恢复构建，不能反过来成为继续工作的前提。
  • 笔记补写失败时保留源记录、引用和既有确定性恢复状态，不能凭空生成成功结论，也不能进入反复补写—压缩循环。正在排队的真实用户补充继续优先。
  • 现有 digest 输入在 18,000 字符处截尾；其结构化字段会与 fallback 合并，但不保证长工具轮次尾部的全部语义都被摘要模型读到。补写应选“本次新增且尚未记录”的结果与未闭合问题，而不是单纯扩大截断常量。[C10]

首个验收：窗口切换后接着完成下一项具体动作；不会重试已经证伪的方法，不把未完成工作改写成已完成，记录失败也不让任务停在维护环节。

P2：让找回的内容真正进入合适的工作集

  • 先接入模型按需搜索；再针对“引用缺失、恢复后具体信息不足、用户提及旧结果”等可观察场景，复用现有 recall 入口做有限的自动查找。不要新建每轮必跑的 LLM 检索规划器。
  • 稳定层放当前任务来源与必要工作状态，临时层放当前命中的少量原文；沿用 stable projection 的分层，避免一次检索把整个稳定前缀改写。
  • 检索文本计入 system/tools/messages 的总输入限制；去重并依据源版本失效。与当前动作无关的历史保留在存储层，不因曾命中过就一直占用上下文。
  • 先保留已有目标值；通过效果和成本对比决定是否调整窗口。百万模型窗口不是扩大日常工作集的充分理由。

首个验收：相同模型与任务下，重复失败和遗忘约束减少；任务完成率不下降，总成本、延迟和输入峰值可接受。没有测量前，不声称“更少 token 必然更聪明”。

四、保持一条链路，不增加第二套系统

真实用户请求与未撤销约束 ──→ 现有目标锚 / continuation
                                  ↓
源消息、工具结果 ──→ 既有 journal ──→ 搜索定位 ──→ 分页读原文
                          ↓                       ↓
                 增量工作笔记 / digest       少量临时命中
                          └─────────┬─────────────┘
                                    ↓
                      现有 ContextPlan + 输入预算
                                    ↓
                              当前模型请求

[INFERENCE]第一批只做“搜索 + 精确读取”闭环；第二批做有来源的增量笔记及切换前保存；第三批按实际失败样本加入自动召回与默认启用策略。每批都需要独立证明用户受益，而不是先把所有开关打开。

不建议照搬：关闭所有 compaction、无限注入笔记、让模型自由决定物理窗口切换、另建一个全局记忆库、只换 Astra 模型 ID、把原生 WebSocket steering 或模型内部循环混入这一改造。它们不是当前最明确缺口的解决方案。

最终产品应默认可用、无需用户理解摘要 ID 或手工管理笔记。上线前的实验开关留给开发验证；机制细节留在日志或 san stats，不增加主界面的记录面板。

五、本次实际运行的验证

直接调用仓库现有 expandDigestSpan 与 resolveContextPlanBudget；使用内存里的构造历史，没有调用真实模型、没有修改 journal 或运行时、没有新增测试文件。

场景观测结果能证明什么
摘要刻意不记录失败原因，已知 ref，三条源消息digestContainsMarker=false；recovered=true；messageCount=3；truncated=false；原输入未变。已知引用能取回摘要没有记录的源细节，不必重做这一基础。
相同失败原因在前，后接约 40K 字符输出源记录仍有原因；默认展开 recovered=false、truncated=true；结果 30,067 字符，含截断提示。helper 显式设 60,000 上限后 recovered=true；原输入未变。默认读取窗口会遗漏首部细节；不是数据被删除。应做定位与分页，而非只把上限调大。
1,050,000 模型窗口；源码默认稳态预算；system/tools 估算 10,000steadyTarget=240000；controlMax=260000；burstCeiling=320000；messageBudget=250000；模式 steady。San 已有独立于模型最大容量的全输入控制策略，不必推倒重建。

不能据此声称：新搜索/笔记已经实现、模型会主动正确查找、长期任务成功率已经提升，或 San 的效果优于 Codex。这里验证的是现有函数行为与具体边界。

六、未来实现的验收，不只量 token

以下是建议的对比评估，本次未执行。同一模型、同一任务集合、相同初始仓库与工具条件，对比当前稳态、加入搜索/读取、再加入增量笔记三组；模型执行重复采样，不能从单次结果下质量结论。

行为场景判定标准
旧测试原因不在任何摘要中找到正确原始结果；返回可解析源定位；无需重新执行当时已完成的探索。
大区间首部、中文改述、相近错误码正确命中并可续读；不能用相似但不相关结果充数，查不到明确表示未知。
连续多窗口、多次失败方案保留方法、条件、失败原因；条件未变时不重复无效尝试，条件已变时允许有理由地重试。
任务补充、取消、切换分支新要求生效；未撤销约束保持；被取消的旧任务不复活；其他分支内容不自动混入。
代码改动、旧测试通过记录、笔记注入旧结果不证明新代码已通过；历史内容中的指令不变成当前指令；无源成功声明不能升级任务状态。
恢复、补写失败、索引缺失源记录仍可读；可恢复定位；继续执行状态真实，不进入维护循环。

指标：任务成功率、约束违反次数、无意义重复尝试、旧原文检索召回率/定位正确率、分页完整性、全部模型调用的总 token/成本、P95 输入与端到端延迟、缓存命中与切换次数。确定性场景要求来源和状态转换正确；模型效果是否达到默认启用标准，依据对照结果决定，不预写一个未经测量的提升百分比。
