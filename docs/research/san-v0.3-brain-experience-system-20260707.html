San v0.3 · Top-level Design · 2026-07-07

San Brain / Experience System：让经历改变下一次行动

这不是一份 memory feature 需求，也不是先拆 issue 的工程计划。它先回答顶层问题：San 的“脑子”应该如何从经历中形成稳定判断、工作习惯、技能、风险姿态和协作方式。

实施合同

工程实现以 san-v0.3-p0-design-freeze-20260710.html 为规范性合同。 本文继续定义产品目标和脑模型；命名、scope identity、状态权威、投影、撤销、Prompt authority 与阶段顺序由 P0 Design Freeze 冻结。

一句话结论

San v0.3 的主题不是“记得更多”，而是“经历会改变行为”。 一个成熟 agent 的脑子不应该只是检索过去文本，而应该能把过去的成功、失败、纠偏、偏好和项目约定，转化为下一次更正确的默认状态。
Memory 是材料 记忆保存事实、偏好、决策、证据和上下文片段。它回答“过去发生过什么”。
Brain 是判断 脑子决定这些经历是否可信、是否稳定、作用范围多大、下一次应该改变什么行为。
Skill / Workflow 是固化结果 反复有效的做法不该永远停在文本 recall；它们应该变成可触发的工作方式。

问题重定义

当前讨论里最容易走偏的一点，是把“San 的脑子”过早翻译成 memory backend、schema、inbox、approve/discard 或某个 router。 这些都可能需要，但它们是较低层实现。顶层问题应该是：

San 如何从每次协作中形成“下一次默认就会做对”的能力，而不是每次都靠用户重新提醒、靠上下文重新塞满、靠工具重新搜索、靠模型临场发挥？

因此，v0.3 应该先设计“经验如何进入脑状态”，再决定哪些部分落到 memory、skill、workflow、hook、subagent policy 或外部 brain。

San 的脑子是什么

San Brain 不是一个单独数据库，也不是一个万能知识库。它是运行时的一组分层状态和固化机制：

层保存什么改变什么行为
Working State 当前任务、计划、约束、风险、已读证据、当前用户意图。 影响本轮怎么做；任务结束后大多丢弃。
Partnership / User Profile State 用户稳定偏好、画像事实、合作决策、沟通方式、默认交付物形态、容忍的自动化程度。 影响“我默认怎么理解这个用户、如何和这个用户合作”。
Project Operating State 项目约定、测试门禁、常见坑、架构边界、命名习惯、发布纪律。 影响“我在这个 repo 里默认怎么工作”。
Workflow / Skill Library 稳定、可复用、有触发条件的做事方法。 影响“遇到某类任务时自动进入哪套流程”。
Risk Reflexes 反复失败、容易误判、需要提前防御的模式。 影响“我什么时候必须停下来验证”。
Knowledge / Brain Plugins 本地或远程知识脑、资料库、MCP 记忆插件；GBrain 属于这一类。 影响“我该查哪里、信什么、如何综合”，但不替代 San 自己的工作态判断。

笔记仍然有价值

“记忆不是记笔记”不等于“不要笔记”。区别在于：笔记不是终点，而是 San 体验层的原材料。有些内容本身不会立刻变成 workflow 或 skill，但会让 San 更像长期合作伙伴。

可以直接提升体验的笔记 用户偏好、身份画像、长期目标、项目背景、已做过的决策、常用表达、重要事实、反复出现的上下文。
不应固化的笔记 临时情绪、一次性任务细节、未验证推断、过期状态、跨项目会污染判断的局部约束。

所以 v0.3 需要同时处理两类记忆：一类是会改变执行行为的 experience；另一类是会提升合作质感的 profile notes。前者驱动行动，后者改善理解。

Profile Notes 与 Experience 怎么形成

两者都可以来自 San 的 JSONL 会话账本，但不应该直接把 JSONL 当长期记忆。正确路径是：先用 TurnDigest / custom entries 做结构化摘要，再清洗、合并、去重、标注 scope 和证据，最后分别落到 profile 或 experience。

产物主要来源形成方式触发节奏
Profile Notes 用户明确表达、反复偏好、长期决策、项目背景、历史 TurnDigest。 从 session JSONL / TurnDigest 中抽取候选，汇总成用户画像、偏好、事实和 standing decisions；合并同义项，保留证据和更新时间。 轻量候选可在会话中生成；清洗和合并更适合 session stop、resume 前或显式维护命令触发。
Experience 用户纠偏、工具失败、测试失败、成功路径、review 结论、反复出现的执行模式。 解释“这件事下次应该改变什么行为”：状态、风险权重、workflow、skill、hook/check、GBrain 查询策略或普通 recall。 高置信低风险经验可在 turn end 后影响下一轮；复杂经验在 session stop 后 consolidate；后台定时整理应先只做建议，不静默改变高影响行为。
同一条证据可以同时产生 profile note 和 experience。例如用户说“遇到陌生现代项目先查 primary source”：profile note 是用户偏好更重视来源校验；experience 是下次遇到类似实体时必须先搜索/读取 primary source 再分类。

因此 v0.3 的推荐节奏是三层：会话中做候选捕获，停顿/结束时做清洗合并，未来再考虑 dream cycle 式后台整理。后台可以整理和提出建议，但不应在没有证据和撤销面的情况下静默升级高影响行为。

经验的五步生命线

1 Observe

记录发生了什么：用户纠偏、工具失败、测试结果、评审意见、成功路径、反复出现的偏好。

2 Interpret

判断它是什么：事实、偏好、项目规则、流程、技能、风险、一次性噪声，还是错误中间态。

3 Consolidate

决定是否固化、作用范围、置信度、证据、冲突关系和撤销方式。

4 Activate

下一次相似情境中，把经验编译成状态、workflow、skill、hook/check、subagent 选择或 recall。

5 Reflect

解释为什么这样行动；如果判断错了，允许撤销、降权、缩小 scope 或变回临时经验。

核心设计原则

  1. 体验优先。 进入 San Brain 的内容要么改变未来行为，要么提升长期合作体验；纯文本存档不是目标。
  2. Scope 优先于存储。 先判断这是用户级、项目级、repo 级、session 级，后判断放哪个 backend。
  3. Evidence before belief。 稳定经验必须能追溯到 digest、工具结果、文件、测试或用户明确纠偏。
  4. 低风险自动，高影响可控。 用户不应该审批每条专业分类，但能控制会长期改变 San 行为的内容。
  5. 先变状态，再变技能。 一次经验先影响姿态；反复稳定后才升级为 workflow、skill 或 hook。
  6. 可解释、可撤销、可降权。 黑盒判断可以存在；黑箱长期行为不可以存在。

经验形态

经验例子理想落点
事实 某个模型今天 400；某个 API 参数真实名字；某个文件是生成物。 memory / project fact / ContextPacket recall
偏好 研究和架构方案默认写 HTML；回答不要可选项式收尾。 partnership state / user preference
用户画像 用户在意顶层设计、讨厌未验证的自信判断、愿意让 agent 自主推进低风险改动。 partnership profile / user facts
合作决策 “遇到陌生现代项目必须先查 primary source”；“安全风险由用户自己评估，不要反复强调”。 partnership state / standing decisions
项目判断 这个包是 primary focus；某种 import convention 不能破坏。 project operating state
流程 品牌迁移必须分用户面、兼容层、内部包名、测试门禁。 workflow / managed skill draft
风险姿态 模型声明不等于可用；setup wizard 改动要同时验证 source-link 和 tarball。 risk reflex / check candidate
技能 一套稳定的 release audit、migration audit、prompt audit 方法。 SKILL.md / tool-aware workflow pack
外部知识 资料库、会议纪要、公司/人物/项目长期知识。 knowledge brain / MCP memory plugin，如 GBrain；San 负责何时查、如何用、如何把结果编译进工作态

自上而下架构

v0.3 不应从“我们要几个表、几个命令、几个配置项”开始，而应从一条运行时链路开始：

  1. Brain State Builder： 每轮开始前，组合用户画像、项目状态、当前任务、风险和已知 workflow，形成 San 当前工作态。
  2. Profile Synthesizer： 从 JSONL / TurnDigest / 明确用户表达中提取 profile notes，清洗成偏好、事实、画像和合作决策。
  3. Experience Interpreter： 每轮结束后，解释哪些经历应该改变未来行为，哪些只是日志或普通 profile note。
  4. Consolidation Policy： 决定 profile / experience 的 scope、置信度、证据、冲突、寿命、是否自动应用。
  5. Activation Layer： 在未来任务中把经验变成实际行为：加载 skill、选择 workflow、提高风险权重、触发 check、召回文本或查询 GBrain。
  6. Reflection Surface： 让用户看到 San 为什么变聪明、哪里变了、如何撤销。

这条链路之下才是具体实现：memory backend、skills 文件、hooks、subagents、commands、custom entries、ContextPacket 注入。

v0.3 应该证明什么

顶层验收不是“写入了多少 memory”，而是 San 是否真的更像一个会长期协作的 agent：

  • 用户纠正一次明确偏好、画像事实或合作决策后，San 后续默认遵守，不需要反复提醒。
  • 项目踩过的坑会提高下一次同类任务的风险权重，而不是只存在历史记录里。
  • 稳定流程会逐步从一次性状态升级为 workflow/skill 草案。
  • San 能解释“为什么这次我先做 A，再做 B”，并指向历史依据。
  • 错误固化可以撤销、降权、缩小 scope，而不是污染所有项目。
  • GBrain 等知识脑作为 memory/knowledge plugin 接入；Hermes/OpenClaw 等 agent 是对标和架构参考，不和 GBrain 放在同一抽象层。

当前 Experience Routing 文档的位置

现有 Experience Routing 文档应降级为实现草案，不再作为顶层设计主文档。 它已经接近 schema、命令面和 phase 拆分，适合作为后续实现时参考；但在达成脑模型共识前，不应继续往里面补更多实现细节。

更准确的推进顺序是：先冻结本文件里的脑模型，再从中抽出 v0.3 最小闭环，最后才回到 router、ledger、命令、测试和配置。
