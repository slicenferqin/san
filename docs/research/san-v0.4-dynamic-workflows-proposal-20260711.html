San v0.4 · Revised Product Proposal · 2026-07-11

把工作 SOP 变成真正会执行的 Workflow

San v0.4 只做两种 Workflow：固定、版本化、人工批准、显式启动的 Managed SOP Workflow；以及模型为当前任务现场生成、必须先审后跑的 Ad-hoc Dynamic Workflow。

范围已收敛：两种 Workflow，没有自治型第三种

实施状态：核心代码、安全测试和确定性 dogfood 已落地；Ad-hoc 已提供 fail-closed 的 revise-draft 范围缩小路径，token 报告只接受来源一致的 Skill/Managed 成对证据。真实模型对照仍待采样，因此 Managed 与 Ad-hoc 两层开关都默认关闭。详见 San v0.4 Workflows 实施与验收报告。

本提案的核心决定： v0.4 不追求“让 San 自己无限编排”。它只解决两件事：把已经成熟的 SOP 变成精确、低重复、可复用的执行流程；以及在一次复杂任务里，让模型先生成流程草稿，经人批准后只运行这一次。

Managed SOP Workflow v0.4 第一优先级

固定步骤、固定角色、固定权限、固定预算边界，发布前人工批准，每次由用户明确启动。

可版本化 可重复 低风险

Ad-hoc Dynamic Workflow v0.4 第二优先级

模型根据当前任务现场生成草稿；用户查看步骤、权限和预算后批准，只运行当前草稿。

一次性 先审后跑 中风险

范围锁： v0.4 没有“自动生成、自动批准、自动运行”的 Autonomous Workflow。没有定时触发、后台自发触发、Brain 自动提升权限，也没有无需用户意图的静默运行。

1. 为什么有些 SOP 应该是 Workflow，而不是 Skill

Skill 是一份给 Agent 阅读的说明书。它擅长传递知识、判断原则和注意事项，但每次执行时，Agent 仍然需要重新理解说明书、重新拆步骤、重新决定先后顺序。

当一个 SOP 的步骤、角色、交接格式和停止条件已经稳定时，每次重新理解反而会带来误差和重复 token。此时更适合把“怎么执行”交给 Workflow。

比较 Skill Managed SOP Workflow
本质 给 Agent 的说明书 运行时直接执行的工作安排
步骤顺序 Agent 每次重新理解 版本中已经固定
并行关系 Agent 每次重新决定 流程明确规定
中间结果 容易进入主上下文 留在 Workflow 节点和结构化结果中
失败处理 依赖当前 Agent 临场判断 重试、跳过、停止条件已定义
重复运行 可能每次略有不同 同一版本走同一条流程
适合内容 知识、规范、判断方法 稳定 SOP、固定质量门、重复性任务
不是所有 Skill 都要改成 Workflow。 “怎样写好 TypeScript”“怎样评审安全风险”仍然适合 Skill；“依次检查类型、测试、变更日志，再并行做两轮复核”更适合 Workflow。Workflow 内部的 Agent 仍然可以加载 Skill。

2. v0.4 只有这两种 Workflow

类型 谁创建 批准方式 怎么启动 是否保存
Managed SOP 用户、团队，或模型根据已有 SOP 生成草稿 发布具体版本时人工批准 用户每次明确运行命令 保存为版本化文件
Ad-hoc Dynamic 模型根据当前任务现场生成 每个草稿、每次运行都要批准 用户批准当前草稿后运行一次 默认不保存

两者共用的底线

  • Workflow 脚本只负责安排 Agent，不能直接碰电脑。
  • 运行前都能看到阶段、最大 Agent 数、权限和预算。
  • 脚本、权限、scope 或预算变化后，旧批准不能继续使用。
  • Agent 权限只能比当前会话更少，不能通过 Workflow 变多。
  • 每次运行都有状态、成本、证据和最终结果记录。
  • 用户可以查看、暂停、停止，并知道失败发生在哪一步。

3. Managed SOP Workflow 怎么用

Managed SOP 是 v0.4 的核心产品。它把一个已经认可的工作方法，从“每次让 Agent 重新读说明”变成“直接运行同一个已批准版本”。

1

准备 SOP

来源可以是现有 Skill、Markdown 文档、人工描述，或一次已经验证成功的任务流程。

2

生成草稿

San 把步骤、输入、输出、角色、权限、预算和失败条件整理成 Workflow 草稿。

3

批准版本

用户查看人话摘要和原始脚本，批准一个准确版本。任何变化都会产生新版本。

4

明确运行

以后通过命令传入参数运行。只要没有超出已批准边界，不需要每次重读整份 SOP。

建议体验

/workflow publish release-readiness-v1 将发布以下 Managed SOP Workflow： 名称：release-readiness 版本：v1 输入：branch, target 阶段：基线检查 → 并行验证 → 风险复核 → 汇总 最大并发：6 最大 Agent：12 权限：只读 token 上限：120k 操作： 查看人话步骤 查看原始脚本 批准并发布 拒绝
/release-readiness branch=feature/payments target=staging 将显式启动已批准版本： release-readiness@v1 参数范围符合批准条件 权限没有变化 预算没有变化 运行 / 取消
方便但不放松控制： Managed Workflow 的版本批准可以复用，但每一次执行都必须由用户明确启动。脚本指纹、权限、scope、参数格式或预算发生变化时，必须发布并批准新版本。

4. Ad-hoc Dynamic Workflow 怎么用

Ad-hoc 用于当前任务很复杂，但还没有成熟 SOP 的情况。用户明确要求“用 Workflow 做”，模型先生成一份一次性草稿，而不是直接启动一群 Agent。

1

用户明确提出

例如：“用 Workflow 审计全仓权限校验，并让另一批 Agent 复核发现。”

2

模型只生成草稿

草稿包括阶段、Agent 数、工具、预算、停止条件和预期输出，不立即执行。

3

用户批准这一次

用户可以查看、修改、缩小范围或拒绝。批准只对当前草稿和当前参数有效。

4

运行一次

完成、拒绝或过期后删除草稿脚本和参数，只在当前会话审计里保留不可复用的 hash 证据。是否沉淀成 Managed SOP 由用户另行决定。

运行前必须让用户看懂

Ad-hoc Workflow 草稿：audit-auth-routes 目的： 检查 42 个路由文件是否遗漏鉴权，并复核每个发现 阶段： 1. 1 个 Agent 列出路由 2. 最多 8 个 Agent 并行审计 3. 最多 4 个 Agent 复核发现 4. 1 个 Agent 汇总报告 边界： 只读 · 不修改文件 · 不执行 Shell 最多 14 个 Agent · 最多 150k token 操作： 查看原始脚本 缩小范围 批准运行一次 拒绝
Ad-hoc 永远不能“记住批准”。 因为每次脚本都是现场生成的，即使名称相同，也必须重新展示和批准。成功运行一次也不会自动变成 Managed Workflow。

5. 两种 Workflow 如何转换

已有 SOP / Skill / 人工步骤 → 生成 Managed 草稿 → 人工审阅并发布版本 → 用户显式重复运行 复杂的一次性任务 → 模型生成 Ad-hoc 草稿 → 人工批准 → 只运行一次 → 用户认为值得复用时，重新进入 Managed 发布流程

Ad-hoc 可以成为 Managed 的素材，但不能自动升级。升级时必须重新检查：

  • 步骤是否真的稳定，而不是只适合当时那个任务；
  • 参数能否明确描述；
  • Agent 的输入和输出能否固定格式；
  • 权限是否可以进一步缩小；
  • 失败、重试和停止条件是否清楚；
  • 预算是否适合重复运行；
  • 适用 scope 是用户、项目、仓库还是某个目录。
没有第三条自动路线： 运行成功的 Ad-hoc 不会被 Brain 自动保存，不会静默变成命令，也不会在相似任务出现时自行启动。

6. 如何确保不会脱离掌控

控制不是依赖“模型应该听话”，而是由运行时强制执行五道锁。

1. 内容锁

批准绑定到具体脚本指纹。改一个步骤、参数、权限或预算，都算新版本。

2. 权限锁

脚本不能读写文件、执行 Shell、访问网络、环境变量、密钥或模块。实际工作只能交给受限 Agent。

3. 规模锁

并发、Agent 总量、token 和时间都是硬上限。达到上限就停止调度，不只是显示警告。

4. 启动锁

Managed 每次必须显式运行；Ad-hoc 每次必须批准。没有定时、自发或静默启动。

5. 副作用锁

第一版只读。后续写入只允许在独立工作区产生补丁，应用前再次检查和确认。

失败原则

无法证明节点已经完成、权限仍一致或结果已应用时，一律 blocked，不猜、不重复执行。

建议默认限制

限制 默认 硬上限 说明
同时运行的 Agent 8 16 Workflow 有独立限制，不直接继承 task 的 unlimited 配置。
单次 Agent 总数 建议不超过 25 100 超过 25 必须显示大规模运行警告；v0.4 不开放上游的千 Agent 规模。
Managed 首版权限 只读 批准范围内 后续写入必须使用独立工作区。
Ad-hoc 首版权限 只读 每次批准范围内 不允许保存“以后都信任这个名字”。
token / 时间 运行前展示 每次运行固定 脚本只能查看剩余预算，不能修改预算。

用户始终拥有的控制

  • 查看当前阶段和所有 Agent。
  • 查看已用 token、剩余预算和耗时。
  • 暂停，不再启动新 Agent。
  • 停止整个 Workflow 或单个 Agent。
  • 查看原始脚本和人话步骤。
  • 查看每个结果的来源和最终交付状态。
  • 知道当前是 Managed 版本还是一次性 Ad-hoc 草稿。

7. 怎样证明它真的更省 token、更精确

Workflow 不应该只靠感觉宣称“更省”。v0.4 必须把相同 SOP 用 Skill 和 Managed Workflow 各跑一组，比较真实数据。

为什么有机会节省

  • 主 Agent 不再每次读取和重新解释完整 SOP。
  • 步骤和并行关系由运行时执行，不需要主 Agent 反复思考。
  • 中间结果保存在节点中，不全部进入主对话。
  • Agent 只收到当前节点需要的输入，而不是完整历史。
  • 结构化输出减少“解释上一轮文本再决定下一步”的 token。
  • 相同版本不需要每次重新生成工作计划。
需要诚实区分： Workflow 应该显著减少主上下文和编排 token，但如果它启动更多 Agent，总 token 不一定总是更低。目标是以更低的编排成本获得更稳定的质量，并把总成本锁在运行前可见预算内。

建议对比指标

指标 要回答的问题 v0.4 建议门禁
主会话编排 token 主 Agent 为理解 SOP、拆分和调度花了多少 token？ Managed 中位数至少比 Skill 基线低 30%。
主会话上下文增长 中间结果有多少进入主对话？ 中位数至少减少 50%。
总 token 全部 Agent 加起来是否失控？ 不得超过运行前批准预算；超出即失败，不追加。
步骤一致性 同一版本重复运行是否漏步骤或换顺序？ 固定 fixtures 下 100% 走同一节点图。
一次通过率 更精确是否真的减少返工？ 不低于 Skill 基线，关键 SOP 应有提升。
重复运行成本 第 2–10 次是否仍重复付出计划成本？ Managed 不重新生成计划，不重复注入完整 SOP。

建议先选 5 个真实 SOP，每个用 Skill 和 Managed Workflow 各跑至少 5 次。只有在质量不下降、主会话 token 明显下降、成本可预测时，才能正式宣传“更精确、更省 token”。

8. 一个 Managed SOP 大概长什么样

普通用户不必手写代码，但批准前应该同时看到人话版本和原始脚本。

名称：release-readiness 版本：v1 用途：发布前确认代码、测试、变更日志和风险均满足要求 输入： branch：待发布分支 target：目标环境 阶段： 1. 检查分支和工作区基线 2. 并行运行类型、测试、变更日志检查 3. 让复核 Agent 检查失败和风险 4. 汇总为发布建议 权限： 只读 限制： 最大并发 6 最大 Agent 12 最大 120k token 停止： 基线不满足立即 blocked 预算耗尽立即 stopped 关键检查缺证据不得给出通过

对应脚本只表达调度，不直接操作系统：

export const meta = { name: "release-readiness", description: "发布前检查", version: 1, }; phase("基线"); const baseline = await agent("检查发布基线", { schema: baselineSchema }); phase("并行验证"); const checks = await parallel([ () => agent("检查 TypeScript 合同", { schema: checkSchema }), () => agent("检查测试结果", { schema: checkSchema }), () => agent("检查变更日志", { schema: checkSchema }), ]); phase("复核"); const review = await agent("复核基线和检查证据", { schema: releaseReviewSchema, }); return review;

真正读取文件和运行检查的是拥有明确工具范围的 Agent。Workflow 脚本只安排阶段、并行关系和结构化交接。

9. San 与 Claude Dynamic Workflows 的关系

San 会兼容 Claude Code 公开的 Workflow 子集，但产品重点不是复制界面，而是让 Managed SOP 更容易版本化、审批、测量 token 和控制副作用。

内容 v0.4 决定
.claude/workflows/*.js 支持公开格式和最近目录优先规则。
San 原生路径 提供 .san/workflows，用于 Managed SOP 和 San 专属元数据。
meta、args、顶层 await 支持公开合同。
agent、parallel、pipeline 支持公开行为；可以增加 San helper，但不改变已有含义。
未公开内部 API 不兼容、不猜测。
workflowz v0.4 内测期间保持现有“快速 task 编排”行为，不静默改变语义。
ultracode 不作为首版自动触发器；用户明确要求 Ad-hoc 后才生成草稿。

10. v0.4 做什么，不做什么

v0.4 会交付

  • Managed SOP Workflow 的草稿、发布、版本和显式运行。
  • Ad-hoc Dynamic Workflow 的生成草稿、人工批准和一次性运行。
  • 安全 Runtime，只暴露白名单 Workflow helper。
  • San 与 Claude Workflow 文件发现。
  • 结构化参数和结构化 Agent 结果。
  • 后台运行、进度、暂停、停止和同会话恢复。
  • Agent 数、并发、token 和时间硬预算。
  • 只读内测，以及后续独立工作区写入。
  • Skill 与 Managed SOP 的真实 token 对比报告。
  • 运行审计、结果证据和只交付一次。

v0.4 明确不做

  • Autonomous Workflow。
  • 模型自动批准自己生成的 Workflow。
  • 没有用户意图的自动或定时启动。
  • Brain 自动保存、升级或运行 Workflow。
  • Workflow 脚本直接访问文件、Shell、网络、环境变量或密钥。
  • 脚本在运行中提高自己的预算或权限。
  • Ad-hoc 根据名字记住永久批准。
  • Ad-hoc 成功后自动升级为 Managed。
  • 首版直接修改用户当前工作区。
  • 退出 San 后自动继续未完成 Workflow。
  • 兼容 Claude 未公开的私有行为。

11. 实施阶段

实施顺序围绕两个产品逐步展开，不再为未来的自治型 Workflow 预留产品范围。

W0

冻结两种 Workflow 的合同

冻结 Managed 和 Ad-hoc 的文件格式、版本、审批、参数、权限、预算、节点身份、暂停恢复和错误语义。建立允许脚本与恶意脚本 fixtures。

完成标准： 任何需求都能明确归入 Managed、Ad-hoc 或“不属于 v0.4”，并能判断脚本应运行、询问还是拒绝。
W1

安全 Runtime、Agent Bridge 与运行记录

实现受限 JavaScript、agent/parallel/pipeline、结构化结果、硬预算、取消、run/phase/node 事件和最终结果一次性交付。先只读。

完成标准： 公开示例可运行；越权脚本全部阻止；预算和停止真实生效；没有结果重复交付。
W2

交付 Managed SOP Workflow

实现 SOP→草稿、版本发布、批准记录、显式命令、参数校验、同会话暂停恢复、San/Claude 路径和 /workflows。

完成标准： 至少 5 个真实 SOP 可以稳定重复运行；版本变化重新批准；同一版本不重复生成计划；token 对比达到门禁。
W3

交付 Ad-hoc Dynamic Workflow

用户明确要求后，模型生成人话步骤和脚本草稿；展示规模、权限和预算；批准后只运行一次，默认不保存。

完成标准： 未批准零执行；每个草稿独立批准；相同名称不能复用信任；成功后不会自动升级为 Managed。
W4

受控写入

Managed 与 Ad-hoc 都只能让 Agent 在独立工作区修改，输出补丁或分支；应用时检查基线、凭证和人工变化，冲突即 blocked。

完成标准： 零重复写入、零不安全覆盖；崩溃后能判断副作用状态；用户能在应用前查看完整变化。
W5

Dogfood、token 报告与 rollout

对 Managed 和 Ad-hoc 分别做真实任务评估，记录准确率、主上下文 token、总 token、Agent 数、暂停恢复、越权尝试和用户停止行为。

完成标准： 安全门禁全绿；Managed 达到 token 目标；Ad-hoc 无未批准执行；再决定是否扩大内部 opt-in。默认开启仍是独立决策。

12. v0.4 怎么验收

Managed SOP 必须证明

  • 同一版本、同一参数会产生同一节点图和相同权限边界。
  • 版本、参数格式、权限、scope 或预算变化后旧批准失效。
  • 用户没有显式运行时绝不启动。
  • 重复运行不重新生成计划，不重复注入完整 SOP。
  • 主会话编排 token 中位数比 Skill 基线至少降低 30%。
  • 主会话上下文增长中位数至少减少 50%。
  • 质量和一次通过率不低于 Skill 基线。
  • 暂停恢复不重复已完成节点，最终结果只交付一次。

Ad-hoc 必须证明

  • 模型只能生成草稿，不能直接执行。
  • 用户能在批准前看懂步骤、规模、权限、预算和停止条件。
  • 每个草稿都单独批准，名称相同也不能复用。
  • 用户缩小范围后，运行的必须是修改后的草稿。
  • 完成后默认不保存、不自动复用、不自动升级。
  • 拒绝或取消后，Agent 启动数必须为 0。

共同安全门禁

  • 脚本直接访问文件、Shell、网络、process、环境变量、模块和密钥全部被阻止。
  • Agent 权限是 Workflow、会话、Agent 三者允许范围的交集。
  • 并发、Agent 总数、token、时间达到上限后真实停止。
  • 停止后状态明确为 cancelled/aborted，不能显示 completed。
  • 无法证明完成的节点进入 blocked/unknown，不盲目重跑。
  • 日志、UI 和报告不泄漏本机路径或凭据。
  • 现有 task、San Loop、Brain、Skill 和 workflowz 行为不回归。

建议 dogfood 样本

类型 样本 次数 重点
Managed 5 个真实 SOP 每个至少 5 次 步骤稳定、token 节省、重复运行成本
Ad-hoc 10 个不同复杂任务 每个至少 2 个草稿版本 审批、范围修改、预算和一次性边界
恶意脚本 文件、Shell、网络、密钥、无限循环 完整矩阵 全部阻止或硬停止
恢复 暂停、Agent 失败、预算耗尽、用户停止 每种至少 3 次 无重复节点、无双重交付

13. Rollout 顺序

开发期：默认关闭，只跑 fixtures ↓ Managed 只读 dogfood：固定 5 个 SOP ↓ Managed 内部 opt-in：验证 token 与重复运行 ↓ Ad-hoc 只读 dogfood：每次完整审批 ↓ Ad-hoc 内部 opt-in ↓ 独立工作区写入 dogfood ↓ 根据数据决定是否扩大使用

Rollout 使用两个独立开关：san.workflows.enabled 只控制 Managed；san.workflows.adHocEnabled 在 Managed 已开启的前提下单独控制 Ad-hoc。隔离写入仍由第三个开关 san.workflows.allowIsolatedWrite 控制。

任何阶段出现以下情况都停止扩大 rollout：

  • 未批准却启动 Agent；
  • 脚本获得直接系统权限；
  • 预算上限只提示但没有停止；
  • 暂停恢复重复已完成节点；
  • 写入覆盖人工变化；
  • Ad-hoc 自动保存或自动复用；
  • Managed token 没有明显优于 Skill 基线；
  • 用户无法判断当前到底在运行什么。

14. 推荐批准口径

建议批准： San v0.4 只实施 Managed SOP Workflow 和 Ad-hoc Dynamic Workflow。Managed 用于固定、版本化、人工批准、显式启动的重复 SOP；Ad-hoc 由模型为当前任务生成草稿，必须逐次人工批准，只运行一次，默认不保存。两者共用受限 Runtime、硬预算、运行记录和用户停止能力。v0.4 不实施自治型 Workflow、自动批准、自动触发或 Brain 自动运行。
两个类型 Managed + Ad-hoc
三次明确 明确生成、明确批准、明确启动
零自治 没有自动批准或静默运行

15. 简单词汇表

词 这里是什么意思
Managed SOP 已经审阅、批准并保存版本的固定 Workflow。
Ad-hoc 为当前一次任务现场生成、批准后只运行一次的 Workflow。
草稿 可以查看和修改，但还没有获得执行许可的 Workflow。
Runtime 读取 Workflow、安排 Agent、执行限制并记录状态的小引擎。
脚本指纹 根据脚本内容生成的版本标识；任何内容变化都会产生不同指纹。
节点 Workflow 中一个可以单独记录的工作单元，通常对应一次 Agent 调用。
blocked San 无法安全继续，需要停止并告诉用户原因，而不是自己猜。

16. 工程附录

下面内容供实施人员使用。产品审阅不需要理解这些细节。

建议的产品数据类型
  • ManagedWorkflow：name、version、sourceHash、argsSchema、permissionManifest、scope、limits、approval。
  • AdHocWorkflowDraft：draftId、sourceHash、taskRef、args、permissionManifest、limits、expiresAt。
  • WorkflowRun：runId、workflowKind、sourceHash、argsHash、approvalRef、status、budget、deliveryState。
  • WorkflowNode：nodeId、phase、attempt、inputHash、status、agentRef、resultRef、committedAt。

公开 product union 只允许 managed 和 ad_hoc；不要预留 autonomous 枚举值，避免未来实现把未批准路径悄悄接入。

当前模块的复用边界
模块 结论 用途
task/subagent executor 复用 Workflow agent() 的调度后端。
structured output validator 复用 节点输入输出合同。
eval agent bridge 抽出后复用 重构成不依赖 eval 的中立 spawn service。
eval parallel/pipeline 复用行为合同 保留 barrier、顺序和错误传播测试。
eval JsRuntime 禁止作为沙箱 当前暴露 process、fs、require、import、write 和任意活动工具。
Extension loader 不复用 同进程高信任模型不适合项目 Workflow。
AsyncJobManager 执行层复用 不能作为持久状态权威。
AgentOutputManager / agent:// 复用 节点结果和大输出。
task worktree isolation W4 复用 写入 Agent 的补丁和分支。
Brain v0.4 不接自动运行 保持现状，不增加自动发布或触发路径。
建议的审批键

Managed 发布批准至少绑定：

workflowKind name version sourceHash argsSchemaHash scopeKey permissionManifestHash concurrencyLimit agentLimit tokenLimit writeMode

Ad-hoc 运行批准还要绑定当前 taskRef、具体 argsHash 和过期时间，并且不能持久化成名称级信任。

建议的运行事件

draft_created、version_published、run_approved、run_started、phase_started、node_scheduled、agent_started、agent_completed、agent_failed、node_committed、run_paused、run_resumed、run_cancelled、run_blocked、run_completed、result_delivered。

Ad-hoc 还需记录 draft_rejected 和 draft_expired；Managed 还需记录 version_revoked。没有自动批准或自动触发事件。

建议的代码边界
  • src/workflows/types.ts：两个 product kind 和运行状态。
  • src/workflows/schema.ts：meta、args、权限和限制验证。
  • src/workflows/discovery.ts：San/Claude 路径与优先级。
  • src/workflows/runtime/：受限 JavaScript。
  • src/workflows/agent-bridge.ts：白名单 helper 到 subagent 调度。
  • src/workflows/ledger.ts：append-only 事件与读模型。
  • src/workflows/approval.ts：Managed 发布和 Ad-hoc 单次批准。
  • src/workflows/manager.ts：run/pause/resume/cancel/block。
  • src/workflows/delivery.ts：结果 exactly-once 交付。
  • src/workflows/token-report.ts：Skill/Managed 对比数据。
  • src/modes/components/workflows/：管理和进度 UI。
