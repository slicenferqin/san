San v0.2 · Acceptance Benchmark

执行闭环从“能跑”验收到“能交付”

v0.1 验收关注上下文稳态：长对话是否不膨胀、主线是否不丢。v0.2 验收的核心问题更明确： 多角色分工是否真的提升最终交付质量，而不只是把同一个 agent 的自然语言过程拆成更多步骤。 更进一步，San 必须证明 v0.1 的上下文稳态能托住 v0.2 的多角色协作：在不让上下文线性膨胀的前提下， 让 Commander / Worker / Supervisor / Oracle 的分工带来更好的计划、实现、审查、修复和收口。

版本：v0.2 mature execution loop 配置：san-execution-loop-recommended.yml 样本：确定性 gate + 真实 provider dogfood 结论口径：质量 / 成本 / 稳态 ROI 模型策略：同模型控制组 + 异构模型验证组

核心假设

v0.2 不应只证明“多 agent 能跑起来”，而要证明“多角色分工让交付质量更稳定”。因此验收要围绕同一组真实任务做对照： 普通 agent 是否容易遗漏计划、验收、复验和失败边界；San v0.2 是否因为角色分工，把这些质量控制动作结构化、强制化、可审计化。

Commander 负责目标澄清、范围控制、任务拆解、风险登记和验收标准，不直接写代码。
Worker 负责按 assignment 实现和自检，避免边做边改验收口径。
Supervisor 负责独立质量门禁，基于 diff、测试、规则和缺陷证据给 verdict。
Retry 负责把缺陷转回计划和实现，而不是靠最终回答口头补救。
Oracle 只在 deep 模式提供 second opinion，降低复杂决策的单点偏差。
主验收问题 同样的真实开发任务，San v0.2 的多角色执行链是否在 v0.1 上下文稳态支撑下，以可接受甚至更低的有效成本， 产出更少遗漏、更强证据、更可靠复验、更清晰失败收口的最终交付。

模型配置策略

多角色如果全部使用同一个模型，仍然可以验证代码级角色边界、ledger、retry 和检查门禁；但从产品说服力看， v0.2 更应该验证“角色分工 + 模型分工”的组合价值。不同角色天然适合不同模型：Commander 需要规划和架构判断， Worker 需要稳定执行和代码修改性价比，Supervisor 需要强审查能力，Oracle 需要高质量 second opinion。

组别 配置 验证目的 结论解释
控制组 A：普通 agent 单模型、不开 execution loop。 提供当前默认体验的成本和质量基线。 用于判断 v0.2 是否真的改善最终交付，而不是只增加流程。
控制组 B：同模型多角色 Commander / Worker / Supervisor / Oracle 使用同一模型。 隔离“角色分工本身”的收益。 如果同模型多角色也明显更好，说明 workflow 结构本身有效。
主验证组 C：异构模型多角色 按角色选择不同模型，例如 Worker 用高性价比代码模型，Commander 用强规划模型，Supervisor 用强审查模型。 验证 v0.2 作为产品形态的最佳推荐配置。 只有 C 相对 A/B 在质量和 ROI 上都更好，才说明“多角色 + 多模型”方向成立。
推荐角色映射 Worker 可以优先用 DeepSeek 这类高性价比代码执行模型；Commander / Oracle 可以用 GPT 这类强规划和综合判断模型； Supervisor 可以用 Claude Code 这类强代码审查模型。验收时必须同时保留同模型控制组，避免把模型差异误判成 San workflow 收益。

验收目标

闭环是否稳住

每个任务都必须形成明确 objective、plan、assignment、worker result、review、verdict；失败时进入 retry / blocked / aborted，而不是散落在对话里。

交付质量是否提升

最终 diff、测试、文档、风险说明和用户可用性，必须因为独立计划和独立验收而更可靠。

ROI 是否成立

多角色可能增加调用次数，但 v0.1 稳态应降低上下文浪费；验收要看单位成本交付质量是否提升。

验收结论格式 最终报告回答三个问题：一是多角色 execution loop 是否稳住，二是多角色分工是否实质提升最终交付质量， 三是 v0.1 + v0.2 组合后的质量 / 成本投入产出比是否成立。

质量成本模型

v0.2 的产品方向验证不能只看“质量更高”，也不能只看“token 更少”。正确口径是质量收益是否超过多角色协作成本， 以及 v0.1 上下文稳态是否把协作成本压到可接受范围内。理想状态不是“多花很多 token 换质量”，而是进入更好的质量成本前沿： 更稳的交付、更少返工、更低上下文浪费、更高单位 token 产出。

组合 预期成本形态 预期质量形态 产品判断
普通 agent，无稳态 长任务上下文线性膨胀，后期 input tokens 快速变大。 依赖单 agent 自检，计划、实现、验收容易混在一起。 基线组：可能短任务快，但长任务成本和失误率不可控。
v0.1 上下文稳态 通过 digest、checkpoint、ContextPacket 控制上下文表面。 主线保持更稳，但不主动改变执行治理结构。 证明“便宜且稳”的上下文基础。
v0.2 多角色，无稳态 多角色带来更多调用，若无稳态支撑，成本可能放大。 审查和 retry 更强，但容易被上下文成本抵消。 不应作为推荐方向，只用于隔离多角色质量收益。
v0.1 + v0.2 推荐组合 多角色增加必要调用，但每轮上下文保持短、稳、可审计。 计划更清晰、缺陷更少逃逸、失败更能闭环。 目标组：用稳态降低协作成本，用分工提高交付质量。
ROI 验收口径 v0.2 只有在“质量提升 / 有效成本增加”明显优于普通 agent 时才算产品方向成立；如果质量提升不明显，或成本增长吞掉收益， 即使流程全绿也只能算技术验证，不算产品验收通过。

Layer A：确定性 Gate

场景 模式 要验证的通用能力 通过标准
Rush Pass rush 最短路径从 plan 到 worker 到 final verdict。 事件链包含 plan_created -> assignment_created -> worker_completed -> finalized，状态为 passed。
Smart Retry smart Supervisor 发现问题后，Commander 能消费缺陷上下文重新计划。 第一轮 needs_fix，出现 retry_requested，第二轮 passed，retryCount=1。
Deep Blocked deep 深度模式必须先走 Oracle second opinion，再由 Supervisor 做最终门禁。 reviews=2，包含 Oracle evidence，最终可 pass 或 blocked，但必须证据完整。
Budget Exhausted rush hard budget 用完后不再启动额外 agent。 状态为 blocked，remainingTurns=0，Supervisor 不应被调用。
Recovery smart active run 恢复时没有 running child process，必须转为可审计 blocked。 事件包含 recovered，状态为 blocked，reason 可读。
Abort rush 用户停止 run 时不删除历史，只追加 abort 事件。 状态为 aborted，事件包含 aborted，历史 run ledger 可重建。

Layer B：10 个真实任务

这组任务不是为了机械命中特定字符串，而是覆盖真实开发中常见的闭环形态：小修、跨文件、测试、文档、失败、预算、恢复、深度审查。 每个任务完成后都保留 session jsonl、/san-loop status、测试输出和 git diff，并记录多角色分工对最终质量的实际贡献。

T01
小型 bug fix
找一个低风险真实缺陷或 TODO，要求最小改动并补测试。
验收点：Commander 是否限定最小修复；Supervisor 是否发现普通 agent 容易漏掉的边界。
T02
跨文件功能补齐
实现一个涉及 src + test + docs 的小功能，例如报告字段或 CLI 输出增强。
验收点：Commander 拆解是否降低遗漏；Worker 是否按 assignment 交付；Supervisor 是否按文件证据验收。
T03
测试补强
为一个已有边界补 contract-level test，禁止源码 grep 型测试。
验收点：Supervisor 是否拒绝低价值测试；最终测试是否保护真实外部合同。
T04
Supervisor needs_fix
故意给出一个初版不完整的任务，让 Supervisor 要求修复。
验收点：needs_fix 是否证明独立验收有价值；第二轮是否真实关闭缺陷。
T05
项目规则约束
任务涉及 AGENTS.md 里的规则，例如不用 any、不用 ReturnType<>、用 Bun API。
验收点：多角色是否共同守住项目规则；Supervisor 能否指出违反规则的 diff。
T06
文档交付
生成或更新一份 docs/research HTML 报告，要求带结论、证据、矩阵。
验收点：Commander 是否定义报告结构；Supervisor 是否检查证据、矩阵和结论完整性。
T07
失败命令闭环
选择一个会先失败的验证命令或测试，让 San 诊断并修复。
验收点：失败输出是否进入 evidence；retry 是否避免盲改；最终是否重新验证。
T08
Deep 模式架构审查
让 deep 模式审查一个设计变更或 release gate。
验收点：Oracle 是否提供不同视角；Supervisor 是否吸收或反驳 second opinion。
T09
预算边界
设置较紧 maxTurns 或复杂任务，观察 hard budget 收口。
验收点：预算控制是否防止多角色扩散；blocked reason 是否能指导下一步。
T10
综合验收报告
要求 San 总结前 9 个任务的闭环质量、失败样本和改进建议。
验收点：最终报告是否能量化多角色分工带来的质量提升，不编造未发生证据。

评判标准：100 分制

维度 分值 评分口径 一票否决
工程产物质量 20 最终代码/测试/文档是否比普通 agent 对照更少遗漏、更少返工、更符合项目规则；改动是否聚焦；验证是否通过。 bun check 或关键测试失败仍宣称通过。
多角色增量价值 15 Commander、Worker、Supervisor、Oracle 是否分别产生可见贡献：更好计划、更聚焦实现、更严格验收、更可靠决策。 角色输出高度同质化，只是重复总结，没有改变最终交付质量。
质量 / 成本 ROI 15 相对普通 agent，最终质量提升是否足以覆盖多角色带来的额外 turn、tokens、耗时和复杂度。 成本显著上升但质量无明显提升，或高质量只靠不可接受的 token 堆叠换来。
上下文稳态成本控制 10 v0.2 是否复用 v0.1 ContextPacket/checkpoint/digest，让多角色协作不导致上下文线性膨胀。 10 轮后上下文明显膨胀或丢失关键约束，导致协作成本不可控。
闭环完整性 10 是否稳定形成 plan、assignment、worker result、review、terminal verdict；ledger 能否完整重建。 任务结束无 terminal status，或 ledger 无法重建。
证据质量 10 review 是否引用 diff、测试、命令输出、文件路径和具体缺陷；blocked 是否给出可执行原因。 最终结论没有任何可复核证据。
Retry / 失败闭环 10 needs_fix 是否进入 retry；新计划是否消费旧缺陷；失败命令是否被诊断并复验。 发现缺陷后仍 pass，或重复失败却无 blocked reason。
角色边界与预算 10 角色职责是否清晰；turn budget、maxRetries、abort、recovery 是否可审计；预算耗尽是否停止继续派发。 Supervisor 直接改代码、Worker 绕过验收、预算耗尽后继续启动 agent，或 abort 丢历史。
通过门槛 总分 ≥ 85 为 v0.2 dogfood PASS；75-84 为可继续内测但需列出 v0.2.1 修复项；低于 75 或触发一票否决则不建议对外宣称。

对照组设计

v0.1 的对照重点是上下文膨胀；v0.2 的对照重点是最终交付质量。普通 agent 可能也能完成任务， 甚至在小任务上更快；同模型多角色可以证明 workflow 结构是否有效；异构模型多角色则验证推荐产品配置是否成立。 San v0.2 必须证明多角色分工能减少遗漏、提高复验质量、改善失败收口，并且在 v0.1 稳态支撑下， 把这些质量收益控制在合理 token 和时间成本内。

比较项 普通 agent 预期表现 San v0.2 预期表现
投入产出比 单 agent 调用少，但长任务后期上下文膨胀，返工成本可能隐藏在后续轮次。 多角色调用更多，但 ContextPacket 降低上下文浪费，Supervisor 降低缺陷逃逸和后续返工。
最终缺陷率 依赖单个 agent 自检，容易遗漏边界或项目规则。 Supervisor 独立复核 diff、测试和规则，缺陷应更少逃逸到最终交付。
计划质量 计划可能和实现混在一起，范围漂移时不明显。 Commander 先冻结 objective、constraints、taskGraph、acceptanceCriteria。
验收质量 容易把“测试跑了”当成结论，缺少独立审查视角。 Supervisor 基于 checks、diff、testsRun 和 defects 给 verdict。
失败处理 可能直接继续改，失败原因和复验边界不稳定。 needs_fix / blocked / retry_requested 是结构化状态，可回放、可复盘。
汇报复盘 靠最终回答回忆，可能遗漏中间决策。 最终报告能从 ledger 和 review reports 取证。
