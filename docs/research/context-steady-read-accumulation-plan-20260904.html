连续 read 与 Context Steady 触发治理方案

San · packages/coding-agent · 方案稿 · 2026-09-04 · 静态 HTML，无外部依赖 · 供评审，不含实现改动

先给结论：不应通过关闭稳态摘要或无限提高触发阈值来掩盖连续读取。正确的治理顺序是：先在 provider projection 层卸载旧的大型 read 结果，再用一次性、带滞回的维护作为兜底。

原始 session journal 保留完整事实；当前 provider 请求只携带当前任务需要的精确内容、可恢复引用和小型摘要。这样连续读取仍可继续，但不会把每一次 read 的全文永久带入后续请求。

0 · 本次评审需要拍板的事项

事项本方案建议需要评审的取舍
D1：旧工具结果何时降级按“年龄 + 大小 + 保护状态”降级。当前 logical turn 和最近窗口保留原文，更早且较大的已完成 tool result 换成可重读 stub。越早卸载越省 token，但模型回看历史时需要主动 re-read。
D2：默认开关toolOutputOffload=true、stableProjection=true作为推荐配置先启用；先观察，再考虑修改全局默认值。默认开启可直接解决大部分累计增长；关闭则保留当前兼容行为，但连续 read 仍容易增长。
D3：维护触发方式触发线与回落线分离；同一 maintenance cycle 不重复生成摘要。优先卸载，仍超过硬线才 compaction/recovery。更保守的回落目标会增加一次维护规模，但能避免“摘要后马上再次摘要”。
D4：读取重叠去重第一阶段只做 provider projection 层的安全去重，不改 journal，不合并用户可见的 read 记录。不改变持久记录，风险最低；区间级智能合并可留作后续优化。

2 · 根因模型：三层数据不能混为一谈

raw journal（完整、追加写入、用于恢复） │ │ 生成 / 恢复 active messages ▼ active session context（可含多次 read 原文，随工具循环增长） │ │ transform + ContextPlan materialization ▼ provider-bound projection（真正发给模型；应受 steady/burst ceiling 约束） 目标：journal 可增长；active context 可有原文；provider projection 不因旧 read 结果线性增长。

触发机制：Context Steady 关注的是完整 provider input 的估算，而不是某个文件大小。以 500K context、20% reserve、240K steady target 为例：

hardInputCeiling = 500K × (1 - 20%) = 400K
steadyTarget     = 240K
controlMax       = min(burstCeiling, floor(240K × 13 / 12)) ≈ 260K

连续 read 结果若持续留在 provider projection，就会把输入从 steady target 推向 controlMax。维护本身是保护机制；应修的是旧结果没有在 projection 层及时降级，而不是简单取消保护机制。

3 · 目标行为与不变量

  1. journal 不丢：完整 read/tool result 继续写入原有 session journal 或 artifact；本方案不删除历史。
  2. provider 有界：旧的大型 read 结果不因“仍在 journal”而每次原文重发。
  3. 当前工作优先：当前 logical turn、未完成 tool pair、最近精确窗口和当前 prompt 不被年龄卸载。
  4. 可恢复：每个降级结果保留 tool/path/artifact/range 级引用，模型可以通过 read 或 artifact 分页取回。
  5. 维护不抖动：一次卸载/维护后，在同一 cycle 内不重复生成摘要；只有新增长越过重新开放线才允许下一 cycle。
  6. 缓存不被无谓打穿：同一 epoch 内 ContextPlan 字节和材料集合保持稳定；动态 gate 重算不等于重排整个 plan。
  7. 持久记录与投影分离：projection 的 stub、去重和卸载均为发送前转换，不修改 journal 中的原始消息。

4 · 方案总览

每次 provider call 1. 构造 transformed messages 2. 估算 raw projected input 3. 若未进入 Context Steady：按现有路径发送 4. 若已进入 Context Steady： 4.1 保护当前 turn / live tail / 未完成 tool pair 4.2 对旧的大型 completed tool result 生成 aged stub 4.3 对相同 source/range 的旧重复 read 只保留一份有效原文 4.4 重新估算最终 provider projection 5. 若仍超过 control band：只重算 gate，不立即重写稳定 plan 6. 若仍超过硬 burst ceiling：执行一次有边界的 recovery/compaction 7. provider 发送；probe 记录最终 wire projection logical turn 结束 → 生成一次 turn digest / checkpoint（若满足现有条件） 不是每个 read 结果都单独触发一次摘要。

5 · 具体设计

5.1 先用已有 aged tool-output offload，不另起一套 read 特判

当前 planner 已有 buildToolStubMaterials()：它可以跳过 protected refs，把较老、已完成且超过最小 token 数的 tool result 替换为 aged stub；materialize 再将消息内容替换成短引用。优先复用这条链路。

连续 read 应首先作为普通 completed tool result 进入这套机制，而不是在 read.ts 中再写一套只针对 session 文件的全局删除逻辑。

相关代码：packages/coding-agent/src/context-steady/planner.ts:192-293、packages/coding-agent/src/context-steady/materialize.ts:309-342、packages/coding-agent/src/prompts/context-steady/aged-output-stub.md。

消息类别默认投影策略不可卸载条件

当前 assistant tool call原文tool 未完成时保留
当前 tool result原文当前 logical turn 内保留
最近 exact window 内的结果原文由 recentExactTokens 保护
live tail 内的结果原文由 liveTailTokens 保护
较老的大型 completed read/bash/search 结果短 stub + path/artifact/range 引用受保护集、未完成 pair、当前任务必须的 exact entry

5.2 read 重复与重叠：先做安全去重，后做区间合并

同一文件连续读取常见三种重复：

read foo.ts
read foo.ts:1-300
read foo.ts:250-400

第一阶段不需要推断源代码语义，也不需要修改 session 记录。只在 provider projection 中建立一个“本轮已发出的 source identity”：

source identity = normalized source path / artifact id
                 + file snapshot identity（若可用）
                 + requested line range
                 + message role/tool call id
  • 完全相同的 path/range、且旧结果不在保护集：旧消息降为 stub。
  • 有重叠但不完全相同的 range：第一阶段不合并，只按年龄卸载旧结果；避免错误拼接行号、hashline 或上下文。
  • 文件发生 mutation 或 snapshot identity 改变：不去重，保留新旧关系由现有 superseded/coverage 规则处理。
  • journal 仍保留每次调用；用户审计、恢复和 tool-call/result 配对不改变。

现有 ContextSourceIndex 已能识别 tool pair、tool name、mutation path 和 resultEntryId，但当前路径识别主要服务于 mutation supersede。read range identity 需要新增为内部 projection 元数据，不应依赖展示文本解析。

5.3 维护触发增加滞回与 cycle 粘滞

触发线和回落线不能相同。建议：

open line：projectedInputTokens > controlMax
reclaim phase：先执行 aged offload / projection-only downgrade
close line：维护后 projectedInputTokens ≤ 0.85 × steadyTarget
same-cycle rule：maintenance cycle 未完成有效回收时，不再次生成摘要
hard line：仍超过 burstCeiling，才进入 hard_pressure / recovery

这里的 0.85 是初始方案参数，不是当前代码事实；实现时应配置化或先用常量验证。若实际数据表明 0.85 过于激进，可改为 0.9，但不能取消“回落线低于触发线”的关系。

维护结果需要区分：

结果下一步是否允许立刻再摘要
卸载后明显低于 steady target发送当前请求，cycle 关闭否；等待新增长
卸载有回收但仍在 control band 内继续 gate 计算，保持稳定材料否；不因同一原因重复摘要
卸载几乎无回收记录压力状态；若未超 burst ceiling，不重复调用摘要模型否；避免摘要抖动
超过 burst ceiling进入现有 hard-pressure recovery；失败则暂停/报明白原因只按 recovery pass 上限执行

5.4 logical turn 内不做多次 digest

连续工具循环中，read 结果会不断追加，但这不代表每个结果都已经形成一个可总结的完整用户意图。建议保持以下边界：

  • tool-loop 中只做 projection refresh、年龄卸载和最终 payload 估算。
  • 正常 logical turn settle 后，再沿用当前 #generateTurnDigest() 生成一次 consolidated digest。
  • session-stop continuation 链结束后，仍使用现有“覆盖整个 logical turn”的 boundary 规则。
  • 不要为了阻止连续 read 而把每个 tool result 写成新的 digest；这会增加 journal 和 provider 的派生消息数量。

现有 digest 生成位于 packages/coding-agent/src/session/agent-session.ts:5687-5922；当前代码已在 continuation chain 结束后生成 consolidated digest。

5.5 stable projection 的职责

stableProjection不是负责释放所有 token，它负责避免同一 epoch 内因为每次 read 增长而反复重排 ContextPlan、破坏 provider cache prefix。两者要分开：

动作允许频率触发条件
重新估算 projected input / gate每次 provider call必须实时反映 live tail 增长
替换旧 tool result 为 stub需要时超出 offload 门槛且不在保护集
重渲染 ContextPlan bytesepoch 边界checkpoint、physical compaction、topic shift、model/window change 或明确 rebase
生成 digest/checkpointlogical turn / 既有 checkpoint 周期沿用当前生命周期，不按每次 read 触发

不建议：

  • 直接把 san.contextSteady.enabled 关闭后宣称问题解决。
  • 把 activationThresholdTokens 无限提高，让维护永远不触发。
  • 把 read.defaultLimit 降到极低作为唯一方案；这会增加分页调用次数，且连续分页仍会累计上下文。
  • 在 read tool 中删除历史消息或改写 journal；这会破坏恢复、编辑和证据链。

8 · 验收标准

8.1 必须通过的行为场景

  • 连续读取同一个大型文本文件 10～20 次后，raw journal 继续增长，但 provider payload 不随所有旧 read 原文线性增长。
  • 当前 read 结果和未完成 tool pair 始终以可用原文存在；不能被 aged stub 错误替换。
  • 模型根据旧结果中的 path/range/artifact 引用再次读取时，能取回原始内容。
  • 相同 path/range 的重复 read 在 provider projection 中不会重复携带两份大正文；journal 仍保留两次调用。
  • 部分重叠 range 不发生错误合并；行号、hashline 和编辑所需的原文边界保持正确。
  • 一次 offload 后若已回落，后续 provider call 不会仅因同一批 read 再次生成 maintenance/digest。
  • offload 无法回收且 projected input 继续超过 burst ceiling 时，现有 hard-pressure recovery 仍能接管；失败路径不静默丢消息。
  • 开启 stable projection 后，同一 epoch 内 plan message bytes 稳定；动态 projected token 变化仍能参与 gate。

10 · 风险与回滚

风险：模型需要旧正文

stub 可能使模型多发一次 read。缓解：stub 必须包含 path、artifact 或精确 range；当前任务和最近窗口不卸载。

风险：coverage 误判

不改现有 coverage 授权规则；projection stub 不作为 digest coverage。保留最终 payload orphan audit。

风险：provider cache 变冷

stable projection 只在 epoch 边界重排；同一 epoch 的 gate 重算不重选材料，继续使用 wire prefix probe 验证。

回滚方式：关闭 san.contextSteady.contextPlan.toolOutputOffload 和 stableProjection 即可恢复当前 projection 行为；journal 不需要迁移或修复。若滞回逻辑出现异常，先关闭该逻辑开关或回退代码，不触碰原始 session 文件。

11 · 本稿的明确结论

  1. 连续 read 的第一解不是减少 read，而是减少旧 read 在 provider projection 中的寿命。
  2. 已有 aged tool-output offload 是最小改动起点。先打开并通过生产路径 replay，再决定是否扩展 read 专属 identity。
  3. 稳态摘要保留，但后置为兜底。先 projection offload；只有仍超过 hard ceiling 才进入 recovery。
  4. 触发线必须和回落线分离。否则维护、摘要、恢复消息会形成自己的增长和重复触发。
  5. journal、active context、provider projection 三层必须分别验收。不能用“文件仍在”证明模型每轮都应该携带全文，也不能用“provider 变短”证明历史被安全保留。
证据边界：文中标为“代码事实”的内容来自当前工作区源码读取；文件大小来自本轮对目标 session artifacts 的直接测量；阈值、年龄策略、close line、配置值和批次均为本方案建议，不代表已经实现或验证。相关源码：packages/coding-agent/src/tools/read.ts、packages/coding-agent/src/session/streaming-output.ts、packages/coding-agent/src/session/agent-session.ts、packages/coding-agent/src/context-steady/{planner,materialize,source-index,prune}.ts。
