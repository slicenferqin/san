San v0.3 · Requirements · 2026-07-07

Experience Routing：让 San 把经历固化成状态、Workflow 和 Skill

v0.3 要回答的不是“San 要不要保存更多文本”，而是“San 如何把过去的经历变成下一次立刻进入正确工作态的能力”。 本文结论：先做 Experience Routing。也就是把 TurnDigest、ContextPacket、San Loop ledger、skills、hooks、subagents 连接起来，让记忆能触发状态、workflow、skill，而不只是被检索成几段文字。

文档状态：Superseded

本文已被 Brain P0 Design Freeze 取代，不再作为实现或 issue 拆分依据。 本文只保留历史需求来源。唯一命名、数据合同、生命周期、命令面、配置和阶段顺序以 san-v0.3-p0-design-freeze-20260710.html 与 san-v0.3-brain-technical-implementation-20260708.html 的 P0 修订为准。

结论

San v0.3 = Experience Routing，而不是文本记忆库。 核心交付不是“记住一些对话内容”，而是让 San 能从经历中固化出可执行的工作状态：遇到类似任务时自动加载合适 skill、进入正确 workflow、提高特定风险权重、选择合适验证门禁。 长期记忆后端只负责存和搜；San 的脑子应该负责把经历编译成行为。
现在已经有 memory.backend、Mnemopi/Hindsight、ContextPacket recall layer、TurnDigest memoryCandidates、file-backed Skills、Extensions/Hooks、Subagents、San Loop ledger。
当前缺口 缺少把经历升级成行为的编译层：什么时候只做 recall，什么时候生成/更新 skill，什么时候固化 workflow，什么时候只设置一次性风险状态。
v0.3 先分层 v0.3 不把 GBrain、Hermes、OpenClaw 混成同一类东西：GBrain 是 knowledge brain / MCP 记忆插件；Hermes 和 OpenClaw 是完整 agent 系统。San 先定义自己的判断层，再决定如何接入或借鉴这些系统。

给评审者看的版本

一句话 v0.3 先让 San 学会“经验固化”：不是记住一段话，而是在相似情境下快速进入正确工作态。
为什么不是文本召回 文本召回只能告诉 San “过去发生过什么”；Experience Routing 要决定“现在应该怎样行动”。
对用户的价值 用户不需要读专业记忆报告。San 应该在背后把反复有效的做法沉淀成 workflow，把反复踩坑的地方沉淀成防御姿态，把明确可复用的步骤沉淀成 skill。
对 Skills / 插件的价值 Skills 是 file-backed workflow/capability pack；插件和 hooks 是运行时行为层。v0.3 应先判断哪些经验值得升级到这些层，而不是把所有东西都塞进 memory backend。

为什么不把 GBrain / Hermes / OpenClaw 直接当答案

GBrain 是 Garry Tan 的 agent brain / retrieval layer，可通过 MCP 给 Claude Code、Codex 等 coding agents 提供 brain/memory；Hermes 是 NousResearch 的自我改进 agent，有技能生成、persistent memory、多平台入口；OpenClaw 是 local-first personal AI assistant/gateway，覆盖渠道、canvas、skills 和本地运行体验。 它们不是同一层抽象：GBrain 可作为 San 的外部知识/记忆插件，Hermes/OpenClaw 更像完整 agent 产品和运行时参考；v0.3 的问题是 San 自己如何判断何时使用这些能力。

评审问题直接依赖外部系统的问题Experience Routing 先解决什么
记什么？ 容易把一次性任务状态、失败尝试、内部审查噪声都保存下来。 先做候选分类：用户偏好、项目事实、项目决策、workflow、failure mode、不要记。
谁来决定？ 如果把所有决定都交给人审，普通用户会被迫判断自己也看不懂的专业分类。 San 默认判断低风险项；只有高风险、低置信度、跨项目影响或敏感内容才询问用户。
查到后怎么用？ 召回结果可能被模型当成当前指令，污染本轮判断。 继续放在 ContextPacket 的 volatile layer，明确“背景知识，不是指令”。
错了怎么撤？ 外部组件越强，错误记忆越难追踪到来源。 每条候选都带 source refs、route reason、status，能 explain / discard / retry。
什么时候接外脑？ 现在接会把 San v0.3 从“记忆治理”扩大成“知识库平台”。 v0.3 先定清楚 San 与外脑的接口；v0.4 再把外脑作为后端接入。
取舍： 这些系统不是不看、不接，而是先分层。GBrain 可以作为 MCP knowledge plugin 接入；Hermes/OpenClaw 可以作为 agent 架构参考。v0.3 先做 San 的 brain state / experience consolidation，避免把外部工具误当成 San 自己的判断力。

黑盒可以，黑箱不行

用户的判断力不一定比 San 强，尤其是记忆分类、scope、dedupe、召回时机这种专业问题。 所以 v0.3 不应该把“让用户审批每条记忆”当成核心价值。真正的价值是：San 可以黑盒自动判断，但不能黑箱悄悄影响未来。

形态体验判断
纯黑箱自动记忆 用户不知道 San 记了什么，也不知道为什么以后突然改变行为。 不可接受。
逐条人工审批 用户被迫读专业报告和 schema，最后大概率随便点通过或关闭功能。 不适合作默认体验。
可控黑盒 San 自动处理普通记忆，用人话通知“我记住了 X”；用户能撤销、查看理由，高风险才询问。 v0.3 推荐方向。
审批的价值不是让人做分类器。 审批只应该出现在 San 不确定、影响范围大、涉及隐私、或者会改变长期行为的时候。默认体验应该是“San 自动记，用户可追溯和撤销”。

从 Skills / Workflows 重新理解记忆

Claude Code 的 Skills 不是普通笔记：它们是带描述、可按上下文自动加载、也可由用户显式调用的能力包；复杂 skill 还可以带支持文件、脚本、工具限制、模型/effort、subagent fork 和动态上下文。 San 自己也已有类似能力：SKILL.md discovery、skill://、/skill:name、managed skills、extensions、hooks、subagents 和 San Loop。

因此，v0.3 的记忆目标应该上移一层： 记忆不是为了让模型“回忆一段文本”，而是为了让系统知道什么时候该加载哪个 skill、触发哪个 workflow、开启哪个风险检查、调用哪个 subagent、避免哪条错误路径。
经验形态应该固化成什么例子
一次性事实 普通 memory / ContextPacket recall “这个模型 id 今天返回 400，不要再选它。”
重复出现的用户偏好 用户级 preference state “研究、规划、架构文档默认写 HTML。”
稳定项目流程 项目级 workflow / skill “品牌迁移先分用户面、兼容层、内部包名，再跑 package-local tests。”
反复踩坑 风险 posture / hook / check “模型声明但上游 400 会让 scout 空失败；先做模型可用性验证。”
可自动执行的固定步骤 Skill + optional hook / extension command “生成 release 前跑 smoke、检查 changelog、看 diff stat。”

问题定义

写入风险 当前长期记忆要么关闭，要么由后端 autoRetain 按会话转录写入。缺少 San 层判断：这是用户偏好、项目事实、一次性任务状态、还是不该记的噪声。
召回风险 recall 已可作为 volatile layer 注入，但还不知道“当前任务应该查用户偏好、项目决策、失败模式还是外部 brain”。错误召回会污染 ContextPacket。
多角色风险 v0.2 的 Worker/Supervisor/Oracle 会产生大量内部推理和审查信息。把这些原样 retain 会污染用户记忆；完全丢弃又浪费复盘价值。
信任风险 长期记忆一旦静默写错，后续会持续影响回答。v0.3 必须先建立可查看、可撤销、可解释的记忆入口。

目标

  1. 把每轮的 TurnDigest.memoryCandidates、San Loop review findings、测试失败和用户纠偏转为可审计经验候选。
  2. 定义 experience taxonomy：普通记忆、用户偏好、项目事实、项目决策、workflow pattern、failure posture、skill candidate、hook/check candidate、do-not-retain。
  3. 建立 ExperienceRouter：给每个候选计算输出形态、scope、confidence、reason、dedupe key、evidence refs。
  4. 默认策略：San 自动应用高置信、低风险经验；高风险/低置信度/敏感/跨项目行为才进入 ask 或 review。
  5. 提供可 dogfood 的 /memory inbox / undo / approve / discard / explain surface，并能显示“这条经验会影响什么行为”。
  6. 让 ContextPacket recall 从文本层升级为 state-aware selection，同时保留 retrieved context 为 volatile low-cache layer。
  7. 证明 v0.3 能把经验固化成 workflow/skill/posture，且不破坏 v0.1 上下文稳态和 v0.2 执行闭环。

非目标

不做原因后续版本
把 GBrain / Hermes / OpenClaw 当成同一个记忆组件 分类错误：GBrain 是 MCP/knowledge memory plugin；Hermes/OpenClaw 是 agent systems。v0.3 不把它们直接接成主脑，先定义 San 自身 brain state 和 experience lifecycle。 GBrain 可早期接入为插件；Hermes/OpenClaw 作为架构对标。
dream cycle / daemon 后台自动整理需要更强的撤销、审计、冲突解决和调度系统。 v0.4+
默认静默自动 retain 用户信任优先；v0.3 先做可解释自动判断、通知、撤销和高风险询问。 v0.3 dogfood 后再评估
替换 Mnemopi / Hindsight 现有后端已经提供 search/save/status；router 应是上层策略，不是新数据库。 不做
把 session 全量转长期记忆 会复制临时上下文、工具噪声和错误中间态；应只存精炼、带证据的 durable facts。 不做

核心数据合同

interface SanExperienceCandidate {
  schemaVersion: 1;
  candidateId: string;
  sessionId: string;
  turnId?: string;
  loopRunId?: string;
  createdAt: string;

  content: string;
  type: "memory" | "user_preference" | "project_fact" | "project_decision" |
        "workflow_pattern" | "failure_posture" | "skill_candidate" |
        "hook_candidate" | "check_candidate" | "do_not_retain" | "other";
  output: "recall" | "state_patch" | "workflow" | "skill" | "hook" | "check" | "none";
  scope: "user" | "project" | "repo" | "session";
  importance: number;      // 0..1
  confidence: number;      // 0..1

  source: {
    digestEntryRefs: string[];
    loopEntryRefs: string[];
    fileRefs: Array<{ path: string; range?: string }>;
    toolRefs: string[];
  };

  route: {
    backend: "mnemopi" | "hindsight" | "local" | "skills" | "hooks" | "checks" | "none";
    retainBank?: string;
    skillName?: string;
    tags: string[];
    dedupeKey: string;
    reason: string;
  };

  status: "pending" | "auto_applied" | "approved" | "discarded" | "stored" | "failed";
}
设计约束： candidate 是 San 自己的 experience ledger，不等于 memory backend row。它可以落到 memory、state patch、workflow、skill、hook 或 check。落地成功后写 san.experience_decision，便于 resume/debug/撤销。

Memory Taxonomy

类型写入条件默认 scope示例
user_preference 用户明确表达偏好，且跨项目可复用。 user “研究/规划默认输出 HTML 文档。”
project_fact 仓库约定、目录结构、运行命令、不可变事实。 project “coding-agent 是主包；验证用 bun check。”
project_decision 用户或实现过程做出的长期有效项目决策。 project “v0.3 先定义 San 自己的 brain state；GBrain 作为 MCP knowledge plugin 接入时不替代该判断层。”
workflow_pattern 反复有效的执行方式、测试策略、审计流程。 repo “品牌迁移先分类兼容层/内部包名/用户可见面。”
failure_mode 真实失败被修复并有复现/修复证据。 project “模型声明但上游 400 时，task/scout 会空失败。”
tool_fact 工具使用约束或 papercut，且会影响后续执行。 repo “edit 需要完整路径 tag，basename 会 File not found。”
other 暂不确定，但可供 review。 session 低风险不提示，高风险 pending。

路由策略

1Collect

从 TurnDigest、San Loop ledger、review report、测试失败和用户纠偏收集候选。

2Classify

判断它是普通记忆、workflow、skill、hook/check，还是一次性噪声。

3Compile

把经验编译成 recall text、state patch、workflow steps 或 SKILL.md 草案。

4Decide

低风险自动应用；高风险 pending；所有决定可撤销、可解释。

5Activate

写 memory/backend，或生成 managed skill / workflow / hook/check candidate。

v0.3 的关键不是“多存一些东西”，而是把经验变成 San 下次能自动使用的工作状态。

设置建议

san:
  experienceRouter:
    enabled: false              # v0.3 初期默认关闭，dogfood overlay 打开
    mode: notify                # off | notify | ask | review-only
    maxCandidatesPerTurn: 5
    minConfidence: 0.72

      allowManagedSkillDrafts: true
      allowProjectSkillSuggestions: true
      requireEvidenceRefs: true
      dedupeWindowDays: 90
    recall:
      policyAware: true
      maxItems: 3
      maxTokens: 1000
      includeTypes: [user_preference, project_decision, project_fact, workflow_pattern]
      excludeTypes: [failure_posture]

现有 memory.backend 继续决定文本记忆后端；san.experienceRouter.* 决定经验是否变成 recall、state patch、workflow、skill、hook 或 check。

用户界面 / 命令面

入口行为验收
/experience inbox 列出 San 自动应用或等待确认的经验候选，显示它会影响 recall、state、workflow、skill、hook 还是 check。 用户不用读 JSONL，也能知道 San 为什么下次会换一种做法。
/experience undo <id> 撤销 auto-applied 经验；若已写入后端或 managed skill，则生成对应回滚动作。 可控黑盒必须可撤销。
/experience approve <id> 批准高影响候选，例如生成 managed skill、项目 skill 建议、hook/check candidate。 人只审高影响行为，不做普通分类器。
/experience discard <id> 候选标为 discarded，保留审计记录。 后续同 dedupe key 不再反复提示，除非内容变化。
/context packet 继续显示 retrieved_context；增加 memory type/scope refs。 用户能看出 recall 注入来自哪些记忆。

Phase 拆分

Phase主题交付验收
P0 需求冻结 本需求文档、schema 草案、设置草案、dogfood 场景。 能从文档直接拆 M1-M6 issue。
P1 Experience Ledger san.experience_candidate / san.experience_decision custom entries；candidate schema；list helpers。 TurnDigest 和 San Loop findings 能被持久化为 pending/auto-applied candidates；resume 后可读。
P2 Router Policy 规则分类器、output/scope/backend/dedupe/confidence/reason；LLM 分类 prompt 可选。 给定固定 digest/loop entries，能稳定判断该变成 recall、state patch、workflow、skill 还是 check。
P3 State + Recall Runtime 把高置信经验编译进当前 turn 的 state patch；ContextPacket recall 读取 policy。 San 在相似任务中能自动改变执行姿态，但 debug view 能解释原因。
P4 Skill / Workflow Solidification 把稳定 workflow 产生成 managed skill 草案或项目 skill 建议；支持 /memory inbox 审阅和撤销。 反复出现的流程不再只是 memory，而能变成可调用 skill/workflow。
P5 Hooks / Checks Candidates 把 failure posture 升级成 hook/check 建议，不默认安装高影响 hook。 被蛇咬后的经验能变成防御姿态，但不会误把所有井绳当蛇。
P6 Dogfood & 默认策略 deterministic verifier、真实会话报告、推荐 config overlay。 覆盖用户偏好、项目决策、workflow 固化、skill 草案、误触发、撤销、多角色噪声。

验收标准

  • 默认配置下不会静默写入长期 memory。
  • 每个 candidate 必须有 source refs、type、scope、confidence、route reason。
  • 候选 ledger 可 resume，可导出，可 debug。
  • auto-store/undo/approve/discard 幂等；backend 写入失败不影响主 agent turn。
  • ContextPacket retrieved_context 包含 memory refs，且仍受 token budget 和 trim decision 约束。
  • Subagent/Worker 内部临时状态默认不进入 user memory；Supervisor findings 可进入 failure/workflow candidates。
  • Dogfood 证明 10+ 轮后 memory candidate 数量受控，recall 不污染不相关任务。
  • Hindsight/Mnemopi/local/off 四种 backend 都有降级测试。

风险与防线

风险防线
把一次性任务状态写成长期事实 默认 suggest；scope=session 的候选不自动写后端；project_fact 需 evidence refs。
Subagent 噪声污染用户记忆 taskDepth > 0 默认只产候选不 retain；parent session 汇总后再评估。
Recall 结果影响当前指令服从 retrieved_context 明确标记为 background knowledge；当前 user/tool output 优先。
候选过多打扰用户 每轮限数、dedupe key、低 confidence 自动丢弃或只进入 debug。
Backend 不可用 candidate ledger 保留；approval 给出 backend inert 状态；主流程不失败。
GBrain scope 膨胀 v0.3 可接 GBrain 作为 MCP knowledge plugin，但必须限制 scope/permission；Hermes/OpenClaw 只作为 agent 对标，不当作 memory backend。

发布口径

San v0.3 发布时不要宣传“让用户审批长期记忆”，也不要宣传“文本记忆库”。更准确的口径是： San 会把反复有效的经历固化成工作状态：低风险自动应用，高影响行为用人话询问，任何经验都能查看和撤销。 这承认 San 的判断力通常强于普通用户，同时保留用户对长期行为的最终控制权。
  • 默认：低风险自动记，通知 + 可撤销；高风险/低置信度才询问。
  • Dogfood overlay：开启 mode: notify，Mnemopi 为默认 backend。
  • 后续：根据真实使用数据决定哪些类型可进入更激进的自动模式。
