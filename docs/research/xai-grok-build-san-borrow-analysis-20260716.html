Grok Build × San 交叉分析

源仓库：https://github.com/xai-org/grok-build（SpaceXAI 终端 coding agent，Rust 单仓同步产物） · 对照仓库：本仓 San（Bun/TS，Context Steady + Execution Loop + Brain + Workflows）

日期：2026-07-16 分析对象：main @ b189869 类型：架构借鉴 / 路线筛选 结论：可借鉴，但不该整仓抄 文件：xai-grok-build-san-borrow-analysis-20260716.html
一句话结论

Grok Build 是工业级 harness 产品：TUI、权限、OS sandbox、session 恢复、subagent 生态、memory、worktree 都做得很厚。 San 是执行系统产品：Context Steady、多角色 ledger、Brain 经验、Workflows 才是差异化。 对 San 最有价值的不是再做一个“Grok 克隆”，而是挑 6–8 个补齐工程闭环的点：OS sandbox、memory dream/flush、hunk 归因、后台任务协调、folder trust、permission 分层、plan 审批 UX、capability 偏序。

1. Grok Build 是什么

定位

SpaceXAI 的终端 AI coding agent（二进制名 grok / 源码产物 xai-grok-pager）。全屏 TUI、headless、ACP IDE 集成。

栈

Rust monorepo 切片；~60 个 codegen crate；ratatui TUI；workspace hub；sqlite journal；tree-sitter code graph。

对外贡献

CONTRIBUTING.md 明确不接受外部贡献；仓库是 monorepo 定期同步。可当参考实现，不可当 upstream 协作对象。

系谱痕迹

THIRD-PARTY-NOTICES 声明 tools 实现有 openai/codex、sst/opencode 端口；与 San 同属 coding-agent harness 谱系，不是正交领域。

3. 最值得借鉴的点（按 ROI 排序）

P0 3.1 OS-level Sandbox（补安全底座）

Grok 做法：--sandbox workspace|read-only|strict|devbox；macOS Seatbelt、Linux Landlock + bubblewrap deny bind-over；自定义 profile 支持 deny glob（含 **/.env），并显式关闭 mv secret && cat 类旁路。

San 现状：task isolation / path-scope / approval 主要是应用层；主会话 bash 仍可触达任意路径（依赖用户信任）。

可迁移形态（不必照搬 Rust crate）：

  • 先做 san.sandbox.profile = off|workspace|read-only|strict 设置与 CLI 开关。
  • macOS 用 Seatbelt profile 包住 bash 子进程；Linux 用 landlock/bwrap（有则启用，无则 fail-closed 或降级警告）。
  • 与现有 path-scope / workflows isolated write 叠加，不互相替代。

为什么现在值得做：San 的 loop/workflows/team worker 会并发跑工具；没有 kernel 边界时，“可审计执行”仍可能误伤本机秘密文件。

P0 3.2 Permission 分层 + Folder Trust

Grok 授权流水线：

PreToolUse hooks
 → deny/ask/allow rules
 → remembered grants（危险命令除外）
 → 内置只读自动批准（工具 + shell 白名单分句）
 → permission mode（default / dontAsk / acceptEdits / bypass）

Folder trust 把 project hooks / MCP / LSP 统一成“是否信任这个目录”的一门闸。

对 San：今天 approval 与 settings 有碎片感。可把“项目是否受信任”抽成统一 gate，驱动：

  • 项目级 MCP / skills / workflows discovery
  • 默认 write 权限策略
  • San Loop team/council 是否允许自动跑 checks

P1 3.3 Memory Dream + 压实前 Flush + Hybrid Recall

Grok 亮点：

  • 存储是人可读 Markdown（global / workspace / session logs），不是黑盒向量库 alone。
  • SQLite FTS5 + 可选 vec0 hybrid search。
  • autoDream：按时间 + 会话数 gate，把 session logs 合并进 durable MEMORY.md（消矛盾、绝对日期、丢短暂细节）。
  • pre-compaction memory flush：在 compact 丢历史前，先强制把重要事实写入 memory。
  • 可选 MMR 去冗余重排（Jaccard，无 embedding 也可）。

对 San 的映射：

  • San Brain 的 capture → approve → consolidate → project 已比 Grok “更结构化/可审计”。
  • 缺口在：压实/裁剪前强制 flush、跨 session 人可读 curated 层、检索多样性（MMR）、以及 “dream gate” 的节流策略。
  • 建议：给 Context Steady compaction / plan rebuild 前加 san.brain.flushBeforePrune；给 Brain consolidate 加 dream 风格的时间/会话阈值，避免每轮都 consolidate。

P1 3.4 Hunk Tracker（Agent vs External 归因）

Grok 用 actor 模式跟踪文件 hunk，区分 agent 写入与外部编辑，支持 accept/reject，并与 fs_notify 合流。

对 San 的价值：

  • Context Steady TurnDigest 的 files_touched 可以更准（过滤用户手动改动）。
  • San Loop Supervisor 复验可以只审 agent 引入 diff。
  • Workflows isolated write review 可从“整文件 artifact”升级到 “hunk-level 决策”。

不必一次性做完整 IDE-style review UI；先做 session 内 hunk ledger + 归因标签即可。

P1 3.5 后台任务协调：background / wait_any|all / monitor /loop

Grok 把长跑进程从“阻塞对话”中解放出来：

  • run_terminal_command(background=true) → task_id
  • get_command_or_subagent_output / wait_commands_or_subagents(mode=wait_any|wait_all)
  • monitor 把脚本逐行事件注入会话
  • /loop 5m ... 周期 prompt（带过期与上限）

对 San：team/council 与 dogfood、dev server + 测例并行特别受益。现有 job/task 可统一到同一 task bus，并让 San Loop Worker 的并行等待语义与 runner 的 sibling abort 共用同一取消传播模型（mapWithLimit abort 方向一致）。

P2 3.6 Plan Mode 审批 UX

Grok 的 plan 审批不是“是/否”：可滚动预览、行级评论、改计划、空 plan 仍可决策、compact 后仍保持 plan 状态。

San 已有 plan protection 与 approved plan handoff。可借鉴的是 人机共审协议：

  • 行注释 → 回灌给 agent 修订 plan
  • plan 状态穿越 compaction / ContextPlan rebuild
  • 与 San Loop Commander 输出 plan 的 ledger 挂钩（plan revision 进入 loop event）

P2 3.7 Subagent Capability 偏序 + Personas 分层

Grok 把：

  • Agent：会话本体（model/tools/prompt）
  • Persona：行为覆盖（tone/format/IO 契约）
  • CapabilityMode：ReadOnly ⊂ ReadWrite 等偏序，过滤工具集

San Loop 已有角色（Commander/Worker/Supervisor/Oracle），但 capability 过滤更多散落在工具与 path-scope。可把 “角色 → capability 偏序 → 允许工具/写范围” 做成显式表，减少 prompt 文本约束泄漏。

P2 3.8 Agent completionRequirement（强制收口）

Grok agent 定义可要求结束前必须调用 complete_task，否则自动提醒重试（带 maxRetries/backoff）。

对 San Loop Worker / Workflows agent bridge 很实用：避免 “讲完故事却不交付结构化结果”，与 delivery receipts / run snapshot 终端状态机对齐。

P3 3.9 Codebase Graph（可选加速）

tree-sitter 增量索引 + goto def/refs，适合 explore/plan 代理降工具往返。San 可作可选后台索引（不阻塞启动），喂给 Context Steady relevance 或 San Brain evidence。优先级低于安全与记忆 flush。

P3 3.10 Fast Worktree Pool

Grok 的 CoW/BTRFS/overlay pool 主要解决“大仓频繁 spawn 的启动成本”。San 已有 iso；若 dogfood 显示 isolation spawn 成为瓶颈，再引入 pool / dirty-sync。不要先做。

4. 不建议照搬的点

项原因
整仓 Rust 重写 harness San 的差异化在 Context Steady / Loop / Brain / Workflows，已在 Bun/TS 落地并 dogfood；迁移成本会吞噬路线图。
Claude/Cursor 兼容层堆叠 Grok 作为大众 CLI 需要兼容面；San 作为独立产品应优先自己的 .san 契约，兼容可作为后置。
xAI 绑定的 auth/telemetry 产品形态 与 San 多 provider 路线冲突。
用 classic compact 取代 Context Steady Grok 的 compact+memory 是“丢历史后靠记忆找回”；San 走的是“provider-bound 稳态 + 可审计 digest”。方向不要回退。
把 subagent personas 当 San Loop 替代品 personas 是提示层；San Loop 是状态机 + ledger + checks。可叠加，不可替换。

5. 建议落到 San 路线图的方式

5.1 与现有版本叙事对齐

San 版本轴可吸收的 Grok 点验收形态
v0.1 Context Steady compact/prune 前 memory/brain flush；hunk 归因提升 files_touched 质量 压实后关键事实仍可在下一轮 ContextPlan/Brain activation 中出现
v0.2 Execution Loop sibling abort + 后台 wait；Worker capability 偏序；completionRequirement team 模式失败收敛、Worker 不交付结构化结果会自动收口
v0.3 Brain dream gate、hybrid recall、MMR、人可读 curated MEMORY 层 跨 session 召回质量 + 巩固节流可测
v0.4 Workflows hunk-level write review；folder trust 对 project workflows/hooks isolated write 可 hunk 审；未信任仓库不自动加载危险扩展
v0.5 路由 / 模型选择 agent profile 作为路由目标的一部分；plan 审批反馈进入路由证据 任务类型 → 角色/能力/模型 的可解释选择
横切平台能力 OS sandbox + permission mode + 后台任务 bus 默认安全姿态可声明；长任务不阻塞 loop

5.2 推荐落地顺序（90 天量级）

  1. Week 1–2：Permission + Folder Trust 契约
    统一 project trust gate；整理 deny/ask/allow 与现有 approval 的优先级文档 + 最小实现。
  2. Week 2–5：Sandbox MVP
    workspace/read-only 两档；包住 bash 与 subagent；dogfood 用 strict 跑 explore。
  3. Week 3–6：Brain flush-before-prune + dream gate
    接 Context Steady 压实路径；consolidate 频率化；补 hybrid search 质量指标。
  4. Week 5–8：Task bus（background/wait/monitor）
    统一 job/subagent/loop 等待与取消；San Loop 并行 Worker 复用。
  5. Week 7–10：Hunk ledger MVP
    agent write 归因 + session 查询 API；Supervisor/Workflows review 消费。
  6. 之后可选： plan 行评论 UX、code graph 后台索引、worktree pool。

6. 对 San 差异化的再确认

继续 fortify（San 自己的 moat）

  • Context Steady / ContextPlan 质量门
  • San Loop ledger + checks + 多角色收敛
  • Brain approve/project 可审计经验系统
  • Workflows restricted runtime + exactly-once delivery

从 Grok 补齐（工业 harness 短板）

  • OS sandbox 与 permission 分层
  • 长任务后台协调
  • 改动 hunk 归因与审阅
  • 记忆巩固的节流与压实联动

明确不做

  • 重写为 Grok 风格通用 CLI 全家桶
  • 用 personas 取代 loop 角色状态机
  • 用 classic compact 取代 Context Steady

8. 最终判断

能帮助 San 吗？能。 主要帮助在于把 “可审计执行系统” 补成 “可在真实机器上安全、可恢复、可并行运行的工程 runtime”。

Grok 强在 harness 完成度；San 强在 执行语义与上下文稳态。 正确策略是：吸收 Grok 的安全、并发、审阅、记忆巩固机制，继续加深 San 自己的 loop/brain/context/workflows 叙事，而不是追齐它的功能目录。

若只挑 3 个立刻动手的点：① OS sandbox + folder trust；② compact/prune 前 Brain flush + dream gate；③ 统一 background task bus（含 wait/cancel）。
