Design only · 2026-08-27 · Context Steady Recovery

把窗口压在稳态区间，尽量不触发 /compact

本方案不是“超过阈值就摘要”，也不是“永远不停止”。目标是维护一个足够小、足够精确、细节可恢复的当前工作集：先在工具层控制增长，再用确定性投影释放空间；只有这些办法无法让 provider 请求 fit 时，才使用原生 compaction，最后才暂停。

设计优先：暂不改代码保护语义，减少重写等待评审后实现

先看结论

目标

稳态优先

把常态输入维持在 steady/control 区间。轻微超出先维护，不立即重写整段 session。

第一手手段

工具结果可恢复压缩

完整结果写入 artifact，provider 只看到受限预览、状态和回读入口；这是解决大工具输出的主要办法。

最后手段

原生 compaction 后再救援

跨 turn 压缩仍不 fit 时，允许处理最近 tail 中已经完成且可恢复的普通工具结果；确实无解才暂停。

一句话：digest 保存语义状态；工具 offload 释放正文；原生 /compact 只负责更大范围的历史重写；artifact 保证被释放的细节仍然可找回。

一张图看懂完整控制流

蓝色是测量，黄色是确定性回收，紫色是原生 compaction，绿色是继续，红色是最终暂停。新增的关键不是再跑几次摘要，而是让 hard pressure 能处理“最近但已经完成的普通工具结果”。

先把三种“压缩”分开

机制处理对象是否改写语义正确职责
Context Steady digest旧历史的任务状态有损保存目标、决策、已完成事项、未决问题和下一步；不能冒充精确代码证据。
工具输出 offload / shake工具结果正文确定性投影完整原文保留在 artifact，当前 payload 只保留状态、关键片段和回读入口。
native compaction / /compact完整历史 turn有损重写跨 turn 释放空间；按 boundary 工作，不能保证切开最近 turn 的单个结果。
emergency artifact elide最近 tail 内已完成普通工具结果当前视图替换，原文不丢补上 native compaction 的盲区，避免“最近窗口保护”把整个请求锁死。
关键判断：保护的是“当前任务仍依赖的 exact working set”，不是“最近出现过的所有原文”。如果一个普通工具结果已经完成、有完整配对、有 artifact 且 placeholder 可回读，就不应因为它在最近窗口内而永远不可释放。

上下文应维护两个视图

完整历史

不删除、不丢证据

session journal 和 artifact 保留完整调用、结果和原始细节。它是恢复来源，不等于每次 provider 请求都要携带全部内容。

当前工作集

小而精确、可以继续工作

只放当前 prompt、未完成链路、任务约束、正在编辑所需内容、未解决错误和仍有依赖的事实。其他正文通过确定性投影释放。

必须精确保留

  • 当前 user prompt 和明确验收条件。
  • 未完成的 tool call、半截流式结果和调用/结果配对。
  • 正在编辑文件的必要内容。
  • 最近且尚未被覆盖的关键错误。
  • 计划、规则以及当前仍依赖的决策。

允许可恢复压缩

  • 已完成的 stdout、搜索结果和文件预览。
  • 已完成测试的普通输出。
  • 旧网页文本、旧 diff 和旧图片。
  • 有 artifact 来源的最近普通工具正文。
  • 已经被后续事实覆盖的重复内容。

为什么现有路径会暂停

现有死角

四个机制叠在一起

  1. provider projection 超过 burst ceiling。
  2. native compaction 只能在 turn boundary 压缩旧历史。
  3. 普通 shake 保护最近窗口，最近大结果因此无法入选。
  4. 恢复 pass 用尽，重测仍不 fit，为避免 compact/retry 活锁而暂停。
设计修正

把最近大结果拆成两部分处理

  1. 任务状态和未完成链路继续保护。
  2. 已完成普通正文进入 artifact-backed placeholder。
  3. 重建 projection 并再次验证，而不是只看存储 token 是否下降。
  4. 只有不可安全处理的 exact working set 仍超限时才暂停。
因此，主动暂停是安全阀，不应被删除。不合理的是把“最近窗口不能动”当成绝对规则，导致本来可以恢复的请求直接进入安全阀。

约束“模型一直读、一直输出”的完整方案

提示词只能软引导；真正的增长约束必须在工具返回层和 context projection 层执行。

工具层

单结果双预算

每个工具同时受 token 和 bytes 限制。完整结果落 artifact，provider 只拿受限预览；不能让异常 payload 绕过预算。

回合层

共享 logical-turn budget

同一回合的多个工具共享总输出预算，避免每个结果单独合规、叠加后整体超过 burst。

工具策略

按工具保留不同信息

read 按范围分页；grep 按匹配数和行宽；bash 保留退出码、错误和头尾；browser、diff、图片使用独立预览策略。

模型层

提示先分页、先搜索

提示模型避免全量日志和重复读取，但即使模型忽略提示，wrapper 也必须限制最终可见正文。

read 的特殊点：read 已有自己的固定截断和 output-meta spill 路径。设计实现时要把 read 纳入当前回合预算；不能假设普通 wrapper 的 artifact threshold 会自动覆盖 read 的所有返回路径。

预算模型：以真实 provider input 为准

projectedProviderInput
  = system prompt
  + tool definitions / schemas
  + 当前 conversation messages
  + 当前 tool calls / results
  + reserve

可用窗口不是 model.contextWindow 的裸值
steady target 是维护目标，不是 provider 保证的硬容量
burst ceiling 也不能超过 provider 实际可接受的输入

这段对话中出现过 256K 模型窗口、200K quality window、320K burst 等配置讨论；这些数字不能直接相减得出真实可用消息预算。实现时必须把 system、工具 schema、reserve、当前请求和实际序列化结果一起计算，且每次恢复后重新测量。

不要用摘要模型扩大主模型窗口。摘要模型可以帮助生成 digest，但不能让主 provider 的 256K 请求容纳更多内容；也不能用“本地估算已下降”替代真实 provider projection 的 fit 判断。

emergency artifact elide 的安全边界

可以处理

  • 已经完成且有明确 call/result 配对的普通工具结果。
  • stdout、搜索结果、文件预览、网页文本、旧 diff。
  • 已写入 artifact、可以重新读取的完整原文。
  • 能保留工具名、状态、关键片段和回读入口的结果。

不能处理

  • 未完成的调用、半截流式结果。
  • 当前 user prompt 和明确任务约束。
  • 没有 artifact、无法重建来源的唯一事实。
  • 当前仍依赖的 plan、skill、错误和 exact working set。

状态机的防活锁规则

PASSprojection 在 control band 内，直接发送；不做 compaction。
MAINTENANCE轻微超过 control 时，先做 aged tool offload、当前回合预算收缩和一次重测；只有超过滞回条件才升级。
HARD PRESSURE超过 burst 时，执行一次 native compaction；不能因为多跑 pass 就期待同一大结果自动消失。
EMERGENCYcompact 后仍不 fit，选择可恢复的最近普通工具正文做 artifact elide；每次动作后重新构建 projection。
FAIL-CLOSED仍然不 fit 时，不重复发送同一个 oversized request；转 handoff / 新 context epoch，或暂停并说明是“保留内容超过当前可用上下文”。
硬规则：每个 recovery pass 必须产生可验证的 projection 变化或明确结束；禁止 compact → retry → compact → retry 无限循环，也不能只依据 stored token 下降判断成功。

建议的第一版实现边界

区域第一版责任不做什么
agent-session.ts在 native compaction dead-end 后接 emergency elide；以重建后的 provider projection 判断 fit。不增加无限 recovery pass，不删除最终暂停。
packages/agent/src/compaction/shake.ts提供“只选择已完成普通 tool result”的 emergency 策略；保留 call/result 关联和 artifact 入口。不触碰未完成调用、当前 prompt 或受保护任务材料。
context-steady/planner.ts继续负责 steady-state 的 aged offload；明确维护后重新规划的状态。不把 digest 当作精确工具正文的替代物。
tools/read.ts、tools/output-meta.ts统一 read 与其他工具的 token/byte 可见预算，保留分页和回读入口。不修改模型请求的原始命令或读取语义。
packages/coding-agent/test/覆盖 hard pressure、最近大结果 rescue、不可恢复状态暂停、防重复 oversized request。不测试源代码文本，不用 mock.module 污染全局模块注册表。

验收标准

恢复成功

  • 最近 turn 含超大但已完成的普通 tool result。
  • native compaction 后仍超过 burst ceiling。
  • emergency elide 生成 placeholder 和 artifact 回读入口。
  • 重建 projection 回到 provider 可接受范围。
  • 原始结果可重新读取。
  • 原请求继续执行，不需要用户手动输入 /compact。

必须暂停

  • user prompt、未完成调用或不可恢复 exact working set 本身超过可用窗口。
  • 所有可安全回收内容都已处理，projection 仍不 fit。
  • 恢复动作没有可验证的输入下降。
  • 系统不会重复发送同一 oversized provider request。
  • 暂停原因明确说明“保留内容超过可用上下文”。

实现前需要确认的三个产品决策

A：允许压缩最近窗口内已完成的普通工具结果吗？（建议：允许）

允许。保护任务状态、未完成链路和可恢复性；只要原文已经落 artifact、调用/结果关联完整、placeholder 可回读，就不应把整段正文永久留在 provider payload。

B：emergency elide 默认开启吗？（建议：开启，但只在 hard pressure 触发）

建议默认开启 emergency 策略，同时保留普通 aged tool-output offload 的配置开关。这样正常路径不改变，只有 native compaction 无法 fit 时才启用更激进的最近结果释放。

C：统一工具预算按 bytes 还是 tokens？（建议：tokens 主限额，bytes 硬底线）

tokens 更接近 provider 成本和上下文占用；bytes 用于防止异常大 payload。read 的实际分页仍可按行和字节执行，但最终必须受 token/byte 双预算共同约束。
