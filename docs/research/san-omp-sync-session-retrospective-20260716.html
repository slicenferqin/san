关键缺陷

P0-01 · Context Steady recent-exact deadlock

固定保护最近 3 个 turn，在“一个 turn 含数百次工具调用”时等价于保护整个会话

当前 #contextSteadyRecentExactEntryRefs(..., 3) 按 user turn 数量保护 raw entries，不按 token 限制。第一次长工具回合尚未结束时，第二条用户消息已经让 297 个条目成为 protected exact context；后续分别达到 280、290、501 个。权威 TurnDigest 虽然存在，但 protected refs 不允许被 digest coverage 替换。

10:40edit 成功 → hard_pressure 227,475 → 无下一次 provider call
12:38edit 成功 → hard_pressure 226,093 → 再次停止
01:37edit 成功 → hard_pressure 226,232 → 进入 compaction
02:46冲突 read 完成 → hard_pressure 231,794 → 13 分钟 compaction

这是用户反复感知“做一点就停”的主要可证实根因，不应只归因于模型行为或进度答复。源码中的 tool-loop re-gate 在 hard pressure 时会持久化 audit 并直接抛错，todo reminder 只处理正常 stop，无法恢复这条异常路径。

P0-02 · Post-compaction refusal loop

压缩已经把 projected input 降到 28K，quality gate 仍因 484 个 raw protected refs 拒绝请求

最后一次 snapcompact 将 provider 投影从约 249K 降到 46,867、31,017、28,188，均远低于 225,000 上限；但 gate 仍返回 hard_pressure，原因只剩 protected_entries_exceed_message_budget/control_band/burst_ceiling。也就是说，active provider context 已缩小，source-index 的 raw 保护集合却没有同步释放。

  • 02:59、03:00:05、03:00:35、03:01 四条用户消息后都只有 ContextPlan audit，没有 assistant request。
  • 03:00:21 压缩成功写入 17 个 snapcompact frames，仍未使下一条 prompt 可执行。
  • 03:00:45 session 正常 dispose；重新 resume 后同样立即 hard pressure。

这证明恢复流程不是“压缩慢”，而是压缩结果与 quality gate 的保护权威不一致。该状态无法靠用户继续追问自愈。

P1-01 · Budget pressure checkpoint cannot preempt cadence

checkpoint 每 6 turn 的配置在本样本中按设计没有触发，但预算压力也无法强制提前折叠

会话只有 5 个已结算 TurnDigest，全部是 fallback=false 的权威摘要，所以 0 checkpoint 符合当前 everyTurns=6 合同。问题在于：单个 turn 已经超过稳态预算，budget_pressure 仍必须等待第 6 个 turn 才能建立 checkpoint，恰好错过最需要它的时刻。

P1-02 · Retry policy is reliable but too coarse

10 次连续重试最终恢复成功；问题是不同故障类型共享同一条 10-attempt 跑道

01:57:03 到 02:07:50 的一次请求经历 3 次 first-event timeout 和 7 次 account concurrency limit，恰好用满默认 retry.maxRetries=10，第 11 次请求成功。所有失败条目都写入 retryRecovery.status=recovered。02:35 的 timeout 和 02:38 的 stream stall 也都在第一次重试后恢复。

因此“自动恢复失败”不是事实；真正的问题是第一条 retry train 占用约 10 分 47 秒，且 concurrency limit、首事件超时、 流中断没有独立预算和退避。Provider 报的是 account concurrency，根因可能跨进程或来自其他会话，不能仅凭本 JSONL 判定为当前进程发出了并行请求。

P1-03 · Intra-turn cost remains unbounded

TurnDigest 只在 settle 后产生，无法压缩单个 200+ provider-call 的工具回合

会话累计记录 35.92M tokens，其中 32.23M 是 cache read。缓存降低了部分成本，但不改变 229 次 provider request 反复携带大上下文的事实。Context Steady 对跨 turn 有摘要，对一个持续一小时、包含数百条 tool call/result 的 turn 缺少滚动摘要或 token-bounded raw tail。

P2-01 · Same-task progress prompts become topic_shift

“当前进度如何”被标成 topic_shift，进一步阻断 derived material 复用

12:38 和 01:37 的计划均记录 rebaseReason=topic_shift，但用户只是在询问同一上游同步任务的进度。 当前 continuation markers 不覆盖“进度”“什么进度”等表达，且自然话题判断在短中文提示上缺乏足够语义锚点。

P2-02 · Audit lacks the number that explains the refusal

projectedInputTokens 很低时仍 hard_pressure，但 audit 没有持久化 requiredTokens / selectedInputTokens

最后几份 audit 展示 projected input 只有 28K–47K，却只给出三条 protected overflow reason。源码实际还计算了 requiredTokens 和 selectedInputTokens，但没有把它们写入 audit。这使现场看起来像 gate 自相矛盾， 增加了排障成本。

整改顺序

  1. P0：把 recent exact 从固定 turn 数改为 token-bounded policy。 权威 digest 应能覆盖一个异常巨大的已结算 turn；当前未结算 live tail 也需要按工具结果 offload/rolling digest 控制。
  2. P0：修复 compaction 与 quality gate 的权威同步。 compaction 后必须基于 active context 重建 protected refs；当 projected input 已低于 ceiling 时，不得继续被已归档 raw refs 永久锁死。
  3. P0：保证被拒绝 prompt 有终态。 compaction 成功后自动重放一次；仍失败时写入明确、可见、可恢复的错误事件，不能只留下 audit 和无答复 user message。
  4. P1：budget_pressure 强制 checkpoint。 不应等待 everyTurns；同时保证 fallback digest 不获得 raw omission authority。
  5. P1：按错误类别拆 retry budget。 concurrency limit 使用 provider/credential 级节流和较长 jitter；first-event timeout 与 stream stall 使用独立次数和 fallback 策略；UI 合并展示 retry train。
  6. P2：补齐 audit 与 continuation semantics。 持久化 requiredTokens/selectedInputTokens；将“进度如何/什么进度/压缩完了吗”识别为当前会话连续请求。

错误类型独立退避 concurrency limit 不消耗与 timeout 相同的快速 10-attempt train；recovery 元数据保持完整

最终判断

本会话不是“模型不会做大合并”，也不是“24 次工具都坏了”。Agent 已经完成高质量评估、隔离工作区、三个阶段 merge 和中间验证；Provider 的 12 次错误也全部自动恢复。真正阻断交付的是 Context Steady 的保护集合与压缩权威不一致： 它在最需要缩减上下文时保护了整个超长 turn，并在压缩成功后继续把已归档 raw history 当成必须精确保留的输入。 该 P0 修复后，才值得用同类 200+ provider-call 长任务重新验收 resume、compaction 和最终收口。
