San Self-hosting · Architecture & Footprint Audit

San / OMP 瘦身评估

社区说 OMP 相对 Pi “太臃肿”，这个判断同时指向三件不同的事：发布物更大、默认能力面更宽、每次模型请求携带更多固定上下文。对 San 而言，最值得先减的不是源码行数，而是常驻成本与单体发行耦合。

结论：保留 San 的差异化内核，拆掉“所有能力必须跟主二进制一起常驻”的假设。

San 的价值集中在 Context Steady、模型路由、代码智能、按需工具发现与可审计执行；其物理体积却主要来自 OMP 平台化能力、超宽工具栈、模型目录、浏览器/文档/导出依赖和兼容面。先做配置级瘦身和度量守门，再做发行架构拆分。不要直接删除有真实使用证据的 browser、MCP、eval 或代码导航。

“臃肿”的四层实测对比打包构成上下文税San 使用画像保留 / 拆分 / 删除执行路线已落地 preview验收门方法与边界

01 · Definition

“臃肿”不是一个指标，而是四种成本叠加

如果只盯二进制大小，会误删高价值能力；如果只说“功能多所以正常”，又会掩盖默认加载和发行耦合。需要分层判断。

物理体积

下载、更新、缓存和冷启动要搬运多少字节。由 Bun runtime、打包 JS、内嵌资源、原生模块共同决定。

运行时常驻

启动时间、峰值 RSS、初始化 I/O、后台进程。代码在二进制里不等于会执行，但静态图过宽会提高解析与初始化风险。

模型上下文税

system prompt、工具描述与 JSON Schema 每轮送入 provider。它直接消耗 token、延迟和注意力，是用户最容易感知的“脑内臃肿”。

产品与维护面

命令、模式、协议、兼容层和配置组合数量。它不一定变慢，却放大测试矩阵、文档漂移和故障面。

关键区分：工具“按需显示给模型”解决上下文税；工具“按需安装 / 独立发行”才解决二进制体积；功能“默认关闭”只减少运行时行为，不会自动被 Bun 从单体编译图中移除。

04 · Context tax

模型侧的“臃肿”比磁盘侧更直接：首次请求曾达到 Pi 的 17.3×

本地兼容 provider 捕获各 harness 的空白首请求，按紧凑 JSON 计字节。每组请求重复 4–17 次且字节完全一致。这里测的是当时运行配置，不是协议理论下限。

Harness请求总字节System chars工具数工具 JSON相对 Pi
Pi5,6612,50442,900 B1.00×
OMP74,85927,9581144,936 B13.23×
San（全量工具捕获）97,88715,3392081,949 B17.29×

San 捕获中最贵的 schema：browser 9.7 KB、edit 8.2 KB、launch 7.2 KB、eval 6.9 KB、debug 5.3 KB、todo 4.9 KB。工具数不是成本的好代理；一个 browser 就超过多个小工具总和。

已完成的正确瘦身：仓库级 .san/config.yml 已采用 tools.discoveryMode: all，常驻 read/bash/edit/write/glob/eval/grep/lsp，其余由 search_tool_bm25 激活。2026-07-15 实测 System tools 从 16,958 降至 10,186 tokens（−39.9%，每轮省 6,772）。用当前代码重新测 builtin schema，过滤前 15,118、过滤后 8,883 tokens（不含动态 MCP/扩展描述），降 41.2%。
仍有两个问题：一是激活在会话内累积、不会自动卸载，长会话会“工具再膨胀”；二是 tools/index.ts 仍静态导入所有工具类，因此上下文变瘦并没有让二进制变瘦。

06 · Product decision

保留差异化内核；把平台能力从“内建常驻”改为“可达但可卸载”

能力San 判断决定理由
Context Steady / ContextPlan / segment产品核心，解决长会话上下文稳定保留 core差异化价值高，静态归属小。
read / bash / edit / write / grep / glob / eval / LSP覆盖绝大多数真实调用保留 core79.9% 核心组；无需工具发现往返。
tool discovery + MCP client真实使用，连接无限外部能力保留 core用小发现入口替代全 schema 常驻。
San execution loop方向正确但当前再审计仍有 P0/P1 合同缺口保留，默认实验不可因不成熟而删，也不应默认扩张主路径。
Browser / document converters低覆盖、突发高价值、依赖重capability pack调用时安装/加载；保持 API 可达。
ACP / RPC / collab / HTML export面向外部客户端或专项工作流发行 profile不应让每个本地 TUI 用户承担完整协议面。
STT / TTS / tiny models / stats dashboard专项能力，已有 worker/on-demand runtime 设计独立 companion继续从主图剥离，而非只在运行时懒执行。
Autoresearch / workflows / commit agent当前样本无明确使用实验 pack保留可安装性，移出 core release gate。
Embedded full docs便利但复制成本固定移出二进制用版本化压缩资源、首次缓存或独立 docs 包。
重复/漂移产品合同真正维护臃肿删除无消费者设置、失真文案、重复模式必须清理；不是留下兼容 shim。
建议发行形态：san-core（TUI + context + core coding tools + MCP/discovery）与 san-full（当前完整体验）并存一个过渡周期；browser/docs/protocol/voice/experiments 作为能力包。默认安装 core，首次调用缺失能力时给出确定性安装动作，不允许静默降级或伪 fallback。

07 · Execution plan

按“立刻省 token → 建守门 → 拆发行图”推进

P0：修正度量与配置漂移，不改功能

已完成：measure-prompt-tokens.ts 只读加载真实全局/项目设置，应用运行时 discovery 筛选，并分别输出 initial/discoverable/all built-in 工具成本。在当前 San 项目配置下，tools.xdevDocs: catalog 将嵌入式 xdev 文档从 3,036 tokens 降至 131 tokens；固定首轮输入为 12,001 tokens。bundle metafile、二进制体积、启动和 RSS 基线也已建立。

P0：让工具 active set 有生命周期

保留 8 个项目 essential；专项工具在最近 N 轮未使用后可卸载，session 持久化“已发现”与“当前活动”两种状态。先做观察模式，证明不会造成反复 search 抖动。

P1：建立 core/full 两个可运行编译图

不要在 tools/index.ts 里静态 import 所有 factory；用构建期 profile 生成 registry，使未选能力没有静态 edge。CLI command table虽用动态 import，但 Bun 单文件编译仍会收进可达 chunks；profile 必须从入口图层切断。

P1：先拆四个边界清楚的 pack

优先 browser、document conversion、protocol adapters（ACP/RPC/collab）、voice/tiny/stats。每个 pack 必须有明确 manifest、版本兼容、安装缓存、完整错误语义与 smoke probe。

P1：瘦 model catalog

不手改生成的 models.json。改生成器/descriptor：core 内置推荐与常用 provider 的最小索引，完整 catalog 版本化下载并校验，离线时使用内置子集。目标先拿掉 2.26 MB 单文件与不必要生成 client。

P2：清理维护面而非追逐每个 KB

用真实命令遥测与发布 profile 决定哪些命令移包。合并重叠配置/模式，删除无消费者设置。不要为了二进制数字牺牲 TUI、LSP、MCP 或 San context 核心。

建议的 3 阶段目标

阶段 A · 1 个发布周期

当前 full 行为不变；项目级 discovery 固化；建立四维基线和 CI 预算。目标：首轮工具 tokens ≤ 9K（不含用户 MCP 指令），无核心工具额外发现。

阶段 B · Core preview

产出 san-core，从编译图切出 browser/docs export/voice/ACP/RPC/experiments。目标：[INFERENCE] bundle JS ≤ 20 MB，二进制 ≤ 110 MiB；所有被拆能力能显式安装并通过 smoke。

阶段 C · 默认切换

真实 dogfood 至少 30 个不同任务；core 的任务成功率与 full 差异 ≤ 2pp、p50 startup 改善 ≥ 15%、首请求固定 tokens 改善 ≥ 35%。达到门槛后 core 才成为默认。

09 · Acceptance gates

瘦身必须证明“更轻且没有更笨”

Gate A · 物理与启动

  • 同 target、同 Bun、同签名策略比较。
  • 记录 binary bytes、bundle metafile、模块数、冷/暖启动。
  • core 二进制预算 ≤ 110 MiB；后续每次增长 >1% 需归因。

Gate B · 上下文

  • 空首轮 active tool schema ≤ 9K tokens。
  • 长会话工具卸载后无 provider tool_choice 400。
  • 发现往返率、重复发现率、每轮 schema tokens 可观测。

Gate C · 行为完整

  • read/edit/bash/eval/LSP/MCP/context steady 全合同通过。
  • 每个外置 pack 有安装、加载、升级、离线错误 smoke。
  • 禁止 stub、静默 fallback、缺能力时假成功。

Gate D · 质量与 ROI

  • 同一任务集 core/full 各至少 3 轮。
  • 成功率差 ≤ 2pp；总 token 不因发现抖动上升 >5%。
  • 报告均值、方差、失败样本，不只报最佳 run。
明确禁止：直接从 full 删除 browser/MCP/eval 以追数字；把动态 import 当作已减 binary；手改生成的 packages/catalog/src/models.json；只跑单元测试不启动 core；用“功能默认 off”冒充可选安装。

  1. 版本不是完全同日同 commit：Pi 0.82.1、OMP 17.1.3、San 16.5.2。该设计用于回答产品量级，不用于归因某一 upstream commit。
  2. 启动/RSS 测 --version，没有 provider、MCP、TUI 交互和浏览器。完整会话可能扩大差异。
  3. bytesInOutput 是 Bun 的模块贡献估计；功能栈归属含共享依赖，删除净值必须以真实 profile build 复测。
  4. 会话样本高度偏向本仓库的重度 self-hosting；前四个会话占 71.9%。命令“未观察到”不等于用户群无人使用。
  5. 首次请求捕获代表当时全量工具配置。当前项目 discovery-all 已显著改善，因此它是历史问题规模和回归基线，不是当前每轮精确值。
  6. 二进制从候选模块字节机械相减的结果均标为 [INFERENCE]；Bun runtime、签名、资源布局会使真实结果不同。
