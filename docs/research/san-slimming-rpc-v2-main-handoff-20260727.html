Rationale

为什么做：San 的价值不应被“全平台能力常驻”拖累

问题一：发行图过宽

前置评估确认 San 与 OMP 处于同一体量级，明显重于 Pi。增量主要来自 coding-agent 平台图：PDF/文档转换、内嵌 harness 文档、Stats Web、HTML export、浏览器和兼容面等中型子系统叠加，而不是 Context Steady 等 San 差异化内核本身。

问题二：模型上下文税

模型每轮都为 system prompt 和工具描述付费。项目配置过去没有稳定利用文档目录模式；需要用运行时真实配置测量，而不是只比较源码或静态 schema。

问题三：RPC v2 客户端可见性不足

thinkingDeltas 虽可配置却未真正发出；agent 自己更新 todo 时客户端收不到；tool.completed 缺少 path/diff，客户端无法渲染有信息量的工具卡片。

问题四：慢客户端和损坏 sidecar 风险

流量突发、高基数 stream key、stdout 背压及 crash recovery 都需要有界行为。之前的状态文件和 lease/recovery JSON 依赖类型断言，损坏输入可能在恢复深处造成错误或跨 Session 污染。

核心决策：不把 San 退化成 Pi 的四工具模型；保留 Context Steady、核心 coding tools、MCP/discovery、plugin/Skills 和 legacy extension 兼容。先拆构建图与常驻资源，再用真实任务门槛决定默认发行切换。

RPC v2

RPC v2 结果：客户端信息完整、慢消费有界、恢复入口 fail-closed

流隔离

  • visible / thinking message delta 使用独立 channel。
  • tool progress 以 toolCallId 作为 stream key。
  • 不同 Run/Turn/stream 不会错误合并。

背压与限速

  • 持久事件绕过瞬态限流。
  • 瞬态事件按 key 保留最新值。
  • writer 和 limiter 都限制高基数 pending key；最旧流被淘汰。
  • 诊断暴露 pending、coalesced、dropped 和 stdout purity counters。

对外安全边界

  • 工具 preview、retry error、notice、intent 和 subagent metadata 统一脱敏。
  • 凭据与 home path 不应穿过 RPC 投影。
  • path/diff preview 有 4 KiB 边界和 truncation 标记。

恢复完整性

  • 校验 state schema、revision 和 lastSequence。
  • 拒绝跨 Session event 和领先 journal 的 watermark。
  • 过滤畸形 receipt/evidence。
  • 严格校验 lease PID/identity/timestamp/sequence 和 recovery reason/strategy。

Next work

接手后的建议顺序：先发布守门，再决定默认切换

  1. 把 core 纳入 CI/release matrix。至少覆盖 Darwin arm64/x64、Linux x64/arm64；每个 target 运行 --version 和 --smoke-test，记录 binary bytes 与 metafile。
  2. 建立体积预算。core 目标继续保持 ≤110 MiB；单次增长 >1% 必须在 CI artifact 中给出模块归因。当前本机值 94.97 MiB 提供约 15 MiB 缓冲。
  3. 做 core/full 真实任务对照。至少 30 个不同任务，成功率差 ≤2pp；同时记录 provider 请求数、首次固定 tokens、工具发现往返、重复发现率和 p50 startup。
  4. 完成工具 active-set 生命周期。当前项目首次固定输入仍为 12,003 tokens；需要在不增加高频发现往返的前提下，把 initial active tool schema 稳定压到目标范围。
  5. 做 RPC v2 跨进程 soak。使用真实客户端模拟慢 stdout、成千上万 stream keys、断电式 sidecar 截断和重连；断言 dropped/coalesced diagnostics 与最终 durable state 一致。
  6. 设计 capability pack，而不是永久依赖 full fallback。先定义安装、版本兼容、离线错误和升级合同，再考虑 browser/docs/export/experiments 的独立发行。
不要做的事：不要直接删除 browser、MCP、eval、LSP 或 legacy extension 支持；现有历史使用与 self-hosting 依赖说明这些能力有价值。先通过 profile 或 pack 降低常驻成本。
