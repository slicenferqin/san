San v0.5 确定性任务路由架构

研究结论、冻结契约与分阶段实施方案。目标不是再造一个“难度分类器”，而是把模型选择、执行编排、权限控制、预算分配和证据要求拆成可解释、可回放、不会越权的独立决策轴。

1. 结论

继续 v0.5；先改架构语义，再写路由器。

原规划的方向成立：任务复杂度不是单轴，路由必须能解释模型、effort、工具、编排和预算。但原来的 R0–R4 把“模型能力等级”和“执行控制等级”混在同一序列里，直接实现会导致权限与预算被自动升级、Workflow 审批边界被稀释、solo/team/council 被错误视为强弱顺序。

Classifier
Rules v1

首版只用确定性规则。LLM 只能在后续作为建议器，并且只能抬高质量建议，不能降低安全下限。

Authority
No grants

路由器只提出请求和收紧边界；不能授予工具、提高审批权限或突破已有预算上限。

Rollout
Off → Observe

默认关闭。先记录不执行，再做 child invocation enforcement，最后才考虑 root turn 和自动编排。

推荐将 v0.5 定义为四个组件：TaskProfile、纯函数 RoutePolicy、RouteApplication、相位边界上的 EscalationEvent。策略输出角色与约束，不直接选择具体 provider/id；具体模型仍由现有角色解析器和 registry 解析，并在应用阶段做兼容性校验。

2. 对原规划的必要修正

原语义问题冻结决策
R0 = 无模型 / 直接处理自然语言问候仍需模型；把“简单”误当成“宿主可确定回答”会产生假响应或特殊分支。host_direct 只允许宿主拥有确定语义的命令、状态页和静态帮助。普通问候进入 economy 模型类。
R1–R4 是单调强度等级R4 的本质是审批、隔离与交付确认，不是“更强模型”。高风险但机械的发布任务未必需要 reasoning 模型。拆成 modelClass、orchestration、workflowRequirement、capabilityRequest、budgetClass 五个轴。
升级模型、预算和权限自动扩大权限是越权；自动扩大硬预算破坏审批和成本上限。模型/effort 可在兼容范围内抬高；预算只能在预批准 ceiling 内重分配；工具集合只能取交集；超过 ceiling 必须审批或阻塞。
solo < team < council三者不是全序。team 解决独立切片，council 解决独立判断/复核；单个高风险 Workflow 可能只需要 solo。根据 decomposition 与 reviewRequirement 派生编排。不得把 council 当作“最强模式”。
显式覆盖整体优先于自动策略一个 model override 不应顺便覆盖工具、Workflow 和预算；一个 solo override 也不能取消强制复核。优先级按轴计算。模型显式值只影响模型；权限取交集；安全与证据要求取并集；预算取更小 ceiling。
模型不可用时 fallback当前 task 路径可退回父会话模型，但没有证明它仍满足模型类、上下文和能力要求。provider fallback 不是“升级”。每个候选都必须重新验证；不满足最低兼容条件则继续候选或明确阻塞。
preflight 一次判定执行前不知道真实文件范围和工具副作用；只靠 prompt 分类必然漏判。TaskProfile 是追加修订。初始请求、ContextPlan、工具提案、测试/审查结果都可形成新 revision；执行副作用前必须重算。
安全边界。 通用 bash、扩展工具和 MCP 工具本身可表达广泛副作用。v0.5 路由不能把“给了某个工具名”等价为“已经安全”。外部写入、不可逆操作和发布必须进入既有 Workflow 审批/隔离边界；路由器不是新的授权系统。

4. 目标与非目标

Goals
  • 同一规范化输入、policy version 和 authority snapshot 得到字节级可比较的决策。
  • 解释为什么选择某个角色、effort、编排、预算类、工具请求和证据要求。
  • 在真实证据出现时按相位重新评估，不在工具执行中途切换模型。
  • 保持 Workflow、task、San Loop、ContextPlan 的现有权威边界。
  • san.routing.mode=off 时不改变 v0.1–v0.4 的模型、工具、预算、session ledger 和 UI 行为。
Non-goals
  • 不训练通用难度分类器，不接入 learned router 作为首版安全决策。
  • 不由路由器生成或自动批准 Workflow。
  • 不重新实现 model registry、token accounting、ContextPlan 或 San Loop 状态机。
  • 不把所有简单请求都委派给 subagent；委派开销必须由 benchmark 证明。
  • 不承诺根据 prompt 文本完全识别 shell/MCP 的实际副作用。

5. 目标架构

用户输入 / 已批准 Workflow / 显式 task invocation
              │
              ▼
  ProfileBuilder ── host facts + request rules + ContextPlan + authority snapshot
              │                    │
              │                    └── 未知必须显式保留，不能猜成低风险
              ▼
  TaskProfileV1 (revision N, append-only)
              │
              ▼
  evaluateRoute(profile, authority, policy)  ← 纯函数；无 I/O、无时间、无 registry
              │
              ▼
  RouteDecisionV1
     ├── modelClass / requestedRoles / recommendedThinking
     ├── executionMode / workflowRequirement / reviewRequirement
     ├── capabilityRequest / budgetClass / evidenceRequirements
     └── disposition + stable reasonCodes
              │
              ▼
  RouteApplication
     ├── 解析具体 model + auth + context/capability validation
     ├── 工具取交集、预算取 min、审批验证 hash
     └── applied | shadow_only | approval_required | blocked
              │
              ▼
  AgentSession / task executor / San Loop / Workflow interpreter
              │
              ├── 工具提案、范围变化、ContextPlan、测试、review、provider failure
              ▼
  PhaseObserver → TaskProfile revision N+1 → EscalationPolicy → EscalationEventV1

5.1 五个独立决策轴

模型类

economy | balanced | reasoning。表示质量/上下文需求，不表示权限。映射到现有角色候选链。

执行编排

session | solo | team | council。由分解结构和独立复核要求决定，不是能力强弱全序。

控制要求

Workflow、approval、isolation、independent review、delivery receipt。升级只做集合并集。

能力请求

工具类别和 exact names 是请求/上限，不是授权。有效集合始终来自所有 authority 的交集。

预算分配

small | standard | extended 选择预定义 profile；有效值不得超过 session/Workflow ceiling。

命名决策。 不使用 fast/standard/deep 作为运行模式，因为现有 deep 是 council 的 legacy alias。模型质量轴使用 economy/balanced/reasoning，避免与 San Loop 语义碰撞。

5.2 权威关系

effectiveTools  = sessionGrant ∩ workflowManifest ∩ agentManifest ∩ routeRequest
effectiveBudget = min(sessionCeiling, workflowCeiling, routeAllocation)
safetyRequired  = union(hostFloor, workflowFloor, routeFloor, runtimeEscalations)
modelChoice     = scope-specific explicit selector ?? route role resolution ?? existing default

前三条是安全不变量。第四条只管理模型，不得反向改变前三条。

7. TaskProfile 构建

7.1 事实来源顺序

  1. 宿主结构化事实：slash command ID、是否为 managed/ad-hoc Workflow、已批准 manifest、当前 session authority、显式 task/agent/model 参数。
  2. 请求高精度规则：屏蔽代码块、引用和附件正文后，只分析主动句。识别明确 read/explain/edit/test/design/review/release/external-action；未命中保留 unknown。
  3. ContextPlan：直接读取 qualityGate.outcome、requiredTokens、selectedInputLimit 和 entry ref，不自行估算上下文。
  4. 工具提案：在产生副作用前，根据 exact tool + normalized args 添加 sideEffect/toolClass 信号并生成 profile revision。
  5. 运行证据：文件范围、测试失败、review verdict、provider failure、预算状态只在相位边界追加。

7.2 未知值默认

未知维度默认动作理由
cognitiveLoad至少 balanced，不进入 economy。质量不确定不能用于降配。
contextDemand / scope先 balanced；发现 repository/large 后修订为 reasoning。初始 prompt 无法可靠推断真实 blast radius。
sideEffectread-only ceiling；任何写入提案前重算。未知不能当作“允许写”，也不必把纯对话直接送审批。
reversibility当 sideEffect ≥ local_write 时按 conditional；工具提案证明 irreversible 后要求 Workflow。把恢复能力作为证据，不靠关键词乐观推断。
decompositionsession 或 solo；不自动 fan-out。多 agent 有固定延迟、成本和合并风险。

7.3 规则引擎边界

  • 规则必须是版本化静态数据，禁止从 settings 注入任意脚本；policy version 绑定规则内容 fingerprint。
  • 中英文规则必须共享 intent/effect 语义和同一 fixtures，不允许两套路由矩阵。
  • 引用文本、代码块和文件内容中的 “deploy”“rm” 不得单独触发高风险；用户主动句或真实 tool proposal 才可触发。
  • LLM triage 后续若引入，只能返回 TaskProfilePatch 建议；确定性 floor 与 host/tool facts 优先，模型建议不能删除事实或降低控制要求。

8. 确定性 RoutePolicy

8.1 决策顺序

1. 若是宿主拥有的确定命令 → host_direct；否则继续。
2. 计算 control floor：external_write / destructive / irreversible / release → Workflow required。
3. 计算 model class：先 cognitive/context floor，再应用 explicit model scope。
4. 计算 evidence floor：local write 至少 smoke/test；controlled 至少 approval + delivery receipt。
5. 根据 decomposition 与 review requirement 选择 execution mode；不是按模型类映射。
6. 选择 budget class；与 authority ceiling 比较，不能满足则 approval_required 或 blocked。
7. 计算 capability request；application 阶段与所有 manifest 取交集。
8. 排序/去重输出数组，生成 stable reason codes。

8.3 编排选择不是能力等级

模式选择条件禁止条件
session单条主线、交互式澄清、低 fan-out 价值。已要求独立复核但只有同一模型自检。
solo需要 San Loop 的计划/执行/监督状态机，但任务不可并行或 worker ceiling=1。把 solo 当作低风险/低模型的同义词。
team至少两个不共享写入热点的独立 slice，且并行收益大于调度开销。仅因为“任务很难”就 fan-out；同一文件/接口未冻结前并行写。
council明确需要独立 reviewer/oracle、反例、投票或不同专业视角。把 council 当成默认最高档；用多 agent 替代可执行验收。

9. 分轴优先级

轴优先级 / 合并规则冲突处理
Root modelsession user override > route role > existing default。显式模型缺少硬能力/context 时明确阻塞；质量建议只警告，不偷偷覆盖用户模型。
Child modelexplicit invocation > agent definition > route role > parent/default。每个候选仍做 hard compatibility；调用者显式值只覆盖模型轴。
Thinking显式 selector suffix > explicit invocation/agent thinking > route recommendation > role/model default。维持 task/executor.ts:2405–2409 的既有语义；不支持的 effort 由现有 clamp 处理并记录。
Tools所有 authority exact set 取交集。缺工具即 blocked/approval_required；禁止 union 和自动 discovery。
Write mode选择最严格模式：read_only < isolated_write < session_write。route 只能收紧。Workflow manifest 的 writeMode 不能被 route 放宽。
Budgetroute profile 与 session/Workflow ceilings 逐字段取 min。需要更大 allocation 且 ceiling 足够可自动重分配；超过 ceiling 必须审批。
Workflowhost/policy/approved artifact 的 required 条件取并集；只有 exact approval 满足。模型或 mode override 不能取消 Workflow requirement。
Evidence所有 requirement 取并集。缺少独立复核/交付回执不能用“模型更强”替代。
ContextContextPlan audit 是 authoritative source。hard_pressure 不允许模型继续盲跑；burst 只在 burst ceiling 内应用。

10. 路由应用与模型回退

10.1 RouteApplication 算法

  1. 验证 routing mode；observe 只写 application，绝不改变 session/task/Workflow 参数。
  2. 按当前 scope 的模型优先级得到 selector 或 role candidate chain。
  3. 调用现有 resolveModelRoleValue/resolveRoleSelection，不复制 fuzzy/exact matching。
  4. 对候选检查有效凭据、必要 tool support、vision（若需要）、ContextPlan requiredTokens ≤ model context allowance。
  5. 若失败，尝试同一候选链下一项；provider retry fallback 也执行同样检查。
  6. 将工具集合取交集、writeMode 取最严、预算逐字段取 min。
  7. 若 Workflow required，验证 approval ref、source hash、permission manifest hash、scope key；不匹配即 approval_required。
  8. 持久化 concrete resolution、catalog fingerprint、authority fingerprint 和 fallback index，再启动执行。

10.2 Root turn lease

现有 AgentSession 的 model 是会话状态，用户切换会写 model_change。自动路由若直接调用同一路径，会把临时决策伪装成用户选择，并让 resume 把最后一次自动模型当成默认值。因此 root enforcement 必须先引入逻辑租约：

interface RoutedTurnLeaseV1 {
  turnRef: string;
  applicationEntryRef: string;
  baselineModelSelector?: string;
  effectiveModelSelector: string;
  effectiveThinking?: "minimal" | "low" | "medium" | "high" | "xhigh";
  state: "active" | "completed" | "aborted";
}

// 不写用户 model_change；route_application 是唯一审计来源。
// turn 结束后清除逻辑 lease。下一 turn 重新计算；manual baseline 不被覆盖。
// resume 未完成 turn 时从 application 恢复；已完成 turn 忽略旧 lease。
发布顺序。 在 RoutedTurnLease、resume 和 provider cache/session reset 路径验证前，不启用 root model auto-switch。第一轮 enforcement 只作用于新建 child invocation，避免污染主会话语义。

10.3 明确失败，不做“可用就行”

  • economy 找不到模型：可退 balanced/default，但记录 fallback；不能伪造 host_direct。
  • reasoning 找不到满足 context/capability 的模型：阻塞或接受用户显式模型；不能无提示降到 smol。
  • auth fallback 到父模型：仅当父模型通过同一兼容校验；否则继续候选或失败。
  • ContextPlan hard_pressure：不通过增加 output budget 掩盖；先走 Context Steady 恢复或阻塞。
  • Workflow tool 缺失：不启用 discovery；要求新的 exact approval/manifest。

11. 升级状态机

11.1 触发点

只允许在以下边界重算：preflight 完成、工具提案执行前、ContextPlan 生成后、worker batch 完成后、测试/检查完成后、supervisor review 后、provider attempt 失败后。禁止在 tool call 正执行时换模型、工具集合或 writeMode。

11.2 触发与处置矩阵

Trigger自动动作不得做
scope_expanded修订 profile；module→repository 可提升 modelClass/context budget。扩大 exact tools 或 Workflow scope。
side_effect_increased增加 workflow/isolation/approval；在副作用前暂停。因为任务已开始就继续执行。
context_burst_required若预批准 burst ceiling 足够，切 burst；必要时选择更大 context 模型。突破 burst ceiling。
context_hard_pressure阻塞推理并请求 Context Steady 恢复；记录 hard_pressure。静默截断必要证据。
verification_failed同配置最多一次定向修复；再次失败可提升 modelClass/effort 或增加 review。无限 retry。
review_needs_fix / evidence_gap保留证据要求，追加修复 phase；必要时独立 reviewer。用更强模型替代缺失证据。
model_output_invalid同模型一次 schema retry；再失败提升模型类。接受无效 structured output。
provider_unavailable同最低条件内 fallback；记录 RouteApplication。把 provider fallback 计作安全升级或降配。
budget_exhausted在既有 ceiling 内重分配；否则 approval_required/blocked。自动提高硬 ceiling。

11.3 单调性与停止条件

  • modelClass 只允许 economy→balanced→reasoning；effort 只允许上升或保持。
  • safety/evidence requirements 只允许集合并集。
  • effective tools 不得增加，除非出现新的批准 authority snapshot；新增 approval 后形成新决策，不算旧决策自动放权。
  • orchestration 不是全序；变化必须有 independent_slices 或 independent_review reason。
  • 每个 root turn / Workflow run 最多 2 次自动升级；相同 fromDecision + trigger + evidenceFingerprint 去重。
  • 达到上限、再次验证失败或需要新权限时必须进入 limit_reached、approval_required 或 blocked，不能静默降级。

export interface ToolRouteDescriptorV1 {

    reversibility: Reversibility;

// 无 classifier 的通用工具按 potentialClasses 处理。
// bash/MCP 不因“名称看起来只读”获得安全结论；受控副作用仍要求 Workflow。

这是 enforce controlled routes 的前置条件，不是 observe mode 的前置条件。

13. 审计与回放

13.1 CustomEntry 设计

  • san.routing_profile：append-only profile revision，引用 request/tool/context/test entries。
  • san.route_decision：纯 decision、policy version、input fingerprint、profile entry ref。
  • san.route_application：具体 model、thinking、fallback index、tools、budget、authority/catalog fingerprints、outcome。
  • san.route_escalation：trigger、evidence、delta、disposition、from/to decision refs。

这些数据默认不直接进入 LLM context。需要给 commander/supervisor 时，像现有 San Loop role packet 一样渲染最小视图；原始 ledger 保持审计用途。

13.2 Replay 定义

  1. 从 decision record 读取 profile entry、authority snapshot、context snapshot、policy version。
  2. 对数组排序和规范化 JSON 后重算 input fingerprint。
  3. 运行对应版本的纯 evaluateRoute，比较完整 RouteDecisionV1。
  4. 具体模型只与保存的 catalog/authority snapshot 做 application replay；当前 catalog 的重新解析属于“re-evaluate”，不能冒充 replay。
  5. 未知 schema/version 保留可读，不参与当前策略重放，和现有 session 兼容策略一致。

14. 发布阶段

阶段行为退出条件
P0：contracts + fixtures只实现 types、normalization、pure policy、ledger parser；无 session 接线。fixtures 100% deterministic；contract review 通过。
P1：observe主会话和 child invocation 计算 profile/decision/application，记录 shadow_only；不改模型、effort、工具、预算、模式。真实 traces 可解释；critical under-route 为 0；router overhead 达标。
P2：child enforcement只对新建 task/Workflow child 应用 model role、thinking recommendation、strict tools 和更小 budgets；不改 root model，不自动启动 San Loop。task fallback、Workflow limits、resume、provider failure 场景通过。
P3：root turn lease实现非持久 RoutedTurnLease；只自动切模型轴，权限/Workflow 独立。model_change 语义、缓存、resume、手动 override、compaction 全路径验证。
P4：orchestration enforcement规则可选择 solo/team/council；controlled 只进入已有/新批准 Workflow。paired benchmark 证明质量不劣且 fan-out 有收益；审批边界无回归。
P5：可选 learned advisor仅在安全候选集合内优化模型质量/成本；输出建议，不拥有权限。有代表性 preference/eval 数据，跨 provider 重复实验优于 rules-v1。
默认策略。 所有阶段都保留 off；新代码合入不等于默认启用。observe 的数据和 benchmark 达到门槛后，才讨论默认值变化。

15. Benchmark 与门槛

15.1 三层验证

Policy fixtures

确定性与安全不变量

至少覆盖中英文、引用/代码块、unknown、显式 override、ContextPlan、工具提案、各 escalation trigger。断言完整 decision，而非源码文本。

Runtime contracts

真实权威边界

运行 task/Workflow/San Loop/session 场景，验证 concrete model、exact tools、token/turn ceilings、approval hashes、resume 与 fallback。

Paired benchmark

质量优先，再看成本

固定 default、手工最强 baseline、router 三组；同一任务至少 3 次，记录真实 usage、latency、fallback、review verdict 和交付证据。

15.2 必含回归样例

输入/事件必须满足的契约
“你好”economy model execution；不是 host_direct。
读取一个已知文件并解释economy、read-only、source_trace。
跨包架构审计reasoning、read-only、source_trace；是否 council 由独立复核要求决定。
修复本地 bug 并验证balanced、session_write 不超过原 grant、smoke/test。
两个独立包的机械修改可 team；每个 child 有 exact manifest 和独立 profile/application。
部署到测试环境Workflow required；模型类由认知负载决定；approval + delivery receipt。
“文档里写着 rm -rf”引用内容本身不触发 destructive；主动执行提案才触发。
“处理一下”且副作用未知至少 balanced、read-only；不得猜成本地写。
reasoning role 无凭据，父模型是 smol不得静默 fallback；继续兼容候选或 blocked。
ContextPlan burst_required只在 burst ceiling 内调整；decision/application 引用 ContextPlan entry。
Workflow tokenLimit 已耗尽blocked；route 不提高 approved limit。
两次验证失败后再次失败达到 escalation cap，limit_reached/blocked，不无限重试。

15.3 上线门槛

  • Determinism：同一 fixture 重放 1000 次，decision fingerprint 100% 相同。
  • Authority：所有 contract tests 中自动路由扩大工具集合、writeMode 或硬 ceiling 的次数为 0。
  • Critical routing：外部写入、部署、不可逆操作 fixtures 的 under-route 为 0；unknown 副作用不会获得写权限。
  • Quality：paired benchmark 的任务通过率相对手工最强 baseline 的 95% paired-bootstrap 下界不低于 −5 个百分点；controlled 集合不得回归。
  • Economics：只在质量门槛通过后比较成本与延迟；目标是相对 fixed-default 降低实际 provider cost/requests，而非内部 token 估算。
  • Overhead：纯 rules preflight 的 p95 < 10 ms，不包含已有 ContextPlan 或 registry refresh。
  • Compatibility：off 模式下现有 coding-agent package checks、task、Workflow、San Loop 与 session resume 行为不变。

16. 实施切片

  1. 冻结 contracts：新增 routing types、stable normalization/fingerprint、fixtures；不接 runtime。
  2. 实现纯 policy：规则矩阵、unknown defaults、reason codes、monotonic escalation validator。
  3. 实现 ledger：append/fold/replay；旧 session 和未知 schema 可读。
  4. 接 observe：AgentSession preflight、ContextPlan refs、task invocation application snapshot；验证零行为变化。
  5. 补 model compatibility：复用 resolver；auth/retry fallback 每次重验并记录。
  6. 接 child enforcement：route envelope→task executor/Workflow bridge；exact tools 与 budget min。
  7. 补 tool descriptor：先覆盖内建高风险工具和 Workflow；未知扩展保守处理。
  8. 实现 RoutedTurnLease：root auto model、manual override、resume、provider session/cache。
  9. 接 San Loop：决策 ref、现有 mode/options、相位升级；不复制 runner 状态机。
  10. 运行 paired benchmark：满足门槛后才开放 enforce；最后更新 coding-agent CHANGELOG。

这些切片严格有依赖：P0/P1 可独立验证；root lease 和自动 orchestration 不应与基础 policy 首次提交混在一起。

17. 验收标准

Correctness
  • 决策纯函数可回放。
  • unknown 不降配/放权。
  • provider fallback 保持硬兼容。
  • ContextPlan 是唯一 context authority。
Safety
  • 自动路由不授予工具。
  • Workflow required 不可被 model/mode override 取消。
  • 预算不突破 approved ceiling。
  • 升级有硬上限和去重。
Compatibility
  • off 模式零行为变化。
  • 显式 model/thinking 优先级保持。
  • San Loop ledger/status 保持。
  • Workflow input hash/hard limits 保持。
Evidence
  • observe traces 含 profile/decision/application。
  • 每次升级引用真实 evidence entries。
  • benchmark 记录实际 usage 和 provider。
  • 质量先过门槛，再宣称节省。
最终 Definition of Done。 不是“能为几个 prompt 选模型”，而是：从请求事实到具体执行的每次转换都有可追踪契约；模型不可用、范围扩大、权限不足、证据失败时都能停止或升级；关闭开关后旧系统行为完全不变。
